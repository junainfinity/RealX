# Screen Coverage Matrix

**Every product-map requirement mapped to the nodes that build and test it: 91 screens, 22 journeys (J01 to J21 plus J22 from founder decision D04), 22 gates, 27 modules and 14 state machines. Every screen, journey, gate and state machine has at least one node in the graph; M15 Lending and liquidity is excluded on purpose. 38 screens are drawn in full in the design prototype, 8 are drawn in part and 45 are not drawn at all. The design-extension nodes [[A50 - Design extension A- investor and sponsor screens not in the prototype|A50]] and [[A51 - Design extension B- operator console screens not in the prototype|A51]] draw the 53 partly drawn and undrawn screens and the drawn-screen supplements, and the founder reviews them at HG-REVIEW.**

**Source.** This note is generated by `06 Evidence\Tools\app_plan\build_matrix.py` from the canonical graph `Data/app-graph.json` (which already includes every change in `Data/graph-revisions.json`) and the canonical id list `Data/requirements-lists.json`; edit those, not this note. Screen-to-journey steps come from the product map's `data_flows.py`. Design status comes from the design analysis §3 and [[Design Integration]] §5. When the build runs, [[A00 - Charter and acceptance baseline|A00]] freezes this matrix as `docs/charter/coverage-matrix.json`, and [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised|A88]] re-checks every row against evidence.

**How the build runs.** Opus 5.5 (high) plans each node, Grok 4.7 (xhigh) builds it, and Opus 5.5 (high) does the node QA at every gauntlet loop in a fresh session. Fable 5.1 (high) runs the graph QA when a milestone's nodes have all passed ([[App Gauntlet]], decision D19). A requirement counts as covered only when its node passes its gate and its milestone passes the graph gate.

**How this plan was checked.** Fable 5.1 (high) wrote the 106-node graph and the specs A00 to A45 and A47 on 23 and 24 Sep 2026, and then reached its weekly limit. Opus 5.5 wrote the other specs and assembled the plan. A separate Opus 5.5 reviewer with no stake in the plan checked it; under D19 the remaining re-checks are Opus 5.5 (high) per spec and a Fable 5.1 (high) review of the whole plan. When the check run started, every node spec had had one independent check followed by a fix pass. 1 spec (A05) has passed a re-check; 105 still await their re-check, because the usage limit stopped the check run; A106 was added by the plan fixer on 24 Sep 2026 and has had no independent check yet. The check records are in `Data/checks/`.

## 1. Key and counts

- **Designed.** "Yes" means the prototype `<workspace>\design\RealX App.dc.html` draws the screen, and the prototype screen key is shown. "Partial" means the prototype shows part of the screen (a tab, a card or a few rows) and the design-extension node draws the rest. "No" means the screen is not drawn, so a design-extension node draws it. "No (D04)" marks the three screens added by founder decision D04. Drawn screens can still lack product-map components or states; A50 and A51 draw those as drawn-screen supplements under the parent screen's code ([[Design Integration]] §6).
- **Builds.** These are the UI nodes that own the screen's route and code. The design nodes A50 and A51, the preview node A61 and the launch node A89 also list screens in the graph, but they do not own screen code, so they are left out of this column.
- **Journeys.** These are the product-map journeys that pass through the screen. Every one of the 91 screens is on at least one journey.
- **Journey tests.** These are the end-to-end nodes that run those journeys: A61 (preview), A65 (sponsor), A78 (J20), A79, A80, A81, A82 (agent, J22), A84 (performance), A86 (testnet), A88 (P1 regression, three clean runs of all 18 P1 journeys), A89 (launch) and A94 (P2). Three checks run in addition to these for every screen. [[A87 - Design fidelity and accessibility pass|A87]] checks design fidelity and accessibility on every P1 screen and the partner portal pages, and the P2 and P3 nodes re-run its harness. [[A100 - Agent-parity suite- every UI action has an API and MCP equivalent under the same gates|A100]] proves that every UI action has an API and MCP twin under the same gates. Each UI node also tests its own state matrix.
