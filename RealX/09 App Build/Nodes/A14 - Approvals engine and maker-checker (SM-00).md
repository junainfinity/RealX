# A14 - Approvals engine and maker-checker (SM-00)

**The one place every privileged action passes through: an `ApprovalRequest` with a canonical payload hash and an `APR-<yyyymmdd>-<base32>` id, approval policies as versioned data, segregation of duties that excludes the maker through every route, hardware-key decisions that a token can never satisfy, act-first-ratify-within-2-h for protective actions, and an `AUTO` path that fires only on an exact hash match, so that nothing moves money, supply or holdings without an approval id that custody, the register and the audit chain all share.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops).

## Build brief

This node is API-only: module `approvals` in the Fastify monolith (`services/api/src/modules/approvals/`, with its worker jobs registered from the same folder through A09's job registry). It has no screens of its own. ADM-30, the approval chains on SPN-09, SPN-11, SPN-14, ADM-03, ADM-06 and ADM-15, and the custody signing screen ADM-14 are built by their owning UI nodes on top of this module's API. Every rule below is enforced in the API, never only in a screen, and every read contract is in the OpenAPI document from the first commit so `packages/sdk` and the MCP tool catalogue (A12, A104) see it before the engine passes. The only source of time is A09's injectable clock; `Date.now()` and argument-less `new Date()` are forbidden in the owned path and grepped by `npm run verify`.

**Data and identifiers**

- `approval_requests`, one row per privileged action: `approval_id` in the form `APR-<yyyymmdd>-<6 base32 chars>` (Crockford alphabet, uppercase, no I, L, O or U; the date in `Australia/Sydney` civil time; generated server-side, collision-checked, never client-supplied); `tenant_id`; `action_code` (from the action catalogue in `packages/domain`, for example `distribution.run.approve`, `allocation.mint`, `register.adjust`, `token.pause`, `withdrawal.release`, `kyc.override`, `listing.go_live`, `policy.change`, `agent.token.create_staff`, `agent.token.create_sponsor`, `agents.traffic.kill_switch`); `policy_code` (`4E`, `4E+Q`, `6E`, `6E+Q`, `SGL+R`, `AUTO`); `policy_version`; `object_ref` (type plus id, exactly one per request); `payload_canonical` (sorted-key JSON, integer cents and whole units, no floats, no whitespace, strings in UTF-8 NFC); `payload_sha256`; `maker_principal` (human id, or agent or token id plus `on_behalf_of` human id); `maker_identity_set[]` (see SoD); `required_checkers[]` (role sets resolved to eligible user ids at submit time); `precheck_result` with the rule-pack version and `GateEvaluation` ids; `risk` (`high`, `medium`, `low` from the policy row); `expires_at` (the decision TTL; see Expiry); `timelock_until`; `execution_deadline` (`(timelock_until` or, for rows without a timelock, `approved_at) + execution_grace_hours`; the same instant A15 uses as the attestation expiry); `ratify_by` and `ratification_state` (`n/a`, `pending`, `ratified`, `lapsed`); `trigger_ref` (set only on a system-triggered `SGL+R` act); `custody_op_id`; `state` (SM-00); plus the standard `tenant_id`, `created_*` and `updated_*` columns under RLS (A04).
- `approval_decisions`, one row per checker act, insert-only: `decider_id`, `role_at_decision`, `verdict` (`approve`, `reject`, `veto`, `cancel`, `act`, `ratify`), `reason_code` (mandatory on `reject`, `veto` and `cancel`), `credential_kind` (`webauthn_hardware` or `auto`), the raw WebAuthn assertion (client data hash, authenticator data, signature, credential id), `fresh_assertion_id` (A11's single-use `FreshAssertion` row; unique across the table except that one bulk-decide assertion appears on each decision row of that one batch, recorded with `bulk_batch_id`), `decision_digest` (see Decision binding), `ratify_by` (written on the `act` row only, so the deadline lives in an insert-only row), `trigger_ref` (system acts only), `acknowledged_warnings[]`, `verified_at`. One check constraint governs the credential: `(credential_kind = 'webauthn_hardware' AND assertion IS NOT NULL AND fresh_assertion_id IS NOT NULL) OR (credential_kind = 'auto' AND decider_id = SVCA AND assertion IS NULL AND (policy_code = 'AUTO' OR (policy_code = 'SGL+R' AND verdict = 'act' AND trigger_ref IS NOT NULL)))`. No other combination can be inserted.
- `custody_ops` (columns here; A15 owns behaviour): `UNIQUE(approval_id)` so one approval id binds exactly one custody op, and a `consumed` flag set in the same transaction that records `signed`; a second op for the same approval id is refused by the constraint (`APR_CUSTODY_OP_EXISTS`).
- Decision binding: every hardware-key act on a request (`decide`, `act`, `ratify`, `veto`, `cancel`) uses A11's fresh-assertion primitive, never the raw payload hash. The module computes `decision_digest = sha256(approval_id || payload_sha256 || verdict)` and calls A11's `fresh-assertion/options` with that digest as the payload hash and purpose `approval_decide` (or `approval_act`, `approval_ratify`, `approval_veto`, `approval_cancel`); A11 derives the challenge `sha256(server_nonce || digest || purpose)`, keeps it short-lived and marks it consumed on verify. Because the approval id and the verdict are inside the digest, two requests with byte-identical payloads (for example a resubmission after expiry or rejection) never share a challenge, and an approve assertion cannot be replayed as a reject or on another request. A consumed or expired fresh assertion is refused with `APR_ASSERTION_INVALID`; a digest that does not match the request's current hash, id or the verdict sent is refused with `APR_CHALLENGE_MISMATCH`.
- `approval_policies` as versioned data, seeded by A03 from the maker-checker rows of the product map's D-sections: `action_code`, `policy_code`, `maker_roles[]`, `checker_role_sets[][]` (one set per required checker, for example `[[CFO],[CCO]]`), `ratifier_roles[]` (for `SGL+R`), `applies_when` (a predicate that selects this row over the other rows of the same action code; see below), `tier_label` (the name another node uses for the row, for example A16's `4E_SECOND_APPROVAL`), `ttl_hours` (default 72), `timelock_hours`, `execution_grace_hours` (default 24; data, read by A15 for the attestation expiry), `ratify_hours` (2 for `SGL+R` unless the product map names another window), `protective` (only these action codes may use `SGL+R`), `system_trigger_allowed` (the row accepts an `SVCA` act with a `trigger_ref`), `reversible` (default `false`; see Ratification lapse), `revert_action_code`, `bulk_allowed` (true only where `risk = low`), `custody_vault` (V1..V7 or none), `effective_from`, `version`, `supersedes`.
- `applies_when` is a small predicate vocabulary stored as JSON data, evaluated on the frozen canonical payload and on facts resolved at submit: comparisons on integer fields (`amount_cents gt|gte|lte|lt <int>`, `variance_bps gte <int>`), booleans resolved by named resolvers (`from_locked_allocation_file`, `destination_allowlisted`, `trustee_countersign_required`, `track = retail`, `tenant_owner_count = 1`), and `all`/`any`/`not`. Rows of one action code must be mutually exclusive and exhaustive over the vocabulary; a seed test enumerates the boundary values of every numeric predicate and asserts exactly one row matches each. A conditional checker in the product map is a separate row, not code: mint or batch mint `4E+Q` TOKO → CFO when `from_locked_allocation_file`, and CFO + CCO when not; forced transfer and register adjustment add the trustee checker set when `trustee_countersign_required`; retail-track rows (P2) add the external RE (X-RE) set when `track = retail`; sponsor-side rows naming SP-OWN fall back to RealX PART or SECO when `tenant_owner_count = 1`.
- Seeded money tiers (integer cents, boundaries exact to the cent; A16's configuration keys `ledger.withdrawal.auto_max_cents` and `second_approval_cents` feed the withdrawal rows so there is one source):

| Action code | `applies_when` | Policy | Maker → checkers | `tier_label` |
|---|---|---|---|---|
| `distribution.run.approve` | `amount_cents lte 100000000` and `variance_bps lt 2500` | `4E` | FINA → CFO (after SP-OWN tenant sign-off) | `standard` |
| `distribution.run.approve` | `amount_cents gt 100000000` or `variance_bps gte 2500` | `6E` | FINA → CFO + CEO | `large` |
| `withdrawal.release` | `destination_allowlisted` and `amount_cents lte 2500000` and same-day sum `lte 2500000` | `AUTO` | System threshold → SVCA | `AUTO` |
| `withdrawal.release` | `amount_cents lt 5000000` and not the `AUTO` row's predicate (over A$25,000.00, a destination not allow-listed, or the same-day sum over the cap) | `4E` | TRSY or System threshold → CFO | `4E` |
| `withdrawal.release` | `amount_cents gte 5000000` | `6E` | TRSY or System threshold → CFO + a second RealX approver (CCO or CEO) | `4E_SECOND_APPROVAL` |

  "Above A$1M" in the product map (J06: "CEO too above $1m") means A$1,000,000.00 stays `4E` and A$1,000,000.01 is `6E`; a 25 % variance is `6E` at exactly 2,500 bps. The withdrawal boundaries follow A16 and A39 (A$25,000.00 `AUTO`-eligible, A$25,000.01 `4E`, A$50,000.00 second approval); the design's copy says "over A$50,000", so whether exactly A$50,000.00 needs the second approval is recorded as a founder question and changes one row, not code.
- Seeded timelocks, one value per action code, and the same value in A13's `sla_policy` and A15's P10 table: forced transfer 48 h, wallet recovery 48 h, owner-quorum agent or compliance changes 48 h (A15 P10 and A28), token contract upgrade 72 h (product map "Proxy upgrade after a 72 h timelock"), approval-policy change 24 h. The seed test asserts A14 `approval_policies` = A13 `sla_policy` = A15 P10 for every timelocked action code. Rows are immutable once effective; a change is itself an `ApprovalRequest` with `action_code = policy.change` under policy row 52 (SECO → CCO + CFO + CEO, `6E`, 24 h timelock, mirrored to A15's policy engine). Nothing about thresholds, role sets or hours is hard-coded; the approval TTL (72 h) and ratification windows are also A13 `sla_policy` rows and are covered by the same seed test.
- `AUTO` rows carry `auto_condition` as data (`file_sha256_equals_approved`, `destination_allowlisted_and_amount_lte`, `kyc_case_state_equals_approved`, `ratification_lapsed_for`). The engine approves an `AUTO` request only when the condition evaluates true on an exact hash or exact match, records the service account `SVCA` as the decider (no assertion; allowed only by the `credential_kind = 'auto'` branch of the check constraint), and marks the request for mandatory post-execution reconciliation. Any inexact match (a different file hash, one cent over, a destination not on the list) falls through to the human policy row for that action code, never to a refusal-free path.
- Hand-offs from A12, wired through ports only (this node never edits `modules/agent-access/`, which A12 owns): A12 exposes an `ApprovalPort` (token issue and activation, kill-switch toggle) whose default provider is A12's interim two-step, and its existing `KillSwitchProvider`. At boot this module registers its own `ApprovalPort` implementation from `modules/approvals/`: `agent.token.create_sponsor` (`4E`, SP-OWN of the same tenant who is not the requester; RealX PART or SECO when `tenant_owner_count = 1`) and `agent.token.create_staff` (`4E`, SECO ≠ requester), and `agents.traffic.kill_switch` as an `SGL+R` protective row (CCO or SECO acts; the other ratifies within 2 h; not reversible). This node's gate re-runs A12's token-creation tests against the registered provider and asserts that the interim two-step is unreachable once the provider is registered (a call that would take the interim path is refused and no token is activated without an `ApprovalRequest`). A12's spec must name `ApprovalPort`; if it does not at Specify, that is an upstream spec defect (escalate), not a reason to edit A12's path.

**SM-00 lifecycle, verbatim from A03**

- The state table is A03's, not this node's: the 14 catalogue states (`draft`, `submitted`, `prechecked`, `approved`, `queued_for_custody`, `signed`, `broadcast`, `confirmed`, `reconciled`, `closed`; terminal `rejected`, `expired`, `cancelled`, `failed`) and the 14 catalogue transitions from `data_states.py` (the `[*] --> draft` entry is the initial state, not a transition), plus two `extensions.ts` entries spelled with SM-00 states only:
  - (a) timelock window (architecture brief §6.2 step 10): `approved -> queued : timelock applies`, `queued -> queued_for_custody : timelock elapses`, `queued -> cancelled : veto`.
  - (c) exits the catalogue lacks, with this node as the source: `prechecked -> rejected : checker rejects` (the catalogue's checker reject leaves from `submitted`, which this design makes transient); `prechecked -> expired : TTL`; `queued -> expired : execution deadline passes`; `queued_for_custody -> expired : execution deadline passes before the custody quorum`; and the brief's "a maker or a checker can cancel before execution" as `prechecked -> cancelled : maker or checker cancels`, `approved -> cancelled : maker or checker cancels before custody accepts`, `queued -> cancelled : maker or checker cancels`, `queued_for_custody -> cancelled : maker or checker cancels before the first signature`. Nothing leaves `signed` or later except forward, `broadcast -> failed`, and never by cancellation ("cancellation after signature is impossible").
  - Resulting counts, asserted by the pass criteria: 15 states (14 plus `queued`), 25 trigger-labelled transitions (14 catalogue, 3 in (a), 8 in (c)) over 23 distinct ordered state pairs, so 225 − 23 = 202 ordered pairs (self-loops included) are refused.
  - A03's current spec pins its extension list to (a) and (b) and spells (a) with `approved-for-execution` and `vetoed`; A03 must be amended to this spelling and to add (c) before the node QA writes this node's oracle (upstream change; this node does not edit `packages/domain`). Every transition goes through `packages/domain` `transition()`; anything not in the table is refused with the engine's `SM_FORBIDDEN` wrapped as `SM00_ILLEGAL_TRANSITION`. This node adds no state and no transition beyond (a) and (c).
- `POST /v1/approvals` creates a `draft`: canonicalises the payload, computes `payload_sha256`, resolves the policy row from `action_code` plus thresholds and returns the resolved `policy_code`, checker role sets, `expires_at` preview and a non-binding precheck preview so the maker can fix problems first. Drafts are editable; every edit recomputes the hash. The maker cancels a draft (`draft -> cancelled`, the only cancellation the table allows).
- `POST /v1/approvals/{id}/submit` moves `draft -> submitted -> prechecked` in one transaction: it freezes `payload_canonical`, runs the binding precheck hook chain, and on a hard failure takes `prechecked -> rejected` with the reason codes (terminal; the maker drafts again and a new id is issued). On success it resolves `required_checkers[]` through A11's `eligibleCheckers(request)` at that moment, sets `expires_at = submitted_at + ttl_hours`, opens the A13 TTL clock, and writes audit `action.requested` and `action.prechecked`.
- `POST /v1/approvals/{id}/decide` takes a WebAuthn assertion over the fresh-assertion challenge described under Decision binding (purpose `approval_decide`, digest over approval id, payload hash and verdict); the module verifies it through A11's hardware-attested fresh-assertion verifier, stores the `fresh_assertion_id` on the decision row, checks eligibility now (decider in `required_checkers`, role still held, not in the maker identity set, no hard SoD conflict, not already decided on this request, break-glass session present where the action demands one), requires `acknowledged_warnings[]` to equal the warn codes present (else `APR_WARNINGS_NOT_ACKNOWLEDGED`), then records the decision. When every required set has an approve, the state becomes `approved` (or `queued` when `timelock_hours > 0`); one `reject` moves `prechecked -> rejected` (extension (c)) and writes the outbox event `approval.rejected` (A43, a downstream node, turns it into the maker's notice; this node only emits and tests the emission). Audit `action.approved` or `action.rejected` per decision. `POST /v1/approvals/{id}/cancel` (maker or eligible checker, reason code, hardware-key assertion with purpose `approval_cancel`) takes the extension (c) cancel transitions and is refused with `SM00_ILLEGAL_TRANSITION` once the first custody signature exists.
- Execution through the table for every policy code: on `approved` (or when `queued` elapses) the module creates the `custody_ops` row (`vault_code`, `target`, `selector`, `calldata_sha256`, `excluded_signers[]`) and asks the registered custody port for the EIP-712 attestation over `(approvalId, target, dataHash, expiry, makerId, cap)` with `expiry = execution_deadline`. This node never ships code that a dependent later edits: it exposes `registerCustodyPort(port)` and ships an in-module fake used by its own tests; A15 registers the real port from its own path. `approved -> queued_for_custody` fires when the custody adapter accepts the op; `signed`, `broadcast`, `confirmed`, `reconciled` and `closed` are driven by events from A15, A18 and the reconciliation module through `POST /v1/internal/approvals/{id}/transition` (service-principal auth only), and `closed` is refused unless a `reconciled` event exists (`APR_NOT_RECONCILED`). For rows without `+Q` (a KYC override, a policy change, a tenant suspension) the executor is the owning module's effector, registered with `registerEffector(action_code, {execute, revert, postcondition})`; it walks `queued_for_custody -> signed -> broadcast -> confirmed` in one transaction with one audit event per state, `confirmed` means the effect committed, `reconciled` means the postcondition passed (or a targeted reconciliation, where money or holdings moved), and an effector exception takes `broadcast -> failed`.
- `SGL+R` without an extra state: the single authorised actor submits with a hardware-key assertion (purpose `approval_act`) recorded as verdict `act`; the row's pre-approval checker set is empty, so `submitted -> prechecked -> approved` happens in the submit transaction, the effector or custody path runs at once (act first), `ratification_state = pending`, `ratify_by = act time + ratify_hours` is written both on the insert-only `act` decision row and on the request, and an A13 `ratification` clock opens. An API token, MCP tool or agent principal may create an `SGL+R` request only as a `draft` (for its human to act on); `submit` or `act` on an `SGL+R` row by any token or agent principal is refused with `APR_CHECKER_MUST_BE_HUMAN` before scope evaluation, and nothing executes.
- System-triggered protective acts (the product map's "Halt / resume resale: MKTO (auto on trigger)", and a Sev1 reconciliation break halting resale through A20 and A48) use the same `SGL+R` row when it has `system_trigger_allowed = true`: `SVCA` is the actor, the `act` row has `credential_kind = 'auto'` and a mandatory `trigger_ref` (the break, rule or monitor id that fired), and a human in `ratifier_roles` must ratify within `ratify_hours` exactly as for a human act. A row without that flag refuses an `SVCA` act with `APR_SYSTEM_TRIGGER_NOT_ALLOWED`. Restorative follow-ups (resume, unpause) are never system-triggered. `POST /v1/approvals/{id}/ratify` records verdict `ratify` from a person in `ratifier_roles` who is not the actor, not in the maker identity set and not a token; A13's clock is met and `ratification_state = ratified`. Only action codes flagged `protective` (freeze on sanctions match, pause, halt, tenant suspension, inflow freeze, kill switch) accept `SGL+R`; restorative actions (unpause, unfreeze, resume) are refused with `APR_SGLR_NOT_PROTECTIVE`.
- Ratification lapse: the worker job `approvals.ratification_sweep` (every minute, idempotent) finds requests whose `ratify_by`, read from the insert-only `act` decision row (never the mutable request column), is before now with `ratification_state = pending`, sets `lapsed`, writes audit `action.ratification_lapsed`, and raises Sev2 `approval.unratified` (owner CCO) through A13, escalating on A13's ladder. A lapse never lifts a protective act by itself: the product map puts every restorative action behind its own maker-checker row ("Unpause token … 6E+Q", "V3 pauser can only restrict; unpausing goes through V2"), and A28, A42 and A48 rely on that. For `token.pause` the lapse also opens a `draft` `token.unpause` request under the normal `6E+Q` row (CCO → SECO + CFO) for humans to decide; the token stays paused. Every seeded `SGL+R` row has `reversible = false`:

| `SGL+R` action code (product map row) | Actor → ratifier | `ratify_hours` | `system_trigger_allowed` | `reversible` | On lapse |
|---|---|---|---|---|---|
| `aml.sanctions_freeze` (Confirm true sanctions match; freeze) | MLRO → Ratification (CCO) | 2 | no | false | Sev2 alert only |
| `account.suspend` (Suspend account) | MLRO or CCO → the other | 2 | no | false | Sev2 alert only |
| `wallet.freeze` (Freeze wallet, sanctions path) | MLRO/CCO → the other | 2 | no | false | Sev2 alert only |
| `token.pause` (Pause token) | CCO / SECO / V3 pauser → Ratification | 2 | no | false | Sev2 alert + `token.unpause` draft (`6E+Q`) |
| `resale.halt` (Halt resale, P2) | MKTO or SVCA on trigger → CCO | 2 | yes | false | Sev2 alert only |
| `offering.halt` (time-boxed halt, J21 step 2) | CCO → board delegate | 24 | yes | false | Sev2 alert only |
| `treasury.inflow_freeze` (Global inflow freeze) | CCO or RE board delegate → Ratification | 2 | no | false | Sev2 alert only |
| `agents.traffic.kill_switch` and the tenant and user kill switches | CCO or SECO → the other | 2 | no | false | Sev2 alert only |

  The architecture brief's "auto-reverts where reversible" survives only as the mechanism: if the founder, on counsel's advice, marks a row `reversible = true`, the lapse creates one `ApprovalRequest` for its `revert_action_code` under the `AUTO` row whose condition is `ratification_lapsed_for = <original approval id>` (exact id match), executed by `SVCA`, exactly once. Which rows (if any) may auto-revert is recorded as a founder and counsel question under Human gates. The original request keeps its own state (an on-chain pause that happened is `confirmed` and reconciles; it is never rewritten as if it had not happened). The action codes above are the ones A03 seeds; if A03 spells a code differently, A03's spelling wins and the flags stay as listed.
- Timelock and veto: while `queued`, any eligible checker or the trustee may `veto` (reason code mandatory; hardware-key assertion with purpose `approval_veto`) which takes `queued -> cancelled` and instructs custody to refuse the approval id; the custody layer refuses execution before `timelock_until` unless a waiver `ApprovalRequest` (`court_order_waiver`, CCO + CEO, `6E`) references it. An A13 clock drives the elapse.
- Expiry has two clocks, never one TTL over the whole life. (1) The decision TTL, `expires_at = submitted_at + ttl_hours`, applies only to the pre-execution window: states `submitted`, `prechecked`, and `approved` before custody accepts the op. `approvals.expiry_sweep` (every 5 minutes, idempotent) takes `prechecked -> expired` or `approved -> expired` when `expires_at < now`; a `decide`, `cancel` or bulk decision in those states after `expires_at` is refused with `APR_EXPIRED`. When a timelocked request moves `approved -> queued` inside its TTL, the TTL clock is closed and no longer applies. (2) The execution deadline, `execution_deadline = (timelock_until` or `approved_at) + execution_grace_hours`, applies to `queued` and `queued_for_custody`: past it the sweep takes `queued -> expired` or `queued_for_custody -> expired` (no quorum reached) and instructs custody to refuse the id; A15's attestation carries the same instant as its expiry. After custody has accepted the op and a signature exists, neither clock applies: event-driven internal transitions (`signed`, `broadcast`, `confirmed`, `reconciled`, `closed`, `failed`) and ratification of an `SGL+R` act are never refused with `APR_EXPIRED`, so a late registry acknowledgement still closes the request. Each expiry cancels pending clocks, writes `action.expired` and the outbox event `approval.expired` for the maker's notice. Neither clock can be extended; the maker resubmits and a new id is issued.
- Bulk approve: `POST /v1/approvals/bulk-decide` accepts up to 50 ids and one A11 fresh assertion with purpose `approval_bulk_decide` over `sha256(verdict || the list of (approval_id, payload_sha256) pairs sorted by approval_id)`, so the nonce, every id and every hash are bound; the fresh assertion id is stored on each of the resulting decision rows and consumed once. It is refused whole (nothing applied) if any id is not `risk = low` with `bulk_allowed = true` on its current policy version, if the decider is in any id's maker identity set, if any id is expired, or if the set mixes tenants (`APR_BULK_NOT_LOW_RISK`, `APR_BULK_MIXED`).
- The SM-00 gaps are resolved in this spec, not deferred: extension (c) above closes the checker reject from `prechecked`, expiry of a request awaiting checkers, the no-quorum exit from `queued_for_custody`, the timelocked row that is never executed, and the brief's maker-or-checker cancel before execution. There is no fallback to the bare catalogue table: without (c), ADM-30's Reject has no legal transition, so the node would fail its own pass criteria. If A03 has not adopted (a) and (c) as spelled above when this node's Specify step starts, the Specify step stops and A03 is reopened. The oracle is written against the 25-transition table.

**Precheck hook interface (the rules engine plugs in here)**

- `registerPrecheck(action_code | '*', hook)` where `hook(request, context) -> { result: 'pass' | 'warn' | 'fail', code, detail, gates_evaluated[] }`. Built-in hooks shipped here: policy resolution; SoD (maker identity set not in any checker set; hard conflicts from A11's SoD table; FINA/CFO and VALO/MKTO exclusivity; SUPER never on money, custody or signer actions; custody initiator ≠ signer); custody function allow-list (asked of the registered custody port); supply guard (`sum(units) ≤ cap` for mints); recon-break guard (refuses new mint, burn, distribution execution and escrow release requests for a vehicle with an open Sev1 break, `APR_RECON_BREAK_OPEN`; asks whatever `registerReconGuard(guard)` holds); licence-perimeter guard (asks whatever `registerPerimeterGuard(guard)` holds); and the agent-authority gate G22 through A12's evaluator (mandate live, scope covers the action, per-action and daily caps, allowed vehicles include `object_ref`, time window open). The three ports are registration points, not stubs that dependents edit: A15, A20 (with A18) and A21 register their implementations from their own paths; until one registers, this module's default for that port is fail-closed (`warn` with code `APR_GUARD_NOT_REGISTERED` in local and test, and `fail` in any environment flagged non-local), and its own tests use in-module fakes. The G01-G21 hooks belong to A19, which registers them per action code through `registerPrecheck` from its own path; this node does not call A19. This node's gate proves the registry with a fake `fail` hook (the request ends `rejected` with the hook's code) and a fake `warn` hook (the decision is refused until the warning is acknowledged). A graph edge A14 → A19 is required so A19 can register against a passed engine and assert in its own pass criteria that every policy action code has its G01-G21 hooks registered (graph and A19 change, not made here). Results are stored on the request with the rule-pack version and every `GateEvaluation` id so the checker sees the simulation the maker saw and an audit can replay it.
- A `fail` ends in `rejected` at submit; a `warn` is shown to checkers and must be acknowledged in the decision.

**Segregation of duties through every route**

- The maker identity set is computed at submit and recomputed at every decision as: the maker human; every human the maker delegates to or is a delegate of (A11 delegations, both directions, active at either moment); the human behind any agent or token that drafted, edited or submitted the request; and every agent or token whose `on_behalf_of` is any of those humans. No member may appear in `required_checkers[]`, decide, ratify, veto or sign; the set is passed to A15 as `excluded_signers[]` (P9).
- Role changes mid-flight follow A11's rule: a role granted after the request was drafted makes nobody eligible on that request; a decider who lost the role before deciding is refused with `APR_ROLE_NOT_HELD`; a maker who gains a checker role stays excluded by identity. A11's role-change event re-resolves `required_checkers[]`; a request left with zero eligible checkers for any set raises Sev3 `approval.no_eligible_checker` to SECO through A13.
- Sponsor-side approvals: where the policy row names SP-OWN as a checker (listing send, distribution proposal, valuation submission, sponsor token creation), that checker is resolved inside the tenant under the same SoD; a sponsor agent may prepare, a sponsor human approves, and a second sponsor human is required where the policy says two people. RealX's platform CCO stays a required checker on every tenant offering (SoD #15).

**Agents and tokens (G22, aligned with A12)**

- A request created through an API token or MCP tool is accepted as maker only when A12's mandate evaluator passes; `maker_principal` records the token id and `on_behalf_of` the human; the audit event reads "agent <token prefix> on behalf of <person>"; the module writes the outbox event `approval.agent_submitted` (with `risk`) for every agent submission. A43 (sensitive-action notice to the person for `risk = high`) and A101 (anomaly scoring) consume those events later; they are downstream nodes, so this node's gate asserts the events are emitted with the right fields, not that anyone receives them.
- `decide`, `act`, `ratify`, `veto`, `cancel`, `bulk-decide` and custody `sign` refuse any token, agent or service-account principal with `APR_CHECKER_MUST_BE_HUMAN` before scope evaluation (the only `SVCA` decisions are the `AUTO` path and a system-triggered `SGL+R` act, both internal and never reachable through a public route), so a token with a hypothetical `approvals:decide` scope still cannot approve; a WebAuthn assertion is required on every decision and a token cannot produce one. Each refusal writes the outbox event `approval.agent_decision_refused` (token id, human, route). Every agent action on a request appears in the person's activity feed and in ADM-35's oversight view (read later by the owning UI node from the audit log).
- Every human-only route (`decide`, `act`, `ratify`, `veto`, `cancel`, `bulk-decide`) carries the OpenAPI extensions `x-realx-requires-human: true` and `x-realx-agent-never-checker: true`; A100 and A104 read those markers to keep the routes out of agent tools, so this node asserts the markers in its own OpenAPI document rather than asserting anything about the MCP catalogue.

**Read API for the UI nodes (all under `/v1`, cursor pagination, idempotency keys on writes)**

- `GET /v1/approvals?state=&risk=&tenant=&mine=checker|maker` returns the inbox shape the design's `ApprovalListCard` needs (id, age, risk, type, object, maker name and team or "System threshold"); `GET /v1/approvals/{id}` returns the detail shape: `checks[]` from precheck with gate refs and Pass, Done, Matched, Pending or flag states, the diff against the last approved payload of the same object, evidence document ids, other approvers and their status, TTL remaining, timelock, ratification state, custody op state, and the SoD note derived from the caller's relation to the request ("you are not the maker, so you can approve", "you are the maker", "already decided"). `GET /v1/approvals/{id}/audit` returns the request's audit events in chain order; `GET /v1/approvals/policies` the effective policy rows.
- Empty inbox returns `{items: [], next: null}` so the UI shows "Inbox clear."; a request that left the inbox returns 200 with its terminal state, never 404; a tenant user asking for another tenant's request gets 404 (no existence leak); unknown ids 404.

**Audit and errors**

- Exactly one hash-chained audit event per transition and per decision, written through A10's interface (`action.requested`, `action.prechecked`, `action.approved`, `action.rejected`, `action.acted`, `action.ratified`, `action.ratification_lapsed`, `action.vetoed`, `action.queued`, `action.queued_for_custody`, `action.signed`, `action.broadcast`, `action.confirmed`, `action.reconciled`, `action.closed`, `action.expired`, `action.cancelled`, `action.failed`) carrying `approval_id`, `actor_id`, `on_behalf_of_id` and before/after hashes.
- Alerts use only A13's catalogue codes: `approval.unratified` (Sev2, CCO, lapsed `SGL+R`) and `approval.no_eligible_checker` (Sev3, SECO). A seed test asserts that every alert code this module can emit exists in A13's `alert_type` table; a code missing there is an A13 data change, never a new string here.
- Error codes are stable strings listed in the OpenAPI document (`APR_MAKER_IS_CHECKER`, `APR_CHECKER_MUST_BE_HUMAN`, `APR_ASSERTION_INVALID`, `APR_CHALLENGE_MISMATCH`, `APR_ROLE_NOT_HELD`, `APR_EXPIRED`, `APR_POLICY_NOT_FOUND`, `APR_AUTO_CONDITION_MISMATCH`, `APR_SGLR_NOT_PROTECTIVE`, `APR_SYSTEM_TRIGGER_NOT_ALLOWED`, `APR_CUSTODY_OP_EXISTS`, `APR_GUARD_NOT_REGISTERED`, `APR_BULK_NOT_LOW_RISK`, `APR_BULK_MIXED`, `APR_RECON_BREAK_OPEN`, `APR_NOT_RECONCILED`, `APR_WARNINGS_NOT_ACKNOWLEDGED`, `SM00_ILLEGAL_TRANSITION`) returned with 403, 409 or 422 so the SDK and MCP server surface them verbatim.

## Node-specific challenges (node QA)

- **Assertion from another request or an earlier draft.** A checker approves with a valid fresh assertion made for a different request, for the same request before the maker changed an amount, or for the same request with the verdict `reject`: the decision must be refused with `APR_CHALLENGE_MISMATCH` (or `APR_ASSERTION_INVALID` for a consumed or expired assertion) and nothing recorded. The sharp case: two requests with byte-identical payloads (a resubmission after expiry); the approve assertion captured on the first is presented on the second and must be refused because the approval id is inside the digest. A decision row for a stale hash, another id or another verdict fails the node.
- **The maker hiding behind an agent and a colleague.** The original maker drafts through their agent token on their own behalf, a colleague submits from their own login, then the original maker approves: the identity-set resolver must trace draft authorship through the token's `on_behalf_of` and refuse with `APR_MAKER_IS_CHECKER`. If the approve succeeds, the node fails.
- **A scoped staff token with a replayed assertion.** A staff token holding every staff module scope calls `decide` with an assertion captured from its human's earlier decision: refused with `APR_CHECKER_MUST_BE_HUMAN` before any scope check, and exactly one outbox event `approval.agent_decision_refused` is written for A101 to consume later. A scope check that runs first, a missing event, or a 200, fails.
- **Ratification clock edited in the database.** The CCO pauses a token under `SGL+R`, nobody ratifies, and `ratify_by` on the request row is pushed forward by hand: the sweep must use the `ratify_by` recorded in the insert-only `act` decision row and the A13 clock, raise Sev2 `approval.unratified` at the original 2 h, and open exactly one `draft` `token.unpause` request under the normal `6E+Q` row; the token stays paused and no `SVCA` decision is written. A late alert, a second draft, or anything that lifts the pause without CCO → SECO + CFO fails. The same lapse on a sanctions freeze or an AML suspension raises the alert and changes nothing else.
- **Late but legitimate execution.** A 72 h-timelocked upgrade is approved at hour 71 of its TTL; at hour 143 the timelock elapses and the op executes, because the decision TTL closed at `approved -> queued` and only the execution deadline applies. A mint confirmed on chain at hour 60 whose registry acknowledgement arrives at hour 80 still walks `confirmed -> reconciled -> closed`. Any `APR_EXPIRED` in either case fails; so does a decision accepted on a `prechecked` request at 72 h 01 min.
- **Agent at the red button.** An investor-support staff token drafts an `account.suspend` request (allowed, as a draft for its human), then calls `submit` and `act`: both refused with `APR_CHECKER_MUST_BE_HUMAN` and nothing executes. Separately, `SVCA` acts on `resale.halt` with a recon-break `trigger_ref` (accepted, ratification clock opens) and on `account.suspend` (refused with `APR_SYSTEM_TRIGGER_NOT_ALLOWED`).
- **AUTO on a near-match.** An `AUTO` payout row is fed a file whose hash "matches" only after a Unicode NFC/NFD or key-order difference in the canonicaliser: the oracle plants both variants and expects `APR_AUTO_CONDITION_MISMATCH` unless the bytes are identical after canonicalisation and the hashes are equal; the same for an amount one cent over the allow-listed cap.
- **Bulk approve with a superseded policy row.** Fifty low-risk ids where one item's policy row was superseded to medium risk between listing and decision: the whole batch must be refused with the offending id named and none applied; the same fifty without it must succeed with exactly fifty decision rows and fifty audit events.
- **Confirmed on chain, silent register.** A request reaches `confirmed` but the registry never acknowledges, and a UI node calls the internal transition endpoint with `closed`: refused with `APR_NOT_RECONCILED`; the request must show `confirmed` with an open recon break, not success, and the design's "register sync queued" wording must map to that state.
