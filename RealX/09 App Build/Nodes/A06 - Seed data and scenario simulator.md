# A06 - Seed data and scenario simulator

**One seed script with a single as-of date (Wednesday 23 September 2026) that turns the design prototype's mock data into a consistent, gate-valid database, plus a deterministic scenario simulator (`packages/sim`) that generates investors, sponsors, offers, payments, distribution runs, agent principals and planted breaks from a seed string, so every later node, every hidden oracle and the Docker previews run on the same numbers.**

**Build status:** not started. **Milestone:** AM1 (moved from AM0 on 24 Sep 2026 because the seed now writes audit, passkey and token rows through A10, A11 and A12). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops).

**Depends on:** [[A04 - Database schema, migrations and row-level security]], [[A03 - State machines, gate codes, approval codes and permission matrix as data]], [[A08 - Sandbox adapter framework, config and phase flags]], [[A10 - Append-only hash-chained audit log]], [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]]
**Unlocks:** [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A49 - Money-path smoke through the SDK (AM3 exit and founder checkpoint)]], [[A61 - Docker Desktop preview of the investor app (AM5 exit)]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]]

There is no cycle: A06 only unlocks A23, A49, A61 and A99, and none of A03, A04, A08, A10, A11 or A12 depends on A06. The graph data (`Data\app-graph.json`) must carry the same edges and milestone.

**Oracle rule:** this is not an oracle node, so the node QA does not write hidden tests for the build to pass. Before the build starts, the node QA writes two things to `<workspace>\gauntlet\hidden\A06\` from this note alone: (1) an independent derivation script that computes every figure in the "Locked invariants" table from the design's mock data and the rules stated here, and (2) a planted-fault list (for example one approval role swapped, one lot in an unminted trust, one audit row out of order, one token above its owner's rights) that the Challenge step injects into a copy of the generated graph to prove `seed:verify` catches each fault. The builder never sees that folder. The nodes that consume the simulator where money moves (A49 and the register, ledger and reconciliation cores) carry their own hidden oracles, and those oracles compute from the seed, never from the design's or the product map's typed numbers.

## Build brief

### The clock, ids and determinism

- One constant `AS_OF = 2026-09-23T10:30:00+10:00` (Wednesday 23 Sep 2026, AEST; daylight saving has not started) lives in `packages/db/seed/as-of.ts` and is exported through the seed manifest. Every seeded timestamp is derived from it (the daily reconciliation run is `AS_OF` at 06:00, the Gympie Road break was detected 06:02, the order RX-ORD-55120 was placed the day before at 10:41, "oldest break 4h" and "21 days to valuation" are computed, never typed). No seeded event is later than `AS_OF`. The local run mode's fixed clock (`packages/config`, and A23's `CLOCK_AS_OF`) reads the same value so screens show the same relative times as the design.
- Relative ages are computed by one rule: under 1 hour, whole minutes rounded down; from 1 hour to under 24 hours, hours rounded half-up to the nearest hour; from 24 hours, whole days rounded down. With the `created_at` values fixed below (approvals inbox) and the break at 06:02, this rule gives the design's "2h" (APR-2291), "5h" (APR-2290), "1d" (APR-2286), "2d" (APR-2285) and "4h" (oldest break, APR-2292). The rule is a shared display helper (see Skipped cross-node items: A02 must own it); until A02 exports it, the seed's verifier carries the rule only to assert these five outputs.
- No wall clock and no `Math.random` anywhere in `packages/sim` or `packages/db/seed`. The simulator uses a seeded PRNG (xoshiro128** or mulberry32) keyed by a seed string (default `realx-baseline`); the same seed string, schema version and scenario name produce a byte-identical generated graph on any machine. The manifest records `seed`, `asOf`, `schemaVersion`, `scenario` and a `contentHash` over the generated graph in canonical order (the output of `generate()`, before loading). Credential material created at load time by A11 and A12 (passkey key pairs, credential ids, token lookups, secrets, Argon2id salts and hashes) is random by design, never comes from the seed PRNG, and is outside the content hash; `seed:verify` checks that every loaded row equals its graph row on every other column.
- Stable ids: investors `INV-00001…` with the design's named people fixed (Alex Morgan `INV-00841`, legal name "Alex James Morgan" so A22's exact-name persona table matches, PayID `alex.morgan.841@pay.realx.au`; Daniel Okafor `INV-00912`, legal name "Daniel Okafor"; the AML-118 subject `INV-00377`), orders `RX-ORD-nnnnn`, approvals `APR-nnnn`, custody ops `OP-nnnn`, AML cases `AML-nnn`, trusts by short code.
- Id ordering: the design block APR-2261 to APR-2292 and OP-7726 to OP-7731 keeps the design's numbers and is **not** time-ordered (APR-2270 and OP-7726 are dated 25 Jun 2026, APR-2261 21 Sep). The seed adds APR-2287, APR-2289 and APR-2292 inside that block for events the design implies. Every generated history id is allocated below the block (APR-0001 to APR-2199, OP-0001 to OP-7699) in time order. No id above APR-2292 or OP-7731 exists in the baseline, so the first id the running app allocates cannot collide.
- Wallet addresses are full 40-hex constants. One display rule applies everywhere: first 6 characters (including `0x`) + "…" + last 4. Alex's wallet is chosen so the rule gives the design's `0x7a3f…c91e`. The design strings `0x4b…19` (estate of H. Lowe), `0x9e…a2` (estate beneficiary) and `0x2c…7f` (AML-118 frozen wallet) are first 4 + last 2 and cannot come from the same rule; the seed picks addresses that begin `0x4b`, `0x9e`, `0x2c` and end `19`, `a2`, `7f`, so they display as `0x4bxx…xx19` style strings, and the design's short forms are not reproduced (resolution row below).
- Money is integer cents, units are integers, percentages are basis points; the seed uses `packages/domain` money and unit helpers for every derived figure and never re-implements arithmetic. A lint in the node fails on any `number` money column or any `parseFloat` in the two owned packages.

### The scenario simulator (`packages/sim`)

- Pure generator: `generate({ seed, asOf, profile, scenario })` returns a plain object graph (no database access). `load(graph, db)` writes it as the `realx_app` role through A04's `withTenant` and `withPlatform` helpers (`SET LOCAL` context per transaction), so row-level security checks every row's `tenant_id` exactly as for the API; it never connects as `realx_migrator` (reserved for `db:migrate`) or a superuser. Credentials go through A11 (passkey registration) and A12 (token issue); audit events go through A10's `audit.record`. `emitFixtures(graph, dir)` writes only files with a named consumer: `chain-state.json` (per-trust holder balances for the local chain, for A27's boot deploy) and `bank-balances.json` (the client-money account balances A23 compares with A17's sandbox `state()`); both consumers must name these files (see Skipped cross-node items). Registry, identity and bank outcomes come from markers in the seeded rows, not from emitted files. The seed script is `load(generate(baseline))` plus the invariant checks.
- Generators, each a small module with its own tests: investors (types individual, joint, SMSF, company, trust; wholesale, sophisticated, retail, foreign; KYC states across SM-01; classifications across SM-02; PEP and risk flags), sponsors and users, trusts and offers (SM-03, SM-04), orders (SM-05, including scaled-back, cancelled, expired), bank lines and payments (NPP delays, returned payments, third-party deposits, all through A08 markers), register versions and lots (SM-07 states), distribution runs with snapshots, withholding and exceptions (SM-08 states), approvals and custody ops (SM-00 states with policy codes from A03), AML alerts and cases (SM-11), complaints (SM-12), recovery and forced-transfer cases (SM-13), agent token requests and activity (issued through A12 at load), audit events (written through A10 at load).
