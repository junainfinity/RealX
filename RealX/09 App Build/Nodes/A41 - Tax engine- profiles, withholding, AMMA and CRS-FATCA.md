# A41 - Tax engine: profiles, withholding, AMMA and CRS/FATCA

**The tax module of the API: one effective-dated TaxProfile per holder (TFN and ABN encrypted and never displayed, tax residencies and TINs, FATCA and CRS self-certification, the consequence of no TFN explained and recorded), the implementation of A40's `WithholdingProvider` (A41 computes every line's withholding amount per tax component with A02's table; A40 copies it; no TFN 47 % for Australian residents; non-resident interest, dividend and MIT fund-payment withholding for foreign residents; every rate a versioned parameter row, never a literal), AMIT tax components per run with a year-end true-up, AMMA statements per holder per trust per financial year due by 30 September, the annual tax summary, cost base and lots, the withholding remittance and filing calendar, and the CRS/FATCA report file, with every rule edit, true-up, batch, remittance, filing and override behind a maker-checker approval and every figure reproducible to the cent from the stored inputs.**

**Build status:** not started. **Milestone:** AM3 (Chain, identity and the money path). **Lane:** Money. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-16 agent-hours (build, challenge and verify loops). The scope is larger than A40's and A37's (profiles with encryption, the provider with a 10,000-line oracle, true-up, AMMA over 200 generated FYs, lots, remittance, CRS/FATCA, four jobs, more than 25 routes and a PII scan), and this node gates A49, the AM3 exit.

**Depends on:** [[A40 - Distributions engine (SM-08)]], [[A30 - Investor onboarding, KYC cases and KYB (SM-01)]], [[A35 - Documents, disclosure library, e-sign and acknowledgements (G12)]], [[A43 - Communications, notifications, tasks and marketing claims (G17)]], [[A46 - Job scheduler, integrations health and webhooks]], [[A17 - Bank rail sandbox adapter (NPP-PayID-PayTo) and receipt matching]], [[A37 - Orders, escrow, allocation and refunds (SM-05)]], [[A06 - Seed data and scenario simulator]], [[A20 - Three-way reconciliation engine with zero tolerance]], [[A104 - MCP server generated from the OpenAPI document]] (none of these depends on A41, so no cycle). A101 is not a dependency: A41 → A45 → A48 → A101 already, so an edge A101 → A41 would be a cycle. A41's agent-writable tax routes write A10 audit codes that carry sensitivity `sensitive`; A101 raises its `agent.sensitive_action` notice from any such code without depending on A41. This node proves the audit sensitivity at its gate; the notice itself is proven at A101's gate, in A49 and in A100 (graph note, 24 Sep 2026).
**Unlocks:** [[A45 - Reporting, regulatory calendar, filings and metric governance]], [[A49 - Money-path smoke through the SDK (AM3 exit and founder checkpoint)]], [[A56 - Onboarding flow ONB-01 to ONB-10 with entity branch]], [[A58 - Portfolio, holding detail, transactions, distributions and statements]], [[A74 - Console- treasury, distribution run review, tax centre]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A41\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The oracle scope is the money and authority surface of the module: withholding vectors to the cent over a generated table of profiles × rate-set versions × component splits × gross and carry-in amounts (at least 10,000 lines, including every A02 reason code, every rounding boundary and `.5`-cent cases); the provider's line amounts are the amounts A40 stores; dust-carried lines are `carried` and excluded from every withholding total; the run total equals the sum of its `applied` lines; the G16 decision table (below) row by row; AMMA components for a financial year sum exactly to that year's attributed lines (with and without a true-up) and the AMMA withheld total equals the year's attributed withholding; a June run paid in July counts in the next FY's paid figures and in the earlier FY's AMMA; a TFN added mid-year changes only lines calculated after it was saved; a rate-set version selected by calculation time and by approval time, never by payment time; every approval-bound action refusing without a matching approved id; and no TFN, TIN or ABN appearing in any response, log line, audit payload or error message.

## Build brief

This node is API-only: module `tax` in the Fastify monolith, four worker jobs in `services\worker\src\jobs\tax\`, and the `tax-authority` sandbox adapter in `packages\adapters\tax-authority\`. It has no screens of its own: ONB-05 (A56), the distributions table of POR-03 (A58), the withholding preview on SPN-09 (A64), the "Tax details" row of ACC-01 (A59) and ADM-20 Tax centre (A74, drawn by A51) are built on the contracts below; POR-07's screen contract is A47's `me/statements`, which this node feeds through outbox events. Money never moves here: A40 posts the per-line `distribution.pay` journal in A16 with the `withholding_payable` leg whose amount this node computed, and remittance is a journal A16 posts under this node's approval. Every rule is enforced in the service layer, never only in a screen or a caller, so that the same behaviour reaches a person on a screen, their agent through the API and the MCP server (D04, A100).

**Tables: A04's core tables plus this module's own**

- A04 already owns the core tables `tax_profile`, `tax_component` and `amma_statement` (A04's table list names A41 as their user). This node uses them as the heads of its records and adds everything else as tables wholly its own through A04's `registerModuleSchema({ node: 'A41', tables, rlsClass, insertOnly, humanOnlyActorColumns, migrationsDir })`: `tax_profile_versions`, `tax_residencies`, `tax_self_certifications`, `tax_rate_sets`, `eoi_countries`, `tax_component_types`, `tax_component_versions`, `withholding_calcs`, `withholding_calc_lines`, `tax_exceptions`, `tax_lots`, `lot_adjustments`, `withholding_remittances`, `tax_filings`, `crs_reports`. Columns this node needs on A04's core tables that A04 does not yet define (the version pointer on `tax_profile`, the component-version link on `tax_component`, `state`/`version`/`document_id` on `amma_statement`) and on `vehicle` (`tax_class` in `amit | mit | other`, `clean_building_mit` boolean) are an A04 follow-up loop (A04.x) raised before this node's Build step; this node never writes a migration against a table A04 owns.
- Reference data (rate set version 1, the EOI country list, the component-type catalogue and its A02 kind map, the filing due rules) ships as insert-only migrations in this module's own `migrationsDir` under the owned path, each row labelled `unverified` until the tax adviser answers. Persona-level tax data (Alex Morgan's profile with TFN on file, a no-TFN resident, a foreign resident in an EOI country and one in a non-EOI country, a joint holding with one party missing a TFN) is an A06 follow-up (A06.x); this node never writes into `packages\db\seed\`. A06 keeps its rule that seeds hold only encrypted placeholders for TFNs; the plain synthetic TFNs and TINs used by the leak and format tests are created at test time through the API by this node's own tests and the node QA's challenge.

**Tax profile (`tax_profile`, `TaxProfileVersion`, `TaxResidency`, `SelfCertification`)**

- One `tax_profile` per holder of record (`investor_id` from A30, which covers individuals, joint holders, SMSFs, companies and trusts). Joint holdings carry one profile with a `parties[]` list, one party per verified joint holder, each with its own TFN status; the profile's `tfn_withholding_applies` is true when any Australian-resident party has no TFN, ABN or exemption (the ATO joint-account rule as this node understands it; a counsel question under Human gates, shipped as the config key `tax.joint.withhold_if_any_party_missing`, default true).
- Profiles are effective-dated and append-only: every change writes a new `TaxProfileVersion` with `effective_from` (A09's injectable clock, `Australia/Sydney` civil date recorded alongside), `changed_by_principal`, `on_behalf_of` and `change_reason`; versions are never updated or deleted (A04's insert-only convention, declared through `registerModuleSchema({ insertOnly })`). The engine always resolves "the version effective at instant T", so a run calculated at T sees exactly the version a person or agent had saved before T. There is no retroactive recalculation of any line by this node; an investor who quotes a TFN after a line was withheld claims the credit in their own return, and the tax profile read carries the plain-English text ("Tax withheld before you gave us your TFN is shown on your statement; you claim it in your tax return") for A58 and A47 to show.
- Fields per version: `tfn_status` (`on_file`, `abn_on_file`, `exempt`, `not_provided`, `declined`), `tfn_enc` and `abn_enc` (envelope-encrypted through the `kms` adapter of A08 with the per-tenant key, following A04's `_enc` convention and A09's `PII_PATHS`, which lists both `tfn` and `abn`; excluded from every ORM select by default and readable only by `verifyTfnFormat`, `verifyAbnFormat` and `buildReport`), `abn_present` (boolean display column; no ABN digits are ever returned, even masked, which is what A74 renders), `tfn_exemption_code` (a seeded code list: pensioner, non-resident, entity not required, and so on; the list is data, and its legal completeness is a tax-adviser question), `abn_status`, `residency_status` (`australian_resident`, `foreign_resident`, `temporary_resident`), `residencies[]` (country, `tin_enc`, `tin_unavailable_reason`), `us_person` (FATCA indicia: citizenship, birthplace, US address; each captured as a boolean with a source), `crs_entity_type` (`individual`, `financial_institution`, `active_nfe`, `passive_nfe`) with `controlling_persons[]` for a passive NFE (linked to A30's `BeneficialOwner` rows, each with their own residencies and TINs), `self_cert` (`state` `missing | signed | stale`, `signed_at`, `version`, `signature_kind` = `passkey_step_up` or `agent_token`, `declaration_text_sha256`), `reasonableness_flags[]` (mismatches between the claimed residencies and A30's KYC address and identity-document country, for TAXO review), `eoi_country` (derived: is the primary foreign residency in the seeded information-exchange country list; this is A02's `eoiCountry`, not a tax-treaty flag), `no_tfn_consequence_acknowledged_at`.
- **Residency drives the branch (A02's rule).** `australian_resident` and `temporary_resident` map to A02's `resident`; `foreign_resident` maps to `foreign`; a profile with no `residency_status` maps to `unknown`, which A02 refuses. TFN withholding never applies to a foreign resident: when a profile version is saved with `residency_status = foreign_resident` and no TFN, the service records `tfn_status = exempt` with `tfn_exemption_code = non-resident` automatically, audited as `tax.profile.nr_exemption_applied` with the version id, so the reason is on file rather than implied. `no_tfn` is reachable only for Australian and temporary residents.
- Format checks only: `verifyTfnFormat` implements the public TFN check-digit algorithm (weights 1, 4, 3, 7, 5, 8, 6, 9, 10, modulus 11) and refuses `TAX_TFN_INVALID_FORMAT`; `verifyAbnFormat` implements the public mod-89 check and refuses `TAX_ABN_INVALID`. They prove nothing about whose number it is and the response says "format accepted", never "verified". The ATO's TFN validation service is a vendor behind the sandbox adapter `tax-authority` (defined with A08's `defineAdapter`, its conformance suite run by A08's harness, and its swap point listed in A08's generated `SWAP-POINTS.md` and recorded in [[Decisions]]) that always returns `format_only` locally.
- Change in circumstances: when A30 records a new residential address country, or a residency is edited, the profile's `self_cert.state` becomes `stale` and a task is written for the person through A43 to re-certify within `tax.self_cert.recert_days` (config, default 90); after that the job `tax.self_cert_sweep` marks the account `undocumented_reportable` for the CRS report and writes a `tax_exceptions` row for ADM-20. The 90-day figure is a CRS rule as this node understands it and is a counsel question, not a decision.

**G16 evaluation (`evaluateG16(investor_id, at)` for A19's `GateEvaluation`)**

The result is total: every profile state lands on exactly one row, first match wins, and the oracle enumerates the table. Missing TFN is never a block on investing (product map D08); it is a withholding flag.

| # | Condition on the version effective at `at` | Result | Reason code |
|---|---|---|---|
| 1 | no `residency_status` | `fail` | `TAX_RESIDENCY_REQUIRED` |
| 2 | `self_cert.state = missing` (never signed) | `fail` | `TAX_SELF_CERT_REQUIRED` |
| 3 | any foreign residency with neither a TIN nor a `tin_unavailable_reason` | `refer` | `TAX_TIN_REQUIRED` |
| 4 | `self_cert.state = stale` | `refer` | `TAX_SELF_CERT_STALE` |
| 5 | an open reasonableness flag | `refer` | `TAX_REASONABLENESS_OPEN` |
| 6 | anything else (including `tfn_status` `not_provided` or `declined`) | `pass` | none |

Every result also carries `withholding_applies` and `withholding_basis_hint`: `true` / `no_tfn` for a resident with `not_provided` or `declined` (or a joint profile under `tax.joint.withhold_if_any_party_missing`); `true` / `foreign_resident` for a foreign resident (the rate then depends on the component and vehicle class); otherwise `false` / `tfn_quoted` or `exempt`. The acknowledgement of the no-TFN consequence is enforced when the profile is saved, not at the gate: a resident's `PUT` with `tfn_status` `not_provided` or `declined` is refused `TAX_NO_TFN_ACK_REQUIRED` unless the effective version already carries `no_tfn_consequence_acknowledged_at`, so row 6 cannot be reached without it through any route. ONB-10's "Tax details (G16) Pass" is row 6 with `withholding_applies: true` for a holder who declined a TFN, since the design's checklist has no amber state for tax; a `refer` goes to A19's referral path and never blocks a holding already held.

**Withholding rate sets and the country list (`TaxRateSet`, `ExchangeOfInformationCountry`, `TaxComponentType`)**

- `TaxRateSet` rows are versioned parameters whose fields are exactly A02's parameters: `version`, `effective_from`, `approved_at`, `tax_class` (`amit`, `mit`, `other`, matching the `vehicle.tax_class` column from the A04 follow-up), `no_tfn_bp` (seed 4700, A02 `NO_TFN_BP`), `nr_interest_bp` (1000, `NR_INTEREST_BP`), `nr_unfranked_dividend_bp` (3000, `NR_UNFRANKED_DIVIDEND_BP`), `mit_clean_building_eoi_bp` (1000), `mit_foreign_eoi_bp` (1500, `MIT_FOREIGN_EOI_BP`), `mit_foreign_non_eoi_bp` (3000, `MIT_FOREIGN_NON_EOI_BP`), `foreign_non_mit_bp` (3000, A02's placeholder `FOREIGN_NON_MIT_BP`), `treaty_overrides[]` (country, A02 component kind, bp; data passed to A02 as the per-profile override in `rates`, never looked up inside A02), `rounding` (`down`, the A02 default, per component; the alternative is a tax-adviser question), `component_kind_map` (each `TaxComponentType` → one A02 component kind, see below), `approval_id`, `supersedes`. Every seed value is labelled `unverified` and each is a tax-adviser question under HG-LEGAL. No function body in `src/modules/tax/` contains a rate number; A02's no-magic-literal lint rule is extended to `bp` literals in this module, and a planted `4700` in the engine fails `verify`.
- A vehicle whose `tax_class` has no effective rate row cannot have a run calculated: the provider refuses `TAX_NO_RATE_FOR_CLASS`, and A40 keeps the run in `calculating` with the error on the run (the A40 follow-up below documents that state). A vehicle with no `tax_class` is refused `TAX_VEHICLE_TAX_CLASS_MISSING` the same way.
- **Editing a rate set** is the A03 action `M13.withholdingRule.edit` (the product map's ADM-20 "Edit withholding rule", `6E` TAXO → CCO + CFO), created through A14 with the new row as the canonical payload. At draft, `effective_from` must be the start of a Sydney calendar day no earlier than tomorrow, otherwise `TAX_RATE_SET_EFFECTIVE_PASSED`. When A14 reports `approved`, if `effective_from` is at or before `approved_at` (the checkers decided late), the service moves `effective_from` to the start of the next Sydney calendar day after `approved_at` and writes the audit event `tax.rate_set.effective_from_moved` with both dates; the row never claims an effective date earlier than its approval. Version selection for a calculation at instant T is: the highest `version` with `effective_from ≤ T` and `approved_at ≤ T`. A version never touches lines already calculated, and a caller naming a version that is not the one selected is refused `TAX_RATE_SET_NOT_EFFECTIVE`.
- `ExchangeOfInformationCountry` is a seeded list with `effective_from`/`effective_to`; `eoi_country` on a profile is recomputed on every version write and every list change. The list content is a tax-adviser deliverable; the seed is labelled `unverified`.
- `TaxComponentType` catalogue (data): `australian_rental_income`, `interest`, `unfranked_dividend`, `capital_gain_discount`, `capital_gain_other`, `tax_deferred` (AMIT cost base net amount), `franked_distribution`, `franking_credit`, `foreign_income`, `other`, each with `affects_cost_base` (`up`, `down`, `none`) and `cash` (false for `franking_credit`, which is attributed but never paid). The rate set's `component_kind_map` maps each type to exactly one of A02's five kinds (seed: rental income and capital gains → `other_income`, the MIT fund-payment portion; `interest` → `interest`; `unfranked_dividend` → `unfranked_dividend`; `franked_distribution` → `franked_dividend`; `tax_deferred`, `foreign_income` and `other` → `non_assessable`); changing the map is a rate-set edit under the same `6E` policy, and the seed map is a tax-adviser question.

**Withholding: A41 implements A40's `WithholdingProvider` (called by A40 at the `calculating` transition of SM-08)**

One contract, owned here and consumed by A40 without re-derivation. A41 computes every amount; A40 copies it.

- `WithholdingProvider.computeRun({ run_id, run_kind: 'income' | 'exit' | 'zero' | 'reduced', vehicle_id, calculated_at, period_end, components_declaration_id, lines: [{ line_id, investor_id, units, gross_cents, carry_in_cents }] }) → { rate_set_version, components_version_id, calc_sha256, replayed, lines: [{ line_id, profile_version_id, base_cents, components: [{ type, kind, gross_cents, rate_bp, reason, withheld_cents }], withholding_cents, net_cents, withholding_rate_bps, withholding_basis, primary_reason, review_flag }], totals: { base_cents, withholding_cents, net_cents } }`. Exported only through `modules/tax/index.ts` and callable only by A40's service principal.
- Per line: `base_cents = gross_cents + carry_in_cents` (withholding is assessed on the money actually being paid, including dust carried from earlier runs); the base is split into components with A02's `split` using the run's declared basis points (the rounding cent lands in `other`); `profile = versionEffectiveAt(investor_id, calculated_at)`; A02's `withholdingForLine({ components, profile, rates, rounding })` with `rates` and `rounding` from the selected rate set and the treaty overrides for the profile's residency country gives each component's `rate_bp`, `reason` and `withheld_cents`; `withholding_cents = Σ withheld_cents`; `net_cents = base_cents − withholding_cents` exactly. `withholding_rate_bps` is a display figure for A40's line and A74's column: the rate of the line's `other_income` component when present, otherwise the highest component rate; it is never used to recompute anything. A single rounding parameter exists (the rate set's `rounding`, default `down` per component, A02's default); A40 applies no rounding of its own to withholding.
- `withholding_basis` maps A02's reason codes onto A40's enum explicitly: `none` with a TFN or ABN on file → `tfn_quoted`; `none` with an exemption code → `exempt`; `no_tfn` → `no_tfn`; every foreign reason (`foreign_exempt_component`, `foreign_interest`, `foreign_unfranked_dividend`, `foreign_mit_clean_building`, `foreign_mit_eoi`, `foreign_mit_non_eoi`, `foreign_non_mit`) → `foreign_resident`. A02's `residency_unknown` refusal is never mapped: the provider refuses the whole run with `TAX_PROFILE_INCOMPLETE` naming the line ids, and A40 keeps the run in `calculating`.
- Foreign residents get the non-resident branch per component, exactly A02's rows 4-10: franked and non-assessable components at 0 (`foreign_exempt_component`), interest at `nr_interest_bp` (`foreign_interest`), unfranked dividends at `nr_unfranked_dividend_bp` (`foreign_unfranked_dividend`), and the `other_income` (fund-payment) component at the MIT EOI, non-EOI or clean-building rate for `amit`/`mit` vehicles, or at `foreign_non_mit_bp` (`foreign_non_mit`) for `other` vehicles. A foreign line on an `other` vehicle also sets `review_flag = foreign_non_mit_review` and writes a `tax_exceptions` row for TAXO, because the trustee's own assessment of a non-MIT trust's foreign beneficiaries is outside what this node computes (a counsel question); the exception is a review item, not a block on the run.
- `WithholdingProvider.confirmRun({ run_id, calc_sha256, carried_line_ids[] })` is A40's second call, made after its dust rule and before `calculated`: lines A40 carried (`exception_code = dust_carried`) are marked `state = carried` in `withholding_calc_lines`, count zero withholding and are excluded from every withholding total, the AMMA and the remittance; every other line becomes `applied`. The carried money is assessed when a later run pays it through `carry_in_cents`. A `computeRun` without a matching `confirmRun` leaves the calc `unconfirmed`, and an unconfirmed calc is never counted anywhere.
- Every result is stored (`withholding_calcs` per run with the inputs, the rate-set version, the components version and `calc_sha256`; `withholding_calc_lines` per line and component) so ADM-19's lines and ADM-20's totals are read from stored facts, never recomputed live. A20's reconciliation rule R8 ("withholding total = tax module total") compares A40's run `withholding_cents` with Σ `withholding_cents` of the run's `applied` calc lines. A second `computeRun` for a run whose calc already exists returns the stored result with `replayed = true`; A40 may pass `recalculate: true` only while the run is `draft` or `calculating`, which supersedes the old rows (kept, marked `superseded_by`); from any later state it is refused `TAX_RUN_NOT_DRAFT`. The provider is pure over its inputs plus the parameter tables: the same call twice returns the same `calc_sha256`.
- `run_kind = exit` (J08 step 9) takes components that include `capital_gain_*`; nothing else differs. `zero` runs have no lines; `reduced` runs are ordinary lines.
- **Components per run (`tax_component`).** The sponsor's fund accountant (SP-FIN) declares the split of the run's gross into component types as basis points that sum to 10,000 (`TAX_COMPONENTS_DO_NOT_SUM` otherwise), through `PUT /v1/vehicles/{id}/tax/runs/{run_id}/components` while the run is `draft` (`TAX_RUN_NOT_DRAFT` after). A missing declaration defaults to 100 % `australian_rental_income` with `estimated: true`. The stored declaration's id (`components_declaration_id`) and its sha256 travel inside A40's `distribution.propose` payload, so the sponsor approval binds them; A40 passes the id to `computeRun`. This node validates and stores the declaration; A40's proposal carrying it is the A40 follow-up below.

**Year-end component true-up**

- After 30 June the fund accountant replaces the year's estimates with the actual split: `PUT /v1/vehicles/{id}/tax/fy/{fy}/components` (A03 action `SPN.taxComponents.trueUp`, SP-FIN maker, the person's agent token allowed as maker; checker TAXO under the named policy `4E` SP-FIN → TAXO, requested from A03 as a new row; whether the trustee or RE must also sign is a tax-adviser question). The payload is the FY component split in basis points summing to 10,000 of the vehicle's FY attributed income; `TAX_COMPONENTS_DO_NOT_SUM` otherwise, `TAX_FY_OPEN` while any run with `period_end` in the FY is not `closed` or `cancelled`.
- On approval the service writes a new `TaxComponentVersion` for the vehicle and FY with `supersedes` pointing at the per-run estimates (or the previous true-up); nothing is edited, and the audit event `tax.components.trued_up` carries the approval id and both version ids.
- The AMMA uses the latest approved `TaxComponentVersion` for the FY when one exists (each holder's FY attributed income split by A02's `split`, rounding cent to `other`); otherwise it uses the per-run declarations. The AMMA batch refuses `TAX_COMPONENTS_ESTIMATED` while any run in the FY has `estimated: true` and no true-up exists.
- Stored withholding is never recomputed. At true-up approval the service computes, per holder, what the stored lines would have withheld under the trued-up split with the rate sets then effective, and writes the signed difference as a `tax_exceptions` row (`kind = trueup_withholding_difference`, amount in cents) for TAXO; no journal is posted and no line changes. How a difference is settled (a top-up, a refund, or the holder's own return) is a tax-adviser question.
- A true-up approved after the FY's AMMA batch makes the batch reissuable; the reissue (below) uses the new version.

**AMMA statements, annual tax summary, cost base and lots**

- Financial year = 1 July to 30 June (`Australia/Sydney`). Two figures are kept apart and never mixed: **income attributed** is Σ `base_cents` of `applied` lines of runs whose `period_end` falls in the FY (gross, the AMMA's basis), and **distributions paid** is Σ `net_cents` of lines A40 reports paid (`distribution.line.paid`) with `paid_at` in the FY (net cash, the design's KPI). A June run paid on 10 July counts in the next FY's paid figure and in the earlier FY's AMMA.
- `amma_statement` per holder per vehicle per FY: `state` (`draft`, `generated`, `delivered`, `reissued`, `withdrawn`), `version`, `components[]` (in cents, summing exactly to the holder's income attributed; per-run declarations or the FY true-up as above), `cash_cents` (Σ attributed `net_cents` of the FY's applied lines), `withholding_cents` (Σ attributed withholding), `cost_base_adjustment_cents` (signed), `components_version_id`, `document_id` and `sha256` (A35's deterministic renderer), `generated_at`, `delivered_at`, `approval_id`.
- Batch generation is the A03 action `M13.ammaBatch.generate` (the product map's ADM-20 "Generate AMMA batch", `4E` TAXO → CFO), one approval per vehicle per FY with the canonical payload being the sorted list of `(investor_id, components, cash, withholding)` and its hash. The batch runs only after `approved`, refuses `TAX_FY_OPEN` while any run with `period_end` in the FY is not `closed` or `cancelled`, `TAX_COMPONENTS_ESTIMATED` as above, and `TAX_AMMA_ALREADY_GENERATED` for a second batch. Reissue is the A03 action `M13.ammaBatch.reissue` under the same policy (requested from A03 as a new row), which creates version n+1 and marks version n `reissued`; nothing is edited in place. On batch completion each statement is rendered by A35, written to the holder's document vault through A35, and moves `generated → delivered` when A35 confirms the vault write; A43 sends "AMMA ready" per statement and the outbox event `tax.amma.issued { investor_id, vehicle_id, fy, version, document_id, sha256, issued_at }` is published for A47 (POR-07) and A45. The design's seed has FY26 AMMA issued 28 July 2026.
- Annual tax summary per holder per FY (`GET /v1/me/tax/summary?fy=`, for the holder's agents and for A49's cross-check; POR-07's tiles come from A47): `{ fy, income_attributed_cents, withheld_attributed_cents, distributions_paid_cents, withheld_paid_cents, tfn_status, withholding_applies, amma: [{ vehicle, version, issued_at, document_id }], lots_summary }`. `distributions_paid_cents` must equal A47's `fy_to_date_net_cents` and POR-01's "Distributions FY27" figure, and `withheld_paid_cents` must equal A47's `tax_withheld_fy_cents`; that cross-module equality is asserted by A49, not here. At the August run the line withholds A$58.47 on A$124.41 gross; the person saves a TFN on 5 September, and the August run is paid on 8 September; the September run is calculated on 30 September: the August line stays at A$58.47 in every read (POR-03, ADM-19, the AMMA), the September line withholds A$0.00 with reason `none` and basis `tfn_quoted`, and no journal, calc or statement for August changes; a `recalculate: true` call for the August run from `executing` is refused `TAX_RUN_NOT_DRAFT`.
- **Rate edit that reaches backwards (compliance, G13).** TAXO creates a rate-set version with `no_tfn_bp = 4500` and `effective_from` yesterday: refused `TAX_RATE_SET_EFFECTIVE_PASSED` at draft. With `effective_from` tomorrow, approved by CCO and CFO today, a run calculated today still uses 4700 bp and a run calculated the day after uses 4500 bp. With `effective_from` tomorrow but CFO deciding two days later, the version's `effective_from` moves to the day after approval with `tax.rate_set.effective_from_moved`, and a run calculated in between uses 4700 bp. The same version with only CCO's decision, or with an agent token as one of the two checkers, never becomes effective and A14 refuses the decision under SoD.
- **Dust, carry-in and rounding (money).** A holder whose August line is below the dust threshold: A40 carries it, `confirmRun` marks the calc line `carried`, R8 and the August remittance exclude it; in September the line arrives with `carry_in_cents`, is withheld on `gross + carry_in`, and the AMMA counts it once. A no-TFN line whose withholding lands on an exact `.5` cent withholds the `down` amount in both A41's calc and A40's stored line.
- **AMMA that does not add up (money).** An FY with runs whose component splits include a `tax_deferred` share of 2,000 bp and a holder whose lines produce rounding remainders every month: Σ per-holder components must equal Σ that holder's attributed income exactly, Σ withheld on the AMMA must equal Σ attributed withholding of `applied` lines, the cost base adjustment must equal Σ `tax_deferred` components, and Σ over all holders of every component must equal the vehicle's FY total; one cent of drift fails the batch with `TAX_COMPONENTS_DO_NOT_SUM` rather than being absorbed. The same FY after a true-up to 70 % rental / 20 % tax deferred / 10 % interest: the AMMA uses the true-up, stored withholding is unchanged, and each holder's difference is a `trueup_withholding_difference` exception.
- **Foreign resident branch (compliance, G16).** A foreign resident with no TFN in an EOI country on an `amit` vehicle whose run is 80 % rental and 20 % interest: the TFN exemption `non-resident` is on file automatically, the rental component withholds at `mit_foreign_eoi_bp` (`foreign_mit_eoi`), the interest component at `nr_interest_bp` (`foreign_interest`), basis `foreign_resident`, and no component reaches `no_tfn`. The same holder in a non-EOI country withholds the rental component at `mit_foreign_non_eoi_bp`; a treaty override row for the holder's country changes only the interest component.
- **Foreign resident on a non-MIT vehicle (compliance).** A foreign resident holds units in a vehicle with `tax_class = other`: the `other_income` component withholds at `foreign_non_mit_bp` with reason `foreign_non_mit`, the line carries `review_flag = foreign_non_mit_review`, a `tax_exceptions` row appears in ADM-20's foreign count and in `tax/withholding/exceptions`, and the run proceeds and closes normally; TAXO clears the exception only through `M13.taxProfile.override` (`4E` TAXO → CCO) with a recorded treatment.
- **TFN leak (security).** The challenge creates, through the API, a test investor with synthetic TFN 123 456 782 (check digit valid), ABN and TIN "DE-99988877" (A06's seed keeps only encrypted placeholders), then greps every HTTP response, OpenAPI example, log line, audit `reason`, outbox payload, error message and the CRS report route's response for those strings and for their masked forms; the only permitted sightings are inside the encrypted columns and inside the report file written through A35's storage.
- **Agent authority on a declaration (D04, G22).** An investor agent token without `ONB.taxProfile.save` calls `PUT /v1/me/tax-profile` (403, audited as agent on behalf of the person). One with the scope saves a TFN: it succeeds and its audit event carries sensitivity `sensitive` (A101's notice from it is proven at A101's gate). The same token calling the self-certification, residency declaration or no-TFN acknowledgement route is refused by A12 with A03's counsel-pending code before this module runs, while the person's passkey step-up works. On a scratch branch where the self-certification cell is flipped to `true` with a test decision id, the agent call succeeds with `signature_kind = agent_token` and a `sensitive` audit event, and nothing in `src/modules/tax/` changed. A token whose mandate expired an hour ago is refused by A12 before this module runs.
- **Design fidelity (read contracts).** From A06's seed, `me/tax/summary?fy=FY27` for Alex Morgan returns `distributions_paid_cents = 57696`, `withheld_paid_cents = 0`, `tfn_status = on_file`; `?fy=FY26` returns A06's derived FY26 paid figure, an `income_attributed_cents` that includes the June 2026 run paid in July, and one AMMA with `issued_at = 2026-07-28`; `me/tax/statements` lists that AMMA in state `delivered` with a document id A35 can serve and `tax.amma.issued` was published for it; a float, a `number` money field, a masked TFN or a missing sub-line field fails the contract test.
