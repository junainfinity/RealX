# A59 - AUD wallet, token wallet and account screens

**The six investor screens where a person looks after their cash, their token wallet and their account, rendered from the treasury, ledger, bank-rail, wallet, identity, classification, tax, communications and support APIs and nothing else: POR-05 AUD wallet (funds available and reserved, the PayID deposit card, the PayTo note, a withdrawal that can only go to the verified account with the second-approval threshold sentence read from data, the float-interest policy and the ledger table), POR-06 token wallet and recovery (address and network, tokens by trust with frozen amounts and generic reasons only, wallet passkeys and devices, guardians, agent session keys, start recovery), ACC-01 profile and security (details whose change re-runs identity, sign-in passkeys and sessions, the bank account, classification expiry, tax status, close account, the link to ACC-05), ACC-02 the recover-account stepper with the 48-hour wait, cancel from any signed-in device and the fallback banner, ACC-03 notifications with preferences in which agent and money-movement notices cannot be muted, and ACC-04 support and complaints with AFCA details made prominent when a deadline is missed. Every person-only act (withdrawal step-up, bank-account change, passkeys, guardians, recovery, close account) runs the passkey ceremony; every other action is one SDK call an agent can also make under the same gates.**

**Build status:** not started. **Milestone:** AM5 (Investor app). **Lane:** Investor app. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops).

**Depends on:** [[A52 - Web app shells, routing and passkey sign-in (public, investor, sponsor)]], [[A39 - Treasury- withdrawals, escrow release, client-money reconciliation]], [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests]], [[A43 - Communications, notifications, tasks and marketing claims (G17)]], [[A44 - Support, complaints (SM-12) and Investor 360 read model]], [[A50 - Design extension A- investor and sponsor screens not in the prototype]]

**Oracle rule:** this is an oracle node (`oracle: yes`, set on 24 Sep 2026 by the plan fixer). It moves no money, supply or holdings itself; it asks the API to, and renders the answer. But it is the investor's front door to withdrawals, the bank account, wallet keys and recovery, so the Oracle stage runs at max effort, and a missing or empty `gauntlet\hidden\A59\` folder at the start of Build is a gate failure, not a vacuous pass. The node QA writes hidden oracle tests to `<workspace>\gauntlet\hidden\A59\` before the build starts, from this note alone: component and Playwright tests that pin every tile, card, row and pill to the API fields named below, the empty, loading, error, held, `under_review`, frozen, waiting-period, timelock, disputed, fallback and AFCA-prominent states, the passkey step-up on every person-only act, the agent markers and the locked agent notices, the tipping-off string scan over the rendered DOM, the parity manifest check, and the design-fidelity comparison against the prototype's `wallet` region and A50's drawings of POR-06 and ACC-01 to ACC-04. The builder never reads that folder ([[App Gauntlet]] §2).

This note is not legal advice. The float-interest wording, the recovery disclosure, the complaint periods and the AFCA wording, and which account acts are legally personal are counsel questions recorded in A39's, A29's, A44's and A12's Human gates; this node renders the wording those modules return and never writes its own version of a legal sentence.

## Build brief

This node is UI-only: the `(investor)/wallet` and `(investor)/account` route groups of `apps/web` and the `features/wallet-account` package of components, hooks and copy tables. It calls the API only through `packages/sdk` (A09, regenerated from the OpenAPI documents of A16, A17, A39, A29, A11, A30, A32, A41, A43, A44 and A12) and never through a hand-written fetch. It owns no API route, no table, no job and no adapter. Every money figure is the API's `formatted` twin; every status, reason, threshold, deadline and step is the API's answer; the browser never adds, compares, converts or infers. Every person-only act goes through A52's `withFreshAssertion(action)` helper, which runs A11's fresh-assertion ceremony over the payload hash the API returns, so the step-up cannot be skipped by the screen. Because the same routes serve a person's agent through A12's tokens and A104's MCP server, this node adds nothing an agent could not also do where the act is delegable, and it publishes the mapping that proves it (`parity.json`, below).

**Routing, shells and screen codes**

- Routes under A52's investor shell and route table (`src/shell/routes.ts`, paths frozen there): POR-05 `/wallet`, POR-06 `/wallet/tokens`, ACC-01 `/account`, ACC-02 `/account/recover`, ACC-03 `/account/notifications`, ACC-04 `/account/support`. Every page exports `screen = defineScreen({ code, design })` (A52's signature, `src/shell/screen.ts`) with `design` = `'wallet'` for POR-05 and `'ext:POR-06'`, `'ext:ACC-01'` to `'ext:ACC-04'` for the others; the canonical id in tests, evidence and analytics is the product-map code, never the design's "INV · Wallet".
- ACC-05 is not built here. Spec point (a), settled: A52's frozen route table (Account row) puts ACC-05 at `/account/agents`, and A60 owns `app\(investor)\account\agents\` (its list, `new`, `[tokenId]` and `activity` pages). That folder is carved out of this node's `(investor)\account\` path (see Owned paths); the generator reads the carve-out from both notes into `Data/app-graph.json`. This node creates no page, layout, redirect or file under `account\agents\`. Every link to ACC-05 is `href('ACC-05')` or, for one token, `href('ACC-05', { tokenId })` + `#activity`, where `tokenId` is the `TOK-` id and nothing else: a token prefix, name or secret is never a path or query parameter (A52's parameter allow-list rejects it). Agent-marked rows that arrive without a `token_id` link to `href('ACC-05')` (the list), never to a prefix-filtered URL; `token_id` inside the investor `placed_by` object is requested from A16, A39, A47 and A43 (for notice `target_screen` params) as a follow-up.
- All pages are server components that read through the SDK with `cache: 'no-store'` (cash, frozen amounts, recovery state and complaint deadlines must be current on every load; a freeze or hold set between two loads must be visible on the second). Client components exist only for dialogs, the copy buttons, the countdown, the preference toggles, forms and "Load more".
- Signed-out or expired session: A52's guard redirects to sign-in and back; `SESSION_EXPIRED` in the middle of the withdrawal or complaint form keeps the form in memory for one round trip (`preserveOnReauth`); a sponsor user with no investor account gets A52's "no investor account" page.

**POR-05 AUD wallet (`/wallet`, design `wallet`)**

- Header "Wallet" and the design's subline "Cash sits in RealX's client-money trust account until you invest. Tokens sit in a wallet only you control."
- KpiGrid, three tiles: **Funds available** = `GET /v1/me/wallet` `formatted.available` with "Client-money trust account" (or "Under review" and no reason when `account_status = under_review`); **Awaiting investment** = `formatted.awaiting_investment` with "In offer escrow", and mono lines "A$x reserved for open orders" when `reserved_cents.orders > 0` and "A$x reserved for withdrawals" when `reserved_cents.withdrawals > 0` (the product map's "Funds available and funds reserved"; the amounts come from the formatted twins `formatted.reserved_orders` and `formatted.reserved_withdrawals`, requested from A16, or from the `formatAud` exception under Cross-cutting behaviour until they land; `holds_present` renders only as the word "held" on the rows it concerns, never as a figure or a reason); **Tokens held** = `GET /v1/wallets/me` `tokens_held_total` with "Across {trust_count} trusts" (a contract test asserts it equals A47's `units_total` for the seed).
- **Deposit with PayID** card: title Newsreader 22, the sentence "Arrives in under a minute over NPP." and the PayID from `GET /v1/payments/payids/me` in the mono chip with a copy button (copy is the only client action; it calls nothing). Beneath it the plain rule A56 also shows: "Deposits are matched to your name; money sent by someone else is returned." `409 payid_not_issued` renders "Your PayID appears once your identity is verified" with a link to the ONB-10 status page; `503 bank_not_initialised` renders the shared error state. **PayTo note:** the design's "Or set up PayTo for automatic monthly top-ups" is phase-gated by A21's `payments.payto` flag (P3, off): while off, the card shows "PayTo automatic top-ups arrive later" with a grey "Later" pill and no control, link or form; the route is never called (it would return `501 not_in_phase`). When the flag is on the sentence becomes a link that A95 owns.
- **Withdraw** card: title "Withdraw", the sentence "To your verified account {destination_masked}." from the nominated account, and the threshold sentence rendered from `withdrawal_policy.second_approval_cents` through the copy table ("Withdrawals over {amount} need a second RealX approval.", `{amount}` = `formatted.second_approval`, requested from A16, or `formatAud` until then); no threshold digit exists in `features/wallet-account` (lint). "Withdraw funds" (outline ink, as the design) opens a dialog: an amount TextField (the string is converted to integer cents by A02's `parseAud` from `@realx/domain`, never by float arithmetic), the destination shown read-only (no field, no picker: A39's route has no destination parameter), the available figure as a hint, the expected time from configuration (`expected_by`), and "Request withdrawal", which calls `POST /v1/me/withdrawals { amount_cents, idempotency_key }` through `withFreshAssertion` (purpose `withdrawal_request`). The client never compares the amount with the balance or the thresholds; it renders the API's answer: `LDG_INSUFFICIENT_AVAILABLE` → "That is more than your funds available ({available})"; `WDR_STEP_UP_REQUIRED` or `FRESH_ASSERTION_*` → the ceremony again, once; `WDR_DESTINATION_NOT_VERIFIED` → "Add a bank account in your name first" linking to ACC-01 Bank accounts. Success toasts the design's sentence built from the response ("Withdrawal of A$1,000.00 requested · arrives in minutes", or "usually same day" when the API says so). "Withdraw funds" is disabled with its reason as a sub-line only for facts that are not compliance facts: no nominated account ("Add a bank account in your name"), `available_cents = 0` as returned ("Nothing available to withdraw"). An AML restriction never disables the button; the request is accepted and its row reads "Under review", exactly as for any other held withdrawal (A39's rule), so the screen cannot tip anyone off by refusing earlier.
- **Withdrawals** list from `GET /v1/me/withdrawals` (above the ledger when any row is not final): Date / Amount / To / Status / Expected, statuses `requested` and `processing` amber "Processing", `under_review` amber "Under review" with the expected time and no reason, `held_name_mismatch` amber "Account name doesn't match" with the plain fix link to ACC-01 (this is not an AML matter and A39 allows it to be said), `paid` and `settled` green, `returned`, `cancelled`, `rejected` grey. **Cancel** (outline soft) appears only on rows the API marks cancellable and calls `POST /v1/me/withdrawals/{id}/cancel`; `WDR_NOT_CANCELLABLE` renders "This withdrawal is already being paid".
- **Agent confirmation banner:** an agent's withdrawal request that needs the person (A12's `428 CONFIRMATION_REQUIRED`, which creates no withdrawal row) is shown as an amber banner "Your agent {agent_name} asked to withdraw {amount} · Review" linking to the confirmation page A60 renders; this node never confirms on its own page, so there is one confirmation surface. Spec point (h): A12 lists only `confirmations/{id}` (get, confirm, cancel), so a pending-confirmations list `GET /v1/agent-access/confirmations?state=pending&kind=withdrawal` is requested from A12 as a follow-up. Until it exists the banner is omitted (not faked from another read), and the person reaches the confirmation through A43's agent notice on ACC-03, whose deep link is A60's confirmation page. The banner's test is written against the requested route and is skipped, with the follow-up id recorded in `A59.qa.md`, while the route is absent.
- **Limits and float interest:** a KeyValueList "Limits" from `withdrawal_policy` (the automatic-release ceiling and the second-approval threshold; amounts from the requested twins `formatted.auto_max` and `formatted.second_approval`, or `formatAud` until they land; each plain sentence is a `copy.ts` entry with the amount as its only placeholder, unless A16 or A39 return policy sentences, which then replace the copy entries) and "Interest on cash" showing the float-interest disclosure text and effective date exactly as A39 publishes them for PUB-06, with the link "See all fees" to the fees page. While A39's policy is `undecided` the API's sentence is shown as returned; the screen never writes its own interest sentence. Spec point (b): if the investor app has no read of that disclosure except the staff `GET /v1/treasury/float-interest`, a public projection is requested from A39 as a follow-up, not called under a staff scope.
- **Ledger** DataTable from `GET /v1/me/ledger` (and the held-receipt rows of `GET /v1/payments/receipts/me` merged by the API's order, never re-sorted by the client): Date / Type / Detail / Amount / Status with the design's rows and tones (Distribution "3 trusts" Paid green; Deposit "PayID · NPP" Settled green; Withdrawal "To CBA ••4471" Settled green; In escrow and Pending amber; Refunded grey; a held deposit "Deposit received · under review" amber with no reason). A row with `placed_by.kind = 'agent'` carries the mono caption "by your agent {agent_name}" and the token prefix as display text only, linking to `href('ACC-05', { tokenId: placed_by.token_id })` + `#activity` (or to `href('ACC-05')` when `token_id` is absent; see spec point (a)), with the same five-kind `placedByLabel` table as A58 (lifted to `packages/ui` through A05 as a follow-up; until then a local copy that passes the identical shared table test). Spec point (c): if A16's or A39's investor rows do not carry `placed_by`, it is a follow-up to those nodes, because D04 requires every agent act to appear in the person's activity. "Load more" pages by cursor; empty is "No activity yet." with a link to Investments.

**POR-06 Token wallet and recovery (`/wallet/tokens`, drawn by A50)**

- Everything from one `GET /v1/wallets/me` read. Address chip with copy: `address_short` (first 6 + last 4, the single truncation rule) and the full address in the copy payload; network line "{chain name} · mirrors the trustee register"; registry status pill from `registry_status` and its API label; `recovery_disclosure_version` selects the approved sentence ("RealX can't move your tokens without trustee approval" in the seed); no wallet yet (`wallet: null`) renders A56's ONB-08 link, never an empty page.
- **Tokens by trust** as HoldingRows: trust name, units, and when `frozen_amount > 0` a grey pill "{n} frozen" with a sub-line from a closed reason table: `listed_for_sale` → "listed for sale", `lock_in` → "locked until {date}", `legal_hold` → "legal hold", `under_review` → "not available". Any other `frozen_reason` value renders "Not available" and fails the contract test against A29 and A27 (the fix belongs there); no free-text reason prop exists on the component. A wallet-level `frozen` flag shows "Your wallet is paused · contact support" with no reason. `recovered_out` wallets show "Tokens moved to your new wallet on {date}".
- **Passkeys and devices** CheckList from the wallet `keys` (device label, added, last used; purpose `wallet`, never the sign-in passkeys, which live on ACC-01, so the design's "3 passkeys" chip on POR-05 and "2 passkeys" on ACC-01 are two different counts and are labelled "wallet passkeys" and "sign-in passkeys"). "Add a passkey" runs `POST /v1/wallets/me/keys` with the WebAuthn registration ceremony under a fresh assertion (purpose `wallet_key_add`); "Remove" calls `DELETE /v1/wallets/me/keys/{id}` under a fresh assertion and renders `WALLET_LAST_KEY` as "You need at least one passkey on your wallet".
- **Guardians** CheckList from `guardians` (RealX guardian Active; Second device; Trusted contact) with `guardian_status` pills: `waiting_period` amber "Active from {effective_at}" and "Cancel" (the one-click cancel A29 sends by notice is the same call), `pending_reverification` amber with the API's plain reason and "Verify again". "Add a guardian" opens the re-verification flow (`POST /v1/wallets/me/guardians`, `requiresHuman`, liveness through the shared capture component in `packages/ui`; if that component still lives in A56's feature folder, lifting it is a follow-up to A05, not an import across features); `GUARDIAN_LOCKED_DURING_RECOVERY` renders "Guardians can't change while a recovery is open".
- **Agent session keys** (D04): rows from `session_keys` with mandate name, limits in plain English, expiry, last use and state; each links to `href('ACC-05', { tokenId })` for the mandate's token (`TOK-` id from the row). "Revoke" calls `DELETE /v1/wallets/me/session-keys/{id}` (it only narrows authority) and shows the pending on-chain revoke hash until confirmed. No control on this page creates or widens a session key; that is A60's flow and A29's `requiresHuman` route.
- Pending UserOps: a `sent` op older than the API's stuck threshold shows "Pending · {hash}" in mono, never a silent failure.
- **Start recovery** (outline soft) links to ACC-02; when a recovery is open, a banner "Recovery in progress · step {step}" replaces it and links to the request.

**ACC-01 Profile and security (`/account`, drawn by A50)**

- A settings list of TaskRows, each a read the person's agent can also make, in A50's order:
  - **Personal details** from `GET /v1/investors/me` (masked name, contact email and mobile, address as suburb and state, investor type, residency and, for foreign investors, "Foreign person (FIRB rules apply per listing)" read-only). The form is built from `packages/ui` blocks; A56's components are used only if exported through A56's `index.ts` or lifted to `packages/ui` by A05, never imported from A56's internals. After CLSR approval the row shows the new `valid_until` on the next load.

  - **Close account** (danger button at the bottom, with "Needs your passkey and no open orders or holdings"): the page reads `GET /v1/investors/{id}/close-checks` (A44) and lists each blocker in plain words (units held, cash balance, open order, distribution in flight, open complaint or ticket, "an open matter" for any KYC or AML matter, legal hold, estate); the button is disabled while the list is non-empty and, when empty, opens a confirmation dialog that calls `POST /v1/investors/{id}/close` through `withFreshAssertion`. The blocker list is the API's; the page never decides that an account is closable.

**ACC-02 Recover account (`/account/recover`, drawn by A50)**

- The wallet-recovery stepper (SM-13), not the sign-in recovery at `/recover-login` (A52). The page sits in the session-gated `(investor)` group, so a person with no working device reaches it only through login recovery: A52's sign-in error state already links "No passkey found on this device" to `/recover-login` (this node adds no "Can't sign in?" link, because anyone on ACC-02 is already signed in). Handoff, requested of A52 as a follow-up: when `/recover-login` completes, it lands on `/account/recover?start=wallet` with "Start wallet recovery" pre-selected when `GET /v1/wallets/me` shows no usable wallet key on this device; the `start` value is an allow-listed enum, never an identifier. The fresh assertion for "Start recovery" is then made with the new login passkey. A05's HorizontalStepper with the four labels Verify you / Guardian approval / Wait 48 hours / New passkey, driven only by `GET /v1/wallets/recovery/{id}` `step` and `fallback`; the page has no ordering logic of its own. Spec point (e): A29 registers the new wallet passkey before the CCO approval while the design draws "New passkey" last; the proposed reading is that the fourth step shows as done once `new_owner_key_id` exists and the final screen is "Your wallet is back", and the choice is recorded at Specify.
- Start: "Start recovery" (reason `passkey_lost`) calls `POST /v1/wallets/recovery` through `withFreshAssertion`; `RECOVERY_IN_PROGRESS` opens the existing request instead. Step content in DropBox-style centred panels: **verify** runs the liveness capture and `POST .../reverify`; **new passkey** runs the wallet-purpose registration ceremony and `POST .../new-key`; **guardian** shows "Waiting for RealX approval · once the 48-hour wait starts you can cancel it from any signed-in device"; **wait** shows the countdown to `timelock_until` in Geist Mono, computed from the server's `timelock_until` and the server time in the response (a client clock set forward cannot shorten what is shown, and each reload re-reads the server).
- **Cancel recovery** (danger) renders only when `GET /v1/wallets/recovery/{id}` returns `cancellable: true` (field requested from A29 as a follow-up; until it lands, `tables.ts` holds one closed row mapping `state = waiting_period` to cancellable, removed when the field arrives). Today A29's WR machine allows a cancel only as `waiting_period -> disputed`, which is inside the `wait` step; in the `guardian` step (`compliance_approval`, `proposing`) there is no transition, so no button is shown there. The design's Cancel on step 2 is recorded in `A59.qa.md` as a design deviation. Follow-up raised to A29 and A03: an additive "holder withdraws or objects before the timelock" transition from `requested`, `triage`, `identity_reverification`, `awaiting_new_key`, `compliance_approval` and `proposing` to `disputed`, so a victim can stop a hijacked recovery before the wait; when it lands, `cancellable` turns true in those states and the button appears with no code change here. The button calls `POST /v1/wallets/recovery/{id}/cancel` after a confirmation dialog; the result is `disputed`, rendered red "Recovery paused · someone cancelled it. Our team will contact you on your registered details." ## Node-specific challenges (node QA)

- **Withdrawal to somewhere else (money, G13, security).** With a stolen session cookie and no passkey, the node QA (i) submits the withdraw dialog, (ii) replays a captured `POST /v1/me/withdrawals` with a new idempotency key, (iii) adds `destination: {bsb, account}` to the body, (iv) changes the bank account and then withdraws. (i) and (ii) must stop at the fresh-assertion ceremony with `FRESH_ASSERTION_REQUIRED` and no reservation; (iii) must reach only the verified account or be refused; (iv) must stop at the bank-account step-up. Then, with a valid passkey, a A$50,000.00 request must show the second-approval sentence from data and the row "Processing", and changing `second_approval_cents` to A$40,000 in configuration must change the sentence on the next load with no deploy.
- **Tipping-off through six pages (compliance, G02, G14).** For the seeded holder under AML-118 (cash `under_review`, a withdrawal `held: aml_restricted`, a deposit held, wallet frozen, a redress held, an open AML matter as a close-account blocker) and an ordinary investor whose withdrawal is held only for name mismatch, the rendered HTML, the accessibility tree and the network responses the pages request are searched for "AML", "sanction", "PEP", "118", "case", "screening", "restricted" and the MLRO's note text; any hit fails the node, the Withdraw button must be enabled for both, and the restricted holder's screens must be indistinguishable from an ordinary under-review investor's apart from amounts and dates.
- **Recovery race (security, SM-13, G13).** An attacker who has the victim's email starts a wallet recovery; the victim, signed in on a laptop, sees the ACC-02 banner and cancels during the wait; separately the attacker sets the device clock 48 hours ahead and reloads, and tries to register a new passkey and remove the RealX guardian while the request is open. Expected: no Cancel is offered while the request is in the `guardian` step (the API reports `cancellable: false`; a forged cancel there is refused by A29 and rendered as its plain sentence); once it reaches `waiting_period` the cancel moves the request to `disputed` on the next load of every device; the countdown still shows the server's remaining time; guardian and key changes render `GUARDIAN_LOCKED_DURING_RECOVERY` and `WALLET_RECOVERY_PENDING`; no screen offers "Complete now"; an agent token calling start, re-verify or new key gets `AGNT_NOT_ALLOWED`, while the same token may call cancel (it only narrows).
- **The agent that hides its tracks (D04, G22).** The investor's agent "Rebalance bot" requests a A$4,000 withdrawal under a mandate with no signing key, then calls `read-all` on notifications and `PUT` preferences to mute agent email, then tries to change the bank account and to add a wallet passkey. Expected: the withdrawal call returns `428 CONFIRMATION_REQUIRED` and creates no row; the POR-05 banner "Your agent Rebalance bot asked to withdraw A$4,000.00 · Review" links to A60's confirmation (or, while A12's pending-confirmations list is absent, the ACC-03 agent notice does); `read-all` returns `skipped_protected` and ACC-03 still shows the agent notice unread with the "Always on" lock; `COMMS_TYPE_MANDATORY` is returned; the bank and passkey calls are refused before scope evaluation; the ledger row after confirmation carries "by your agent Rebalance bot" before and after the token is revoked.
- **Frozen reason laundering (compliance, design).** The fixture returns `frozen_reason: "aml_freeze"` and then `"Frozen by MLRO under AML-118"` for a holding on POR-06: both must render "Not available" and fail the contract test naming A29; the "listed for sale", "locked until 3 Oct 2026" and "legal hold" fixtures must render their generic words; no component accepts a free-text reason.
- **Close account with money left (money).** An investor with A$0.01 available, one held withdrawal and an open ticket opens Close account: the three blockers render in plain words, the button is disabled, and a forged `POST /v1/investors/{id}/close` from the browser console with a valid passkey must be refused by the API with the blockers (the page never closes on its own logic); after the blockers clear, closing requires the passkey and lands on the signed-out page.
- **AFCA deadline (compliance, G18).** With the injectable clock, a complaint received on 30 Sep 2026 shows the small AFCA line until the response-due date and the prominent Banner from the first load after it passes, and also after `response_issued` and in `escalated_external`; changing the AFCA phone in A44's data row changes the screen text with no code change; a person with no complaints still sees the AFCA line; using the AFCA option on a `response_issued` complaint opens only the contact card (external link and phone) and the network log shows no investor-side write to any `/afca` route.
- **Design drift (design fidelity).** Screenshots of `/wallet` at 1240 px are compared with the prototype's `wallet` view and the other five pages with A50's drawings by the token-level harness: a changed font family, the PayID chip not in Geist Mono on cream, "Withdraw funds" styled as primary, a status pill outside the TONE map, the wallet-passkey count and the sign-in-passkey count swapped, or page-level horizontal scroll at 375 px fails; a differing mock name does not.
