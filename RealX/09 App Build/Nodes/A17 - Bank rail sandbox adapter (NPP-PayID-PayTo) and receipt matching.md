# A17 - Bank rail sandbox adapter (NPP/PayID/PayTo) and receipt matching

**The bank rail behind a swap point: one adapter interface for PayID issuance, receipt feeds, payouts, statements and webhooks (with a P1 PayTo stub); a sandbox bank that can receive, delay, return and double-deliver payments on command; and a payments module that classifies every bank line, auto-credits an investor's client-money cash only when the payer's name matches a verified name under a written name rule and the amount is below A14's manual-match threshold, puts every other receipt into A16's suspense account so the bank and the ledger always agree, routes non-exact and large matches to the CFO, owns the investor's nominated withdrawal account (a non-delegable change), gives A37, A39 and A40 one in-process payout primitive that cannot skip G02, and hands AML the TTR, third-party-deposit, rapid in-out, structuring and international (IFTI) lines.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Money. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 14-20 agent-hours (build, challenge and verify loops). The build splits by folder into an adapter-and-sandbox part (`packages/adapters/bank`) and a payments-module part (`modules/payments`); the orchestrator may run them as two sub-nodes A17a and A17b under one gate if the first loop overruns.

**Depends on:** [[A16 - Client-money ledger (double entry)]], [[A08 - Sandbox adapter framework, config and phase flags]], [[A10 - Append-only hash-chained audit log]], [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]], [[A13 - Alerts and SLA-clocks service]], [[A14 - Approvals engine and maker-checker (SM-00)]], [[A19 - Rules engine- gates G01-G22, rule packs, threshold monitors, simulator]], [[A22 - Identity-DVS and sanctions sandbox adapters]]
**Unlocks:** [[A20 - Three-way reconciliation engine with zero tolerance]], [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A37 - Orders, escrow, allocation and refunds (SM-05)]], [[A39 - Treasury- withdrawals, escrow release, client-money reconciliation]], [[A41 - Tax engine- profiles, withholding, AMMA and CRS-FATCA]], [[A42 - AML screening, monitoring, cases and SMR clocks (SM-11)]], [[A48 - Halts, kill switches and wind-down]], [[A56 - Onboarding flow ONB-01 to ONB-10 with entity branch]], [[A95 - P3- Auto Invest and PayTo mandates]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A17\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder; the cases are published into the repo only after the gate passes. The three oracle invariants are: (1) a receipt that fails the name rule, or that is at or above A14's manual-match threshold, never auto-credits `investor_cash` or any wallet; it posts exactly one `deposit.unmatched` journal (`bank_mirror` / `suspense_unmatched`) in the ingest transaction, so the bank statement and A16's ledger stay equal to the cent; (2) matching is idempotent under webhook retries, re-polls and re-ingested statements, a repeated key with different content is refused, never silently skipped, and every bank undo uses A16's bank-fact rows (never `reverseJournal`); (3) no payout reaches `submitted` without an unexpired G02 screening reference for the right subject, the destination its purpose allows, and the approval its purpose requires.

Money in this node is sandbox money. No bank, no NPP participant, no real client-money trust account and no real PayID is touched; a Monoova or Zepto-type rail is reached later through the same interface after HG-VENDOR and HG-CAPITAL. The ledger is [[A16 - Client-money ledger (double entry)]]'s; this node posts bank facts into it by calling A16's `index.ts` exports in-process with an `SVCA` origin, and never writes balances itself. This plan is not legal advice.

**Sandbox bank (packages/adapters/bank/sandbox)**

- Four seeded accounts matching the design's ADM-18 table: `client-money-wallets` (Bank A ••2201), `offer-escrow` (••2202), `distributions` (Bank B ••8810) and `realx-operating` (••8811, flagged `not_client_money`). **Opening balances are loaded from A06's `bank-balances.json` by `SandboxControl.reset(seed)`**, never typed into this folder; `SandboxControl.state()` returns per-account balances in the same shape as `bank-balances.json`, which is what A23 compares. A06's seeded bank lines (the seeded day's NPP credits and the AML scenario lines) are delivered by `reset(seed)` through `trigger('receive', …)` and so through `ingestTransaction`, never inserted into the payments tables directly. The ledger's matching opening position is A06's and A16's. Balances and lines persist in the sandbox's own Postgres tables (A08 storage conventions), never in the ledger's tables. The sandbox can also post bank-originated lines: `trigger('interest', { accountRef, amountCents })` and the credit leg of an internal transfer on the destination account when an `internal_transfer` payout settles.
- Virtual accounts: one PayID and one deposit reference per investor, always bound to `client-money-wallets`; a second `createVirtualAccount` for the same investor returns the existing PayID (idempotent). PayIDs for suspended investors reject inbound credits with a rail-level `return` scenario.
- **Receive endpoint and console panel.** `SandboxControl.trigger('receive', { payId | accountRef + reference, payerName, payerBsb, payerAccount, amountCents, reference, rail, originCountry? })` creates a credit, emits the webhook and appears in `listTransactions`. A09 mounts it at `/sandbox/bank/receive` in `RUN_MODE=local|test` only (never in the public OpenAPI, the SDK or the MCP server); the ADM-32 sandbox panel (built later in A69) uses the same call. The payload's `payerName` is free text so tests can send the wrong name.
- **Scenarios** via the markers above, parsed only by A08's `scenarioOf()` inside `sandbox/`: reference `SIM-DELAY-<seconds>` or amount ending `.13` delays the webhook and the transaction's appearance by that long (default random NPP delay under the injected `SeededRandom`, 2-90 s, so "arrives in under a minute" is the common case, not the only case); `SIM-RETURN` or `.99` posts the credit, then a matching debit `return` event after a configurable interval (default 6 h of injected clock); `SIM-MISMATCH` swaps the payer name for a planted third-party name; `SIM-DUP` delivers the same webhook event id three times, once out of order with the next event; `.77` splits the amount into two partial credits with **distinct** `bankTxnId`s (`<parent>-P1`, `<parent>-P2`) that both carry `parentBankTxnId`, each matched on its own; `SIM-CASH` marks the line `rail = cash` (over-the-counter deposit) for the TTR path; `SIM-INTL` marks the line `rail = swift`, `international = true` with the `originCountry` from the payload (default `NZ`) for the IFTI path; name suffix ` SLOW` on the payout destination delays settlement; a payout to BSB `000-000` fails with `invalid_account`, to account `99999999` returns after settlement (`returned_payout`).
- **Webhooks.** Events `credit.received`, `credit.returned`, `payout.settled`, `payout.failed`, `payout.returned`, `mandate.authorised`, `mandate.cancelled`, `statement.ready`, each with `eventId`, `occurredAt`, `bankTxnId`, HMAC-SHA256 signature over timestamp plus body with a sandbox secret from the `kms` adapter, and at-least-once delivery with retries and jitter. The sandbox keeps a delivery log the operator panel can replay.
- **Daily statements** cut at midnight Australia/Sydney from the injected clock (so AEST and AEDT are both correct and a 23- or 25-hour day loses and repeats no line): opening, every line since the last cut, closing, `statementId`, SHA-256 of the canonical file. `statement.ready` fires after generation. The statement is the bank-side snapshot A20's rule R10 reads; this node produces and ingests it.
- **PayTo mandates (P1 stub)** are implemented in the sandbox only as the lifecycle A95 needs (create → `pending_authorisation` → `active` after the payer "authorises" through the panel → `cancelled`; a debit against an active mandate is a `credit.received` with `rail = payto`). The sandbox does not know about phases; the API does.

**Payments module (services/api/src/modules/payments)**

- **Data.** `BankAccount` (the four accounts, `purpose`, `is_client_money`, `bank_label_masked`, sandbox `deposit_bsb` and `deposit_account` for `client-money-wallets`), `VirtualAccount` (investor, PayID, `deposit_reference`, account, state `active` | `suspended`), `NominatedAccount` (below), `BankTransaction` (one row per `(rail, bankTxnId)`, unique; `parent_bank_txn_id`, `account_ref`, `receipt_class`, `international`, `origin_country`, `payer_name_enc`, `payer_account_enc`, `payer_key_hash` (below), masked views, `amount_cents`, `value_date`, `direction`, `content_sha256`, `match_state`, `hold_reason`, `open_approval_id` (unique among open requests, so one A14 request per `bankTxnId`), `matched_investor_id`, `ledger_journal_ids[]`, `statement_id`), `MatchAttempt` (each evaluation: inputs hash, name parts compared, the name form that matched, rule version, outcome), `Payout` (`purpose` per the table below, destination masked, `nominated_account_version` where relevant, `screening_result_ref`, `screening_subject`, `approval_id`, `line_ref` where relevant, `authorisations[]`, `state`, `rail_payout_id`, `ledger_journal_id`), `WebhookEvent` (`event_id` unique, `body_sha256`, `received_at`, `processed_at`, `outcome`), `Statement`, `AmlIntakeLine` (schema below). Every write carries the A08 correlation id; every row has `tenant_id` (platform tenant for client-money rows) per A04.
- **Ingestion is idempotent by construction, and conflicts are loud.** A webhook, a `listTransactions` poll (worker job every 60 s as the fallback to webhooks) and a statement line all funnel into one `ingestTransaction(txn)`. It computes `content_sha256` over the fields every source carries (account, direction, amount, value date, reference, payer-account digest). A new `(rail, bankTxnId)` is inserted and classified in the same database transaction; the same key with the same hash is a no-op; the same key with a **different** hash is refused with `BANK_TXN_CONFLICT`: the stored row and the ledger are unchanged, a Sev1 integrity alert goes out through A13 (`dedupKey = bank_txn_conflict:<bankTxnId>`) and one audit event is written. Webhooks do the same with `body_sha256`: a duplicate `eventId` with the same body is recorded and answered `200 duplicate: true`; the same `eventId` with a different body is refused with `WEBHOOK_EVENT_CONFLICT`, a Sev1 alert and an audit event. Out-of-order delivery (a `credit.returned` before its `credit.received`) parks the return as `awaiting_original` and resolves it when the original arrives, within the same idempotent path.
- **Receipt classes, evaluated first by destination account and reference** (`classify.ts`, pure):
  1. `distribution_funding` — a credit to `distributions` (••8810). The reference is resolved through `DistributionFundingProvider`; the payer name must pass the name rule below against `payerNames`; the amount must equal `expectedCents`. Match → `distribution.fund` (`external_ref = bankTxnId`). Unknown reference, payer mismatch or amount mismatch → `held: distribution_unknown_reference | distribution_payer_mismatch | distribution_amount_mismatch` with `deposit.unmatched` on that account's suspense. A held sponsor funding is resolved only by return to payer and a fresh payment, because A16's catalogue has no suspense-to-`distribution_payable` row (see Skipped).
  2. `interest` — a line with `txnKind = interest` on a client-money account → `interest.float` (`bank_mirror` / `float_interest_payable`). Interest on `realx-operating` goes to `OperatingReceiptSink` with no client-money journal.
  3. `internal_transfer_in` — the credit leg on the destination account of an `internal_transfer` payout (reference = the payout id). A17 links it to the payout and posts nothing: A39 posts `bank.internal_transfer` on `payout.settled`, and A16's unique `(journal_type, external_ref)` turns any second post into a replay. A credit claiming a transfer reference that matches no payout → `held: unknown_destination`.
  4. `operating_receipt` — any customer credit on `realx-operating` → `OperatingReceiptSink`; never matched to an investor and never posted to a client-money account.
  5. `investor_deposit` — any customer credit on `client-money-wallets`, by PayID or by BSB and account with the investor's `deposit_reference`; the investor path below. A customer credit to `offer-escrow` with no transfer reference → `held: unknown_destination`.
- **Name rule (`matching/name-rules.ts`, data; the same rule serves receipts, distribution funding and the nominated account).** No fuzzy score: every comparison is exact equality between normalised strings, and every comparison is recorded in `MatchAttempt`.
  - *Normalise:* upper case, strip diacritics (NFKD), punctuation to space, collapse whitespace, drop the honorifics stop-list (`MR MRS MS MISS DR`) and a leading `THE`; canonicalise entity suffixes from a table (`PROPRIETARY LIMITED`, `PTY. LTD.` → `PTY LTD`; `LIMITED` → `LTD`). `PTY`, `LTD` and `ATF` are no longer stop-words.
  - *Split:* the payer name is split into parts on the separator list `&`, `AND`, `+`, `ATF`, `AS TRUSTEE FOR`, `ITF`; each part is compared on its own.
  - *Person forms:* for each verified person the rule generates the accepted forms — full legal name (given, all middle names, family); given plus family with every middle name omitted; given plus middle initials plus family. So for Alex James Morgan, `ALEX JAMES MORGAN`, `ALEX MORGAN` and `ALEX J MORGAN` match. An initial in place of the given name (`A MORGAN`) is **not** a match form while `name_rules.accept_initial_given` is `false` (the default; an MLRO question, below).
  - *Individual:* the payer is one part equal to a person form of the investor.
  - *Joint:* every part equals a person form of a distinct holder of the account (so `ALEX MORGAN & SAM MORGAN` and a single holder's own `ALEX J MORGAN` both match); any part that is not a holder fails.
  - *Company, trust, SMSF:* every part equals a verified entity name (`investor_entity`, `trustee_company` or `fund_or_trust`) or a person form of a verified individual trustee, **and** at least one part is the investor entity or the fund or trust name. So `X PTY LTD ATF Y SUPER FUND` and `JANE SMITH & JOHN SMITH ATF SMITH SUPER FUND` match; a trustee's personal name alone (`JANE SMITH`, the payer's own account) never auto-credits an entity: it is held `entity_payer_personal_name`, which is AML-related (third-party-deposit line, AML clearance needed), and whether such a payment may ever be credited is an MLRO and counsel question (below).
  - *Partial:* a payer whose every part would match only under the initial-given form is held `payer_name_initials_only`, which is **not** AML-related (no third-party line) but is not exact, so it needs the CFO route.
- **Investor matching engine** (`matching/*.ts`, pure functions over typed inputs so the node QA's oracles can feed synthetic receipts). Order of evaluation: (1) resolve the PayID or deposit reference to a `VirtualAccount`; none → `held: unknown_destination`. (2) Investor state from `InvestorFactsProvider` must be `active` or `pending_first_deposit`, and `RestrictionProvider.restrictionStatus` must be `none` or `payouts_held`; `suspended`, `closed` or `full` → `held: investor_restricted` and an AML hint. (3) Name rule above; a mismatch → `held: payer_name_mismatch` and an AML `third_party_deposit` line (or the entity and partial reasons above). (4) **Manual-match threshold:** the amount is checked against A14's resolver for `suspense.resolve` with `{ amount_cents, match_exact: true }`; when the resolver says an approval is needed (default A$10,000.00 and above), the receipt is `held: large_receipt_review` (not AML-related) and is moved later by `suspense.resolve` under `4E` TRSY → CFO, exactly as A16's `deposit.matched` row requires. A17 keeps no copy of the threshold and no config key for it. (5) **Every hold posts exactly one `deposit.unmatched` journal** (`bank_mirror` of the receiving account / `suspense_unmatched`, `external_ref = bankTxnId`) in the ingest transaction; nothing is ever credited to `investor_cash` or a wallet by a hold (oracle invariant 1). (6) An exact match below the threshold → exactly one `deposit.matched` journal through A16 (`bank_mirror` / the investor's `investor_cash`, `external_ref = bankTxnId`, no approval id); A16 would refuse it with `LDG_APPROVAL_REQUIRED` at or above its manual-match row, so a refusal of that kind is a spec breach, not a fallback. The journal id is written back on the `BankTransaction` in the same transaction. (7) Emit `payment.credited { investor_id, bank_txn_id, amount_cents, journal_id, route: 'auto' | 'manual' }` on the outbox for A37 and notifications. This node does not touch orders or reservations.
- **Manual match (follows A16's `suspense.resolve` row).** `POST /v1/payments/receipts/:id/match { investorId, reasonCode, evidenceRef }` by TRSY (human, or TRSY's agent as maker) on a held `investor_deposit`:
  - The `BankTransaction` row is locked `FOR UPDATE`. A receipt already in `manual_match_pending` is refused with `409 MATCH_PENDING` carrying the open approval id; one already matched with `409 ALREADY_MATCHED` carrying the journal id. There is at most one open A14 request per `bankTxnId`.
  - If the hold reason is AML-related (`payer_name_mismatch`, `investor_restricted`, `entity_payer_personal_name`), `AmlClearanceProvider.clearanceFor` must return `cleared` first; `pending` → `409 AML_CLEARANCE_REQUIRED` with no state change and a plain message that says only "This receipt is waiting for a compliance review" (no reason, to avoid tipping off).
  - The journal is `suspense.resolve` (`suspense_unmatched` / `investor_cash`, `external_ref = bankTxnId`). A `4E` request TRSY → CFO (action code `suspense.resolve`, `object_ref = bank_transaction:<bankTxnId>`, `amount_cents` equal) is required whenever A14's resolver says so: every non-exact match (`payer_name_mismatch`, `payer_name_initials_only`, `entity_payer_personal_name`, `unknown_destination`) at any amount, and every match at or above the manual-match threshold (including `large_receipt_review`). The only case TRSY may resolve alone is an exact name-and-destination match below the threshold whose hold reason has been cleared (for example `investor_restricted` after the restriction is lifted); A16 accepts it without an approval id and the action is audited.
  - The journal posts only through A14's effector when the request is `approved`; the receipt sits in `manual_match_pending` until then, and a `rejected` or `expired` request returns it to `held` with the same reason. The effector re-checks at posting time that the receipt is still `manual_match_pending`, the investor has a live `investor_cash` account and is not `full`-restricted; otherwise it posts nothing and alerts TRSY (Sev2) to cancel the request.
- **Return to payer.** `POST /v1/payments/receipts/:id/return { approvalId }` is the payout step of A39's "Return unmatched funds" action: A39's route creates the `4E` request (`suspense.return`, TRSY → CFO) and, on approval, posts A16's `suspense.return`; A17's route then refuses unless the approval is `approved` with `object_ref = bank_transaction:<bankTxnId>`, A16 shows the `suspense.return` journal posted under that approval id, and, for an AML-related hold, `AmlClearanceProvider` returns `cleared`. A receipt in `manual_match_pending` is refused with `409 MATCH_PENDING`. It creates a `return_to_payer` payout to the originating BSB and account only, never to a typed-in destination (`422 RETURN_DESTINATION_MUST_BE_PAYER`). Until A39 exists, A17's tests create the approval through A14 and post `suspense.return` through A16's `postJournal` with a test `SVCA` origin standing in for A39.
- **Returned credits (bank facts only; never `reverseJournal`).** A `credit.returned` for a receipt still in suspense (`held` or `manual_match_pending`) posts A16.x's `deposit.returned_unmatched` (`suspense_unmatched` / `bank_mirror`) and moves the receipt to `returned_by_bank`; an open manual-match request is left for its effector to refuse and TRSY is alerted. A `credit.returned` for a matched receipt (auto or manual) posts `deposit.returned` (`investor_cash` / `bank_mirror`, linked to the original by `reversal_of`). If A16 refuses with `LDG_INSUFFICIENT_AVAILABLE` (the money is reserved in offer escrow or held) or `LDG_ACCOUNT_FROZEN`, the return is parked as `reversal_pending`, a Sev2 alert goes to TRSY, an AML hint is written, and `payment.reversal_pending` is emitted for A37 to unwind the reservation. A37 then calls `completePendingReversal(bankTxnId)` (an in-process function exported from `index.ts`), which retries `deposit.returned` once; balances never go negative silently.
- **Ageing and alerts.** An hourly job flags any receipt in `held` or `manual_match_pending` older than 48 h with a Sev2 alert to TRSY and CFO through A13's `emit` (`dedupKey = payments.held:<bankTxnId>`, so it is raised once per receipt), and re-raises it as Sev1 at `businessDaysAfter(received_at, 5, 'AU-NSW')` with "return to payer" as the proposed action. ADM-18's queue orders held receipts by age.
- **AML intake (G14).** Every receipt and payout writes one or more `AmlIntakeLine` rows and emits `payment.aml_intake` on the outbox for each (A42 consumes the event and the public `index.ts`, never A17's tables). Schema: `{ line_id, kind: 'receipt' | 'payout' | 'ttr_candidate' | 'third_party_deposit' | 'rapid_in_out' | 'structuring' | 'ifti_candidate', investor_id?, bank_txn_id?, payout_id?, amount_cents, rail, international, origin_country?, payer_key_hash?, window_start?, window_end?, related_refs[], rule_version, occurred_at, sandbox: true | false, tipping_off: true }`. Rules, with every number a config key in the `payments.aml` section: `ttr_candidate` for any single credit at or above `payments.aml.ttr_candidate_cents` (default 1,000,000) or any line with `rail = cash` (whether an electronic NPP credit is a reportable "threshold transaction" or only a monitoring input is an MLRO and counsel question, recorded in the evidence, not decided here); `third_party_deposit` on every name mismatch and every `entity_payer_personal_name` hold; `rapid_in_out` when a payout for an investor is requested for `payout_cents ≥ payments.aml.rapid_in_out_pct` (default 80 %) of any single credit to that investor received within `payments.aml.rapid_in_out_hours` (default 24); `structuring` when credits from one payer key sum to at least `payments.aml.structuring_sum_cents` (default 1,000,000) within `payments.aml.structuring_window_hours` (default 24) while each is below it; `ifti_candidate` for every credit with `international = true` (the line carries A42's `international` flag, so A42's `ifti` item and `ifti_10bd` clock work on it; in P1 every such line is marked `sandbox: true` because no international rail is contracted, and A96 makes the rail real). Who lodges an IFTI, RealX or the receiving ADI, is an HG-LEGAL question (below). **Payer identity** (`payer_key_hash`) is SHA-256 of the normalised BSB and account number; when the bank line has no account number (cash, some statement lines) it falls back to SHA-256 of the normalised payer name. Lines carry the tipping-off ACL flag so investor-facing surfaces never see them.
- **Nominated withdrawal account (the only payout destination for an investor).** `NominatedAccount` rows are versioned (`investor_id`, `version`, `bsb_enc`, `account_number_enc`, `account_name`, masked `••4471`, `bank_label`, `name_check_attempt_id`, `state` `active` | `superseded`, `fresh_assertion_id`, `created_by`, `created_at`); a change inserts a new version and supersedes the old one, never edits it. `POST /v1/payments/nominated-account { bsb, account_number, account_name }` (A56's ONB-09 and A59's ACC-01 call it) is A03's `ACC.bank.change`, which A03 marks `delegable: false`; A09 therefore emits `x-realx-requires-human` from A03's value (not from a hand-set flag), and any agent or API token is refused (`403 G22_SCOPE_NON_DELEGABLE`; a token asking for the scope is refused at issue with `SCOPE_NON_DELEGABLE`). The route requires A11's `requireFreshAssertion({maxAgeMinutes: 10, purpose: 'bank_account_change'})`. The account name must pass the name rule above against the investor's verified names (joint and entity composites included; an individual trustee's personal name alone does not qualify for an entity) (`422 NOMINATED_NAME_MISMATCH`, with the plain message "The account name does not match your verified name"; this is not an AML matter). Each change writes one audit event, notifies the investor through the outbox (`payment.nominated_account.changed`, consumed by A43 for email and in-app notices), and any payout to the old version that has not reached `submitted` is refused at submit with `PAYOUT_DESTINATION_SUPERSEDED` and returned to its caller. `GET /v1/payments/nominated-account` returns the masked view only.
- **PayID issuance.** On `investor.verified` (through `InvestorFactsProvider`) a worker handler issues the PayID; `POST /v1/payments/payids/me` does the same on demand and is idempotent (a second call returns the existing PayID). Both run G01 (verified identity) and G02 (sanctions clear) through A19 and require `restrictionStatus = none`; otherwise nothing is issued and the investor sees `409 PAYID_NOT_ISSUED` with the ONB-09 text "Your PayID appears once your identity is verified" (the same response for unverified and restricted investors, so no hold reason leaks). Issuance writes one audit event and emits `payid.issued`.
- **Payout primitive (G02 before every payout; in-process only).** `createPayout` is an in-process function exported from the module's `index.ts` and nothing else: there is no HTTP route for it, so it cannot appear in the OpenAPI document, the SDK or the MCP server. It accepts only an `SVCA` origin of A37, A39 or A40 (from A09's request context, never a caller field) or A17's own return route; any other principal is refused with `PAYOUT_CALLER_NOT_ALLOWED`. It refuses without a `screening_result_ref` from A22 for the purpose's screening subject no older than A19's `screening_max_age_h` (default 24 h), without the destination its purpose allows, and without the approval its purpose requires; it never queues a payout "pending screening". The check is a `GateEvaluation` through A19. Approval tiers are A14 policy rows read through the resolver; A17 holds no threshold. Per purpose:

The routes are `money` and `sensitive`, so A12 emits `agent.action.money` and the person is notified of every agent-initiated match or return (A101 and A43). **No agent is ever checker or approver:** every CFO decision goes through A14, which refuses any token or agent principal with `APR_CHECKER_MUST_BE_HUMAN`, and segregation of duties counts an agent as its human, so a person who holds both TRSY and CFO cannot approve a request their own agent made (`APR_MAKER_IS_CHECKER`, A14's code, through A11's `eligibleCheckers`). The product map lists ONB-09 "Set up PayTo" as a P1 action (G02) and the founder context names PayTo among the first AUD rails, while the build graph places PayTo mandates in A95 (P3); this difference is recorded as a founder question (below), and the flag moves only on that decision (plus HG-VENDOR for a PayTo-capable rail). The module exports `registerPayToHandler(handler)` so A95 registers its implementation behind the same route and contract without editing this folder; A95's `packages/adapters/payto` port becomes the PayTo swap point, and money it collects still reaches the wallet only through `ingestTransaction` and the name rule.
- **Jobs (M26)** registered with the worker: `bank.poll` every 60 s per account, `bank.statement.ingest` at 00:30 Australia/Sydney (after the midnight cut and before A20's 02:00 run), `payments.aging` hourly, `payments.payout.poll` every 60 s for `submitted` payouts. Each job records last run, duration and outcome for ADM-32.
- **Empty and error states.** No PayID yet → `409 PAYID_NOT_ISSUED` with the ONB-09 prompt; sandbox not seeded → `503 BANK_NOT_INITIALISED`; webhook with bad signature → `401` and an audit event, no processing; duplicate event → `200` with `duplicate: true`; conflicting duplicate → `409 WEBHOOK_EVENT_CONFLICT` or `BANK_TXN_CONFLICT`; manual match on a receipt already matched → `409 ALREADY_MATCHED` with the journal id; match or return on a receipt with an open request → `409 MATCH_PENDING` with the approval id; manual match or return waiting for AML clearance → `409 AML_CLEARANCE_REQUIRED`; payout without screening → `422 G02_SCREENING_REQUIRED`; payout from a caller that is not allowed → `PAYOUT_CALLER_NOT_ALLOWED`; return to a destination other than the payer → `422 RETURN_DESTINATION_MUST_BE_PAYER`; nominated-account name mismatch → `422 NOMINATED_NAME_MISMATCH`; missing or stale passkey step-up → A11's `FRESH_ASSERTION_REQUIRED` / `FRESH_ASSERTION_STALE`; a fake provider bound outside `test` once its owner is built → `PROVIDER_FAKE_BOUND` at start-up. Every refusal carries a code and a plain-English message and never echoes payer account numbers.
- **Audit.** Every ingest, classification, match attempt, hold, manual decision, nominated-account change, PayID issue, payout transition, conflict and webhook rejection writes exactly one hash-chained audit event (A10) with `actor_id`, `on_behalf_of_id` and `token_id` for token or agent actions ("agent <token> on behalf of <person>"), `approval_id` where one applies and the `bankTxnId`, `payoutId` or nominated-account version as `object_ref`.

- Gate **G14 AML monitoring and reports**: done means every receipt and payout produces its intake line and `payment.aml_intake` event (TTR candidate, third-party deposit, rapid in-out, structuring, IFTI candidate) for A42 with the tipping-off ACL set, an AML-restricted investor's receipts are held and payouts refused, AML-related holds cannot be matched or returned without an AML clearance, and nothing about a hold's AML reason reaches an investor-facing response.
- Gate **G22 Agent authority**: done means every route above declares an A03 action id that resolves, its delegable flag comes from A03, agent match and return calls are capped and counted by the mandate in the same transaction, the person is notified of each, no agent can be checker, segregation of duties counts an agent as its human, and the nominated-account change and PayTo setup are refused to every token.
- Module **M16 Treasury and client money**: done means the four accounts, receipt classes, PayID issuance, receipt ingestion and matching with suspense posting, the name rule, holds and the 48 h alert, manual match with the CFO route, the return payout step, the nominated account, the payout primitive with its bank-outcome rows, returned-credit handling and the daily statement feed exist with their data contracts and pass the conformance and oracle suites; the reconciliation itself and withdrawal policy are A20's and A39's.
- Module **M26 Integrations and API**: done means the bank adapter appears in `adapterHealth()` and the ADM-32 connector table with implementation `sandbox` and each provider's binding, its manifest row is in `SWAP-POINTS.md` with Monoova/Zepto as candidates, HG-VENDOR as the gate and the PayTo note, its markers are in `MAGIC-INPUTS.md`, the four jobs report to the jobs table, and the webhook route is signature-verified with dedup and conflict detection.
- State machines: none owned. Done means the module's own transition tables (`BankTransaction.match_state`: `received → auto_matched | classified_posted | held(reason)`; `held → manual_match_pending → manually_matched | held`; `held | manual_match_pending → returned_by_bank`; `held → returned_to_payer`; `auto_matched | manually_matched → returned_by_bank | reversal_pending → returned_by_bank`; `Payout.state`: `requested → screened → submitted → settled | failed | returned`; `NominatedAccount.state`: `active → superseded`) are data registered with A03's state-machine runner, every forbidden transition is refused, and the `payment.credited` event is the trigger for SM-05's `awaiting_funds → funded` in A37.
