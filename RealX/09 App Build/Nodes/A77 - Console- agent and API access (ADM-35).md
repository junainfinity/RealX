# A77 - Console: agent and API access (ADM-35)

**ADM-35 "Agent and API access" in the operator console, built from design extension B with the MandateTable block: a staff member's own tokens, issued and widened only under a hardware-key assertion, with any token or widened mandate that carries a write family activated only when a SECO who is not the requester approves (`4E`); a SECO queue that approves or declines those requests; every token and mandate platform-wide with owner, principal type, tenant, scopes, today's use against its caps, last used, environment and status, with sandbox tokens kept apart from live ones; agent principals beside their human owners; the G22 evaluation log with every refusal and the missing scope or cap named; revoke any token at once with a reason; the anomaly queue, notice log, token holds and A101's user, tenant and user-type kill-switch tiers; the "all agent traffic" kill switch as `SGL+R` through the halts module with its 2 h ratification banner; per-tenant and per-investor rate-limit views; the platform agent policy with its `4E` change path; and the MCP tool catalogue exactly as A104 publishes it. Every action on the page is an API operation that a staff member's agent can call under the same rules, except the acts that must be a person's, and an agent is never the checker, approver, ratifier or signer.**

**Build status:** not started. **Milestone:** AM7 (Operator console). **Lane:** Operator console. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops): seven tabs, the create and widen flows, the SECO approval queue, five kill-switch tiers, the policy change flow and the parity manifest.

**Depends on:** [[A53 - Operator console shell, hardware-key sign-in and approval action pattern]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]], [[A51 - Design extension B- operator console screens not in the prototype]], [[A48 - Halts, kill switches and wind-down]], [[A67 - Console- users, roles, access reviews and break-glass (ADM-37)]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]], [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]], [[A104 - MCP server generated from the OpenAPI document]]
**Unlocks:** [[A78 - Operator journey J20 end to end in Docker (AM7 exit)]], [[A82 - End-to-end- an agent drives the account through the API and MCP]], [[A103 - Runbook drills R1-R9 executed on the stack]]

**Oracle rule:** this is not an oracle node (`oracle: no`): no money, supply or holdings move here, and every rule the page shows is decided by A12 (an oracle node), A14, A48 and A101. Authority does move here, though, so the node QA still writes hidden tests and Challenge fixtures to `<workspace>\gauntlet\hidden\A77\` from this note alone before the build starts ([[App Gauntlet]] §2): Playwright specs against the running stack with the sandbox authenticator (hardware-attested and software passkeys), a staff token issue, widen and approval persona set with self-approval and SoD traps, a kill-switch drill script for the user, tenant, type and platform tiers under the injectable clock across the 2 h ratification and the 4 h escalation, a policy-tightening clamp fixture, an anomaly-burst fixture, a tipping-off fixture, a secret-leak scan list, its own crops of the extension-B ADM-35 frames and an agent-parity table for every action on the page. The builder never reads that folder; the tests are published into `app/` only after the gate passes.

This node draws screens. It holds no business rule: who may hold which scope, whether a change widens a mandate, who may approve a staff token, when a kill switch acts and who ratifies it, what counts as an anomaly and who may clear a hold are all decided in the API (A12 for tokens, mandates and G22; A14 for maker-checker; A48 for the platform switch; A101 for anomalies, holds, notices and the user, tenant and type tiers; A104 for the tool catalogue; A99 for sandbox and docs). The page shows what the API decided, cites the rule or code the API names, and never lets a person believe a token, hold or switch has changed before the API says so. The person-facing token pages are A60 (ACC-05, SPN-16); ADM-37 (A67) lists staff tokens in the access review and links here. This note is not legal advice.

**3. Your tokens tab (staff self-service, D04)**

- The caller's own `MandateTable` rows (A12's `tokens` list for the caller), live and sandbox apart, with Rotate, Change limits, Revoke and Activity per row, the current mandate sentence from `mandateSummary`, and the version list.
- "Change limits" is a narrow or a widen, decided by the API, not the page. A narrow needs only the session. A widen (a scope, a higher cap, a vehicle, a longer expiry, a wider window, a removed IP restriction, a higher rate limit) runs `HardwareKeyConfirm` with purpose `mandate_widen` in its `attestation-required` variant over the mandate hash the API returned (the same hash check as at create). When the widened version adds any write cell, the new version renders as a second amber row under the current one, "Widening waiting for SECO approval · APR-…", while the current version stays in force and its sentence stays on the row; the write cells of the new version show "Not yet approved" and are refused by the API until a different SECO approves (A12.1's staff-widen rule, §1).
- "Create token" opens the five-step flow extension B draws: Name and agent / Scopes / Limits / Confirm with security key / Copy once. Scopes come from A12's per-viewer family listing: the caller's own module cells M01-M27 as family pills, each cell in one of five states from the listing: `selectable`, `not_yours`, `never_delegable`, `needs_counsel` or `phase_off` (grey, "Not enabled in this phase", G21, rendering `SCOPE_PHASE_OFF`; the enum tone test covers all five); approve, ratify, veto and execute-or-sign cells never render as rows, with the grey note "Agents never check, approve or sign". Limits: per-action and daily caps in A$ parsed to integer cents with A02's parser (no float), allowed vehicles, time windows in Australia/Sydney, expiry (default 90 days, the API's `max_expires_at` shown with its cause), IP allow-list, rate limit adjustable downwards only.
- Confirm runs `HardwareKeyConfirm` with purpose `token_issue` in its `attestation-required` variant: before the ceremony the feature recomputes A12's `mandateHash` of the displayed payload and refuses to start if it differs from the hash the API returned ("What you'd sign doesn't match what's on screen. Nothing was created."). A software passkey renders `ATTESTATION_REQUIRED`; a SUPER asking for a money, custody or signer cell renders `SOD_HARD_CONFLICT` with the API's rule text; `SCOPE_EXCEEDS_OWNER`, `SCOPE_AGENT_NEVER_CHECKER` (an approve or sign cell, which reads "Agents never approve"), `SCOPE_NON_DELEGABLE`, `SCOPE_PENDING_COUNSEL`, `SCOPE_PHASE_OFF` and `SCOPE_UNKNOWN` return to the Scopes step with the cell named, and `POLICY_CEILING` returns to the Limits step with the field named.
- Copy once: the WalletCard `ValueChip` with the full secret, a Copy button, the red Banner "Shown once. RealX stores only a hash.", and the connection details from A99 (REST base URL, MCP snippet for stdio and HTTP, SDK install line, the staff quickstart link). The secret handling rules are A60's, applied here unchanged: create and rotate called from a client component through the browser SDK client, never a server action or server component; the response excluded from the query cache; the secret cleared on unmount, on "Done", after five minutes hidden and on sign-out; never in storage, URL, history, analytics, console, error reports or the RSC payload; `Cache-Control: no-store`.
- A token with any write family is `pending` with "Waiting for SECO approval · APR-…" until a SECO who is not the requester approves (A12 §2, A14 `4E`); a read-only token is `active` at once, as A12 §2 freezes. The product map's row for this action says "Passkey plus the line manager's approval"; A12's frozen rule (hardware-attested key, SECO checker) wins, and the difference is recorded as Specify point (a) for the founder, not resolved in the page. A SECO requesting their own token sees "A second SECO must approve"; where no eligible checker exists the API's refusal renders verbatim and Submit is absent.
- Partners do not use this tab (§2, Specify point (f)). For the record, A12 §2's partner rule is: "the PARTNER principal creates with a fresh assertion; the token can carry only the partner's own cells and is limited to the partner's `partnerScope`"; TP-AUD and TP-OBS tokens are read-only and inherit the partner's time box as `expires_at`. There is no second-person step for partner tokens in A12; whether partner write tokens should follow the product-map "second person" row is recorded in Specify point (f) for the founder, and this page claims no such rule.

**4. All tokens and mandates tab (oversight)**

- `MandateTable` over `oversight/tokens` with `FilterChip` groups for owner type, tenant, status, environment (default `live`), family, write scope and anomaly. Columns exactly as `blocks.md` defines: Token (prefix `ValueChip`), Agent, Owner, On behalf of, Type, Tenant, Scopes (family pills), Today, Expires, Last used, Env (brick `sandbox`), State (A12's vocabulary through `toneFor`: `active` green, `pending` amber, `suspended` amber with hold class, `revoked` red with reason in words, `expired` grey). A status string outside the vocabulary renders nothing and fails the contract test. A "by owner type" summary table above it follows the product-map mock (User type / Tokens / Write scopes / State).
- Sandbox tokens (A99) never appear in the live table, the KPIs or the live evaluation log: the Env filter switches the whole tab to the sandbox partition with the brick pill on every row and the tab title "Sandbox tokens", and sandbox counts are shown only there.
- Row expansion: limits, caps used today with remaining, windows, IP list, signing-key presence, session-key policy, mandate versions (created, by whom, "widened with security key" or "narrowed", assertion time), open confirmations, the last 20 activity rows with `AgentMarker`, and links to the owner's Investor 360 (A68, for callers with `V` on that module) or tenant (A69).
- **Staff tokens awaiting approval** (a panel above the table, rendered for callers whose `GET /iam/me` has the check cell for `agent.token.create_staff`, and for each requester over their own requests): a `SplitListDetail` over `oversight/tokens?owner_type=staff&status=pending` plus pending staff mandate widenings.
