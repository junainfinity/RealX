# A106 - IAM admin API for ADM-37

**The service behind ADM-37 "Users, roles and access reviews" (M25): the staff directory with hardware-key status, dormancy and SoD state; immediate role revoke with a defined quorum floor; the protective single-person suspend (`SGL+R`) that may cross that floor; dormancy unlock and hardware-key re-enrolment as A14 requests; staff invitations as role grants; SoD violation lists and time-boxed SoD exceptions; the quarterly access review with reviewer self-exclusion and a signed result hash; the break-glass log, its reviewer set and the board notice; the "view as tenant" grant log; and a line-manager relationship on each staff user. Every route is an A09 route with an M25 scope, so a staff member's agent can draft under the same rules, and every act that must be a person's is `requiresHuman`. It draws no screen: [[A67 - Console- users, roles, access reviews and break-glass (ADM-37)]] renders what this node returns.**

**Build status:** not started. **Milestone:** AM3 (Business services). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-16 agent-hours (build, challenge and verify loops): about 25 routes, four A14 action codes with effectors, one quarterly job, the board-notice consumer, the quorum-floor evaluator, the reviewer-set rules and the hidden oracle.

**Depends on:** [[A03 - State machines, gate codes, approval codes and permission matrix as data]] (M25 cells, `sod.ts`, `approval-policies.ts`, `delegable.ts`), [[A04 - Database schema, migrations and row-level security]] (the M25 tables and `registerModuleSchema`), [[A11 - Authentication, sessions, RBAC and segregation of duties]] (principals, roles, sessions, SoD precheck, break-glass sessions, the dormancy job), [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]] (token introspection counts, the automatic-revocation path), [[A13 - Alerts and SLA-clocks service]] (Sev1 and Sev2 alerts, the review clocks), [[A14 - Approvals engine and maker-checker (SM-00)]] (requests, effectors, `required_checkers[]` re-resolution), [[A15 - Custody sandbox adapter and policy engine P1-P10]] (signer slots and the signer-set policy change), [[A25 - AgentGateway and owner multisig- approval IDs bound on-chain]] (the multisig signer-set selector), [[A43 - Communications, notifications, tasks and marketing claims (G17)]] (the board notice and post-session notice), [[A46 - Job scheduler, integrations health and webhooks]] (the quarterly access-review job)
**Unlocks:** [[A67 - Console- users, roles, access reviews and break-glass (ADM-37)]]

**Where this node comes from.** A67's spec (line 34) proposed this backend as its own node with the working id A11.1, because it is too large and too security-critical for a follow-up loop. The plan fixer gave it the id A106 on 24 Sep 2026 and placed it in AM3 with the other services, so the orchestration can run it (a dotted id that is not a loop of its owner is not used for a node). **It has not had an independent check yet**: it was written after the check run stopped, and it needs its own independent check before AM3 starts ([[Build Orchestration]] §2 treats a spec with no passed re-check as unconfirmed).

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A106\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The tests are published into `app/` only after the gate passes, so A67 and A78 re-run them as regression. The hidden set covers at least the invariants listed under the Gauntlet loop below.

This node holds authority logic over who can act in the console, so it is an oracle node. It decides nothing about a single token call (A12) or about a maker-checker request's own lifecycle (A14); it owns the administration of staff access. This plan is not legal advice; the board-notice wording, the independent reviewer and the access-review cadence are HG-LEGAL items.

## Build brief

**1. What this node reuses (no duplication of A11, A12 or A14)**

- From A11 (already specified there and not re-implemented): `GET /iam/me`, `POST /iam/roles/grant` (the assignment is created `pending_approval`; A14's effector calls A11's `activateGrant`), `GET /iam/roles/review-set`, the SoD precheck and its codes (`SOD_HARD_CONFLICT`, `SOD_SELF_GRANT`, `SOD_EXCEPTION_REQUIRED`), the `BreakGlassSession` endpoints and events (`iam.breakglass.activated`, `iam.breakglass.board_notice`, `iam.breakglass.closed`), `POST /iam/view-as-tenant`, the dormancy job and `ACCOUNT_DORMANT`, the role-expiry job `auth.role.expire`, and the rule that staff never use self-service login recovery.
- From A12: `introspect` for the count of live tokens a person owns (count only), and the automatic-revocation path that A12 runs on `iam.role.revoked`, `iam.account.suspended` and `iam.staff.reenrolled`.
- From A14: request creation, effectors, `required_checkers[]` re-resolution on open requests, and the agent-never-checker rule. From A15 and A25: the signer-set change request (`6E+Q`) whose `APR-` id a revoke or suspend returns.

**2. Schema (registered here; changes to A04-owned tables go through a loop)**

- New tables registered by this node through A04's `registerModuleSchema`, in its own migration folder: `sod_exception` (principal, rule, compensating control of at most 500 characters, `expires_at` at most 90 days, `approval_id`); `view_as_tenant_grant` (staff, tenant, reason, started, extended, ended and why, `session_id`); `access_review_item` and `access_review_decision` (decision `keep | reduce | remove`, reason code, `reduce_to`, decided by, `drafted_by_agent`, `confirmed_by`, effect reported); `staff_enrolment_invitation` (single use, 24 h, reason code); and **`staff_line_manager`** (staff principal, manager principal, `effective_from`, `effective_to`, `approval_id`).
- Columns on A04-owned tables (`access_review`: `reviewer_role`, `due_at`, `signed_off_by`, `result_hash`; `break_glass_session`: `drill`, `review_state`, `review_due_at`, `reviewer_principal_id`, `review_outcome`, `board_notice_state`, `board_notice_sent_at`, `post_session_notice_sent_at`; `account`: `suspended_at`, `suspended_by`, `suspension_reason`, `ratification_approval_id`) go through the next free A04 follow-up loop (`A04.n`), which the Specify step raises and checks in `status.json` before Build.
- RLS: `break_glass_session` rows and their review are visible only to CCO, SECO, CEO, the requester, the activators and TP-AUD (need to know); everything else follows A04's `app.platform_access` rules.

**3. Routes and effects** (every route declared through `defineRoute` with an M25 scope, so it is in `openapi.json`, `packages/sdk` and A104's MCP catalogue)

- `GET /iam/staff`, `GET /iam/staff/{id}` and `GET /iam/staff/summary`: cursor-paged, filters `principal_kind` (`staff`, `partner` once A98 exists, `service`, `agent`; the last two read-only and linking to ADM-35), `role`, `state` (`invited | active | dormant | locked | closed`, plus a `suspended` flag), `hardware_key` (`enrolled | not_enrolled | single_key`), `sod` (`clear | exception | violation`), `dormant_within_days`. Each row carries the masked email, roles with `granted_at`, `expires_at`, `granted_by`, `approval_id`, hardware keys by AAGUID label (never a full credential id), last sign-in, days to dormancy, active SoD exceptions, the count of live API tokens, the line manager, and `allowed_actions[]` for the caller, so no button is decided in the client. The summary returns the five KPI counts A67 shows.
- `POST /iam/roles/revoke` `{assignment_id, reason_code, note?, dry_run?}`: SUPER or SECO, immediate, protective, no checker (product-map M25 row). In one transaction: end the assignment, revoke every session of the person, fire `iam.role.revoked` (A12 revokes the token cells that role granted), re-resolve A14's `required_checkers[]`, and lock the account if it was the last role. The person is excluded from custody signing and on-chain agent calls at once, and a signer-set change request is opened through A15 and A25; the response carries its `APR-` id. `dry_run: true` changes nothing and lists sessions, token cells, open requests where the person is a required checker, custody signer slots and on-chain role memberships.
- **Quorum floor.** After a revoke, counting only principals `active` or `dormant` and never the subject: (i) at least 2 distinct principals each hold at least one of CCO, SECO or CEO (one person with two roles counts once); (ii) for every live A14 policy row, the distinct eligible checkers for each checker role set are at least the row's `minCheckerSets`. Otherwise `IAM_QUORUM_FLOOR`, naming the broken rule (`breakglass_holders` with the remaining count, or the policy row id and role). Suspend is the only path that may cross the floor.
- `POST /iam/staff/{id}/suspend` `{reason_code, note}`: `SGL+R`; actor SECO or CCO, never the subject, never an agent (`requiresHuman`, fresh hardware-key assertion, purpose `staff_suspend`). In one transaction: account `locked` with the suspension fields; every session, API token (A12, event `iam.account.suspended`), break-glass elevation and "view as tenant" grant of the person ended; custody signing excluded and a signer-set change request opened; the person removed as eligible checker from open requests. With `SUSPECTED_COMPROMISE` it bypasses the quorum floor, raises a Sev1 alert to CCO, SECO and CEO, and returns a break-glass hint when fewer than two uninvolved sealed-credential holders remain. Ratification by one of CCO, SECO or CEO other than the actor and the subject within A03's `approval.ratifyWithinMinutes`, else the named independent reviewer; an unratified suspend stays in force and escalates Sev1; a rejected ratification does not reinstate the account.
- `POST /iam/staff/{id}/unlock`: A14 request `iam.account.unlock` (`4E`, SECO maker, CCO or a second SECO checker; the person and their agents on neither side). The effector moves `dormant -> active` and sets the dormancy clock; the person must sign in with a hardware key within 72 h or the account returns to `dormant`. A suspended account cannot be unlocked.
- `POST /iam/staff/{id}/re-enrol`: A14 request `iam.staff.reenrol` (`4E`; maker SECO, or CCO when the subject is a SECO; checker CCO, a second SECO or CEO, never the subject or maker; reasons `KEY_LOST | KEY_DAMAGED | LEAVER_RETURN | SUSPECTED_COMPROMISE`). The effector revokes every login passkey, session and API token of the person (event `iam.staff.reenrolled`) and issues a single-use 24 h enrolment invitation that ADM-36 (A53) completes with a hardware-attested key.
- `POST /iam/staff/invite` `{email, full_name, roles[], expires_at?}`: creates the `invited` principal and one `iam.role.grant` request per role in one A14 request group; nothing is active until approved and a hardware key is enrolled.
- **SoD violation lists.** Every SoD refusal returns `violations[]` (`code`, `rule_no`, `message`, `source_ref` from A03's `sod.ts`) and a top-level `code` by fixed precedence: `SOD_SELF_GRANT`, then `SOD_HARD_CONFLICT`, then `SOD_EXCEPTION_REQUIRED`. `GET /iam/sod-exceptions` and the A14 request `iam.sod_exception.grant` (`6E`, maker SUPER or a SECO who is not the subject; checkers CCO and SECO; the subject and their agents on neither side). Hard conflicts never take an exception.
- **Access reviews.** `GET /iam/access-reviews`, `GET /iam/access-reviews/{id}`, `POST /iam/access-reviews/{id}/items/{item_id}/decide` `{decision, reason_code, reduce_to?}` and `POST /iam/access-reviews/{id}/sign-off` (fresh hardware-key assertion over the campaign's canonical result hash, purpose `access_review_signoff`). The job `iam.access_review.open` is registered with A46's scheduler (00:05 Sydney on the first business day of January, April, July and October; idempotent per quarter) and snapshots A11's review set, API tokens beside roles. `reviewer_role` is SECO; items about a SECO holder are routed to CCO, and to CEO when the CCO is also a subject or none is active. **Nobody decides an item about themselves or their own tokens** (`ACCESS_REVIEW_OWN_ITEM`). A `remove` decision runs the revoke path above, so sessions and token cells go with the role. The M25 cells `access_review.decide` and `access_review.signoff` are proposed to A03 as a `matrix.ts` diff at Specify.
- **Break-glass log and review.** `GET /iam/break-glass/log` (the log with review state, due date and eligible reviewers) and `POST /iam/break-glass/{id}/review`; the session read `GET /iam/break-glass/{id}` and the pending list belong to A11's loop A11.2 (A53 line 41), which this node reads and never duplicates. The review takes `{outcome: no_findings | findings_raised, findings, actions[]}` with a fresh hardware-key assertion (purpose `breakglass_review`). **Reviewer set:** any active CCO, SECO or CEO who was neither the requester nor an activator of that session; only if that set is empty does the review fall to the named independent reviewer (board delegate or TP-AUD). A wrong reviewer is refused with `BREAK_GLASS_REVIEWER_INVOLVED`. On `iam.breakglass.board_notice` this node sends the board notice through A43 and records `board_notice_state` (`sent`, or `failed` with a Sev2 alert through A13); on `iam.breakglass.closed` it sends the post-session notice to TP-AUD.
- `GET /iam/view-as-tenant/grants`: the grant log with request counts and a deep link to ADM-31 filtered by `acting_tenant_id` and `session_id`.
- **Line manager.** `PUT /iam/staff/{id}/line-manager` as A14 request `iam.staff.line_manager.set` (`4E`, maker SUPER or SECO, checker SECO or CCO; the subject and the proposed manager on neither side). A manager must be an active staff principal, never the subject, and the relation may not form a cycle (`IAM_LINE_MANAGER_CYCLE`). The node exports `lineManagerOf(principalId, at)` from its `index.ts`. ADM-35's "Create my token with write scopes" row names the line manager as the approver in the product map, while A12's default is a SECO who is not the requester (DF-A51-07). Which rule applies is the user's decision; if it is the line manager, A12 reads `lineManagerOf` through a resolver port raised as follow-up loop A12.2 at this node's Specify. This node provides the relationship either way.

**4. Agents (D04, G22).** Every read route admits a staff token within its human's M25 slice. A staff agent may draft an access-review decision (`drafted_by_agent`, confirmed by its human with a fresh assertion) and may create A14 requests as maker within its human's role, but is never checker, approver, ratifier, reviewer or signer, and SoD counts the agent as its human. Suspend, sign-off, break-glass review and every hardware-key step are `requiresHuman`. Every change writes one A10 audit event with `actor` and `on_behalf_of`.

## Node-specific challenges (node QA)

- **Lock-out by revoke (security).** With exactly two sealed-credential holders (CCO Ana, SECO Ben), SUPER revokes Ben's SECO role: refused with `IAM_QUORUM_FLOOR` naming `breakglass_holders` and the count 1. The same with a third holder present succeeds. A revoke of a person who holds CCO and SECO counts them once.
- **Compromise path (security).** SECO Ben suspends CCO Ana with `SUSPECTED_COMPROMISE` when only Ana and Ben hold sealed credentials: the suspend succeeds, crosses the floor, raises one Sev1, ends Ana's sessions, tokens and break-glass elevation in the same transaction, opens a signer-set change request, and returns the break-glass hint. Ben cannot ratify his own suspend; the CEO can.
- **Reviewer marks own homework (compliance).** A SECO decides an item about their own token: `ACCESS_REVIEW_OWN_ITEM`. A break-glass activator reviews the session: `BREAK_GLASS_REVIEWER_INVOLVED`. The SECO's own items route to CCO and sign-off still succeeds once they are decided.
- **Agent as checker (D04).** A staff agent token of a SECO drafts a keep decision (allowed, `drafted_by_agent`), then tries to confirm it, approve an unlock and review a break-glass session: each refused with the specific code, and each attempt audited as agent on behalf of the SECO.
- **Half revoke (money and authority).** A fault injected after the assignment ends but before the token cells are revoked must roll the whole revoke back; no request may still list the person as a required checker.
