# A26 - Passkey smart wallet, paymaster and guardian recovery contracts

**The investor's wallet as Solidity: an ERC-4337 v0.7 smart account owned by P-256 passkeys (no seed phrase, no EOA owner), a CREATE2 factory whose salt binds the investor id hash, the owner passkey and the recovery passkey so the address is known before anything is deployed, a RecoveryModule with two guardians (the RealX guardian, resolved through a registry that only the V1 owner multisig can change, and the investor's second device) where a proposed new owner waits 48 hours, can be vetoed by the current passkey and can only be executed by the RealX guardian, a staked RealXPaymaster that pays gas only for RealX targets within per-wallet and global daily caps, and a SessionKeyModule (founder requirement D04) through which the owner passkey delegates a bounded key to the investor's own AI agent that can never touch owners, guardians, keys or anything outside its allow-list, caps and expiry, and can only act through the RealX paymaster so every agent UserOp passes the server-side gates first. Every validation path obeys the ERC-7562 bundler rules, so what passes locally also passes a real bundler.**

**Build status:** not started. **Milestone:** AM2 (Token and wallet core). **Lane:** Chain. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops).

**Depends on:** [[A07 - Local chain and contracts toolchain (Hardhat, T-REX vendored)]]
**Unlocks:** [[A27 - Chain adapter, deployment manifests and indexer]], [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests|A29 - Wallet service: smart-account factory, bundler sandbox, guardians and recovery requests]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A26\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder; the cases are published into the repo only after the gate passes. The oracle scope is fixed by the node summary: recovery cannot execute inside 48 h; a veto by the current passkey works; the paymaster refuses non-RealX targets; the account cannot be drained by the guardian alone inside 48 h or over a veto (the residual power after 48 h is stated as invariant I5); for the SessionKeyModule, no call outside the allow-list, over a per-action or daily cap, after expiry, after revocation or without the RealX paymaster, and never a change to owners, guardians or keys; and every UserOp kind's validation phase is free of ERC-7562 banned opcodes and non-associated storage. The oracle uses the ABI and the expected-outcome table in §8 exactly, so the oracle and the build cannot disagree on an error name.

This node is the on-chain half of the design's promise on ONB-08 ("Your tokens live in a wallet secured by a passkey on your device. No seed phrase to lose.") and on the Token wallet card ("Secured by your passkey. RealX can't move your tokens without trustee approval."). It is custom Solidity, so it is audited before mainnet (HG-AUDIT) and deployed only to the local Hardhat chain and, later, the testnet. The off-chain wallet service (rows, bundler sandbox, recovery requests, notices, the DAP-mechanism interface) is [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests|A29 - Wallet service: smart-account factory, bundler sandbox, guardians and recovery requests]]; the token-level fallback `recoveryAddress` belongs to the ERC-3643 suite and the AgentGateway (A24, A25, A28). Whether RealX's guardian power makes the wallet quasi-custodial or a digital asset platform under the 2027 framework is a counsel question (HG-LEGAL), not something this node decides. This plan is not legal advice.

## Build brief

**0. Bundler validation rules (ERC-7562), which shape everything below**

- Hardhat's direct `handleOps` does not enforce ERC-7562, but every real bundler (A29 on the testnet, A86 on Base Sepolia) does. So every function that runs in the validation phase (`validateUserOp` and everything it calls, `validatePaymasterUserOp`, the factory call inside `initCode`) must: use no banned opcode (in particular no `TIMESTAMP` or `NUMBER`, rule OP-011: time bounds travel only as `validUntil`/`validAfter` packed into the returned `validationData`); read or write only the account's own storage, or storage in another contract that is *associated* with the sender (slot `keccak256(sender || x) + n`, so the sender address must be the innermost mapping key and no dynamic array may be read); and, for the paymaster, read its own global storage only because it is staked.
- Consequences written into the sections below: session-key expiry and `validAfter` are returned in `validationData` only; the rolling daily spend, `lastUsedAt` and the `SessionKeyUsed` event move to the execution phase; the session-key allow-list is passed in calldata and checked against a policy hash kept in associated storage; the paymaster is staked and its caps use a signed day window instead of the clock; the factory's implementation is an immutable, not a storage pointer; the global session-key pause is read in the execution phase only.
- `contracts/src/wallet/README.md` records, per contract and per validation function, the ERC-7562 rule references it relies on (OP-011, OP-041, OP-062 for the RIP-7212 precompile, STO-021, STO-031, the staking rule) and the trace check in §7 that proves them.

**1. `RealXAccount` (ERC-4337 v0.7 smart account, `contracts/src/wallet/RealXAccount.sol`)**

- Implements `IAccount.validateUserOp` against the canonical EntryPoint v0.7 that A07 places at `0x0000000071727De22E5E9d8BAf0edAc6f37da032`; only the EntryPoint may call `validateUserOp`, `execute(address target, uint256 value, bytes data)`, `executeBatch(Call[] calls)` and `executeWithSessionKey(bytes32 keyId, SessionPolicy policy, Call[] calls)`; any other caller reverts `NotEntryPoint`. Configuration functions (`addOwner`, `removeOwner`, `upgradeToAndCall`) are callable only by the account itself (`msg.sender == address(this)`, so they must ride inside a UserOp the owner passkey signed), otherwise `NotSelf`. `replaceOwnersByRecovery(PasskeyPubKey newOwner)` is callable only by the immutable RecoveryModule address (`NotRecoveryModule`) and is the only path by which anything other than the owner changes the owner set.
- Owners are P-256 public keys `(x, y)` (WebAuthn passkeys), at most 5 per account, at least 1 at all times (`LastOwnerCannotBeRemoved`). There is no secp256k1 owner and no EOA path of any kind; a test asserts the ABI has no function that accepts an `address` as an owner. The design shows "3 passkeys" on the wallet card, which this limit allows. The owner set lives in the account's own storage, which validation may read.
- Signature format on a UserOp: one leading type byte, `0x00` owner passkey or `0x01` session key; any other byte reverts `UnknownSignatureType`. For `0x00` the payload is `(ownerIndex, authenticatorData, clientDataJSON, r, s)`; the account rebuilds the WebAuthn message (`sha256(authenticatorData || sha256(clientDataJSON))`), checks that `clientDataJSON` carries `"type":"webauthn.get"` and a `challenge` equal to the base64url of the `userOpHash` (which already binds chain id and EntryPoint, so an assertion can never be replayed on another chain, account or op), checks the user-presence and user-verification flags in `authenticatorData`, rejects a high-`s` value, and verifies through `P256Verifier` below. A structural failure (unknown owner index, wrong `type`, challenge mismatch, UP or UV flag missing, high-`s`, malformed encoding) reverts `InvalidPasskeySignature(uint8 reason)` with reason codes 1-7 listed in the README; a well-formed assertion whose curve check fails returns `SIG_VALIDATION_FAILED` (ERC-4337's rule, so bundler gas estimation with a dummy signature works). For `0x01` the account delegates to the SessionKeyModule (§4) and returns whatever `validationData` it produces, including `validUntil`/`validAfter` packing. Validation contains no `TIMESTAMP`.
- `P256Verifier` (`P256Verifier.sol`, one singleton used by the account and the RecoveryModule): its constructor runs a probe that `staticcall`s the RIP-7212 address `0x0000000000000000000000000000000000000100` with one known-valid and one known-invalid Wycheproof P-256 vector (pinned in the source) and sets the immutable `USE_PRECOMPILE` to true only if the valid vector returns exactly 32 bytes equal to 1 and the invalid vector returns empty or 0. Selection is therefore neither by code presence (a real RIP-7212 precompile has no code) nor by a runtime return value (a real precompile returns empty for an invalid signature too). When `USE_PRECOMPILE` is false every verification goes to the pinned daimo `p256-verifier` (MIT, recorded by A07) deployed by this node's script; when true, every verification goes to `0x100` and an empty return is treated as invalid. `path()` returns `precompile` or `solidity`, recorded in the manifest. Because the probe runs in the constructor, the init code and so the CREATE2 address are the same on every chain, while the runtime flag reflects the chain.
- ERC-1271 `isValidSignature` accepts owner passkeys only and returns `0xffffffff` for a session-key signature or any failure, so an agent can never produce an off-chain signature that looks like the investor's (typed-data acknowledgements, permits, ballots signed off-chain).
- Upgrade: ERC-1967 proxy with UUPS, `upgradeToAndCall` restricted to the account itself under an owner-passkey UserOp; neither guardian nor any session key can upgrade. ERC-7702 and ERC-7579 modular accounts are not used at launch; the module addresses and the P-256 verifier are immutables of the implementation and recorded as a later option.
- Reads for the screens: `owners()` returns the key list with `addedAt`, `recoveryModule()`, `sessionKeyModule()`, `entryPoint()`, `getNonce()`; a fresh (counterfactual) account has no code and the factory answers instead (§2).

**2. `SmartAccountFactory` (`SmartAccountFactory.sol`)**

- `createAccount(bytes32 salt, PasskeyPubKey owner, PasskeyPubKey recoveryPasskey) returns (address)` deploys an ERC-1967 proxy with CREATE2 and initialises the account with the owner and records the recovery passkey in the RecoveryModule (associated storage keyed by the new account) in the same transaction; calling it again with the same inputs returns the existing address without reverting (idempotent, so a UserOp with `initCode` and an ordinary creation never race). The recovery passkey is optional (zero key allowed) because the second device may be added later through the module. There is no guardian parameter: the RealX guardian is resolved through `RealXGuardianRegistry` (§3), which no investor and no creator can set.
- `getAddress(salt, owner, recoveryPasskey)` is the pure counterfactual address; the CREATE2 salt is `keccak256(salt || ownerHash || recoveryPasskeyHash)` (the zero key hashes to a fixed constant), so nobody can pre-deploy an account at an investor's address with a different owner or with an attacker's recovery passkey. A29 sets `salt = keccak256(investor id)`; this node treats it as opaque bytes.
- The account implementation is an immutable of the factory (a factory reading a storage pointer in `initCode` would need stake under ERC-7562). A new implementation means a new factory version recorded in the manifest; it affects new accounts only, and existing accounts move only by their owner's `upgradeToAndCall`.
- Determinism: the P-256 verifier, the paymaster, the guardian registry, both modules, the implementation and the factory are deployed through A07's deterministic deployment proxy with fixed salts. Their addresses, and therefore every account address, are a pure function of the recorded constructor inputs (the EntryPoint, the paymaster owner, the registry owner): identical across boots, and identical across the local chain, Base Sepolia and any later chain (the pack's Redbelly option stays open) whenever those inputs are the same. The manifest records the inputs so A27 can tell whether two chains share addresses.
- `initCode` format for the first UserOp is `factory || createAccount(...)` per ERC-4337; a test creates an account through `initCode` inside a paymaster-sponsored UserOp, so onboarding never needs the investor to hold ETH and never waits on a separate deployment.

**3. `RealXGuardianRegistry` and `RecoveryModule` (`RealXGuardianRegistry.sol`, `RecoveryModule.sol`, singletons)**

- `RealXGuardianRegistry` holds, for every account at once: `guardian` (in deployment the V2 AgentGateway of A25, so every guardian act arrives with an approval ID under 2-of-3 custody; in this node's tests a `TestRealXGuardian` 2-of-3 stub; never assumed to be an EOA), `revoker` (in deployment the V3 restrict-only gateway of A25; locally a `TestRealXRevoker` 1-of-N stub) and the flag `sessionKeysPaused`. `setGuardian` and `setRevoker` are `onlyOwner` (in deployment the V1 owner multisig, so every change passes its 48 h timelock and veto; locally the deployer), refuse the zero address (`ZeroAddress`) and emit `GuardianRotated(old, new)` and `RevokerRotated(old, new)`; ownership moves only by a two-step transfer (OpenZeppelin 5 `Ownable2Step`). When A25 redeploys the V2 gateway for a new version, one V1 change rotates the guardian for every existing account at once, with no investor signature. The owner of an account cannot replace, zero or point the guardian at themselves: there is no per-account guardian slot and no `setRealXGuardian` function (asserted by an ABI test).
- Guardians per account are therefore the registry's `guardian` and the account's `recoveryPasskey` (a P-256 key on the investor's second device; it is not an owner and cannot sign UserOps). Only the account itself (owner passkey UserOp) may change `recoveryPasskey` (`setRecoveryPasskey`), and only while no proposal is open (`RecoverySetupLocked`). The catalogue rule for ONB-08 and ACC-02 ("recovery set-up needs identity re-verification and a waiting period") is enforced off-chain by A29 before it builds that UserOp; on-chain the change is immediate once the owner signs.
- Proposals, one open per account (`ProposalAlreadyOpen` otherwise), each with `proposalId = keccak256(account, proposalNonce)`, `proposer`, `proposerKind` (`guardian` or `recoveryPasskey`), `newOwnerHash`, `approvalRef`, `executableAt = block.timestamp + 48 h`, `expiresAt = executableAt + 7 days`, and a status `Open`, `Vetoed`, `Cancelled` or `Executed`. Records are kept after they close (never deleted), so every later call on a closed proposal has one defined error. `proposalNonce[account]` increments each time a proposal opens.
  - `proposeOwner(account, newPasskey, approvalRef)` by the registry's current `guardian` (`NotRealXGuardian`). `approvalRef = keccak256(approvalId)` of the approval that authorised this step (`ApprovalRefRequired` if zero). If the open proposal was made by the recovery passkey, the guardian's proposal supersedes it in the same call (`RecoveryCancelled` then `RecoveryProposed`); if the open proposal is the guardian's own, `ProposalAlreadyOpen`.
  - `proposeOwnerWithPasskey(account, newPasskey, webauthnSig)` by any relayer (A29 relays and pays gas; this is a direct call, not a UserOp). The WebAuthn `challenge` must be the base64url of `keccak256(account, newOwnerHash, proposalNonce[account], chainId, module)` and verify against the stored `recoveryPasskey` (`InvalidPasskeySignature`, `NoRecoveryPasskey`). Because the nonce is in the challenge, an assertion cannot be replayed for a second proposal.
  - `cancelProposal(account, proposalId, approvalRef)` by the registry's `guardian` cancels any open proposal (`RecoveryCancelled(account, proposalId, canceller)`). This ends the lost-device lockout: a planted or compromised recovery passkey that re-proposes every 9 days is cancelled or superseded by the RealX guardian, and cannot itself cancel or supersede anything.
  - All proposals emit `RecoveryProposed(account, proposalId, proposer, proposerKind, executableAt, approvalRef)`. `TIMELOCK = 48 hours` is a compile-time constant with no setter, so no key, guardian or owner can shorten it; there is no waiver path on-chain (the CCO + CEO court-order waiver in SM-13 applies to the token-level `recoveryAddress` fallback through the AgentGateway, never to this module).
- `veto(account, proposalId, ownerIndex, webauthnSig)` by any relayer: a current owner passkey, by WebAuthn assertion over `keccak256(account, proposalId, chainId, module)`, sets the status to `Vetoed` at once and for good; emits `RecoveryVetoed`. A veto is possible from the moment of proposal until execution.
- `executeRecovery(account, proposalId, approvalRef)`: `msg.sender` must be the registry's current `guardian` (so a proposal made before a guardian rotation is executable by the new guardian), the proposal must exist and be `Open`, `block.timestamp >= executableAt`, `< expiresAt`, and `approvalRef` non-zero. It calls `account.replaceOwnersByRecovery(newPasskey)`, revokes every session key on the account through the SessionKeyModule in the same transaction, sets the status to `Executed` and emits `RecoveryExecuted(account, proposalId, oldOwnersHash, newOwnerHash, executor, approvalRef)`, which A27's indexer matches to the CustodyOp and the `RecoveryRequest` (SM-13) closes on. A guardian-proposed recovery also clears the recovery passkey slot (the new owner adds a second device again through A29's re-verification and waiting period), because the lost-device case cannot rule out that the old second device is the problem; a recovery-passkey-proposed recovery keeps the slot.
- Approval binding: `approvalRef` is the keccak of the approval ID, different for each step. A25 consumes an approval ID per non-mint call, so the propose, cancel and execute steps each need their own approval ID (or an approval-level nonce): one approval cannot cover both `proposeOwner` and `executeRecovery`. The selectors A25 must allow-list are recorded in the README and the manifest: on V2, `RecoveryModule.proposeOwner`, `RecoveryModule.cancelProposal`, `RecoveryModule.executeRecovery`, `SessionKeyModule.revoke`, `SessionKeyModule.revokeAll`, `RealXGuardianRegistry.pauseSessionKeys` and `unpauseSessionKeys`; on V3 (restrict-only), `SessionKeyModule.revoke`, `SessionKeyModule.revokeAll` and `RealXGuardianRegistry.pauseSessionKeys` only.
- Drain invariant, stated so the oracle can test it: the RealX guardian address can never call `execute`, `executeBatch`, `executeWithSessionKey`, `addOwner`, `removeOwner`, `upgradeToAndCall`, `registerSessionKey` or any transfer on the account; the only things it can do are propose (starting a 48 h notice the owner can veto), cancel a proposal, execute a matured, unvetoed proposal, and revoke or pause session keys (§4). "Within 48 h, or over a veto, the guardian can do nothing to the holdings" holds by construction. The residual power is stated, not hidden (invariant I5): after 48 h with no veto, the guardian alone can install a passkey it controls. The chain cannot know who approved that off-chain, so the mitigation is that every guardian step carries an `approvalRef` that A27 matches to A14's approval record, and the approval for `executeRecovery` must include SM-13's `checker_approval` (CFO and trustee); that binding is A29's and A14's to enforce. The counsel disclosure question below stays open.
- The on-chain states map to the middle of SM-13: `none` → `proposed` (SM-13 `timelock`) → `executed` (SM-13 `executing` → `confirmed`), or `vetoed` (SM-13 `disputed`, which the app returns to `legal_review`), or `cancelled` or `expired` (an `Open` proposal read at or after `expiresAt`; `pendingRecovery` reports it as `expired`), for which A29 moves the request back to `legal_review` so a new proposal needs a fresh approval. Everything before `timelock` (`requested`, `triage`, `identity_reverification`, `legal_review`, `compliance_approval`, `checker_approval`, `old_wallet_frozen`) is off-chain in A29 and A28; this module records only what the chain must enforce.

**4. `SessionKeyModule` (`SessionKeyModule.sol`, singleton; founder requirement D04, gate G22 on-chain)**

- `registerSessionKey(bytes32 keyId, address signer, SessionPolicy policy, uint48 validAfter, uint48 expiry)` is callable only by an account for itself (`msg.sender` is the account), and the account reaches it only from `execute` inside a UserOp validated with signature type `0x00` (owner passkey): a session-key UserOp can never reach it because the SessionKeyModule is a hard-denied target (below). This is execution phase, so the clock is allowed: `expiry` is mandatory, after `validAfter`, and at most `MAX_SESSION_KEY_LIFETIME = 365 days` ahead (`ExpiryTooFar`), matching A12's mandate ceiling; A29 clamps each key's expiry to its mandate's `expires_at`, which is usually shorter (default 90 days). At most 20 keys per account (`TooManySessionKeys`); a reused `keyId` reverts `SessionKeyExists`.
- `keyId = keccak256(abi.encode(A12 mandate id, mandate_sha256))`, so every on-chain session-key event joins to the A12 mandate and API token, and the activity feed can show "agent <token> on behalf of <person>" for on-chain acts. A widened or renewed mandate has a new hash and therefore a new key.
- `SessionPolicy` is a list of `TargetPolicy { address target; bytes4[] selectors; uint8[] amountArgIndex; uint256 perActionCap; uint256 dailyCap; }`, the on-chain form of A12's `session_key_policy` (allowed contracts and functions, per-transaction and daily unit ceilings). `amountArgIndex` names, for each selector, the ABI word that holds the amount (for example the `uint256` of `transfer(address,uint256)` on a 0-decimal T-REX token or a resale-board bid), or `0xFF` for a selector that carries no amount (claim acceptance, a ballot), which counts 0. Caps are per target, so spend on target X never uses target Y's cap. The module stores only `keccak256(abi.encode(policy))`.
- Storage is laid out for ERC-7562: `keys[keyId][account]` (account innermost, so the record slot is associated with the sender) holds `{ signer, policyHash, validAfter, expiry, epoch, revoked }`, and `epoch[account]` is a single-level mapping; neither contains a dynamic array. The list of an account's key ids, the daily spend counters and `lastUsedAt` are read only in the execution phase and in views.
- Validation of a `0x01` UserOp, in this fixed order (each revert surfaces as `FailedOpWithRevert` AA23 with the named error as inner data; see §8):
  1. The UserOp's `callData` must be `executeWithSessionKey` and its `keyId` must equal the signature's `keyId` (`SessionKeyEntryNotAllowed`; `execute` and `executeBatch` are never allowed for a session key).
  2. `paymasterAndData` must start with the RealXPaymaster address, an immutable of the module (`SessionKeyPaymasterRequired`). An in-policy op with self-paid gas or a foreign paymaster therefore fails, so no agent UserOp can skip the paymaster signer, which signs only after A12's and A29's G01-G22 evaluation and A101's kill switches.
  3. Key exists for this account (`SessionKeyNotFound`); not revoked and `epoch` current (`SessionKeyRevoked`); `keccak256(policy)` equals the stored hash (`SessionKeyPolicyMismatch`).
  4. For each call in order: target not hard-denied (`ForbiddenTarget`), target in the policy (`TargetNotAllowed`), selector allowed for that target (`SelectorNotAllowed`), `value == 0` (`ValueNotAllowed`), amount not over that target's `perActionCap` (`PerActionCapExceeded`).
  5. The signer recovered from the low-`s` secp256k1 signature over `userOpHash` must equal the key's signer; otherwise return `SIG_VALIDATION_FAILED` (AA24).
  6. Return `validationData` with `validUntil = expiry` and `validAfter = validAfter`; the EntryPoint rejects an expired or not-yet-valid key with `FailedOp` AA22. The module never reads the clock in validation.
- Execution of `executeWithSessionKey`: the account first calls `sessionKeyModule.checkAndBook(keyId, policy, calls)`, which re-checks revocation, reverts `SessionKeysPaused` if the registry flag is set, sums the amounts per target across the whole batch, adds them to that target's spend in the key's current 24 h cap window (the window starts at the first spend and resets once 24 h have passed since `windowStart`), reverts `CapExceeded(target)` if any target's `dailyCap` would be exceeded, then books the spend, sets `lastUsedAt` and emits `SessionKeyUsed(account, keyId, spentByTarget)`; only then does the account make the calls. `executeWithSessionKey` is all-or-nothing: an execution-phase revert undoes the booking and every call, surfaces as `UserOperationEvent(success = false)` with `UserOperationRevertReason` carrying the named error, and leaves balances and spend counters unchanged (gas is still charged to the paymaster, which the paymaster signer's off-chain checks keep rare). Splitting a transfer across calls in one batch or across ops in one window cannot beat the daily cap.
- Hard denies that no policy can override (`ForbiddenTarget`): the account itself, the factory, the RecoveryModule, the SessionKeyModule, the guardian registry, the P-256 verifier, the EntryPoint (deposits, withdrawals), the paymaster, and any `delegatecall` (the account has no delegatecall execution path). A session key therefore can never add or remove owners, change guardians, upgrade, register keys, veto or propose recovery, or move the account's EntryPoint deposit. A test enumerates every selector of every wallet contract and proves a session key reaches none of them.
- `revoke(account, keyId)` at once by the account (owner passkey UserOp), the registry's `guardian` or the registry's `revoker`; `revokeAll(account)` by any of these and by the RecoveryModule on `executeRecovery`. `revokeAll` marks every key on the account revoked, emits one `SessionKeyRevoked(account, keyId, revokedBy)` per key and increments `epoch[account]`. Revocation is immediate (validation reads the revoked flag and the epoch) and cannot be undone: a new key needs a new `registerSessionKey` by the owner. `pauseSessionKeys()` on the registry (guardian or revoker) stops every session-key execution on every account at the execution phase; `unpauseSessionKeys()` is guardian or registry owner only, so the restrict-only V3 route can pause but never resume.
- Kill switches, stated for A101 and ADM-35: the instant platform-wide agent kill switch is the paymaster policy signer's refusal to sign any session-key UserOp (off-chain, no custody operation, and on-chain unavoidable because of step 2 above); per user it is `revokeAll` through the V3 revoker; per token it is `revoke`; `pauseSessionKeys` is the on-chain belt behind the signer.
- Events: `SessionKeyRegistered(account, keyId, signer, policyHash, validAfter, expiry)`, `SessionKeyUsed`, `SessionKeyRevoked`, `SessionKeysPaused(by)`, `SessionKeysUnpaused(by)`.
- Reads for A29, A60 (ACC-05) and A77 (ADM-35): `sessionKeys(account)` returns every key with `keyId`, `signer`, `policyHash`, per-target `spentInWindow`, `windowStart`, `validAfter`, `expiry`, `revoked`, `lastUsedAt`; an account with no keys returns an empty array, never reverts.

**5. `RealXPaymaster` (`RealXPaymaster.sol`, extends the v0.7 `VerifyingPaymaster` base)**

- `validatePaymasterUserOp` requires (a) a signature by the off-chain policy signer over `(userOp fields, validUntil, validAfter, windowId, sponsoredCapWei)` as in the base contract, returned as a signature failure (AA34) if wrong and with `validUntil`/`validAfter` in `validationData` (AA32 if outside), and (b) on-chain checks the signer cannot waive, in this order (each revert surfaces as `FailedOpWithRevert` AA33):
  1. The signed window is one UTC day: `validAfter == windowId * 1 days` and `validUntil <= validAfter + 1 days` (`PaymasterWindowInvalid`). The EntryPoint enforces the window against the clock, so the paymaster never reads `TIMESTAMP`.
  2. The UserOp's `callData` decodes as `execute`, `executeBatch` or `executeWithSessionKey` (`PaymasterCallNotDecodable`), or the op carries `initCode` that starts with the RealX factory address (account creation is sponsored).
  3. For every call: the target is in `allowedTargets`, or the target is `userOp.sender` and the selector is `addOwner` or `removeOwner` (so the "3 passkeys" chip and the POR-06 devices list never need ETH; every other self-call is refused) (`PaymasterTargetNotAllowed`); `value == 0` (`PaymasterValueNotAllowed`).
  4. `maxCost <= sponsoredCapWei` (`PaymasterMaxCostOverSigned`).
  5. Per wallet: the counter `usage[sender] = {windowId, spent}` (associated storage) is treated as 0 if its `windowId` is older than the signed one, and `spent + maxCost` must stay under `perWalletDailyCapWei` (`PaymasterWalletCapExceeded`). Global: the same with the paymaster's own counter against `dailyCapWei` (`PaymasterDailyCapExceeded`). Both counters reserve `maxCost` in validation.
  6. `postOp` refunds the unused part of the reservation (`maxCost - actualGasCost`) to both counters, so the booked total is the actual cost.
- The paymaster is staked: `deploy-wallet.ts` calls `addStake` with a one-day unstake delay (`86400` seconds, ERC-7562's minimum) and a local stake of 1 ETH of test value from the V7 funder, because reading its allow-list and global counter is reading its own global storage. The manifest records the stake and the delay; A29 sets the testnet stake to the bundler's published minimum.
- Allow-list and caps are set by the paymaster `owner` (in deployment the V1 owner multisig of A25; locally the deployer, account 0 of A07's `accounts.json`) through `addTarget`, `removeTarget`, `setCaps`, `setSigner`, each emitting an event; the initial local allow-list is empty and A27 fills it with the deployed token, identity and wallet-module addresses (the SessionKeyModule and RecoveryModule are allow-listed so owner key registration and revocation are sponsored; session keys still cannot reach them because of the module's hard denies). **8. How failures surface, and the one expected outcome per case**

- A revert inside `validateUserOp` (account, SessionKeyModule, P-256 verifier) surfaces from `handleOps` as `FailedOpWithRevert(opIndex, "AA23 reverted", inner)`; tests decode `inner` to the named error. A signature mismatch returned as `SIG_VALIDATION_FAILED` surfaces as `FailedOp(opIndex, "AA24 signature error")`. An expired or not-yet-valid session key surfaces as `FailedOp(opIndex, "AA22 expired or not due")`. A paymaster revert surfaces as `FailedOpWithRevert(opIndex, "AA33 reverted", inner)`, a bad paymaster signature as `FailedOp "AA34 signature error"`, a paymaster window outside the clock as `FailedOp "AA32 paymaster expired or not due"`. A revert in the execution phase surfaces as `UserOperationEvent(success = false)` plus `UserOperationRevertReason(inner)`. A direct call (not through the EntryPoint) reverts with the named error itself.
- Check order is the order written in §1, §3, §4 and §5; when a case breaks several rules, the first in that order is the only expected outcome. For `executeRecovery` the order is `NotRealXGuardian`, `ProposalNotFound`, then the status (`ProposalVetoed`, `ProposalCancelled`, `ProposalAlreadyExecuted`), then `TimelockNotElapsed`, `ProposalExpired`, `ApprovalRefRequired`. `veto` on an executed proposal reverts `ProposalAlreadyExecuted`, on a vetoed one `ProposalVetoed`, on a cancelled one `ProposalCancelled`.
- The expected outcome of every challenge row below is written next to it; the oracle asserts exactly that outcome and the builder's tests assert the same.

**Error and empty states.** Every revert is a named custom error (listed above plus `OwnerAlreadyExists`, `MaxOwners`, `ZeroAddress`, `NotOwnerOrGuardian`), and the typechain types expose them so A29 can map each to a plain-English message. `pendingRecovery(account)` on an account with no proposal returns a zero struct and state `none`; `sessionKeys(account)` returns `[]`; `getAddress` works before any deployment; the deploy script on a chain without EntryPoint fails with `ENTRYPOINT_MISSING` and deploys nothing.
