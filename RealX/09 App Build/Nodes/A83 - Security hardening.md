# A83 - Security hardening

**The adversarial pass over the whole P1 stack before regression: generated RBAC tests for every matrix cell against the live API under a session and under a token, attacks on token scopes and mandates (scope escalation, expired mandate, replayed mandate signature, cross-tenant token, sandbox and live confusion), cross-tenant row-level-security probes through every route and straight at the database, a strict CSP and cookie posture with CSRF and CORS checks, rate limits per session, per token and per owner, webhook signature and replay vectors in both directions, secrets scanning and a dependency and licence audit inside `npm run verify`, PII redaction of logs and evidence, hostile input for the claims lint, the document and CSV parsers and the MCP tool catalogue (prompt-injection style), a scan proving no production adapter selector or mainnet RPC exists in any artefact, and a threat model that maps every threat to a control and a passing test. Its own code lives in its own security folders; every weakness it finds in another node becomes a fix item on that node. HG-PENTEST stays open and is recorded as such.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Quality. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 16-24 agent-hours (build, challenge and verify loops). The scope is thirteen attack areas, five sub-agents, Slither, SBOM, git-history and image-layer scans, a sweep of every operation x every principal fixture x three paths, the enforced-CSP journey re-runs and three seeded hidden runs. Time spent waiting for other nodes to close the fix items this node raises is outside the estimate. If the orchestrator prefers smaller nodes, the clean split is A83a (authorisation, agents and tenancy: §3 to §5 and §13), A83b (browser, webhooks and rate limits: §6 to §8) and A83c (static, PII, hostile input and deny list: §9 to §12), with the threat model and findings register in A83a; that split is a graph change and is not assumed here.

**Depends on:** [[A79 - End-to-end journeys- investor money path]], [[A80 - End-to-end journeys- sponsor and operations]], [[A81 - End-to-end journeys- recovery, AML and planted breaks]], [[A104 - MCP server generated from the OpenAPI document]]
**Unlocks:** [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A83\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The tests are published into `app/` only after the gate passes, so A88 can re-run them as regression. This node moves no money, supply or holdings itself and owns no business rule, but it is the D04 agent-security hardening node and its attacks decide whether money and authority paths hold, so it carries an oracle (`oracle: yes`; the matching `oracle: true` in `final-graph.json` is a graph change the plan assembler must make). The hidden set covers at least: the token and mandate bypass vectors, the cross-tenant probe set, the webhook signature and replay vectors, the planted secret and PII canaries, the independent list of D04 non-delegable acts mapped to operations (§3), the hostile-input corpus for the claims lint, the parsers and the MCP catalogue, and the mainnet and live-vendor deny list. An empty or missing hidden set fails the gate; it never passes trivially.

What this node is for in one sentence: before the three clean regression runs, someone other than each node's builder tries hard to break the whole assembled system, and every hole they find is either fixed by its owner or written down as an open item for the human pentest. The runtime agent controls (A101) are a separate node; this node attacks them and does not rebuild them. The parity matrix (A100) is an AM8 sibling, not an ancestor, so this node does not attack or read it: it proves refusal parity on its own from the OpenAPI document and A104's catalogue (§14), and A88 runs both together. This plan is not legal advice, and it is not a penetration test: HG-PENTEST is a human gate that stays open after this node passes.

## Build brief

**1. Boundary: what this node owns, what it attacks, how findings travel**

- Owned code has three homes only. `services/api/src/security/` holds the one runtime control no other node owns, the API response-header plugin, plus the security test fixtures that need API internals. `e2e/security/` holds every attack suite, the static scanners and a log-only CSP violation collector used only by the test runs. `docs/security/` holds the threat model, the header policy, the findings register, the deny lists and the pentest brief. No file outside these three folders is edited by this node.
- This node adds **no API route, no MCP tool and no error code**. So `packages/sdk/openapi.json` and the generated SDK (A09), A104's `catalogue.json` and `excluded.json`, and A100's exemptions stay byte-identical, and A09's `openapi:check` is unaffected. CSRF is A11's control (`__Host-rx_csrf` double submit plus the `Origin` check, code `CSRF_REJECTED`), and this node attacks it rather than adding a second guard. CSP violations are counted in the browser (§6), not by an API endpoint. A production CSP report sink is not in P1; if the founder wants one later, it is a new route with its own owner and its A09, A104 and A100 registrations, recorded as an open item in the pentest brief.
- The header plugin is wired only through A09's documented extension point, the `response-headers` slot, through `registerModule` or the slot registration API. If A09 gives no way to load `src/security/` without an edit to `src/core/`, the one-line inclusion is raised as a fix item on A09 (loop A09.x), the same rule A12 uses for A04. The static scanners run as the `e2e/security` workspace's `verify` script, which A01's `npm run verify` reaches through its workspace fan-out. If it does not, that is a fix item on A01.
- A weakness in another node's code is never patched here. It becomes a row in `docs/security/findings.md` with an id (`SEC-F-<nnn>`), a severity (Critical, High, Medium, Low, from the threat-model scale), the owning node, the failing test id in `e2e/security/`, the reproduction, and the fix-item id raised on the owner through the gauntlet's fix-item mechanism. The row stays open until the owner's fix passes and this node's test turns green. The node cannot pass with any Critical or High finding open. It cannot pass with any open finding on a money, supply, holdings, authority or agent path, whatever its severity.
- Every refusal code this node asserts is imported from the registry that owns it (A09's core code table and `registerErrors()` registry, and the module codes A11, A12, A14, A15, A21 and A101 register there), never typed as a string literal. Core codes are UPPER_SNAKE_CASE as A09 fixes them (`VALIDATION_FAILED`, `INVALID_CURSOR`, `IDEMPOTENCY_KEY_REUSED`, `AGENTS_PAUSED`, `RATE_LIMITED`); a code the suites need that is missing from the registry is a fix item on its owner, not a literal here.
- Every attack runs twice, under a passkey session (A11's simulated authenticator) and under a mandate token (A12), and where a tool exists, a third time through the MCP server (A104) with the same token. A refusal that holds on one path and not another is a finding, whichever path leaks.

**2. Threat model (`docs/security/threat-model.md` plus `threat-model.json`)**

- Assets: the unit register and its hash, client money and the ledger, token supply and holdings, custody signing requests and approval ids, API token secrets and mandate signing keys, passkey credentials and sessions, investor PII and KYC documents, AML case content (tipping-off), the audit chain head, feature flags and the licence perimeter, sandbox keys (no value, but they must never be mistaken for production).
- Actors: anonymous visitor, investor of every sub-type, sponsor member of every role, partner (TP-RE, TP-AUD, TP-OBS, TP-LIC, SP-VAL, SP-PM), every staff role, an AGNT acting for each of them, a compromised agent (a stolen token or a prompt-injected model), a malicious sponsor tenant, a malicious webhook receiver, a malicious uploaded document, a malicious dependency, and an insider with database access under `realx_app`.
- Trust boundaries: browser to `apps/web`, browser to `apps/console` (a separate origin), apps to API, agent or MCP client to API, API to worker through the outbox, API and worker to Postgres under RLS, adapters to the sandbox vendors, the chain adapter to Hardhat and Base Sepolia, outbound webhooks to receivers, custody signing.
- One row per threat, STRIDE-classified: `id` (`TM-<nnn>`), boundary, asset, actor, the abuse case in one plain sentence, likelihood and impact, the control and the node that owns it, the test id(s) in `e2e/security/` or in the owner's suite that prove the control, and the status (`covered`, `finding SEC-F-…`, `accepted (reason, owner)`, `pentest (HG-PENTEST)`). A verify check parses the JSON and fails when a row names a test id that does not exist or did not run green in the last evidence, when a control names a node that does not exist, or when any Critical or High row is `accepted` without a founder decision reference.
- The model carries one pre-decided `accepted` row: `style-src-attr 'unsafe-inline'` (§6). The abuse case is CSS injection through a style attribute. It is rated Low: script execution stays nonce-locked, `<style>` elements stay nonce-locked (so attribute-selector exfiltration through injected style sheets is blocked), and style attributes are written by React from typed props, never from raw user strings. Owner A83; the §6 stored-XSS suite includes a style-attribute payload in every user string to prove it.
- The model must include at least the D04 agent threats: token theft, scope creep by widening, mandate replay, agent acting as checker, agent prompt-injected through data it reads, agent flooding (rate and cost), agent reaching a non-delegable act, agent evading the kill switch, agent suppressing the owner's sensitive-action notices (A101), break-glass activated by one person or by an agent, and sandbox-to-live crossover. It must also include the money threats: double spend through idempotency, cap race, a withdrawal to an account not in the investor's name, a mint without a register entry, an unbound custody operation, and a halted vehicle still trading.

**3. Authorisation: generated RBAC and segregation-of-duties tests against the live API (G13, M25)**

- The generator reads the frozen A03 permission matrix (`role x module x action` cells), A11's SoD data, A03's `delegable.ts` and the OpenAPI document (`x-realx-scope`, `x-realx-mutation`, `x-realx-money`, `x-realx-gates` on every operation). For every operation it builds a request from the operation's own zod example (a synthetic fixture, never production data), and for every principal-type fixture from A06 (all 52 roles, one principal each, plus one AGNT per role) it asserts the expected outcome: allowed, refused by the matrix (`FORBIDDEN`), refused by SoD, refused as non-delegable (`AGNT_NOT_ALLOWED` before scope evaluation), refused as a checker action for an agent (`G22_AGENT_NEVER_CHECKER`, `APR_CHECKER_MUST_BE_HUMAN`), or refused by G22 scope (`G22_SCOPE_MISSING` naming the cell). The expected value is computed from the data, never typed by hand. The run is the live two-process compose stack, not a mocked router.
- Coverage checks that fail the run: an operation without `x-realx-scope`; a `GET` or `HEAD` operation whose handler writes (detected by a transaction spy that counts write statements, and cross-checked against `x-realx-mutation: false`); a write operation that accepts unknown body keys (mass assignment: every write is sent with extra keys `tenant_id`, `status`, `approval_id`, `on_behalf_of_id`, `actor_type`, `sandbox_of`, `role`, `scopes`, `price_cents` and must answer `VALIDATION_FAILED` naming them, or ignore them provably, and never persist them); a money operation without an `Idempotency-Key` requirement.
- Maker-checker (G13) attacks, each under session, token and MCP: the maker approves their own request; the maker's agent approves it; a sibling agent of another checker approves it; a checker whose role was revoked after the request was made approves it; a bulk approve that mixes one high-risk request into low-risk ones; an `SGL+R` protective act that is not protective; an approval id reused for a second custody operation (`P1_REPLAY`, `TOP_APPROVAL_CONSUMED`); a custody signing request with no approval id, with a payload hash that differs from the approval (`P1_HASH_MISMATCH`), initiated by an agent principal (`P9_AGENT_PRINCIPAL`) or carrying a token credential (`P9_TOKEN_CREDENTIAL`); and a staff agent reaching any approve, ratify, veto or sign cell by any route. Every case must be refused with A14's or A15's own code and must leave its audit row. One success is Critical.
- Non-delegable acts, checked independently of `delegable.ts`: the node QA's hidden suite carries its own hand-written list mapping each D04 non-delegable act to the operations that perform it (identity and liveness verification; creating the first passkey or wallet; creating or widening an API token; changing the withdrawal bank account; account recovery and guardian changes; closing the account). For every operation on that list, whatever `delegable.ts` says, an AGNT call through the API answers `AGNT_NOT_ALLOWED` before scope evaluation, and the operation is absent from A104's MCP catalogue or listed in A104's `excluded.json`. A disagreement with `delegable.ts` is a High finding on A03. The same suite asserts that the counsel-flagged personal declarations (wholesale-status truthfulness, target-market answers, and every other `counselFlagged` entry in A00's `agent-access.json`) are marked `delegable: "counsel"` in `delegable.ts`, not `true` and not silently `false`, and that an AGNT call to them is refused with the counsel-pending refusal A03 defines.
- Break-glass (M25, A11 §7): activation by a single human (one fresh assertion, or two assertions from the same person), by any AGNT, by a token-authenticated request, or by a service principal is refused; a break-glass session used one second after `expires_at` (at most 4 hours after activation, under the injectable clock) is refused on both API processes with no traffic in between; elevation never reaches an approve cell on the requester's own request or a signer role. Every refusal writes its audit row, and every activation attempt appears in the ADM-31 audit shape.
- Segregation of duties counts the agent as its human: the generator produces every (maker, checker) pair from A14's policy rows in which the checker is the maker's own agent or an agent of any principal in the maker identity set, and every one must be refused.

**4. Token-scope, mandate and on-chain delegation bypass (G22, M26)**

- Scope escalation: widening without a fresh assertion, with a stale one, with one over the previous mandate hash, and with one produced by another principal's passkey; scope strings sent with different case, surrounding whitespace, Unicode confusables, a trailing wildcard, duplicate entries, a family name instead of cells, and a cell of a module the owner lacks. Expected: A11's `FRESH_ASSERTION_*` codes or A12's `SCOPE_EXCEEDS_OWNER` naming the cell, with the mandate unchanged and its previous version readable.
- Mandate lifecycle: calls after `expires_at` (at the boundary second under the injectable clock), after revocation on the other API process, after the owner's recovery, after the owner lost the role, after the tenant was suspended, after the partner engagement ended. Every one must be refused within one request with the specific A12 code.
- Replayed mandate signature: a signed order payload replayed with a new `Idempotency-Key`, replayed after the signing key was revoked, replayed against another vehicle, replayed by a different token of the same owner, and a payload signed with a key registered to another mandate. None may create a second order, and the `428 CONFIRMATION_REQUIRED` path must refuse confirmation by any bearer token.
- Cross-tenant token: a sponsor member's token of tenant A against every tenant-B route (generated from the OpenAPI document), a token whose owner is later added to tenant B (the token must not follow), a partner token against a vehicle outside its engagement, and `view as tenant` attempted under a token (refused: it is a staff session act only).
- Environment: a `rx_sb_` token on live routes, a live token on sandbox routes, a live token with its prefix edited, and a sandbox request that tries to read a live row through a route missing its `sandbox_of` filter. All must be refused with `TOKEN_WRONG_ENVIRONMENT` or return nothing, and A04's `sandbox_of` policy must hold at the database even when the service is bypassed.
- Token hygiene: the secret sent as a query parameter, in a cookie or in a `Referer` must be refused and never logged; a token compared against a near-miss secret must take constant time within noise (1,000 timed attempts per run, Welch test at p < 0.01 counts as a rejection; the case fails only if two of three runs reject, so a correct build is not failed by chance); a burst of invalid tokens from one IP is throttled by A09's anonymous bucket and raises A101's anomaly signal; a request with both a session cookie and a bearer token gets `TOKEN_AMBIGUOUS_PRINCIPAL`.
- Kill-switch evasion: with each tier set (platform `agents.traffic` through A48's `SGL+R`, tenant and user through A101, a single token through A12), agent calls through the API, the MCP server and webhook-triggered follow-ups must answer `423` with the `AGENTS_PAUSED` code imported from the registry (§1), naming the tier, before the rate-limit and idempotency slots run. Human sessions on the same routes must be unaffected.
- Sensitive-action notices (G22, A101): every agent action that A101's `NoticePolicy` marks sensitive (money movement, invest or trade, governance, near-cap, anomaly hold) produces the notice that policy requires (immediate or in the daily summary, deduplicated as A101 defines) to the owner's own channel in A43's sandbox inbox, and none to the agent. The agent cannot suppress them: loosening the notice policy, changing the owner's email, phone or other contact channel, or changing notification preferences through a token or MCP is refused with `AGNT_NOT_ALLOWED` (or the owner's non-delegable code), and a tightening change made by the agent leaves every existing notice row in force. A sensitive action that completes with no notice, or a notice delivered to an address the agent set, is a High finding on A101 (or on the owner of the contact-details route).
- On-chain delegation (A26's SessionKeyModule and A29's registration, on the local Hardhat chain only): a session key calling a selector outside its allow-list (owner change, guardian change, key registration, an arbitrary ERC-20 transfer), exceeding its per-transaction or daily unit cap, used after expiry, used after the owner or the RealX guardian revoked it, and a UserOp sponsored by the paymaster for a non-RealX target. Every one must revert, and the API must have revoked the key when A12 emitted `agent.mandate.revoked`.
- Aggregate rate across tokens: an owner who creates many tokens must not multiply their throughput. The owner-level aggregate across all their tokens must stay within the principal-type ceiling in `packages/config`. If A12 or A09 enforces only per-token buckets, this is a finding on A12, and A101's burst rule must at least raise an anomaly.

**5. Row-level security and object access across tenants**

- API sweep: for every operation with a path or query id (generated from OpenAPI), the stack is seeded with two tenants, two investors, two partners and one per-user sandbox, and each principal requests the other's objects. Expected: `404` (or the documented refusal code where the route defines one, such as A30's sponsor-without-consent `404`), never a `2xx`, and never a response body or error message that reveals the object exists (the same status, the same envelope shape, the same length class). List endpoints must never include a foreign row. Cursors from one principal replayed by another must fail with `INVALID_CURSOR` (A09's cursor HMAC).
- Database sweep: under `realx_app`, `realx_worker` and `realx_readonly` (A04's exports and reporting role), for every table outside A04's `EXEMPT_TABLES`, a context-less connection sees zero rows; a tenant-A context cannot `SELECT`, `INSERT`, `UPDATE` or `DELETE` a tenant-B row (`USING` and `WITH CHECK` both proven); a `SET` (not `SET LOCAL`) of `app.tenant_id` does not survive to the next pooled request; `app.platform_access` cannot be set from a non-staff request path; the support roles cannot see that an `aml_case` exists; none of the four database roles has `BYPASSRLS` or `SUPERUSER`. A04 already tests its own policies. This sweep re-runs after every module has registered its tables, which A04 could not do.
- `view as tenant` from the console is refused without the staff session flag, writes exactly one audit event, and ends at the end of the session.

**6. Browser surface: CSP, cookies, CSRF, CORS and headers**

- `docs/security/headers.json` is the single policy the tests read. `apps/web` and `apps/console` get a nonce-based `script-src 'self' 'nonce-…' 'strict-dynamic'` with no `'unsafe-inline'`, no `'unsafe-eval'` and no remote script host; `style-src 'self' 'nonce-…'` and `style-src-elem 'self' 'nonce-…'` for style sheets and `<style>` elements; **`style-src-attr 'unsafe-inline'`** for style attributes; `font-src 'self'` (A05 vendors Newsreader, Geist and Geist Mono as woff2, so no Google Fonts host is allowed); `img-src 'self' data: blob:`; `connect-src 'self'` plus the API origin only; `frame-ancestors 'none'`; `form-action 'self'`; `base-uri 'none'`; `object-src 'none'`; `upgrade-insecure-requests`. There is no `report-to` or `report-uri` directive in P1 (§1). They also get `Strict-Transport-Security` (the value is recorded here and enforced only on TLS origins, since compose runs on localhost), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (`no-referrer` on the console), `Permissions-Policy` allowing `publickey-credentials-get` and `publickey-credentials-create` for `self` only and denying camera except on the ONB-03 liveness route, `Cross-Origin-Opener-Policy: same-origin`, and `Cross-Origin-Resource-Policy: same-site`. API JSON responses get `Cache-Control: no-store` on every authenticated response, `nosniff` and `frame-ancestors 'none'` through the plugin in `src/security/headers.ts`.
- **Style policy, decided here (option a).** Nonces cover `<style>` elements but not `style` attributes, and the design prototype and A05's components set inline style attributes (the prototype has about 379). No upstream node forbids them, so a nonce-only `style-src` would block them and break the design. The policy therefore allows style attributes through `style-src-attr 'unsafe-inline'` and keeps everything that can run code or load a style sheet locked: scripts are nonce and `strict-dynamic` only, style sheets and `<style>` elements are nonce or `'self'` only. The residual risk is the accepted Low row in §2. Option (b), class-only styling enforced by a lint rule in A05, A52 and A53, was not chosen because it would reopen those nodes; if the founder later wants it, it is an upstream change on those nodes and this directive is then removed.
- The app headers are set by A52 (`apps/web` root files) and A53 (`apps/console` root files). This node does not edit them. `e2e/security/headers.spec.ts` asserts them on every HTML route of both apps at desktop and 375 px, and any gap is a fix item on A52 or A53.
- CSP violations are counted in the browser, not by an API route: every Playwright page in the security runs gets an init script that records each `securitypolicyviolation` event (directive, blocked URI origin, document path without query string), and the console's CSP error messages are captured as a cross-check. Both feed the log-only collector in `e2e/security/`, which writes the counts to `app/evidence/A83.json`. The P1 journeys (A79, A80, A81) are re-run with the CSP in enforce mode, and the ACC-05, SPN-16 and ADM-35 screens (A60, A77) are walked through their create, narrow, revoke and kill-switch actions under the same observer; the collector must record zero violations. A violation means either an inline script, which is a finding on the owning UI node, or a missing allowance, which is a finding here. The full agent journey (A82) is an AM8 sibling, not an ancestor, so its enforced-CSP run belongs to A88.
- Cookies (A11's frozen cookie rule): `__Host-rx_sid`, `__Host-rx_dev` and `__Host-rx_csrf`, all `Secure`, `Path=/` and no `Domain`; the session and device cookies also `HttpOnly` (the CSRF cookie is not, because A11's double submit reads it); `SameSite=Lax` on `apps/web` and `SameSite=Strict` on the console. The console's cookies are never sent to the web origin and vice versa. The expected values are read from A11's spec at the hash recorded at Specify. The tests read the `Set-Cookie` headers and the browser jar after sign-in on both origins. Anything weaker is a finding on A11.
- CSRF is A11's control, attacked here: for every cookie-authenticated request with an unsafe method, A11 requires `Origin` equal to the surface's configured origin (or, when `Origin` is absent, `Sec-Fetch-Site: same-origin`) and `X-CSRF-Token` equal to the `__Host-rx_csrf` cookie, otherwise `403 CSRF_REJECTED` with `auth.csrf_rejected` written and no body logged. Bearer-token requests carry no cookie, so they are outside the check; a request carrying both is already refused by A12. Tests: a cross-site form post, a `text/plain` fetch, a request from a sibling origin (web to console and console to web), a missing `Origin` with a present cookie, a request with a valid cookie and a stale or foreign CSRF token, and a `GET` that would change state (none may exist, per §3). Any vector that is not refused with `CSRF_REJECTED`, or that leaves a state change, is a finding on A11.
- CORS: no wildcard with credentials; `Access-Control-Allow-Origin` echoes only the two app origins for cookie requests; token requests from arbitrary origins are allowed without credentials so browser-based agent tools work, and the preflight never lists `Cookie`. Stored XSS: every user-controlled string that a screen renders is posted with an XSS payload set through the API, including a style-attribute and CSS-injection payload. Those strings are property and sponsor names, announcement text, agent and token names, webhook names, reason notes, document titles and file names. Playwright then opens each screen that shows the string (ACC-05, SPN-16, ADM-35, ADM-31 audit rows, SPN-12 announcements, PUB-03 property page) and asserts that no script runs, that no violation is recorded, that no user string reaches a `style` attribute or a style sheet, and that the text renders literally.

**7. Rate limits per session, per token and per owner**

- Buckets from A09 (`human:<id>`, `partner:<id>`, `agent:<token_id>`, `service:<id>`, `anon:<ip>`) and the mandate limits from A12. The tests exhaust each bucket and assert `429 RATE_LIMITED` with `Retry-After` and the `RateLimit-*` headers. They also check that exhausting an agent's bucket leaves its human's session bucket untouched, and the reverse; that rotating a token does not reset its bucket (the key is the `TOK-` id, not the secret); that `X-Forwarded-For` is honoured only from the compose proxy address in `packages/config`, so a spoofed header cannot mint fresh anonymous buckets; and that a mandate's own lower limit applies before the principal-type ceiling.
- Expensive and abuse-prone routes get their own measured limits, which are asserted here and owned by their nodes: passkey ceremony option endpoints (challenge flooding against A11), sign-up and invitation sends (email and SMS bombing against A43's sandbox inbox), document upload (A35, A34), claims lint runs (A43), webhook test deliveries (A46) and sandbox dataset generation (A99). A route with no limit beyond the default, where the threat model says one is needed, is a finding on the owner.
- The passkey sign-in options endpoint must not reveal whether an email or credential exists (the same response shape and timing class for known and unknown identifiers). A difference is a finding on A11.

**8. Webhook signatures and replay, both directions**

- Outbound (A46 wire format `X-RealX-Signature: v1=<hex HMAC-SHA256 of "<timestamp>.<body>">`, 5-minute window): the hidden vectors cover a wrong secret, a missing or duplicated timestamp, a timestamp 301 seconds old and 301 seconds in the future, a body changed by one byte or re-serialised, header name case, a `v2=` or empty scheme, both signatures during the 24-hour rotation overlap, and only the old secret after the overlap. Each vector runs against the SDK's `verifyWebhook`, the `POST /v1/webhooks/verify` helper and the sandbox sink, and all three must agree. Deliveries after the creating token is revoked or narrowed must stop or narrow at once. Payloads must carry only `webhook_safe` event types and no PII (§10 canaries). Hostile receiver URLs (private ranges, `localhost`, link-local, IPv6-mapped IPv4, DNS that flips between check and connect, redirects to an internal host) must be refused by A46's egress guard.
- Inbound (A17's bank webhook, A22's identity provider webhook, and the custody and registry sandbox callbacks): each endpoint must refuse an unsigned request, a request signed with another adapter's secret, a replay of an accepted delivery (idempotent: no second credit, no second state change, observed through the ledger and the audit count), and a delivery that arrives out of order. A duplicated bank receipt must never credit twice. A payer-name mismatch must hold the receipt, whatever the webhook claims.

**9. Secrets, dependencies and licences inside `npm run verify`**

- Secrets scan over the working tree, the full git history of `<workspace>\app`, the built bundles of both apps, the `packages/sdk` and `packages/mcp` packages, the evidence folder and the layers of every image the compose stack builds.
