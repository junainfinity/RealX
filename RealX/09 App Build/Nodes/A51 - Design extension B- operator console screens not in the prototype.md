# A51 - Design extension B: operator console screens not in the prototype

**A second dc-format design file, `RealX Admin Ext.dc.html`, drawn in the prototype's own dark admin shell and tokens, that gives every operator-console screen the prototype does not show a designed reference before any console code is written: the 26 product-map admin screens listed below (including ADM-35 "Agent and API access" for founder requirement D04), the five undrawn screens under their charter ids ADM-36 to ADM-40, the extended seven-group sidebar, the hardware-key confirmation modal that every approval and protective action goes through, every product-map action of those screens with its maker, checker and policy code, and the new blocks ExemptionMeter, FunnelRow, ApprovalsChain, MandateTable and KillSwitchBanner; the user reviews it (HG-REVIEW) before A53 and the console nodes A67 to A77, A92 and A93 start.**

**Build status:** not started. **Milestone:** AM4 (Screens and consoles). **Lane:** Design. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 16-22 agent-hours (build, challenge and verify loops).

**Depends on:** [[A05 - Design system package from the prototype tokens]], [[A00 - Charter and acceptance baseline]]
**Upstream inputs read at Specify and by the manifest test (they must exist before Build starts):** [[A03 - State machines, gate codes, approval codes and permission matrix as data]] (permission cells, `delegable.ts`, the maker-checker resolution table, state vocabulary), [[A09 - API and worker skeleton with OpenAPI-generated SDK]] (`openapi.json` and its `<module>.<verb>.<noun>` operationId convention), [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]] (token status and refusal vocabulary), [[A14 - Approvals engine and maker-checker (SM-00)]] (seeded policy rows), [[A21 - Licences, feature flags and licence perimeter (G21)]] with A08's flag table (flag keys and launch states), [[A48 - Halts, kill switches and wind-down]] (platform switches), [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]] (holds, tiers, anomalies, notices). The graph carries these seven edges since 24 Sep 2026 (`Data\graph-revisions.json`), so the scheduler cannot start A51 before they pass; A51 is in AM4, after AM3's exit. A50 is **not** an input: the three A50-owned blocks this file draws (TextArea, ThresholdMeter, the copy-once secret card) and A50's ScopePicker and MandateSummary are drawn from A50's frozen node spec text, not from A50's built files (§4).
**Unlocks:** [[A53 - Operator console shell, hardware-key sign-in and approval action pattern]], [[A67 - Console- users, roles, access reviews and break-glass (ADM-37)]], [[A68 - Console- identity review, wholesale certificates, investor directory and Investor 360]], [[A69 - Console- sponsor admission, licences, sponsors and guardrails, feature flags, entities register]], [[A70 - Console- property register, valuations workbench, property operations]], [[A71 - Console- listing review, live raise monitor, orders and allocation]], [[A72 - Console- token operations, forced transfer and recovery desk, wallets and custody, token registry]], [[A73 - Console- rule packs and threshold monitors, register and reconciliation]], [[A74 - Console- treasury, distribution run review, tax centre]], [[A75 - Console- AML cases, complaints register, marketing compliance, disclosure library]], [[A76 - Console- regulatory calendar and data room, sponsor performance, integrations and jobs]], [[A77 - Console- agent and API access (ADM-35)]], [[A92 - P2- resale board screens (sell, buy on the board, market tracker, board control)]], [[A93 - P2- governance votes and meetings (SM-10) with screens]]

**Oracle rule:** this node has no hidden oracle (`oracle: no`); no money, supply or holdings move here. The node QA still writes its Challenge material to `<workspace>\gauntlet\hidden\A51\` before the build starts: its own hex and font extractor for the extension file, its per-screen content checklists derived from the requirements catalogue and from `data_admin.py` (one list of required fields, actions, states and policy codes per screen), the scratch-copy mutation patches used in the challenges below, and its eight reference-region crops of the prototype. The builder never reads that folder ([[App Gauntlet]] §2).

This node draws; it does not build product code. It produces a design artefact in the same format as the prototype, so that the console nodes have a "region of the design" to be faithful to, exactly as the drawn screens have today. Because the console nodes build only what HG-REVIEW has seen, a product-map action missing here would become an action missing from the console; so every product-map action of these screens is drawn (§5a). Nothing in this file decides eligibility, money or approvals; every rule it shows as a disabled button or a red pill is a rule the API enforces in A12, A14, A19 and the service nodes. This plan is not legal advice; where a screen shows a legal threshold or deadline (the DAF Act low-value exemption on ADM-04, the landholder-duty and s601ED figures on ADM-16, the complaint deadlines on ADM-27, the SMR clock on ADM-26) the figure is a parameter labelled "counsel to confirm".

## Build brief

**1. Where the file lives and how it runs (design analysis §0 and §5)**
- The design folder `<workspace>\design\` is read-only. The extension lives at `<workspace>\app\design-ext\admin\RealX Admin Ext.dc.html`, written in the same dc grammar the prototype uses (`<x-dc>`, `<sc-if>`, `<sc-for>`, `{{ }}` bindings, `style-hover`, a `data-dc-script` block with `class Component extends DCLogic`), so the two files can be read side by side and the same tooling (A05's extractor, the node QA's extractor, the e2e fidelity comparison of later nodes) works on both.
- **Runtime copy.** The prototype runtime is copied verbatim to `design-ext\admin\runtime\support.js` (A50 keeps its own copy in its own folder, so the two nodes never write the same file). A harness `index.html` in the same folder loads React from A01's installed dependencies and that local copy; nothing in the harness refers to a path outside the app repo, so it works from a clean clone. `design-source.json` records the SHA-256 of the local copy and of the originals (`RealX App.dc.html`, `support.js`) at build time; a test asserts the local copy's hash equals the recorded original hash. The check against the design folder itself (originals unchanged before and after the build) runs only when `<workspace>\design\` is present; on a clean clone without it the check reports `skipped: design folder not present` and does not fail. If `support.js` cannot be hosted outside the Claude Design host within two hours of trying, the builder records why in the evidence, keeps the dc file as the design artefact, and renders it through A05's catalogue runner instead (same blocks, same tokens); that fallback is an escalation trigger, not a silent switch.
- `mock-admin.js` holds the extension's mock data: the prototype's data set (design analysis §7: eight properties, three sponsors, APS approvals, OPS token operations, recon rows, treasury accounts, KYC and AML cases, audit rows) re-used unchanged where it exists, plus the rows the new screens need. One as-of date, Wednesday 23 Sep 2026, 06:00 AEST reconciliation; any other date is a named scenario state with its own date caption. The seed invariants of design analysis §6.4 item 20 are kept exactly (6,400 × A$238.40 = A$1,525,760 in escrow for 128 applications; to soft cap A$262,240 = 1,100 tokens; A$0.2592 per token = 2,592 ÷ 10,000); the admin-side mock bugs §6.4 items 4 (estate wallet trust), 5 (APR-2279 used twice), 6 (Unley Road minted before close), 8 (static badges), 13 (Marine Parade missing from recon) and 14 (escrow shown as register units) are fixed in the mock, not reproduced, and each fix is listed in `design-findings.md` as DF-A51-01 to DF-A51-06.

**Escalate** when a third loop still fails on the same finding; when `support.js` cannot be hosted outside the design host and the catalogue fallback is needed (the user decides whether the dc format stays the artefact); when a product-map field cannot be placed without a new colour, font weight or radius (never allowed; the user decides between dropping the field or changing the design system in A05); when a screen's maker-checker rows contradict A03's resolution or A14's policy rows in a way §6 does not already list (a spec defect reopened in A03's data, not patched here); when a P1 action has no operation in `openapi.json` (the owning service node is reopened); or when the user's review asks for a change that alters a drawn prototype screen (out of scope for this node; goes to a new finding).
