# A88 - P1 full regression: 18 P1 journeys, three clean runs, every gate exercised

**The last check before the launch: all 18 P1 journeys (the 17 product-map journeys J01-J06, J09-J15, J17, J19-J21, plus the D04 journey J22 "Delegate to your own agent", run as A82's agent groups) and the simulator's planted-break run, run as the owners' own run groups (each group started from the reset its owner documents) on a freshly created Docker compose stack, three runs in a row with no retries, every gate G01-G22 exercised at least once in its P1 form (G05, G09 and G15 as refusals behind their phase flags, G22 as both a pass and a refusal), a gate ledger, a state ledger and an audit check computed from database extracts rather than from test output, the charter's coverage matrix re-checked against the evidence on disk, resume from `status.json` proven by killing a run halfway, and a code freeze after the pass: nothing changes code after this node except the fix items it raises.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Quality. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops); raised from 6-10 by the 24 Sep 2026 plan review, in line with the grown spec. The three counting runs and the kill-and-resume run are wall-clock time on the local machine, not agent-hours; their duration is measured and recorded.

**Depends on:** [[A83 - Security hardening]], [[A84 - Performance and scale]], [[A85 - Observability and runbooks]], [[A86 - Base Sepolia integration run and HG-AUDIT pack]], [[A87 - Design fidelity and accessibility pass]], [[A82 - End-to-end- an agent drives the account through the API and MCP]], [[A100 - Agent-parity suite- every UI action has an API and MCP equivalent under the same gates]], [[A102 - Backups, restore drill, data retention and erasure]], [[A103 - Runbook drills R1-R9 executed on the stack]]
**Unlocks:** [[A89 - Docker Desktop launch (P1)]]

**Oracle rule:** this is not an oracle node (`oracle: no`): it adds no product behaviour and moves no money itself. The node QA still writes hidden tests from this frozen spec to `<workspace>\gauntlet\hidden\A88\` before the build starts: seeded-fault fixtures that the regression harness must catch (a hidden retry, a skipped step, a stubbed sandbox rail, a `not_applicable` gate counted as a pass, a reused stack, an incomplete reset, a hidden order dependence between groups, a corrupted `status.json`, a back-door state edit), plus an independent gate-ledger, state-ledger and money-identity query set that the node QA runs against the same database extracts to check the harness's counts. The builder never reads that folder, and the tests are published into `app/` only after the gate passes ([[App Gauntlet]] §2).

What this node is for in one sentence: prove that the P1 product, frozen at one commit, does every P1 journey the same way three times in a row on a clean machine state, with every rule applied, and leave behind evidence that a person can check without re-running anything. It writes no journey tests: those belong to A79, A65, A78, A80, A81 and A82, and A88 runs them unchanged, in the run groups and from the resets their owners define. It fixes nothing: every failure becomes a fix item on the node that owns the failing path. This plan is not legal advice; every sentence about what counsel requires is a counsel question.

## Build brief

**1. What this node reuses and what it adds (no duplication of the journey, parity, security or drill nodes)**

- Journey suites are taken as they are from their owners' paths and never edited, and they run in the owners' own run groups: A79's Run A (J01, J02, J03, J17 before, J04, J15, J17 after, in that order, with its fixed seeded personas such as Alex Morgan INV-00841), A79's Run B (J05 from `soft-cap-missed`) and its negatives (`e2e\investor\`); A65's isolated J11, J12, J13, J14 and J19 files and their failure-path files (`e2e\sponsor\`), run with `OPERATOR_STEPS=console` exactly as A78's `operator:sponsor-rerun` runs them; A78's J20 (`e2e\operator\`); A80's isolated J06 and J21 specs and its operating month, the one continuous run in which J06, J11-J14, J19, J20 and J21 meet on one clock (`e2e\operations\`); A81's J09, J10 and planted-breaks groups (`e2e\risk\`); A82's agent scenarios (J22 shape: investor, sponsor-accountant, operator, partner and guard scenarios through the API and MCP, `e2e\agent\`). A suite that needs a change to run in the regression is a fix item on its owner, not a local patch.

- Seed and scenarios come from A06 (`npm run seed` with seed string `realx-baseline`, `AS_OF` Wednesday 23 Sep 2026 10:30 AEST, and the named scenarios the owners' groups load, such as `soft-cap-missed`, `unknown-holder`, `cash-delta`, `stale-valuation`, `aml-third-party-deposits`, and `p2-preview` loaded with P1 flag defaults for the phase probes only). If `realx_readonly` cannot read a table or partition the ledgers need, or row-level security hides rows from it, that is a fix item on A04 (the precondition in the Gauntlet loop), never a new role or a wider grant here. Because each group starts from a reset that wipes the previous group's rows, the harness extracts what the ledgers need at the end of every group, before the next reset (section 4).

**3. Scheduling, resets, clocks and order independence**

- Groups run one at a time on the run's stack, never in parallel (they share one database and each begins with a reset). Each group runs under its owner's project or command with the regression overrides layered on and nothing else changed: `retries: 0`, `trace: 'on'` (the owners' masking stays in force under this override: A79's PII masker over request bodies through A04's `mask()` shapes and every other owner's masking hook apply to every trace, not only failed ones), the JSON reporter, `workers` as the owner sets it (1 where the owner requires order). The regression config asserts that every other option equals the owner's; an owner config that cannot take these overrides is a fix item on the owner.
- **Before each group** the runner calls the group's documented reset and then checks, through read-only queries and public APIs, that the reset produced that group's `reset_expected` set (section 2) exactly: the seed manifest `contentHash` equals A06's and the loaded scenario's hash equals the one in `reset_expected`, A09's clock reads the `reset_expected` clock (`AS_OF` unless the scenario's `expect` block names another), flags, kill switches, halts, open breaks and open Sev1 alerts equal `reset_expected`, token supplies and the chain state equal A27's post-deployment baseline as changed by the scenario's `expect` block, the client-money bank balances equal the expected opening balances, and A10's chain head (or the audit event count and types, where `reset_expected` records those instead) equals the expected value after the scenario loads. Any difference fails with `REGR_RESET_INCOMPLETE` naming the leftover, and the fix item goes to the reset's owner (A23, A61 or A80), never to the group that ran before.
- **Seeded-row boundary.** After each passing reset check the runner records, in `.runs\<runId>\groups\<groupId>\baseline-ids.json`, the set of existing primary keys (or the maximum sequence value, where the table has a monotonic sequence) of every table the ledgers read: `gate_evaluation`, `evaluation_set`, `api_token_activity`, the audit events, A16's journals and entries, A14's approvals, A18's register versions, A20's runs and breaks, and the orders, runs and holdings the state ledger reads. Under the fixed local clock new rows can carry the same `evaluated_at` as the latest seeded rows, so timestamps and the audit head alone never separate seeded history from the group's own rows; only rows outside `baseline-ids.json` count toward the run's ledgers, and the node QA's hidden queries use the same rule.
- **Clock origin per group.** Every group starts from its own clock origin (`AS_OF` after the reset); the owner's suite moves the clock as it documents (for example A79's J05 to three days before ANN01's close on 2 Nov 2026, A80's month from 23 Sep to December 2026, A78's morning at 07:30). The runner never moves the clock itself; it records each group's clock at start and end in `status.json` and in the report.
- **Order.** Order inside a group is the owner's and is never changed (A79's Run A order, A80's month timeline). Order across groups differs by run: run 1 uses manifest order, run 2 reverse order, run 3 a seeded shuffle (`realx-regression-<runId>`), recorded in `status.json`. Because every group starts from an independent reset, a group that passes only after another group ran is a hidden order dependence, and the shuffled runs expose it as a failure, never as a pass.
- **End of each group, in this fixed order:** (1) the undeclared-effect snapshot: the runner snapshots every feature flag (A21), the kill-switch tiers (A12, A101), the clock and the open halts and breaks (A48, A20); a group whose end state differs from its `reset_expected` set plus its declared `touches`, `plants` and `leaves` fails with `REGR_UNDECLARED_EFFECT` naming the flag, switch, halt or break; (2) the full A20 reconciliation (section 7), triggered through A20's public API with a named seeded REGO credential recorded in the manifest (A06's seeded REGO staff persona, signed in through A11's simulated authenticator); its own rows (the reconciliation run, its audit events and any alert it raises or re-raises) are a declared harness effect, recorded by id and excluded from the group's undeclared-effect comparison and ledgers, and re-detecting the baseline GYM01 break must open no second break and no second Sev1 alert; (3) the post-group invariants (section 4); (4) the per-group extract (section 4). The runner never restores state on a group's behalf; the next reset does, and the reset check proves it.
- A group's budget is twice the longest duration its owner's evidence records for it (default 30 minutes where none is recorded); a group over budget fails with `REGR_UNIT_TIMEOUT`. The run's total duration is measured and reported, not enforced (with A80's month alone at up to 150 minutes, a run is expected to take several hours).

**4. What a clean run is, and the per-group extract**

- A run is clean only when all of the following hold: every group in the frozen manifest passed on its first and only attempt; Playwright and Vitest ran with retries off, forced by the regression config and checked in the reporter's `retry` index for every test (any non-zero index fails the run with `REGR_RETRY_DETECTED`); no test was skipped, marked `fixme`, marked `fail`, or filtered by `only` (a static scan of the owners' suites at the frozen commit plus the runtime report, `REGR_SKIP_DETECTED`); no `expect.soft` failure was recorded; every reset check passed; the post-group invariants held after every group; and the post-run checks (section 7) passed.
- Three clean runs in a row, each on its own freshly created stack, are the pass condition. Any failed group, any failed reset check, any infrastructure failure (stack not healthy within 10 minutes, Docker error, port clash) and any post-run check failure resets the streak to zero; an infrastructure failure is still recorded as a failure and needs a cause in the report before the next attempt, because the launch in A89 boots the same stack.
- Flake classification: when a group fails in one run and passed in another at the same commit, the fix item is raised as `flaky` against the owner with both traces; it is never cleared by re-running. A test that uses a fixed sleep (`waitForTimeout`) or a wall-clock time instead of A09's clock or the sandbox's test-controlled mining is reported as a flake risk in the fix-item list even when it passed.
- **Post-group invariants** (checked after every group, after the snapshot and the reconciliation and before its extract and the next reset, in the order section 3 fixes, through read-only queries and public APIs): A10's hash chain verifies to the current head; the client-money ledger trial balance is zero (A16); every client-money bank account's balance in the bank sandbox's `state()` equals A16's ledger account for it (Δ 0, the same check as A79's C1); the per-account money identity of section 7 holds to the cent; for every vehicle, token supply equals the latest acknowledged register version (A18, A27 indexer) except where the group's `reset_expected` set or its declared `plants` or `leaves` name a break, and those differ by exactly the declared delta; the open breaks, open Sev1 alerts and halts equal the group's `reset_expected` set plus the group's declared `plants` still open plus its `leaves`, exactly, with every planted break closed by the group's own clean re-run unless the owner declares otherwise; the GYM01 baseline break is unchanged unless the group's `leaves` declare that the owner resolves it (for example a group that decides APR-2292); every agent-written audit event since the reset carries `token_id` and `on_behalf_of_id`. A failure is `REGR_INVARIANT_BROKEN` naming the invariant, group and vehicle or account.
- **Per-group extract.** After the invariants, the runner takes a read-only `pg_dump` of the product database with the reporting role's grants (if those grants cannot read a table the ledgers need, that is a fix item on A04, never a wider grant here), plus the bank sandbox `state()` export and A27's indexer records, into `.runs\<runId>\groups\<groupId>\`, with SHA-256 of each file in `status.json`. Only rows outside the group's `baseline-ids.json` (section 3) count toward the run's ledgers, and the audit events additionally sit after the reset's expected head; the seeded history and the scenario's rows are excluded by that boundary, not by timestamps. Extracts, the Playwright traces and the checkpoint renders contain the seed's synthetic personal data by design, so they all live only in the git-ignored `.runs\` folder, are never copied into the evidence or report paths, are scanned for the token pattern (the database stores only token hashes, so zero matches is expected in the extracts; traces of A82's and the probes' token creation can capture the copy-once secret, so the trace post-processor redacts the token pattern from every trace and render before anything else reads it, and the scan then expects zero matches), and are deleted only by `regression:clean`.

**5. Gate probes (P1 forms no journey reaches, driven only through public surfaces)**

- Probes live in `e2e\regression\probes\`, use only the SDK, the MCP client from `packages\mcp`, the web or console UI, the sandbox panels, the clock control and, for the G08 on-chain part only, A29's wallet SDK submitting a user operation through the local bundler sandbox with A11's simulated passkey (the same path an investor's wallet uses; listed in the static scan's allow-list), and are small: they exist so that the gate ledger has a row where a journey cannot produce one. They run as three groups, each from its own reset: `PROBES-PHASE` (G05, G09, G15, and the J08 and J18 entry refusals for the coverage re-check, section 10), `PROBES-CORE` (G01, G06, G08, G12, G16, G22 and the agent parity pairs) and `PROBES-CLOCK` (G18, the only probe that moves the clock). Each probe asserts the refusal code and the fix-it message key, not only the HTTP status. The probes use generated personas, except the seeded personas named below and listed in `gate-sources.json` (section 1). `PROBES-CORE` also carries the SDK refusal probes the gate-source rule of section 2 adds for gates whose owner refusals are UI-only (at least G01, G06 and G12). **No route, handler, flag or stub may be added under `e2e\regression\`**: a probe that cannot reach its gate through an existing public route is a fix item on the route's owner or an escalation, never a local route.
- **Expected refusal codes come from the catalogue, not from this note.** At Specify the expected codes for each phase probe are taken from A21's reason catalogue and A09's error registry at the frozen commit (G21 refusals behind a flag carry `LICENCE_PERIMETER` as A19's umbrella with A21's specific code inside it, `G21_FLAG_OFF` or `G21_PHASE_NOT_REACHED`, or the route-level `PHASE_NOT_ENABLED`, whichever the catalogue names for that activity, as A83 and A100 allow). **Precondition:** before Specify, the P1 buy route on a retail-regime listing, the P1 sell submission (INV-05 preview) and the stablecoin payout or withdrawal destination request are confirmed from A19's, A21's and A100's frozen specs and evidence to run the gate set before refusing (for the retail buy: G05 `fail` with A19's `G05_PHASE_OFF` plus a G21 `fail` row; for the sell submission and the stablecoin destination: G09 or G15 `not_applicable` plus a G21 `fail` row). Where a route refuses before `evaluateAction` runs, so that no row can be written, fix items are raised on A19, A21 or A100 (and the route's owner) before A88's Specify; A88 does not work around it.
- **G05 behind its flag (`PROBES-PHASE`):** the retail-regime listing record from A06's `p2-preview` scenario is loaded after the group's reset into the probe's own tenant with the P1 flag defaults kept (`offers.retail` and `resale.board` off, no licence binding), the same set-up A19's phase-leakage test uses; if the scenario cannot be loaded that way, that is a fix item on A06, not a local workaround. A wholesale-classified probe investor orders from it through the UI and the SDK: the order is refused with the catalogue's G21 code, the evaluation set holds G05 `fail` with A19's reason code `G05_PHASE_OFF` (the only G05 result reachable in P1 for a retail-regime vehicle, per A19 and A32; the exact code and fix-it key are taken from A19's and A32's registry at Specify, never `not_applicable`, which A19 reserves for wholesale regimes) beside the G21 `fail` row, and afterwards there is no order, no escrow reservation and no ledger entry.
- **G09 behind its flag (`PROBES-PHASE`):** the investor opens `sell` (INV-05 preview) and submits through the UI and through the SDK: no resale order is created (the design says "draft only" in P1), the API refuses with the catalogue's code for `resale.board`, G09's row is `not_applicable`, and the J13 group separately asserts that no band row was recalculated.
- **G15 behind its flag (`PROBES-PHASE`):** a stablecoin payout or withdrawal destination is requested with `payouts.stablecoin` off: refused with the catalogue's code, G15 `not_applicable`, no payout row, no custody request.

**9. Resume from `status.json` and the kill-and-resume run**

- The runner writes `e2e\regression\.runs\<runId>\status.json` after every state change of a group (`pending`, `resetting`, `running`, `passed`, `failed`, `interrupted`), by writing a temporary file and renaming it, so a crash never leaves a half-written file. It holds the run number, the group order and its seed, the frozen commit, the stack project name, the seed hash, the flag snapshot, and per group the attempt number, the reset command, the clock at start and end, start and end times, the extract hashes and the result. The `.runs\` folder is ignored by git through a `.gitignore` inside `e2e\regression\`. This file is the regression's own run state; the gauntlet's `status.json` stays outside the repo under `<workspace>\gauntlet\` (A01's rule) and is never written by this node.
- `npm run regression -- --resume <runId>` re-reads the file, checks that the frozen commit and the stack project are unchanged (`REGR_RESUME_COMMIT_CHANGED` or `REGR_RESUME_STACK_GONE` otherwise, and the run cannot be resumed), skips groups already `passed`, and re-runs a group left `resetting`, `running` or `interrupted` from its own reset and its first step. A resumed attempt is an interruption, not a retry: it is allowed only when the recorded cause is an external stop (the process was killed or the machine stopped) and never after a recorded failure.
- **Orphan check before the re-run.** Before resetting an interrupted group, the runner inspects the half-finished attempt's state through read-only queries and public APIs, records it in `.runs\<runId>\orphans\<groupId>.json` with an extract, and only then resets. Expected orphan states at the default kill points: (1) inside `A79-RUN-A`'s J04, after the order is submitted and before the PayID receipt is matched: the order is `awaiting_funds` (SM-05), with no funding journal and no matched receipt; (2) inside `A80-J06`, after the distribution run is approved and before it is funded: the run is `approved` (SM-08) with its SM-00 approval `approved` and not executed, no funding pay-in and no payout line paid. The check then lets the product's own jobs act on the orphan on the soon-to-be-reset stack (clock advanced through the sandbox panel control past the offer close and the 72-hour approval TTL, jobs run through A46's run-now). That clock move also fires the seeded time-based transitions a correct product makes in the same window (for example HAW01's lock-in ending on 25 Sep, certificates entering `expiring` under SM-02, seeded approvals APR-2285 to APR-2292 passing their 72-hour TTL under SM-00, KST01 going `live → closed` under SM-04, and SLA clocks), so the check has two parts. (a) **The orphan's own objects** (the order, run, approval and child rows named in `orphans\<groupId>.json`) may make only these transitions: SM-05 `awaiting_funds → expired` at the expiry sweep; SM-00 `approved → expired`; and whatever transition A03 and A40 define for the unfunded run when its approval expires. (b) **Every other object** must make exactly the transitions of a control: after the orphan check, the runner resets the group, applies the same clock advance and the same job runs from the same group start without the orphan, records the control's transitions and money movements in `orphans\<groupId>.control.json`, and compares; any difference (an extra, missing or different transition, receipt, payout or journal on a non-orphan object) fails the drill. Any other transition of an orphan object, any receipt matched or line paid for the orphan, any duplicate journal, or a targeted A20 reconciliation reporting a break that the control does not also report fails the drill. The runner then resets again before re-running the group. The orphan's order, run and approval ids are listed in the report as the exact residual of the half-attempt; the reset then removes them.
- The kill-and-resume run is a fourth run on its own fresh stack, with the same run seed and group order as counting run 1. The runner process tree is killed with `taskkill /F /T` at points chosen by the node QA's hidden fixture (default: the two points above). It must then: pass both orphan checks; resume and finish all groups; not re-execute any group already passed (the per-group test count in the reporter's JSON equals the manifest's count exactly once); produce no duplicate money movement (A17 receipts and A40 payouts idempotent); and produce per-group extracts, gate ledger and state ledger equal to counting run 1's for the same groups after replacing generated ids and wall-clock timestamps with ordinal placeholders (the normalisation rule is part of the frozen spec and of the node QA's hidden queries), with the orphan checks' residual as the only recorded difference.
- A counting run interrupted by a usage limit or a machine stop may be resumed and still count only if it passes every check the kill-and-resume run passes; the report records the interruption.

## Node-specific challenges (node QA)

- **Flake laundering (quality).** An owner's suite hides a retry inside `test.describe.configure`, wraps a step in `expect.toPass` with a 5-minute timeout, or catches its own assertion error and re-clicks; separately a group passes in runs 1 and 3 and fails in run 2. Every form must be detected and reported: the hidden retry by the report's `retry` index and the static scan, the self-retry by the flake-risk scan, and the intermittent group by a reset streak and a `flaky` fix item with both traces. Three green runs obtained any of these ways fail the node.
- **The phase gates pass by doing nothing (compliance).** The G05, G09 and G15 probes return 200 because a stub route answers "not available" in a body with status 200, the gate ledger counts `not_applicable` rows as a pass, or a route refuses before the gate set runs so no row exists and someone adds a route under `e2e\regression\` to make one. Expected: the action is refused with the catalogue's named code, no order, reservation, payout or custody request exists, beside a G21 `fail` row the G05 row is `fail` with `G05_PHASE_OFF` on the retail-regime action and the G09 and G15 rows are exactly `not_applicable` on theirs, a G05 set with only `not_applicable` rows fails the form, the ledger shows zero `pass` rows for the three gates in every run, and the static scan finds no route, handler or flag defined under `e2e\regression\`.
- **G22 green on one side only (agent misuse).** The agent groups' negatives are all refusals and no mandate call actually succeeds (a token whose scope was mistyped refuses everything, and the suite asserts only refusals), or the probe pair shows the agent's order passing a gate set that lacks G07 because the agent route took a different path, or the non-delegable refusal carries no audit event. Expected: at least one G22 `pass` that led to an order that settled (`A79-RUN-A`'s `alex-portfolio-bot` KST01 order), the agent and person gate sets equal except for G22 and the actor, a refusal set naming scope, cap, revocation, never-checker, kill-switch and non-delegable codes, and an "agent <token> on behalf of <person>" audit event for each.
- **Order dependence and leaked global state (money).** In the reverse-order run J21's halt, or an agent group's platform-wide kill switch, survives the next reset; or a group silently depends on state another group left. Expected: the reset check fails `REGR_RESET_INCOMPLETE` naming the leftover and the reset's owner; `REGR_UNDECLARED_EFFECT` fires for any end state a group did not declare; the shuffled run reveals any hidden dependence as a failure, never as a pass.
- **Clock collisions (money).** A clock-moving group (A79's J05 before ANN01's 2 Nov close, A80's month into December, the G18 probe) runs after another group moved the clock, so ANN01 has already auto-reverted. Expected: this cannot happen, because every group starts from its own reset at `AS_OF` and the reset check proves the clock; the report shows each group's clock at start and end.
- **Kill during money movement (money).** The runner is killed inside J04 after the order is submitted and before the receipt is matched, then again inside the isolated J06 between approval and funding. Expected: the orphan checks find the order `awaiting_funds` and the run `approved` and unfunded, the orphan's own objects make only the allowed transitions when the clock and jobs move (`awaiting_funds → expired`, the approval `approved → expired`), every other object's transitions (HAW01's lock-in end, certificate expiries, seeded approval TTLs, KST01's close) equal the no-orphan control exactly, no receipt is matched and no line is paid for the orphan, reconciliation reports no break the control does not; the re-run groups start from their resets; no passed group ran twice; the extracts equal run 1's after normalisation, with the orphan ids as the only recorded residual.
- **Stale stack, fresh-looking results (quality).** Run 2 starts on run 1's Postgres volume with the seed re-run on top, or the Hardhat chain keeps run 1's state. Expected: `REGR_STACK_REUSED` from the system identifier, volume ids or genesis hash, the run not counted, and the streak not advanced.
- **Planted breaks miscounted (money, G10).** The invariants treat the baseline GYM01 break as a failure on every group, or treat an A81 plant left open as expected. Expected: every comparison uses the group's `reset_expected` set (the baseline plus its reset scenario) plus its declared plants and leaves exactly, and a correct reset that loads a scenario never fails `REGR_RESET_INCOMPLETE`; the GYM01 break is unchanged at every group's end unless the owner declares its resolution; every A81 plant is closed at `A81-BREAKS`'s end.

Expected: the read-only role refuses writes, internal endpoints refuse the runner's credentials, and a static scan of `e2e\regression\` finds no import of product internals, no service-principal secret and no write SQL; any journey that needed such a step is a fix item on its owner.
