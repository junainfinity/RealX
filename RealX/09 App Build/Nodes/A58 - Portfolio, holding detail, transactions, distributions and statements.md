# A58 - Portfolio, holding detail, transactions, distributions and statements

**The five investor "my money" screens, rendered from A47's read contracts (plus A41's tax profile and A36's open offerings) and nothing else: POR-01 portfolio (four KPI tiles, holdings rows with value at valuation and at last price, alerts, an empty state that points to open offers), POR-02 holding detail (property band, tokens, average cost, income received, lock-in end, register-match date, that holding's distributions, Sell only from a holding), POR-04 transactions (the design's "Activity" table with filters, confirmation PDFs, on-chain references and the "by your agent <name>" marker linking to the token's activity on ACC-05), POR-03 distributions (twelve-month chart, the FY tiles and the month / trust / per token / tokens at record date / gross / withheld / paid table) and POR-07 tax and statements (FY tiles, tax status, AMMA, payment advices, confirmations and annual statements). Every list is cursor-paginated, every figure is the API's integer-cents twin string, and no number, state or reason is ever computed or invented in the browser.**

## Build brief

This node is UI-only: the `(investor)/portfolio` route group of `apps/web` and the `features/portfolio` package of components, hooks and formatters. It calls the API only through `packages/sdk` (the full SDK A09 generates from every module's OpenAPI) and never through a hand-written fetch; the only routes it calls are A47's and A41's investor reads and A36's public offerings read. It owns no API route, no table and no job. Every figure on every screen is an API field rendered as its `formatted` twin; the browser never adds, subtracts, averages or converts. Every rule (who may see what, what is masked, whether and why Sell is blocked, whether a line is held, whether tax is withheld) is decided by the API, and the screen only shows the answer. Because the same reads serve a person's agent through A12's tokens and A104's MCP server, this node adds nothing an agent could not also get, and it publishes the mapping that proves it (`parity.json`, below).

**Follow-up requests this node depends on (raised at Specify, not substituted locally).** Each is a field or parameter another node must add. Until it exists the dependent control is not rendered (never faked in the browser), and the Challenge item that needs it runs on a composed SDK fixture.

**Routing, shells and screen codes**

- Routes under A52's investor shell (public header with Portfolio / Investments / Wallet / Activity / Statements nav, avatar, footer): `/portfolio` (POR-01), `/portfolio/[code]` (POR-02, `code` = the vehicle's short code as returned in `me/portfolio.holdings[].code`), `/portfolio/distributions` (POR-03), `/portfolio/transactions` (POR-04; page title "Activity", nav label "Activity", as the design), `/portfolio/statements` (POR-07; nav label "Statements"). These rows already exist in A52's frozen `routes.ts` table (Portfolio row), including the 308 redirect from the product map's `/documents/tax` to POR-07; this node only asserts them in a test and registers nothing.
- Every link these pages render goes through A52's `href(code, params)` helper, never a literal path: Buy and Buy more to PUB-04 (`/investments/[code]`), Sell to INV-05 (`/invest/[code]/sell`), "All investments" to PUB-03, tax links to ACC-01, the agent marker to ACC-05's token detail (F9), alerts to their targets (below). A Playwright check crawls every `<a href>` on the five pages in every seeded state and asserts each resolves to a row in A52's `routes.ts`.
- Each page exports `screen = defineScreen({ code: 'POR-0x', design: 'port' | 'activity' | 'statements' | 'ext:POR-02' | 'ext:POR-03' })` for A52's screen registry and the fidelity harness; the canonical id in tests, evidence and analytics is the product-map code, never the design's "INV-01" / "INV-03" (A00's reconciliation table).
- All five pages are server components that read through the SDK with `cache: 'no-store'` (portfolio reads are never cached by Next.js, the browser or a service worker, because a halt, a freeze or a break must be visible on the next load; A47's challenge "materialised row keeps saying matched" is re-run here against the page). Client components exist only for the filter chips, "Load more", the chart hover, the withheld popover and the download buttons.
- Signed-out or expired session: A52's guard redirects to sign-in and back; a session for a sponsor user with no investor account gets A52's "no investor account" page, never a blank portfolio.

**POR-01 Portfolio (`/portfolio`, design `port`)**

- Header "Good morning, {first name}" / "Good afternoon" / "Good evening" from the investor's display name and the Australia/Sydney clock (the design's fixed "Good morning, Alex" is the 06:00-11:59 case); subline "Your property tokens, income and cash in one place."

- **Sell rule (POR-01 and POR-02).** The page renders only A47's named Sell-block field (F2) and never derives the reason from `halted`, `holding_state`, `locked_units`, `frozen_units` or the phase flag. A47 applies the precedence halted > frozen > locked > board_closed, so in P1 a halted holding reads "Trading halted", not the board message.

  | Sell-block field | Control | Sub-line |

  | `frozen` | disabled | "Not available" |

**POR-07 Tax and statements (`/portfolio/statements`, design `statements`)**

- Header "Distributions and tax", subline "Monthly payment advices, annual AMMA tax statements and transaction confirmations."
- KpiGrid from `GET /v1/me/statements` `kpis`: **{FY} to date** (`fy_to_date_net_cents`, sub-line month range), **{prior FY} total** (`prior_fy_net_cents`, sub-line "AMMA issued {issued_at}" or, when `prior_fy_amma.issued_at` is null, the API's statutory-date text, "AMMA expected by 30 Sep" on the seed), **Tax withheld** (`tax_withheld_fy_cents`, sub-line from the tax-caption table above).
