# A101 - Agent guard: anomaly detection, sensitive-action notices and tiered kill switches

**The runtime controls from founder decision D04 that A12 does not own. First, anomaly detection over token activity as versioned, replayable rules: a burst against the token's own baseline, first use from a new country, activity outside usual hours, repeated near-cap orders or withdrawals, many refusals in a row, calls after the person has gone dormant, and probing of checker or signer routes. Each rule raises an `AgentAnomaly` that puts the token on hold, fail-closed, until the person clears it with a passkey or a SECO clears it on ADM-35 with a reason, and each also raises an alert through A13. The burst rule also feeds AML monitoring (A42). Second, sensitive-action notices: a `NoticePolicy` per person, delivered through A43 to the person's own channels and never to the agent. Third, kill switches in tiers: per token, per user, per tenant, per user type and platform-wide. Each tier stops exactly its own set of tokens, from the next request.**

**Build status:** not started. **Milestone:** AM3 (Business services). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops). Raised from 6-10 by the 24 Sep 2026 spec review: seven rules, five worker jobs, three tier providers, a 10,000-sequence replay property, a 5,000-tuple tier matrix and a two-process stop-latency run. `final-graph.json` must be updated to match (`est_lo` 10, `est_hi` 14).

In one sentence, this node is for the following: when an agent behaves unlike itself, the person hears about it on their own channels, the agent stops on its next call, and only the person (or a named RealX security officer with a reason) can let it start again. A12 decides whether a single call is allowed. This node watches the pattern of calls over time and owns the brakes above a single token. It draws no screen. ACC-05 and SPN-16 are A60's, and ADM-35 is A77's; both render what this node returns. This plan is not legal advice. Every threshold below is a row of versioned data with a default. **2. Anomaly rules: versioned data, pure functions, replayable**

- A rule set is an `agent_guard_ruleset` row with these columns: `code` (the seed is `AG-2026.1`), `effective_from`, `state` (`draft -> review -> effective -> superseded`, in A03's engine format; an `UPDATE` to an effective row is refused), `params` (canonical JSON), `params_sha256`, `approval_id` and `supersedes_code`. Exactly one rule set is `effective` at any instant. Every anomaly records the rule set code and `params_sha256` it fired under.
- Each rule is a pure function in `rules/`. It takes `(params, window, baseline, context)` and returns `{fired, severity, evidence}`. It does no I/O, and time comes only from `context.now`. `window` is the list of `api_token_activity` rows the rule counted, given as an explicit list of activity ids (never an id range, because ids are not assigned in commit order under concurrency). Windows use the same bucket semantics as the inline counter: a call's bucket is `floor(created_at / bucket_width)`, taken from the activity row's own `created_at` (the injectable clock reading A12 writes), and a rule's window is the current bucket plus the preceding `window / bucket_width - 1` buckets. For `burst` the bucket width is 30 s, so the 120 s window is four buckets. `baseline` is the token's `agent_baseline` row for the relevant hour. `context` holds the token's owner type, mandate caps, time windows, the owner's last human sign-in time from A11 and, for `new_country`, the set of country codes seen for the token in the last 90 days. The rules and their seeded defaults (all are founder-set data; `set_with_counsel` is marked only where AML is touched):
  - `burst`: writes in a sliding window above `max(floor_writes, multiple x baseline_p95)`, or reads above `max(floor_reads, multiple x baseline_p95)`. Defaults: window 120 s, multiple 5, `floor_writes` 20, `floor_reads` 300. A token younger than 7 days uses the floor alone. The product map's example is "40 orders in 2 minutes". This rule also emits `agent.guard.burst_detected` for A42 (`set_with_counsel: true`, because it feeds G14).
  - `new_country`: a call whose resolved country has not been seen for this token in the last 90 days. A new IP inside a country already seen is not an anomaly; it produces the `agent.first_use_new_ip` notice only (§5). A token with an IP allow-list cannot reach this rule, because A12 refuses the call first.
  - `off_hours`: at least `min_calls` calls (default 10) in an hour-of-week bucket (Australia/Sydney) in which the token's last 28 days show zero calls. The rule applies only to tokens older than 14 days and without mandate time windows; windows are already enforced by A12.
  - `near_cap_repeat`: at least 3 orders or withdrawals within 24 hours, each of at least 90 percent of the mandate's `per_action_cap_cents`. It also fires when the daily cap is reached by 3 or more separate actions on each of 3 days in a row.
  - `refusal_streak`: 10 refused calls in a row for one token, or more than 50 percent refused over the last 50 calls within 10 minutes. The count includes every G22 refusal, every pre-scope refusal (including `requiresHuman`), every gate refusal raised inside a handler (G01 to G21, recorded by A12 as `failed_after_gate`) and `TOKEN_WRONG_ENVIRONMENT`. It does not count `TOKEN_INVALID` (no token can be attributed), `429 RATE_LIMITED` (the rate limit is its own brake), or refusals that exist only because the token is already stopped: `TOKEN_REVOKED`, `TOKEN_EXPIRED`, `TOKEN_PENDING`, `AGENT_HELD` and `AGENTS_PAUSED`. A call refused with one of those codes never raises a hold.
  - `dormant_owner`: a write call when the owner has had no signed-in human session or passkey assertion for `dormant_days`. The default is 90 days for investor, sponsor and partner owners and 30 days for staff. Reads continue, and are counted for the daily summary, only until a write trips the rule: the rule's action is `hold`, so from then on every call of that token, reads included, is refused `423 AGENT_HELD` until the person clears the hold (which also proves the person is present). This differs from A12's `owner_dormant` hold class, which A12 places on `iam.account.dormant` for locked privileged accounts.
  - `authority_probe`: a token call refused with one of the codes by which neighbouring nodes say "A101 receives the anomaly event": `APR_CHECKER_MUST_BE_HUMAN` (A14), `P9_TOKEN_CREDENTIAL` (A15, A72), `CLM_INTERNAL_ONLY` (A31), `CLS_DECIDER_MUST_BE_HUMAN` (A32), `AML_MLRO_ONLY` (A42), `INC_HUMAN_ONLY` and `self_subject` (A48, A13), `G22_AGENT_NEVER_CHECKER` (A12), and a 403 on an internal or service-principal route (A36). The threshold is 1 for staff tokens and 3 within 24 hours for every other owner type. The product map's "scope probing" is this rule plus `refusal_streak`. This seventh rule is added to the summary's six because A14, A15, A28, A31, A32, A36, A42 and A48 each already promise to report these events here.
- Each rule has a parameter `action` with value `hold` or `watch`. In `AG-2026.1` every rule is `hold`, as the node summary requires. `watch` exists as a value so that a later rule set can soften a rule. A `watch` anomaly is `open` with a notice and a queue item, but no hold. Softening needs the change policy below.
- **Changing a rule set.** A change is an A14 request `agent_guard.ruleset.change` under `4E` (SECO maker, CCO checker). It uses `6E`, adding MLRO as a second checker, when the change loosens `burst` (a higher threshold, a longer window, or `hold -> watch`), because `burst` feeds G14. `POST /v1/agent-guard/rulesets/simulate` runs a draft rule set over the last N days of activity (N at most 30) and returns the anomalies that would have fired, the anomalies that would not have fired, and the differences from the effective set. This is A19's simulator pattern, and the change request carries the simulation's hash. A staff agent may draft and simulate as maker. It may never be a checker.
- **What each anomaly records for replay.** The rule set code and `params_sha256`; `counted_activity_ids` (the exact list of activity ids the counter counted when the rule fired, copied from the counter rows) and its `counted_ids_sha256`; the bucket keys; the `agent_baseline` row key `(token_id, hour)` and its `snapshot_sha256`; and a `context_snapshot` (canonical JSON of the `context` fields the rule read, for example the country set for `new_country`, never an IP) with its hash. Replay therefore never depends on data that later ages out, such as `agent_token_ip_seen` rows.
- **Retention for replay.** `agent_baseline` is insert-only, keyed `UNIQUE(token_id, hour)`, and a baseline row is kept at least as long as any anomaly that references it. A12 must keep every `api_token_activity` row an anomaly lists for as long as the anomaly record is kept; the retention period itself is set in A102's retention schedule, and A102's erasure job must skip activity rows listed in `counted_activity_ids` while the anomaly is retained. Both are requested as data rows from those owners.
- **Replay.** `replay(anomalyId)` loads the recorded rule set version, the activity rows by `counted_activity_ids` (checking `counted_ids_sha256`), the recorded baseline row (checking `snapshot_sha256`) and the `context_snapshot`, then re-runs the rule. It must return the same `fired`, `severity` and `evidence_sha256`. The nightly worker job `agent-guard.replay-audit` replays every anomaly from the previous day plus a seeded 5 percent sample of older ones. Any mismatch raises `agent.guard_replay_mismatch`. The route is `GET /v1/agent-guard/anomalies/{id}/replay`, staff only, with `V` on M26. An anomaly that came from an external signal (§3) is replayed over the evidence window computed from the token's own activity, like any burst; only a caller who is MLRO or CCO also sees the line "signal `<event id>` present". Every other caller gets exactly the ordinary burst replay shape.

**3. Detection paths: inline (in the request) and event-driven (in the worker)**

- **Inline path (the next call is always stopped).** Two hooks, each in a transaction that A12 commits. Both use O(1) reads of `agent_guard_counter` (one row per token, rule and time bucket, `UNIQUE(token_id, rule, bucket)`, updated under its row lock, so two concurrent calls cannot both slip under a threshold; each row also stores the activity ids it counted), `agent_baseline` and `agent_token_ip_seen`.
  - **`afterEvaluate` (A12's existing slot), for calls G22 has passed.** It returns at once when `result.pass` is false. Otherwise it runs `burst`, `new_country` and `dormant_owner` in the business transaction, before the handler. When a rule fires, the call that crosses the threshold is itself refused with `423 AGENT_HELD`: the hook marks the call refused, the business handler never runs, and A12 records the refusal in its short refusal transaction, in which the `onOutcome` hook below writes the hold, the anomaly, the token hold through `setTokenHold`, the audit event and the outbox events. Nothing about the hold depends on the business transaction committing.
  - **`onOutcome` (requested from A12.1, §1), for every recorded non-pass outcome.** It runs `refusal_streak` and `authority_probe` inside A12's committed refusal or `failed_after_gate` transaction, so it sees refusals raised before scope evaluation (`requiresHuman`, `APR_CHECKER_MUST_BE_HUMAN`, `self_subject`), G22 refusals and gate refusals raised by handlers (G01 to G21). The counter update and any hold are written in that transaction and commit with the refusal rows. The refused call's own refusal code stands; the hold stops the next call. It also writes the hold that `afterEvaluate` decided on. Outcomes excluded by `refusal_streak` (§2) are ignored.
  - **Latency.** On the path where no rule fires, the two hooks together add at most 5 ms at p95 at 200 requests per second on the Docker stack (A84 re-measures it). On the path where a rule fires, the hook work (anomaly, hold, audit and outbox rows) adds at most 25 ms at p95. Neither budget includes chain time, because no external call is made inside either transaction: session-key revocation leaves through the outbox after commit (§4).
- **Event-driven path (the next call after the hold commits is stopped).** The worker job `agent-guard.intake` is an A09 event handler, idempotent on `event.id` through `processed_event`. It consumes:
  - `agent.action.money` (A12) and `orders.placed` with `channel` `api` or `mcp` (A37), deduplicated per operation id, for `near_cap_repeat` and the money notice;
  - `aml.agent_burst` (A42);
  - `agent.action.refused` (A12), used only for backfill when the hook was down, since the inline counter is authoritative;
  - audit events with `actor_type = AGNT` and sensitivity `sensitive`;
  - `tenancy.tenant.suspended` and `tenancy.tenant.reinstated` (A33);
  - `kill_switch.engaged` and `kill_switch.released` for `agents.traffic` (A48).
- **Baselines.** The worker job `agent-guard.baseline` runs hourly. For each token active in the last 28 days it recomputes the p95 calls per 2-minute window by hour of week, and the set of active hours. It writes `agent_baseline` with a `snapshot_sha256`, which anomalies record for replay. It is idempotent and insert-only: re-running the same hour finds the existing `(token_id, hour)` row and checks that the recomputed row is byte-identical, never overwriting it. The schedule is declared through this module's own `registerJob` call, as A46 requires, with a seed test. It is never an edit to A46's code.
- **AML boundary (G14, M20).** On `aml.agent_burst` this node raises a `burst` anomaly for the token, and its effect on the person is exactly that of its own burst detection: the same hold, the same `agent.anomaly_hold` notice with the same plain-English sentence, and the same ADM-35 row.
  - **Need-to-know columns.** The anomaly's `source` (`inline | event | signal`) and `signal_ref` (the signal's event id) sit under A04's need-to-know RLS policy, readable only by MLRO and CCO. For every other reader, including SECO, SUPP and the person, neither field is returned for any anomaly (so its absence says nothing). No other column, response, outbox event, notice, alert title or log line names AML, a case, an alert id, a scenario or the signal's event id. `agent.guard.anomaly_raised` carries no `source`.
  - **Evidence.** The evidence window of a signal anomaly is computed from the token's own activity in the signal's time window, with the same bucket semantics, fields and shape as an inline burst, so its detail, list row and replay are indistinguishable from an ordinary burst for anyone outside need-to-know.
  - **Deduplication against the feedback loop.** A42's `agent_order_burst` scenario may emit `aml.agent_burst` for the same burst this node already detected and reported through `agent.guard.burst_detected`. A signal is merged into any `burst` anomaly on the same token, open, held or cleared, whose evidence window overlaps the signal's window or ended less than `signal_merge_hours` (data, default 24) before it: the signal's id is recorded in `signal_ref` and nothing else changes. No new hold and no new notice are raised, because an ordinary burst never raises two. Only a signal with no such anomaly raises a new one.
  - Clearing such a hold neither closes nor touches A42's alert. G14 blocks payouts through A19, not here.
  - **Account frozen or under AML review (ACC-05 state "every token is suspended").** This is A12's rule, not this node's: A12 holds every token of the account's members with the neutral hold class `account_under_review` on A30's `investor.suspended` and releases only that class on `investor.reinstated`. This node raises no anomaly, no `agent_hold` row and no notice for it, and its `holds` and `anomalies` routes do not list it (A12's hold has no `agent_hold` id, so a clear on it returns 404). Stacked with an `agent_guard` hold, it follows A12.1's stacked-hold rule (§1). Whether an AML freeze should hold the tokens at all is A60's open Specify point (i) for the founder and MLRO (HG-LEGAL); if the answer changes, A12 and A30 change, not this node.
- **IP and country.** `GeoIpResolver` is an interface in `geo/`. The only implementation built is a fixture that maps the RFC 5737 and RFC 3849 documentation ranges to seeded countries (AU, NZ, SG, US, GB). A real IP-to-country database is an HG-VENDOR choice. `agent_token_ip_seen` stores an HMAC of the /24 (IPv4) or /48 (IPv6) prefix under a key from A08's kms sandbox, the country code, and the first-seen and last-seen times, never the address in clear. Rows older than 90 days are deleted by the baseline job. An unresolvable address counts as country `ZZ` and is treated like any other country.

**4. Holds (per-token tier) and how they are cleared**

- An `agent_hold` row (`AGH-<yyyymmdd>-<6 base32>`) has these fields: `token_id`, `on_behalf_of_id`, `tenant_id`, `cause` (`anomaly`, `staff`), `anomaly_id` (for anomaly holds), `placed_by` (`system:agent-guard` or a staff principal), `reason_code`, `placed_at`, `cleared_at`, `cleared_by`, `clear_kind` (`person_passkey`, `staff_reason`, `token_revoked`, `token_expired`) and `clear_ref` (an assertion id or an audit id). A token has at most one open hold; a second anomaly on a held token attaches to the open hold.
- Placing a hold calls A12's `setTokenHold(tokenId, holdId, 'agent_guard', tx)` in the same transaction: the token becomes `suspended`, and the next call on any API process is refused `423 AGENT_HELD` with `hold_id`, `hold_class`, `anomaly_id` and the rule's plain-English name (for example "placed many orders in a short time"). The refusal never includes the threshold, the window or the baseline. The same transaction also:
  - writes one `agent.guard.session_key_revoke` outbox event for every mandate of the token that has a wallet cell (Specify point (f)). No chain call happens inside the transaction. The off-chain block is immediate, because A29's `check.ts` reads the token's hold through `introspect` on every session-key op. After commit, A29's consumer marks the `session_key` row `revoked` and submits the guardian revoke with retry, recording the tx hash within `SESSION_KEY_REVOKE_SLA` (A29 raises its own Sev2 on a breach). The `agent-guard.fanout` job checks completion: every requested revoke must reach `revoked` with a tx hash, and a missing one after the SLA marks the hold's SECO queue item `session_key_revoke_overdue`;
  - emits `agent.guard.hold_placed`, which A46 uses to move the token's webhook subscriptions to `skipped_paused` (A46 already names "paused or suspended by A101").
- A release never restores session keys. After a hold is cleared with `resume`, the person registers a new key through A29's `requiresHuman` route with the owner passkey. Between the hold's commit and the on-chain revoke's confirmation (at most `SESSION_KEY_REVOKE_SLA`), a UserOp sent straight to a third-party bundler on testnet is stopped only by the on-chain policy's own caps; this residual window is recorded for HG-PENTEST.
- Anomaly states (`open | held | cleared | dismissed`, the vocabulary A77 renders) form a local transition table in A03's format. The transitions are: `open -> held` (a staff hold on a watch anomaly), `open -> dismissed` (staff with a reason), `held -> cleared`, and nothing else (`GUARD_ILLEGAL_TRANSITION`). An anomaly's hold state and the token status never disagree: a test checks this after every transition.
- **Clearing by the person.** `POST /v1/agent-guard/holds/{id}/clear` with `{resolution: resume | revoke}`.
  - The route is `requiresHuman: true`: every token and MCP session gets A11's `AGNT_NOT_ALLOWED` before scope evaluation.
  - It needs a fresh passkey assertion (A11 primitive, purpose `anomaly_clear`, at most 5 minutes old) over the canonical hash of `{hold_id, anomaly_ids, resolution, acknowledgement_text_version}`.
  - The caller must be the token's `on_behalf_of` human, or, for a sponsor member's token, an SP-OWN of the same tenant.
  - `resume` calls `releaseTokenHold` (token `active`) and `revoke` calls A12's revoke.
  - Staff-owned tokens cannot be cleared by their owner (`GUARD_STAFF_HOLD_NEEDS_SECO`), because a staff agent that tripped a guard is a security event, not an inconvenience.
  - A hold that staff placed manually cannot be cleared by the person (`GUARD_HOLD_PLACED_BY_STAFF`); the person sees who placed it ("RealX support") and the reason code's person-facing sentence.
- **Clearing by RealX staff (ADM-35).** It uses the same route with `{resolution, reason_code, note?}`.
  - The caller is a SECO, and the route is `requiresHuman`.
  - It needs a hardware-attested assertion (A11's AAGUID check, purpose `anomaly_clear`).
  - The reason code comes from the catalogue: `owner_confirmed_activity`, `rule_false_positive`, `travel_verified`, `integration_change`, or `other` with a note of at most 500 characters, PII-scanned. Without one the route returns `422 GUARD_REASON_REQUIRED`.
  - It is refused when the SECO is the token's owner or the owner's agent (`self_subject`, the code A13 and A48 use) and when the SECO placed the hold (`GUARD_HOLD_PLACER_CANNOT_CLEAR`).
  - A staff clear is a single accountable decision: it restores rights that a human already granted and that two people approved for staff and sponsor tokens (A12 §2). It is audited with the reason, and the person is notified that RealX cleared the hold.
- **Holds placed by staff.** `POST /v1/agent-guard/holds` with `{token_id, reason_code}`.
  - SECO or SUPP may place one, with immediate effect and a mandatory reason. This is a protective act, like A12's revoke ("Revoke any token · SECO or SUPP · immediate").
  - A staff agent may call the route as maker for its human (A51's manifest entry "ADM-35 Hold token → `agent-maker`"). The call returns `428 CONFIRMATION_REQUIRED` in A12's shape and places the hold only when the human confirms with a hardware key (A77 §5).
  - A staff member or their agent may not hold their own tokens through this route. They revoke them through A12 instead.
- Holds never expire by time. A token that reaches `expires_at` while held becomes `expired` (A12 sweep), and the hold closes with `clear_kind = token_expired`. A revoke closes it with `token_revoked`.
- **Review clock.** Each open hold on a staff token, and each `open` watch anomaly, is an item of the A13 queue source `agent_anomaly_holds` (policy `agent_hold_review_1bd`, one business day, owner SECO). A hold on an investor, sponsor or partner token has no clock, because the person decides, but it appears in the SECO queue for visibility.

**5. Sensitive-action notices (NoticePolicy)**

- A `notice_policy` row exists per human principal and is versioned (a change inserts a new version). Its rows and defaults are below. **Locked** rows cannot be switched off (the grey "Required" pill on A50's drawing). **Toggle** rows can. A50 draws five of these rows (see Design references); the other five are data this node returns and are raised with A50 as a design finding.

| Row label | Event source | A43 type | Default | Lock |
|---|---|---|---|---|
| Token created or widened | `agent.token.created`, `agent.token.activated`, `agent.mandate.widened` (A12) | `agent.token.created`, `agent.token.widened` | on | locked |
| Places an order | `orders.placed` with channel `api` or `mcp` (A37) at or above `money_threshold_cents` | `agent.money_action` | on | locked (threshold adjustable) |
| Moves money | `agent.action.money` (A12, A39 withdrawals and others) at or above `money_threshold_cents` | `agent.money_action` | on | locked (threshold adjustable) |
| Reaches its daily cap | mandate usage crosses `near_cap_percent` of a daily cap, once per mandate per Sydney day | `agent.mandate_near_cap` | on, 80 % | toggle |
| Is refused by a gate | `refusal_notice_streak` refusals in a row (default 3; below the anomaly threshold) | `agent.refusal_streak` | on | toggle |
| Is used from a new IP | first call from an IP prefix not seen for the token in 90 days, same country | `agent.first_use_new_ip` | on | toggle |
| Reads documents or other sensitive actions | audit events with `actor_type = AGNT` and sensitivity `sensitive` | `agent.sensitive_action` (A43.1) | off | toggle |
| Is held by an anomaly check | hold placed | `agent.anomaly_hold` | on | locked |
| Kill switch | any tier engaged or released that covers one of the person's tokens | `agent.kill_switch` | on | locked |
| Daily summary | the `agent-guard.daily-summary` job at 07:00 Australia/Sydney when any token of the person made a call in the previous day | `agent.daily_summary` | off | toggle |

- **Bounds.** The bounds are data: `money_threshold_cents` from 0 to 100,000 (A$0 to A$1,000, default A$0, so every agent order or money movement is notified until the person raises it); `near_cap_percent` from 50 to 95; `refusal_notice_streak` from 1 to 9 (it must stay below the rule's streak). A value out of bounds returns `422 GUARD_NOTICE_BOUNDS`. An attempt to switch off a locked row returns `422 GUARD_NOTICE_ROW_LOCKED`.
- **Changing the policy.** `GET /v1/agent-guard/notice-policy` (delegable read) and `PUT /v1/agent-guard/notice-policy`. A change that only tightens (switching a row on, lowering the threshold, lowering the near-cap percentage or the streak) needs the signed-in session, and a token may make it. A change that loosens anything is `requiresHuman` and needs a fresh passkey assertion (purpose `notice_policy_loosen`) over the new policy hash. Otherwise it returns `AGNT_NOT_ALLOWED` for a token and `FRESH_ASSERTION_REQUIRED` for a session. An agent can therefore never quieten the notices that report its own conduct. Notice routing (channels, verified contacts, mute rules) stays A43's. This node decides only whether to emit.
- **Recipients.** The recipient is always the human in `on_behalf_of_id`. For a sponsor member's token, the tenant's SP-OWNs also receive `agent.anomaly_hold` and `agent.kill_switch`. For a staff token, SECO receives the `agent.anomaly_hold` alert through A13; it is an alert, not a notice. Every notice carries `object_ref` (token id, hold id or operation id) and `vars`: the token's agent name as inert text, the prefix, the action, the amount and the remaining allowance. They never carry the secret, a threshold, or anything about an AML signal. Dedup keys are `(type, token_id, operation_id | hold_id | day)`, so a replayed event never makes a second notice.
- **Never to the agent's channel.** The agent's channels are these: the response to its own call, A46 webhooks, A104's MCP resources and notifications, and any address in a request body. The rules that keep notices off them:
  - This node's outbox events (`agent.guard.*`) are `webhook_eligible: false` in A46's catalogue, and A46 already excludes `agent.guard.*` from the staff `agent.*` family. A test proves that no subscription can be created for them, by any owner type. Other `agent.*` events (A12's token and mandate events, which A46 offers to staff, and `agent.confirmation.*`) may legitimately reach webhooks: they are ids and codes, never an A43 notice body.
  - The notice log routes (§7) are `requiresHuman`, so A104's generated catalogue never lists them.
  - A43 never delivers to an address in the triggering request (A43 §"notice goes to the human behind `on_behalf_of_id`").
  - A43.1 hides the `agent` category from token reads (Specify point (e)).
- **Platform switch fan-out.** When A48 engages `agents.traffic`, this node sends `agent.kill_switch` to every human who owns at least one `active` or `suspended` token, in batches of 500 through A43's dispatcher. It sends one notice per person, not one per token. The same fan-out job writes the `agent.guard.session_key_revoke` events for every covered mandate with a wallet cell (§6).

**6. Kill-switch tiers (user, tenant, owner type; the token tier is §4; the platform tier is A48)**

- This node registers three `KillSwitchProvider` implementations with A12's middleware through `registerKillSwitchProvider(tier, provider)`, for the scopes A12 already defines. Each reads `agent_switch` inside the request transaction, from an index on `(scope, scope_id) WHERE state = 'engaged'`, never from a cache:
  - `user(id)`, where id is the token's `on_behalf_of_id`;
  - `tenant(id)`, where id is the owner principal's `tenant_id`;
  - `owner_type(id)`, where id is the owner type (`investor`, `sponsor`, `partner` or `staff`).

  A call is refused if any tier is engaged. The refusal is A12's `423 AGENTS_PAUSED`, with `tier` naming the widest engaged tier in the fixed order `platform > owner_type > tenant > user`, and then `AGENT_HELD` for the token. There is no grace window: the first call after an engage is refused, and the first call after a release succeeds.
- **Wallet session keys at every tier.** An engage of the user, tenant or owner-type tier writes, in the engage transaction, one `agent.guard.session_key_revoke` outbox event for every covered mandate that has a wallet cell (in practice investor mandates with P2 wallet cells). For large tiers (owner type, and the platform tier through the fan-out on A48's `kill_switch.engaged`), the `agent-guard.fanout` job writes those events in batches of 500 after commit. The off-chain block is immediate at every tier, because A29's `check.ts` reads the kill-switch state through `introspect`. The fan-out job checks completion (every covered key `revoked` with a tx hash within `SESSION_KEY_REVOKE_SLA`) and writes one audit event `agent_guard.switch.session_keys_revoked` with the count; an overdue key raises the switch's A13 alert again with that detail. A release never restores keys: each person registers new ones with the owner passkey.
- **Exactly its tier.** Each tier covers the following tokens, and no others.

| Tier | Covers | Never covers |
|---|---|---|
| Token hold (§4) | that token, in its environment | any other token of the person |
| User | every token whose `on_behalf_of_id` is the person, live and sandbox (`rx_sb_`), every prefix | the other holder's tokens on a joint account; the tenant's other members |
| Tenant | tokens whose owner has `tenant_id` equal to the tenant and prefix `rx_spn_`, including the SP-VAL and SP-PM tenant members from A98, plus those owners' `rx_sb_` tokens | investors in the tenant's trusts (`rx_inv_`), platform partners engaged on its vehicles (`rx_ptr_`), staff, other tenants |
| Owner type (Specify point (d)) | every token whose owner type matches, in both environments | the other three owner types |
| Platform (A48) | every token, in both environments | human sessions, which keep working at every tier |

  The tenant tier cannot target the RealX platform tenant (`422 GUARD_TENANT_IS_PLATFORM`). Staff tokens are paused per user, by owner type `staff`, or by the platform tier.
- **Who engages and releases each tier** (A14 policy rows seeded by this node). Engaging is protective, so it acts at once. Releasing restores rights, so it always needs a human and never `SGL+R`, as in A48.
  - **User, engaged by the person.** `POST /v1/agent-guard/switches/user` needs the signed-in session and a confirmation. A fresh passkey assertion is accepted but not required, because pausing only removes rights and friction in an emergency is itself a harm (Specify point (a)). A token of the same person may also engage it (a protective act that stops the token itself). The engaging call returns `200`, and every later call of that token is refused. The person resumes with `POST .../user/release`, which is `requiresHuman` and needs a fresh passkey assertion (purpose `agents_resume`), and only when the person engaged the tier (`source = person`). Otherwise the route returns `GUARD_RESUME_NOT_ALLOWED`, naming the source.
  - **User or tenant, engaged by staff.** A14 action `agent_guard.user_tier.engage` or `agent_guard.tenant_tier.engage` under `SGL+R`, marked protective. A SECO or SUPP (user tier) or a SECO or CCO (tenant tier) acts with a hardware key and a mandatory reason. A different person from {SECO, CCO} ratifies within 2 hours. A lapse raises A13's `approval.unratified` and never lifts the switch. Release is `agent_guard.tier.release` under `4E`: the maker is a SECO or CCO, the checker is the other of SECO and CCO, and the person who engaged may be neither (A48's `KS_ACTOR_CANNOT_RELEASE`).
  - **Tenant, engaged by the sponsor.** An SP-OWN engages "Pause all <tenant> agents" with the signed-in session. The same SP-OWN, or another SP-OWN, resumes with a fresh passkey assertion, and only when an SP-OWN engaged it. SP-OPS, SP-FIN, SP-IR, SP-VAL and SP-PM cannot engage or release the tenant tier; they can pause their own tokens through the user tier.
  - **Tenant, engaged by tenant suspension.** `tenancy.tenant.suspended` engages the tenant tier with `source = tenant_suspension` in the transaction that handles the event. A12 also revokes the tenant's tokens, and this tier is the second, independent brake. It is released only through the staff `4E` release after `tenancy.tenant.reinstated`. A reinstatement does not release it by itself.
  - **Owner type** (Specify point (d)). `agent_guard.type_tier.engage` under `SGL+R`: a CCO or SECO acts, and the other ratifies. Release is `4E`, as for the other staff tiers.
  - **Agents and SoD.** A staff agent can never act on an `SGL+R` engage, ratify, check or release (`APR_CHECKER_MUST_BE_HUMAN` before scope evaluation, reported to the `authority_probe` rule). It may draft a release request as maker only when its human did not engage the switch. An agent whose human engaged a switch cannot draft its release, because the agent counts as its human.
- **State reads.** `GET /v1/agent-guard/switches?scope=&subject=` returns each engaged row: `scope`, `subject_id`, `engaged_at`, `engaged_by_role`, `source` (`person`, `sponsor_owner`, `staff`, `tenant_suspension`), `approval_id`, `ratification_state`, `ratify_by` and `release_allowed_for_caller`. The person's `GET /v1/agent-guard/switches/me` returns every tier that currently covers them, the platform tier included, read through A48's `GET /v1/kill-switches`, so A60's banner can say "Paused by Harbour & Co's owner" or "Paused by RealX for all users" without deciding anything. Engaging an engaged tier is idempotent: `200` with the existing row, never a second row.
- Every engage and release, by any source, writes one audit event (`agent_guard.switch.engaged` or `agent_guard.switch.released`), one A13 `agent.kill_switch_fired` (Sev2 for user or tenant; Sev2 for owner type through the variant requested from A13 in §1; engages only), and one `agent.kill_switch` notice per affected person (§5).

**7. HTTP surface, agent parity, errors and empty states**

- The routes live under `/v1/agent-guard/`, each with `x-realx-scope` in M25 or M26, so they are in the OpenAPI document, the SDK and A104's catalogue (except the `requiresHuman` routes).
  - `anomalies`: list, filtered by token, owner, tenant, rule, state and time. The person sees their own, an SP-OWN sees the tenant's, and staff with `V` on M26 see all.
  - `anomalies/{id}`: detail with rule code and plain-English name, rule set version, evidence window with counts, first seen and state. The evidence carries activity ids and counts, never request bodies. `source` and `signal_ref` are returned only to MLRO and CCO (§3).
  - `anomalies/{id}/dismiss`: staff, for a watch anomaly, with a reason.
  - `anomalies/{id}/replay`: staff with `V` on M26. For a signal anomaly, only MLRO and CCO see the signal line; every other caller gets the ordinary burst replay shape (§2).
  - `holds`: list, place (§4). `holds/{id}/clear` (§4).
  - `notice-policy`: get and put (§5).
  - `notices`: the notice log. The person sees their own. SECO sees any, and for subjects whose A30 `restriction` is not `none` sees type, channel, sent-at and delivered only, never the body, so there is no tipping-off.
  - `switches`: list, `me`, and engage and release per tier (§6).
  - `rulesets`: list, get, `simulate`, draft.
  - `summary`: counts for the ADM-35 KPI tiles and the product-map mock: auto-suspended today, open anomalies by rule, holds open, tiers engaged.
- **Agent parity (D04).** Every action this node exposes is in the parity manifest A100 reads, and every delegability value comes from A03's `delegable.ts`, not from this module.
  - Delegable under the same gates: reading the notice policy; tightening the notice policy; engaging the person's own user tier; staff reads of the anomaly queue, holds, switches, rule sets and summary; staff drafting of rule-set changes, simulations and releases as maker; staff placing a hold as maker (428 then hardware-key confirmation).
  - Non-delegable (`requiresHuman`, refused before scope evaluation with `AGNT_NOT_ALLOWED`): clearing a hold; resuming a user or tenant tier; loosening the notice policy; the person's own anomaly and notice-log reads (Specify point (e)); every `SGL+R` act, ratification, check and dismissal.
  - A token that reads an anomaly or hold about its own token or its human's tokens through a staff route is refused `self_subject`.
  - Every agent call to this module is audited "agent <token prefix> on behalf of <person>" and passes A12's G22 evaluator like any other.
- **Errors.** The error codes are stable strings in the OpenAPI document: `AGENT_HELD` (423), `GUARD_REASON_REQUIRED` (422), `GUARD_HOLD_PLACER_CANNOT_CLEAR` (403), `GUARD_HOLD_PLACED_BY_STAFF` (403), `GUARD_STAFF_HOLD_NEEDS_SECO` (403), `GUARD_HOLD_CLOSED` (409), `GUARD_RESUME_NOT_ALLOWED` (403, naming the source), `GUARD_TENANT_IS_PLATFORM` (422), `GUARD_NOTICE_BOUNDS` (422), `GUARD_NOTICE_ROW_LOCKED` (422), `GUARD_ILLEGAL_TRANSITION` (409) and `GUARD_RULESET_IMMUTABLE` (409). Codes reused from other nodes: A12's `AGENTS_PAUSED` with `tier` and `CONFIRMATION_REQUIRED`; A11's `AGNT_NOT_ALLOWED` and `FRESH_ASSERTION_*`; A14's `APR_CHECKER_MUST_BE_HUMAN`; `self_subject`; and A48's `KS_ACTOR_CANNOT_RELEASE`. Each comes with `gate: G22` (or `G13` for the maker-checker refusals) and `reason_codes`, so the A60 and A77 banners render them without parsing.
- **Empty and edge states.**
  - A person with no anomalies gets `{items: [], next_cursor: null}`, which ACC-05 shows as "No holds".
  - A person with no `notice_policy` row gets the defaults, with `version: 0` and `is_default: true`.
  - An unknown id returns 404, and another person's anomaly also returns 404, never 403, so ids cannot be probed.
  - A clear on a hold that is already closed returns `409 GUARD_HOLD_CLOSED` with the closing kind.
  - The summary on a fresh stack returns zeros, not nulls.
- **Outbox events** (ids and codes only, never PII): `agent.guard.anomaly_raised`, `agent.guard.anomaly_dismissed`, `agent.guard.hold_placed`, `agent.guard.hold_cleared`, `agent.guard.switch_engaged`, `agent.guard.switch_released`, `agent.guard.burst_detected` (for A42), `agent.guard.session_key_revoke` (for A29), and `agent.guard.ruleset_effective`. None carries `source` or `signal_ref`. Audit action codes are registered under `actions.agent-guard.ts` with labels and sensitivity: `agent_guard.anomaly.raised` (sensitive), `agent_guard.hold.placed`, `agent_guard.hold.cleared` (sensitive), `agent_guard.switch.engaged` and `agent_guard.switch.released` (sensitive), `agent_guard.switch.session_keys_revoked`, `agent_guard.notice_policy.changed`, and `agent_guard.ruleset.changed`.

"Done" for this node means every field, action, state and error those screens need for notices, anomalies, holds and tiers exists as a route or event listed above. It is checked by a contract test that A60 and A77 reuse unchanged.
- **Journeys: J20 Operator daily run.** Done when SECO's morning review can be driven at service level: the A13 queue source lists overnight holds and watch anomalies with their clock; `agent.anomaly_hold` and `agent.kill_switch_fired` appear in ADM-01's alert feed; the `summary` route gives the ADM-35 tiles; `replay-audit` has run overnight with zero mismatches (a mismatch is itself a J20 exception, owned by SECO). J22 steps 3 and 6 ("gets a push notice of the agent's purchase"; "reviews agent anomalies, suspends a token placing a burst of orders · owner notified") are delivered here at service level and on screen by A60 and A77.
- **Gates:**
  - **G13 Maker-checker** is done when:
    - staff user, tenant and owner-type tiers are `SGL+R` with ratification by a different person;
    - every release is `4E`, and the engager can be neither maker nor checker of it;
    - rule-set changes are `4E`, or `6E` when `burst` is loosened;
    - a hold is never cleared by its placer, by its owner when the owner is staff, or by any agent;
    - SoD counts every agent as its human throughout.
  - **G14 AML monitoring** is done when the burst rule emits `agent.guard.burst_detected` for A42 and turns `aml.agent_burst` into a hold that is byte-identical, as the person and every non-need-to-know staff reader (list, detail and replay) see it, to an ordinary burst hold, and merges a signal that overlaps an existing burst anomaly (open or cleared) without a second hold or notice. An account frozen or under AML review is A12's neutral `account_under_review` hold; this node adds nothing to it. No column, response, outbox event, notice or log line outside the need-to-know `source` and `signal_ref` names AML.
  - **G22 Agent authority** is done when:
    - anomaly holds and user, tenant and owner-type tiers are enforced by A12's middleware within one request, and every hold and tier revokes the covered wallet session keys (off-chain at once, on-chain within `SESSION_KEY_REVOKE_SLA`);
    - every refusal names the hold or the tier;
    - notices reach the person on every listed action and never the agent;
    - the eight hidden-oracle invariants below pass.
- **Modules:**
  - **M20 AML cases** is done when the agent-burst signal flows both ways between this node and A42 without tipping off.
  - **M25 Access, approvals and audit** is done when every hold, clear, engage, release, dismissal, policy change and rule-set change is an audited M25 event with `on_behalf_of_id` where an agent acted. The A14 action codes named above exist with their policy rows, and a staff agent is never a checker, ratifier or releaser.
  - **M26 Integrations and API** is done when these match the product-map ADM-35 rows: "Unusual agent activity (new IP, burst of orders, scope probing) raises a security alert and can suspend the token automatically"; "Kill switch: suspend agent access for one user type or everyone" (with Specify point (d)); "Revoke any token · immediate; the owner is notified" (the notice half).
- **State machines:** none of the 14 owned. The anomaly transition table and the rule-set lifecycle are recorded as data in A03's format, and their forbidden transitions are tested.
- **Founder requirement D04:** done when anomaly detection, notices to the person on sensitive agent actions, and kill switches per token, per user, per tenant and platform-wide exist for every user type in the fixtures. That means seven investor sub-types, the sponsor and tenant-partner roles, the four platform partner types and a representative staff set. Every action in this module is callable through the API and MCP under the same rules, except the acts that must be the person's.

  - the seed rule set `AG-2026.1`.

  The node QA records `specVersion`, those hashes, `oracleVersion` and `hiddenCasesHash` in the evidence manifest. The Specify points:
  - (a) The user tier by the person is engaged with the session and resumed with a passkey. This resolves A60's point (c); the summary said "with a passkey".
  - (b) Staff user and tenant tiers are `SGL+R`, while a staff token hold is immediate with a reason. This resolves A77's point (b).
  - (c) A new country holds; a new IP in a known country only notifies. The seed relabels the product-map "New country IP · watch" row as "New IP · watch" and adds a held "New country IP" row.
  - (d) Add the owner-type tier from the product map's "one user type or everyone", on the `owner_type` scope A12 already defines, with the A13 Sev2 variant and A48 text correction requested in §1. If this is declined, the row is covered by the platform tier only and recorded as a gap, and the following are removed from this node: the `owner_type` provider, the owner-type engage and release routes, the owner-type rows of the §6 tier table and of the tier matrix, the A14 codes `agent_guard.type_tier.engage` (and the owner-type use of `agent_guard.tier.release`), and the A13 variant request.
  - (e) A person's own anomaly and notice-log reads are non-delegable, and A43.1 hides agent notices from token reads, so an agent cannot learn what the guard saw. If this is declined, record why in `A101.qa.md`.
  - (f) A hold and every tier (user, tenant, owner type, and the platform tier through the fan-out) revoke the covered wallet session keys: off-chain at once through A29's `introspect` check, and on chain through A29's revoke consumer after commit (`agent.guard.session_key_revoke`). A release or clear never restores them; the person registers a new session key with a passkey. The alternative is an off-chain-only block, which a direct UserOp through a third-party bundler on testnet would bypass. The window between commit and on-chain confirmation (at most `SESSION_KEY_REVOKE_SLA`) is accepted and recorded for HG-PENTEST.
- **Oracle.** The node QA writes hidden Vitest and fast-check tests to `<workspace>\gauntlet\hidden\A101\` covering at least these invariants:
  1. An anomaly hold stops the next call. On the inline path the crossing call itself is refused. On the event path, the first call after the hold commits is refused on both API processes. No call slips through in 50 runs each.
  2. A per-tenant switch stops only that tenant. This is a full tier matrix: every tier engaged against a fixture of every owner type, prefix, environment and tenant, with the refused set equal to the table in §6 cell for cell. The same matrix covers the user and owner-type tiers. For every tier, including the platform tier and a token hold, every covered session key with a wallet cell is refused off-chain on the next op and ends `revoked` with a tx hash within `SESSION_KEY_REVOKE_SLA`, and no key outside the tier is touched.
  3. Every listed action writes exactly one notice to the human, and none reaches the agent's channel. Zero A43 notification bodies of the ten agent notice types, and zero `agent.guard.*` events, reach the webhook receiver, the MCP resource stream, the agent's response bodies or any request-supplied address. (Other `agent.*` events that A46 legitimately offers, such as A12's token events to staff subscribers and `agent.confirmation.*`, are allowed and are not notices.)
  4. Clearing a hold needs a passkey or a staff reason. It is refused for every token, for a stale, reused or mismatched assertion, for a staff clear without a reason or without a hardware key, for the placer, and for a staff owner.
  5. Rules replay. A property test over at least 10,000 random activity sequences, including concurrent sequences whose activity ids are assigned out of commit order, shows `replay()` over `counted_activity_ids` gives identical `fired`, `severity` and `evidence_sha256`, and re-running the baseline job over the same hour finds a byte-identical row and never overwrites it. Replay still succeeds after `agent_token_ip_seen` rows have aged out.
  6. Release and resume only by the right human. The source rules of §6 hold for every engager and releaser pair across the five tiers of A00's `agent-access.json` (token hold, user, tenant, owner type, platform), exactly as A00's by-engager lift rule states them: a staff-engaged or guard-engaged user or tenant tier, the owner-type tier and the platform tier are released only 4E by two different humans, neither of them the engager; a person-engaged user tier only by that person with a fresh passkey assertion (`source = person`); an SP-OWN-engaged tenant tier only by an SP-OWN with a fresh passkey assertion; a token hold only by its owner with a fresh passkey or by a SECO who did not place it, with a hardware key and a reason. No agent principal releases, clears or resumes any tier, and no lapse ever lifts a switch.
  7. A hold from A42's signal is indistinguishable, as the person sees it, from an ordinary burst hold: the response bodies, the notice and ACC-05's rows are byte-equal after id substitution. The same holds for staff outside need-to-know: the anomaly list, detail and replay responses seen by SECO and by SUPP for the signal persona and the ordinary persona are byte-equal after id substitution, and only MLRO and CCO see `source` and `signal_ref`.
  8. An agent can never quieten its own oversight. Every loosening of the notice policy and every clear, resume, dismissal, ratification or release by a token is refused before scope evaluation.

  Plus these cases:
  - concurrent calls across a burst threshold admit at most the threshold;
  - ten handler gate refusals in a row (G01 to G21, recorded as `failed_after_gate`), then an otherwise-allowed call: the call gets `423 AGENT_HELD`, and the hold exists although every business transaction rolled back;
  - pre-scope refusals (`requiresHuman`, `APR_CHECKER_MUST_BE_HUMAN`, `self_subject`) count towards `authority_probe` and `refusal_streak`; `TOKEN_INVALID` is not counted; `TOKEN_REVOKED`, `TOKEN_EXPIRED`, `AGENT_HELD` and `AGENTS_PAUSED` refusals never raise a hold;
  - `dormant_owner`: reads before the first write succeed, and after the write trips the rule every call, reads included, gets `423 AGENT_HELD`;
  - an `aml.agent_burst` signal that arrives after the person has cleared the hold for the same burst is merged into the cleared anomaly: no new hold, no new notice, `signal_ref` set;
  - an account frozen or under AML review (A30's `investor.suspended`) creates no anomaly, no `agent_hold` row and no notice in this module; an `agent_guard` hold stacked with A12's `account_under_review` hold, in both orders, leaves the token held until both are released;
  - off-hours buckets are correct across both daylight-saving changes in Australia/Sydney;
  - `near_cap_repeat` at exactly 90 percent and at one cent below it;
  - dormancy at day 89 and day 90;
  - a joint account where one holder pauses;
  - tenant suspension followed by reinstatement leaves the tier engaged;
  - the platform fan-out sends one notice per person, not one per token.

## Node-specific challenges (node QA)

- **The agent that clears its own hold (security, agent misuse).** T3 trips `burst`. Using its own bearer token, then a sibling token of the same person, then an MCP session, it calls `holds/{id}/clear`. It also rotates T3 through A12 (rotation needs only a session, so it must not lift a hold), creates a new token (non-delegable), loosens the notice policy to switch off `agent.anomaly_hold`, and calls A43's `read` on the hold notice. Expected: `AGNT_NOT_ALLOWED` before any scope check; the rotated T3 still `suspended` with `AGENT_HELD`; `AGNT_NOT_ALLOWED` on the token and policy calls; `COMMS_AGENT_CANNOT_ACK_NOTICE`; and the notice still unread in the person's inbox. Any 2xx fails the node.
- **Tier over-reach and under-reach (security).** Harbour & Co's SP-OWN pauses the tenant. Expected: HCO's SP-FIN live token and SP-PM sandbox token are refused with `tier: tenant`. Alex Morgan, who holds HCO's trusts through `rx_inv_`, keeps working. The trustee's `rx_ptr_` token on an HCO vehicle keeps working. NLC's tokens keep working. A staff SECO token keeps working. Then SECO engages the user tier for Alex: Alex's three tokens (live and sandbox) stop, and his joint co-holder's token does not. Then CCO tries to engage the tenant tier on the platform tenant: `GUARD_TENANT_IS_PLATFORM`. The first call after every engage is refused and the first after every release succeeds, on both processes.
- **The race at the threshold (money).** Twenty-five order calls from one token arrive within 50 ms against a `burst` floor of 20 writes in 120 s, each for A$900 against a per-action cap of A$1,000, so each is also `near_cap_repeat` material. Expected: at most 20 orders exist. The 21st call is refused `AGENT_HELD`, and its committed refusal transaction also writes the hold; the handler never ran. No order row, escrow reservation or `mandate_usage` reservation exists for any refused call. Exactly one anomaly (with both rules attached to one hold) and one `agent.anomaly_hold` notice exist.
- **Tipping-off through the guard (compliance, G14).** A42 emits `aml.agent_burst` for A06's AML subject while an ordinary persona trips the same rule by itself. The node QA diffs the two people's `AGENT_HELD` refusals, ACC-05 anomaly reads, notices (subject, text, channels, timing), A77's ADM-35 row as seen by SUPP, the anomaly list, detail and replay responses as seen by SECO and by SUPP, and the `summary` counts. Any byte that differs after id substitution, or any AML term, `source` value or signal event id visible to SECO or SUPP, fails the node; MLRO and CCO must see both. Clearing the AML-origin hold by passkey must leave A42's alert untouched. Then A42 emits a second `aml.agent_burst` for the ordinary persona's already-cleared burst: no new hold and no new notice may result.
- **Notice to the wrong place (security).** The agent registers a webhook for `agent.guard.*` (refused: not webhook-eligible), subscribes to MCP resources for notices (not listed), and places an order with a body field `notify_email: attacker@example.com`. Expected: the notice arrives only at the person's verified email and SMS in A43's sandbox inbox. The webhook receiver, the MCP stream and the attacker's address receive nothing.
- **Replay after a rule change (compliance).** A rule set `AG-2026.2` raises the burst floor under `6E` (SECO, CCO, MLRO). The node QA replays every anomaly raised under `AG-2026.1` and every one raised under `.2`. Each must replay under its own recorded version with identical results. A staff agent tries to be the CCO checker (`APR_CHECKER_MUST_BE_HUMAN`, plus an `authority_probe` hold on the staff token), and a simulation is attached with a hash that does not match the request (refused).
- **Wallet side door (money, security).** Alex's mandate includes a wallet cell with a registered session key. The node QA runs the same probe four times, once for each stop: his token is held; SECO engages the user tier for Alex; CCO engages the owner-type tier `investor`; A48 engages the platform tier. Each time, the node QA submits a session-key UserOp through A29's route at once, and then, after A29 has recorded the revoke's tx hash, directly to the local chain's EntryPoint through a second bundler. Both must fail every time: A29 refuses off-chain from the first op, and A26's SessionKeyModule rejects on chain because the key was revoked. The node QA records the time from commit to on-chain revoke against `SESSION_KEY_REVOKE_SLA`. After each clear or release, the old key must still be refused until Alex registers a new one with his passkey.
- **Design fidelity of the data contract.** With the standard seed:
  - `GET /v1/agent-guard/notice-policy` for Alex must return all ten rows of §5, including A50's five CheckList rows with A50's labels, defaults and locks;
  - `GET /v1/agent-guard/anomalies` for SECO must produce the product-map mock rows (subject to Specify point (c)), and `summary` must give "3" auto-suspended;
  - `switches/me` for an HCO member must return `tier: tenant` with the SP-OWN source so that A60's banner reads "Paused by Harbour & Co's owner".

  Any status string outside `open | held | cleared | dismissed` fails, as does any bare 4xx, or any field the A60 or A77 contract tests need that is missing.

## Pass criteria
