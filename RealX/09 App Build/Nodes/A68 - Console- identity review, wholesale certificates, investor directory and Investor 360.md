# A68 - Console: identity review, wholesale certificates, investor directory and Investor 360

**The four investor screens of the operator console, built from A30's, A32's and A44's read and decision contracts and nothing else. ADM-10 Identity review is a queue showing the provider decision, risk and SLA, plus a case review page: document tiles and liveness score, extracted vs entered fields (values masked until a reason is given), screening hits with false positive / true match / need info, risk factors, and the four decisions (approve, reject, request info, escalate to EDD), each with a mandatory reason code. Clearing a PEP hit becomes a `4E` request with the MLRO as checker, replacing the design's one click. ADM-11 Wholesale certificates is a queue with the Queue / Expiring 60 d / Expiring 30 d / Expired filters, an evidence viewer, the accountant check and hardware-key decisions. ADM-38 Investor directory filters on the server. ADM-09 Investor 360 has thirteen tabs, masked fields, reason-coded unmask, a tokens-and-mandates tab, and the header actions (suspend, reinstate, residency change, estate, revoke on-chain eligibility) run through the shell's maker-checker flow. Every action on these screens has an API and MCP equivalent under the same rules. A staff agent may only prepare; a human decides.**

## Build brief

This node is UI-only: the `(investors)` route group of `apps/console` and the `features/investors` package of components, hooks and label tables. It calls the API only through `packages/sdk` (no `fetch` outside the SDK; A53's lint). It creates approval requests, signs decisions and renders tables only through A53's `PrivilegedActionFlow`, `HardwareKeyConfirm`, `ConsoleTable`, `ConsolePage`, `MaskedCell` and `AgentMarker`. It owns no API route, table, job or rule. Which options a person has, whether a hit blocks approval, whether a person may unmask a field, what support may see and who is the checker are all decided by the API. The screen renders the answer and adds no rule of its own, with one named exception: the `approveGuard` defensive guard in `case-review/` (§3), which can only disable Approve, never enable anything, and logs every disagreement with the API. Every control on these screens is driven by an API field listed in spec point (h): the ADM-09 header's `actions[]`, the ADM-11 review's `options[]`, and the ADM-10 review's `options[]` and per-hit `dispositions[]`. Where a frozen contract lacks such a field, the builder stops and escalates; it never invents a client-side role rule. Because the same routes serve a staff member's agent through A12's tokens and A104's MCP server, the node adds nothing an agent could not also call, and it publishes the mapping that proves it (`parity.json`, below).

**1. Routes, screen codes and shell wiring**

- Route group `app/(investors)/` (the group adds no URL segment; the console is on its own origin, so the product map's `/admin` prefix is dropped): `/investors` (ADM-38 directory), `/investors/[investorId]` and `/investors/[investorId]/[tab]` (ADM-09, `tab` in the thirteen keys below, default `profile`), `/onboarding/cases` (ADM-10 queue), `/onboarding/cases/[caseId]` (ADM-10 case review; the product map's `/admin/onboarding/cases/:id`), `/onboarding/wholesale` (ADM-11 queue) and `/onboarding/wholesale/[reviewId]` (ADM-11 review). Each page exports `screen` (`ADM-38`, `ADM-09`, `ADM-10`, `ADM-11` from A02's `screens.ts`) and `designKey` (`ext:ADM-38`, `ext:ADM-09`, `adKyc`, `ext:ADM-11`). A route-collision test runs over A53's route registry, because A53 reserves an `(onboarding)` group name for later nodes and this node uses the `/onboarding/...` URL inside `(investors)`. A clash is a follow-up request to A53, never a rename done here.
- A53's `nav.ts` already lists Identity review, Investor directory, Investor 360 and Wholesale certificates in the "Onboarding & listings" group with these routes, so this node's pages replace the `soon` placeholders without editing the shell. Investor 360 is reached from the directory, from search or from a deep link. Opened from the sidebar with no id, it shows the directory's search box and the empty state "Open an investor from the directory or search by INV- id".
- Badge sources, registered from `features/investors/register.ts` through `registerBadgeSource`. `identity.review` reads the open count of the `identity_check_24h` queue from A13's `GET /v1/alerts/summary` `queues` block. `wholesale.queue` reads `counts.queue` from A32's `GET /v1/classification/reviews?filter=queue&limit=1`. Neither count is taken from the length of a list page (A53's rule and design bug §6.4-8). An empty queue shows no badge, which is the design's "badge clears after the decision".
- Search providers through `registerSearchProvider`. `INV-` ids open ADM-09. `KYC-` case ids open the ADM-10 review. `CLS-` classification ids open ADM-11 filtered to that investor. Free-text search is by id only in this build. A lookup by exact email through A30's blind index is a follow-up request to A30, and it must be a request-body endpoint, because A53 forbids a name or email in any URL or query string. The palette never sends a name to the API.
- A13's alert `investor.certificate_expiring` (the `adCmd` row "14 wholesale certificates expire within 30 days") has `target_screen = ADM-11`. A32 fires it as two batches. This node registers `/onboarding/wholesale?filter=expiring_30` as the target of the T-30 batch and `?filter=expiring_60` as the target of the T-60 batch, which supersedes the design's link to `adKyc` (A32's note).
- Cross-screen links to screens other nodes own (ADM-15 recovery desk, A72; ADM-35 Agent and API access, A77; ADM-25 AML cases; ADM-27 tickets) are built only from A53's route registry and `nav.ts` entries, never from a hard-coded path. A72 and A77 are in the same milestone and are not dependencies, so a target not yet built resolves to the shell's `soon` placeholder. A component test asserts that each of these links, with its target unregistered, lands on the placeholder and not on a 404 or a broken route.

**2. ADM-10 Identity review: the queue (`/onboarding/cases`)**

- `ConsoleTable` over A30's `GET /v1/kyc/queue` with the product map's columns. **Case** is an `IdCell` with `KYC-…` and the subject's `INV-…` below it. **Subject** is a `MaskedCell` showing a masked name such as "Daniel O.". **Type** is person or entity, with "SMSF", "company" or "trust" for entities. **Provider decision** (`pass`, `refer`, `fail`, `fraud`) uses the TONE map: pass green, refer amber, fail red, fraud red. **Risk** shows the rating pill and mono points ("high · 62"). **SLA** shows the remaining time from the A13 clock ("5h", amber under 4 h, red and "breached" past 24 h). **Age** and **Assignee** are shown read-only; A30 exposes no assign route, so the node shows none. FilterChips for state, risk, provider decision, SLA (`breached`, `due_soon`) and type are URL and API parameters. Rows are in the API's order (SLA due first).
- Page header from the design's PG pattern: eyebrow `ADM-10`, h1 "Identity review", subtitle "{n} cases referred · oldest {age}" from the queue's first page and A13's count, never a computed total. The empty state is the dashed box "Queue clear. Every referred case has a decision." (A53's EmptyState). A case that leaves the queue while the page is open disappears on the next 30-second refresh. If a person opens it by URL, it shows its terminal state and never a 404 (A30's contract).
- An agent-drafted decision on a case shows in the row as an amber `draft` pill with `AgentMarker` ("agent rx_stf_… on behalf of Priya N."). The draft is not a decision. The row stays in the queue until its human confirms.

**3. ADM-10 Identity review: the case (`/onboarding/cases/[caseId]`, design `adKyc`)**

- Data comes from one read, A30's `GET /v1/kyc/cases/{id}/review`, plus A31's eligibility row for approved cases (`GET /identities/:investorId`). The page header's subtitle keeps the design's sentence: "Case {KYC id} · {INV id} · referred by {provider label} at {hh:mm}". The design used the investor id as the case id; both ids are shown, and the seed maps "Case INV-00912" as A30 specifies.
- Left column, in the `adKyc` layout (`minmax(0,1fr) minmax(0,1.2fr)`, gap 20). There are two document tiles (aspect ratio 1.58, radius 10, the striped placeholder until the image loads, Geist Mono 10 px caption such as "NSW licence · front" or "liveness selfie"). Each image loads from the presigned A08 link in the review response into an `<img>` with `referrerpolicy="no-referrer"`. The link is never stored, never put in a URL the console owns and never offered as a download. A slice without document access (A44's `support` and `ir`) gets no link, and the tile shows "Not available in your view". Below the tiles is the subject card: masked name in Newsreader 22, then "{INV id} · {type} · {classification summary} · {suburb state}". The classification summary comes from A32 (`classificationFor`) through the review response, for example "wholesale certificate uploaded".
- Right column, a white card with radius 14. First, the **checks list**: six rows exactly as `kycChecks`: Document check, Name and date of birth, Address, Liveness ("Score 0.98" from `liveness_score` 9800 bp), Sanctions (G02), PEP screen (G02). Each row has a detail string and a pill (`Pass` green, `Refer` amber, `Clear` green, `Review` red), all taken from the review response. The node keeps a label table from A30's check codes to the design's titles and does not compute a pill. Second, the **Extracted vs entered** table (product map): Field / Document / Applicant / Match. The match column (`exact` ✓, `order` "~ order", `mismatch` red ✕) shows at once. The Document and Applicant values show masked (`•••`) until the viewer holds an unmask grant for the `identity_documents` field group (§6). **Unmask on ADM-10.** The Extracted vs entered card and the subject card each carry an **Unmask (reason)** control (outline soft). It reuses the §6 unmask component unchanged: the same reason-code OptionCard list from the frozen enum, the same field-group picker (groups the API marks not permitted shown disabled with `UNMASK_FIELD_NOT_PERMITTED`'s sentence), the same `POST /v1/investors/{id}/unmask` call for the case's subject, and the same in-memory grant rules (React state only, never storage, a URL or a cookie; countdown line; re-mask at expiry, on navigation away, on sign-out and on `UNMASK_GRANT_INVALID`; no copy button; masked in print). With a live grant the page re-reads `GET /v1/kyc/cases/{id}/review` on the client only, with `X-Unmask-Grant` sent by the SDK; the review is never re-read in a server component with a grant. A30 honouring `X-Unmask-Grant` on the review route is part of spec points (d) and (h); A44 defines the header only for Investor 360 tab reads today. Third, **Screening hits**: one card per `screening_hit` with list code, matched name (masked), confidence ("0.71"), `dob_match` ("different DOB"), disposition, and for a disposition in flight the `APR-…` id and its SM-00 state. Fourth, **Risk factors**: each factor with its points and the total against the thresholds A30 returns. Fifth, when present: the SoD note ("You are related to this subject, so you cannot decide this case", A30's `KYC_SOD_OWN_CASE` wording), and for an approved case A31's row "On-chain eligibility · registerIdentity + claims · Queued / Registered" with the V4 op reference.
- **Hit actions** on each open hit: **False positive**, **True match** and **Need info**, rendered from the hit's `dispositions[]` in the review response (spec point (h)): a disposition not listed is not rendered, and one listed as blocked renders disabled with its code. Every hit action opens a disposition panel with a **mandatory reason code** from A30's catalogue (the panel will not submit without one; a returned `KYC_REASON_REQUIRED` is still rendered). **Need info** also takes one or more coded RFI items (`UTILITY_BILL`, `SECOND_DOCUMENT`, `SOURCE_OF_FUNDS`, …) and shows the same consequence line as the case-level Request info below: "expires after 30 days if no reply" before submit and the returned `rfi_expires_at` date after; the case then shows `rfi_pending` as A30 returns it. They call A30's `POST /v1/kyc/cases/{id}/hits/{hitId}` with `disposition`, `reason_code` and, for need info, the RFI items. For a PEP, adverse-media or DFAT false positive, A30 creates the `4E` request (`kyc.screening.clear_hit`: KYCA maker, MLRO checker; MLRO only for DFAT) and returns its `approval_id`. The page then hands that id to A53's `PrivilegedActionFlow` in follow mode, which shows the submitted state, checkers and SM-00 status card, and the hit card reads "Sent to MLRO for approval · APR-…" in the design's DecisionBanner style (amber tint while pending, green once approved). A DFAT **True match** is the silent freeze, `kyc.sanctions.confirm_match` (SGL+R: MLRO acts, CCO ratifies within 2 h). It is offered only when the hit's `dispositions[]` lists `confirm_match` for the caller (A30 lists it for the MLRO only), and it goes through `HardwareKeyConfirm`. The confirmation copy states that the investor sees no change and that an AML case opens. Afterwards the case shows, for MLRO and CCO only, "Restricted · AML case opened" as the API returns it. A PEP true match shows "Confirmed PEP · enhanced due diligence required", and Approve moves behind EDD.
- **Decision bar.** The four verbs come from the review response's `options[]` for this caller, each `{verb, enabled, blocked_code}` (spec point (h)): Approve (green primary), Request info (outline ink), Escalate to EDD (outline ink; the design's "Escalate to MLRO"), Reject (danger `#A3312A` outline). An option the API does not list is not rendered. An option listed with `enabled: false` renders disabled, with its `blocked_code` as the caption: `KYC_OPEN_HIT` "Clear every screening hit first", `KYC_EDD_REQUIRED` "Enhanced due diligence required", `KYC_SOD_OWN_CASE`. **Defensive guard (the one client-side rule, chosen and named).** `case-review/approveGuard.ts` disables Approve whenever the review response itself shows any hit with disposition `open`, any KYB person not `verified`, or the EDD flag set (the field A30 names under spec point (h)), even if `options[]` lists Approve as enabled. It never enables a control and never hides one; the disabled caption is the matching code (`KYC_OPEN_HIT`, `KYB_OWNERS_PENDING`, `KYC_EDD_REQUIRED`). When it overrides `options[]` it logs a client error event `investors.options_mismatch` with the case id and `request_id` (no PII), because the mismatch is an A30 defect. For a response that satisfies A30's schema invariants the guard never fires, and the rendered bar equals `options[]` exactly. Every verb opens a decision panel that needs a reason code from A30's catalogue (the panel will not submit without one; the server's `KYC_REASON_REQUIRED` is still rendered if it comes back). There is an optional note (500 characters, with a counter; the text is sent as typed and never echoed into the page title or a toast). Request info needs one or more coded items (`UTILITY_BILL`, `SECOND_DOCUMENT`, `SOURCE_OF_FUNDS`, `DEED`, …). The panel shows what will follow. Before submit it reads "Investor is asked for: utility bill · expires after 30 days if no reply", where "30 days" comes from the `request_info` option's RFI policy duration (`rfi_policy_days = 30`, calendar days, A13's `kyc_rfi_30d` clock; spec point (h)). After submit it reads "Investor asked for: utility bill · expires on {date} if no reply", where the date is the decision response's `rfi_expires_at` from A13's clock. The browser never computes the date, and a policy name such as `rfi_30d` alone never satisfies this line; if either field is missing the builder escalates to A30. It posts `POST /v1/kyc/cases/{id}/decide`.
- **Where A30 creates an A14 request for a decision, the page follows it:** approve after a provider `fail` (`kyc.case.approve_override`, `4E`, MLRO checker), approve from `edd_review` (`kyc.case.approve_edd`, `6E`, MLRO plus a CCO or CEO). The route's `approval_id` goes into `PrivilegedActionFlow` in follow mode, with the ApprovalsChain block (A51) showing each checker as DONE, YOUR TURN or WAITING. The case state changes on screen only when the API reports it. The design's DecisionBanner "Decision recorded: {verb}" appears only after a 2xx that carries the case's new state, with the toast "Case {KYC id}: {verb}". A `202` with an approval id reads "Sent for approval · APR-…" and never "recorded".
- **Fresh assertion (spec point (a)).** A30's decision route does not state that a human decision needs a fresh hardware-key assertion, while A32's classification decisions do. The proposed reading, recorded for A30's owner, is that approve and reject on a case need one (purpose `kyc_decision`, challenge = the case's canonical hash). If A30 adopts it, the panel submits through `HardwareKeyConfirm`. If not, the panel posts directly after the reason code, and the gap is noted in `A68.qa.md`. The node does not require an assertion the API does not ask for.
- **Entity cases (J03, G03).** For `subject_type = entity` the page adds the KYB block from A30's `GET /v1/kyb/entities/{id}`. It shows: ABN/ACN (masked), registry status, the deed as a DocumentRow, and a people CheckList (trustee, director, signatory, owner with basis points as "50.00 %") with each person's pill (`verified` green, `verifying` amber, `invited` grey, `failed` red), each linking to that person's own case. While any person is not `verified`, Approve renders disabled with the caption "{n} people still verifying (G03)", with the count taken from the API's `KYB_OWNERS_PENDING` detail. The console never computes the count itself; `approveGuard` only checks whether any listed person is unverified, to decide disabled or not.
- **Staff agent drafts (D04).** When the review response carries a pending agent draft (A30's `drafted_by_agent = true`, `state = pending_confirmation`, with A12's `confirmation_id`), the decision bar is replaced by a draft card for the draft's own human: "Drafted by your agent {agent name} · {verb} · {reason code} · expires {time}", with **Confirm with your key** (`HardwareKeyConfirm`, purpose `agent_confirmation`, then `POST /v1/agent-access/confirmations/{id}/confirm`) and **Discard** (`/cancel`). Any other viewer sees the same card read-only, with `AgentMarker` and no buttons. An agent can never appear as a checker in the follow-mode chain (A14 refuses it), and the chain renders A14's `APR_CHECKER_MUST_BE_HUMAN` verbatim if a fixture tries.
- **Other ADM-10 actions** (product map). "Revoke on-chain eligibility" (MLRO or CCO, `4E`) calls A31's `POST /identities/:investorId/delete`, then shows follow mode. A precheck refusal such as `CLM_BALANCE_NOT_ZERO` names the token and says "Freeze or recover first; eligibility is never revoked while units are held". "Grant on-chain eligibility" is `AUTO` (SVCA) and is shown only as A31's status row. There is no button for it.

**4. ADM-11 Wholesale certificates (`/onboarding/wholesale`, drawn by A51)**

- `ConsoleTable` over A32's `GET /v1/classification/reviews?filter=&basis=&assigned=`. Columns: Investor (masked, INV id), Test (accountant's certificate, A$500k in this offer, sophisticated, professional), Evidence (document count), Accountant (name and body number, masked where A32 masks it) with verification pill (`verified` green, `unverified` grey, `not_verifiable` amber), Cert date, Expiry ("per offer" for the ticket basis), State.

The SM-02 table covers all 9 states with a label and a tone: `requested` "requested" grey; `evidence_submitted` "evidence submitted" grey; `under_review` "reviewing" amber; `rfi` "info requested" amber; `valid` "valid" green (on the ticket basis "approved · per offer" green, the product-map Harbour SMSF row); `expiring` "expiring · {days_left} d" amber, with `days_left` from the API; `expired` "expired" grey, detail "can hold and sell, cannot buy"; `rejected` "rejected" red; `revoked` "revoked" red. The review-flag table covers the flags that sit beside a state and are not states: `awaiting_cco` "awaiting CCO" amber (ticket-path approval pending A14) and `referral_cco` "refer CCO" brick (accountant not verifiable or a sophisticated-investor basis). A row shows its state pill and, when present, its flag pill. A state or flag the API returns that is missing from either table fails a generated test over A03's SM-02 table. The seed reproduces the product-map rows exactly: A. Nguyen / Certificate / Chan & Partners / 12 Mar 26 / 12 Mar 28 / reviewing; Harbour SMSF / $500k+ in offer / – / – / per offer / approved; J. Patel / Certificate / Example CPA / 02 Feb 24 / 02 Feb 26 / expired; R. Singh / Sophisticated / – / – / – / refer CCO.
- Review page (`/onboarding/wholesale/[reviewId]`) from `GET /v1/classification/reviews/{id}`. The **evidence viewer** reuses the KycReview document tiles, with the certificate first as a PDF DocumentRow opened through its presigned link, then the declaration record (who declared and when, the declaration id), the accountant fields, `certificate_date` and the `valid_until` the API computed (the page never adds two years itself), the SoD note, and for the ticket basis the linked `approval_id` with its state. **Run accountant check** calls `POST /v1/classification/reviews/{id}/accountant-check` and shows the result. `not_verifiable` shows the amber banner "Accountant not verifiable · referred to CCO" and the review reassigned to CCO, as A32 returns it. **On-chain claim row.** Once a review is approved, the page shows a read-only status row "On-chain wholesale claim · {claim_state}" from A32's `claim_state` (`pending` "pending identity", `issued` "issued · expires {valid_until}", `replacing`, `expired`, `revoked`), with the claim id linking to A31's claim row where the viewer may see it (J02 step 8). There is no control on it; the claim is issued by A31, not by this screen.
- Decisions: **Approve**, **Request info** (reason code, and the investor-facing sentence from the reason code's plain-English text as a preview), **Reject** (reason code), **Revoke** and **Run accountant check**, each rendered from the review response's `options[]` as `{verb, enabled, blocked_code}` (verbs `approve`, `request_info`, `reject`, `revoke`, `accountant_check`; spec point (h)) and absent when not listed. The decision verbs go through `HardwareKeyConfirm` with purpose `classification_decision` over the review's canonical hash, because A32 requires a fresh assertion (`CLS_DECIDER_MUST_BE_HUMAN` and `FRESH_ASSERTION_*` render verbatim). On the ticket basis, Approve returns A14's `classification.ticket.approve` request (`4E`, CCO checker). The page shows "Awaiting CCO · APR-…" in follow mode, and the row stays `awaiting_cco` until the effector runs. A CCO opening the same review sees their own approve slot in the ApprovalsChain. **Revoke** (misrepresentation) is offered to CLSR, KYCA, MLRO or CCO on a `valid` or `expiring` row, only as `options[]` lists it (A32 refuses any token or agent with `CLS_DECIDER_MUST_BE_HUMAN`; it goes through `HardwareKeyConfirm` when A32's frozen revoke route asks for a fresh assertion, and the node never adds one the API does not ask for). It calls `POST /v1/classification/{id}/revoke` and follows the resulting `classification.revoke` request. Revoking from `expiring` is refused until A32's spec gap (i) is settled, and the refusal `SM02_ILLEGAL_TRANSITION` is rendered, not hidden. The panel states what happens next: "Buying blocked; holdings and selling unaffected" (A32's `rights`).
- Expiring and expired rows are read-only here: expiry is `AUTO` by A32's sweep, and there is no "expire now" button. A periodic review opened by A32's job appears in the Queue with the kind label "periodic · risk tier high".

**5. ADM-38 Investor directory (`/investors`, drawn by A51)**

- `ConsoleTable` over A30's `GET /v1/investors?filter=`. **8. Cross-cutting behaviour**

- Formatting: dates in en-AU ("12 Mar 2028", "08:14 AEST" or "08:14 AEDT") from the API's ISO instants in Australia/Sydney. The zone suffix is derived from the instant itself in `Australia/Sydney` (AEDT from the first Sunday in October to the first Sunday in April, AEST otherwise), never hard-coded; the formatter has fixtures one minute before and one minute after each daylight-saving change instant (4 Oct 2026 and 4 Apr 2027), each asserting the suffix; scores and percentages from basis points with the API's twin where one exists; no arithmetic on dates or points in `features/investors` (lint: no `Date` arithmetic helpers, no `+ 2` years, no `/ 100` on `_bp` fields outside the one formatter).
- Loading shows A53's skeletons. An error shows the envelope's code, message and `request_id` with retry. A 403 is the shell's forbidden state and a 404 is the shell's not-found state (a sponsor-tenant or out-of-slice investor is a 404, with no existence leak). A 409 `KYC_CASE_CLOSED` or `CLS_REVIEW_NOT_OPEN` (someone else decided first) shows "Already decided · {state}" and reloads the review rather than retrying. Every code listed in A30 §9 and A32's error list that these screens can receive has a sentence in `features/investors/errors.ts`; a generated test iterates the OpenAPI error catalogue of the two modules.
- Reads are `cache: 'no-store'` everywhere: a restriction, a decision or an expiry must show on the next load.
- Tipping-off applied to the DOM. The rule is defined by what is protected and from whom, not by banned words.
  - **Protected facts:** that a true match exists or a `confirm_match` was requested or made; the reason for any restriction; an AML case id or an AML case count; anything about an SMR; that a freeze is in place; the MLRO's or CCO's note.
  - **Protected viewers:** SUPP, IRCM, the investor (and the investor's own agents), and sponsor users. None of them may receive a protected fact in any DOM text, attribute, network response, chip, tab list, tab count or badge count.
  - **Screening labels are not protected facts.** The ADM-10 checks list ("Sanctions (G02)", "PEP screen (G02)") and the screening-hit cards with their list codes are ordinary onboarding content and appear to the onboarding slice (KYCA) and the compliance slice (MLRO, CCO), as A44 slices them. ADM-10 is not reachable by SUPP or IRCM at all.
  - **Code rule:** the restriction components (`under_review`, `restricted`, "Account under review") have no prop through which a reason could render. A lint over `features/investors` forbids string constants naming sanctions, AML, SMR, freeze or a case trigger, with an allow-list of exactly: the ADM-10 `case-review/checks` and `case-review/hits` components (which render only when the review response is served to the onboarding or compliance slice) and the components that render only MLRO or CCO content (the restricted-case banner, the Cases tab's AML rows). A new entry on the allow-list is a spec change, not a builder choice.
- Layout at 1280 px and 1024 px (A53's widths). `adKyc`'s two columns stack below 1024 px. Tables scroll inside their card. There is no page-level horizontal scroll, and colours and fonts come only from `packages/ui` tokens (A05 lint).
