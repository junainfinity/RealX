# A18 - Unit register (legal record) and registry sandbox adapter

**The trustee's unit register as the legal record inside the system: bitemporal register entries built only from acknowledged registry instructions (issue, transfer, redeem, adjust), stored in A04's `register_*` tables; registry versions certified monthly by the vehicle's trustee; a cap table as of any date; signed extracts and logged exports; the "register first" rule that no mint can reference a holding the register does not already show; one approval id consumed once per instruction, bound to its lines; and a sandbox registry adapter that applies instructions with a configurable delay, writes its nightly extract at 01:30 Sydney time and can reject, delay, withhold, duplicate or drift on command, so reconciliation can be tested against a real break.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Register. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-16 agent-hours (build, challenge and verify loops).

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A18\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The oracle scope is: every row of the approval binding table below (wrong action code, weaker policy, unaccepted SM-00 state, mismatched object, tampered lines, replayed approval id); a unit-delta adjustment without the vehicle's trustee decision is refused; the bitemporal correction rule (as-of reads at any effective date, at the current and at an earlier record time, before and after a back-dated adjustment); the timeout path (slow ack, time out, resubmit, two acks, applied once); a trade-referenced transfer is refused in P1; a signed extract reproduces the entries as of its date exactly (CSV and JSON byte for byte); every export writes exactly one audit event; no entry exists without an acknowledged instruction; the "register first" query returns nothing for an approval id with no acknowledged issue; escrow money never appears as units; an issue is refused unless the offering is in SM-04 `finalising` with a locked allocation. This plan is not legal advice.

## Build brief

This node is API-only (module `register` in the Fastify monolith, with its worker jobs in the module's `jobs/` folder registered from its `index.ts`) plus one adapter package (`registry`). It owns no screens: SPN-08 is rendered by A64; ADM-17's register, cap-table, snapshot and extract panels by A73; POR-02's "register match" and PUB-08's register column by A47. Every rule below is enforced in the API, never only in a screen. The legal record is the trustee's or registry's register (Corporations Act s169); this module holds RealX's copy of it, built only from acknowledged instructions, and it produces both register-side inputs reconciliation (A20) needs: the internal copy and the registry's own extract, plus the comparison between them.

**Bitemporal correction rule (how every acknowledged change is written)**

- Reads use A04's `asOf(vehicle, validAt, knownAt)`: a row answers when `valid_period @> validAt` and `recorded_at <= knownAt` and (`superseded_at IS NULL` or `superseded_at > knownAt`).
- When an acknowledgement with effective time `E` changes a holder, the applier, in one transaction, takes every current row `r` of that `(vehicle_id, investor_id)` whose `valid_period` overlaps `[E, ∞)` and: sets `r.superseded_at = now` (the only update A04's trigger allows); if `lower(r.valid_period) < E`, inserts a copy of `r` (same units and lots) over `[lower(r), E)`; inserts the new values over `[max(E, lower(r)), upper(r))`, where the new values are `r`'s values with the change applied. Lot rows are copied or re-stated with their entry row. History before `E` is therefore still present in the current record time, and nothing that was known before `now` is lost in the earlier record time.
- A change that is not back-dated touches only the open-ended segment. A back-dated `adjust` (effective `E` in the past) re-states every current segment from `E` onward, each with the delta applied and each split at `E` where it straddles it. A holder whose units reach zero from `E` gets no segment for `[E, ...)`; reads return no row, which means zero units.
- Worked example the oracle must reproduce: issue 100 units effective 1 Jul; transfer 40 out effective 1 Aug; adjust +2 effective 10 Jul recorded 1 Sep. At record time now: as of 5 Jul = 100, 15 Jul = 102, 15 Aug = 62. At record time 31 Aug: 15 Jul = 100, 15 Aug = 60. At record time 20 Jul: 15 Aug = 100 (the transfer was not yet known).

**Instruction contract per kind (who calls, order against the chain, which approval binds it)**

The same approval id binds the approval request, the register instruction and (where there is one) the custody operation. For each row: the approval must carry an allowed `action_code`, its `policy_code` must be at least the minimum, its decisions must include the required checker set, its SM-00 state must be one of the accepted states when the instruction is prepared, its `object_ref` must equal the instruction's reference, its vehicle and tenant must equal the instruction's, and the instruction lines must be bound to what the checkers approved by the rule in the last column.

- `canonicalInstructionPayload(vehicle_id, kind, subkind, lines)` is exported from `index.ts` so any node drafting an approval whose payload is a register instruction (A20's propose-fix, A38's exclusion) produces the same bytes A18 hashes (A14's canonicaliser: sorted keys, integers, NFC).
- `registerLineMapper(action_code, fn)` is exported from `index.ts`; A28 and A38 register their mappers from their own paths. Until a mapper is registered for a code, instructions under that code are refused with `REG_NO_LINE_MAPPER` (fail-closed); this node's tests use in-module fake mappers.
- Consumption: `UNIQUE (approval_id, kind)`. A prepare that repeats an existing `(vehicle_id, kind, approval_id, reference)` with the same `lines_sha256` returns the existing instruction (idempotent replay, HTTP 200, the key A38 relies on). The same approval id with different lines, another reference or another vehicle is refused with `REG_APPROVAL_ALREADY_USED`. A registry-rejected instruction is terminal; a retry needs a new approval.
- Refusals: missing approval `REG_APPROVAL_REQUIRED`; action code not allowed for the kind `REG_APPROVAL_MISMATCH`; object, vehicle or tenant differs `REG_APPROVAL_MISMATCH`; SM-00 state not accepted for the row (`draft`, `submitted`, `prechecked`, `rejected`, `expired`, `cancelled`, `failed`, `reconciled`, `closed`, or a state outside the row's list) `REG_APPROVAL_NOT_APPROVED`, with the actual state in the detail; weaker policy code than the row's minimum `REG_ADJUST_REQUIRES_6E` for adjust and `REG_APPROVAL_POLICY_WEAK` otherwise; lines not bound `REG_ADJUST_APPROVAL_MISMATCH` for adjust and `REG_APPROVAL_LINES_MISMATCH` otherwise; trustee checker set required and absent `REG_ADJUST_TRUSTEE_MISSING`.
- Trustee checker set: "the vehicle's trustee checker set" means the people A98's `TRUSTEE_OF_VEHICLE` resolver returns for the vehicle's `trustee_entity_id` (on the wholesale track this can be the sponsor acting as its own trustee). A18 never names a role for this; it asks A14 whether a decision from that resolved set is on the request. Tests use a resolved checker-set fixture. The registry itself is never a checker: its part is the adapter's `certifyVersion` record and its acknowledgements.
- Trade path: while A08's `PHASE` flag for the resale board is off (all of P1), any `transfer` whose reference is a `trade_id` is refused with `REG_TRADE_PATH_DISABLED`. In P2, the instruction is accepted only when `TradeReader.getSettledTrade(trade_id)` (port defined in `index.ts`, implemented by A91, fixture until then) returns a trade in state `settled`, for this vehicle, whose lines equal the instruction lines, and no other instruction references that `trade_id` (`REG_TRADE_NOT_SETTLED`, `REG_TRADE_LINES_MISMATCH`, `REG_TRADE_ALREADY_REGISTERED`).
- Lock-up changes reach the register only through the `adjust` / `lot_attribute` row above; nothing else edits `lock_in_until`.
- Counsel question (HG-LEGAL, recorded, not a rule): whether redeem, forced-transfer and recovery instructions must precede the chain call under each trust deed. Default until counsel answers: issue is register first; burn, forced transfer, recovery and lock-up are chain first with the register instruction submitted in the same transaction that records the chain op `confirmed`, and a registry rejection after a confirmed chain call is a reconciliation break (A28 moves its op to `broken`).

**Instructions and acknowledgements (the only way entries change)**

- `POST /v1/register/vehicles/{vehicleId}/instructions` prepares an instruction. In-process callers (A28, A38, A91) use `prepareInstruction()` from `index.ts` with their service principal; the HTTP route serves REGO and REGO's agent for `adjust`. Validation before `prepared`: every `investor_id` exists and is not `closed`; units are positive whole integers (A02); the approval rules above; for `transfer` and `redeem` the source holder has enough units that are unlocked and unfrozen as of the effective date (`REG_INSUFFICIENT_UNITS`, `REG_LOT_LOCKED`, `REG_HOLDER_FROZEN`), with the lot-lock and frozen-source bypasses listed below; for `issue` / `primary` the reference is an allocation that `AllocationReader` reports as locked, whose lines equal the instruction lines, and whose offering `OfferingStateReader` reports in SM-04 state `finalising` (read from A03's enum; `closed`, `live`, `minted`, `failed` and every other state are refused with `REG_OFFERING_NOT_FINALISING`, and a `finalising` offering without a locked allocation with `REG_ALLOCATION_NOT_LOCKED`).
- Lots: transfers and redemptions consume lots oldest first unless the instruction names lots; a partial consumption splits a lot and keeps `acquired_at`, `price_cents` and `lock_in_until` from the parent (`parent_lot_id`). For issues the caller passes the offering's `lock_in_days`; when the ack is applied, this node sets `lock_in_until` = 00:00 `Australia/Sydney` on the calendar day `lock_in_days` after the Sydney date of `ack.effective_at` (A02 date math). A38 must pass `lock_in_days`, not a computed date.
- Lot-lock bypass: a lot whose `lock_in_until` is after the effective date may be moved or reduced only under `token.forced_transfer`, `token.recovery` (lock-in carries over to the new wallet unchanged), `settlement.exclude_after_issue`, `register.adjust` (`6E`), or `token.burn` when the op carries an A48 wind-down batch id. Every other instruction is refused with `REG_LOT_LOCKED`.
- Frozen source: a holder with a current `register_freeze_fact` can be the destination of an issue or transfer, but the source only under `token.forced_transfer`, `token.recovery`, `settlement.exclude_after_issue`, `register.adjust` (`6E`) or a wind-down `token.burn`; otherwise `REG_HOLDER_FROZEN`. A partial freeze blocks only the frozen units.
- `POST /v1/register/vehicles/{vehicleId}/instructions/{id}/submit` (or `submitInstruction()` in-process) sends it through the adapter's `submitInstruction` with `idempotency_key = instruction_id` (`prepared → submitted`), stores `registry_ref`, sets `sla_due_at = submitted_at + REGISTRY_ACK_SLA_HOURS` (default 24), starts A13's clock `register.instruction.sla` and writes audit `register.instruction.submitted`.
- Acknowledgements are pulled by the worker job `register.ack_poll` (every 30 s locally, adapter-configurable) or pushed to `POST /v1/internal/register/registry-ack` (the registry's SVCA service principal, HMAC signature and replay window from A08). For a vehicle whose `register_keeper = trustee` (A98), the ack comes only through `acknowledgeTrusteeInstruction(instructionId, { principal_id, assertion_id, decision, reason_code? })` exported from `index.ts` and called by A98 after the vehicle's TP-RE confirms with a fresh passkey assertion; the ack row stores both ids. Every ack is first written to `register_ack`.
- On `acked` (from `submitted` or `timed_out`), in one database transaction: apply the bitemporal rule above for each affected holder, link `source_instruction_id`, write audit `register.entry.changed` per affected holder and `register.instruction.acked`, and emit on the outbox `register.changed { vehicle_id, instruction_id, kind, subkind, approval_id, effective_at, holders[] }` for A20 (targeted reconciliation), A28 and A38 (mint may proceed; register-pending ops may close), A37 (order `settled` needs this plus token delivery) and A47 (read models). A second ack for the same `registry_ref` is recorded in `register_ack` with `outcome = duplicate_ignored`, changes nothing and returns the warning `REG_DUPLICATE_ACK_IGNORED`.
- On `rejected`: nothing changes in the register; the instruction stores the rejection code, audit `register.instruction.rejected`, event `register.instruction.rejected` so the caller (A28, A38) can refuse to proceed.
- SLA: the job `register.sla_sweep` (every minute) moves `submitted` instructions past `sla_due_at` with no ack to `timed_out`, emits `register.instruction.pending_sla` (A20 turns this into R17 `pending_ack` and halts resale for the vehicle; this node only emits), raises the A13 alert and audits it. `timed_out` is not terminal: a late ack moves `timed_out → acked` and is applied exactly like an on-time ack (the registry applied it, and the registry is the legal record), with the extra audit note `late_ack`. `POST .../instructions/{id}/resubmit` (REGO, or the resync effector) moves `timed_out → submitted` on the same row with the same `idempotency_key`, increments `submit_count` and restarts the SLA; the adapter must return the original `registry_ref` and, if already applied, the original ack, so a resubmission can never apply an instruction twice. There is never a second instruction row for the same approval and kind.
- Instruction transitions (A03 extension rows): `prepared → submitted`, `submitted → acked`, `submitted → rejected`, `submitted → timed_out`, `timed_out → acked`, `timed_out → rejected`, `timed_out → submitted` (resubmit), `prepared → cancelled` (maker cancel before submit). `acked`, `rejected` and `cancelled` are terminal. Anything else is refused with `REG_ILLEGAL_TRANSITION`.
- Effectors: for the non-custody rows `register.adjust`, `register.holder_detail` and `register.resync`, this node registers its effector with A14 (`registerEffector`), whose `execute` prepares and submits the instruction (or runs the resync), and it reports `confirmed` to A14 on the ack and `failed` on a registry rejection through A14's internal transition endpoint; `reconciled` follows A20's clean targeted run.

**"Register first" (the guard A28 and A38 call)**

- `GET /v1/internal/register/issued?approval_id=APR-…` (service principals of A28 and A38 only), also `getIssuedLines(approvalId)` in `index.ts`: returns the lines of the one acked `issue` instruction carrying that approval id: `{ vehicle_id, instruction_id, lines: [{ investor_id, units, wallet_address }], total_units, acked_at }`, or `404 REG_NO_ENTRY` when no acked issue carries it. `prepared`, `submitted`, `timed_out` and `rejected` instructions return `REG_NO_ENTRY`, never a partial answer. `UNIQUE (approval_id, kind)` guarantees at most one acked issue per approval, so the mint total per approval can never exceed `total_units` twice over. This guard serves issues only; burns, forced transfers, recoveries and lock-ups are chain first (table above) and are confirmed through `register.changed`, not through this query.

**Adjustments**

- An `adjust` / `units` instruction is the only way to change units or lots outside issue, transfer and redeem. Its reference is a `recon_break_id` or a `manual` reason code from the catalogue (`unit_error`, `court_order`, `estate`, `registry_correction`); its binding is the `register.adjust` row above. Adjustments may be back-dated (`effective_at` in the past) and are written with the bitemporal rule, so a query at an earlier record time still returns what the register said then. A manual unit reduction by REGO is an adjust with a negative delta; there is no separate manual redeem.
- `adjust` / `holder_detail` changes classification, residency or display name with no unit or lot change (row `register.holder_detail`, REGO → CCO, `4E`). The precheck reports which row was resolved so the checker sees it; any unit delta, however small, needs `register.adjust` under `6E`.

**Versions, snapshots, comparison and certification**

- Schedules run in `Australia/Sydney`, keyed on `(vehicle_id, as_of date)` and idempotent (a second start for the same key does nothing). `register.snapshot` at 00:00 writes the canonical CSV of current entries as of that midnight and records `register_version { source: internal }` (also on demand through `POST /v1/register/vehicles/{vehicleId}/versions`). The sandbox registrar writes its extract for the same `as_of` at 01:30. `register.fetch_extract` at 01:40 calls `fetchRegisterExtract(vehicle_ref, asOf)` and records `register_version { source: registry }`; for a real registry it polls every 10 minutes until the file for `as_of` exists or 05:00, then emits `register.extract.missing` (A20 then runs `incomplete`). 00:00, 01:30 and 01:40 exist exactly once every night in Sydney (the daylight-saving changes happen between 02:00 and 03:00). If any register job is ever configured into 02:00-02:59: on the October spring-forward night it runs once at the same minute past 03:00 AEDT; on the April fall-back night it runs once, at the first occurrence. The sandbox and A20 use the same rule.
- Comparison (owned here, and only here): right after `register.fetch_extract`, `register.compare` compares the registry version with the internal version of the same `as_of`, by file hash and then per holder and lot, writes `register_version_compare` and emits `register.version.compared { vehicle_id, as_of, internal_version_id, registry_version_id, result, diff[] }`; a `drift` result also raises an A13 alert for REGO. The event and `register.version.created { source }` are what A20 consumes; A20's nightly run at 02:00 reads `getRegisterSnapshot(vehicleId, 'latest_registry')`, so the legal record is in that night's reconciliation.
- `getRegisterSnapshot(vehicleId, selector)` in `index.ts`, selector `version_id | 'latest_registry' | 'latest_internal' | 'latest_certified'`, returns exactly A20's `RegisterSnapshot`: `register_version_id`, `vehicle_id`, `as_of`, `file_sha256`, `certified_by` (`TP-RE` when a `register_certification` row covers the version, otherwise `realx_extract`), `total_units` (always Σ `entries[].units`), `entries[] { investor_id, delivery_wallet, units, lots[] { acquired_at, unit_price_cents, lock_in_until } }` and `pending_instructions[] { instruction_id, submitted_at, approval_id }` (instructions `submitted` or `timed_out` at `as_of`), plus the additive fields `source` and `certified_by_principal_id`.
- Version status, derived from `register_certification` and A14's request state (the row itself never changes): `recorded` → `certification_pending` (an open `register.certify` request exists) → `certified` (a certification row covers it) → `superseded` (a later certification row for the same vehicle and month supersedes it); a rejected or expired request returns the version to `recorded`. Refusals: certifying an `internal` version `REG_CERTIFY_REGISTRY_ONLY`; a second open request for the same version `REG_CERTIFICATION_PENDING`; certifying a `superseded` or already `certified` version `REG_ILLEGAL_TRANSITION`.
- Monthly certification (`register.certify`, `4E`, maker REGO, checker the vehicle's trustee checker set): `POST /v1/register/vehicles/{vehicleId}/versions/{id}/certify` drafts the A14 request with payload `{ version_id, file_sha256, as_of }` for the month-end **registry** version. It is refused with `REG_CERTIFICATION_HASH_MISMATCH` when the registry version's hash differs from the internal month-end version's hash (the compare diff is attached). On approval the effector calls the adapter's `certifyVersion(vehicle_ref, file_sha256, as_of) → { certification_ref, certified_at, file_sha256 }`; if the echoed hash differs, `REG_CERTIFICATION_HASH_MISMATCH` and the request goes to `failed`; otherwise it inserts `register_certification` and writes audit `register.version.certified`. Worker job `register.certification_due` opens a REGO task on the first business day of each month and raises a Sev3 A13 alert when a vehicle has no certified version for the previous month by the 10th business day. A48's wind-down close uses the same request for its final zero-unit version.

**Reads: entries, cap table, holdings (field sets per principal)**

- `GET /v1/register/vehicles/{vehicleId}/entries?as_of=&record_time=&cursor=` returns current entries as of the effective date (default now) as known at `record_time` (default now), paginated with A09's cursor.
- `GET /v1/register/vehicles/{vehicleId}/cap-table?as_of=` returns per holder `units`, `pct_bps` (display only: basis points of total units, rounded half-even; the remainder that makes the display total 10,000 goes to the largest holder), `holder_type`, `classification`, `residency`, `frozen_units` and `locked_units` (units in lots with `lock_in_until > as_of`, from the freeze facts and lots valid at `as_of`), `wallet_display` (first 6 + last 4), `status` (`active`, `frozen`, `partially_frozen`, no reason), plus totals `holder_count`, `total_units`, `largest_holding_units`, `largest_holding_bps` (display), `foreign_units`, `foreign_units_bps` (display), `last_certified_version_id`, `last_version_as_of`. G07 (evaluated by A19) and A73's threshold monitors must use whole units, never `pct_bps`: a holding is within a cap when `units × 10,000 ≤ cap_bps × total_units`.
- `GET /v1/register/holders/{investorId}/entries?as_of=` returns an investor's entries across vehicles for A47 (portfolio, POR-02 "register match" date, lock-in end, frozen units) and for the person's own agent.
- `GET /v1/register/vehicles/{vehicleId}/versions`, `/versions/{id}` (metadata, hash, derived status, certification) and `/versions/{id}/file` (the canonical CSV, streamed, audit `register.version.downloaded`).
- Field sets, declared as zod response schemas per principal (a field not in the caller's set is absent from the schema, not blanked):
  - Sponsor of the vehicle (SP-OWN, SP-FIN, SP-IR of the owning tenant, and their agents): `holder_ref`, display name, `holder_type`, `classification`, `residency`, `units`, `pct_bps`, `wallet_display`, `status`, `locked_units`. Never TFN, address, contact details, date of birth, `investor_id`, `legal_record_ref`, full wallet address or freeze reason. This is the SPN-08 set the design and the product map show ("Kwan Family SMSF", "Estate of H. Lowe").
  - Investor (and their agent): their own rows only, with every register field of their own holding.
  - Staff with M11 read (REGO, CCO, CFO) and their agents: every register field, with the display name masked by A04's `mask` unless the caller holds the unmask cell, which writes an audit event per A11. This module stores no TFN, address, contact or date of birth at all.
  - The vehicle's TP-RE (A98 scope): every register field including the display name (the trustee keeps the register). TP-AUD and TP-OBS within their time-boxed grant: every register field with masked names, plus extract verification.
  - Visitors: nothing (PUB-08 aggregates come from A47).
- Row-level security on `tenant_id` applies underneath. Empty states: a vehicle with no acknowledged issues returns `entries: []`, `total_units: 0`, `holder_count: 0`, never an error; a vehicle id the caller cannot see returns `404`, not `403`, so existence is not leaked across tenants.

**Freeze facts (register side of SM-07)**

- An outbox consumer of A28's `token.op.confirmed` for kinds `freeze`, `unfreeze` and any partial-freeze kind A28 emits writes `register_freeze_fact` rows with the bitemporal rule (effective at the chain confirmation time). **Exports and signed extracts (logged, D04-aware)**

- `POST /v1/register/vehicles/{vehicleId}/exports` (SPN-08 "Export register", ADM-17 export): produces the canonical CSV plus the display-name column allowed by the caller's field set, stores it as a `register_extract { purpose: sponsor_export | audit }`, and writes exactly one audit event `register.exported { extract_id, vehicle_id, as_of, row_count, csv_sha256, actor_id, on_behalf_of_id, purpose }`. Byte-for-byte reproduction applies to CSV and JSON; the PDF is verified by its hash only.
- Investor confirmations (J07 step 6, J09 step 9) are extracts of one holder's entry with `purpose: investor_confirmation`, generated by the worker on `register.changed` for that holder and handed to A47/A43 through the event; this node stores the extract and its hashes.

**Force re-sync (one endpoint, one owner)**

- `POST /v1/register/vehicles/{vehicleId}/resync` drafts a `register.resync` request (`4E`, maker REGO; the product map's checker "Head of operations" is not one of A03's 51 roles, so the interim checker is CCO, recorded as a founder decision for the policy seed). ## Node-specific challenges (node QA)

- REGO drafts an `adjust` of +2 units for Gympie Road Retail to close a break; CCO and CFO approve under `6E` but no one from the resolved trustee checker set has decided: refused with `REG_ADJUST_TRUSTEE_MISSING`. The same lines under a `4E` `register.holder_detail` approval: refused with `REG_ADJUST_REQUIRES_6E`. A valid `6E` approval whose payload differs by one unit: `REG_ADJUST_APPROVAL_MISMATCH`. The audit shows every refusal.
- Replay: an adjust applies under approval X; a second prepare with X and the same lines returns the same instruction and changes nothing; a prepare with X and different lines, or with X for another vehicle, is refused `REG_APPROVAL_ALREADY_USED`; an approval in `expired`, `rejected`, `cancelled`, `failed` or `closed` is refused `REG_APPROVAL_NOT_APPROVED`; a `token.burn` approval still `approved` (chain not yet broadcast) is refused for a chain-first redeem.
- Timeout: A38 submits the issue for an allocation while the sandbox is set to `slow`; the "register first" query returns `REG_NO_ENTRY`; after the SLA the instruction is `timed_out` with `register.instruction.pending_sla` emitted; REGO resubmits (same row, same key); the sandbox then delivers two acks (the late original and the resubmission's). Entries change exactly once, `/issued` returns one acked issue with the allocation total, and `register_ack` holds one `applied` and one `duplicate_ignored` row.
- Duplicate: the sandbox acknowledges the same `registry_ref` twice: entries change once, the second ack is logged `REG_DUPLICATE_ACK_IGNORED`, and Σ units for the vehicle equals the allocation total, not double.
- Fabricated trade: in P1 a transfer referencing any `trade_id` is refused `REG_TRADE_PATH_DISABLED`.
