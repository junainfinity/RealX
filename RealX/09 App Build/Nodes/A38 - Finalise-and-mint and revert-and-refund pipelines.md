# A38 - Finalise-and-mint and revert-and-refund pipelines

**The service that takes a primary offer from its close to either "minted and settled" or "failed and refunded" as one durable, idempotent, maker-checked pipeline that orchestrates its neighbours and owns none of their primitives: on A36's close it confirms the soft-cap outcome in units; on the finalise side it waits for A37's locked allocation and A37's remainder refunds, hands A39 the "finalised" fact and waits for A39's escrow release, gets the trustee's register entry first under the `allocation.mint` approval (`6E+Q`, CAPM to CFO + CCO), asks A28 to mint per the locked file under that same approval id (V2 2-of-3), requires a clean A20 reconciliation (supply = register = allocations, zero tolerance) and then settles each order through A37 only when both its register entry and its token delivery exist; on the revert side it drafts `offer.revert_and_refund` (`4E+Q`, CAPM to CFO) bound to A37's refund batch so every funded order ends `refunded`, the sum of refunds equals the sum of funded orders and not one token is minted.**

**Build status:** not started. **Milestone:** AM3 (Chain, identity and the money path). **Lane:** Register. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops). Re-estimated on 24 Sep 2026 from 6-10 h after the audit; the graph and the critical-path figure must be updated to match (see "Spec dependencies to confirm").

**Depends on:** [[A37 - Orders, escrow, allocation and refunds (SM-05)]], [[A28 - Token operations service (mint, burn, freeze, pause, forced transfer, recovery)]], [[A39 - Treasury- withdrawals, escrow release, client-money reconciliation]]
**Unlocks:** [[A49 - Money-path smoke through the SDK (AM3 exit and founder checkpoint)]], [[A57 - Buy flow- order, review and confirm, order status (INV-01 to INV-03)]], [[A65 - Sponsor journeys J11, J12, J13, J14, J19 end to end in Docker (AM6 exit)]], [[A71 - Console- listing review, live raise monitor, orders and allocation]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec before the build starts ([[App Gauntlet]] §2). They go to `<workspace>\gauntlet\hidden\A38\` and the builder never reads that folder. The oracle scope is the four invariants of the summary and the money conservation behind them: no mint request reaches A28 before the register's acknowledged issue for the same approval id exists; a supply that does not equal the register after a mint leaves the vehicle under A20's reconciliation halt (the mint-queue freeze) as a Sev1 and no order settles until a clean re-run; an ineligible recipient found at any of the three re-check points or after issue is excluded from the file and refunded to the cent (from `offer_escrow` before release, from the trustee's return after release), and the file, the register and the mint agree line for line before broadcast; every step of both pipelines is idempotent under crashes, retries and duplicate events (exactly one `allocation.mint` request, one issue instruction, one custody op, one `offer.revert_and_refund` request per revert, one A37 refund journal per refund line, one A37 settlement and one A37 allotment confirmation per order); on the revert path Σ refund cents = Σ funded order cents, every funded order ends `refunded`, the offering ends `refunded` and no custody op, no register instruction and no token exist for it.

This note is not legal advice. Whether units may be issued and tokens minted before the trustee has settled the property purchase, whether a failed-raise refund may be credited to the investor's client-money wallet or must return to the source bank account, how the trustee returns an excluded investor's subscription after escrow has been released (and whether RealX may or must advance that refund), and whether any settlement declaration is a personal act are counsel or treasury questions recorded in "Human gates touched", not rules decided here.

## Build brief

**Scope and placement**

- One owned area: `services/api/src/modules/settlement/` (the two pipelines as a durable saga, their tables, jobs, read models and routes; the worker jobs live in the module's `jobs/` folder and are registered with pg-boss from the module's `index.ts`, so the worker process only imports the module). Module pattern from A09: one public `index.ts`, boundary lint, zod schemas feeding the OpenAPI document, injectable clock (no `Date.now()`; `npm run verify` greps for it), integer cents and whole units from A02, idempotency keys on every write.
- This node owns no order, allocation, refund, escrow, offering, ledger, register or token primitive, and no approval row that another node already drafts. It orchestrates them only through the exports their notes fix:
  - **A37** (orders, allocation, refunds, settlement): `previewAllocation`, `lockAllocation` (A37 drafts the `orders.allocation.lock` approval, `4E` CAPM to CFO, and on approval drafts the scale-back and allocation-exclusion refund batches itself), `getLockedFile`, `excludeAllocationLine`, `computeRefundBatch`, `executeRefundBatch`, `settle`, and the events `orders.allocation.locked`, `orders.allocation.superseded`, `orders.refund_batch.executed`, `orders.settled`. A37 owns the `refund_batches` table, the `orders.refund_sla` clock (5 business days, Sev2 then Sev1 at 10) and the `allotment` confirmation record. A37 moves orders at close itself (its `orders.expiry_sweep` runs once on `offering.closed`); this node never transitions an order directly.
  - **A36** (SM-04): this node reads `getOfferFacts` and consumes `offering.closed` and `offering.failed`. A36 performs `live -> closed` (its `offerings.schedule_sweep` at `closes_at` and at the hard cap), `closed -> failed` (soft cap missed, or an approved `offer.revert_and_refund`), `closed -> finalising` (on A37's `allocation.locked`), `failed -> refunding -> refunded` (on A37's refund events) and `finalising -> minted` when this node reports the mint reconciled through A36's `index.ts`. This node calls no other SM-04 transition.
  - **A39** (treasury): owns `POST /v1/treasury/escrow/{offeringId}/release`, the `escrow.release` approval (`6E`, FINA to CFO + CCO), its effector, the A16 `offer_escrow / payout_clearing` journal (`external_ref = offering id`) and the A17 payout to the trustee. This node emits the finalise fact A39 checks and waits for A39's release; it never drafts, effects or posts an escrow release.
  - **A18** for `prepareInstruction` / `submitInstruction`, `canonicalInstructionPayload`, `registerLineMapper` and `getIssuedLines` (the "register first" query); **A28** for the mint operation (`POST /v1/token-ops/operations` and `/broadcast`, in process through its `index.ts`); **A20** for `preflight`, `assertClear`, `isHalted` and its outbox events; **A14** for approvals and effectors; **A19** for gate re-evaluation; **A13** for alerts; **A10** for audit. A17 only through A37 or A39: this module never calls the bank.
- Anything this note needs that a neighbour does not yet export is a recorded change request on that neighbour (listed under "Spec dependencies to confirm"), never an invented function name and never a silent edit.
- The pipeline runs as the service account `svc-settlement` (A11 principal row, kind `SVCA`, no login, no custody role, no keys, zero money and supply caps of its own: every money or supply effect it triggers carries a human-approved approval id). Humans and their agents only draft, approve or read; they never "advance" a step by hand.

**Data (Drizzle tables in the module's schema slice, all with `tenant_id` and the standard columns)**

- `settlement_run` (`SET-<yyyymmdd>-<6 base32>`): `offering_id`, `vehicle_id`, `kind` (`finalise`, `revert`), `trigger` (`closed_soft_cap_reached`, `closed_soft_cap_missed`, `revert_requested`, `sponsor_cancel_request`), `trigger_ref`, `state` (below), `allocation_id`, `allocation_version`, `allocation_sha256`, `funded_units`, `soft_cap_units`, `funded_total_cents` (Σ order `total_cents` including fees, used only for money conservation), `allocated_units`, `allocated_subtotal_cents`, `approval_ids` (json: `allocation_lock` (A37's), `refund_batches[]` (A37 batch ids and their approval ids), `escrow_release` (A39's), `allocation_mint`, `offer_revert_and_refund`, `exclusions[]`, `trustee_ack`), `register_instruction_id`, `custody_op_id`, `recon_run_id`, `recon_halt_id` and `halt_break_ids[]` (copied from A20 for display only; the halt itself is A20's), `closing_check` (json: the close-out self-check results, no PII), `started_at`, `finished_at`. One open run per offering (unique partial index); a second start for the same offering returns the existing run.
- `settlement_step`: `run_id`, `step` (F0..F10, R0..R5 below), `state` (`pending`, `running`, `waiting_approval`, `waiting_event`, `done`, `failed`, `skipped`), `attempt`, `idempotency_key` (deterministic: `run_id + step + allocation_version`), `external_ref` (approval id, A37 batch id, instruction id, custody op id, recon run id), `waiting_for` (event name and correlation ids), `error_code`, `started_at`, `finished_at`. A step runs at most once per `idempotency_key`; a retry of a `done` step is a no-op that returns the stored `external_ref`.
- `mint_file`: `run_id`, `allocation_id`, `allocation_version`, `allocation_sha256`, `lines[]` (`order_id`, `investor_id`, `units`, `delivery_wallet` from A18's `getIssuedLines` after the ack, `eligibility_evaluation_ids[]`), `total_units`, `register_ack_at`, `built_at`. The lines are read from A37's `getLockedFile` for the current version; the file's hash equals the locked allocation's hash by construction (check constraint on `total_units` and a test on the hash).
- `exclusion`: `run_id`, `order_id`, `investor_id`, `point` (`2_before_release`, `3_after_release`, `after_issue`), `gate_code`, `evaluation_id`, `superseded_version`, `new_version`, `approval_id` (the exclusion approval where one is required, below), `redeem_instruction_id` (after issue only), `return_state` (`not_needed`, `requested`, `received`) and `return_ref` (A39's receivable id) for exclusions after escrow release, `refund_batch_id` (A37's), `state` (`open`, `refund_ready`, `refunded`). Stored gate codes are the code only; no AML case content is ever written here.
- `settlement_run.state` (local lifecycle, not one of SM-00..SM-13; SM-04 and SM-05 are driven by their owners): for `finalise`: `closed -> allocating -> allocation_locked -> refunding_remainders -> finalised_fact_emitted -> escrow_released -> register_pending -> register_acked -> mint_pending -> mint_confirmed -> reconciling -> settling -> settled`; for `revert`: `closed -> revert_pending -> failed -> refunding -> refunded`; plus `-> paused` (register rejected or timed out, reconciliation halt, approval rejected or expired, trustee return overdue) from any waiting state and `paused -> <previous state>` only by the event that clears the cause; terminal `settled` and `refunded`. There is no `abandoned` state and no path from a `finalise` run to a `revert` run: SM-04 has no `finalising -> failed`, so once A37's allocation locks the offering can only finish as `minted`. Every other pair is refused with `SET_ILLEGAL_TRANSITION`.

**Finalise pipeline (J04 steps 7-13), step by step**

- **F0 Close (J04 step 7).** A36 closes the offering (`live | soft_cap_reached -> closed`) on its own sweep at `closes_at` or at the hard cap; this node consumes `offering.closed` and opens the run within one `settlement.advance` tick. There is no close-early path in this node: an earlier close is A36's close-date change under the product map's "Extend window or material change" row (CAPM to CCO, `4E`); if A36 does not allow `closes_at` to move earlier, early closure does not exist in P1 (a change request on A36, not a path here). At close A37's `orders.expiry_sweep` moves `awaiting_funds -> expired` and handles any order still in placement; this node asserts afterwards that no order of the offering is in `submitted`, `eligibility_check`, `reflection_period` or `awaiting_funds`, and pauses with `SET_ORDERS_NOT_SETTLED_AT_CLOSE` otherwise. A payment A17 matches after close is A37's (it posts to `investor_cash`, not to escrow) and is asserted by a test here.
- **F1 Soft-cap outcome (units, not cents).** The caps are A36's per-listing parameters in units, at price and excluding fees: `soft_cap_units` and `hard_cap_units` (75 % and 100 % of 10,000 units by default; nothing about 75 % is a constant here). The test is `funded_units >= soft_cap_units`, where `funded_units` = Σ `requested_units` of orders in `funded` at close, read from A37's escrow position in the same transaction as the run opens. Exactly equal is reached; one unit short is missed, even when the fee-inclusive `funded_total_cents` would cover `soft_cap_units × unit_price_cents` (the named boundary case: subtotal < soft cap ≤ subtotal + fees must revert). A36 makes the same decision on its own facts (it performs `closed -> failed` in the same job run when the soft cap is missed); this node recomputes it as a cross-check and, if the two disagree, pauses with Sev1 `settlement.soft_cap_disagreement` (CAPM + CFO) and proceeds with neither pipeline. Reached selects `finalise`; missed selects `revert` with trigger `closed_soft_cap_missed`. `funded_total_cents` (fees included) is stored only for the money-conservation checks.
- **F2 Allocation lock (J04 step 8; run `allocating -> allocation_locked`).** The CAPM (or the CAPM's agent as maker) calls A37's `lockAllocation` through ADM-12; A37 runs its allocation algorithm and the first eligibility re-check (point 1, below), writes the draft file, refuses on a non-zero escrow Δ (`ORD_ESCROW_DELTA_NONZERO`) and drafts the one `orders.allocation.lock` approval (`4E`, CAPM to CFO, the product map's "Allocate" row). This node drafts no allocation approval: its `POST /v1/settlement/offerings/{id}/finalise` route is a thin maker route that calls `previewAllocation` for the workbench and then `lockAllocation`, returning A37's approval id. The step waits for A37's `orders.allocation.locked {allocation_id, version, file_sha256}` and records it; A36 then moves SM-04 `closed -> finalising` on the same event. A37 moves `funded -> allocated` (a scaled-back order stays `allocated` with `refund_state = pending`, A37's recorded reading of SM-05) or `funded -> refund_pending` (zero units). Any later change to the line set happens only through A37's `excludeAllocationLine`, which writes a new version and a new hash (`orders.allocation.superseded`); the pipeline never edits a file.
- **F3 Remainder refunds (J04 step 8; run `refunding_remainders`).** The scale-back and allocation-exclusion refund batches are A37's (drafted on lock with reasons `scaled_back` / `excluded_at_allocation`, approved under `orders.refund.batch`, `4E`, FINA to CFO, the product map's "Issue refund" row). On each batch's approval this node calls A37's `executeRefundBatch(batchId)` once (idempotent on the batch id; A37 posts one `order.refund` journal per line with `external_ref = <batch id>:<order id>`, fee leg from `fee_payable_realx`). Amounts are A37's: `refund_cents = total_cents_funded − allocated_cents − fee_cents`, with `fee_cents = mulBp(allocated_cents, fee_bps, half_up)` and `fee_bps` the offering's own parameter from its rule pack (50 bp is only the default; this node never hard-codes a rate). When A37 drafts no batch (no oversubscription, no exclusion), F3 is `skipped`. The step is `done` only when A37 emits `orders.refund_batch.executed` for every batch of the current allocation version. Refund timeliness is A37's `orders.refund_sla` clock; this node adds no refund clock and no refund alert.
- **F4 Finalised fact, then wait for A39's escrow release (J04 step 9; run `finalised_fact_emitted -> escrow_released`).** When SM-04 is `finalising`, F3 is `done` or `skipped` and eligibility point 2 is clean, this node emits once `offering.finalised {offering_id, vehicle_id, allocation_id, allocation_version, allocation_sha256, allocated_subtotal_cents}` (idempotent on `offering_id + allocation_version`). This is the fact A39's release precondition reads: A39's "offering `finalised`" is SM-04 `finalising` plus this event (the naming is reconciled on A39, below). The FINA drafts A39's `escrow.release` on ADM-18; A39 checks its own five preconditions, obtains CFO + CCO, posts `offer_escrow / payout_clearing` for exactly the allocation total and pays the trustee's settlement account. This node waits for A39's `treasury.escrow.released {offering_id, approval_id, amount_cents, journal_id}` and accepts it only when `offering_id` matches, `amount_cents = allocated_subtotal_cents` of the current allocation version and the approval id is an approved `escrow.release` in A14 for that offering; any other event is ignored and audited as a correlation refusal. It does not wait for A17's bank settlement, except that the offering flag `require_trustee_settlement_ack` (default off; counsel question) makes F5 also wait for a `settlement.trustee_ack` approval (`4E`, TP-RE maker, CFO checker; a new A14 row, below). An exclusion at point 2 (before release) supersedes the file before the fact is emitted, so A39 always releases the reduced total.
- **F5 Register entry first (J04 step 10; run `register_pending -> register_acked`).** The CAPM (or the CAPM's agent as maker) drafts `allocation.mint` through `POST /v1/settlement/runs/{id}/mint` (`6E+Q`, CAPM to CFO + CCO, custody vault V2 2-of-3, the product map's "Finalise offer and mint" row; `object_ref = allocation_id`, `payload_sha256 = allocation_sha256`, `cap = total_units`). This single approval id binds the register instruction, the custody op and the chain transaction; it is A28's from-file mint approval, so A28 creates no second draft (A28's recorded proposal; the mint checker set is A28's open spec gap, below). Precheck hooks registered with A14: run `escrow_released`; A20 `preflight({vehicleId, purpose: 'mint'})` clean; eligibility point 3 clean; A36's facts show `finalising` with this allocation locked. On `approved` the effector calls A18's `prepareInstruction` as `svc-settlement` (A18 lists this node as the `issue / primary` caller) with `kind: issue, subkind: primary, reference: allocation_id, approval_id`, one line per allocation line (`investor_id`, `units`, `price_cents`) and the offering's `lock_in_days` (A18 computes `lock_in_until` from the ack date; this node never passes a date), then `submitInstruction`, and waits for A18's `register.changed` carrying the same `approval_id` and `instruction_id`. J04 step 10's TP-RE actor is the ack: for a vehicle whose `register_keeper = trustee`, A18 accepts it only through `acknowledgeTrusteeInstruction` after the TP-RE's passkey confirmation (A98); otherwise the registry sandbox acks. `register.instruction.rejected` -> run `paused` with `SET_REGISTER_REJECTED`, Sev1 alert `settlement.register_rejected` (REGO + CCO), no mint; `register.instruction.pending_sla` (24 h, A18's sweep) -> `paused` with Sev2 `settlement.register_timeout`, resumed only when the resubmitted instruction acks.
- **F6 Mint file, pre-broadcast agreement check and the mint request (J04 step 11; run `mint_pending`).** After the ack the module builds `mint_file` from A37's `getLockedFile` plus each holder's `delivery_wallet` from A18's `getIssuedLines(approvalId)`. Before calling A28 it proves three things and refuses with a named code otherwise: `getIssuedLines` returns lines whose set (investor, units) equals the mint file exactly (`SET_REGISTER_FILE_MISMATCH`, Sev1 alert, run `paused`); every `delivery_wallet` is identity-registered on the token's IR as A19 reports (`SET_DESTINATION_NOT_REGISTERED`; A28's destination guard is the second net); A20 `isHalted(vehicleId)` is false and `assertClear(vehicleId, 'mint', {approvalId})` passes (`SET_RECON_NOT_CLEAR`). Then it creates A28's operation once through A28's `index.ts` equivalent of `POST /v1/token-ops/operations` with `kind: batch_mint`, the vehicle, `params {allocation_id, allocation_version, allocation_sha256, lines, cap: total_units}` and the existing `allocation.mint` approval id (idempotent on that approval id; A28's `UNIQUE` consumption refuses a second use). A28 owns the `CustodyOp`, the attestation, the supply and register-first prechecks, the signer collection on A15 and the indexer confirmation. The V2 signers (TOKO, CCO, CFO per the vault record; any two) sign on ADM-14 under their own hardware keys: that is J04 step 11's TOKO actor, and the product map's "Deliver tokens" row is read, as A28 proposes, as the V2 signing step of this same approval. On A15's `custody.op.signed` for the op, `svc-settlement` calls A28's `/operations/:id/broadcast` (A28 accepts the `SVCA` pipeline principal for this node; a TOKO pressing Broadcast on ADM-14 first is equally valid because broadcast is idempotent on `op_id`; no person's agent can broadcast). The design's "Mint on offer close" operation (OP-7730) is this operation; the run records A28's `custody_op_id`. A mint for an offering that is still `live` (design bug 6) is refused here with `SET_OFFER_NOT_FINALISED`, by A18 (`REG_OFFERING_NOT_FINALISING`) and by A28 (a hidden test tries all three doors).
- **F7 Reconcile and the mint-queue freeze (J04 step 12; run `mint_confirmed -> reconciling`).** A20 runs a targeted reconciliation for the vehicle on the same `custody.op.confirmed`; this node consumes A20's outbox event `recon.run.completed` for the vehicle and correlates on `custody_op_id ∈ trigger_refs[]` (REGO reviews it on ADM-17, J04 step 12's actor). Clean run with `open_break_ids = []` and `register_version_id` at or after the issue's ack: `reconciling -> settling`, the `recon_run_id` stored, and this node reports the mint reconciled to A36, which performs `finalising -> minted` (property SM-03 `funded -> operating` belongs to its owner and consumes A36's event). A run with a Sev1 break for the vehicle (R2, R3 or R7): A20 itself sets its vehicle-level `recon_halt` and emits `recon.halt.set`; that halt is the mint-queue freeze. This node copies the halt id and break ids for display, raises Sev1 `settlement.mint_queue_frozen` (REGO + CCO + TOKO, dedup on vehicle), pauses the run and settles no order. Every later mint for the vehicle (this offering's retry, a second tranche, a correction, A28's not-from-file mints) is refused because A28's precheck (`TOP_BREAK_OPEN`), A14's (`APR_RECON_BREAK_OPEN`) and this node's `assertClear` all read the same halt. The freeze clears only when A20 clears the halt (`recon.halt.cleared`, after a completed run over current keys with zero open Sev1 breaks); there is no route, job, SDK method or MCP tool in this node that clears it, and this node keeps no freeze flag of its own.
- **F8 Settle orders (J04 step 13; SM-05 `allocated -> settled`, run `settling`).** For each allocation line of the current version, after the clean run of F7, the module calls A37's `settle(order_id, { register_entry_id, register_version_id, token_delivery: { custody_op_id, tx_hash, minted_units } })`. It wires A37's `TokenDeliveryProvider` to A28's confirmed `CustodyOp` and passes the A18 register entry whose lot references this run's instruction. A37 refuses with `ORD_SETTLE_REQUIRES_BOTH` or `ORD_SETTLE_UNITS_MISMATCH` when a fact is missing or differs; a test removes each fact in turn and expects the refusal. Settlement is per line, so an excluded line's order never settles and the others do.
- **F9 Confirmations.** A37's `settle` issues the `allotment` confirmation record (canonical JSON with sha256) and emits `orders.settled`; this node creates no confirmation and emits no second settled event. F9 reads back, for every settled order, the allotment confirmation id and sha256 through A37's `index.ts` and stores them in `closing_check`; a missing record is `SET_CONFIRMATION_MISSING` and blocks F10. A47 renders the PDF ("Confirmation RX-ORD-51877 · Ready") and A43 sends "tokens delivered" from A37's `orders.settled`.
- **F10 Close-out.** Run `settled`, `finished_at`; the closing self-check (supply = register = allocation total, every non-excluded order `settled`, every exclusion `refunded`, every trustee return `received`, `offer_escrow` for the offering exactly zero) is stored in `closing_check` and in the payload of the A10 audit event `settlement.run.completed` (no PII). SPN-07 shows "Funded", ADM-12 shows every order's settlement status, INV-03 shows all five timeline rows done.

**Eligibility re-check (G01, G02, G04, G06, G07 at three points and after issue)**

- **Point 1** is A37's allocation-time evaluation set inside `lockAllocation` (G01, G04, G06, G07 through A19, with G02 applied through A37's consumption of A42's `investor.frozen`); an order failing it never enters the file and is refunded from `offer_escrow` in A37's `excluded_at_allocation` batch. **Point 2** runs in this node before F4 emits the finalised fact (before escrow release). **Point 3** runs before the F5 register instruction is prepared (after release). At points 2 and 3 this node asks A19 to evaluate G01 (identity active and KYC unexpired), G02 (sanctions and PEP clear; an AML restriction excludes), G04 (wholesale classification unexpired for the offer), G06 (residency and FIRB rule of the vehicle) and G07 (holder cap with the final line, and the holder-count threshold) per line, storing `GateEvaluation` ids on the line. G12 is not re-evaluated (the acknowledgement was taken at order time and stands under the holder's consent), but a missing acknowledgement id on an order is `SET_DISCLOSURE_MISSING` and excludes. A28's destination guard and A19's G07 on-chain `MaxBalanceModule` remain the last net at broadcast.
- **Exclusion at point 2 (money still in `offer_escrow`).** The module calls A37's `excludeAllocationLine(allocation_id, order_id, gate, approval_id)`, which writes version `n+1` with the line at zero, moves the order `allocated -> refund_pending` (`excluded_at_mint`), drafts A37's refund batch (`4E`, FINA to CFO) and emits `orders.allocation.superseded`. The refund posts from `offer_escrow` (subtotal) and `fee_payable_realx` (fee) through `executeRefundBatch`. The finalised fact is emitted only for the new version, so A39 releases the reduced total. For `approval_id` this node passes the approval A37's signature requires for a gate-driven exclusion; if A37 requires a discretionary approval for a gate outcome, that is settled at Specify as a change on A37. Freed units are not re-allocated in P1 (A37's rule: `unallocated_units` shows them; the raise finalises smaller).
- **Exclusion at point 3 (after release, before the register instruction).** The line's subtotal has left `offer_escrow` for `payout_clearing` and the trustee, so it cannot be refunded from escrow (A16 would refuse with `LDG_INSUFFICIENT_AVAILABLE`, and this node never invents a journal). The post-release leg is: (1) a `settlement.exclude_after_release` approval (`6E`, maker REGO or CAPM, checkers CCO + CFO + the vehicle's trustee checker set, mapped onto the product map's `6E` "Resolve reconciliation break by register adjustment" row; payload = the order id, `allocated_cents` to be returned and the superseded and new file hashes); (2) on approval, `excludeAllocationLine` supersedes the file as at point 2 (a new `allocation.mint` draft is required if one was drafted, because its hash changed); (3) this node emits `settlement.exclusion_return_requested {offering_id, vehicle_id, order_id, amount_cents = allocated_cents, approval_id}` and A39 records a trustee receivable with its own clock and matches the trustee's payment into the escrow trust account as an A16 journal (escrow bank mirror / `offer_escrow` for the offering, `external_ref = <allocation_id>:<order_id>`, the same approval id); (4) on A39's `treasury.exclusion_return.received` the exclusion is `refund_ready` and this node calls A37's `executeRefundBatch` for the excluded line (subtotal from the returned `offer_escrow` balance, fee share from `fee_payable_realx`, which A39's fee sweep must not have swept for an offering whose run is not yet `settled`). The register instruction and the mint proceed on the new version without waiting for the return; F10 waits for it. A return still open at 5 business days raises Sev2 `settlement.trustee_return_overdue` (FINA + CFO) and the run shows `paused` for close-out; A37's `orders.refund_sla` clock keeps running for the investor and breaches as A37 specifies. Whether the trust deed lets the trustee return the money this way, and whether RealX may or must advance the refund from its own operating account while the return is outstanding, are HG-LEGAL and treasury questions (below); the default until answered is "wait for the trustee's return".
- **Exclusion after the register ack and before broadcast (a sanctions match lands between the ack and the signatures).** The pipeline does not mint and does not "skip the line". The REGO (or REGO's agent as maker) drafts `settlement.exclude_after_issue` (`6E`, CCO + CFO + the vehicle's trustee checker set, A18's `redeem / exclusion` row, mapped onto the same product-map register-adjustment row). The approval's `object_ref` and the instruction's `reference` are both `<allocation_id>:<order_id>`, and `payload_sha256 = sha256(canonicalInstructionPayload(vehicle_id, 'redeem', 'exclusion', lines))` from A18's export, as A18's row requires. On approval `svc-settlement` prepares and submits the A18 `redeem / exclusion` instruction (A18 lists this node as that caller; its lot-lock and frozen-source bypasses name this action code), waits for its ack, calls `excludeAllocationLine`, requires a new `allocation.mint` approval for the new hash (the old one is cancelled through A14's veto path before any signature is used, and A15's P1 binding refuses its attestation), then requests the return and refund exactly as at point 3, and only then creates the mint operation for `total_units − excluded units`. The excluded investor's response says "refunded" with amount and date once posted; nothing about the AML reason reaches any investor-facing or sponsor-facing field (A42's tipping-off rule).

**Revert-and-refund pipeline (J05), step by step**

- **R0 Trigger (J05 step 1).** A revert is possible only while SM-04 is `closed` (A36 allows `closed -> failed` on soft cap missed or an approved `offer.revert_and_refund`, and has no `live -> failed` and no `finalising -> failed`). Three sources: (a) F1 selects `closed_soft_cap_missed`; (b) the CAPM chooses to revert a closed offering whose soft cap was reached (for example after an adverse finding) through `POST /v1/settlement/offerings/{id}/revert`; (c) a sponsor's SPN-07 "cancel and refund" request, which becomes a CAPM-drafted revert with the sponsor's request as evidence (a sponsor or a sponsor's agent can request, never draft the approval or approve). J05 step 1's "soft cap at risk three days out; chooses revert" is served while the offer is live by the Sev3 `settlement.soft_cap_at_risk` alert on ADM-08, by A36's pause (`offer.pause`, `SGL+R`) to stop new commitments and, where A36 allows it, by A36's close-date change; the revert itself happens at `closed`. A revert request for an offering in `finalising` or later is refused with `SET_REVERT_AFTER_FINALISING` (after a locked allocation the only exits are A28's burn or A48's wind-down, not a refund).
- **R1 Refund batch and the revert approval (J05 steps 2-3; run `revert_pending`).** The FINA (or FINA's agent) prepares the batch with A37's `computeRefundBatch(offering_id, reason)` (reason `soft_cap_missed` for (a), `offering_cancelled` for (b) and (c)): every order with money in escrow is refunded its full `total_cents` (subtotal and fee), so `Σ line.amount_cents = funded_total_cents`. The CAPM (or the CAPM's agent) then drafts `offer.revert_and_refund` (`4E+Q`, CAPM to CFO, the product map's "Revert and refund a failed raise" row, and A36's spelling of the code); its payload carries `offering_id`, the reason and the batch's `file_sha256`. The custody leg resolves to `not_applicable` while the offering's rule pack has `onchain_escrow = false` (every P1 pack), so the row executes with a human CFO decision and keeps the `+Q` code and its test for any on-chain escrow. For source (a) A36 has already performed `closed -> failed` in its close job; for (b) and (c) A36 performs it on the approval. A human CFO always approves; an agent can only prepare and draft.
- **R2 Fail (run `failed`).** On `offering.failed` A37 moves every `funded` order to `refund_pending` (and every `revoked` order that had paid, in the `fund_at = confirm` variant), and A36 emits the facts its owners consume (SM-03 `listed -> withdrawn` belongs to the property owner). Audit `settlement.reverted`.
- **R3 Refund (J05 step 4; run `refunding`).** Because the approved `offer.revert_and_refund` carries the batch's `file_sha256`, A37 executes the `soft_cap_missed` or `offering_cancelled` batch under A14's `AUTO` row on an exact hash match; this node calls `executeRefundBatch(batchId)` once, and A37 posts one `order.refund` journal per line (`offer_escrow / investor_cash`, fee leg from `fee_payable_realx`), moves each order `refund_pending -> refunded` in the same transaction and emits `orders.refunded`; A36 performs `failed -> refunding -> refunded` from A37's events. A recomputed batch whose hash differs from the approved one is not executed (`SET_REFUND_BATCH_HASH_MISMATCH`, a new approval is needed). The credit lands in the investor's AUD wallet (client money on trust, "funds available"); the offering flag `return_to_bank` (default off; counsel question) additionally emits `settlement.refund.return_to_bank {investor_id, amount_cents}` for A39's payout path, and R4 then also waits on `payout.settled`. Invalid bank details on that path are A39's hold-and-remind policy.
- **R4 Refunded (J05 steps 5-6).** When A37 reports the batch `executed` (and, with `return_to_bank`, every payout settled) and A36 reports `refunded`, the run is `refunded`, audit `settlement.run.completed`. Closing self-check (as tests and in `closing_check`): Σ posted refund cents = `funded_total_cents`; every order that was `funded` at R2 is `refunded`; `offer_escrow` for the offering is exactly zero; no `register_instruction`, no `custody_op`, no `mint_file` row exists for the offering; A20's next run for the vehicle reports `not_issued`. INV-03 shows "Refunded · A$x · date", SPN-07 shows "failed" with the refunded total, ADM-12's refunds queue (A37's) shows every line posted.
- **R5 Partial failure.** A refund journal refused by A16 (`LDG_INSUFFICIENT_AVAILABLE` on `offer_escrow` would mean the escrow invariant broke) leaves A37's batch `executing` with the failing line named. This node pauses the run, raises Sev1 `settlement.refund_failed` (FINA + CFO + REGO), never skips the line, and resumes by calling `executeRefundBatch` again after the cause is fixed by the treasury or a `6E` register adjustment; A37 replays posted lines as no-ops.

**Idempotency and durability (the "whole pipeline under retries" invariant)**

- The saga runner is the worker job `settlement.advance` (every 10 s per open run, plus on every consumed event). Each step is a function `(run) -> StepResult` that reads its `settlement_step` row first: `done` returns the stored ref; `running` older than the step's lease (60 s) is retried; every external effect passes a deterministic idempotency key (`Idempotency-Key` header for A14 drafts, A37's batch id for `executeRefundBatch`, A18's `(vehicle_id, kind, approval_id, reference)` replay rule, A28's approval-id consumption for the mint operation, A28's `op_id` for broadcast, A37's `order_id` for `settle`). Events are consumed through the outbox with `(run_id, event_id)` uniqueness, so a duplicate `register.changed`, `custody.op.confirmed`, `recon.run.completed` or `treasury.escrow.released` advances nothing twice. A crash between an external effect and the local `done` mark is recovered by re-reading the effect by its key (A14 `GET /v1/approvals?idempotency_key=`, A18 instruction by reference, A28 operation by approval id, A37 batch and order state) before deciding to retry, never by blind re-execution.
- Approval expiry (72 h TTL) or rejection at any step: the run `paused` with the reason; a new draft is created only by a human or a human's agent (maker), never by the runner (`settlement.draft_required` task through A43's task hook, stub when absent). Cancelling an approved-but-unexecuted `allocation.mint` is A14's veto path; the run follows.
- A run that has been `paused` for longer than 5 business days raises Sev2 `settlement.run_stalled` (CAPM + CFO); one paused for 10 business days escalates to Sev1. A stalled revert is also visible through A37's `orders.refund_sla` clock.

## Node-specific challenges (node QA)

- **Mint through every door before the register (money, oracle).** The sandbox registrar is in `-SLOW` mode. With the `allocation.mint` approval `approved` and both custody signers ready, the node QA calls `POST /v1/settlement/runs/{id}/mint` again, creates an A28 operation directly with the approval id, and replays a forged `register.changed` event without the instruction's ack. The run must stay `register_pending`, A28 must refuse with `TOP_REGISTER_FIRST` because A18's `getIssuedLines` returns `REG_NO_ENTRY`, the forged event must be rejected by correlation (no instruction with that approval id is `acked`), and no `CustodyOp` may exist. Then the node QA drafts a mint for Unley Road while it is still `live` (design bug 6, in a copy of the seed): `SET_OFFER_NOT_FINALISED` here, `REG_OFFERING_NOT_FINALISING` at A18, a precheck refusal at A28, and three audit events for the three refusals.
- **Two units short after the mint (money, Sev1 freeze).** The registrar is told `-DRIFT-2` for one holder of Unley Road; the mint confirms; A20's targeted run opens a `qty` Sev1 break and sets its vehicle halt. The run must be `paused`, every order of the offering must remain `allocated` (none `settled`, no A37 allotment confirmation, INV-03 showing "we're checking this with the trustee"), a second mint for the vehicle (this node's route and an A28 not-from-file mint) must be refused, and the node QA must fail to clear the freeze by any route: a `POST` to an unfreeze path (must not exist), resolving the A13 alert, restarting the worker, approving a `6E` adjustment without a re-run, or a re-run on an older register version. Only A20's break close plus a clean run over current keys may clear it (`recon.halt.cleared`), after which the orders settle and exactly one A37 confirmation per order exists.
- **The recipient who became ineligible late (compliance, G02/G07).** After the register ack and before the second custody signature, A19's G02 fixture (or A22's sanctions sandbox) reports a sanctions match for one investor of the batch. The pipeline must not mint: the REGO drafts `settlement.exclude_after_issue` with the trustee checker set, `svc-settlement` submits the `redeem / exclusion` instruction with `reference = object_ref = <allocation_id>:<order_id>`, waits for its ack, supersedes the file through A37, requires a new `allocation.mint` approval with a new hash (the old approval id refused by the custody sandbox's P1 binding), requests the trustee return, refunds the line to the cent including its fee share only after the return is received, and mints `total_units − excluded units`. A second case excludes at point 3 (after A39's release, before the instruction) and must follow the same return-then-refund order with no journal against an empty `offer_escrow`. The excluded investor's `GET /v1/me/orders/{id}/settlement` must show `excluded` with amount and date and no mention of AML, sanctions or a case id; the sponsor view must show that application as refunded. A separate case plants a G07 breach into a forged mint request: A28's precheck must refuse it.
- **Crash at every seam, events twice (money, idempotency).** The chaos harness kills the runner after each external effect and before its `done` mark, for every step of both pipelines, and the outbox harness delivers every event twice and once out of order. Across the whole J04 and J05 runs there must be exactly one `orders.allocation.lock` request (A37's), one `escrow.release` request (A39's), one `allocation.mint` and one `offer.revert_and_refund` request, one `offering.finalised` event, one A18 issue instruction, one `CustodyOp`, one refund journal per refund line, one `settle` and one A37 allotment confirmation per order, and no audit event for a replay; the fast-check property `Σ refunds + Σ allocated subtotal released − Σ trustee returns + Σ retained fees = Σ funded` must hold on 10,000 generated offerings with random `fee_bps`, oversubscription, caps, exclusions at every point and kill points.
- **One unit under the soft cap, fees that would cover it, and 12,000 units for 10,000 (compliance, G11).** Funded orders summing to `soft_cap_units − 1` units at the end date, with a fee-inclusive total at or above `soft_cap_units × unit_price_cents`, must produce a `revert` run, every order `refunded`, Σ refunds = Σ funded, `offer_escrow` exactly zero, no instruction, op or mint file; summing to `soft_cap_units` exactly must produce a `finalise` run. An oversubscription of 12,000 requested units against a 10,000-unit hard cap under pro-rata with one holder requesting 800 units under a 5 % cap must allocate exactly 10,000 units, cap that holder at 500, refund each remainder to the cent with its fee share at the default 50 bp and again at a non-default `fee_bps` of 75, and lock a file whose hash the approvals bind; a line change after the lock that does not go through `excludeAllocationLine` must be impossible.
- **Maker, checker and the agents (security, G13/G22).** The CAPM's agent token drafts `allocation.mint` and then tries to decide it, and the CFO who decided the lock of a superseded version tries to approve the mint of that superseded file: both refused by A14 with the SoD or superseded-hash reason and audited. The CAPM's agent token with the vehicle outside its allowed trusts is refused `G22_VEHICLE_NOT_ALLOWED`, and one whose per-action cap is below `cap × unit_price_cents` is refused `G22_LIMIT_EXCEEDED`, both before any A14 draft exists; a FINA agent's `refund-batch` call above its daily cap is refused the same way. A successful agent draft sends A101's sensitive-action notice to the human (not to the agent); a token revoked, and then a tenant kill switch set, between two calls makes the second call fail within one request. A sponsor's agent with `SPN.offer.cancel_request` drafts `offer.revert_and_refund` directly (must be refused; it may only create the cancel request), and a staff token with only `M05.settlement.read` calls `finalise` (refused, 403 with the scope named). Finally the node QA replays the consumed `allocation.mint` approval id into a second A28 operation for another offering of the same vehicle: A28 and the custody sandbox must refuse (id consumed once) and this module must never have issued the second request.
- **The seed that lies about time (design fidelity).** With A06's standard seed, `GET /v1/me/orders/RX-ORD-55120/settlement` must return the three pending rows with the design's exact label and detail strings including "64% of 75% · refunded automatically if not reached by 14 Oct 2026"; `RX-ORD-51877` must be `settled` with `units_issued.done`, `tokens_delivered.done` carrying a tx hash and A37's allotment confirmation reference; the `adToken` waiting op for "Mint on offer close · 9,100 tokens" must belong to a run at `mint_pending` whose offering is `finalising` with `closes_at` before the as-of instant, whose escrow release and register issue exist, and whose `allocation.mint` approval id (APR-2279) appears on no other object; Kent Street and Ann Street must have no run. A seed with a mint request on an open offer, a reused approval id, or a timeline string that differs from the prototype by a character fails the node (and is reported to A06).
