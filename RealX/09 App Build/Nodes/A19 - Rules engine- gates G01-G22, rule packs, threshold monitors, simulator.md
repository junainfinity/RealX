# A19 - Rules engine: gates G01-G22, rule packs, threshold monitors, simulator

**One place that answers "may this action happen, and if not, what fixes it": every order, allocation, mint, transfer, distribution line, withdrawal, listing, offer and agent-initiated action is evaluated against gates G01-G22 by pure, versioned evaluators parameterised from an immutable, versioned rule pack. Every verdict is stored with its inputs hash, its evaluator version and a hash of the exact action it approves, so a consumer can prove the action it executes is the action that passed, and any decision can be replayed years later.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-16 agent-hours (build, challenge and verify loops).

**Unlocks:** [[A20 - Three-way reconciliation engine with zero tolerance]], [[A30 - Investor onboarding, KYC cases and KYB (SM-01)]], [[A31 - On-chain identity and claims service (V4 identity agent)]], [[A34 - Properties, valuations and proof of property (SM-03)]], [[A36 - Offerings- offer terms, listing review, raise monitor (SM-04)]], [[A37 - Orders, escrow, allocation and refunds (SM-05)]], [[A39 - Treasury- withdrawals, escrow release, client-money reconciliation]], [[A73 - Console- rule packs and threshold monitors, register and reconciliation]], [[A91 - P2- resale board market module (SM-09)]], [[A17 - Bank rail sandbox adapter (NPP-PayID-PayTo) and receipt matching]], [[A35 - Documents, disclosure library, e-sign and acknowledgements (G12)]], [[A104 - MCP server generated from the OpenAPI document]] (twelve dependents, as in `app-graph.json`)

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A19\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The oracle scope is one vector set per gate G01-G22 on both sides of every threshold, the gate-sets table exactly as written, the result and proceed rules, rule-pack immutability, the override allow-list, verdict binding (`assertPassed`), replay determinism across evaluator versions, threshold-monitor arithmetic and simulator correctness and output shaping.

## Build brief

Why this node exists: A03 gives the gate ids, phases and fix-it message keys as data with no numbers in them (architecture brief risk 17). A12 gives the G22 evaluator and the token middleware. Every service that comes after (orders, offerings, treasury, register, market, identity) must ask one engine the same question and get the same answer, so the buy stepper, the listing review, the approvals precheck, the MCP tools and the reconciliation engine never disagree about eligibility. This node is that engine. It ships no screen; A73 and the design-extension nodes render its output.

**1. Rule packs: the only home of gate thresholds, dates and defaults.**

- `rule_pack` rows (A04 core table): `code` (`AU-W-2026.1` for the wholesale track now; `AU-R-2027.1` as a P2 stub with `state = draft` and `phase = P2`), `regime` (`s708_wholesale` | `au_mis_retail`), `effective_from`, `effective_to`, `parameters` (canonical JSON), `params_sha256`, `state` (`draft` → `review` → `approved_pending_effect` → `effective` → `superseded`), `approval_id`, `supersedes_code`, `external_refs` (the pinned versions of the module-owned parameter sets in table 1b). A pack in state `effective` or `superseded` is immutable: any `UPDATE` to `parameters` or `external_refs` is refused by the module and by a database trigger. Changing a threshold means drafting a new pack (`AU-W-2026.2`) that A14 routes through the "Rule pack change" approval (action `rules.pack.change`, CCO maker, LEGL checker per ADM-16; design: APR-2285 "Holder cap 5% → 7.5% Ann Street", High, checks "Trust deed allows change", "Licensee notified", "Holders affected"), and the effective date of the new pack is never earlier than its approval time.
- **One source per figure.** A gate threshold lives in the pack and nowhere else. Other nodes read it through `getEffectiveParams(vehicleId | regime, now) -> ResolvedParams` exported from `index.ts`; A32's `classification_policy` and A34's valuation and supply rules read these keys and hold no copy (A32 keeps only its process rows: reminder days, review months, assessor, joint-account rule). Figures owned by a module that already keeps an approved, versioned policy table (A41 tax rates, A43 claims ruleset, A44 complaint clocks, A21 perimeter and DAF exemption meter) stay in that table; the pack pins their version in `external_refs`, the fact provider supplies the values, and every evaluation records the version it used, so replay is still exact and no figure has two homes.

**Result meanings and the proceed rule.** `pass` and `warn` let the action proceed (`warn` is shown, and A14 requires warnings on an approval to be acknowledged). `hold` stops the action without being a compliance failure: the action waits for a named step (for example a FIRB clearance) and resumes when a fresh evaluation passes. `fail` stops the action. `not_applicable` is neither pass nor fail. An evaluation set's outcome is `passed` only when no gate is `fail` or `hold` and every `not_applicable` result is listed as valid for that action kind, regime and phase in table 3; an unlisted `not_applicable` is treated as `fail` with `NA_NOT_VALID_<gate>`. Outcomes: `passed`, `passed_with_warnings`, `held`, `blocked`. A `counsel_pending` parameter downgrades a block to `warn` with `COUNSEL_PENDING_<KEY>` only where table 1a says "warn"; where it says "enforce (safe side)" the block stands and the reason trail names the open question.

**Evaluator ownership and registration.** `packages/domain` owns the gate ids; this module ships a baseline evaluator for every gate in `src/modules/rules/evaluators/g01.ts` … `g22.ts` and exposes `registerGateEvaluator({gate, actionKinds, evaluator, version, owner})` so an owning node replaces the baseline for the kinds it owns: A41 → G16; A43 → G17 (through `checkClaims`); A44 → G18. This node's baseline evaluators are final for **G02, G04, G05 and G14**: A32 and A42 register fact providers only (their specs say A19 owns these verdicts), and `registerGateEvaluator` refuses those four gates from any other owner (`RULES_GATE_OWNED_HERE`); A96 changes P3 wallet screening by replacing A42's fact, not the evaluator. Every version of every evaluator stays registered (versions are immutable; a behaviour change needs a new version string); each `gate_evaluation` row stores `evaluator_id@version`, and replay re-runs the stored version. Startup fails if any of the 22 gates lacks an evaluator for a kind that table 3 assigns to it, or if an evaluator exists for a gate id A03 does not define.

Evaluators are deterministic, receive the clock as an argument, do no I/O and never throw on missing facts. `fix_it` is the plain-English message key and the numbers the screens need (design: "any failed check disables the button and says how to fix it").

What each baseline evaluator decides:

- **G01** identity: `identity_status.whitelisted` and `kyc_valid_until > now`; for `transfer`, `resale_buy`, `forced_transfer` and `estate_transfer`, both sides (the recipient side for forced and estate transfers). Fix-it names the missing step (ONB-03 or re-verification).

For any payout kind (`distribution_line`, `withdrawal`), a subject whose `screened_at` is older than `aml.screening_max_age_h` (table 1a) → `fail SCREENING_STALE`, whatever its outcome. The gate passes only when at least one subject is `clear` and no subject fails. These codes are staff-only; see verdict shaping in section 3.
- **G03** entity and owners: for an entity investor (or the sponsor entity on `offer_submit`, `listing_go_live`, `tenant_admission`), the KYB case is approved and every owner at or above `kyb.ubo_threshold_bps` is verified; otherwise `fail G03_OWNERS_PENDING` with the count, never the names. `not_entity` is `not_applicable` (valid).
- **G04** wholesale status (A32's reason codes, one vocabulary): the effective classification is the `valid` or `expiring` row with the latest `valid_until` (for `ticket_500k`, the row for this offer). For a retail-regime offer G04 is `not_applicable` (valid) and G05 decides.

- **Binding.** `assertPassed(setId, actionSha256, {maxAgeSeconds = rules.set_max_age_seconds, requireFresh})` is called by every consumer inside the transaction that executes the action. It refuses `RULES_SET_NOT_PASSED` (outcome not `passed` or `passed_with_warnings`), `RULES_ACTION_MISMATCH` (the executed action's hash differs), `RULES_SET_STALE` (older than `maxAgeSeconds`); with `requireFresh` it re-runs `evaluateAction` inside the same transaction as a new set referencing the old one and refuses unless that passes too. Execution of transfers, mints, allocations, withdrawals and go-lives uses `requireFresh`, so a halt opened between evaluation and execution stops the action.
- Replay: `replay(evaluation_set_id)` re-runs each stored `evaluator_id@version` on the stored facts, pack and external refs, and must reproduce identical results and reason codes; a mismatch at the same version is a Sev1 finding. An adopted G22 row is replayed by re-running A12's evaluator version on the canonical input A12 stored; if A12 stores only the hash, replay verifies the hash and reports the row as `REPLAY_BY_OWNER`.

- **Precheck hooks.** At boot this node calls A14's `registerPrecheck(action_code, hook)` for every action code in table 3b, so A14's binding precheck runs the table-3 row of the mapped kind; the hook returns the set id for the request's `precheck_result`. The context is built from the request's `payload_canonical` (the inverse of `approvalPayloadFor`). **Precheck mode:** the request is not yet approved, so G13 is recorded as `not_applicable` with reason `PRECHECK_G13_DEFERRED`; that `not_applicable` is valid only in a set whose `mode = precheck` (in any other set it blocks as `NA_NOT_VALID_G13`), and G13 is decided at execution by `assertPassed(..., {requireFresh: true})`, which re-runs the full row including G13. A precheck set can never satisfy `assertPassed` (`RULES_SET_PRECHECK_ONLY`). **Outcome → hook result:** `passed` → `pass`; `passed_with_warnings` → `warn` (code `RULES_WARNINGS`, the warn reason codes in `detail`); `held` → `warn` with code `RULES_HELD_<gate>` (for example `RULES_HELD_G06`), so the request can be approved but cannot execute until the hold clears; `blocked` → `fail` with the first failing gate's reason code. `gates_evaluated[]` lists the set's `gate_evaluation` ids.

**4. Threshold monitors and halts.**

- `threshold_monitor` rows (A04 core table) per vehicle per metric store `current`, `warn_at`, `block_at`, `state` (`ok | warning | breached`), `pretrade_block_on`, `counsel_pending`, `computed_from` (register version id) and `computed_at`. Definitions:
  - `holder_cap`: the largest holder group's units as a percentage of the cap units. `warning` when ≥ `holder_cap.warn_at_pct_of_cap` (450 of a 500-unit cap); a group exactly at the cap is `warning`, not a breach; `breached` when above the cap (501 or more), reachable only through a cap change, a forced or estate transfer or a supply change.
  - `foreign_pct`: foreign-person units over total; `warning` at `foreign.warn_bps`, `breached` at the vehicle's `foreign_block_bps` when set.
  - `member_count`: distinct members by `member_count.count_basis`; `warning` at ≥ `warn_at` (18), `breached` when > `s601ED_trigger` (21 or more).
  - `landholder_duty`: the largest holder group against the vehicle's state threshold; `warning` within 500 bps of it, `breached` at or above it.
  - `valuation_age`, `proof_of_property_age`: from A34's dates.

  | Monitor | Gate | Effect of `breached` on new actions | Effect while `counsel_pending` |
  |---|---|---|---|

  | `foreign_pct` | G06 | acquisitions by foreign persons fail `G06_FOREIGN_PCT_LIMIT` | warn only |
  | `valuation_age` | G20 | resale and go-live fail | - |
  | `proof_of_property_age` | G19 | go-live and new offers for the sponsor fail | - |
  | `member_count` | G07 (only when the vehicle's pre-trade block is on) | warning and alert only; with the block on, a new-holder acquisition past the trigger fails `G07_PRETRADE_MEMBER_COUNT` | warning only unless the block is on |

- **Halts (G10).** `registerHaltSource(name, fn: (vehicleId, now) => {halted, causes[]})` is exported from `index.ts`; G10 is the union of every registered source and names each cause and source in the verdict. A20 registers `recon_break`; this node registers `local_halt` over A04's `halt` core table (A48's text calls its record `halts`; A04's core table name `halt` is the one used here). **5. Simulator.**

- `POST /v1/rules/simulate` takes a proposed change (a new compliance-rule draft, a new pack, an override, or a hypothetical action) and returns, without writing any `evaluation_set` or `gate_evaluation` row: the gate verdicts the change would produce for every current holder of the vehicle, the holders who would be in breach with current units and units over the limit, the monitor states before and after, and the count of pending orders that would fail. A14 embeds the simulation result hash in the "Rule pack change", compliance-rule and override requests, and refuses approval of a request whose simulation is older than the latest register version (`SIMULATION_STALE`). The design's APR-2285 "Holders affected 0" is this output.
- **Output shaped by principal.** Investor (and the investor's agents): only hypothetical actions on their own account, and only their own verdicts; no holder list (`requiredScope` `rules.simulate.self`). Sponsor roles (and their agents): their own vehicles only; holders appear as pseudonymous references stable per vehicle (`H-` plus eight characters of a keyed hash), with units and units over the limit (`rules.simulate.tenant`). M10 staff (CCO, LEGL, REGO): the full list with investor ids (`rules.simulate.platform`). An agent never sees more than its human's shape. The buy stepper's live G07 line is `simulate` with `kind = order` and `dry_run = true` under the self shape.
- Simulation is deterministic for a given register version and pack, and runs under a 5-second budget for a 10,000-unit vehicle with up to 2,000 holders.

**6. Error, empty and edge behaviour.**

- No effective pack for a vehicle's regime: every evaluation fails `RULE_PACK_MISSING` and the vehicle cannot go live; the seed ships `AU-W-2026.1` effective from the seed as-of date.
- Two effective packs for one regime at the same instant is impossible: a partial unique index over `(regime) WHERE state = 'effective'`.
- A pack with `effective_from` in the future is `approved_pending_effect`; evaluations use the currently effective pack until the switch, and the switch is an audit event and emits `rules.pack.published {code, effective_from, vehicle_ids[], tenant_ids[]}` on the outbox so A43 notifies every sponsor using the pack (ADM-16 "Publish pack version").
- Clock: every evaluator takes `now` from the caller; the API passes the database transaction time, and replay passes the stored `evaluated_at`.
- Data: this node uses A04's core tables `rule_pack`, `compliance_rule`, `gate_evaluation`, `threshold_monitor` and `halt`, and creates through A04's module-schema registry only the tables wholly its own: `investor_override` (already in A04's map as an A19 registry table) and `evaluation_set`. It never creates a plural or second copy of a core table. The columns, trigger and index it needs on core tables (listed in the Specify step) are taken by A04 from this spec; any that are missing when this node starts are requested as an A04 follow-up loop (A04.x), never added by this node's migration.
- Audit: every pack, rule, override, pre-trade-block, lock-up and halt change and every `breached` transition writes one audit event through A10 with `approval_id` where one exists; `gate_evaluation` rows are their own append-only record, and the evaluation set id is carried in the audit event of the action they decided. When the maker of an M10 change (a pack draft, compliance-rule draft, override, lock-up or pre-trade block) is an agent, the audit event and the `rules.*` A14 request carry `actor_type = AGNT`, `token_id` and `on_behalf_of_id` (the D04 "agent <token> on behalf of <person>" record); the agent can only be maker, and A14's SoD counts it as its human.

## Node-specific challenges (node QA)

- Money and caps: an investor holding 120 units with an associate holding 380 places an order for 1 unit on a 10,000-unit vehicle capped at 5%: the evaluator that ignores associates passes it; the correct one fails G07 with `max_allowed_units = 0`. Also: an investor submits a 500-unit order and, while it sits unallocated in escrow, a second 1-unit order: the second fails at order time because open orders count. And two orders evaluated in parallel that each see the same pre-order state: both may pass at order time, but allocation and mint are new sets with `requireFresh`, and the second fails there.
- Compliance and immutability: a staff member with M10 write scope patches `parameters` on the effective `AU-W-2026.1` directly through the database role, or submits a new pack with `effective_from` earlier than now to retroactively pass an old order: both refused, and a replay of an evaluation from before the change still returns the old verdict with the old `rule_pack_code`.
- Phase leakage: with the phase flag off, a retail-regime vehicle is seeded and an order is evaluated: G05 must be `fail G05_PHASE_OFF`, never `not_applicable`; G21 must fail; and a set whose non-failing rows are only `not_applicable` must not proceed.
- Result semantics: a foreign person orders on a commercial vehicle with no FIRB clearance: the builder that treats `hold` as `warn` lets the order proceed; the correct outcome is `held`. An investor whose certificate expires in 12 days orders: the builder that treats every `warn` as a block stops them; the correct outcome is `passed_with_warnings`.
- Security and agents: an agent whose mandate covers vehicle A orders on vehicle B under a token that also carries the order scope: A12's middleware refuses `G22_VEHICLE_NOT_ALLOWED`, no other gate row and no evaluation set exist, and A12's row carries `on_behalf_of`. An agent posts `POST /v1/rules/evaluate` with a forged `facts` body claiming `whitelisted: true`: 403 (and 422 if a service principal did the same); nothing is stored. A service evaluates a 1-unit order and tries to execute 499 on that set: `RULES_ACTION_MISMATCH`. Separately, an agent acknowledgement under a standing consent covering IM v1 while IM v2 is effective: G12 fails `DISCLOSURE_VERSION_STALE`.
- Overrides: a 4E override for G13 or G21 is drafted: refused `OVERRIDE_NOT_PERMITTED` before it reaches A14. An override with `ends_at` yesterday, or whose approval request is `expired`, is still applied by a cached rule set; or a G07 override is applied to a G06 evaluation because the evaluator reads overrides by investor and not by gate.
- Halts and monitors: A20 opens a Sev1 recon-break halt through its registered source after a transfer's set was evaluated but before it executes; `assertPassed(..., {requireFresh: true})` must fail with G10 naming `recon_break`. A halt with scope `resale_board` must not fail a distribution line. A staff call to `openHalt` without criteria or an end date is refused. A register version with 21 lines where two lines belong to the same investor record counts 20 members (`warning`, not `breached`), while a person's individual and joint accounts count as two; the expected counts come from `member_count.count_basis`.
- Evaluator replacement: A41 registers G16 version 2 (or this node ships G04 version 2) after 1,000 sets were written with the baseline version 1: replay of the old sets still reproduces their stored results by running version 1; a builder that replays with the current evaluator reports false Sev1 mismatches.
- Design fidelity: the `buyGates` set returns six rows, or the G07 description lacks the percentage and cap, or the ADM-07 G17 verdict returns the phrases without the location, or the ONB-10 G04 row lacks `valid_until`, or the G01 description paraphrases "Reusable credential on wallet 0x7a3f…c91e": any of these fails the contract test the screen nodes reuse.
- Replay honesty: replay is implemented by reading the stored `result` back instead of re-running the evaluators; the node QA's mutated-evaluator probe (a G07 that adds 1 to the cap at the same version string) must make replay report a mismatch, and it will not if replay is a read.
