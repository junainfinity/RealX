# A103 - Runbook drills R1-R9 executed on the stack

**Every runbook A85 wrote is run as a scripted, timed drill on the compose stack, exactly as written, by the seeded staff personas: the nine incident runbooks R1-R9 (global pause and inflow freeze inside the 15-minute window with unpause only by `6E+Q` and the 2-hour ratification timer proven; agent-key compromise; a contract-migration rehearsal that reconciles the register 1:1; registry sync failure; valuation failure; payment-rail event; sanctions hit on a large holder without tipping off; court order or legal hold; operator cessation), plus the key-rotation drill in the custody sandbox, the break-glass drill (2-of-3, 4-hour expiry, review task), the agent kill-switch drill across all four tiers, and short drills of the other operational runbooks. A drill fails if any step cannot be executed as written. Each run leaves timings and evidence, is recorded through A48's drill route, and turns every finding into a fix item on the node that owns it. The testnet re-run of R1 and R3 is recorded in A86's pack.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Quality. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 18-30 agent-hours (build, challenge and verify loops). The gate needs two consecutive full `verify:drills` runs, each resetting the stack for fifteen drills plus the R1-lapse variant with real-time 15-minute windows, then the node QA's run, the mutation set and about ten plants (each re-running a drill from reset), O5's 80 tier measurements, re-runs after owner fixes and up to three fix loops. If the graph prefers smaller nodes, the natural split is: runner plus R1, R1-lapse, R2, R3 and O3 / R4-R9 / O1, O2 and O4-O6.

**Depends on:** [[A85 - Observability and runbooks]], [[A81 - End-to-end journeys- recovery, AML and planted breaks]], [[A80 - End-to-end journeys- sponsor and operations]], [[A48 - Halts, kill switches and wind-down]], [[A77 - Console- agent and API access (ADM-35)]], [[A15 - Custody sandbox adapter and policy engine P1-P10]], [[A11 - Authentication, sessions, RBAC and segregation of duties]]
**Unlocks:** [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised]]

**Oracle rule:** not an oracle node (`oracle: no`). No new rule is enforced and no cent, unit or key moves under code written here; every effect a drill causes is made by an oracle-tested owner (A12, A14, A15, A18, A20, A28, A40, A42, A48) through its public routes. But a drill that passes when an effect is missing would give the founder false confidence in the one moment that matters, so the node QA writes its Challenge material to `<workspace>\gauntlet\hidden\A103\` from this note alone before the build starts: the runbook mutation set (a row made impossible to execute, two rows swapped, a "done when" that is already true before the step, an operation id renamed, a human-only row given an MCP tool), the quiet-failure plants (one token that does not pause in time, one payout job that fires during a freeze, a burn that stops half-way through a migration, one investor-facing string that hints at a sanctions freeze, one agent tier that leaks), and the expected outcome of each. The builder never reads that folder. After the gate the cases are published so A88 re-runs them as regression ([[App Gauntlet]] §2).

This node builds no business behaviour, no route, no table and no screen. It proves that a person woken at 3 a.m. can follow the runbooks A85 wrote, on the system AM1-AM7 built, and that each runbook does what it says in the time it says. When a runbook and the system disagree, the drill does not choose: it fails, and the disagreement becomes a fix item on the runbook (A85), the seeded runbook data (A48) or the module. This plan is not legal advice; every regulator-notification step inside a drill is a counsel question, carried as written ("notify as counsel directs") and marked in the report.

## Build brief

**1. Scope, placement and what is reused (no duplication)**

- Two owned folders. `e2e/drills/` holds the drill runner, the runbook parser, the check library, the persona and agent actors, one script per drill, the parity probes, the evidence writer and the node's own tests. `docs/drills/` holds the drill plan, the generated per-drill reports, the findings register and the run bundles (`docs/drills/runs/`). Nothing is added under `services/`, `apps/`, `packages/`, `infra/` or `docs/runbooks/`. There is no migration and no `/v1` route. A lint in the node's tests refuses any import of `@realx/db`, `pg`, `drizzle-orm` or a module's internal path from `e2e/drills/`: a drill acts only through the SDK, the MCP server, the built screens and the documented `/__test/*` and sandbox-control hooks, as a person or an agent would.
- The runbooks are the script. The runner reads A85's `docs/runbooks/*.md` (frontmatter and the checklist tables with their fixed column order: `[ ] | n | role | screen | API operation id | MCP tool or "human only" | policy code | done when | time budget`) and executes rows in order. It also uses A85's `status.json` and `status-map.json` for "done when" facts; A48's `GET /v1/runbooks`, `POST /v1/runbooks/{id}/declare`, `POST /v1/incidents/{id}/actions/{n}/act | skip`, `POST /v1/incidents/{id}/close` and `POST /v1/runbooks/{id}/drills`; A48's kill switches and halts; A14's requests, decisions and ratification; A15's custody console actions and `SandboxControl` (`advance-timelock`); A28's token operations; A20's runs and breaks; A18's certified versions, audited exports and `register.resync` request; A17's bank sandbox; A40's holds; A42's restrictions; A34's property transitions; A11's sessions and break-glass; A12's tokens and introspection; A101's per-user and per-tenant holds; A09's `POST /__test/clock/advance`; A06's seeded personas, agent principals and planted scenarios; A23's `stack:*` scripts and A85's `obs:up`. Persona sign-in, page objects and the sandbox authenticator (passkey for investors and sponsor users, hardware-attested key for staff) are imported from the A78, A79, A80 and A81 suites through their exported helpers, never copied.
- Requested from other nodes as their own follow-up loops before this build starts (the pattern A12 uses with A04.1), never faked here:
  - (a) Sandbox scenarios the drills trigger through `SandboxControl.trigger`, each a data-only addition with a conformance test in the owning adapter: A17 `rail-outage` and `rail-restore` (NPP and PayTo unavailable, then back), A18 `registry-ack-withhold` and `registry-ack-release`, A15 `signer-compromised` (marks one V2 signer's key reference as compromised for the P-rule checks). A06 already plants the stale valuation, the registry drift and the unknown holder. A22's existing `trigger('list-update', { addEntries })` serves R7.
  - (b) The SVCA principal `svc-drill` in A11's principal seed with only `drills:record` on M01 and read cells, which A48 already names ("the A103 service principal").
  - (c) **Runbook R3 and SM-06.** Runbook R3 pauses the token first, but SM-06 (product map `data_states.py`, A03's table, A27's answer and A28's driver) allows only `active → migrating`, so the migration row would be refused `409 transition_not_allowed` after the pause. Requested decision, as a follow-up loop on A03, A27, A28, A48 and A85: add `paused → migrating` (`6E+Q`, V1 owner quorum, "critical flaw while paused") to SM-06, so R3's old-token path is `active → paused → migrating → retired`. The alternative (drop the pause row from R3) is weaker, because a token with a critical flaw would stay transferable until the migration starts. Until the loop lands, R3 cannot pass and this is listed at Specify.
  - (d) **Runbook R4 force re-sync policy, settled here.** The product map (ADM-17, "Force re-sync with the registry", maker REGO, checker head of operations) is the requirement, so the re-sync is a two-person `4E`: REGO maker, head of operations checker (A18's recorded interim checker is CCO, because "head of operations" is not one of A03's roles). A18 already defines this as `POST /v1/register/vehicles/{vehicleId}/resync` (`register.resync`, `4E` through A14). A20's `POST /v1/recon/vehicles/{id}/resync`, which A73 describes as a REGO action taken alone, contradicts it. Requested follow-up loops: A20 (its route either opens A18's `4E` request through A14 or is removed; A73's row then follows A20), A03 (the `register.resync` policy row with the checker), and A85 (runbook R4's row names A18's operation id and `4E`). The drill then checks that REGO acting alone is refused and that the `4E` path executes.
  - (e) **Runbook R5 phase.** A48 seeds "R5 valuation failure (P2)", which would make the whole runbook `skipped_phase` in P1. The rows that exist in P1 are: the `valuation_stale` halt, the G20 refusal of new offers and mints, and the HaltModule set and clear. Only the resale-board rows are P2. Requested follow-up on A48 (per-row `phase`, runbook `phase: P1`) and A85 (the same phases in the R5 file). Until then R5 is a known disagreement at Specify.
  - (f) **Runbook R9 retention.** A48 places the retention row only at `exit_approved`, which needs the P1 exit track (a `4E` proposal with a trustee resolution, then `6E` approval) and cannot be reached in a drill without a real sale decision. Requested follow-up on A48: the R9 "retention flagged" action places the 7-year retention row on every vehicle when it is acted, independent of the exit state (the `exit_approved` placement stays and is idempotent with it), and A85's R9 row names that action. R9 does not drive any vehicle through the exit track.
  - (g) **A second API process.** A23 runs one `api` replica (A78 §1). The multi-process checks in R1, R2 and O5 need two. This node adds `e2e/drills/compose.drills.yml`, inside its own folder and the same way A84 adds `api-1`/`api-2` in `e2e/perf/`: it includes A23's compose file and adds `api-2` (same image, same environment, its own port, no load balancer). Nothing under `infra/` changes. Preflight checks that both instances answer with distinct instance ids and the same commit.
  - If a loop is refused, this node escalates instead of working around it. A drill never writes a row, flips a flag or edits a fixture to get past a step.
- Commands, registered through A01's script-registration convention: `npm run drill -- <id> [--env local|testnet] [--seed <s>] [--keep]` (one drill; ids `R1`-`R9`, `R1-lapse`, `O1`-`O6`), `npm run drills` (all sixteen in the fixed order of `docs/drills/PLAN.md`), `npm run drills:report` (regenerates the reports and the findings register from the run bundles), and `verify:drills` (for each drill: `stack:reset`, `stack:up`, the `api-2` overlay, `obs:up`, seed, preflight, run, collect evidence, the in-drill A48 record checks, `stack:down`), which is what the gauntlet runs. Each drill starts from a fresh reset, because R1, R3 and R9 change the whole platform. `R1-lapse` is a named variant of runbook R1 (§3), with its own reset, bundle and A48 drill record.
- Naming: the incident runbooks R1-R9 are not the reconciliation rules R1-R18 of A20. Every report, finding and log line writes "runbook R4" or "recon rule R17" in full, and the runner refuses a runbook file whose `id` does not match `^(R[1-9]|O[1-6])$`.

**2. The runner: execute the row as written, time it, prove it, probe the agent lane**

- Preflight (`DRILL_PREFLIGHT` names the failing check and the drill does not start): A23's `stack:check` green; `api` and `api-2` both answer with distinct instance ids and the same commit; the `obs` profile up; the drill's `PLAN.md` fixtures present (including the non-vacuity fixtures of this section); every `realx_exporter_read_up` gauge 1; chain id 31337 (or 84532 with `--env testnet`); every A46 integration environment `sandbox`; `status.json` shows no halt, no engaged switch and no open Sev1 before the trigger; the runbook passes A85's lint at the same commit; the A48 seed row for the runbook has the same id, title and ordered action codes as the file (the drill refuses to run a runbook that has drifted from the data).
- Row resolution, with no knowledge that is not in the runbook: `role` becomes the seeded persona holding that role (a role with no persona fails the row `DRILL_ROLE_UNRESOLVED`); `screen` becomes the imported page object for that product-map code, and the row is driven through the screen in Playwright when a screen is named; `API operation id` becomes the SDK call, which the runner also uses to read the result; `policy code` sets the expected A14 path (`SGL+R` acts at once and opens a ratification clock; `4E`, `6E` and `6E+Q` open requests that a different persona decides; `6E+Q` also collects the custody quorum through A15's console actions under each signer's own hardware-key login); `done when` becomes one check from a closed library (an A10 audit action with the expected object and approval id, an A13 alert type and state, a flag value from `GET /v1/kill-switches` or `/perimeter/public`, a `status.json` field by its `status-map.json` operation id, or a direct chain read through A27 for pause state, supply and balances); `time budget` becomes the step's timer. A per-drill script (`drills/R1.drill.ts` and so on) may add only four things: the trigger, the fixture choices (which vehicle, which holder), after-state assertions, and declared **negative probes and plants**. It may not add, skip, reorder or replace a step.
- **Negative probes and plants.** Some checks need calls that no runbook row contains: wrong-path attempts (R1's five refused unpause routes, R4's REGO-alone re-sync, O4's four refused activations, O3's overdue-hot-key op and signer-set change), plants (R1's PayID deposit during the freeze, R4's holding change requested while the ack is withheld), extra proofs (R2's replacement-agent test op) and load (O5's background agent traffic and its 20 engage-and-release measurements per tier). Each one is declared for its drill in `docs/drills/PLAN.md` with its kind (`agent-lane`, `wrong-path`, `plant`, `proof` or `load`), the call, the persona or agent making it, when it runs relative to the rows, and the expected refusal code or effect. They run outside the row sequence, are logged in `probes.jsonl` with their kind, and are left out of the operation-id diff; a second diff checks them against `PLAN.md` instead (nothing undeclared, nothing declared and missing, each with its expected outcome). A probe or plant never moves the stack past a row: it may not make a "done when" true.
- **Non-vacuity.** Every after-state assertion must record at least one observed event of its kind (a skipped job fire, a held receipt, a queued payout, a stopped batch line, a refused call), or the drill fails with `DRILL_VACUOUS_CHECK`. The fixtures that make this possible are mandatory in `PLAN.md` and checked at preflight: at least one distribution run and one PayID or PayTo receipt due inside R1's window; at least two payouts due during R6's outage; a distribution run mid-batch when R8's court order is recorded; and, for R7, at least one other holder's line on the same distribution run. The observed counts go into `app/evidence/A103.json`.
- A row that cannot be executed as written stops the drill with `DRILL_STEP_NOT_EXECUTABLE` and a finding. This covers an operation id that does not exist in `packages/sdk/openapi.json`, a persona whose role lacks the cell, a screen without the named action, a policy code the route does not open, a "done when" that is already true before the step (the check proves nothing), a "done when" still false at twice the time budget, or a row a person could read two ways. A failed write is never retried with a new idempotency key. A network retry reuses the same key and is logged.
- Two clocks, kept apart. Wall time (monotonic) measures every step and every window the runbooks name ("first 15 minutes", "next 24 hours" for the parts that run in real time). The injectable clock (A09's `/__test/clock/advance`) and A15's `advance-timelock` jump only over waits a row names: the 2-hour ratification, the 4-hour escalation, the 48-hour and 24-hour custody timelocks, the 24-hour registry SLA, the 4-hour break-glass expiry, the 5-business-day review due date. Every jump is recorded with its reason. A jump inside a timed window is refused with `DRILL_ADVANCE_IN_WINDOW`, so a clock trick can never make a window pass. Timings are recomputed afterwards from A10 audit timestamps and must agree with the runner within 2 seconds.
- Agent-lane probes (founder requirement D04, gate G22), on every row. For a row marked "human only", the runner first makes the same call with the acting persona's own staff agent token, through the SDK and through the MCP server, and expects the specific refusal the owner defines: `APR_CHECKER_MUST_BE_HUMAN` (A14) for acts, checks, ratifications and custody signatures; `INC_HUMAN_ONLY` (A48) for declare; `self_subject` (A21) for the `agents.traffic` release; `G22_AGENT_NEVER_CHECKER` (A12); and `AGNT_NOT_ALLOWED` (A11) for break-glass. Only then does the human act. A probe that succeeds is a Critical finding and stops the drill, and the act it performed is recorded. For a row that names an MCP tool, the step itself is carried out by the persona's agent through the MCP server, not by the person. This proves that the agent lane written in the runbook works. The proof is not the runner's own log: for every agent row the A10 audit event must show `actor` = the token and `on_behalf_of` = the persona, and the same event must appear in that persona's own activity read ("agent <token> on behalf of <person>"). A read-only staff agent also follows every drill through the API and must see every `status.json` fact the humans used.
- Evidence per run, in `docs/drills/runs/<drill-id>/<env>-<yyyymmdd-hhmm>-<seed>/`: `steps.jsonl` (row number, persona role, principal kind, token id when an agent acted, operation id, request id, trace id, approval id, custody op id, tx hash, started, ended, budget, result, the done-when evidence), `probes.jsonl`, `clock.jsonl` (every jump and its reason), `status-before.json` and `status-after.json`, one screenshot and one DOM-and-state capture per screen row, A13 alerts raised with their clocks, audit event ids with A10's chain verification result after the drill, the A48 drill record id, and a `manifest.json` with the commit, seed, runbook file hashes, A48 `runbooks.ts` hash and every file's SHA-256. No token secret, passkey assertion, cookie or key material is ever written; a leak scan (A12's token pattern, bearer values, 64-hex key shapes, A06 fixture PII) runs over the bundle before it is kept.
- Recording: at the end of every drill, pass or fail, the runner calls A48's `POST /v1/runbooks/{id}/drills` as `svc-drill` with `environment`, `steps[]` (row, result, duration), `duration`, `findings[]` (ids) and `passed`. A passed drill sets `last_drilled_at` and clears A48's Sev4 `runbook.drill_due`. A failed drill is recorded as failed, never left out. Because every reset wipes these records, the runner checks them inside each drill, before `stack:down`: it reads the drill record back, reads the runbook's `last_drilled_at`, and confirms `runbook.drill_due` is cleared (or, for a failed drill, still open), and stores those reads in the drill's bundle as `a48-record.json`.
- **Journey J20 signals.** For every drill whose trigger is something the operator daily run would find, the runner asserts that the trigger first appears as its J20 step's signal before the incident is declared, and writes the A13 alert id into `steps.jsonl`: step 2 chain alert on ADM-02 (O1); step 4 break on ADM-17 (R1's `unknown_holder`, R4's `pending_ack`, O2's drift); step 5 connector down on ADM-32 (R6, O6); step 9 on ADM-29 (R5's stale valuation); step 12 launch flags on ADM-34 (R1's restore criteria). Drills whose trigger is outside the daily run (R2, R3, R7, R8, R9, O3, O4, O5) are marked "not a J20 signal" in `PLAN.md`.
- Reports and findings: `npm run drills:report` generates `docs/drills/<id>.md` for each drill: what was triggered, each row with its time against budget, clock jumps, probes, after-state and findings, all in plain English with no acronym left unexpanded on first use. It also generates `docs/drills/findings.md`, the register: `FND-A103-<n>`, drill, row, severity (Critical, High, Medium, Low), the owner node (resolved from the graph's owned paths, or A85 for runbook text and A48 for seeded runbook data), the fix item as one sentence, state (`open`, `fixed`, `verified`) and the run that verified it. "Verified" means the owner's fix loop passed and the drill re-ran clean from a fresh reset. Only the user can accept a finding as known and deferred. The builder cannot.
- Empty and error states: a runbook file missing gives `DRILL_RUNBOOK_MISSING`. A row whose phase is later than `PHASE` (R5's resale-board rows in P2, R6's stablecoin half in P3) is recorded as `skipped_phase` with A48's `RB_PHASE`, counted, listed in the report, and never counted as a pass. A drill killed halfway is never resumed: its bundle is kept marked `aborted` and the drill re-runs from a reset. An A13 or A43 outage during a drill is itself a finding, because protection must not depend on notices (A48: "protection first, notice second").

**3. The incident drills R1-R9 (what each proves beyond its own "done when" cells)**

- **Runbook R1, global pause and inflow freeze.** Trigger: A06's unknown-holder plant (transfers to unregistered wallets on the local chain) makes A20 raise a Sev1 `unknown_holder` break. The window runs from the `incident.declared` audit event to the last "first 15 minutes" check, and it must close within 15 minutes of wall time. Rows run as written: the incident is declared from ADM-01's Declare incident action (A66), each token pause is acted from the incident checklist or ADM-01's Emergency pause deep link on ADM-14 (A72, A28's `token.pause`), and the two money switches are engaged on ADM-34 (A69), each confirmed through A53's hardware-key confirmation. After the window, the runner checks the following. Every token in A27's manifest that was `active` at window end, not only those known at the start, reads `paused()` true on chain and SM-06 `paused`, each with its own `SGL+R` approval id bound to a V3 custody op. `platform.marketplace_suspend` is on, every live offering is paused under A48's code, and `/perimeter/public` reports `marketplace_suspended`. `platform.inflow_freeze` is on: the planted PayID deposit (a declared plant) during the freeze is held unapplied and no order moves `awaiting_funds → funded`. `agents.traffic` is off, and the next agent call on both API processes (`api` and `api-2`) gets 423 `AGENTS_PAUSED` with `tier: platform`. Every vehicle has a distribution hold, the payout job fires scheduled inside the window by the mandatory fixture are skipped with the reason in A46's job runs (at least one observed), and no debit leaves the bank sandbox (read from the bank sandbox's own transaction list). A full A20 run over every vehicle completed. Ratification: every act is ratified by a persona other than its actor. Restore: the unpause is attempted, as five declared `wrong-path` probes, as `SGL+R` (refused `APR_SGLR_NOT_PROTECTIVE`), as `4E`, by the engaging person, by any agent, and while the restore criteria fail (recon not clean or a Sev1 incident open). Each attempt must be refused. It succeeds only as `6E+Q` (CCO → SECO + CFO, through custody). The switch releases run as `4E`, never by the engager (`KS_ACTOR_CANNOT_RELEASE`). After release, the held receipts match with the bank-ledger delta at 0 cents, and the incident closes (CCO → CEO, `4E`) only with no action `pending`.
- **Variant R1-lapse (runbook R1, ratification lapse).** Its own reset, bundle and A48 drill record. It runs runbook R1's rows up to the end of the first 15 minutes exactly as R1 does, except that the ratification row `PLAN.md` names for one act (the `platform.inflow_freeze` engage) is withheld. That row is recorded as `withheld_by_variant`, never as a pass, and the operation-id diff expects exactly that one omission. Advancing 2 hours raises Sev2 `approval.unratified`, and advancing to 4 hours upgrades it to Sev1 with CEO as owner. The ADM-34 banner shows the red "Unratified" pill, the switch stays engaged and nothing is lifted. The variant then ratifies late, as the runbook's escalation row says, and ends; it does not repeat R1's restore.
- **Runbook R2, agent-key compromise.** Trigger: A15 `signer-compromised` on one V2 token-agent signer, whose person also holds a console session and a staff API token. Rows: A15 vault freeze and signer revocation (SECO); `token.pause` where the key holds agent rights; the agent removed and re-added through AgentGateway under the V1 owner quorum (3-of-5, `6E+Q`, 48-hour timelock jumped with `advance-timelock`); that person's sessions revoked through A11 and tokens through A12. The runner checks four things. The compromised key reference cannot sign any op after revocation (A15's policy refusal is recorded). The old agent address holds no agent role on chain (direct read), and recon rule R1 (roles) is clean. The replacement agent signs a fresh test op under a new approval id (a declared `proof` probe). The first request after revocation with the person's token is refused `TOKEN_REVOKED` on both API processes (`api` and `api-2`), and their session is gone. No op in the window carries a signature from the revoked key.
- **Runbook R3, contract migration rehearsal.** Trigger: a declared critical flaw on one seeded vehicle's token. Rows: pause; snapshot (A18 certified `RegisterVersion` and A20's snapshot at block N); redeploy a new suite through the T-REX factory (A28 `deploy`, `6E+Q`, V1); SM-06 old token `paused → migrating` (the transition requested in §1(c); until it exists this row fails `DRILL_STEP_NOT_EXECUTABLE` and R3 cannot pass); mint not-from-file on the new token per holder equal to register units (TOKO → CFO + CCO + CEO, `6E+Q`, one approval id per batch as A28 defines); burn on the old token per holder; old token `retired`. The redeploy's `deploy_requested` step needs "tests and audit attached"; the sandbox stand-in for HG-AUDIT is A28's audit slot marked `open (HG-AUDIT)` against A24's `contracts/src/AUDIT-SCOPE.md`, and the report says so. After-state: new supply = register total = old supply before migration; old supply 0; every holder's new balance equals their register units (1:1); frozen units and lock-in dates carried over; zero unknown holders; A20 targeted runs clean on both tokens. The new token keeps the compliance rules: a direct chain read lists the compliance modules bound to the new token and their parameters (holder cap for G07, lock-up for G08, residency, and the rest A24 binds), and they equal the old token's, one for one; the new token's identity registry address equals the old token's. The old token's SM-06 audit events read `active → paused → migrating → retired` in order, and the new token's read `designed → sandbox_deployed → deploy_requested → deployed → configured → issuing → active`, one A10 event per transition. An indexer walk over every block of the migration shows that old plus new supply never exceeded the register total at any confirmed block.
- **Runbook R4, registry sync failure.** Trigger: A18 `registry-ack-withhold` on one vehicle. A declared plant then requests a holding change for that vehicle, and the runner checks that nothing reaches the chain without an ack: A28 holds the op and a direct chain read shows no transaction. Recon rule R17 shows `pending_ack`, and advancing past the 24-hour SLA halts resale for the vehicle under G10 with its criterion and end date. The forced re-sync is `4E`, as settled in §1(d): REGO drafts A18's `register.resync` and the head of operations (interim CCO) approves through A14. A declared `wrong-path` probe first tries the re-sync as REGO acting alone and must be refused; then the `4E` path must execute. Until the follow-up loops on A20, A03 and A85 land, a row whose route does not open `4E` fails `DRILL_STEP_NOT_EXECUTABLE` with a finding on those three nodes. Restore happens only at zero pending instructions and a clean three-way run. The halt clears only on A20's `recon.halt.cleared`, and the chain HaltModule clears before the record does.
