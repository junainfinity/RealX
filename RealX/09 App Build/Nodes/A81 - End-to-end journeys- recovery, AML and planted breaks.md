# A81 - End-to-end journeys: recovery, AML and planted breaks

**The Playwright and Vitest suite that proves the three risk paths work as one product on the running stack. It covers J09 lost-phone recovery: the smart-wallet path first, then the token-level fallback with re-verification, legal review, two approvals, the frozen old wallet, the 48-hour notice to the old channels, the custody quorum signature, the register update and a clean targeted reconciliation. It covers J10 AML alert to SMR: monitoring alert, triage, case, restriction that acts at once and is ratified within 2 hours, SMR decision and filing on the business-day clock, and exit. The tipping-off guard is checked from the investor side, the support side and the token-scope side. It also covers the simulator's four planted drifts (registry drift, unknown on-chain holder, one-cent bank delta, stale valuation). For each drift the suite proves that the right alert opens, the right trust and only that trust is halted, mint and payout are refused where the halt list says so, the break shows on ADM-17, PUB-08 and SPN-08 as each surface's rule requires, and the break closes only on a clean re-run. Every step is taken through the built screens, with human acts as passkey or hardware-key assertions, and every delegable step is repeated through the SDK and the MCP server with identical gate results.**

## Build brief

This node writes no product behaviour and draws no screen. It owns a Playwright and Vitest suite, drift and clock drivers, a tipping-off comparer, screenshot captures and an evidence writer, all under `e2e/risk/`. Every call goes through one of three routes: the browser against the running `web` and `console` containers, `packages/sdk` (A09) against the running `api`, or `packages/mcp` (A104) against the running `mcp` server. The only exceptions are the sandbox and test controls listed in §1, which exist only in `RUN_MODE=local|test`. Nothing in `e2e/risk/` imports from `services/*`, `packages/db`, any adapter or any `apps/*` source file, and a lint in `npm run verify` fails if it does. Human acts go through A11's local simulated authenticator (`/__test/*`): investor passkey sign-in and step-up, staff hardware-key approvals, ratifications, custody signatures under each signer's own login, and the MLRO's tipping-off check and SMR decision. Every action therefore reaches the same routes, gates, approval policies and audit events a person would.

**2. J09 Lost phone: wallet recovery (`e2e/risk/j09/`)**

Six ordered specs. Two state machines are involved, as A29 and A28 settled them: A29's internal wallet-recovery machine `WR` for the smart-wallet path (it is not SM-13 and adds nothing to A03's table), and A28's `transfer_requests`, which run SM-13 one to one for the token-level fallback and for forced transfers. Each checkpoint reads the WR or SM-13 state, approval ids, custody op ids and audit event ids through the SDK after every step. Error codes below are A29's and A28's; where either node's final code list differs, the owning node wins and this note is corrected at Specify.

- **J09-A, smart-wallet path first (A29 `WR`).** Alex has lost every wallet passkey (the fixture removes his three owner credentials from the simulated authenticator) but still holds a login passkey on his laptop.
  1. Alex signs in with that login passkey. On ACC-02 he starts recovery (`POST /v1/wallets/recovery`, WR `requested`). His wallet shows `recovery_pending` on POR-06, and his session keys are revoked by the separate `wallet.session_key.revoke` custody op (`AUTO`, its own approval id).
  2. SUPP triages on ADM-15 (`requested -> triage -> identity_reverification`).
  3. Re-verification by liveness and document through the identity sandbox (`-> awaiting_new_key`). If the case is referred, KYCA decides it on ADM-10 with a reason code.
  4. Alex registers the new wallet passkey on ACC-02 (`POST .../new-key`).
  5. KYCA re-verifies the record and submits "Approve smart-wallet recovery" (`wallet.recovery.approve`, `4E`, KYCA → CCO) from ADM-13's recovery panel (A72), which is the product map's J09 step 3 screen (`-> compliance_approval`). CCO approves on ADM-30 with a hardware-key assertion. The ADM-13 row, the ADM-30 row, the ADM-14 custody op and the audit events carry one approval id.
  6. The RealX guardian's `proposeOwner` custody op is signed under that id (`-> proposing`), and the indexer's `RecoveryProposed` moves the request to `waiting_period`. The notice goes to every channel in `channel_snapshot`. The notices are read from the captured inbox: one per channel kind, each with the single-use cancel link. ADM-13's waiting-period timeline and ACC-02's wait show the same `timelock_until`.
  7. The clock is advanced to 47 h 59 min: `wallet.recovery.execute` is refused `RECOVERY_TIMELOCK_ACTIVE`. At 48 h the suite advances one watcher tick: `executing`, `confirmed` on the indexer's `RecoveryExecuted`, then `closed` after A18's read shows the register's wallet reference unchanged and A20's targeted run is clean.
  8. POR-06 shows the same tokens under the same address with the new passkey, and the old passkeys are gone. ACC-02's stepper ("Verify you, Guardian, Wait 48 h, New passkey", A50's extension) shows each step complete. The captured inbox holds the recovery-complete notice to Alex (J09's closing "notifies the investor").
- **J09-B, every device lost, then the token-level fallback.**
  1. **Login recovery first (A11 §9, non-delegable, person present).** The persona has no credential left. It follows A11's lost-login-passkey flow: `POST /v1/auth/recovery/start`, the magic link from the captured inbox, liveness plus document through the identity sandbox (`reverified`), the cooling period advanced by the clock, then a new login passkey. The same calls made with the persona's pre-existing `rx_inv_` token are refused `AGNT_NOT_ALLOWED` before scope evaluation. `auth.recovery.completed` is published once, and the pre-existing token then fails with `TOKEN_REVOKED` (A12). A new `rx_inv_` token is created after sign-in with a fresh assertion for the agent-side checks below. The suite asserts the order of the audit events: `auth.recovery.started`, `auth.recovery.reverified`, `auth.recovery.completed`, then `wallet.recovery.requested`.
  2. **Smart-wallet attempt.** The persona starts `POST /v1/wallets/recovery` and the WR request runs as in J09-A up to `waiting_period`. The bundler sandbox is set to revert the recovery execution twice, so at 48 h the request moves `executing -> unrecoverable` with the reverted transaction hashes recorded as evidence. This is how "smart-wallet recovery is attempted first" is proven from data.
  3. **Handoff.** A new passkey wallet is created. `POST /recovery/{id}/handoff` is tried before A31 registers it and is refused `RECOVERY_NEW_WALLET_UNREGISTERED`. After A31 registers it, the handoff opens A28's `lost_wallet` transfer request and WR moves to `handed_off`.
  4. **SM-13.** `requested -> triage -> identity_reverification` (SUPP on ADM-15), `-> legal_review` (KYCA's re-verification result), `-> compliance_approval` (KYCA's legal-review record for `lost_wallet`), `-> checker_approval` (CCO on ADM-30), then CFO and TP-RE approve under `6E+Q` (`recovery`, `recoveryAddress`).
  5. TOKO's freeze of the old wallet (`setAddressFrozen(true)`) appears on ADM-14 and is confirmed by the quorum (`-> old_wallet_frozen`). SPN-08 now shows that holder as "Frozen" with no reason, and POR-06 shows the frozen amount with the generic reason.
  6. The notice goes out to the old channels (`-> timelock`), and the 48 h wait runs on ADM-15's countdown.
  7. The TP-SIGN signers sign `recoveryAddress(lost, new, onchainID)` on ADM-14, each under their own login. The SignatureMeter moves 1 of 3, then 2 of 3, and Broadcast is enabled only at 2 of 3 (V2 is 2-of-3). The request moves `timelock -> executing -> confirmed`.
  8. The register instruction moves the units to the new wallet reference under the same approval id (`register_updated` on the registry ack, visible on ADM-17 and SPN-08).
  9. The targeted reconciliation run completes clean, and only then does the request move to `closed`.
  10. Final checks: old wallet balance 0, new wallet balance equal to the old one, total supply unchanged, register units unchanged, POR-06 shows the tokens in the new wallet, and the captured inbox holds the recovery-complete notice.
- **J09-C, dispute during the wait.**
  - **Smart-wallet path.** A recovery for Alex is started from a second session while he still holds his wallet passkeys (the "someone else started it" case) and reaches `waiting_period`. From his other signed-in device he cancels on ACC-02, and a second run uses the notice's cancel link instead. Results: `waiting_period -> disputed`; the on-chain proposal is vetoed through `POST /recovery/{id}/veto` with his owner passkey assertion; a Sev2 alert goes to MLRO and SECO on ADM-02; the wallet stays `recovery_pending`; LEGL records the dispute review and CCO decides `disputed -> rejected`; an execution attempt at T+48 h is refused (`RECOVERY_DISPUTED`).
  - **Fallback path (SM-13).** On a second transfer request driven to `timelock` (a `divorce` or `error` type for a seeded holder, chosen at Specify, so no second full recovery is needed), SUPP records the holder's objection (`timelock -> disputed`, the op cancelled and its approval id refused by A15), LEGL reopens review (`disputed -> legal_review`) and LEGL or CCO rejects (`legal_review -> rejected`). The quorum's signature at T+48 h is refused.
- **J09-D, re-verification fails.** The identity sandbox's reject scenario moves the WR request `identity_reverification -> rejected` with the reason shown to staff, and, on a `lost_wallet` transfer request, KYCA's `fail` result moves SM-13 `identity_reverification -> rejected`. The investor sees the support path on ACC-02, and nothing moves on chain.
- **J09-E, court-order waiver (SM-13).** LEGL opens a `court_order` transfer request for the court-order persona with the court document hash. It runs `requested -> triage -> legal_review` (the triage route for non-recovery types) `-> compliance_approval -> checker_approval`. Refusals first, each asserted with A28's code: the CCO's decision alone; both decisions without the court document (`TOP_WAIVER_NEEDS_COURT_ORDER`); a waiver approval made for another request; the CEO's agent token as the second decision (`APR_CHECKER_MUST_BE_HUMAN`). Then a valid waiver (CCO and CEO, two hardware-key decisions, A28's `court_order_waiver` request, `6E`) moves `checker_approval -> executing` with no old-wallet freeze and no timelock. The quorum signs, and the request runs `executing -> confirmed -> register_updated -> closed` after a clean targeted run. Two further refusals: a waiver on a `lost_wallet` request is refused as A28's `waivable_types` row says (proposed seed: `TOP_WAIVER_TYPE_NOT_WAIVABLE`; the suite asserts the row, never restates it), and a waiver on a smart-wallet WR request is refused `RECOVERY_NO_WAIVER` with the message that a court order takes the token fallback.
- **J09-F, the seeded estate case.** The design's OP-7731 (forced transfer under APR-2288, 1 signature of the 2 needed, 3 signers) is completed from its seeded SM-13 `timelock` state, whose `timelock_until` is already before `AS_OF`. The second eligible V2 signer signs on ADM-14 (the op flips to `signed` and Broadcast is enabled), the request moves `executing -> confirmed`, the register instruction is acknowledged (`register_updated`), the targeted run is clean and the request is `closed`. Expected effects, from A28's OP-7731 seed: exactly 12 units move from `0x4b…19` to `0x9e…a2` in Bay Road Apartment; SPN-08's "Estate of H. Lowe" row keeps 48 units (its freeze status is whatever A28's seed and op leave, asserted against the Challenge material); a new 12-unit holder row appears for `0x9e…a2`; total supply and total register units are unchanged; the estate wallet's balance falls by 12 and the new holder's rises by 12.
- **Agent side of J09 (D04).** The investor's `rx_inv_` token calls `POST /v1/wallets/recovery`, the new-key route, the veto and cancel routes, the guardian routes and A11's `/v1/auth/recovery/*` routes as SDK calls and as MCP tools called by operation id. Each is refused `AGNT_NOT_ALLOWED` before scope evaluation, and none appears in the token's MCP tool list. While the request is open, the token's reads (`GET /v1/wallets/me`, holdings, activity) work, and every on-chain act under the mandate is refused with `WALLET_RECOVERY_PENDING`. Staff tokens:
  - KYCA's agent may draft `wallet.recovery.approve` as maker from ADM-13's API, and ADM-30 shows "submitted by agent on behalf of".
  - CCO's agent presented as checker is refused `APR_CHECKER_MUST_BE_HUMAN`.
  - TOKO's agent may prepare the freeze op and can never sign it: the signing call is refused before scope evaluation with A15's `P9_TOKEN_CREDENTIAL` or `P9_AGENT_PRINCIPAL` (whichever A15 raises for the credential presented), and its G22 gate evaluation carries `G22_AGENT_NEVER_CHECKER`.
  - SUPP's agent may triage in ADM-15's API only if A03's `delegable.ts` says so. The suite asserts whatever that row says and never restates it.

**3. J10 AML alert to SMR, with the tipping-off guard (`e2e/risk/j10/`)**

Four specs plus the tipping-off comparer. Each J10 spec starts from its own `stack:reset` and A06's baseline and uses its own fresh, unrestricted subject (§1), so no spec's result depends on a restriction another spec left behind. Case content stays inside the staff views allowed below, and the suite never prints it into the evidence. The SM-11 rules are A42's: the live restriction is the `aml_restriction` row, `account_restricted -> investigating` is taken only by `POST .../resume` (or by a lift's effector) and keeps the restriction in force, and `no_file -> case_closed` and `post_filing_monitoring -> case_closed` are refused `AML_RESTRICTION_ACTIVE` while a linked restriction is active.

- **J10-A, third-party deposits to exit (subject S1).**
  1. Six deposits from third-party payer names reach S1 through the bank sandbox (A06's `aml-third-party-deposits` shape, applied to the clean subject). The clock advances past one `screening.monitor` tick, and one `third_party_deposit` alert (not six) appears on ADM-25's triage list with its score (`alert_new`).
  2. KYCA triages and escalates with a reason code (`alert_new -> triage -> case_open`), and the ADM-25 nav badge count rises by one.
  3. The MLRO takes the case with `suspicion = formed` (`case_open -> investigating`), and the SMR clock opens (`smr_3bd`).
  4. The MLRO completes the tipping-off checklist with a hardware-key assertion, then sends an RFI from the approved template (`investigating -> rfi_customer`). A second RFI attempted with no check less than 24 h old is refused `AML_TIPPING_OFF_CHECK_REQUIRED`. The investor receives only the approved template text in the captured inbox. The investor uploads the document on ACC-04, and the case returns to `investigating`.
  5. The MLRO restricts the account (`full`, wallets listed; `investigating -> account_restricted`). This is an `SGL+R` act: the restriction and the payout, withdrawal and order holds take effect at once, before any ratification. One A28 freeze op per wallet appears on ADM-14 in the design's "Freeze wallet · <wallet short> · <case alias>" shape. After the TP-SIGN quorum confirms it, ADM-25's status reads "Wallet frozen" in red. The CCO ratifies within 2 h on ADM-30. The MLRO then resumes the investigation (`POST .../resume`, `account_restricted -> investigating`), and the suite asserts that the restriction row, the holds and the freeze are unchanged by the resume.
  6. While the restriction is live, S1 requests a withdrawal on POR-05 and places an order. The withdrawal row reads `under_review`, and no A17 payout exists. The order is refused by G14 with the investor-facing generic message. A distribution line for S1 is marked "AML hold, no notice" and pays nothing. The tipping-off comparison (below) runs in this window.
  7. The MLRO records the SMR decision on ADM-25 (`investigating -> smr_decision`). The SMR is then filed through ADM-26's filing workspace (A76, sealed to MLRO and CCO) with the lodgement reference before `due_at`, and A42's case moves `smr_decision -> smr_filed` with `external_ref`. The suite asserts in the browser that ADM-26's obligation row for this SMR reads filed, and that SUPP opening ADM-26 sees no row, no count and a not-found state on the filing's id URL. If A76 and A42 settle at Specify that the lodgement is taken on ADM-25's filing form instead, the filing is taken there and ADM-26's obligation row is still asserted in the browser. The filing record is also read through the SDK.
  8. The monitoring window opens (`smr_filed -> post_filing_monitoring`). A close attempted now is refused `AML_RESTRICTION_ACTIVE`. The exit relationship follows (`4E`, MLRO maker, CCO checker; `post_filing_monitoring -> exit_relationship`). S1 moves to `offboarded` with the restriction kept and `exit_holdings_pending` recorded, and the MLRO closes with the holdings disposition (`exit_relationship -> case_closed`, "Exited" grey).
- **J10-B, false positive, then a case closed with no SMR (subject S2).**

The closure is a `4E` request with MLRO as checker (`triage -> closed_false_positive`), and it appears in the MLRO's QA list on ADM-25. A false-positive alert is not a case, so it adds no ADM-25 case row.
  2. A second alert on S2 is escalated (`alert_new -> triage -> case_open -> investigating`) with no restriction. The MLRO records the decision (`investigating -> smr_decision`) and decides not to file with a documented rationale (`smr_decision -> no_file`), then closes (`no_file -> case_closed`). The ADM-25 row ends "Closed · no SMR" grey, in the AML-114 shape.
- **J10-C, sanctions list update to silent freeze (G02, subject S3).**
  1. A22's `update-01` list update is triggered. Within one job cycle there is exactly one new review for the seeded `INV-00377` and exactly one Sev1 on ADM-02.
  2. The fixture list entry that makes S3 a true match is then loaded through the sanctions sandbox, before any screening tick has run for S3 and while S3 has no restriction and no case. S3 immediately requests a withdrawal. The suite asserts: the withdrawal does not proceed; its `GateEvaluation` is G02 from the synchronous `screenForPayout`; a screening row for S3 is timestamped at the withdrawal request; no restriction row exists for S3 before the list update; no A17 payout exists; S3 sees only the generic `under_review` state.

  4. The MLRO records the SMR decision.
