# A97 - P3: minors, development and debt vehicles, licensed-market venue mode

**Three P3 capabilities, each behind its own P3 flag bound to a licence record and each carrying its counsel question: the guardian-for-a-minor investor type (INV-M) with its own onboarding branch, relationship evidence, a smart wallet owned by the guardians' passkeys, an on-chain claim, a designated bank account and a coming-of-age handover to the adult under A28's forced-transfer path; development and debt trusts as new `vehicle_type` values with their own SM-03 lifecycle branches (construction to practical completion; loan drawn to repaid), their own maker-checker payouts (progress-claim certification, construction draws and the loan drawdown, each bound by one approval id to A39's payment), their own distribution rules (no income until practical completion is recorded and a preferred-return-then-promote exit; interest-only income from allocated receipts and a principal return) and their own listing checks (quantity-surveyor draws, loan-to-value, verified borrower, no consumer credit); and the continuous licensed-market venue mode as the `Instrument` venue mode that A91 calls `licensed_partner`, which only a licence of a counsel-approved kind can switch on, which checks that licence on every match and halts when it lapses, and which otherwise reuses A91's matching, bands, halts and settlement. Every new action has an API and MCP equivalent under the same gates and a screen for the person who does it; the acts a person must do personally stay personal.**

## Build brief

This node is one API module `p3-vehicles` in the Fastify monolith (`services/api/src/modules/p3-vehicles/`, worker jobs registered from the same folder through A09's job registry) plus the investor web surfaces of the guardian branch. It adds no money engine: orders go through A37 (and A95 for Auto Invest), trades through A91, distributions and exit waterfalls through A40, payments out of client money through A39, token movements through A28 (which sends its own register instruction to A18), identity through A30 and A31, wallets through A29, halts through A48 and flags through A21. Every rule below is enforced in the API, never only in a screen; every read contract is in the OpenAPI document from the first commit so `packages/sdk` and the MCP tool catalogue (A12, A104) see it before the module passes. The only source of time is A09's injectable clock (`Date.now()` and argument-less `new Date()` are grepped by `npm run verify`); dates of birth and ages are computed as Australia/Sydney calendar dates. No vendor is reached; the only new adapter port (`venue`, for a partner-operated market) ships as a sandbox that refuses every call (below).

**1. Flags, phase and the licence perimeter (G21, M02)**

- The four flag keys come from A08.1 (A08 owns `flags.ts`; A21 adds no keys, per their own rules). A21's `activity_flag_map` gains, through A21.x: `investors.minor_guardian` needs `deal_retail_units` (a minor account is never wholesale by default, see §2); `vehicles.development` needs `issue_development_units`; `vehicles.debt` needs `issue_mortgage_units`; `market.continuous` needs `operate_market` **and** the binding licence's `kind` must be in the data row `market.continuous.allowed_licence_kinds` (default `[market_licence]`, set with counsel; whether an ASIC exemption or other relief can support a continuous market is an HG-LEGAL question, and a counsel answer adds a kind to the row, not code). A licence of a kind outside the row may still bind `resale.board` for A91's bulletin board, never `market.continuous`; A21's binding precheck refuses it with `G21_BINDING_NOT_COVERED` naming the allowed kinds. This node supplies the rule as data and a test, not code in A21's folder.
- Every route of this module first asks `isEnabled(key, {tenant, vehicle})` for its feature and returns `PHASE_NOT_ENABLED` (403, with `gate: G21` and the flag key in `reason_codes`) when the flag is off for the scope, before any validation or read of business rows, so a P1 or P2 build answers every P3 call the same way whatever the payload. `GET /v1/p3/capabilities` is the exception: it returns each feature with `available: false` and the plain reason ("Later (P3)"), so screens can render the preview banner.
- `PHASE` from A08 must be `P3` for any of the four flags to be toggled on; A21's toggle precheck already refuses a flag whose phase is later than the running phase; a test here proves it for the four keys.
- Licence lapse: this node subscribes to A21's `flag.auto_reverted` and `licence.state.changed` events. The guarantee that no continuous trade matches after a lapse does **not** rest on this consumer: it rests on A91.1's per-match check (§4). The consumer then opens the durable halt: every instrument in `continuous` mode is halted through A48's `openSystemHalt` with cause `perimeter` and criterion `system:market_continuous_binding_valid` (A48.1), default end date from A48's `halt.system_default_days`. When `investors.minor_guardian`, `vehicles.development` or `vehicles.debt` reverts, new purchases, new listings and new accounts of that kind are refused from the next request; existing holdings, distributions and exits continue (a lapse never strands a holder), and A43 receives `p3.feature.lapsed` for the staff alert.

**2. Guardian for a minor (INV-M; SM-01 branch; G01, G03)**

- Data (A04 tables through the module-schema registry; this node adds only `minor_subject` and `minor_account_status`): `account.account_type = minor_guardian` (the enum value A30 already reserves and refuses with `PHASE_NOT_ENABLED` in P1 and P2); `account_member` rows `guardian` (the verified adult; one or two guardians, `signing_rule` either or both reused from A30's joint model) and `beneficiary` (the minor, never a principal, never a login); `minor_subject` (`investor_id`, `given_names_enc`, `family_name_enc`, `dob_enc`, `dob_bidx`, `name_bidx`, `relationship` in {`parent`, `legal_guardian`, `court_appointed`}, `kyc_case_id` for the minor's document case, `relationship_case_id`, `tfn_ref` held by A41 only); `minor_account_status` (`minor`, `aging_out`, `aged_out`, `claimed`, `transferred`, `closed`) with `aging_out_from`, `turns_18_on`, `claimed_by_investor_id`, `transfer_approval_id`. The register records the holder as "<guardian> ATF <minor>" through A18.x's holder-name template (the chain holds no name).
- `POST /v1/p3/minor-accounts` (`requiresHuman: true`, the guardian's passkey assertion over the canonical payload; an AGNT principal gets A11's `AGNT_NOT_ALLOWED` before scope evaluation) is callable only by a principal whose own investor is `whitelisted` (else `MINOR_GUARDIAN_NOT_VERIFIED`); it takes the child's names and date of birth, the relationship, the guardian's declaration of authority (text version recorded through A35's acknowledgement interface; flagged `"counsel"` in A03's `delegable.ts`) and, for two guardians, the second guardian's email and the signing rule. A child aged 18 or more on the clock's Sydney date is refused with `MINOR_NOT_UNDER_18`; a child with the same `name_bidx` and `dob_bidx` already on an open minor account is `409 MINOR_ACCOUNT_EXISTS` (naming nothing). It creates the investor in SM-01 `started`, the account, the member rows, `minor_subject`, and two `kyc_case` rows through A30's `index.ts` with A30.1's `subject_kind`: `minor_subject` (the child's birth certificate or passport through A22's identity adapter; `liveness_required = false`, a data row set with counsel) and `guardian_relationship` (the document that links guardian and child: birth certificate naming the parent, or guardianship or court order). The case `kind` (purpose) stays A30's `initial`. Both cases run A30's 15 states and 21 transitions unchanged (no new SM-01 state); `guardian_relationship` always lands in `manual_review` after `provider_checks` (a document-authenticity check only), because a person must judge the link. This node supplies the rules through A30.1's `registerCaseSubjectRules`, not by editing A30's folder.
- Documents: `POST /v1/p3/minor-accounts/{id}/documents` with `{subject_kind: minor_subject | guardian_relationship, upload_id}` (`requiresHuman: true`: identity verification is personal) links an A35 upload to the case; under `signing_rule both` either guardian may upload.
- G03 for minors (the account and every person behind it verified): a minor account reaches `whitelisted` only when every guardian investor is `whitelisted`, the `minor_subject` case is `approved` and the `guardian_relationship` case is `approved`. Enforced by the service and by a database check trigger registered here (`minor_requires_verified_guardians`, same pattern as A30's `entity_requires_verified_owners`). A guardian who later becomes `suspended` or `offboarded` drops the minor account to `refresh_due` at once (A30's transition endpoint, service principal) and new purchases stop until a replacement guardian is verified through `POST /v1/p3/minor-accounts/{id}/guardians` (`requiresHuman`, an A14 request `investor.minor.guardian_change` under `4E`, LEGL maker, CCO checker, evidence mandatory; the estate path of A44 calls the same request). A30's `isWhitelisted(account)` is what G01 reads, so no order, deposit, transfer or distribution credit can reach a minor account before this.
- **Wallet (A29.x).** The minor account's smart wallet is created by A29 when the account is created, through the same ceremony as an adult's first wallet: `requiresHuman`, each guardian registering their own passkey in person as an owner key of that wallet (creating a first wallet is non-delegable under D04). The child has no key. Under `signing_rule either` any one owner may sign a UserOp. Under `signing_rule both`, spec point (d): the proposed reading is that A29 sets the account's owner threshold to 2 where A26's account supports a threshold; if it does not, A29 holds every owner UserOp in a co-sign record until the second guardian asserts over the same payload hash, and submits only then. The hidden tests are written for the reading chosen at Specify. A guardian change rotates the owners under the `investor.minor.guardian_change` approval id: the new guardian's key is added first (A29's `addOwner`), then every key of the removed guardian is removed, so A29's `WALLET_LAST_KEY` never fires; a removed guardian's passkey can no longer sign. Guardian-agent session keys follow A12's mandate and A29's session-key rules, are registered by the guardian's own passkey (under `both`, both guardians), are scoped to this wallet only, and are revoked when that guardian is removed and at `transferred`. Guardian recovery settings on the minor wallet follow A29 with the guardians as the recovering people.
- On-chain: A31 issues claim topic `MINOR_ATF` (6, P3, A31.x) on the minor account's identity when the account is whitelisted, and revokes it at `transferred`. A token's compliance includes or excludes topic 6 through A28's configuration; the retail pack in P3 (`AU-R-2027.x`) excludes minor accounts unless the listing's TMD names "investing for a child" (A90.x). A wholesale classification (A32) on a minor account is refused with `MINOR_WHOLESALE_NOT_ALLOWED` (default; counsel may change the row), so in P3 a minor account can buy only retail listings whose TMD allows it; any other order is refused by A19 with `MINOR_LISTING_NOT_ELIGIBLE` from the rule this node registers with A19's rule-pack interface.
- Money: deposits come from the guardian's PayID for that account (A17 issues one PayID per account). Withdrawals go only to a bank account designated for the minor (in the child's name, or in a guardian's name with the account designated for the child, recorded with evidence); setting or changing it is `POST /v1/p3/minor-accounts/{id}/bank-account` (`requiresHuman`: D04's "changing the withdrawal bank account" is personal) and A39 refuses any other destination with `MINOR_BANK_ACCOUNT_NOT_DESIGNATED` through the destination rule this node registers with A39.1. Auto Invest (A95) on a minor account is allowed only under a PayTo mandate from a guardian's own bank account and runs every gate per purchase exactly as for an adult; a guardian-signed mandate is `requiresHuman` as in A95.
- **Signing rule `both` for orders.** Under `both`, an order, bid, ask, Auto Invest change or withdrawal placed by one guardian or by that guardian's agent is created held (`awaiting_co_signer`, through A12's confirmation record: `428 CONFIRMATION_REQUIRED` for an agent) and is not submitted to A37, A91 or A39 until the other guardian confirms by passkey within the confirmation's life (24 h, A12's rule); an agent can never be the confirming guardian. Under `either`, one guardian or their agent within its mandate is enough.
- Coming of age: the worker job `p3.minor_age_sweep` (daily 04:30 Sydney, idempotent, injectable clock) moves `minor -> aging_out` at `turns_18_on` minus `minor.notice_days` (default 90) and emits `p3.minor.aging_out` (A43 notifies the guardians); moves `aging_out -> aged_out` on `turns_18_on` (a child born 29 February turns 18 on 1 March in a non-leap year, a data rule set with counsel) and from then refuses new purchases, new Auto Invest runs and new bids with `MINOR_AGED_OUT`; holdings, asks already resting, distributions and statements continue. The adult onboards in their own right (A56's ONB-01 to ONB-10, own passkey, own identity case, own wallet) and calls `POST /v1/p3/minor-accounts/{id}/claim` (`requiresHuman`, the adult's own principal, never a guardian or an agent), which matches the adult's verified identity to `minor_subject` by blind index on name and date of birth (a mismatch is `MINOR_CLAIMANT_MISMATCH` and opens a KYCA task, never a silent match) and moves the account to `claimed`.
- **Handover (money; one approval id binds every leg).** The claim opens one A14 request `investor.minor.handover`. Its policy row is A28's `forced_transfer` row (LEGL maker → CCO `compliance_approval` → CFO and the trustee `checker_approval`, `6E+Q`, 48 h timelock, not waivable by default); a lighter code may replace it only as an A03 policy row set by the founder or counsel, never in code. On approval, this node's effector, idempotently and keyed on the approval id: (1) opens, through A28.x, one SM-13 `forced_transfer` request of type `minor_handover` per token the minor wallet holds, each carrying the handover approval id; A28 runs its own prechecks, including the destination guard (the adult's wallet linked to a verified identity; G06 and G07 for the adult evaluated through A19), the timelock and the V2 custody quorum whose signatures carry the approval id; after chain confirmation A28 itself sends A18 the `transfer` instruction (subkind `forced`) under the same approval id and waits for the ack. This node never calls A18 and never moves a token itself. (2) Only when every A28 op for the account is `closed` (register acked and A20's targeted reconciliation clean), posts an internal A16 ledger transfer of the AUD balance from the minor account to the adult's account under the same approval id (not a withdrawal). (3) Revokes `MINOR_ATF` through A31, revokes the guardians' session keys on the minor wallet through A29, emits A12.x's `account.scope.revoked` for the account (only tokens scoped to that account are revoked; the guardians' own-account tokens survive), and sets `minor_account_status = transferred`. An A28 op that ends `refused`, `failed` or `broken` stops the effector at that step and opens an A13 Sev2 for REGO; nothing after it runs. Until the handover the guardians keep read access and can withdraw only to the designated account; after it they have none. A guardian cannot block or delay the claim (default; counsel question).
- Closing: `POST /v1/p3/minor-accounts/{id}/close` (`requiresHuman`; an A14 request `investor.minor.close`, `4E`, guardian as maker by passkey, OPS checker; under `both` both guardians assert) is allowed only when the account holds zero units and zero AUD (`MINOR_ACCOUNT_NOT_EMPTY`, naming the counts) or after `transferred`; it emits `account.scope.revoked` and sets `closed`.
- Error and empty states: `GET /v1/p3/minor-accounts` returns `{items: [], next: null, available}` with `available` from the flag; a guardian with no verified identity gets `next_action: "verify_yourself_first"`; the status of a minor account is A30's ONB-10 composer with two extra rows this node contributes through `StatusContributor` (`child` and `relationship`, each `done`, `reviewing`, `action_needed` or `not_started`); a claim before `aged_out` is `409 MINOR_NOT_YET_18` with the date.

**3. Development and debt vehicles (M02, M03; SM-03 branches; G03)**

- Vehicle types, spec point (a) to settle at Specify: A33's `vehicle_type` is the wrapper (`trust`, `sub_fund`). The proposed reading adds four values, `development_trust`, `debt_trust`, `development_sub_fund` and `debt_sub_fund`, with two pure functions in `packages/domain` (A03.x): `wrapperOf(vehicle_type)` (`trust` or `sub_fund`) and `strategyOf(vehicle_type)` (`income`, `development`, `debt`). A33.1 and A04.x apply the enum extension and switch their `sub_fund` comparisons to `wrapperOf`, so every existing rule (a `sub_fund` needs `scheme_id`; `PHASE_NOT_ENABLED` for a `sub_fund` in P1) keeps working unchanged. If the user prefers, the alternative is a separate `strategy` column with `vehicle_type` untouched; the hidden tests are written against whichever reading is chosen. Creating a vehicle of a development or debt type with its flag off is `PHASE_NOT_ENABLED`; a sub-fund type additionally needs `offers.retail`.
- Development data (`development_plan`, one per vehicle, sponsor-entered): `builder_entity_id` (an A33 entity with the builder's licence number and expiry as a `licence` row of kind `other`), `quantity_surveyor_entity_id`, `budget_lines` (land, construction, fees, contingency; integer cents) and `budget_cents` (their sum), `contingency_bps`, `expected_completion_on`, `strategy` (`build_to_hold` or `build_to_sell`), `preferred_return_bps` (simple, per year, default 800, from the offer terms), `promote_bps` (sponsor share above the preferred return, default 2,000), `construction_loan_cents` (optional senior debt), `practical_completion_recorded_at` (null until the `vehicle.development.practical_completion` effector runs). **`DEV_PLAN_REQUIRED`**: a development vehicle without a saved plan whose budget lines sum to `budget_cents`, whose QS is named and whose builder licence is current cannot pass listing review (A36.1 listing check) nor move `funded -> under_construction` (A34.1 guard); the refusal names the missing items.
- Progress claims (`progress_claim`: `claim_no`, `certified_cost_to_date_cents` from the QS certificate uploaded through A35, `certificate_doc_id`, `claimed_cents`, `payee_bank_ref` (the builder's account recorded with evidence), `state` `submitted`, `certified`, `paid`, `rejected`, `certify_approval_id`, `draw_approval_id`). Who moves them, each with maker-checker:
  - `submitted -> certified`: A14 `progress_claim.certify` (`4E`; SP-OPS maker attaching the QS certificate, evidence mandatory; RealX ASTM checker). The QS certificate may be uploaded by SP-OPS or by a partner principal of A98 within its tenant.
  - `certified -> paid`: A14 `vehicle.development.draw` (`4E`; SP-FIN maker, SP-OWN approver, the trustee or RE countersign, RealX TRSY checker; above `dev.draw_large_cents` (data row) CFO is added). On approval A39 pays the builder out of the trust's client-money account through A39.1's `registerDrawPayment`, bound to exactly this approval id; A39 refuses a payment with no approval id or an approval id of another code. `paid` is set on A39's payment confirmation.
  - The precheck of `vehicle.development.draw` (`checkDevelopmentDraw`, registered through A39.1): cumulative drawn plus this claim may not exceed the QS-certified cost to date nor the budget plus approved contingency (`DEV_DRAW_EXCEEDS_CERTIFIED`, naming the headroom); the builder's licence must be current (`DEV_BUILDER_LICENCE_EXPIRED`); the claim must be `certified` under its own `certify_approval_id`.
- Debt data (`loan`, one per debt vehicle): `borrower_entity_id` (an entity verified through A30's `kyb/` path with `subject_type = entity`; the borrower's directors and every guarantor are persons with their own cases; G03 for debt vehicles is: no listing review passes while any of them is unverified, `DEBT_BORROWER_NOT_VERIFIED` naming the count), `purpose` (`business` or `investment`), `principal_cents`, `interest_rate_bps` (fixed; variable is a counsel question and refused in this build), `interest_frequency` (`monthly`), `term_months`, `security_property_id` (an A34 property; the title search must show a registered first mortgage in favour of the vehicle's custodian or trustee, else `DEBT_SECURITY_NOT_REGISTERED`), `security_owner_occupied` (boolean, with `occupant_person_ids[]`), `max_lvr_bps` (data row, default 6,500), `receipt_payid` (A17 issues one PayID per loan; the borrower's payments carry it), `arrears_days` (computed by the job below), `state` (`draft`, `drawn`, `performing`, `in_arrears`, `in_default`, `repaid`, `enforcing`), `drawdown_approval_id`.
- Consumer credit: a loan is refused with `DEBT_CONSUMER_CREDIT_NOT_ALLOWED` when its purpose is personal, domestic or household (only `business` and `investment` are accepted) **or** when `security_owner_occupied` is true and any `occupant_person_ids` is an individual borrower, a borrower director or a guarantor. This is the default until counsel answers whether a debt trust may ever touch regulated consumer credit; the rule's inputs are data and a counsel answer changes the row.
- LVR is computed on the server with A02's integer functions as `principal_cents * 10,000 / security_value_cents` rounded up (so a borderline value fails closed), using A34's latest published valuation of the security property; a loan whose LVR exceeds `max_lvr_bps` is refused at listing review and at drawdown (`DEBT_LVR_EXCEEDS_MAX`, naming the maximum principal allowed), and a stale security valuation is A34's G20 refusal, not a new rule.
- Drawdown: the principal is paid to the borrower only through A14 `vehicle.debt.drawdown` (`4E`; SP-FIN maker, SP-OWN approver, the trustee or RE countersign, RealX ASTM and TRSY checkers; above `debt.drawdown_large_cents` CFO is added). Its precheck reruns LVR, security registration, borrower verification and consumer-credit rules; its effector pays through A39.1 bound to the approval id, and on A39's payment confirmation sets the loan `draft -> drawn -> performing` and drives SM-03 `funded -> operating : loan drawn`. No other path pays principal out.
- Receipts: borrower payments arrive on the loan's `receipt_payid` and are matched by A17 to the loan. Each receipt is allocated in the order of the data row `debt.receipt_allocation_order` (default, set with counsel: fees, interest arrears oldest first, current interest, then principal) and posted to distinct A16 accounts per loan (`loan_fees_received`, `loan_interest_received`, `loan_principal_received`); a part payment fills the order as far as it goes; an overpayment beyond everything due is held in `loan_overpayment_held` and never counted as interest or principal until a human applies it or A39's existing unapplied-receipt path returns it to the payer. The allocation is a pure function with vectors.
- SM-03 branches, recorded as extensions in A03's `extensions.ts` with this node as source (the A30 precedent) and applied through A34.1's strategy guards registered from this node:
  - Development adds states `under_construction` and `practical_completion` and transitions `funded -> under_construction : construction commenced` (development only; needs `DEV_PLAN_REQUIRED` to pass), `under_construction -> practical_completion : occupation certificate` (A14 `vehicle.development.practical_completion`, `4E`, SP-OPS maker, then SP-OWN, then RealX ASTM checker per A14's chain, evidence mandatory; its effector sets `practical_completion_recorded_at`), `under_construction -> distressed : cost overrun or delay` (automatic when certified cost exceeds budget plus contingency or the clock passes `expected_completion_on` plus the tolerance row, default 90 days), `distressed -> under_construction : remediated` (development only, while practical completion is not recorded), `legal_hold -> under_construction : order discharged` (development only, same condition), `practical_completion -> operating : build-to-hold leased`, `practical_completion -> under_sale : build-to-sell sell-down`.
  - Development guards on existing transitions: while `practical_completion_recorded_at` is null, `funded -> operating`, `distressed -> operating` and `legal_hold -> operating` are refused for a development vehicle with `PROP_ILLEGAL_TRANSITION` (reason `DEV_PRACTICAL_COMPLETION_NOT_RECORDED`); the vehicle returns to `under_construction` instead.
  - Debt adds state `repaid` and transitions `funded -> operating : loan drawn` (only from the `vehicle.debt.drawdown` effector), `operating -> repaid : repaid in full` (only when A16's `loan_principal_received` equals `principal_cents` and interest received equals interest due to date), `distressed -> repaid : refinanced` (same condition), `distressed -> under_sale : mortgagee sale` (debt only, after `enforcing`, A14 `vehicle.debt.enforce`, `6E`, ASTM maker, CCO and LEGL checkers plus the trustee countersign where A14's row names it), `repaid -> wound_down : principal returned`; `operating -> exit_proposed` is refused for debt vehicles (a loan ends by repayment or enforcement, not a vote).
  - Every transition goes through `packages/domain` `transition()`; A34's executor applies them; every non-listed pair is refused with A34's `PROP_ILLEGAL_TRANSITION`.
- Arrears: the worker job `p3.loan_arrears_sweep` (daily 05:00 Sydney, idempotent) reads interest due against A16's `loan_interest_received` for the vehicle, sets `arrears_days`, moves the loan `performing -> in_arrears` at 1 day and `in_arrears -> in_default` at `debt.default_days` (default 30), and at default moves the property `operating -> distressed` through A34, which A48 already turns into a halt of resale, new offers and distributions (cause `distress`). A payment that clears all arrears moves `in_arrears -> performing`. Nothing about arrears is shown to an investor except the halt notice A48 generates and the loan status row below.
- Distribution rules (A40 computes; this node supplies inputs and refusals through A40.1, never a payment): (i) development vehicles pay no income before practical completion is recorded: a distribution run of `kind = income` for a development vehicle whose `practical_completion_recorded_at` is null is refused by the precheck this node registers (`DEV_NO_INCOME_DURING_CONSTRUCTION`), whatever its SM-03 state or line labels; a build-to-hold vehicle in `operating` after practical completion pays rent like any income trust. (ii) At sale, the exit uses A40's `computeExitWaterfall` unchanged with the promote computed here by a pure function `developmentPromote({equity_cents, preferred_return_bps, promote_bps, days_held, residual_cents})`: preferred return is simple interest on equity for `days_held / 365` floored to the cent; `promote_cents = floor((residual - equity - preferred) * promote_bps / 10,000)` when positive, else 0; it is passed to A40 as one `fees_cents[]` entry labelled `sponsor_promote`, computed on the residual A40's first preview returns after debt, costs and the other fees (a two-pass preview whose hashes are both in the A14 payload). Vector: equity A$2,000,000, 8 %, 730 days, residual A$2,720,000 gives preferred A$320,000, promote A$80,000, investors A$2,640,000; residual A$2,100,000 gives promote A$0 and investors A$2,100,000. (iii) Debt vehicles distribute interest actually received, never interest due: spec point (c), the proposed reading adds `income_source` (`rent_roll` default, `loan_interest`) and a nullable `interest_statement_id` to A40's `income_periods` (A40.1; arithmetic unchanged; PM fee and maintenance are zero; the gross line is labelled "Interest received"); this node produces the `interest_statement` from A16's `loan_interest_received` for the period, immutable once referenced; a period for a debt vehicle that references a rent roll is refused (`DEBT_INCOME_SOURCE_MISMATCH`). If the user declines, debt vehicles stay unusable behind their flag. Principal repaid is returned through A40's exit run with `kind = exit` at `repaid`.
- Display facts: `GET /v1/p3/vehicles/{id}/facts` returns display-ready rows `{label, value, tone}` in the design's KeyValueList shape (the property page `details` list, `RealX App.dc.html` line 773) so the property page (A54), holding detail (A58) and property register (A70) render them without new components: development ("Stage: Under construction", "Certified cost to date", "Expected completion", "Preferred return 8.0% p.a., then 80/20", "Income: None until completion") and debt ("Loan to value 62.5%" computed as above, "Interest 9.25% p.a., paid monthly", "Term 24 months, repays 30 Sep 2028", "Borrower: verified company", "Status: Performing"). - **Lapse guarantee (A91.1 per-match check).** In `continuous` mode A91's matcher, inside the transaction that holds the instrument lock and before it commits each match, reads the bound licence row with `SELECT ... FOR SHARE` and calls A21.x's `isBindingValid(market_licence_id, at = match_time)` and `isEnabled('market.continuous', {vehicle})`; if either is false it matches nothing, rests or suspends the incoming order and opens the `perimeter` halt in the same transaction. - Modules: **M02 Sponsors, trusts & entities** — done when development and debt vehicle types, their plans, loans, borrower entities and the licence-to-flag bindings they need exist as this API and A33's vehicle rules still hold through `wrapperOf`. **M03 Properties & assets** — done when the development and debt SM-03 branches, the certify, draw and drawdown requests, the LVR and consumer-credit rules, the receipt allocation, the arrears sweep, the no-income-before-completion rule, the promote function and the debt income source are implemented and tested, and the facts rows render in A54, A58 and A70 without new components. **M14 Resale board** — done when `continuous` is A91's venue mode bound to an allowed licence, changed only through the `4E` request, run on a session calendar with time in force, checked per match, and otherwise identical to A91's bulletin board in its SM-09 trace.
- State machines: **SM-01 Onboarding case** — done when the `minor_subject` and `guardian_relationship` case subjects run A30's 15 states and 21 transitions with no new state, the relationship case always reaches `manual_review`, and the minor account's `whitelisted` depends on both. **SM-03 Property and listing** — done when the development and debt extensions are in A03's `extensions.ts`, every new transition is reachable only through `transition()` with its guard, `funded -> operating`, `distressed -> operating` and `legal_hold -> operating` are refused for development before practical completion, `operating -> exit_proposed` is refused for debt, and every other pair is refused with `PROP_ILLEGAL_TRANSITION`. **SM-09 Resale order and trade** — done when no new state or transition is added, the only continuous-mode differences are session-driven cancellations, the opening cross and time in force, and a lapse moves every open order to `suspended`. **SM-13** — done when `minor_handover` runs A28's forced-transfer path end to end.
- Founder requirement D04: done when every delegable action of this node works under a scoped token with parity to the screens (investor, sponsor, partner and staff), every non-delegable act refuses tokens before scope evaluation, the personal declarations are `"counsel"` rows, and no agent is ever the checker of the nine action codes in §5.

## Node-specific challenges (node QA)

- **A minor account buys before the link is proven (compliance, money).** A whitelisted guardian creates a minor account; the child's document case is auto-approved by the sandbox and the relationship case sits in `manual_review`. The node QA then tries to buy through the guardian's session, the guardian's agent with a generous mandate, an Auto Invest run under A95, and a resale bid on a continuous instrument; then drives the account to `whitelisted` by calling A30's internal transition endpoint with the service principal. Every order must be refused by G01 upstream, the transition by the trigger and the service; any token, unit or AUD credit on the account fails the node.
- **Two guardians, one agent (compliance, D04).** Under `signing_rule both`, guardian A's agent places an order within its cap: it must return `428 CONFIRMATION_REQUIRED` and nothing reaches A37 until guardian B confirms by passkey; B's agent confirming is refused; the confirmation expiring leaves no order. Then guardian B is removed through `investor.minor.guardian_change`: B's passkey must no longer sign a UserOp on the minor wallet, B's session keys are revoked, and the wallet never drops to zero owners.
- **Coming of age by the calendar (compliance).** A child born 29 February 2012: under the injectable clock the sweep must move to `aging_out` on 1 December 2029 (90 days before 1 March 2030), to `aged_out` on 1 March 2030 and not on 28 February, refuse a buy at 00:01 Sydney on 1 March while accepting one at 23:59 on 28 February, and emit exactly one event for each step when the sweep runs twice or the clock jumps 400 days at once. Then the claim: a guardian's session and the guardian's agent calling `claim` get `AGNT_NOT_ALLOWED` or `FORBIDDEN`; an adult whose verified date of birth differs by one day gets `MINOR_CLAIMANT_MISMATCH` and a KYCA task, never a transfer.
- **Handover half done, and a handover without custody (money).** (1) The `investor.minor.handover` effector is killed after the first A28 op closes and before the AUD ledger transfer. On restart it must complete exactly once: the adult holds every unit, the register and chain agree in A20's targeted reconciliation, the AUD balance moves once, `MINOR_ATF` is revoked, only the tokens scoped to the minor account are revoked (the guardian's own-account token still works), and replaying the approval id changes nothing. (2) the node QA tries to move a token or post the AUD transfer with no approval id, with another request's approval id, before the 48 h timelock ends, or with a custody signature that does not carry the approval id: every attempt is refused and nothing moves. (3) No register instruction for the handover exists before its A28 op is `confirmed`.
- **The development trust that pays itself early (money).** A sponsor's fund accountant, and then their agent, create a distribution run for a development vehicle in `under_construction` with "rent" of A$40,000 (a mis-coded progress-claim refund); A40 must refuse it with `DEV_NO_INCOME_DURING_CONSTRUCTION`. Then the vehicle overruns, goes `distressed`, is remediated, and the node QA tries `distressed -> operating`, `legal_hold -> operating` (after a hold and discharge) and a distribution labelled rent: every one refused (`PROP_ILLEGAL_TRANSITION` with `DEV_PRACTICAL_COMPLETION_NOT_RECORDED`, and `DEV_NO_INCOME_DURING_CONSTRUCTION`). Then a progress claim for A$900,000 against a QS certificate of A$850,000 cost to date with A$0 contingency left must be refused with `DEV_DRAW_EXCEEDS_CERTIFIED` naming the headroom; then the exit vectors (residual A$2,720,000 and A$2,100,000) must give promote A$80,000 and A$0, and a residual that yields a promote of A$0.005 must floor to A$0.00 in the investors' favour.
- **A draw nobody checked (money, G13).** A certified claim is paid by a single SP-FIN action with no approval: refused by A39. The draw request approved by SP-FIN's own agent, by SP-FIN themself, or by an SP-OWN agent: refused (`G22_AGENT_NEVER_CHECKER` or SoD). A draw against an uncertified claim: refused. A debt drawdown attempted by moving SM-03 `funded -> operating` directly, without `vehicle.debt.drawdown`: refused, and no principal leaves client money.
- **LVR at the edge, a consumer loan in disguise and a short payment (compliance, money).** With the security valued at A$2,000,000 and `max_lvr_bps = 6,500`, a loan of A$1,300,000 passes and A$1,300,001 fails with `DEBT_LVR_EXCEEDS_MAX` naming A$1,300,000; the valuation then goes stale and the listing review fails on A34's G20, not on a new rule; a loan whose purpose is `business` but whose security is flagged owner-occupied with the borrower director as occupant is refused `DEBT_CONSUMER_CREDIT_NOT_ALLOWED`; a borrower with one guarantor still `verifying` fails `DEBT_BORROWER_NOT_VERIFIED` naming 1. Then a part payment of half a month's interest while a month is in arrears, and an overpayment of 110 % of everything due: the allocation follows the data row, the interest statement counts only interest received, and the overpayment sits in `loan_overpayment_held`.
- **A market without a market licence (compliance, G21).** CCO requests `continuous` for an instrument bound to a licence whose kind is not in `market.continuous.allowed_licence_kinds` (for example an `asic_relief` record listing `operate_market` while the row is at its default): refused with `VENUE_CONTINUOUS_REQUIRES_MARKET_LICENCE` before any A14 request exists; adding the kind to the row (as a counsel answer would) makes the same request pass without a code change. - **Agent parity without agent authority (D04).** A guardian's agent with a mandate for the guardian's own account tries to read and buy for the minor account (`G22_SCOPE_MISSING` naming the account); with a mandate scoped to the minor account it buys within its cap and the audit row reads "agent … on behalf of" the guardian; then it tries `documents`, `bank-account`, `guardians`, `claim` and `close` (`AGNT_NOT_ALLOWED` before any scope check). - **Leaks and fidelity (security, design).** A planted child's name, date of birth and a borrower director's name must not appear in logs at any level, the outbox, `gate_evaluation` inputs, error messages, OpenAPI examples, SDK types or the evidence folder; the guardian pages compared with the ONB-02 option card, the ONB field, the DropBox and the ONB-10 CheckList in the design must match tokens, radii, fonts and spacing, the fourth card must be indistinguishable in style from the other three, and every flag-off state must use the PreviewBanner colours; any new pill string or bare 4xx fails.
