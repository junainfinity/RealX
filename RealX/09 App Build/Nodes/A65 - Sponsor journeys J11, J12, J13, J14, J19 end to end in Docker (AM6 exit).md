# A65 - Sponsor journeys J11, J12, J13, J14, J19 end to end in Docker (AM6 exit)

**One Playwright suite over A61's Docker Desktop preview stack, extended with the sponsor console, that walks the five sponsor journeys through the real screens with real passkeys: J11 a new sponsor applies on SPN-01, passes KYB and background checks and gets a live tenant; J12 a sponsor takes a property through the four-step wizard to a submitted, returned, resubmitted, approved, token-deployed and live listing that a visitor can see on PUB-04; J13 a six-monthly valuation with a move above 10 percent is refused without comparables and published with them; J14 a missed insurance renewal shows an amber proof-of-property flag in public, escalates to distressed and clears only after RealX reviews the new evidence; J19 the sponsor's month-end runs from tasks generated by due dates. RealX-side steps (application review, KYB approval, tenant creation, investment committee, title, valuation committee, listing review, token deploy, go-live, property operations) are driven through `packages/sdk` and the approvals API with the correct staff persona for each step, behind one swappable interface that A78 replaces with console paths in AM7. Every failure path in the catalogue is a negative test, SPN-16 token issue and revoke is exercised once through the screen, and the three designed sponsor screens are compared with the prototype. It is the AM6 exit.**

**Build status:** not started. **Milestone:** AM6 (Sponsor console). **Lane:** Quality. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-16 agent-hours (build, challenge and verify loops). `verify:sponsor` alone is three runs of up to 45 minutes plus the node QA's fourth seed, and each of up to three fix loops re-runs all three seeds; the suite has twelve spec files, the J12 mint tail, the fidelity captures, the bounded public-cache polls and the daylight-saving probes (A80, which covers similar ground, is estimated at 10-14).

## Build brief

This node writes no product behaviour, no product screen and no API. It owns a test suite, a small compose overlay, an operator-step driver, an evidence writer and a one-page README, all under `<workspace>\app\e2e\sponsor\`. Browser steps go through `apps/web` as a person would. RealX-side steps go through `packages/sdk` against the running `api` container. Nothing in `e2e/sponsor/` imports from `services/*`, `packages/db`, any adapter or any `apps/*` source file, and a lint in the suite fails if it does.

**1. Stack, commands and harness**

- The suite runs on A61's preview profile (`infra/preview/`), included, never copied or edited. When the sponsor journeys need a service A61's profile does not start (the custody signer panel of A15 for the token deploy quorum, the registry sandbox panel of A18, the email sandbox's captured inbox of A43 for invitations and notices), `e2e/sponsor/compose.sponsor.yml` adds only those services by `include:` of A23's stack definitions. It changes no port, image or environment value of A61 or A23. Every `ADAPTER_*` stays `sandbox`, `RUN_MODE` stays `local`, `CHAIN_ID` stays 31337, and A23's static no-live test is extended to scan this folder. A service A61 or A23 cannot provide without an edit is a loop on that node (A61.2 or A23.1; A61.1 is A61's scheduled AM5 re-run), never a change here.
- Commands under A01's script-registration convention: `sponsor:up` (preview stack plus the overlay, healthy), `sponsor:e2e [--seed <string>] [--journey J11|J12|J13|J14|J19] [--headed]`, `sponsor:walkthrough` (the same suite headed with a pause before each numbered step, printing which screen and which persona is next, for anyone who wants to watch), `sponsor:down`, `sponsor:evidence` (rebuilds `app/evidence/A65.json` from the last run), and `verify:sponsor` (= `stack:reset`, `sponsor:up`, the full suite three times with three different `--seed` strings, `sponsor:down`; needs Docker Desktop and is what the gauntlet runs). `npm run verify` stays Docker-free and runs only this node's static checks: the import lint, the operator-step allowlist lint, the schema of the expected-step table and the README link check.
- Playwright on Chromium, desktop viewport 1280 x 800 (the consoles are desktop-first); one extra pass of SPN-02 at 1023 px checks the collapsed sidebar. Passkeys for sponsor users, applicants and partner users are real WebAuthn ceremonies against a Playwright CDP virtual authenticator registered per persona, so every "fresh passkey step-up" in the product is a real assertion through A11's verifier. Staff actions use A11's local simulated authenticator with hardware-key attestation (`/__test/*`, mounted only in `RUN_MODE=local|test`) through the SDK.
- Time comes only from A09's injectable clock (`CLOCK_AS_OF` = A06's as-of date, Wednesday 23 September 2026) and is advanced explicitly with `/__test/clock/advance` for offer opening, attestation deadlines and grace periods, invoice due dates, valuation age and job cycles. The suite never sleeps on wall time for business time; after a clock advance it triggers the named worker job once through the job scheduler's run-now test hook and then asserts.
- **Public caches and "one job cycle".** Public reads are cached on wall time by their owners: A34's `GET /v1/properties/{id}/proof` for 60 seconds and A54's page revalidation for 60 seconds, stacked. "One job cycle" in this note therefore means: the named job's run-now call has completed, plus both cache layers, with a ceiling of 125 seconds of wall time (60 + 60 + 5 seconds of margin). Every public assertion that follows a state change (J12 step 12's 404, "Coming soon" and "Open offer" flips, the J14 overdue flag on PUB-04 and PUB-05, the J19 public rent-roll flag and its clearing, and C6) is a bounded poll every 5 seconds up to that ceiling, never a fixed sleep; the elapsed time of every poll is written to evidence, and a poll that reaches the ceiling fails the step. If at Specify A34 and A54 confirm that A09's clock-advance route also expires their caches, the poll ends at the first matching read and the ceiling still applies. These bounded polls are the only wall-clock waits in the suite.
- **Collateral effects of clock advances.** Every clock advance is listed in `expect-table.ts` with its collateral alerts, pauses and signals, not only the one the step is about: for example, passing 30 September makes the August attestations of BAY01, MRN01 and HAW01 overdue (and, ten days later, pauses those sponsors' new offers under G19), and passing about 14 October makes MRN01's valuation (dated 14 April 2026) older than 183 days (G20 alert). Files that advance past 30 September and are not about the August attestation (J12, J14 and the J14 rates file) have Mia sign BAY01's August attestation on SPN-10 and PROP accept it before the first advance, and the expect table lists what remains. Alert and signal assertions are scoped to the alert key of the object under test, so a correct build's collateral alerts do not fail a step and are still counted in evidence.
- Test files, one per journey plus the failure paths, each starting from `stack:reset` plus A06's baseline and then the seed's own sim rows (`npm run sim -- generate --scenario <s> --seed <string>`): `fidelity.spec.ts` (runs first; see Design references for its order), `j11-sponsor-joins.spec.ts`, `j11-declined.spec.ts`, `j12-lists-a-property.spec.ts`, `j12-rfi-title-defect.spec.ts`, `j13-valuation.spec.ts`, `j13-stale-valuation.spec.ts`, `j14-reporting-breach.spec.ts`, `j14-rates-and-court-order.spec.ts`, `j19-month-end.spec.ts`, `j19-late-report.spec.ts`, `j19-grace-dst.spec.ts` (the daylight-saving boundary on the untouched baseline), plus `personas.ts`, `operator-steps/` (below), `expect-table.ts` (the expected state, gate result, policy code, error code or envelope set, and audit event types per step), `checkpoints.ts`, `actions-manifest.ts` and `evidence.ts`. Files run sequentially (`workers: 1`) because they share one stack.
- **Expected codes and precedence.** Every negative in this note has one primary code, or an explicit "envelope contains" set, taken from the owning node's error list and pinned in `expect-table.ts` at Specify. For a request that presents a bearer token, A12's `agentAuth` middleware runs before A11's session logic and before the route handler, and its G22 evaluator adds every failing check to one envelope. So: a token on any A14 decide, listing sign-off or countersign route must be refused with an envelope containing `G22_AGENT_NEVER_CHECKER` (A12: refused "regardless of scope"), and the owning node's human-only code (A33 `SPONSOR_APPROVER_MUST_BE_HUMAN`, A14 or A36 `APR_CHECKER_MUST_BE_HUMAN`) is additionally required only if the owning node states it is raised in that envelope; a token on `POST /v1/attestations/{id}/sign` must be refused with an envelope containing `ATT_SIGNER_NOT_HUMAN`, which A34 raises before scope evaluation. Where A12 and an owning node disagree about which check runs first, that is a spec defect filed against both at Specify; the suite never accepts "either code".
- Every browser mutation is captured from the network (`page.on('response')` on `/v1/*`) with its operation id, persona, gate evaluations returned and the idempotency key; one write per journey is replayed with the same key through the SDK and must return the same result with no second row.

## Node-specific challenges (node QA)

- *Green by driving the operator side too hard (compliance).* The SDK driver approves the tenant, the investment committee or the go-live with one persona that holds several roles, uses a SUPER token to set `offering.state = live`, or calls a test route to write `title_verified`, so every journey passes while maker-checker is never exercised. The allowlist lint must catch the route, C2 must find the same person as maker and checker, and the node QA's scan of the run's HTTP log must show one distinct human per decision with a hardware-key assertion.
- *The listing that is public too early (compliance, design bug 19).* The J12 listing appears on PUB-03 or PUB-04 as "Coming soon" while still in `compliance_review`, or its code resolves through `GET /v1/public/offerings/{code}` with a 403 that leaks existence, or go-live is approved with G17 flags still open because the precheck only checked version 1. C6 must fail on any public read of a non-public state, and the precheck refusal with open flags must be observed before the return.
- *Comparables theatre (valuation).* The >10 percent move is accepted because the suite attached three comparables in one call before the refusal was ever tested, or a comparable 366 days old is counted, or PUB-04 shows a token valuation typed by the sponsor rather than the server's. The refusals at 0, 2 and "3 with one stale" must each be observed in order, and the published figure must equal the formula re-derived from the seed.
- *Coupled flags and early clearing (G19, design bug 2).* Approving the September distribution flips SPN-10's pill to "Signed", or uploading the renewed certificate clears PUB-04's amber flag before PROP reviews, or signing the late attestation lifts the pause. Each must be asserted in both directions, and the design-bug-2 test must fail against the node QA's coupled scratch copy.
- *The agent that is really its owner (agent misuse, G22).* Leo's agent call is sent with both his session cookie and the bearer token so the "agent" carries no `on_behalf_of`; the SPN-16 token is approved by Leo himself; the revoked token still works on the MCP path because the MCP server caches introspection; or the activity list hides refusals. The suite must send token-only requests, assert `TOKEN_AMBIGUOUS_PRINCIPAL` once with both, assert Mia as the approver of record, assert `TOKEN_REVOKED` on SDK and MCP alike, and count refusals in the activity list.
- *Tasks that are only painted (J19 oracle hook).* The seed stores "Due in 7 days" as text, so the clock advance changes nothing, or the overdue task turns red only after a page reload that re-seeds. The advance must change the wording with no write in the audit trail, and the red tone must come from the API's `overdue` flag.
- *Time-zone slip.* The ten-day grace is computed in UTC or ignores the start of daylight saving on 4 October 2026, so BAY01 is paused an hour early; or the invoice becomes overdue at UTC midnight. The node QA's boundary probes one hour either side must give the documented result.
- *Tipping-off on decline (compliance).* Coastline's declined page, an email or a network response includes "sanctions", "PEP", "AML" or the match score. A text scan of all three must find none.
- *Design fidelity that passes by masking.* The visual diff passes because whole regions were masked, the tone of "Changes requested" is amber instead of brick, or the SPN-02 KPIs were compared after J19 changed them. Only the listed masks are allowed, the structural comparison checks tones as colours, and `fidelity.spec.ts` must run first, capturing SPN-02 and SPN-10 on the untouched baseline before it creates the design-value draft.
- *Swap-point rot.* A journey file reads a field only the SDK driver returns (an internal request id, a raw database state), so A78's console implementation cannot satisfy it. The node QA runs the journeys against a stub `console` implementation that returns only what the ADM screen specs in A51 show, and any journey that cannot compile or assert against it is a finding.
