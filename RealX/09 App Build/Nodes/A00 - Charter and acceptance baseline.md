# A00 - Charter and acceptance baseline

**Freeze the build charter before any code: the fixed context D01-D04, the P1/P2/P3 vocabulary, Q12 option 1 with its swap points, the human gates, the canonical screen table that reconciles design codes to product-map codes, D04 agent access frozen as data, the design-folder hash, and a coverage matrix that maps every one of the 91 screens, 21 journeys, 22 gates, 27 modules and 14 state machines to a node or an exclusion.**

**Build status:** not started. **Milestone:** AM0 (Foundations). **Lane:** Plan. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 2-4 agent-hours (build, challenge and verify loops).

**Depends on:** none
**Unlocks:** [[A01 - Repo scaffold, toolchain and verify command|A01]], [[A50 - Design extension A- investor and sponsor screens not in the prototype|A50]], [[A51 - Design extension B- operator console screens not in the prototype|A51]]

**Oracle rule:** `oracle: no`. No money, supply or holdings move in this node, so the node QA writes no hidden oracle tests from it. The node QA still prepares its Challenge material before the build starts and writes it to `<workspace>\gauntlet\hidden\A00\`: the seeded-fault fixtures (one missing id, one duplicated id, one overlapping owned path, one innocuously named scope whose action list includes a non-delegable action id, one design file with a single byte changed on a scratch copy, one graph copy with J22 removed from A82, one screens file with an owner chosen by list order instead of by route) and its own hash and id-tracing scripts. The builder never reads that folder ([[App Gauntlet]] §2). This note is planning material, not legal advice; every legal sentence in the charter is written as a counsel question or a counsel expectation, never as a rule.

## Build brief

The node produces documents and data under one folder. Nothing else in the repo exists yet (A01 creates the scaffold and makes the first commit, carrying this folder with it), so the only tool the checker may need is Python 3.13 (`py`) with the standard library. Every file below is UTF-8 with LF line endings, in plain English. JSON is the source of truth for every list and count; the rendered `.md` files are generated from it, so a prose count can never drift from the data.

- **`charter.md`.** Records, verbatim from the plan, the fixed context that no node may re-decide: D01 Australia; D02 marketplace listing other sponsors' property trusts (RealX never owns property); D03 residential and commercial; D04 every user type manages API tokens so its own AI agents can carry out every account action through the API and MCP under exactly the same gates as the UI. Defines the phase vocabulary once: **P1** wholesale now (sponsors issue units of their own wholesale trusts under their own AFSL; RealX arranges as a corporate authorised representative, CAR); **P2** from about 8 Apr 2027 (Digital Assets Framework Act: umbrella registered MIS run by a hired RE, sub-fund per property, PDS and TMD per listing, guarded resale board and on-platform votes once counsel or ASIC relief allows); **P3** later (continuous licensed market, AUD stablecoins, Auto Invest, minors, development and debt trusts). States the legal-record rule: the trustee or RE unit register under Corporations Act s169 is the record; ERC-3643 tokens mirror it; the daily three-way reconciliation register - chain - bank has zero tolerance; a break halts resale for that trust and blocks mints and payouts for it. States the investor model (non-custodial passkey smart wallets with guardian recovery and no seed phrase; AUD first over NPP/PayID/PayTo into client-money trust accounts; no utility token; audited metrics only; sponsors carry property operations and RealX monitors them through proof of property). States the two-tier admin model (RealX operator console with modules M01-M27 over the sponsor console), the maker-checker codes as a fixed vocabulary (4E, 4E+Q, 6E, 6E+Q, SGL+R, AUTO; one approval ID binds the console approval, the custody signature and the chain transaction) and the key hierarchy (V1 owner 3-of-5, V2 token agent 2-of-3, V3 pauser 1-of-N, V4 identity agent auto, V7 paymaster; V5 and V6 reserved for P3). Names the custody signing policy rules **CP01-CP10**, never "P1-P10", so they cannot be confused with the P1/P2/P3 phases (A15's title still says "P1-P10"; see the note under Requirements covered). Records that the requirements catalogue's decision row 5, which numbered the supplementary console screens ADM-35 to ADM-39, is replaced by ADM-36 to ADM-40, because ADM-35 is "Agent and API access" (D04). Lists the gate catalogue G01-G22 by id and name and the build-state vocabulary used everywhere (`not started, building, challenged, passed, escalated`). Contains the line "This charter is not legal advice" in its first paragraph.
- **`decisions.md`.** Records **ENG-01, Q12 option 1** as a proposed and reversible engineering decision: open-standard ERC-3643 (T-REX reference implementation, GPL-3.0 licence referred to counsel under HG-LEGAL, clean-room implementation of the EIP interfaces named as the fallback) plus rented services behind sandbox adapters. The swap-point table has one row per rented layer with four columns (layer; assumed provider type; the adapter interface the build owns; what changes on a swap and what must not change): custody signing policy engine (Fireblocks-type; `CustodySigner.submit(approvalId, tx) -> status`; custody policy rules CP01-CP10 re-expressed in the vendor's engine; `ApprovalRequest` and `CustodyOp` unchanged), bank rail (Monoova/Zepto-type NPP/PayID/PayTo into client-money trust accounts; `BankRail.issuePayId / receipts / payout / statement`; the ledger and matching stay RealX's), unit registry (IQ-EQ/Automic-type; `Registry.instruct / ack / dailyFile / certify`; only the file format and ack semantics change, and reconciliation keeps reading the register extract, never the vendor's balances), identity and DVS (Equifax/Sumsub/Averer-type; `IdentityProvider.verify / screen / rescreen`; provider client only), token contracts (T-REX <-> a vendor platform behind the chain and custody interfaces; the register, ledger, reconciliation and rules engine must not depend on T-REX internals), chain (Hardhat <-> Base Sepolia <-> mainnet or Redbelly; URL and chain id), e-sign, email and SMS. Records the reversal path: the node ids re-run if the founder chooses option 2 or 3, taken from `app-graph.json` at build time. Also records **ENG-02 partner surfaces** and **ENG-03 agent principal model** (both from `agent-access.json` below) as proposed decisions the founder may overturn. Each decision has a rationale and a "confirmed in" node id.
- **`human-gates.md`.** One section per gate with three parts (what the human does; what agents prepare; the evidence that closes it): **HG-LEGAL** (licences, CAR appointment, RE for hire, counsel opinions including the questions in `counsel-questions.md`), **HG-VENDOR/ACCOUNTS** (contracts and accounts for KYC/DVS, bank/NPP, custody, registry, e-sign, RPC, bundler; agents get sandbox credentials only), **HG-KEYS** (V1-V7 key ceremonies, production secrets), **HG-AUDIT** (two independent smart-contract audits before mainnet), **HG-PENTEST**, **HG-CAPITAL** (real client money, trust-account opening), **HG-PROD** (mainnet deployment, production infrastructure), **HG-REVIEW** (founder sign-off on the charter, the design-extension files and visual QA), **HG-LAUNCH** (go-live). The closing paragraph states what agents never do: touch licences, counsel opinions, vendor contracts, production keys, real money, mainnet, audits, pentest or go-live; they build and test locally, on a local chain and testnet, with sandbox adapters only. The standing human roles table (RE/trustee registrar, AFSL responsible managers, compliance officer and MLRO, custody signers V1 3-of-5 and V2 2-of-3 and V3 pauser, production operators, complaints officer for G18, external counsel, auditor) lists a minimum headcount and the first node that needs each, so no "never an agent" duty is left without an owner.

## Node-specific challenges (node QA)

- A screen row names an owning node whose owned paths do not contain the route that renders it (for example ACC-05 mapped to the token-service node A12 instead of the investor-app node), so the matrix reads "covered" while nothing will draw the screen.
- The reconciliation table is applied backwards: a route or test declares design code "INV-01" for product-map INV-01 Buy tokens, so a later screenshot comparison would grade the buy page against the portfolio and pass.
- The five supplementary console screens are numbered from ADM-35 in an older draft, so ADM-35 "Agent and API access" and "sign-in and 2FA" share an id and the matrix counts 91 with one row silently dropped.
- A non-delegable action (change withdrawal bank account, widen a token, guardian change, close account) appears in the scope catalogue under another name (for example `account:bank.write`), so a person could mint a token that performs it.
- A counsel question's default is written into `charter.md` as a rule ("agents may acknowledge disclosures") with no CQ id, flag key or re-test node, so the build hard-codes a legal answer.
- The token-layer swap point says the register and reconciliation "do not depend on T-REX internals" but the swap table omits what the registry adapter returns, so a swap to a vendor platform would leave reconciliation reading balances from the wrong source of truth.
- `design-baseline.json` is computed after a git checkout with `autocrlf` on, or from a copy that omits `.thumbnail` and `uploads\`, so a later edit to the design folder goes unnoticed.
- `ids.json` was copied from the product map instead of the plan's ID list, dropping G22 and the three D04 screens, or J22 was counted in, so the gate family lists 21 and the journey family 22 while the matrix still passes.
- `agent-access.json` folds the user's own agent into AGNT (or drops AGT-U), so the staff maker-only rule and the D04 token rules become one principal and `ids.json` still reports 52 roles.
- A staff-engaged, guard-engaged, owner-type or platform kill switch can be lifted by a single person, any tier can be lifted by an agent acting as maker, or a sandbox (`rx_sb_`) token is accepted on live (or a live token in the sandbox).
- `agent-access.json` keeps token prefixes or a hash algorithm that differ from A12 and D11, so A01's secrets scanner, which reads its prefixes from this file, never flags a committed `rx_inv_` or `rx_stf_` literal.
- A matrix row for J22, ADM-36 to ADM-40 or a G01-G22 parity column is filled by hand with a node that does not list the id in `app-graph.json`, so the matrix reads complete while no node is on the hook to build it.
- A screen is listed by three nodes (design, UI, preview) and the owner is picked as the first in graph order rather than by route, so the design node owns a screen it will never render.
- Two nodes in `app-graph.json` own overlapping prefixes (for example `packages\domain\` and `packages\domain\recon\`), and the checker reports no overlap because it compares equality, not prefixes.
