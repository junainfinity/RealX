# A13 - Alerts and SLA-clocks service

**One service that every other module calls to raise an alert or start a clock: the 17 alert types of the catalogue plus ten extension types, a registry through which later nodes add their own types and clock policies, the Sev1-Sev4 severity model with its acknowledgement SLAs, business-day clocks in Australian time with public holidays as data, owners by role, need-to-know alerts for AML, acknowledge / assign / escalate / snooze with a mandatory reason, bulk acknowledge for Sev3 and Sev4 only, escalation ladders, the 07:00 daily digest and the queue-SLA-breach detector; it is the backend of ADM-02 and of the alert tiles on ADM-01.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 6-9 agent-hours (build, challenge and verify loops).

**Depends on:** [[A09 - API and worker skeleton with OpenAPI-generated SDK]], [[A10 - Append-only hash-chained audit log]], [[A11 - Authentication, sessions, RBAC and segregation of duties]] (real staff sessions and the RBAC middleware; A13 registers its clock and `emit` into A11's break-glass clock port), [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]] (real tokens with `on_behalf_of`), [[A06 - Seed data and scenario simulator]] (the standard seed that holds the design's alerts)
**Unlocks:** [[A14 - Approvals engine and maker-checker (SM-00)]], [[A20 - Three-way reconciliation engine with zero tolerance]], [[A21 - Licences, feature flags and licence perimeter (G21)]], [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A27 - Chain adapter, deployment manifests and indexer]], [[A39 - Treasury- withdrawals, escrow release, client-money reconciliation]], [[A42 - AML screening, monitoring, cases and SMR clocks (SM-11)]], [[A46 - Job scheduler, integrations health and webhooks]], [[A48 - Halts, kill switches and wind-down]], [[A66 - Console- command center, alerts centre, approvals inbox, audit log]], [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]]

**Graph edges (settled 24 Sep 2026).** A11, A12 and A06 are upstream of this node in the graph, so the pass criteria marked **[needs A11/A12]** and **[needs A06]** run at this node's gate on real sessions, real tokens and the standard seed. The node may not pass on a stubbed principal or a private copy of the seed. A11 does not depend on A13: this node registers `openClock`, `businessDaysAfter` and `emit` into A11's break-glass clock port at boot, and a contract test here proves the registration.

**Oracle rule:** not an oracle node in the graph (`oracle: no`), but because these clocks drive SMR deadlines, SGL+R ratification lapses (which trigger reverts) and approval TTLs, the node QA writes hidden tests from this frozen spec **before the build**, into `<workspace>\gauntlet\hidden\A13\`: the business-day, DST and holiday vectors (at least 60), the full `ALERT` transition-table cases, the escalation-ladder case, the bulk-acknowledge cases, the need-to-know cases and the `self_subject` cases. The builder never reads that folder. After the gate the dependents that carry money or authority (A14, A20, A39, A42, A48, A101) re-run them as regression.

This note is not legal advice. Every clock length in this node (SMR, complaint, TMD, licence) is a row of data with a default and a "set with counsel" marker; counsel's answers change rows, not code.

## Build brief

**Scope and placement**

- Module `alerts` in the API (`services/api/src/modules/alerts/`) and the job folder `services/worker/src/jobs/alerts/`, following the module pattern of A09: a public `index.ts` (the only import other modules may use, enforced by the boundary lint), zod schemas that feed the OpenAPI document, and pg-boss jobs registered by the worker. The base `alert` table is declared by A04 "with the row A13 specifies", so the column list below is the contract A04 builds; `alert_type`, `alert_activity`, `alert_template`, `sla_policy`, `sla_clock`, `business_calendar`, `escalation_path`, `alert_digest` and `queue_item_snapshot` are A13's own tables, declared through A04's module-schema registry. Read contracts (list, detail, summary, types, digests, calendar) go into the OpenAPI document in the first commit so `packages/sdk` types exist before the engine passes (A09 rule).
- The only source of time is the injectable clock from A09. `Date.now()`, `new Date()` without an argument and library "now" helpers are forbidden in the owned paths; `npm run verify` greps for them. In `RUN_MODE=local` and `test` the clock-advance endpoint of A09 drives every SLA, snooze, ladder, digest and breach in this node, so a "1 business day" clock is testable in seconds.
- Time zone: all instants are stored as UTC `timestamptz`. Business-day arithmetic runs in an IANA zone that is a platform setting, default `Australia/Sydney` (AEST in winter, AEDT in summer). The zone is a column on `sla_policy` so a later node can give a Queensland sponsor a Brisbane calendar without touching code.

**Alert types (the catalogue) as data**

- `alert_type` rows carry: `code`, `title_template` and `detail_template` (see "No PII" below), `params_schema` (a zod schema per type), `default_severity`, `owner_role` (a role code from A03's role list), `secondary_roles`, `module` (M-code, for the module filter), `need_to_know` (boolean; see below), `sponsor_visible` (whether the sponsor's SP-OWN slice may see it), `closes_by` (`human` or `system`), `dedup_window` (a duration; see "Deduplication and flapping"), `target_screen` (the product-map screen the alert deep-links to), `gate_ref` (optional, e.g. G20), and the policy code of its acknowledgement SLA.
- A13's own seed is exactly **17 catalogue types plus 10 extension types**. The 17 catalogue types (requirements catalogue Appendix A.6): `money.client_money_delta` (Sev2, TRSY + CFO, ADM-18); `recon.break` (Sev2 by default, Sev1 when the emitter passes `qty`, `unknown_holder`, `role_drift`, `rule_drift`, `payout_mismatch`, `snapshot_drift` or `audit_chain_broken`; REGO, ADM-17); `chain.unknown_holder` (Sev1, REGO + CCO, ADM-17); `holdings.near_cap` (Sev2, CCO, ADM-16); `holdings.foreign_threshold` (Sev2, CCO, ADM-16); `aml.smr_clock` (Sev2, Sev1 at breach, MLRO, ADM-25, need-to-know); `ddo.outside_tmd` (Sev2, CCO, ADM-26; P2 flag); `licence.daf_exemption_meter` (Sev2 at 80 %, CCO, ADM-04); `aml.sanctions_list_hit` (Sev1, MLRO, ADM-25, need-to-know); `money.payout_funding_short` (Sev2, TRSY + CFO, ADM-18); `wallet.paymaster_runway` (Sev2, ENGO, ADM-13); `chain.stuck_or_lagging` (Sev3, ENGO, ADM-32; sub-codes `stuck_tx_30m`, `indexer_lag_5m`; dedup window 30 minutes); `property.proof_overdue` (Sev3, PROP, sponsor visible, ADM-22); `property.valuation_stale` (Sev3, VALO, sponsor visible, ADM-06; also carries the "due in N days" pre-warning the design shows); `investor.certificate_expiring` (Sev4, CLSR, ADM-11; T-60 and T-30, and an outbox event for the investor's own notification); `licence.expiry` (Sev3, CCO + LEGL, ADM-04; T-90/30/7); `queue.sla_breach` (Sev3, the queue's owner role, ADM-01).
- The ten extension types (the codes are the contract; the emitter named is the only raiser): `approval.unratified` (Sev2, CCO, ADM-34, `closes_by = system`; raised only by the breach of a `ratification` clock, see "Escalation ladders"; A14 and A48 open those clocks and do not emit this code themselves); `approval.no_eligible_checker` (Sev3, SECO; emitted by A14 when a role change leaves a checker set empty); `agent.kill_switch_fired` (Sev1 platform-wide, Sev2 tenant or user; SECO + CCO; emitted by A48 and A101); `agent.revocation_storm` (Sev2, SECO; raised by A13's own `alerts.agent-watch` detector, below); `agent.anomaly_hold` (Sev2, SECO; emitted by A101); `job.dead_letter` (Sev3, ENGO; emitted by A46); `iam.break_glass_active` (Sev1, CCO + CEO, `closes_by = system`; raised by A13's own `alerts.break-glass-watch` detector, below); `audit.chain_broken` (Sev1, SECO + CCO; raised by A13's `alerts.audit-chain-watch`); `audit.hold_review_due` (Sev4, LEGL; the task A10's hourly hold sweep hands over); and the self-alert `sla.calendar_exhausted` (Sev3, ENGO). Because A11 and A12 sit beside A13 rather than downstream, the break-glass and revocation-storm alerts are not calls from those nodes: A13 detector jobs read A04's `break_glass_session` and `api_token` tables and raise them. A101 may later add a finer revocation detector that emits the same code; dedup keeps one alert.
- **Extension registry.** Later nodes add types and clock policies without editing A13's files: `registerAlertTypes([...])` and `registerSlaPolicies([...])` exported from `index.ts`, modelled on A04's `registerModuleSchema`, called from the owning module's own folder (for example A36's clock rows, A42's AML rows, A45's filing rows, A46's `integration.degraded`, A48's halt and kill-switch policies, A85's observability types, A101's guard types). The registry is validated when the API and the worker boot: unique `code`, owner and secondary roles in A03's role list, `target_screen` in the 91-screen list, `module` in M01-M27, a policy code that exists (seeded or registered), a `params_schema` that passes the PII check below, and `need_to_know` true for every `aml.*` code. Any failure is a boot error, never a runtime surprise; emitting a code that is not registered is also a boot-time check wherever the emitter declares its codes, and a 500 `alert_type_unknown` otherwise.

**Need-to-know alerts (N08, tipping-off; SM-11 "case access limited to MLRO and CCO")**

- Types with `need_to_know = true` (all `aml.*` codes, seeded and registered) are visible to MLRO and CCO only. Enforcement is by row-level security on `app.principal_role`, the same pattern A04 uses for `aml_case`: the `alert` policy hides a row whose type is need-to-know unless the principal holds MLRO or CCO, so the row is invisible, not forbidden. The policy is registered through A04's module-schema registry; if that registry cannot attach a policy to the base `alert` table, that is an A04 spec defect, not a workaround here.
- The rule holds on every path: list, detail, summary counts (by severity, by owner role, `open`, `high`, `breached`), MTTA and MTTR, digests (only the MLRO and CCO digests contain them), `alert.raised` and `alert.page` outbox events (addressed to MLRO and CCO only, never on-call ENGO), bulk acknowledge (a need-to-know id is reported as `not_found`, exactly like an unknown id) and the escalation path (MLRO -> CCO only; a need-to-know alert never escalates to CEO, SECO or ENGO).
- `subject_ref` of a need-to-know alert is the AML case id (`aml_case`), never the investor, and its title and detail come from templates with no investor attribute (for example "SMR clock · case AML-118 · due 17:00 Thu").

**No PII: templates and typed parameters**

- `emit()` takes typed `params`, never free text. Title and detail are rendered from the type's `title_template` and `detail_template`. `params` and `payload` are validated against the type's `params_schema`, which may contain only: references (vehicle, property, sponsor, tenant, approval, job, integration, api_token prefix, aml_case, investor id) whose display label is resolved server-side from the reference (an investor reference renders as its `INV-` id, never a name), bounded enums, integers, amounts, dates and instants. No key may intersect `PII_PATHS` from `@realx/db` (checked at boot). An unknown parameter, an extra key, a free-text string or a label override is refused with `pii_refused` (HTTP 422 on the test endpoint; a thrown typed error on the module interface), and nothing is written.

**Alert model**

- `alert` row: `id` (`ALT-<yyyymmdd>-<6 base32>`), `type_code`, `severity` (1-4), `tenant_id` (platform tenant for RealX-wide alerts), `subject_ref` (typed reference: vehicle, investor, token, approval, job, api_token, tenant, aml_case, staff_user), `params_json`, `title` and `detail` (rendered), `payload_json` (references only), `owner_role`, `escalation_level` (0 at creation), `assignee_id`, `state`, `dedup_key`, `occurrences`, `first_seen`, `last_seen`, `ack_due_at`, `acknowledged_at/by`, `breached_at`, `snoozed_until`, `resolved_at/by`, `resolved_by_system` (boolean), `display_tone`, `target_screen`, `emitted_by` (module code and, when a request caused it, the actor and `on_behalf_of`).

**The `ALERT` lifecycle (local to this module; not one of SM-00..SM-13)**

States (7): `new`, `acknowledged`, `assigned`, `escalated`, `snoozed`, `resolved`, `reopened`. Human actions (6): `acknowledge`, `assign`, `escalate`, `snooze`, `resolve`, `reopen`. System actions (6): `breach`, `ladder_step`, `upgrade`, `snooze_expire`, `resolve_by_system`, `reopen_by_system`. `breached` is a flag, not a state. The acknowledgement clock runs only in `new` and `reopened`.

- The `escalated` state is for manual escalation only. Breach escalation changes `owner_role`, `escalation_level` and `breached_at` without changing the state.
- Open states are every state except `resolved`. Human `resolve` on a `closes_by = system` type is refused with 409 `system_closed`, naming the closing condition (for example "closes when the reconciliation re-run is clean").
- Forbidden human pairs: 7 states x 6 actions = 42 pairs, minus the 23 allowed human rows = **19 forbidden pairs**. The 5 forbidden pairs from `resolved` (every action except `reopen`) return 409 `alert_closed`; the other 14 return 409 `transition_not_allowed` with the current state. The test counts are derived from the table above, never typed by hand.
- Snooze is never allowed from `new` or `reopened`, so the acknowledgement clock keeps running until a person acts.

**Acknowledgement SLAs, breach escalation and notifications**

- Acknowledgement SLA by severity, as `sla_policy` rows: Sev1 15 minutes elapsed; Sev2 1 hour elapsed; Sev3 1 business day; Sev4 no clock. The clock starts at `first_seen` (or at reopen) and stops as the table says.
- On breach (Sev1, Sev2 and Sev3): the owner role moves one step up the `escalation_path` table. Sev1 and Sev2 go to CCO, plus on-call ENGO for `chain.*`, `wallet.*`, `job.*` and `agent.*` types; need-to-know types go MLRO -> CCO only. Sev3 goes to the owner role's head (REGO -> CCO, TRSY -> CFO, ENGO -> SECO, PROP -> CCO, VALO -> CCO, CLSR -> CCO, MLRO -> CCO, SECO -> CCO, CCO -> CEO, LEGL -> CCO). A Sev1 breach also writes one `alert.page` outbox event so the notifications node (A43) can page; the pager is a sandbox channel until human gates open real channels.
- **Creation and upgrade notices.** Every creation, emitter upgrade and ladder step of a Sev1 or Sev2 alert writes one `alert.raised` outbox event (`mode: page` for Sev1, `notify` for Sev2) addressed to the owner role (MLRO and CCO only for need-to-know types). Sev3 and Sev4 reach people through the digest and the console. So a Sev1 pages on-call when it is raised, as the product map requires, and `alert.page` is kept for breach escalation.
- Severity upgrade from an emitter keeps the owner role; downgrades are not accepted from emitters (a human may resolve and the emitter may raise anew).

**Escalation ladders**

- `sla_policy.escalation_ladder` is an ordered list of steps `{after_ms, new_severity, new_owner_role}`, measured from the clock's `started_at`. The breach detector applies each due step once to the alert that clock raised, in place, with one `alert.upgraded` audit event per step and the `alert.raised` notice above. A ladder step may change the owner role; an emitter upgrade may not.
- Seeded ratification policies: `ratification.sgl_r` (2 h, on breach `approval.unratified` Sev2 owner CCO; ladder: at 4 h Sev1, owner CEO), `ratification.halt` and `ratification.kill_switch` (2 h, same breach and ladder), `ratification.board` (24 h, `set_with_counsel`, same ladder shape at 48 h). A14 opens a `ratification.sgl_r` clock for every SGL+R act and meets it on ratification; A48 opens the halt, kill-switch and (P2) board clocks. The breach of that clock is the only raiser of `approval.unratified`; A14's own ratification sweep keeps the lapse state, its `action.ratification_lapsed` audit and the revert request, but does not emit an alert. When the act is ratified late or reverted, the owning node calls `resolveBySystem`; meeting a breached clock also resolves its alert by system.

**Deduplication and flapping**

- `emit()` takes a `dedup_key` (default: type + subject). If an open alert with that key exists, `occurrences` increments, `last_seen` updates, an `alert_activity` row records the repeat, and no new alert or audit event is written (a higher severity is an upgrade, above).
- `dedup_window`: if no open alert matches but an alert with that key was resolved **by the system** within the type's `dedup_window`, the emit reopens it by system (`reopen_by_system`: no reason, one `alert.reopen` audit event, `occurrences` + 1, fresh ack clock). A human-resolved alert is never reopened by an emit; a new alert is created. Outside the window a new alert is created.

**Actions, reasons and permissions**

- `acknowledge` (no reason), `assign` (to a user who holds the owner role or a role in the escalation path; reason optional), `escalate` (reason mandatory; moves the owner role one step up the path, or to a named role that is above the current owner on the path), `snooze` (reason mandatory; never for Sev1; Sev2 at most 4 hours; Sev3 and Sev4 at most 5 business days; `snoozed_until` for business days follows the business-day rule below), `resolve` (reason mandatory), `reopen` (reason mandatory). A reason is a non-empty trimmed string of at most 500 characters; missing or blank returns 422 `reason_required`. Reasons are stored in `alert_activity` and the audit event, not rendered into titles.
- `bulk-acknowledge` takes up to 200 ids and is all-or-nothing: if any id is Sev1 or Sev2, not in an acknowledgeable state, unknown or outside the caller's scope, the whole request is refused with 422 `bulk_refused` listing every offending id with a reason code (`severity`, `state`, `not_found`; an out-of-scope or need-to-know id is `not_found`, indistinguishable from an unknown id) and nothing is acknowledged. A successful bulk writes one audit event per alert, not one per request.
- Permissions come from the role x module x action matrix in `packages/domain` (module M01, actions `alerts:read`, `alerts:act`, `alerts:bulk`, `alerts:resolve`). CCO sees every alert; SECO and CEO see every alert except need-to-know types; every other staff role sees alerts whose owner role or escalation path includes one of its roles (MLRO also sees need-to-know types); SP-OWN and SP-OPS see only `sponsor_visible` alerts of their own tenant through row-level security; investors have no alert endpoints. TP-AUD and TP-OBS read only, and never see need-to-know types.
- **Self-subject rule (D04: segregation of duties counts the agent as its human).** An alert is "about" a person when its subject is that person, any API token of that person, or an anomaly hold or user-level kill switch aimed at that person. For such an alert the person may **acknowledge** it (with a passkey session), but `snooze`, `assign`, `resolve` and `escalate` to a named role are refused with 403 `self_subject`. A token of that person may take no action on it at all (403 `self_subject`), and a token may also take no action on a tenant-level kill-switch alert for its own tenant. At creation, an alert about a person who holds the type's owner role is routed to that role's head on the escalation path (for example a SECO's own token on hold goes to CCO; a CCO's goes to CEO).
- Agent parity (D04, G22): every endpoint below is in the public OpenAPI document under module scope M01 with A09's operation extensions (`x-realx-scope`, `x-realx-gates`, `x-realx-screens`, `x-realx-mutation`, `x-realx-money`) and `x-realx-requires-human: false`, so a staff member's agent token can list, acknowledge, assign, escalate, snooze and resolve exactly what its human can, as maker, subject to the self-subject rule. Acknowledging an alert is not a checker or ratification act, so nothing here breaks the never-checker rule (ratification lives in A14 and is refused to tokens there). Every action taken under a token is audited as the token on behalf of the person and appears in the token's activity (A12).
- Audit: every creation, transition, upgrade, ladder step, breach and digest writes exactly the `AuditEvent`s named in the table through A10, with `actor_id`, `on_behalf_of_id`, `action` (`alert.created`, `alert.ack`, `alert.assign`, `alert.escalate`, `alert.snooze`, `alert.resolve`, `alert.reopen`, `alert.upgraded`, `alert.breached`, `alert.digest_sent`) and `object_ref`. Creation writes one `alert.created`; a breach writes exactly `alert.breached` plus `alert.escalate`; repeated occurrences write none.

**SLA clocks as a primitive**

- `sla_clock` row: `id`, `kind` (`ack`, `ratification`, `queue`, `custom`), `subject_ref`, `policy_code`, `policy_version`, `started_at`, `due_at`, `state` (`running`, `met`, `breached`, `cancelled`), `on_breach_type`, `on_breach_params`, `ladder_steps_applied`, `raised_alert_id`, `met_at`, `breached_at`. Alerts' own acknowledgement clocks are rows of this table, so there is one breach detector.
- Module interface for other nodes: `openClock({kind, subjectRef, policyCode | dueAt, onBreach})`, `meetClock(id | subjectRef)`, `cancelClock(id, reason)`, `businessDaysAfter(instant, n, calendarCode)`, `isBusinessDay(date, calendarCode)`, `emit({typeCode, subjectRef, severity?, params, payload?, dedupKey?, tenantId})`, `resolveBySystem({typeCode, subjectRef, reason})`, `registerAlertTypes([...])`, `registerSlaPolicies([...])`, `registerQueueSource(source)`. A42 opens SMR clocks in business days; A20 raises breaks and resolves them by system; A14 and A48 use ratification clocks as above.
- `sla_policy` rows seeded with the catalogue's N06 values and a `set_with_counsel` flag where the requirements say so: ack Sev1 15 min, Sev2 60 min, Sev3 1 business day; identity check 24 h elapsed; SMR 3 business days and 24 h (terrorism financing); outside-TMD 10 business days; refund 5 business days; distribution 10 business days; complaint acknowledgement and complaint final response (catalogue placeholders, set with counsel: the seeded defaults are acknowledgement 1 business day and final response 30 calendar days, both `set_with_counsel`; the catalogue's "acknowledgement by day 5 of 7" wording is a counsel question, see Human gates); approval TTL 72 h; timelocks 48 h and 72 h; the four ratification policies above. Kinds: `elapsed`, `business_days`, `calendar_days`. Rows are versioned (`effective_from`); a clock stores the policy version it used.
- **Business-day rule, fixed so the node QA can test it:** a clock of N business days is due at close of business (17:00 local, a column of the policy) on the **Nth business day strictly after the local date of the trigger**. The time of day of the trigger does not matter, and whether the trigger day is itself a business day does not matter. So a trigger on a non-business day makes the next business day day 1, and a trigger on a business day after 17:00 behaves the same way as one before 17:00. Weekends and every date in `business_calendar` for the calendar code are skipped. Arithmetic is done in local civil time, never by adding multiples of 86,400 seconds, so the AEDT start (first Sunday of October) and end (first Sunday of April) produce the right local time. Calendar-day clocks are due at 17:00 local on the Nth calendar day after the trigger date.
- `business_calendar` table seeded from a data file with national and NSW public holidays for 2026, 2027 and 2028 (including the Easter dates, King's Birthday, Labour Day and the Christmas to New Year substitutes as gazetted), plus a `calendar_code` (`AU-NSW` default; `AU-QLD`, `AU-VIC` files may be added later as data). Asking for a business-day calculation beyond the last seeded year is refused with 422 `calendar_exhausted` and raises the `sla.calendar_exhausted` self-alert once per day (dedup).

**Worker jobs (all scheduled through A09's scheduler, never pg-boss cron)**

A09's `scheduler.tick` fires plain cron schedules against the injected clock, idempotent per `(job, due instant)` in `job_schedule_fire`. A09's cron has no time-zone parameter, so local-time jobs use an hourly UTC cron and check the local hour inside the handler; because Sydney's offsets are whole hours and DST changes at 02:00-03:00, a tick at minute 0 of every UTC hour hits local 07:00 exactly once on every local date, including both DST-change days.

- `alerts.breach-detector` (every minute): moves running clocks past `due_at` to `breached`, raises the configured alert or applies the breach escalation, applies due ladder steps, writes the page and raised events; idempotent and replayable (re-running over the same minute changes nothing).
- `alerts.snooze-expiry` (every minute): returns snoozed alerts whose `snoozed_until` has passed to `acknowledged`.
- `alerts.queue-sla` (every five minutes): asks each registered `QueueSource` (identity cases, complaints, approvals, withdrawals, registry acks, sponsor attestations, agent anomaly holds; in AM1 only a fixture source and the approvals TTL source exist, later nodes register theirs) for items with `entered_at`, a policy code and template params, stores them in `queue_item_snapshot`, opens or updates one `queue` clock per item, and raises `queue.sla_breach` with the queue's owner role on breach, dedup per queue and item.
- `alerts.agent-watch` (every minute): counts `api_token` revocations (`revoked_at` in A04's table) in a trailing window per tenant and per person, and raises `agent.revocation_storm` (dedup per tenant or person) when a threshold row is crossed (defaults, as data: 20 revocations in 5 minutes per tenant, 5 per person); resolves by system when the rate falls below half the threshold for 30 minutes.
- `alerts.break-glass-watch` (every minute): raises `iam.break_glass_active` for every active row of A04's `break_glass_session` (dedup per session) and resolves it by system when the session ends. It runs as the worker service account; if A04's need-to-know policy hides that table from the service account, that is an A04 spec defect.
- `alerts.digest` (hourly UTC cron; acts only when the local `Australia/Sydney` hour is 07): one digest per role that owns at least one open alert visible to it, listing open alerts by severity, breaches in the last 24 h, snoozes ending today and clocks due within 24 h; stored as `alert_digest` (`date`, `role`, `content_json`, `sent_at`, unique on `(date, role)` as a second guard) and emitted as an `alert.digest` outbox event for A43 to deliver. Exactly one digest per (date, role): re-running the job the same day is a no-op. A46 lists this schedule as emitted by the alerts service.
- `alerts.audit-chain-watch` (hourly): raises `audit.chain_broken` Sev1 if A10's last verification failed or none has succeeded for more than 26 hours.

**HTTP API (all under `/v1`, cursor pagination, idempotency keys on writes, in the OpenAPI document from the first commit)**

- `GET /v1/alerts` with filters `severity`, `state`, `type`, `module`, `owner_role`, `assignee` (`me` | `none` | a user id), `tenant_id`, `subject`, `breached`, `since`; default sort severity ascending then `ack_due_at`. Each row returns `display_tone`, `target_screen`, `first_seen`, `time_label`, `age_ms`, `sla_remaining_ms`, `allowed_actions[]` (for the caller, after permissions, state and the self-subject rule) and `snooze_max_until` (null when snooze is not allowed), so ADM-02's columns (ID, Sev, Rule, Object, Created, Owner, State), its "Mine" and "Unassigned" chips, and ADM-01's rows (pill, text, mono time) are direct reads.
- `GET /v1/alerts/summary` returning `open`, `high`, `breached`, counts by severity and by owner role, `mtta_ms` and `mttr_ms` by severity over the trailing 7 and 30 days (mean of acknowledgement and resolution times of alerts first seen in the window; null when there is no sample), `queues` (name, items, oldest age, past SLA) and `queue_items` (the oldest items per queue: `title`, `detail`, `object_label`, `entered_at`, `age_ms`, `time_label`, `target_screen`, tone `review`), all filtered by the caller's visibility.
- `GET /v1/alerts/digests?date=&role=` returns the stored digest; a caller may read the digest of a role it holds, CCO may read any, and the MLRO digest is readable by MLRO and CCO only. `GET /v1/alerts/{id}` with its activity and audit refs; `GET /v1/alerts/types`; `POST /v1/alerts/{id}/acknowledge | assign | escalate | snooze | resolve | reopen`; `POST /v1/alerts/bulk-acknowledge`; `GET /v1/sla/clocks?subject=`; `GET /v1/sla/policies`; `GET /v1/sla/calendar?code=&year=`.
- **Time-label rule (server-computed in `Australia/Sydney` from the injected clock; raw instants are returned too):** for an alert, `HH:mm` (24-hour) when `first_seen` falls on today's local date, `Yesterday` when on the previous local date, otherwise `d MMM` (for example `3 Oct`); for a queue item, its age floored: under 60 minutes `<n>m`, under 48 hours `<n>h`, otherwise `<n>d`.
- Test-only: `POST /__test/alerts/emit` (outside `/v1`, absent from the OpenAPI document and therefore from the SDK and MCP, 404 in every mode other than `local` and `test`, per A09's `/__test/*` convention) so e2e and the node QA can raise any registered type without another module; it goes through the same template, params and PII checks as `emit()`.
- Empty and error states: an empty list is `{items: [], next: null}`; summary with nothing open is all zeros with `queues: []`, `queue_items: []` and null MTTA/MTTR; acting on a resolved alert returns 409 `alert_closed`; a snooze past the policy maximum returns 422 `snooze_too_long` with the maximum; an unknown id is 404; a tenant user asking for another tenant's alert, or anyone outside need-to-know asking for an AML alert, gets 404, never 403 (no existence leak).

## Node-specific challenges (node QA)

- **Daylight saving and holiday arithmetic.** A Sev3 alert raised at 15:00 on Saturday 3 October 2026 (AEST): the first business day strictly after Saturday is Tuesday 6 October (Monday 5 October is Labour Day in NSW), so it is due at 17:00 on Tuesday 6 October 2026 AEDT (DST began on Sunday 4 October), which is 06:00 UTC, not 07:00. A Sev3 alert raised at 18:30 on Tuesday 6 October 2026 AEDT (after close of business on a business day) is due at 17:00 on Wednesday 7 October 2026 AEDT (06:00 UTC). A 3-business-day SMR clock opened at 10:00 on Thursday 25 March 2027 must skip Good Friday (26 March) and Easter Monday (29 March) and land on Thursday 1 April 2027 17:00 AEDT (06:00 UTC); a 3-business-day clock opened at 10:00 on Thursday 1 April 2027 must land on Tuesday 6 April 2027 17:00 AEST (07:00 UTC) after the DST end on Sunday 4 April. All of these hold under the single rule in the build brief. The 07:00 digest must fire exactly once on 4 October 2026 and once on 4 April 2027. An implementation that adds 86,400-second multiples, uses the server's zone, counts the trigger day, or ignores the holiday table fails at least one of these.
- **Storm and flapping (A13's own fixture emitter and `/__test` endpoint).** 5,000 emits of `agent.anomaly_hold` with one dedup key inside one minute: one open alert, `occurrences` 5,000, exactly one `alert.created` audit event, one `alert.raised` outbox event, a list endpoint that still answers in under 200 ms. Then `chain.stuck_or_lagging` (dedup window 30 minutes) flipped 300 times inside 10 minutes of injected time, each flip an emit followed by `resolveBySystem`: one alert, `occurrences` 300, final state `resolved`, and exactly 1 `alert.created`, 300 `alert.resolve` and 299 `alert.reopen` audit events; the next day's ENGO digest shows it once. Then, with a revocation fixture that writes 25 `api_token` revocations in one tenant inside 5 minutes of injected time, `alerts.agent-watch` raises exactly one `agent.revocation_storm`. Any duplicate alert, extra or missing audit event, or lost occurrence count fails.
- **Bulk acknowledge with a hidden Sev1.** Fifty ids of which forty-nine are Sev3 or Sev4 and one is a Sev1 register break: the whole request must be refused with the offending id named and none of the fifty acknowledged; the same forty-nine without the Sev1 must succeed with exactly forty-nine audit events. Adding an AML alert id for a SECO caller must be reported as `not_found`, exactly like a random id. Partial success, a request-level audit event, or a distinguishable need-to-know id fails.
- **An agent, or its human, acting on the alert about itself.** SECO Jordan's agent token is placed on an anomaly hold (fixture emit of `agent.anomaly_hold` with the token as subject): the alert is owned by CCO, not SECO. Any action from that token, or from any other token of Jordan's, returns 403 `self_subject`. Jordan signed in with a passkey may acknowledge it, but snooze, assign, resolve and escalate to a named role return 403 `self_subject`. A tenant-level kill-switch alert for Jordan's tenant refuses every token of that tenant the same way. If any of these succeeds, the node fails. **[needs A11/A12]** for real sessions and tokens.
- **Need-to-know (tipping-off).** With an open `aml.smr_clock` and `aml.sanctions_list_hit` whose subject is a case id: SECO, CEO, SUPP, TP-AUD, TP-OBS, SP-OWN and a SECO token each get 404 on the detail, do not see them in the list, and do not see them in `open`, `high`, the severity and owner-role counts, MTTA and MTTR, or their digests; the Sev1 `alert.raised` event and any breach page are addressed to MLRO and CCO only (no ENGO on-call); a breach escalates MLRO -> CCO; no title, detail or payload contains an investor id or attribute. MLRO and CCO see both.
- **Ratification ladder.** One SGL+R act whose `ratification.sgl_r` clock is never met: at 2 h exactly one `approval.unratified` alert exists (Sev2, owner CCO, one `alert.created`, one `alert.raised`); at 4 h the same alert is Sev1 owned by CEO with exactly one `alert.upgraded` event and one `alert.raised` (page); there is never a second alert for the lapse. Ratifying late resolves it by system.
- **Snooze as a way to hide a breach.** A Sev1 snooze attempt must be refused; a Sev2 snooze of 30 days must be refused with the 4-hour maximum; a Sev3 alert snoozed for 5 business days must reappear as `acknowledged` on the first minute after the snooze ends under the injectable clock; snoozing must never be possible from `new` or `reopened` (the acknowledgement clock keeps running until someone acts). A snooze that stops the breach detector or that is accepted from `new` fails.
- **No PII by construction.** The fixture emitter tries an extra `investor_name` parameter on `investor.certificate_expiring` and a `title` override on `recon.break`; both must be refused with `pii_refused` and write nothing. A registered type whose `params_schema` has a key in `PII_PATHS` must fail boot.
- **Design fidelity of the read models [needs A06].** With A06's standard seed and the injected clock at its as-of instant, `GET /v1/alerts/summary` must return `open: 3, high: 1` and `GET /v1/alerts` must return the three design rows with the exact title and detail strings listed under Design references, `display_tone` high, medium, medium, `time_label` `06:02`, `05:00`, `Yesterday`, and `target_screen` ADM-17, ADM-11, ADM-06; `queue_items` must contain "Listing waiting for review" / "Marine Parade Apartment · Harbour & Co" with `time_label` `5h`, tone `review` and target ADM-07. A seed that turns the queue item into an alert or counts Sev3 as high fails.
