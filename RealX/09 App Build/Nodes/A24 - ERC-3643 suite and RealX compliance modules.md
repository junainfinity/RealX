# A24 - ERC-3643 suite and RealX compliance modules

**The on-chain mirror of one property trust: a shared identity layer deployed once per chain (identity registry storage, trusted issuers, claim topics KYC_VERIFIED, SANCTIONS_CLEAR, WHOLESALE_AU, RESIDENCY_FIRB, TMD_FIT, the RealX claim issuer and the ONCHAINID factory) and, per trust, a 0-decimal T-REX token with 10,000 units by default, its own identity registry bound to the shared storage, and a modular compliance stack (country allow, max balance as the holder cap, RealX holder count, RealX lock-in set at mint, RealX halt flag distinct from pause, supply limit, RealX acquisition-claim check for the wholesale certificate) plus a document anchor, all deployed by a factory script at CREATE2 addresses that are the same on every chain. The chain's `canTransfer` is the last line of G01, G06, G07, G08 and G10, not the first; the off-chain rules engine (A19) runs first and the register (A18) stays the legal record.**

**Build status:** not started. **Milestone:** AM2 (Token and wallet core). **Lane:** Chain. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops).

**Depends on:** [[A07 - Local chain and contracts toolchain (Hardhat, T-REX vendored)]]
**Unlocks:** [[A25 - AgentGateway and owner multisig- approval IDs bound on-chain]], [[A27 - Chain adapter, deployment manifests and indexer]], [[A91 - P2- resale board market module (SM-09)]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A24\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder; the cases are published into the repo only after the gate passes. The oracle scope is fixed by the node summary: `canTransfer` vectors for every module; forced transfers blocked while paused; a wallet not in the identity registry cannot receive; the module parameter hash matches the approved rule. The vectors use the JSON schema in brief item 6 so the node QA can write them blind. They run through two runners that must agree: the builder's harness, and a minimal independent runner the node QA ships in the hidden folder (see brief item 6), so a harness that swallows reverts or misreads `expect` cannot let a wrong build pass.

This node is the first RealX Solidity. It runs entirely on the Hardhat chain from A07 with keys that carry no value. Supply, holdings and eligibility move on-chain here for the first time, which is why it is an oracle node; nothing here talks to a register, a ledger, a bank or a vendor, and mainnet stays behind HG-AUDIT and HG-PROD. Q12 option 1 (T-REX plus rented services behind adapters) is assumed as a proposed, reversible engineering decision; the swap points are named in the requirements section. This plan is not legal advice.

## Build brief

**1. Workspace, compiler and licence boundary**

- RealX Solidity lives in `contracts/src/token/` (`RealXClaimIssuer.sol`, `DocumentAnchor.sol`, `SuiteInspector.sol`, `ClaimTopics.sol`, `IsoCountries.sol`, `RealXCreate2Deployer.sol`) and `contracts/src/compliance/` (`HolderCountModule.sol`, `LockInModule.sol`, `HaltModule.sol`, `AcquisitionClaimModule.sol`, `RuleHash.sol`, and `RealXModuleBase.sol` if the builder chooses not to inherit T-REX's `AbstractModuleUpgradeable`). Everything else on-chain is the vendored T-REX v4.1.x and `@onchain-id/solidity` from A07, compiled from `contracts/vendor/` and never copied or patched. A07's "no `.sol` outside `vendor/`" check is replaced by "no `.sol` outside `contracts/src/` and `contracts/vendor/`"; A07's licence-boundary grep (no T-REX or ONCHAINID code outside `contracts/vendor/` and generated artifacts) stays and now also covers `contracts/src/` for copied text, since inheriting is allowed and copying is not.
- RealX contracts use the same solc version and optimizer settings as the vendored suite (`pragma solidity 0.8.17` unless `contracts/TOOLCHAIN.md` from A07 records that the pinned tag builds on a later compiler), so the interfaces match byte for byte and A07's "compile twice, byte-identical" property still holds for the whole project. Every RealX file carries an SPDX header; files that inherit vendored GPL-3.0 code are marked GPL-3.0 by default as the safe assumption, `contracts/vendor/LICENSE-NOTES.md` gains a list of every RealX file that inherits vendored code (contract, parent, why), and counsel may relax the marking under HG-LEGAL. No ABI, address or type crosses into `packages/*` except through `packages/contracts` (A27 wires it; this node only writes the ABI export list in `contracts/deploy/suite/exports.json`).
- Compact custom code is a goal, not a hint: the four RealX modules, the rules hash, the claim issuer, the document anchor, the CREATE2 deployer and the inspector together stay under about 800 lines of Solidity excluding comments, tests and the `IsoCountries.sol` data table, and `contracts/src/AUDIT-SCOPE.md` lists every RealX contract with its line count, its parents, its privileged functions and who may call them. That file is the input to HG-AUDIT.

**2. Shared identity layer (deployed once per chain by `deploy-shared.ts`)**

- `IdentityRegistryStorage` (vendored): one storage for the whole marketplace, so an investor verified once is known to every trust's identity registry ("one KYC, many tokens"). Per-token `IdentityRegistry` contracts are bound to it with `bindIdentityRegistry`; only bound registries may write. Country codes are ISO 3166-1 numeric (`36` = Australia).
- **What the IR `country` field means (G06).** The field is A19's G06 classification written as a country code, not the residence address: `36` when A30/A19 classify the person as **not** a foreign person under the FATA test (Australian citizens wherever they live, permanent residents and Australian-controlled entities), and otherwise the ISO numeric code of the person's nationality (an individual) or controlling jurisdiction (an entity, from A30's KYB). A temporary-visa holder living in Australia is therefore registered with their nationality's code, not `36`, and is refused by `CountryAllowModule` on an established-residential trust; an Australian citizen living in London is registered as `36` and is accepted. `CountryAllowModule` only ever sees this field. Test vectors: a temporary resident (setup country = their nationality, e.g. `554`) is refused on a residential trust with `CountryAllow` as the failing row; a citizen abroad (setup country `36`) is accepted. Writing this value is A31's job (cross-node: A31 currently writes "ISO numeric of the confirmed residency" and must write the G06 classification code instead, from A30's `foreign_person` flag). The `RESIDENCY_FIRB` claim attests the same classification plus the FIRB position: its `evidenceHash` is the hash of A30's classification record `{ foreign_person, classification_basis, firb_ref?, firb_valid_until? }` at issue time, and its `validUntil` is `firb_valid_until` when a FIRB approval is the basis, else the KYC refresh date. Whether a fractional unit in a trust over established residential property is itself an "interest" that FATA treats as an acquisition by a foreign person (and so whether the `36`-only rule is too strict or too loose) is an HG-LEGAL question, recorded below; the code does not decide it.
- `TrustedIssuersRegistry` (vendored): the `RealXClaimIssuer` is trusted for all five topics; a second slot is left for a later external credential issuer (Averer-type), added only by the registry owner (V1 in A25; the deployer account locally). A test proves a claim from an untrusted issuer never counts.
- `ClaimTopicsRegistry` (vendored): the five topic ids are `keccak256` constants in `ClaimTopics.sol` (`KYC_VERIFIED`, `SANCTIONS_CLEAR`, `WHOLESALE_AU`, `RESIDENCY_FIRB`, `TMD_FIT`). Reconciliation with the rule packs: a token's `isVerified` requires a valid claim for every topic in the registry its identity registry is bound to, so one instance is deployed per rule pack code, not one for the chain. The topics split into two kinds:
  - **Holding topics** (in the claim-topics registry, checked by `isVerified` on every receipt including forced transfers): `KYC_VERIFIED`, `SANCTIONS_CLEAR`, `RESIDENCY_FIRB` for both `AU-W-2026.1` and the P2 stub `AU-R-2027.1`.
  - **Acquisition topics** (not in the claim-topics registry; checked by the RealX `AcquisitionClaimModule` only on a mint and on a transfer whose receiving identity differs from the sending identity): `WHOLESALE_AU` for `AU-W-2026.1`, `TMD_FIT` for `AU-R-2027.1`.
  - This split is what G04 requires ("expiry blocks new purchases, not holdings"): a holder whose two-year certificate has lapsed still passes `isVerified`, so they can sell to another eligible identity, their own wallets can be recovered, units can be moved between wallets of their own identity, and a court-ordered forced transfer can reach them; they cannot receive a mint or a transfer from another identity. A P1 wholesale token never demands a TMD claim, and a P2 retail token never demands a wholesale certificate. Cross-node: A31's statement that `AU-W-2026.1` "requires 1, 2, 3 and 4" on the registry must be read as holding topics 1, 2, 4 plus acquisition topic 3. The rule pack code is a deploy parameter and appears in the manifest. `RuleHash.sol` keeps a write-once map `claimTopicsRegistry → keccak256(bytes(rulePackCode))`, set by the shared layer's owner in `deploy-shared.ts` when each pack's registry is deployed, so the rule pack code is readable on-chain from the token's identity registry.
- `RealXClaimIssuer` (inherits the ONCHAINID `ClaimIssuer`): management key is the deployer locally (the V1 owner multisig after A25); the claim-signing key is the V4 identity agent address (A07 `accounts.json` account 10 locally; a custody-held key later). Claims are ERC-735 scheme 1 (ECDSA) over `(identity, topic, data)`; `data` is ABI-encoded `(uint64 validUntil, bytes32 evidenceHash)` and carries no PII. `isClaimValid` is overridden to return false when `block.timestamp > validUntil` or the claim was revoked (`revokeClaimBySignature`), so an expired wholesale certificate (two-year validity, product map G04) stops new acquisitions without a chain transaction (through `AcquisitionClaimModule`, which calls the same `isClaimValid`). **Check at Specify:** whether `ClaimIssuer.isClaimValid` in the pinned `@onchain-id/solidity` tag is declared `virtual`; record the answer in `contracts/TOOLCHAIN.md`. If it is not, the fallback is fixed now so Build does not stall: `RealXClaimIssuer` becomes a RealX `IClaimIssuer` built on the vendored `Identity` (inherit `Identity`, implement `isClaimValid`, `revokeClaimBySignature`, `revokeClaim` and `isClaimRevoked` in RealX code, listed in `AUDIT-SCOPE.md` and `LICENSE-NOTES.md`), with the same ABI and the same expiry rule. A V4 job that revokes expired claims is not an acceptable substitute, because a missed job would leave an expired certificate valid on-chain. Issuing and revoking claims stays off-chain work for A31; this node ships the contract, the signing helper `deploy/suite/claims.ts` (sign, encode, verify) and its test vectors.
- ONCHAINID factory (vendored `IdFactory` bound to the shared implementation authority): one `Identity` per investor, created at a CREATE2 address from a salt the caller supplies (A31 uses the investor id hash). `deploy-shared.ts` registers the `TREXFactory` as a token factory on the `IdFactory` (`addTokenFactory`) so `deployTREXSuite` can create each token's own identity.
- **ONCHAINID key layout (every investor identity).** Keys are `keccak256(abi.encode(address))` as ONCHAINID requires:
  | Key | Purpose | Why |
  |---|---|---|
  | the investor's wallet (an EOA in this node's tests; the passkey smart account once A26 exists) | 1 management | the investor controls their own identity |
  | RealX recovery key `R` (the deployer locally; a V1-controlled custody key slot later, HG-KEYS) | 1 management | lets RealX add a recovered wallet and remove the lost one when the investor's only management key is gone (J09) |
  | V4 identity agent (A07 `accounts.json` account 10 locally) | 3 claim | ONCHAINID lets only a claim key (or a management key) call `addClaim` and `removeClaim` on the identity; A31 adds claims through V4 |
  The helper `deploy/suite/identity.ts` `createInvestorIdentity(wallet, salt)` produces this layout and is what the tests and A31 call. Preferred path on the pinned tag: `IdFactory.createIdentityWithManagementKeys(wallet, salt, [R])`, then `R` calls `addKey(V4, 3, 1)` and `addKey(wallet, 1, 1)`; if the tag only offers `createIdentity(wallet, salt)`, the wallet's first transaction adds `R` and `V4` (tests do this with the EOA; A29 does it inside wallet creation, cross-node). The builder confirms the function names at Specify in `TOOLCHAIN.md`; if the layout cannot be produced without patching the vendored factory, escalate before Build. Tests: on a fresh identity, V4 can `addClaim` and `removeClaim`, a stranger cannot; `R` can `addKey(newWallet, 1, 1)` and `removeKey(lostWallet, 1)` after the lost wallet is gone; V4 cannot add or remove a management key. A wallet is "registered" only when the token's identity registry maps it to an identity with a country; `registerIdentity`, `updateCountry`, `updateIdentity` and `deleteIdentity` are agent functions of the identity registry (the V4 agent later, the deployer locally).

**3. Per-trust suite (deployed by `deploy-vehicle.ts`)**

- `Token` (vendored T-REX, behind the vendored `TokenProxy` and implementation authority as upstream intends): `decimals() = 0`, name `RealX <Trust name> Units`, symbol `RX` plus A06's vehicle code (the eight seed symbols are `RXKST01`, `RXMRN01`, `RXBAY01`, `RXANN01`, `RXHAW01`, `RXMPA01`, `RXGYM01`, `RXUNL01`), `onchainID` set to the token's own identity from the factory. **Start state:** the pinned tag's `Token.init` leaves the token paused (the builder confirms this at Specify and records it in `TOOLCHAIN.md`; A27 already assumes it), and `mint`/`batchMint` do not require unpaused, so issuance happens while paused. The step from issuing to trading is `HaltModule.activate(compliance)` followed by the token's `unpause()` under one approval (A28 composes both). Units are whole numbers; a test asserts `decimals() == 0` and that `mint(1)` is one unit, which is what the prototype's "each property has 10,000 tokens" and the `ProofBand` "units = tokens" line mean.
- `IdentityRegistry` per token, bound to the shared storage, the shared trusted-issuers registry and the claim-topics registry of the token's rule pack. `deployTREXSuite` always creates a fresh trusted-issuers registry and claim-topics registry for each token, so `deploy-vehicle.ts` re-points the new IR afterwards with `setTrustedIssuersRegistry(sharedTIR)` and `setClaimTopicsRegistry(ctrForRulePack)` (IR owner calls) and reads both back; the per-token registries the factory created are left unused and listed as such in the manifest. Binding the IR to the shared storage needs the caller to hold the storage's binding right (owner or agent, per the pinned tag; confirmed at Specify): `deploy-shared.ts` gives the `TREXFactory` that right on the storage so the `irs` parameter of `deployTREXSuite` works, or, if the tag's factory cannot bind an external storage, `deploy-vehicle.ts` binds the IR manually with `bindIdentityRegistry`. Either way the read-back checks that the storage's linked registries include the new IR.
- `ModularCompliance` per token with these modules bound in this order (modules are the plug-and-play kind: deployed once per chain, keyed by compliance address, bound by `addModule` and configured through `callModuleFunction` by the compliance owner):
  - **`CountryAllowModule`** (vendored) — G06. The allowed-country list is derived from A19's `foreign_policy` for the vehicle, which A19 itself derives from the property type, by this exact mapping (implemented once in `deploy/suite/rule-params.ts` and used by the deploy script and by `ruleParamsFromCompliance` below):
    | A19 `foreign_policy` | `foreign.allowed` flag off (the default until counsel answers) | `foreign.allowed` on |
    |---|---|---|
    | `blocked` (established residential) | `[36]` | `[36]` (the flag is ignored; a params file that sets it is refused) |
    | `after_firb_check` (commercial, industrial, build-to-rent and the other FIRB-check classes) | `[36]` | `[36]` ∪ the vehicle's approved `allowedCountries` |
    | `allowed` | `[36]` | `[36]` ∪ the vehicle's approved `allowedCountries` |
    So while `foreign.allowed` is off, **every** trust is `[36]` on-chain. The design's Details-tab row ("Not permitted (established residential)" or "Permitted after FIRB checks") is rendered from A19's `foreign_policy`, not from the module; the chain only has to be consistent with it (`blocked` ⇒ exactly `[36]`, asserted by the deploy read-back). The FIRB assessment of a person is off-chain (A19 G06 and the `RESIDENCY_FIRB` claim); the module only refuses a country the vehicle does not allow. The "until 30 Jun 2029" date stays rule-pack data, never module state.
    **Seed fixture.** The local seed turns the flag on for the three commercial seed trusts only, using the named fixture `deploy/suite/fixtures/seed-foreign-policy.json`: `MRN01`, `ANN01`, `GYM01` → `foreign.allowed = true`, `allowedCountries = [36, 554]` (`554` = New Zealand, the seeded `INV-F` persona's code, which A61's N01 check needs on `ANN01`). The fixture is sandbox data marked "not legal advice; counsel sets production values under HG-LEGAL"; the five residential seed trusts are `[36]`. Tests pin this: residential seeds `[36]`, commercial seeds `[36, 554]`, and a commercial trust deployed without the fixture is `[36]`.
  - **`MaxBalanceModule`** (vendored) — G07. `maxBalance` in units per ONCHAINID (so two wallets of one identity share the cap): `maxBalance = floor(totalUnits × holder_cap_bps / 10,000)`, default 500 bps = 500 of 10,000, set per offer from the listing terms. The design's rule-pack change APR-2285 (5% → 7.5%) is `setMaxBalance(750)` and changes the rules hash. "Including associates" cannot be known on-chain and stays with A19.
  - **`HolderCountModule`** (RealX). Per compliance: `maxHolders` (0 = no on-chain cap) and a live `holderCount` counted by ONCHAINID, not wallet, maintained in the mint, burn and transfer hooks from post-state balances; `moduleCheck` refuses a transfer or mint that would create a new holder beyond `maxHolders`. The s601ED 20-member question is an off-chain threshold monitor in A19 that warns; the on-chain cap is set only when the vehicle's approved rule says so. A view `wouldAddHolder(compliance, from, to, value)` exists for the inspector.
  - **`LockInModule`** (RealX) — G08. Per compliance: `lockInSeconds` (default 7,776,000, the product map's "3 months proposed, per listing"); per holder: `unlockAt[compliance][identity]`. The mint hook sets `unlockAt = max(existing, block.timestamp + lockInSeconds)` for the recipient's identity; `moduleCheck` refuses any transfer while `block.timestamp < unlockAt[from]`; the transfer hook makes the recipient inherit `max(unlockAt[to], unlockAt[from])`, which only matters for forced transfers and recoveries out of a locked holder (a normal transfer only passes when the sender is unlocked). `setUnlockAt(compliance, identity, timestamp)` is callable by the compliance owner or the `lifter` for that compliance (set on this module by the compliance owner with `setLifter(compliance, a)` at deploy, the same V2 address as on `HaltModule`; the REGO "set lock-up dates" 4E+Q through V2 in A28); it may extend or shorten and emits `UnlockSet`. Lock is per holder, conservative: a holder who buys twice is locked until the later unlock; the register (A18) keeps per-lot `lock_in_until` and is the legal view.
  - **`HaltModule`** (RealX) — G10. Per compliance: `halted` flag and `cause` (`MANUAL`, `MEETING`, `VALUATION_STALE`, `RECON_BREAK`, `TOKEN_PAUSE`, `OTHER`). Roles per compliance, set by the compliance owner: `halter` (the V3 restrict-only gateway in A25; a 1-of-N signer locally) and `lifter` (the V2 gateway in A25). The module is shared by every token on the chain, so every function takes the compliance address as its first argument and checks the caller's role **for that compliance**. Role table (anyone not listed is refused with the named error):
    | Function | Allowed callers | Refused with |
    |---|---|---|
    | `halt(compliance, cause)` | halter, lifter, compliance owner (restricting is always allowed to the stronger roles) | `NotHalter` |
    | `lift(compliance)` | lifter, compliance owner | `NotLifter` (the halter is refused) |
    | `activate(compliance)` (one-way activation marker, see `tokenState`) | lifter, compliance owner | `NotLifter` |
    | `forcedTransferOverride(compliance, from, to, value, expiry, approvalId)` | lifter, compliance owner | `NotLifter` |
    | `setHalter(compliance, a)`, `setLifter(compliance, a)` | compliance owner only (through `callModuleFunction` or directly, per the module base's owner check) | `NotComplianceOwner` |
    | `moduleTransferAction`, `moduleMintAction`, `moduleBurnAction`, `bindCompliance`, `unbindCompliance` | the bound compliance only | `NotBoundCompliance` |
    `LockInModule.setUnlockAt(compliance, identity, timestamp)` follows the same shape: lifter or compliance owner, else `NotLifter`. `DocumentAnchor.setDocument(token, …)`: the token's owner or an agent of that token, else `NotTokenAgent`. `moduleCheck` returns false for every transfer while halted; mints and burns are not refused by the module (the off-chain recon rule and the approvals engine refuse them for a vehicle with an open Sev1 break). Halt is distinct from `pause`: `pause` is the token-level T-REX function that stops all transfers and is shown as "Token paused"; halt stops the marketplace board for that trust and is shown as "Resale halted", and both can be read separately by the inspector. The **forced-transfer-while-paused rule** (SM-06 invariant) also lives here, because the vendored `forcedTransfer` does not run `canTransfer` or `whenNotPaused` but does call every module's transfer hook: `HaltModule.moduleTransferAction` reverts with `FORCED_TRANSFER_WHILE_PAUSED` when `IToken(compliance.getTokenBound()).paused()` is true, unless the owner or lifter has armed a single-use `forcedTransferOverride(compliance, from, to, value, expiry, bytes32 approvalId)` for exactly that move (the product map's "unless an override is approved"); arming emits `OverrideArmed(compliance, from, to, value, expiry, approvalId)`, and the hook consumes the override and emits `OverrideConsumed(compliance, from, to, value, approvalId)`, so A25 and A28 can prove that arming the override and the forced transfer came from one approval ID. A test asserts the consumed event carries exactly the approval ID it was armed with. The recovery sequence (item 3a) uses `forcedTransfer`, so a recovery while paused needs the same override; a test proves both. A halt's time-box ("halted until") and its published reason text are not on-chain: they live off-chain in [[A48 - Halts, kill switches and wind-down]], which calls `lift` when the time-box ends; the module only holds the flag and the cause code.
  - **`SupplyLimitModule`** (vendored) — the "10,000 units default". `supplyLimit` = the vehicle's total units from the offer terms; the mint hook refuses a mint that would exceed it. The approval-bound per-mint cap is A25's job; this module is the last line so a wrong allocation file can never over-issue on-chain.
  - **`AcquisitionClaimModule`** (RealX) — G04 (and G05's TMD in P2). Per compliance: `acquisitionTopics` (`[WHOLESALE_AU]` for `AU-W-2026.1`, `[TMD_FIT]` for `AU-R-2027.1`), set by the compliance owner and readable by `getAcquisitionTopics(compliance)`. `moduleCheck` refuses a mint, and a transfer whose receiving wallet's identity differs from the sending wallet's identity, unless the receiving identity holds, for every acquisition topic, a claim from an issuer the token's trusted-issuers registry trusts for that topic and for which that issuer's `isClaimValid` is true (so expiry and revocation apply). A transfer between two wallets of one identity is never refused by this module. Forced transfers do not run `moduleCheck` (vendored behaviour), so a court-ordered move or a recovery is not blocked by a lapsed certificate; `isVerified` still applies to the receiver through the holding topics. The module keeps no per-holder state, so it has no hook logic beyond the compliance-only guard.
  - Order of binding (fixed, and the order the rules hash uses): `CountryAllow`, `MaxBalance`, `HolderCount`, `LockIn`, `Halt`, `SupplyLimit`, `AcquisitionClaim`. The deploy script refuses to finish unless all seven are bound in this order.
  - **Getters and read strategy (settled at Specify).** The builder lists, in `contracts/TOOLCHAIN.md`, every view function the pinned tag's `CountryAllowModule`, `MaxBalanceModule` and `SupplyLimitModule` expose. The read strategy is fixed now: allowed countries are read by iterating the constant ascending ISO 3166-1 numeric table in `IsoCountries.sol` (249 codes, data only) and calling the module's per-country view (`isCountryAllowed(compliance, country)` or the tag's equivalent), which yields the ascending list without enumeration storage; `maxBalance` and `supplyLimit` are read from the module's getter. If a needed getter is missing (a per-country view, a `maxBalance` getter or a `supplyLimit` getter), the builder writes the RealX equivalent of that one module in `contracts/src/compliance/` with the same function names plus the getter and records it in `AUDIT-SCOPE.md`; the same applies if the tag lacks `MaxBalanceModule` or `SupplyLimitModule`. No other reason justifies a RealX copy of a vendored module, and a separate "declared parameters" store is not used, because the hash must describe what the modules actually enforce.
- **`DocumentAnchor`** (RealX, one per chain, keyed by token): `setDocument(token, bytes32 docType, bytes32 sha256, string uri, uint32 version)` callable by the token's owner or an agent of that token (V1 or V2 through A25); `docType` constants `IM`, `PDS`, `TMD`, `CONSTITUTION`, `VALUATION`, `FEE_SCHEDULE`; `latest(token, docType)` and the full history by event. No content, no PII, only hashes and a URI. This is what recon rule R14 (document drift) reads and what ERC-3643 lacks (ERC-1643-style `setDocument`).
- **`SuiteInspector`** (RealX, view-only, one per chain): `explainTransfer(token, from, to, value)` returns the identity-registry result and one `(module, name, ok)` row per bound module so the API can name the failed check (the design's PUB-04 "names the failed check and how to fix it" and the buy step's G07 line); `tokenState(token)` returns the on-chain slice of SM-06 from these facts, evaluated in this order (first match wins):
  1. `deployed` — not all seven modules bound in the fixed order, or the token has no agent, or the IR is not re-pointed to the shared issuers registry and the pack's topics registry.
  2. `configured` — all of the above hold, `totalSupply() == 0`, `HaltModule.activatedAt(compliance) == 0` (the token is still paused from deployment).
  3. `issuing` — `totalSupply() > 0` and `activatedAt == 0` (mints happen while paused). If the token is unpaused while `activatedAt == 0`, the state is still `issuing` and `explainToken(token)` returns the flag `UNPAUSED_NOT_ACTIVATED`, which A27 treats as a configuration break.
  4. `active` — `activatedAt > 0` and `paused() == false`.
  5. `paused` — `activatedAt > 0` and `paused() == true`.
  `activatedAt` is set once by `HaltModule.activate(compliance)` (lifter or owner; a second call is refused with `AlreadyActivated`), and A28 sends it with the first `unpause` under the same approval. This matches A27's seven `configured` checks (A27's check "`paused()` is true" holds at `configured`); cross-node: A27's line "A28's first unpause and first mint move it to `issuing`" must read "the first mint moves it to `issuing`; `activate` plus `unpause` move it to `active`".
  `holdingState(token, wallet)` returns the on-chain slice of SM-07 from `identity`, `balanceOf`, `unlockAt`, `getFrozenTokens` and `isFrozen`, with this precedence when facts overlap (first match wins): `frozen` (`isFrozen(wallet)`) > `partially_frozen` (`getFrozenTokens(wallet) > 0`) > `locked` (`balanceOf > 0` and `now < unlockAt[identity]`) > `active` (`balanceOf > 0`) > `eligible_empty` (registered in the storage, balance 0) > `unregistered` (no identity in the storage). So a wallet that is locked and partially frozen reads `partially_frozen`, a frozen wallet inside its lock-in reads `frozen`, and a lost wallet left frozen after recovery reads `frozen` until A28 unfreezes it or `unregistered` once unfrozen and deleted. `rulesHash(token)` is item 4.
- Frozen states use the vendored functions unchanged: `setAddressFrozen` (whole wallet; the sponsor register's "Estate of H. Lowe · 60 units · Frozen"), `freezePartialTokens` and `unfreezePartialTokens` (the P2 "listed for sale" partial freeze equal to the listed quantity). Tests cover: a frozen wallet cannot send or receive; a partial freeze blocks transfers above the free balance and allows below it; `forcedTransfer` unfreezes what it needs, as upstream does.

**3a. Recovery on shared storage (J09)**

- The vendored `recoveryAddress(lost, new, onchainID)` is **not** the recovery path on RealX, because on the shared storage it cannot work for an investor who holds more than one trust: it requires the new wallet to already be a management key (purpose 1) of the identity, it calls `registerIdentity(new)` itself (which reverts when A31 has already registered the new wallet in the shared storage, and on the second token in any case), it re-freezes the new wallet when the lost one was frozen, and it calls `deleteIdentity(lost)` on the **shared** storage, which strands the lost wallet's units in every other trust and makes the second token's recovery revert. The function stays in the vendored token and in `exports.json` for completeness, and a test documents the failure above on a two-trust holder; A28 must not call it (cross-node: A28's `recovery` row currently names `recoveryAddress` and must name the sequence below).
- The RealX recovery sequence, which this node proves by test so A28 only composes calls:
  1. J09 step 6: `setAddressFrozen(lost, true)` on every token where the lost wallet holds units (V3 through A25; the deployer locally).
  2. A31 (V4): `registerIdentity(new, identity, country)` once, through any bound IR, so the new wallet is in the shared storage for every token; the country is copied from the lost wallet.
  3. The recovery key `R`: `addKey(new, 1, 1)` and `removeKey(lost, 1)` on the investor's ONCHAINID (A29 and A31 drive this; the identity address never changes).
  4. Per token with `balanceOf(lost) > 0` (V2 through A25 after the timelock, one approval ID for the whole recovery): if the token is paused, `HaltModule.forcedTransferOverride(compliance, lost, new, balance, expiry, approvalId)`; then `forcedTransfer(lost, new, balanceOf(lost))`; then `setAddressFrozen(new, true)`; and, if the lost wallet had a partial freeze recorded before step 1, `freezePartialTokens(new, thatAmount)` so a P2 listed quantity stays marked.
  5. Only when `balanceOf(lost) == 0` on every token: A31 `deleteIdentity(lost)`.
- **Expected end state:** the new wallet holds exactly the lost wallet's former balance on every token, is **frozen on every token** (because J09 froze the lost wallet first), and stays frozen until a four-eyes unfreeze through A14 and A28; `holderCount` is unchanged (same identity); `unlockAt[identity]` is unchanged; `MaxBalance` per identity is unchanged; the lost wallet is `unregistered` once step 5 runs (or `frozen` with zero balance until A28 unfreezes it); `holdingState(new)` reads `frozen`.
- **Required test ("recovery on shared storage"):** an investor identity holds 300 units of trust A (unpaused) and 120 units of trust B (paused), the lost wallet is frozen on both, A31 has pre-registered the new wallet; the sequence above succeeds on both tokens, trust B only with an override bound to the approval ID and consumed; the end state above holds on both; step 5 before trust B is moved is refused by A31's precondition and, if forced in the test, leaves trust B's units stranded (asserted, to document why the order matters). A vector with `action.kind = "recovery"` runs steps 2 to 4 for one token.
- If the pinned tag's `forcedTransfer` refuses to move out of a wallet frozen with `setAddressFrozen` (confirmed at Specify), step 4 becomes `setAddressFrozen(lost, false)`, `forcedTransfer`, `setAddressFrozen(new, true)` in one custody batch under the same approval ID, so the lost wallet is never unfrozen outside that batch; the builder records which variant applies in `deploy/suite/README.md`.

**4. Rules hash (recon rule R6 and the "module parameter hash matches the approved rule" oracle)**

- `RuleHash.sol` computes exactly this value (the spec, not `RULE-HASH.md`, is the source the node QA writes the 50 hidden expected hashes from; `RULE-HASH.md` restates it and may not change it):
  ```
  rulesHash = keccak256(abi.encode(
    bytes32  version,            // keccak256("realx.rulehash.v1")
    bytes32  rulePackCodeHash,   // keccak256(bytes(rulePackCode)), e.g. keccak256("AU-W-2026.1"), read from RuleHash's claimTopicsRegistry → code map
    uint256[] holdingTopicsAsc,  // topics in the IR's claim-topics registry, ascending
    uint256[] acquisitionTopicsAsc, // AcquisitionClaimModule.getAcquisitionTopics(compliance), ascending
    IssuerEntry[] issuersAsc,    // IssuerEntry = (address issuer, uint256[] topicsAsc): every issuer in the IR's trusted-issuers registry, ascending by address, each with the topics it is trusted for, ascending
    ModuleEntry[] modulesBound,  // ModuleEntry = (bytes32 nameHash, address module), nameHash = keccak256(bytes(IModule(module).name())), in compliance.getModules() order (binding order, NOT sorted)
    uint16[]  countriesAsc,      // allowed ISO 3166-1 numeric codes, ascending
    uint256   maxBalance,
    uint256   maxHolders,
    uint256   lockInSeconds,
    uint256   supplyLimit
  ))
  ```
  Topic ids are the `uint256` values of the `ClaimTopics.sol` constants; a parameter whose module is not bound is encoded as `0` (or an empty array). Because modules are in binding order, swapping the order of two bound modules changes the hash, and because each issuer carries its topics, changing the topics an issuer is trusted for changes the hash. State is excluded (halted, paused, `activatedAt`, per-holder unlocks, balances, overrides, halter and lifter addresses) so the hash changes only when a rule changes. `SuiteInspector.rulesHash(token)` exposes it, and `SuiteInspector.ruleParams(token)` returns the decoded tuple so ADM-16 reads every value in one call.
- `contracts/deploy/suite/rule-hash.ts` exports `ruleHash(params: RuleParams)` computing the identical value in TypeScript (the ABI encoder of A07's toolchain over the same tuple types), and `ruleParamsFromCompliance(input)` mapping A19's resolved `ComplianceRule` to `RuleParams` with these fixed mappings: `rule_pack_code` → `rulePackCodeHash`; the pack's holding and acquisition topics as listed in item 2; the chain's trusted issuers from `shared.json`; the module list from the fixed binding order and `shared.json` addresses; `foreign_policy` plus `foreign.allowed` plus the vehicle's approved list → `countriesAsc` by the table in item 3; `holder_cap_bps` and total units → `maxBalance = floor(totalUnits × holder_cap_bps / 10,000)`; `member_cap` → `maxHolders` only when the vehicle's approved rule sets an on-chain cap, else `0`; `lock_in_days` → `lockInSeconds = days × 86,400`; total units → `supplyLimit`. Both functions are listed in `exports.json` so A27 re-exports them through `packages/contracts`. A property test over 500 random parameter sets asserts chain and TypeScript agree and that changing any single field changes the hash.
- **How R6 uses it.** Recon rule R6 is defined as: on-chain `SuiteInspector.rulesHash(token)` == `ruleHash(ruleParamsFromCompliance(A19.expectedOnchainParams(vehicle)))`. It is **not** A19's `params_sha256`: that value is SHA-256 over canonical JSON of the whole resolved set, including off-chain fields, and can never equal a keccak hash of the on-chain slice, so comparing them would raise a permanent Sev1 `rule_drift` and halt resale. The approvals payload for "change rule parameter" (CCO → LEGL, 4E+Q) carries both A19's `params_sha256` and the expected post-change `rulesHash`. Cross-node changes required (not made here): A19 must expose `expectedOnchainParams(vehicle)` in the shape `ruleParamsFromCompliance` takes and stop describing `params_sha256` as the on-chain comparison value; A20's R6 row must compare `rulesHash` as defined here; A27's `configured` check "every module … bound with the parameter hash equal to `params_sha256`" must become "`rulesHash(token)` equals the expected `rulesHash` in the manifest" and its `token` table needs an `expected_rules_hash` column beside `params_sha256`.

**5. Deploy scripts (`contracts/deploy/suite/`)**

- **Ownership-safe deterministic deployment.** Deploying an `Ownable` contract (the `TREXFactory`, the `IdFactory`, the implementation authority, the storage and registry proxies) directly through the `0x4e59…` deterministic proxy would make the proxy its owner, so `deployTREXSuite` (owner-only) could never be called. The RealX `RealXCreate2Deployer` (about 40 lines) is itself deployed once through the `0x4e59…` proxy with a fixed salt and one constructor argument, the permitted deployer account, so it has the same address on every chain where that account is used. Its single function `deployAndInit(bytes32 salt, bytes initCode, bytes initCalldata, address newOwner)` (callable only by the permitted deployer, else `NotDeployer`) does, in one transaction: CREATE2 with `salt`; the optional `initCalldata` call (for the upgradeable T-REX proxies whose `init` makes the caller the owner); `transferOwnership(newOwner)` when the contract is `Ownable`. A test asserts, after `deploy-shared.ts`, that `owner()` of every shared contract equals the configured owner (the deployer locally, V1 after A25) and that none is owned by the deployer contract or the `0x4e59…` proxy.
- `deploy-shared.ts --network <hardhat|localhost|baseSepolia>`: deploys, through `RealXCreate2Deployer`, the implementation authority and implementations (vendored), the shared storage, trusted-issuers registry, one claim-topics registry per rule pack (registering each with `RuleHash`'s code map), `RealXClaimIssuer`, the identity factory, the **seven** compliance modules (three vendored, four RealX), `DocumentAnchor`, `SuiteInspector`, `RuleHash` and the vendored `TREXFactory`, with salts `keccak256("realx.shared.<name>.v1")`, so the shared layer sits at the same addresses on the Hardhat chain, on Base Sepolia and on any later chain where the proxy exists. It then calls `IdFactory.addTokenFactory(trexFactory)` and gives the `TREXFactory` the binding right on the shared storage (item 3), reading both back. Writes `deploy/suite/out/<chainId>/shared.json`.
- `deploy-vehicle.ts --vehicle <code> --params <file>`: `params` is a validated JSON (`vehicleCode`, `trustName`, `rulePack`, `propertyType`, `foreignPolicy` (`blocked | after_firb_check | allowed`, from A19), `totalUnits` default 10,000, `holderCapBps` default 500, `maxHolders` default 0, `lockInSeconds` default 7,776,000, `foreign.allowed` default false with `allowedCountries` required only when it is true, `owner`, `agents[]`, `halter`, `lifter`, `documents[]`); the countries and `maxBalance` are derived by `rule-params.ts`, never typed. It calls `TREXFactory.deployTREXSuite` with the salt string `realx.vehicle.<vehicleCode>.v<n>` (no chain id, so the token, IR and compliance addresses are the same on every chain) and the shared storage as `irs`; re-points the IR to the shared trusted-issuers registry and the pack's claim-topics registry; binds and configures the seven modules in the fixed order; sets `halter` and `lifter` on `HaltModule` and `lifter` on `LockInModule`; anchors the documents; then reads back every parameter, the IR's registries, the storage binding, the agents, the owner, `paused() == true` and `rulesHash`, and refuses to finish unless what is on-chain equals the params and `rulesHash == ruleHash(params)`. Writes `deploy/suite/out/<chainId>/<vehicleCode>.json` (addresses, salt, params, `rulesHash`, tx hashes, block numbers, compiler metadata hash), the manifest A27 copies into `packages/contracts`.
- `predict-addresses.ts` prints the CREATE2 addresses for a vehicle code before anything is deployed; the deployed addresses must equal the prediction on every chain, which is how the mainnet chain can be chosen later without changing the address book (architecture brief §4.5).
- Guard rails: the scripts refuse any network A07's config guard does not allow, refuse to redeploy a vehicle code whose manifest exists unless `--force-new-salt-version` is given (which changes the salt suffix and is recorded), and never accept private keys as arguments (the network's configured signer only). Re-running `deploy-shared.ts` on a chain where the shared layer exists is a no-op that re-verifies addresses and code hashes.
- Seed: `seed-vehicles.ts` deploys the eight prototype properties from A06's seed definitions with their property types and A06's vehicle codes: residential `KST01` Kent Street Terrace, `BAY01` Bay Road Apartment, `HAW01` Hawthorn Grove Townhouse, `MPA01` Marine Parade Apartment, `UNL01` Unley Road Cottage (each `blocked` → `[36]`), and commercial `MRN01` Marion Street Warehouse, `ANN01` Ann Street Office Floor, `GYM01` Gympie Road Retail (each `after_firb_check`, with `seed-foreign-policy.json` → `[36, 554]`); it mints nothing. It needs A06's seed definitions and A03's state enums to exist (see the dependency note under Gauntlet).

- **SM-06 Token:** done means the on-chain slice `deployed → configured → issuing → active`, `active ↔ paused` is derived from chain facts by `tokenState` (tokens start paused; `HaltModule.activate` plus `unpause` is the step from `issuing` to `active`) and every forbidden on-chain transition is refused; `designed`, `sandbox_deployed`, `deploy_requested` (tests and the audit placeholder attached), `upgrading`, `migrating`, `redeeming` and `retired` are off-chain rows in A27 and A28, and the invariants "compliance modules on every token" (the deploy script refuses to finish without all seven bound in order) and "forced transfers blocked while paused unless an override is approved" (HaltModule hook) hold by construction.
- **SM-07 Holding (wallet × token):** done means `holdingState` derives `unregistered`, `eligible_empty`, `active`, `locked`, `partially_frozen` and `frozen` from chain facts, with the precedence in item 3, the transitions `eligible_empty → active` (units received), `active → eligible_empty` (balance to zero), `active → locked → active` (time), `active → partially_frozen → active`, `active|partially_frozen → frozen`, `frozen → active` and `frozen|active → recovered_out` exist as tested calls, `recovered_out` is the item 3a sequence moving the balance to zero (labelled off-chain from its approval ID, since the vendored `RecoverySuccess` event is not emitted on RealX's path) and `deregistered` is `deleteIdentity` (A31 enforces zero balance first), and the invariant "tokens cannot be received by a wallet not in `eligible_empty` or later" is the registry check. "Unfreezing always needs four eyes" is A14 and A28 policy, not chain code.
- **Founder requirement D04 and G22:** no API or token surface here. Done means the chain rules apply identically to a UserOp signed by an investor's delegated session key (A26) and to a human's passkey, since `canTransfer` does not see who signed, which is the last-line parity guarantee the agent-parity suite in A100 (and A82's end-to-end run) relies on.
- **Swap points (Q12 option 1, reversible):** the token layer is the vendored T-REX suite plus the four RealX modules; swapping to a Tokeny-style platform replaces `deploy/suite/` and the module contracts with a platform adapter behind A08's `chain` interface, while `RuleParams`, `rulesHash`, the vector schema, `SuiteInspector`'s read shapes and everything off-chain survive; the clean-room fallback (EIP-3643 interfaces re-implemented under `contracts/src/`) keeps every test in this node as its acceptance suite. The chain is a chain id and an RPC URL (A07); mainnet stays behind HG-PROD.

## Node-specific challenges (node QA)

- **Supply and money.** A `batchMint` of 9,100 units to 120 identities against a `supplyLimit` of 10,000 on a token that already has 950 units: the whole batch must revert, not partially mint; a `burn` of 61 units from a holder with 60 must revert; after 2,000 random operations the sum of balances must equal `totalSupply` exactly and never exceed the limit.
- **Holder-cap and lock-in evasion.** One investor registers two wallets to one ONCHAINID and is minted 300 units to each on a 500-cap trust: the second mint must fail on `MaxBalance`, and `holderCount` must read 1, not 2. A holder minted at day 0 on a 90-day lock transfers to a second wallet of their own identity on day 10 (must fail on `LockIn`), then a court-ordered `forcedTransfer` moves the units to an estate wallet on day 20: the estate wallet must inherit the day-90 unlock and be refused a transfer on day 30.
- **Halt versus pause, and the override.** With the token unpaused and halted by the V3 halter, a transfer must fail on `Halt` while a mint passes the module; the halter's `lift(compliance)` must revert with `NotLifter`, while the lifter's `halt(compliance, cause)` succeeds; with the token paused, `forcedTransfer` of 12 units must revert with `ForcedTransferWhilePaused`; an override armed for `(from, to, 12)` must not authorise `(from, to, 13)` or `(from, other, 12)`, must be consumed by the first matching move with an `OverrideConsumed` event carrying the approval ID it was armed with, and must be refused after its expiry; an override armed on one token's compliance must not authorise the same move on another token; the item 3a recovery sequence while paused must behave the same way.
- **Identity and claims.** For a holding topic (`KYC_VERIFIED`): a claim with `validUntil` one second in the past, a claim signed by a key that is not the issuer's claim key, a claim from an issuer trusted for `SANCTIONS_CLEAR` but not for `KYC_VERIFIED`, and a revoked claim: each must make `isVerified` false and every mint, transfer or forced transfer to that wallet must fail on `IdentityRegistry`. The same four defects on `WHOLESALE_AU` must leave `isVerified` true and make a mint or a transfer from another identity fail on `AcquisitionClaim`, while a sale by that holder, a move to their own second wallet, a recovery of their wallet and a forced transfer to them succeed. A wallet with no identity at all must be refused by `transfer`, `mint`, `forcedTransfer`, the recovery sequence and `recoveryAddress` alike. On a fresh investor identity V4 can add and remove a claim and a stranger cannot.
- **Recovery on shared storage.** The two-trust recovery test of item 3a, re-run by the node QA with different balances, one token paused and a partial freeze on one: both tokens recover, the new wallet ends frozen on both, `holderCount` and `unlockAt` are unchanged, and running the vendored `recoveryAddress` on the same fixture fails as documented.
- **Residency classification.** A temporary resident (nationality code) is refused on a residential trust and a citizen abroad (`36`) accepted; a commercial trust deployed while `foreign.allowed` is off refuses `554`; a residential params file with `foreign.allowed = true` is refused before any transaction.
- **Rules-hash blind spots.** Change the allowed-country list from `[36]` to `[36, 554]`, change `lockInSeconds` by one second, swap the order of two bound modules, add a second trusted issuer, change the topics an existing issuer is trusted for, and change the acquisition topics: each must change `rulesHash`; halting, pausing, activating, minting, arming an override, changing the halter or lifter and setting a per-holder unlock must not; the TypeScript hash must equal the chain hash and the node QA's independently computed value for all 50 hidden parameter sets; `ruleHash(ruleParamsFromCompliance(x))` for the seeded `AU-W-2026.1` compliance rules equals the deployed `rulesHash` of every seed trust.
- **Security and roles.** Every RealX privileged function called by a stranger, by the wrong role and by the right role from another token's compliance; a direct call to `moduleTransferAction` by an EOA; `setDocument` by an agent of a different token; a `deploy-vehicle.ts` run with a params file whose `owner` is the zero address or whose `foreignPolicy` is `blocked` but sets `foreign.allowed` or lists a country other than 36; a second deploy of the same vehicle code without the salt-version flag; a `deployAndInit` call from an account that is not the permitted deployer; a shared contract whose `owner()` is the deployer contract or the `0x4e59…` proxy: each must be refused with a named error and leave no partial deployment recorded in `out/`.
- **Design fidelity and defaults.** A seed deploy must produce `decimals() = 0`, `supplyLimit = 10,000`, `maxBalance = 500`, `lockInSeconds = 7,776,000`, `[36]` for every residential trust and `[36, 554]` (from `seed-foreign-policy.json`) for every commercial one, symbols `RX` plus A06's vehicle code; `explainTransfer` for a 501-unit mint must name `MaxBalance` so the buy step's G07 line can say "maximum 500 units"; any hand-typed country or cap in a contract rather than in params fails.
- **Licence and scope.** A vendored function body copied into `contracts/src/` "to add a reason string", a `.sol` file outside the two allowed folders, a RealX module inheriting from a vendored contract that is missing from the `LICENSE-NOTES.md` inheritance list, or RealX Solidity over the `AUDIT-SCOPE.md` line count without an explanation: each fails the challenge.
