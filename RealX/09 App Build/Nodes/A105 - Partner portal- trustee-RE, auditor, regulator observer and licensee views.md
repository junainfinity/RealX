# A105 - Partner portal: trustee/RE, auditor, regulator observer and licensee views

**The signed-in surface for the four platform-level partner principals of A98 (TP-RE trustee or responsible entity, TP-AUD auditor, TP-OBS regulator observer, TP-LIC licensee; valuers and property managers stay in the sponsor console): a `(partner)` route group under `/p/[engagement]` in `apps/web` with the partner variant of the light sidebar, passkey sign-in from design extension A, and existing screens mounted in read-only or checker mode instead of new product-map codes. The frame, card and nav come from A98's `GET /v1/partners/me` without translation. The trustee sees the register and reconciliation of its own vehicles with signed extracts, the SPN-09 distribution chain with its countersign step, the register instructions it must acknowledge where it keeps the register, and an "Approvals awaiting me" list from A98's `your_turn` view (register certification and adjustment, distribution and exit-waterfall countersign, forced transfer and recovery with veto during the timelock). The auditor and observer read the data room only through their own time-boxed, watermarked grants (and, for the auditor, its engagement's collections), with every read logged. The licensee reads the marketing review list, the complaints register with personal data masked, and its own obligation rows. Everyone gets PUB-08 and PUB-09 as signed-in views, SPN-16 for their own tokens, a Security page for their passkeys and hardware key, and an Activity page. Every countersign, veto and acknowledgement is a hardware-attested WebAuthn assertion through the owning module, so a partner token can never perform one.**

## Build brief

This node is UI-only: the `(partner)` route folder of `apps/web` and the `features/partner` package of pages, components, hooks and test page objects. It calls the API only through `packages/sdk` (A09, regenerated from the OpenAPI documents of A98, A11, A14, A18, A20, A40, A44, A45, A43, A35, A47 and A12) and never through a hand-written fetch. It owns no API route, no table, no job and no event. Who a partner is, which vehicles, grants or engagement collections they hold, which requests name them as checker, whether a grant is live, whether they can countersign, and whether a decision is allowed are all decided by the API; the page asks, renders the answer, and runs A52's `withFreshAssertion` when the API asks for a passkey. Because every route it calls is also reachable by the partner's agent through A12's tokens and A104's MCP server, this node adds nothing an agent could not also do within the partner's scopes, except the person-only acts, and it publishes the mapping that proves it (`parity.json`, §8).

**1. Routing, frame and screen codes**

- Pages live under `<workspace>\app\apps\web\app\(partner)\p\`. `/p` is the landing: it reads A98's `GET /v1/partners/me` (kind, `organisation`, `role_label`, `read_only`, `time_box_label`, `can_countersign` with its reason, `engagements`, `grants`, `nav[]`, state, dormancy date) and redirects to the only engagement, or lists them as a DataTable (Organisation / Role / Vehicles or grant / Ends) when there are several. When `engagements` is empty and `state` is `lapsed` (A98 then answers 403 `PARTNER_NO_SCOPE` everywhere else), `/p` renders the **No current access** page (`PRT-22`): "You have no current access through RealX. Contact RealX if you need it again." with the Security and sign-out links only; no other page is reachable. `[engagement]` is the engagement's `PEN-` code as A98 returns it; the group layout resolves it through the same read and renders A52's `not-found` for a code the principal does not hold, exactly as the sponsor group does for a foreign tenant slug (no 403, no hint that the code exists).
- Pages under `/p/[engagement]/`: `home` (index), `vehicles`, `vehicles/[code]/register`, `vehicles/[code]/reconciliation`, `extracts`, `distributions`, `approvals`, `approvals/[id]`, `trustee-acts`, `register-instructions`, `register-instructions/[id]` (TP-RE); `data-room`, `data-room/[grant]/[collection]`, `data-room/[grant]/items/[itemId]`, `data-room/engagement/[collection]`, `data-room/engagement/items/[itemId]`, `metrics` (TP-AUD); `marketing`, `marketing/[item]`, `complaints`, `complaints/[id]`, `obligations` (TP-LIC); `transparency`, `documents`, `agents`, `security` and `activity` for every partner type.
- Screen codes (spec point (a)): the partner pages are not new product-map screens. Each page declares an extension-only shell code `PRT-01` to `PRT-22` (prefix `PRT-`, not `PTR-`, which is A98's `partner_user` id prefix and would collide in logs, search and the Geist Mono id pattern) through A52's `defineScreen`, with a `reuses` field naming the product-map or extension screen it mounts (`SPN-08`, `SPN-09`, `SPN-16`, `PUB-08`, `PUB-09`, `ext:ADM-26`, `ext:ADM-28`, `design:adApprovals`) so that A52's build test, `screens.generated.json` and the [[Screen Coverage Matrix]] list them without counting them against the 91. A52's `defineScreen({ code, design })` has no `shell` or `reuses` field and A02's `SCREENS` / `ScreenCode` has no extension-only shell codes, so this needs an explicit **reopening of A52 and A02 after their gates**: A02 adds a shell-code family `PRT-01..22` outside the 91; A52 adds `shell: true` and `reuses` to `defineScreen`, teaches its build test to accept shell codes, and adds the twenty-two `routes.ts` rows under the reserved `/p/[engagement]/` path (A52's test requires the page path and the table path to agree). This node never edits `routes.ts` or A02's data; until the reopening lands, the pages cannot pass A52's build test, and the Gate waits.
- Code map: `PRT-01` home, `PRT-02` vehicles, `PRT-03` register, `PRT-04` reconciliation, `PRT-05` register extracts, `PRT-06` distributions, `PRT-07` approvals awaiting me, `PRT-08` approval detail and countersign, `PRT-09` trustee acts, `PRT-10` data room, `PRT-11` collection and item (grant and engagement paths), `PRT-12` metric values citing your sign-off, `PRT-13` marketing review, `PRT-14` licensee obligations, `PRT-15` transparency, `PRT-16` documents, `PRT-17` API tokens and agents, `PRT-18` register instructions (list and detail), `PRT-19` complaints (TP-LIC), `PRT-20` security, `PRT-21` activity, `PRT-22` no current access.
- **Partner frame** (`design-ext:partner sign-in` and the partner variant of the light sidebar from A50 §2): `(partner)/layout.tsx` composes A05's light-sidebar primitive (the same one A52's `SponsorSidebar` composes; if A52 does not export the primitive, the export is raised to A52 at Specify and nothing is copied) with: the logo and the `PARTNER` Geist Mono tag; the cream partner card with `organisation`, the person and `role_label` exactly as `GET /v1/partners/me` returns them ("Trustee and RE", "Auditor", "Regulator observer", "Licensee"); the grey pill under the card showing `time_box_label` verbatim when it is non-null (A98 returns it only for TP-AUD and TP-OBS, so no pill is drawn for TP-RE or TP-LIC and the page computes no date); and the nav. The nav draws exactly the entries of `nav[]`, in that order, each code mapped to its route and label through A52's `href()` and a fixed code-to-label table in `shell/`; the page keeps no role-based nav sets of its own, and an unknown code fails A98's screen contract test. The "Approvals awaiting me" count is the length of A98's `GET /v1/partners/me/approvals?stage=your_turn`. The frame keeps the sponsor frame's widths: a 240 px column at 1024 px and above, an off-canvas drawer behind a 56 px top bar below, `main` padding `32px 40px 64px`, 16 px side padding below 768 px.
- Sign-in is A52's `/sign-in/partner` (SGN-03) with the partner frame; the principal's home after sign-in is `/p`. This node fidelity-checks SGN-03 against A50's drawing (A52 §3 asks it to) and adds nothing to the ceremony. Dormancy lock, device mismatch and session expiry render A52's sentences; an engagement that ended while the partner was signed in (A98 drops the scope from the session) renders "Your access through {organisation} ended on {date}. Contact RealX if you need it again." from A98's error code (named at Specify; `PARTNER_ENGAGEMENT_ENDED` is the proposed name), and when no engagement remains the next load of `/p` is `PRT-22`.
- All pages are server components reading with `cache: 'no-store'`, and every page and file response in the group carries `Cache-Control: no-store` (a revoked grant, a decided approval or a break must show on the next load, and a shared computer's back button must not show a data-room page from the browser cache). Links to data-room items, extracts, complaints and approval details set `prefetch={false}`, so Next.js never fetches an item the person did not open (that would write a false read audit row). Client components exist only for the decide, veto and acknowledgement sheets, the extract request form, the passkey enrolment, the item viewer frame, "Load more" and toasts.

These are person-only acts (`requiresHuman`); no control renders on a token session.

- **Collection** (`PRT-11`, `data-room/[grant]/[collection]` and `data-room/engagement/[collection]`): `GET /v1/dataroom/grants/{id}/collections/{code}` (or the engagement path) rendered as a DataTable with the provider's columns (A45 fixes them per collection: `register_extracts`, `recon_runs`, `filings`, `obligations`, `licences`, `board_reports`, `investor_reports`, `audit_exports`, `financials`, `aml_program`), cursor-paginated with "Load more", and a header line "Every page and file you open here is logged and watermarked". The audit trail reaches TP-AUD and TP-OBS only as the `audit_exports` collection; where A66's note says they "reach the same API", this node asks at Specify whether A10's live events read is also granted to partners within a grant (spec point (d)); until A10 and A45 confirm it, the portal calls only the collection.
- **Item** (`PRT-11`, `…/items/[itemId]` on either path, same code as the collection): `GET /v1/dataroom/grants/{id}/items/{itemId}` (or the engagement path) returns the item and a short-lived A08 link to the watermarked rendering, never the original object. The viewer shows the file in a sandboxed frame (PDF) or as a table (CSV and JSON as returned), a brick band above it with the watermark text exactly as the API returns it (`watermark_text`, for example "Provided to {grantee} under grant DRG-… · {date}"), and a "Download" button that fetches the same watermarked file through the API (one `dataroom.item_downloaded` event). The page never keeps the link after navigation, never stores an item in `localStorage`, `sessionStorage`, IndexedDB or a service worker, and never re-uses a link after the API refuses.
