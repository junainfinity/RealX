# A10 - Append-only hash-chained audit log

**The one write path into the insert-only `audit_event` table that every later module calls inside its own database transaction: a byte-exact canonical form hashed and chained row to row per partition, actor plus on-behalf-of on every event, before/after hashes instead of PII copies, visibility classes that stop tipping-off, a daily full verification (R18) that checks every anchor and publishes the head hash to evidence, audited exports and unmask events, legal holds, and a seven-year retention model with exactly one sanctioned deletion path in this build.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-10 agent-hours (build, challenge and verify loops).

**Depends on:** [[A09 - API and worker skeleton with OpenAPI-generated SDK]]
**Unlocks:** [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]], [[A13 - Alerts and SLA-clocks service]], [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A35 - Documents, disclosure library, e-sign and acknowledgements (G12)]], [[A66 - Console- command center, alerts centre, approvals inbox, audit log]], [[A102 - Backups, restore drill, data retention and erasure]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A10\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. This is an oracle node because the audit chain is the evidence every money, supply and holdings movement later relies on: if it can be altered, forked or silently skipped, nothing downstream can be trusted.

## Build brief

Why this node is first in AM1: every node after it (authentication, API tokens, alerts, approvals, ledger, register, reconciliation, every console screen) must leave a trace here, so the write interface, the canonical form and the "exactly one event per privileged step" rule are frozen before any of them is built. This node is also the technical home of founder requirement D04's audit clause: every agent action is recorded as "agent `<token>` on behalf of `<person>`" and appears in that person's own activity.

**Ownership model (who owns which table).** [[A04 - Database schema, migrations and row-level security]] owns the base table `audit_event` (its columns, the insert-only trigger, `UNIQUE (prev_event_sha256)`, `UNIQUE (seq)`, the two agent CHECKs, the grants) plus `legal_hold`, `retention_policy`, `principal` and `document`. A04's words: "A10 adds hashing, the head lock, anchors, holds and exports through the registry and never alters the base table." So this node:

- **registers three tables of its own** through A04's module-schema registry (`registerModuleSchema({ node: 'A10', tables, migrationsDir })`), with numbered migrations under `services\api\src\modules\audit\migrations\` (inside this node's owned path): `audit_anchor` and `audit_partition` (both insert-only: the migration attaches A04's insert-only trigger function to them, and they are declared insert-only through the registry's flag, or through A04.x item 9 below if the registry has no such flag) and `audit_export` (an ordinary tenant table with RLS). Column lists are in "Tables this node registers" below.
- **never alters `audit_event` or any A04 core table.** Every change it needs on `audit_event` is an A04.x follow-up item, listed next, opened by the orchestrator at the Specify step and passed before this node's Build step starts.

**A04.x items this node needs (opened at Specify; each carries its own test in A04's suite).** A04's current column set is `seq`, `id`, `ts`, `tenant_id`, `actor_type`, `actor_id`, `actor_role`, `actor_label`, `on_behalf_of_id`, `token_id`, `session_id`, `request_id`, `trace_id`, `action`, `object_type`, `object_id`, `object_label`, `approval_id`, `custody_op_id`, `tx_hash`, `before_sha256`, `after_sha256`, `before_ref`, `after_ref`, `reason`, `result`, `gate_codes[]`, `rule_pack_version`, `sensitivity`, `canonical_version`, `prev_event_sha256`, `event_sha256`, plus the conventions (`created_at`, `created_by`, `updated_at`, `updated_by`, `deleted_at`, `sandbox_of`). The items:

1. Add `gate_evaluation_id` (nullable FK to `gate_evaluation`).
2. Replace free-text `reason` with `reason_code` (text, checked by `record` against the closed reason-code registry) and `reason_params` (jsonb, nullable). No free text is ever stored in `audit_event`.
3. Add `visibility` (enum `subject_visible | staff | need_to_know | security`, NOT NULL), `need_to_know_acl` (role codes, text[], NOT NULL when `visibility = need_to_know`, by CHECK), `subject_principal_id` (nullable FK to `principal`: the person the event is about) and `vehicle_id` (nullable: the trust or sub-fund the event concerns, for partner scope).
4. `CHECK (actor_label IS NULL AND object_label IS NULL)` (labels are resolved at read time, never stored in an unerasable row); if A04 prefers, drop the two columns instead.
5. `CHECK (updated_at IS NULL AND updated_by IS NULL AND deleted_at IS NULL)` on `audit_event`.
6. `ts` and `created_at` as `timestamptz(3)` (millisecond precision), so no sub-millisecond digit exists outside the hash.
7. The exact `audit_event` RLS policy (USING only for SELECT; INSERT WITH CHECK on tenant and sandbox), as one A04 policy with a test per clause:
   - sandbox: live sessions see `sandbox_of IS NULL`; a sandbox session sees only `sandbox_of = app.sandbox_of`.
   - platform staff (`app.platform_access`): all tenants, or one under `app.view_as_tenant`; rows with `visibility = need_to_know` only when a role of the session is in `need_to_know_acl`; rows with `visibility = security` only for SECO and CCO.
   - sponsor users (`app.tenant_id`): own tenant, `visibility IN (subject_visible, staff)`.
   - partner users (`app.principal_kind = PARTNER`): `vehicle_id` in `app.vehicle_scope`, `visibility IN (subject_visible, staff)`.
   - investors and every other person: rows where `actor_id`, `on_behalf_of_id` or `subject_principal_id` equals `app.principal_id`, and `visibility = subject_visible`, or they are the actor or on-behalf-of person of the row.
   - never: a `need_to_know` or `security` row for anyone outside its ACL, including the subject.
8. Indexes: `(sandbox_of, seq)`, `(tenant_id, seq)`, `(actor_id, seq)`, `(on_behalf_of_id, seq)`, `(subject_principal_id, seq)`, `(token_id, seq)`, `(object_type, object_id, seq)`, `(approval_id)`, `(action, ts)`, `(vehicle_id, seq)`.
9. If the registry has no insert-only flag: add `audit_anchor` and `audit_partition` to `INSERT_ONLY_TABLES` so A04's convention tests cover them.
10. The sanctioned-deletion admission (see "Sanctioned deletion" below): a NOLOGIN role `realx_audit_purger` that owns only A99's `developer_purge_partition` function, and the `audit_event` immutability trigger admits a `DELETE` only when `current_user = 'realx_audit_purger'`, the transaction-local setting `realx.audit_purge` is `on`, and the row's `sandbox_of` equals the setting `realx.audit_purge_partition`. Every other `UPDATE`, `DELETE` or `TRUNCATE` stays refused for every role.
11. If feasible in a CHECK: `CHECK (actor_type <> 'AGNT' OR action NOT IN (<the human-only action codes known at that migration>))`. The `record` refusal below is the primary net; this is the second.

**Actors and labels (no PII in the row).**

- `actor_id`, `on_behalf_of_id` and `subject_principal_id` point to A04's `principal` table; `actor_type` is A04's principal type (`HUMAN`, `PARTNER`, `AGNT`, `SVCA`). A recon job, the identity adapter, the outbox relay, the scheduler and the custody quorum are `SVCA` principals (A04's `service_account` rows); "Identity provider", "Recon job" and "Custody quorum" in the design are display labels of those principals, not free text.
- `actor_role` stores the role code the actor held at `ts` (a code such as `CCO`, never a name), filled by `record` from the request or job context. `actor_label` and `object_label` are never stored.
- Rows hold ids, codes, integers and hashes only. Display labels are resolved at read time: the person label is the principal's masked display name (A04's `mask` codec) plus `(<actor_role>)`, for example "Jordan B. (CCO)"; the object label comes from a resolver registry (`audit.registerLabelResolver(object_type, fn)`) that each owning module fills in later, and its output passes through the mask codec. A missing resolver yields the raw `object_ref`, never an error.
- **The agent label (D04), exact form.** For an `AGNT` row the list and detail responses carry `actor_label = "agent <agent_name>"`, `token_id` (the `TOK-` record id from A02, never the secret or its `rx_` prefix), `on_behalf_of_label` (the person label above) and `actor_display = "agent <token_id> (<agent_name>) on behalf of <on_behalf_of_label>"`, for example `agent TOK-TD00000001 (treasury-drafter) on behalf of Priya N. (TRSY)`. For every other row `actor_display = actor_label`.
- **What an investor or other outside person sees for staff.** When the reader is not platform staff, a staff actor is shown as `RealX team` (no name, no role) and an `SVCA` actor keeps its display label.
- `object_ref` is an API field derived as `<object_type>:<object_id>`, for example `approval_request:APR-2291`. `object_id` must parse as an A02 id (or the table's uuid id); anything else is refused (see the PII guard). The list filter `object_ref` accepts an exact ref or a type prefix (`approval_request:`).
- `ts` comes from A09's injected clock (`ctx.clock.now()`) truncated to milliseconds, never `Date.now()`; the clock lint applies to this module. Chain order is `seq` within a partition, not `ts`, so an advanced test clock never breaks verification.

**Partitions and genesis.**

- A partition is one independent chain. The live chain's key is `live`. A per-user sandbox chain's key is `sandbox:<principal_id>:<generation>`, where `generation` comes from the request context (A99's `sandbox_partition.generation`; `0` until A99 exists).
- The first event written into a partition inserts one `audit_partition` row (`partition_key`, `sandbox_of`, `generation`, `genesis_sha256`, `created_at`, `first_seq`), so the verifier knows every partition and its genesis. Genesis is `genesis_sha256 = sha256_hex(utf8("realx-audit-genesis:" + partition_key))`. Because the key includes the generation, a reset sandbox never reuses a genesis value, so `UNIQUE (prev_event_sha256)` cannot collide with a surviving row of an older generation.
- `seq` is one global ordering key (a bigserial shared by all partitions). **It may have gaps and it interleaves across partitions**: a rolled-back transaction consumes a value, and sandbox rows take values between live rows. It is never shown in any screen. Continuity is defined per partition as: in `seq` order, the first row's `prev_event_sha256` equals the partition's `genesis_sha256` and every later row's `prev_event_sha256` equals the previous row's `event_sha256`.

**Canonical form, `canonical_version = 1` (normative; the golden vectors are computed from this text alone).**

1. Input is the stored `audit_event` row as the database returns it, every column, keyed by its **snake_case database column name** (never the Drizzle camelCase key).
2. Leave out exactly three keys: `seq`, `prev_event_sha256` (it is hashed as the prefix in step 8) and `event_sha256`. Every other column is included, including `id`, `created_at`, `created_by` and `sandbox_of`.
3. Leave out every key whose value is SQL NULL. (So the NULL-by-CHECK columns `actor_label`, `object_label`, `updated_at`, `updated_by`, `deleted_at` are normally absent; if one is ever set by tampering it appears and the hash changes. A later nullable column with no default keeps old rows verifying.)
4. Value encoding: every integer column (`bigint`, `integer`, `smallint`, including `canonical_version`) as a JSON string of its decimal digits with no sign for positives and no leading zeros (`"1"`); booleans as JSON `true` / `false`; enums as their text label; uuids as lowercase hyphenated text; timestamps as UTC `YYYY-MM-DDTHH:mm:ss.SSSZ` (always three millisecond digits); hashes as 64-character lowercase hex; arrays (`gate_codes`, `need_to_know_acl`) as JSON arrays in stored order, each element encoded by the same rules; `reason_params` (jsonb) as a JSON object whose values are only strings and booleans (`record` refuses a jsonb number, so integers are stored as decimal strings there too), canonicalised recursively by these rules.
5. Strings are stored in Unicode NFC (`record` normalises to NFC before insert, so what is stored is what is hashed; the verifier never normalises, it hashes the stored bytes).
6. Serialise with RFC 8785 (JSON Canonicalization Scheme): object keys sorted by UTF-16 code units, no whitespace, strings in raw UTF-8 with only the RFC 8785 escapes (`\"`, `\\`, `\b`, `\f`, `\n`, `\r`, `\t`, and `\u00xx` in lowercase hex for other control characters below U+0020).
7. The result is `canonical_json`, a string.
8. `event_sha256 = lowercase_hex(SHA-256(utf8(prev_event_sha256_hex + canonical_json)))`: the 64 ASCII hex characters of the predecessor hash, immediately followed by the canonical JSON text, no separator, hashed as UTF-8 bytes.
9. `before_sha256` / `after_sha256` are computed by the calling module with the same rules (steps 1, 3 to 7, over the full business row, snake_case keys, no keys left out except those the owning module's spec names) and `lowercase_hex(SHA-256(utf8(canonical_json)))`.

Worked example (inputs are illustrative strings; the bytes are exact). A row that is the first event of the `live` partition with these non-null columns: `id` `11111111-2222-4333-8444-555555555555`, `ts` and `created_at` `2026-09-22T23:02:00.000Z`, `tenant_id` `00000000-0000-4000-8000-000000000001`, `actor_type` `HUMAN`, `actor_id` and `created_by` `PRN-JB00000001`, `actor_role` `CCO`, `action` `approval.approved`, `object_type` `approval_request`, `object_id` and `approval_id` `APR-2278`, `after_sha256` sixty-four `a`, `result` `ok`, `gate_codes` `{G13}`, `sensitivity` `normal`, `visibility` `staff`, `canonical_version` `1`.

- `canonical_json` = `{"action":"approval.approved","actor_id":"PRN-JB00000001","actor_role":"CCO","actor_type":"HUMAN","after_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","approval_id":"APR-2278","canonical_version":"1","created_at":"2026-09-22T23:02:00.000Z","created_by":"PRN-JB00000001","gate_codes":["G13"],"id":"11111111-2222-4333-8444-555555555555","object_id":"APR-2278","object_type":"approval_request","result":"ok","sensitivity":"normal","tenant_id":"00000000-0000-4000-8000-000000000001","ts":"2026-09-22T23:02:00.000Z","visibility":"staff"}`
- `prev_event_sha256` = genesis of `live` = `4f2a7c9e5a9522efaee6dca2789f0b55157cca880245739af8c168dd9e217478`
- `event_sha256` = `f9bba3814b58c9d027585bc5834d135b6c4959d139fcdf9a9b57246de74f2034`

`canonical_version` is part of the hashed content, so the form can change later without invalidating old rows; the verifier keeps one canonicaliser per version.

The canonicaliser, hasher and verifier live in `services/api/src/modules/audit/core/` and, because the worker may not import the API's code (A09 rule), a byte-identical copy in `services/worker/src/jobs/audit/core/`. Byte identity is asserted by a test inside this node's module (`modules/audit/tests/core-identity.test.ts` reads both trees and compares bytes), which runs as part of the unit tests `npm run verify` already runs, so no A09 file changes. [[A06 - Seed data and scenario simulator]] seeds audit rows; its fixture hashing must follow this canonical form (a third byte-identical copy under `packages/db/seed` through an A06 follow-up loop if it differs; this node does not edit A06's paths). [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]] records no extraction into `packages/runtime` in P1.

**Write path (internal interface, used by every module; the only way a row gets in).**

- `audit.auditedTx(ctx, fn)` wraps A09's `withTx`: it runs `fn(tx)`, then, as the last statement before commit and inside the same transaction, flushes the events queued on that transaction. Worker jobs and A09 event handlers use `audit.auditedJob(fn)` / `audit.auditedHandler(fn)`, which do the same inside the handler's transaction.
- `audit.record(tx, event)` validates at once (known action, required fields, PII guard, human-only rule, approval and custody ids) and **queues** the event on the transaction; it throws `audit_tx_not_audited` if `tx` was not opened by one of the three wrappers. It fills `ts`, `request_id`, `trace_id`, `session_id`, `tenant_id`, `sandbox_of`, actor fields, `actor_role`, `on_behalf_of_id`, `token_id` and `approval_id` from the request or job context, and `sensitivity` and `visibility` from the action table.
- The flush takes `pg_advisory_xact_lock(hashtext('audit:' || partition_key))`, reads the partition head (`WHERE <partition predicate> ORDER BY seq DESC LIMIT 1`), computes the hashes for the queued events in record order and inserts them. Business change and events commit or roll back together; there is no `record` without a transaction and no queued or asynchronous variant for business events.
- **Lock order.** Modules take their business row locks inside `fn`; the audit advisory lock is always the last lock a transaction takes, and nothing takes a lock after it. So the audit lock is held only for the insert and the commit, and it can never be part of a deadlock cycle. This is written into the module README and tested (below).
- A gate refusal must survive the failed request: `audit.recordRefusal(tx, { gate, reason_codes, gate_evaluation_id })` is called in its own `auditedTx` that commits even though the request returns an error. It writes `gate.refused` with `result = refused`, `gate_codes` and `gate_evaluation_id`, so a G13 or G22 refusal is a visible row.
- `audit.recordUnmask(tx, { object_type, object_id, fields[], reason_code })` writes `pii.unmasked` with field names only (never values). `audit.recordExport(tx, …)` is called by the export route below and by other nodes' export routes.
- **The action table** `actions.ts` is closed. Each entry has: a dotted code; a label (the design's "Approved", "Proposed", "Referred", "Detected break", or a template over `reason_params` such as "Signed {signed}/{of}"); `mutation` (true means `after_sha256` and an object are mandatory); `sensitivity` (`normal | sensitive`, which [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]] reads to notify a person of sensitive agent actions); `visibility` (`subject_visible | staff | need_to_know:<ACL> | security`); `requires_approval_id`; `requires_custody_op_id`; `human_only`. Later nodes add entries under their own name in a per-module `actions.<module>.ts` merged at registration; an unknown code is refused with `audit_unknown_action`.
- **G13 codes are generated, not hand-written.** Every SM-00 transition in A03's exported table (including `draft`, `submitted`, `closed`, the veto-window extension and `broadcast -> failed`) yields an `approval.<to_state>` code with `requires_approval_id = true`; the custody states (`queued_for_custody`, `signed`, `broadcast`, `confirmed`, `failed`) yield `custody.<state>` codes with `requires_approval_id` and `requires_custody_op_id` both true. A drift test regenerates the list from A03 and fails on any difference. `record` refuses a G13 action without `approval_id` (`audit_missing_approval_id`) and a custody action without `custody_op_id` (`audit_missing_custody_op_id`).
- **Human-only actions (staff agents are never checker).** `approval.approved`, `approval.rejected`, `approval.ratified`, `approval.vetoed`, every `custody.signed*` code and `hold.placed` / `hold.released` carry `human_only = true`; `record` refuses them for `actor_type = AGNT` with `audit_agent_human_only_action` (A04.x item 11 is the database net).
- **Visibility and tipping-off.** Defaults: `subject_visible` for the person's own account, order, holding and token actions; `staff` for operator and sponsor workflow actions; `need_to_know:MLRO,CCO` for every AML action (alert, case, SMR clock, sanctions hit, AML-driven unmask) and for any event whose `reason_code` is in the AML family (for example `AML_HOLD` on a held distribution exception), which `record` forces regardless of the module's declared class; `security` for `breakglass.*`, `audit.chain_broken` and security-driven unmasks. The class is enforced server-side in list, detail, export and `/v1/me/activity`, and by the A04.x RLS policy underneath. A hidden row produces no count, no gap marker and no cursor difference that a reader could notice.
- **PII guard (no free text anywhere).**
  - `reason_code` must be in the closed reason-code registry; `reason_params` values must be A02 ids, registered codes, decimal-integer strings or booleans; dates are not accepted in params (a date that matters sits on the business row, covered by `after_sha256`), so a date of birth cannot enter the chain.
  - `object_id`, `before_ref`, `after_ref` must parse as A02 ids or uuids.
  - Every string and integer value is also checked against `core/pii-patterns.ts`, an explicit field-class-to-pattern table (`tfn` → nine digits with the ATO check digit; `abn` → eleven digits with the ABN checksum; `bsb` + `account_number` → `\d{3}-?\d{3}` followed by six to ten digits; `email`; `phone` → Australian mobile and landline shapes; `payid`; `document_number` → passport and licence shapes). A startup check fails if any field class in A04's `PII_PATHS` has no row in the table.
  - A value that fails the grammar and matches a PII pattern is refused with `audit_pii_in_event`; a value that fails only the grammar is refused with `audit_invalid_ref`. Nothing is stored in either case.
  - The pattern table is tested on a positive corpus (the PII in A06's fixture shapes) and a negative corpus (ISO dates, A02 ids, uuids, hashes, cent amounts, unit counts): 100% hits, zero false positives.
- **Only writer.** A test in this module (`modules/audit/tests/writer-boundary.test.ts`, run by `npm run verify`'s unit tests) scans `services/`, `packages/` and `apps/` for any import of the `audit_event` Drizzle table object and any SQL text that inserts into `audit_event` outside `modules/audit` and `jobs/audit`; a planted direct insert elsewhere fails `verify`. A09 may later lift this into its lint config; that is A09's choice, not required here.
- **Outbox mirror** (the one asynchronous path, for events with no request or job transaction of their own): the worker handler `audit.outbox-mirror` consumes A09 outbox events whose `type` is on a closed allow-list of system events (`clock.advanced`, `job.failed`, `adapter.health_changed`, `outbox.relay_stalled`) and writes one chained row per `event.id` through `auditedHandler` (idempotent through A09's `processed_event` dedupe). A test asserts that no business event type is on that list, so no action is ever recorded twice.
- Test helpers exported from `modules/audit/testing/`: `expectAuditEvents(db, { action, object_ref, count })` and `countEventsSince(seq)`, so every later oracle can assert "exactly one event per privileged step" without touching the table directly.

**Read and export API (all under `/v1`, declared through A09's `defineRoute` with full `meta`, published into OpenAPI in the first commit so `packages/sdk` and the later MCP catalogue carry them).**

- `GET /v1/audit/events` (`listRoute`, cursor on `seq`, **newest first (`seq DESC`) by default**, `order=asc` optional, default 50, max 200): filters `from`, `to`, `actor_id`, `on_behalf_of_id`, `token_id`, `action`, `object_ref` (exact or type prefix), `approval_id`, `result`, `tenant_id` (platform staff only). Each item carries exactly what the design's table needs from one call: `ts`, `actor_label`, `actor_display`, `actor_type`, `action`, `action_label`, `object_ref`, `object_label`, `approval_id`, `result`, plus `on_behalf_of_label`, `token_id`, `event_sha256` and `seq`. Empty result: `{ items: [], next_cursor: null }`. Rows are scoped by the visibility rules above and the A04.x RLS policy. Authorisation is declared through `meta.scope` (the M25 audit cells of A03's matrix, as A11 names them) and enforced when A11's middleware lands; this node's tests set principals through A09's test hook and the node QA re-runs the scope probes at A11's gate.
- `GET /v1/audit/events/{id}`: one event with `prev_event_sha256`, `event_sha256`, `before_sha256`, `after_sha256`, `gate_evaluation_id` and `canonical_version`, under the same visibility rules (a hidden row is `404 not_found`, identical to a missing one).
- `GET /v1/audit/head`: current head per partition the caller can see and the last verification (`verified_at`, `mode: full`, `rows`, `anchors_checked`, `status: ok | broken | missing`, `first_bad_seq`), the data behind ADM-31's verification banner.
- `POST /v1/audit/verify` (mutation, idempotent, SECO and CCO): verifies synchronously up to 100,000 rows, otherwise enqueues the job and returns `202` with a job id; either way writes `audit.verified` or `audit.chain_broken`.
- `POST /v1/audit/exports` and `GET /v1/audit/exports/{id}`:
  - Body: the list filters, `format` (`csv | jsonl`) and an optional `reason_code` (enum: `internal_review`, `external_audit`, `regulator_request`, `complaint`, `legal`, `other_registered`), stored on `audit_export`.
  - At request time, under the partition's advisory lock, the route reads the partition head `max_seq`, counts the rows the caller can read with `seq <= max_seq` and the filter, and writes the `audit_export` row (`max_seq`, `row_count`, the caller's captured context) and the `audit.exported` event (filter hash, row count) in the same transaction. The export's own event has a higher `seq` and is never in its file.
  - The worker writes the file with the same predicate (`seq <= max_seq`) under the requester's captured context (principal, tenant, roles, sandbox, partner scope), so RLS and visibility match the request. If the rows written differ from `row_count`, the export ends in `failed` with `audit_export_count_mismatch` and an `audit.export_failed` event; otherwise the file is stored through A04's `document` conventions, its sha256 is written back, and `audit.export_completed` is written with the file hash.
  - Files are CSV or JSON lines with the list columns; more than 1,000,000 rows is refused with `audit_export_too_large` and the error body suggests a narrower filter. Sponsor register exports (SPN-08) and board-pack exports reuse `recordExport` from their own nodes.
- `GET /v1/me/activity`: rows where the caller is actor, on-behalf-of or subject and the row is visible to them, including everything their agents did; newest first by default, `order=asc` optional; POR-04, ACC-05 and SPN-16 read it later.
- `GET /v1/audit/holds`, `POST /v1/audit/holds`, `POST /v1/audit/holds/{id}/release`: legal holds over A04's `legal_hold` (`scope`: investor, vehicle, tenant, date range or action set; `reason_code`: court order, regulator request, complaint, litigation). **Worker jobs (`services/worker/src/jobs/audit/`).**

- `audit.verify` daily at 05:30 Australia/Sydney on A09's injected-clock scheduler (before the 06:00 reconciliation the design shows) is a **full recomputation from genesis** for every partition in `audit_partition` (1,000,000 rows in under 120 seconds is the budget): it checks linkage and every hash with the canonicaliser for each row's `canonical_version`; then checks that **every** stored `audit_anchor` row's `head_sha256` equals the recomputed hash at its `to_seq`, and that each anchor's evidence file (in both the evidence and the off-database directory) exists and its sha256 equals `evidence_sha256`. On success it inserts a new `audit_anchor` row and writes `head-<date>.json` for the live chain (`seq`, `event_sha256`, `ts`, `row_count`, verifier version, previous anchor hash), where `<date>` is the Australia/Sydney calendar date of the run. A break writes `audit.chain_broken` with `first_bad_seq` and the failed check (hash, linkage, anchor or evidence file), exits non-zero and writes `BROKEN-<date>.json`; [[A13 - Alerts and SLA-clocks service]] raises `audit.chain_broken` Sev1 from the last verification result (its `alerts.audit-chain-watch` job), and [[A20 - Three-way reconciliation engine with zero tolerance]] rule R18 calls this node's exported `verifyChain()` (the same full mode) rather than re-implementing it.
- `npm run audit:verify` runs the same verifier on demand; [[A23 - Whole-stack Docker boot (AM1 exit)]] uses it as the "audit chain verifies" exit check on the A06-seeded stack.
- `audit.hold-sweep` hourly: lists holds past their review date for A13 (as tasks, once A13 exists) and never releases one itself.
- `audit.evidence-ship` nightly: copies the day's head file and anchor record into the off-database directory, so an anchor exists outside the database and outside the directory the verifier writes. The optional on-chain `AuditAnchor` contract is a later chain node behind HG-AUDIT and HG-PROD; `onchain_tx` stays null until then.
- **Evidence directories.** The worker reads `AUDIT_EVIDENCE_DIR` and `AUDIT_OFFSITE_DIR` from A08's config (container defaults `/evidence/audit` and `/evidence-offsite/audit`), bind-mounted from `<workspace>\app\evidence\audit\` and `<workspace>\app\evidence\audit-offsite\`. **Retention, erasure and sanctioned deletion (defined here, executed by A99 and A102).**

- No live `audit_event` row is deleted in this build. `retention_policy` rows for `audit_event`, `audit_anchor`, `audit_partition` and `audit_export` are written by this node's seed hook with `min_years = 7` and `action_after = keep` (A102 keeps `audit_event` as `keep`). The next sandbox event starts generation n+1 with a fresh genesis.

When counsel answers the retention question, the design is: purge only a whole prefix up to a verified anchor older than seven years and not held, write a live `audit.prefix_purged` event with the purged head hash and count, and start verification from the oldest retained anchor. ## Node-specific challenges (node QA)

- **Money: a change without its event, or an event without its change.** A stub ledger module posts a journal on one connection and calls `record` on another; the process is killed between the two commits. Expected: impossible by construction because `record` queues on the caller's transaction and refuses any transaction not opened by `auditedTx` (`audit_tx_not_audited`); the "exactly one event" probe fails a module that writes zero or two events for one journal, and the writer-boundary test fails a planted direct insert into `audit_event`.
- **Money: the after-hash that does not cover the amount.** A distribution approval event carries an `after_sha256` computed over a payload without `net_cents`; the amount is then changed and the hash still matches. Expected: the same canonicaliser serialises every column of the business row, the golden vectors include a bigint change that flips the hash, and a mutation action without `after_sha256` is refused.
- **Compliance (D04, G22): the agent that looks like a person.** A token-authenticated request records `actor_id` as the human and leaves `on_behalf_of_id` and `token_id` null. Expected: `record` takes the principal from the context (kind `agent` → `AGNT` with `on_behalf_of_id` and `token_id` mandatory), the database constraint refuses the row without a human, a direct SQL insert with the same shape is refused too, and `GET /v1/me/activity` for the human shows the row with `actor_display` in the exact form `agent <TOK id> (<agent_name>) on behalf of <person label>`.
- **Compliance (G13): the agent checker.** An `AGNT` principal records `approval.approved`, `approval.vetoed` or `custody.signed`. Expected: `audit_agent_human_only_action`, nothing stored; `approval.approved` without `approval_id` is `audit_missing_approval_id`; `custody.broadcast` without `custody_op_id` is `audit_missing_custody_op_id`; a transition added to A03's SM-00 without a regenerated code fails the drift test.
- **Compliance (tipping-off): the investor who sees the AML case.** Seed an AML alert, an AML case, an `AML_HOLD` distribution exception and an AML-driven unmask about investor INV-A. Expected: diffing INV-A's `/v1/me/activity`, INV-A's export, SUPP's event list and an ordinary investor's activity before and after shows zero added rows, zero count differences and identical cursors; MLRO and CCO see all four rows; a `need_to_know` row fetched by id is `404` for everyone else.
- **Security: re-chaining after a mutation, before the anchor.** Someone with superuser access disables the trigger, edits a row older than the latest anchor and recomputes every later `event_sha256` so the in-database chain verifies clean. Expected: the daily full walk and `verifyChain()` both report the stored anchor whose `head_sha256` no longer matches, and the off-database head file disagrees with the database; R18 goes red.
- **Security: the agent that verifies or holds.** A staff token calls `POST /v1/audit/verify`, `POST /v1/audit/holds` and `POST /v1/audit/exports`. Expected: the first two are `audit_human_only` with no job enqueued and no row written; the export succeeds within the human's read rights, is written with `actor_type = AGNT`, `on_behalf_of_id` and `token_id`, is `sensitive`, and appears in the human's activity.
- **Security: PII through the side door.** A refusal param "123456782" (a valid TFN shape), an `object_id` that is an email, and a label resolver that returns a full legal name. Expected: `audit_pii_in_event` for the first two with nothing stored; the resolver output passes through the mask codec so the list shows "Jordan B.", never the full name; no ISO date or A02 id in the negative corpus is refused.
- **Concurrency: the fork and the deadlock.** Two workers read the same head and insert simultaneously; a third writes into a sandbox partition; other callers hold business row locks and long transactions; some transactions roll back after recording. Expected: the advisory lock serialises live writers, the unique index is the second net, every partition links from its genesis with no break, `seq` has gaps where rollbacks happened and nobody treats them as errors, no deadlock involves the audit lock, and the sandbox chain is independent with its own genesis.
- **Export and tenancy: the sponsor who exports the platform.** A sponsor user requests an export with another sponsor's `tenant_id`, or with no filter at all, while other events keep arriving; an investor requests an export of events about another investor. Expected: RLS and visibility limit rows to what the caller may read, `audit.exported` records the filter hash and a row count equal to the rows in the file, the file's sha256 equals the export row, and the investor's export contains only rows visible to them.
- **Partners: the auditor outside the engagement.** A TP-AUD user and a TP-OBS user list and export events for a vehicle outside their `vehicle_scope` and for an AML row inside it. Expected: zero rows in both cases; inside their scope they see `subject_visible` and `staff` rows only.
- **Design fidelity: the row the console cannot draw.** The list contract lacks `actor_display`, `object_label` or `result`, or returns rows oldest first by default. Expected: the five reconciled design rows come back from one `GET /v1/audit/events` call with every column the table shows, newest first, with "Custody quorum · Signed 3/3 · OP-7728 transfer (trustee) · APR-2268 · ok" fully resolved from ids.
- **Retention: erasure under a hold, and the sandbox purge.** An erasure is processed for an investor under a court-order `legal_hold`; the live chain is targeted by the sandbox purge function; a sandbox is purged and regenerated. Expected: `isHeld` returns true and the caller gets `audit_hold_active`; the purge function deletes no live row; the purge writes `audit.partition_purged` to the live chain with the final head hash and count; generation n+1 starts from a new genesis; the live chain verifies.

## Pass criteria

- 100% of the node QA's hidden oracle cases in `gauntlet\hidden\A10\` pass three runs in a row; the twenty canonicalisation golden vectors (including the worked example in this note) match byte for byte on Windows and inside the Linux container; the two `core/` copies are byte-identical under `npm run verify`.
- `UPDATE`, `DELETE` and `TRUNCATE` on `audit_event`, `audit_anchor` and `audit_partition` are refused for `realx_app` and `realx_worker` (missing grant) and for `realx_migrator` and a superuser session with triggers enabled (trigger), shown in the evidence with the database error text; the only admitted `DELETE` is a sandbox row deleted by the `realx_audit_purger`-owned function with both settings set; `realx_app`'s privileges on `audit_event` are exactly `SELECT, INSERT`.
- **Tamper coverage, by column.** Every column except `seq` is covered: all hashed columns (step 2 of the canonical form, including `id`, `created_at`, `created_by`, `sandbox_of`) by recomputation; the NULL-by-CHECK columns by appearing in the canonical form if set; `prev_event_sha256` as the hashed prefix and by linkage; `event_sha256` by recomputation and by the next row's `prev_event_sha256`. A one-byte change to any of those columns in any of 10,000 fixture rows (100 random trials across columns, rows before and after the latest anchor) is either refused by the database (type or constraint) or detected at that row, by both the scheduled `audit.verify` job and `verifyChain()`: 100 of 100.
