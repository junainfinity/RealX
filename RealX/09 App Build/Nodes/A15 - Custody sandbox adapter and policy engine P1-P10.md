# A15 - Custody sandbox adapter and policy engine P1-P10

**The custody layer that refuses to sign anything without an approved request: vault records V1-V7 with the product map's exact quorums, a no-value local keystore reached only through the `kms` adapter, the EIP-712 attestation key that binds one approval ID to one chain call, policy rules P1-P10 as pure functions fed through named provider ports, signer approvals as console actions under each signer's own hardware-key login, `CustodyOp` states from `prepared` to `reconciled`, a modelled rotation schedule, and the Q12 swap point where a Fireblocks-type engine replaces the sandbox behind the same interface and conformance suite.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-18 agent-hours (build, challenge and verify loops). If the first build loop runs past 18 hours, split into A15a (adapter, keystore, attestation, policy P1-P10, conformance) and A15b (API module, `CustodyOp` lifecycle, seeds, end-to-end runs) at the Escalate step.

**Depends on:** [[A14 - Approvals engine and maker-checker (SM-00)]], [[A08 - Sandbox adapter framework, config and phase flags]]
**Unlocks:** [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A28 - Token operations service (mint, burn, freeze, pause, forced transfer, recovery)]], [[A31 - On-chain identity and claims service (V4 identity agent)]], [[A72 - Console- token operations, forced transfer and recovery desk, wallets and custody, token registry|A72 - Console: token operations, forced transfer and recovery desk, wallets and custody, token registry]], [[A96 - P3- AUD stablecoin rail, V5-V6 vaults and travel rule (G15)|A96 - P3: AUD stablecoin rail, V5/V6 vaults and travel rule (G15)]], [[A103 - Runbook drills R1-R9 executed on the stack]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A15\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder; the cases are published into the repo only after the gate passes. The oracle scope is fixed by the node summary: nothing signs without an approved request; a replayed approval ID is refused; a signing request carrying a token credential is refused; plus the supply cap, the final-burn owner quorum, the maker-is-not-signer rule through every route, and the timelock.

This node is the software half of the key hierarchy (requirements catalogue D03 "Key hierarchy, must be modelled exactly"; architecture brief §4.2-§4.3 and §6). It runs entirely on the build machine with keys that carry no value. Production custody (a rented policy engine, an HSM or MPC vendor, the V1-V7 key ceremonies) sits behind human gates and is reached later through the same adapter interface; nothing in this node talks to a vendor. This plan is not legal advice.

## Build brief

**1. Adapter package (`packages/adapters/custody`), built on A08's frame**

- `manifest.ts` calls A08's `defineAdapter` with `name: 'custody'`, the zod interface contract, `implementations: { sandbox }` only, and `swap: { humanGate: 'HG-VENDOR', candidates: ['Fireblocks', 'BitGo', 'Dfns'], whatChanges: 'signer of AgentGateway calls and the policy evaluation (the product map role TP-SIGN, "Custody signing provider"); CustodyOp, attestation format, provider ports and API module unchanged' }`, so A08's generated `SWAP-POINTS.md` and its cross-check test pick the row up unchanged.
- `interface.ts` verbs, each with typed zod input and output and none taking or returning private key material: `createVault(spec)`, `getVault(code)`, `listVaults()`, `checkAllowList(vaultCode, target, selector)` (pure; A14's precheck hook calls it), `evaluatePolicy(op, context)`, `submitOp(op)`, `approveOp(opId, signerId, assertion)`, `broadcast(opId)`, `getStatus(opId)`, `cancelOp(opId, reason, principal)`, `rotateKey(vaultCode, signerId, ceremonyRecord)`, `suspendVault(vaultCode, reason)`, `issueAttestation(payload)`, `verifyAttestation(sig, payload)`, `health()`. There is no `sign` verb: signing happens atomically inside the `approveOp` call that meets the quorum (§5). There is no timelock or veto verb: the V2 and V3 window and its veto belong to A14 and the V1 window to the owner multisig (P10).
- **Provider ports** (also in `interface.ts`), the only way the policy engine reads data other modules own. Each is a typed zod interface with a sandbox fixture provider in `sandbox/providers/` and at least one conformance case of its own. A port with no registered provider makes every rule that needs it fail closed with `CST_PROVIDER_MISSING` (never a pass, never a skip):
  - `ApprovalReader` — `getRequest(approvalId)` returns state, `policy_code`, policy row id and version, `payload_canonical`, `payload_sha256`, `expires_at`, `maker_principal`, `excluded_signers[]`, the audit id and time of the `action.queued` event (or none) and any referenced waiver id. Real provider: A14's public `index.ts`, wired in the API composition root (A14 is a dependency). The adapter never queries A14's tables.
  - `RegisterReader` — holder units and the trust's total issued units at a point in time. Real provider registered by [[A18 - Unit register (legal record) and registry sandbox adapter]].
  - `AllocationReader` — the locked allocation file (id, lock hash, line destinations and units, file total, units already minted under it). Real provider registered by [[A38 - Finalise-and-mint and revert-and-refund pipelines]].
  - `IdentityRegistryReader` — whether a wallet is registered to a verified identity (off-chain record). Real provider registered by [[A30 - Investor onboarding, KYC cases and KYB (SM-01)]], with the on-chain check added by [[A31 - On-chain identity and claims service (V4 identity agent)]].
  - `KycCaseReader` — KYC case state and expiry for V4 ops. Real provider registered by A30.
  - `PaymasterBalance` — V7 deposit in wei and daily sponsored spend. Real provider registered by [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests|A29 - Wallet service: smart-account factory, bundler sandbox, guardians and recovery requests]] from A27's reads.
  - `ChainSubmitter` — receives a signed bundle. The in-memory chain stub inside this node until A28 registers its verified broadcast path over A27.
  Each node that registers a real provider re-runs this node's provider conformance cases against it before registration. In this node every end-to-end run uses the fixture providers.
- `sandbox/` is selected by `ADAPTER_CUSTODY=sandbox` through A08's registry; A08's config refuses any other selector while `RUN_MODE=local|test`. The sandbox receives A08's injected `Clock` and `SeededRandom` (never `Date.now()`), honours A08's magic inputs only inside `sandbox/` (reference prefix `SIM-REJECT` on an op forces a policy refusal; `SIM-DELAY-<seconds>` delays `broadcast`; `SIM-REVERT` fails at `broadcast`), and registers a `SandboxControl` with `trigger('advance-onchain-timelock', {opId})` (V1 multisig stub only; the V2 window is advanced through A13's clock), `trigger('expire-attestation-key')`, `trigger('broadcast-failure', {opId})`, `trigger('paymaster-drain', {toWei})`, `advance(duration)`, `reset(seed)`, `state()` (which never serialises key refs or signatures). A09 mounts these under `/sandbox/custody/*` in `local|test` only; the ADM-32 sandbox panel (A69) exposes them by hand.
- `conformance/*.conf.ts` is written against the interface, not the sandbox, and runs through A08's `runConformance` harness: at least one case per verb and per provider port, every policy rule P1-P10 with a pass and a refusal, every `CustodyOp` transition and every forbidden transition, determinism under `reset(seed)`, and the refusal cases in the challenge list below. It runs in `npm run verify` against the sandbox now; it is the artefact a human runs against a live vendor sandbox after HG-VENDOR before that implementation may be registered.
- `README.md` states the swap point in plain words: the signer of AgentGateway calls and the policy evaluation move into the vendor's engine (TP-SIGN); P1-P10 are re-expressed as the vendor's policy rules and the conformance suite proves the same refusals; `CustodyOp`, the attestation format, the provider ports, the API module and A72's screens are unchanged. This is one Q12 option-1 swap point and is reversible.

**2. Vault records (`CustodyAccount`) and the keystore**

- Tables owned by this node's module (`services/api/src/modules/custody/schema.ts`, under A04's module-schema convention): `custody_accounts`, `custody_signers`, `custody_signatures`, `custody_policy_evaluations`, `custody_key_rotations`, `custody_policy_changes` (the effector ledger P8 uses), `custody_business_calendar` (P6). The `custody_ops` columns come from A14; this node owns their behaviour and adds the columns it needs by migration in its own folder (`nonce`, `kind` `execute | authorisation`, `executable_at`, `timelock_source`, `bundle_id`, `owner_authorisation_op_id`).
- `CustodyAccount` fields: `vault_code` (V1..V7), `purpose`, `quorum_m` (signatures required), `quorum_n` (signers total), `signers[]` (each a named slot, a staff principal id and a kms `keyRef`; a check constraint refuses any `AGNT`, `AGT-U`, token or `SVCA` principal except the V4 and V7 service accounts, and refuses a vendor principal as a counted quorum member), `policy_version`, `function_allow_list[]` (target contract kind plus 4-byte selector), `p6_scoped_selectors[]`, `timelock_seconds` per function with `timelock_owner` (`approvals` or `owner_multisig`), `restrict_only`, `chain_id`, `gateway_address` (placeholder until the chain nodes deploy), `rotation_class` (hot / warm / cold), `rotation_due_at`, `daily_cap` and `runway_days` (V7 only), `sponsor_signer_slot` (null by default; the open founder question "does a sponsor hold a key" is data, not code), `state` (`active`, `rotating`, `suspended`, `reserved`).
- Seeded exactly as the product map's key hierarchy, asserted by a test rather than read from prose:
  - **V1 owner** 3-of-5 (slots CEO, CFO, CCO, SECO, independent), cold, allow-list limited to owner functions (`addAgent`, `removeAgent`, `setCompliance`, `setIdentityRegistry`, `setOnchainID`, `addModule`, `removeModule`, upgrade, token factory deploy) and never a value-moving function. Timelock 48 h for agent and compliance changes and 72 h for upgrades, `timelock_owner = owner_multisig` (P10).
  - **V2 token agent** 2-of-3, warm. Slots (default, marked founder-choice in the seed and on ADM-13): `V2-A` SECO, `V2-B` CEO, `V2-C` a second token-operations officer (TOKO) who is not the op's maker. CFO and CCO are deliberately not V2 slots because they are the usual checkers on mints and would be excluded by P9 on the ops they approve. Allow-list `mint`, `batchMint`, `burn`, `batchBurn`, `forcedTransfer`, `batchForcedTransfer`, `recoveryAddress`, `setAddressFrozen`, `batchSetAddressFrozen`, `freezePartialTokens`, `unfreezePartialTokens`, `unpause`, `HaltModule.setHalt` (the same list as A25's `gateway-config.json`). Timelock 48 h on `forcedTransfer`, `batchForcedTransfer` and `recoveryAddress`, `timelock_owner = approvals`.
  - **V3 pauser/freezer** 1-of-4 (slots CCO, SECO, MLRO, on-call ENGO), warm, `restrict_only = true`, allow-list `pause`, `setAddressFrozen(true)`, `batchSetAddressFrozen(true)`, `HaltModule.setHalt(true)`; anything that lifts a restriction is refused at V3 with `P2_RESTRICT_ONLY` and the approvals policy row routes it to V2.
  - **V4 identity agent** quorum 0-of-0, hot, the `SVCA` service principal as sole signer, allow-list `registerIdentity`, `batchRegisterIdentity`, `updateCountry`, `deleteIdentity`, `ClaimIssuer.addClaim`, `revokeClaim`; condition: the referenced KYC case is in state `approved` and unexpired (through `KycCaseReader`); per-minute rate limit as data.
  - **V7 paymaster** one hot key, held by this adapter's kms keystore, `daily_cap` in wei and `runway_days = 3`. This is the key A29's `paymaster/sponsor` asks to sign VerifyingPaymaster data; A29 holds no key of its own (see §4, V7).
  - **V5 distribution** and **V6 treasury** created in state `reserved` with empty allow-lists so A96 fills them without a schema change.
  - Product map ADM-13 says "Custody vaults V1–V9"; the key hierarchy defines V1-V7 and lists "Not needed: V8 DeFi admin". This node seeds V1-V7 only: V8 is not needed and V9 is undefined in the map. A72 shows V1-V7; the ADM-13 wording "V1–V9" is flagged for correction in [[A51 - Design extension B- operator console screens not in the prototype|A51 - Design extension B: operator console screens not in the prototype]].
- A seed-time **quorum reachability** test: for every approvals policy row whose `custody_vault` is V1, V2 or V3, the vault's signer slots minus the largest possible excluded set for that row (maker roles plus every checker role set) still reach `quorum_m`; otherwise the seed fails with `CST_QUORUM_UNREACHABLE` naming the row. This is why the V2 default slots avoid CFO and CCO.
- Reconciling the design with the product map on freezes: `setAddressFrozen(true)` sits on both the V2 and the V3 allow-list. The approvals policy row chooses the vault: an urgent sanctions freeze under `SGL+R` executes through V3; a standard freeze under `4E+Q` (the design's OP-7729 "Freeze wallet, AML-118, 2 of 3") executes through V2. The op record carries `vault_code` so ADM-14 shows the right meter.
- **`SGL+R` through V3 needs two people.** The `SGL+R` actor (CCO, SECO or MLRO) is the op's maker and is excluded by P9, so an urgent pause or freeze is signed by a different V3 member (1 of the remaining 3). A28 already verifies "exactly one signer who is not the `SGL+R` actor"; A48 and A103 must assume two people are needed for an urgent pause. Whether a one-person emergency action is wanted is recorded as a founder question (Human gates), not built.
- **TP-SIGN mapping.** The product map role TP-SIGN ("Custody signing provider", ADM-14, J09 step 8) is the production vendor engine behind the swap point: it evaluates P1-P10 as its own policy and executes once the staff quorum has approved. In the sandbox the sandbox engine plays TP-SIGN. It is never a counted quorum member and never a staff principal.
- Keystore: on first run the sandbox asks the `kms` adapter (A08) to `createKey` one secp256k1 key per signer slot of V1-V3, the V4 and V7 hot keys and the EIP-712 attestation key, and stores only the returned `keyRef`s and public keys in `custody_signers`. Signing is always `kms.sign(keyRef, digest, 'secp256k1')`; no file under `packages/adapters/custody/` ever holds key bytes, the encrypted material lives in the kms sandbox store under `STORAGE_SANDBOX_ROOT` (outside `app/`, a docker volume), and the keys are regenerable, carry no value, and never appear in logs, evidence or `state()`.
- Rotation schedule modelled as data (`rotation_class`): hot keys (V4, V7, attestation) every 90 days; warm keys (V2, V3) every 12 months or on staff change (A11's role-change event triggers a `rotation_due_at = now` for that signer); cold keys (V1) on ceremony only. `rotateKey` needs a `ceremonyRecord` (witness SECO plus custodian, date, old and new key refs) and is itself a request through A14 under the policy row "change custody signer policy: SECO to admin quorum", executed by the P8 effector (§4). A worker job flags `rotation_due_at` within 14 days as a Sev3 task to SECO; overdue rotation of a hot key suspends that vault's non-protective functions. Every rotation is an audit event. A103's key-compromise drill uses `suspendVault` plus `rotateKey`.

**3. Attestation key and the approval-ID binding**

- `issueAttestation` signs the EIP-712 typed message `CustodyAttestation(bytes32 approvalId, address target, bytes32 dataHash, uint256 expiry, bytes32 makerId, uint256 cap, uint256 nonce)` with the attestation key through kms. The domain is pinned to A25's: `{name: "RealXAgentGateway", version: "1", chainId, verifyingContract}` where `verifyingContract` is the gateway address of the op's vault (separate V2 and V3 gateways), so a V2 attestation is refused on V3. Until the chain nodes deploy, each vault's `gateway_address` is a fixed local placeholder from `packages/config` derived from A25's CREATE2 salts (`keccak("RealX/AgentGateway/V2")`, `.../V3`); A27's manifest replaces it. V1 ops use no gateway attestation: they carry `approvalId` and `makerId` into the owner multisig proposal (A25).
- Hash definitions, recomputed by P1 and never taken from the caller: `calldata` is produced by a deterministic encoder (`policy/encode.ts`) from A14's `payload_canonical`; `calldata_sha256 = sha256(calldata)` (stored on the op, shown on ADM-14 and signed over by signers' WebAuthn assertions); `dataHash = keccak256(calldata)` (in the attestation, checked on-chain). P1 recomputes both from the canonical payload and refuses if either differs from the op.
- The attestation is requested only by this module's own flow when an op meets its quorum (§5); the adapter reads the request's state through `ApprovalReader` before signing (P1) and never trusts the caller. It carries no PII and expires with the approval (A14's 72 h TTL).
- **One atomic point.** In the single transaction of the `approveOp` call that meets the quorum: the policy engine re-runs P1-P10, the attestation is issued, the signer signatures and the attestation are assembled into the bundle (`bundle_id`), `(approvalId, nonce)` is recorded as consumed, and the op moves `signing → signed`. If any step fails the whole transaction rolls back and the op stays `signing` with the refusal recorded. §5, the routes and the challenges all use this point.
- `verifyAttestation` is the same pure function the AgentGateway contract implements in Solidity (A25); the test vectors this node writes (`conformance/attestation-vectors.json`) are the shared fixture, so an attestation accepted here is accepted on-chain and vice versa.

**4. Policy engine P1-P10 (pure functions in `policy/*.ts`, evaluated on submit, on every approve, and on broadcast)**

- **P1 approval-ID binding.** The op carries an `approval_id`; `ApprovalReader` returns a request with that id that is `approved` or `queued_for_custody` (or `AUTO` with exact hash match), is unexpired and not cancelled; the encoder's `calldata` from its `payload_canonical` gives the op's `calldata_sha256` and `dataHash` exactly; and `(approvalId, nonce)` has never been consumed. Refusals: `P1_MISSING`, `P1_NOT_APPROVED`, `P1_HASH_MISMATCH`, `P1_EXPIRED`, `P1_REPLAY`, `P1_CANCELLED`.
- **P2 function allow-list.** `target` kind plus selector is in the vault's allow-list (`P2_NOT_ALLOWED`); V3 additionally refuses `unpause`, `setAddressFrozen(false)`, `unfreezePartialTokens`, `setHalt(false)` (`P2_RESTRICT_ONLY`).
- **P3 supply guard.** For `mint` and `batchMint` the running total minted under one `approval_id` never exceeds the attested `cap`, and concurrent ops under one id are serialised by a row lock so the sum is checked against committed state. The cap source depends on the approval: when the approved payload references a locked allocation file, the cap equals that file's total from `AllocationReader` (else `P3_CAP_MISMATCH`); when it does not, the cap equals the approved payload's unit total and the request must have been approved under the stricter non-file policy row (CFO + CCO, plus CEO where A28's row adds it), read through `ApprovalReader` (else `P3_NON_FILE_MINT_POLICY`). For `burn` the amount never exceeds the holder's units from `RegisterReader`. `P3_CAP_EXCEEDED`, `P3_CAP_MISMATCH`, `P3_NON_FILE_MINT_POLICY`, `P3_BURN_EXCEEDS_HOLDING`.
- **P3 final-burn owner quorum.** A burn (or `batchBurn`) that would take the trust's total issued units to zero according to `RegisterReader`, or whose approved payload carries `dissolution = true`, is a final burn (J08 step 10 "4E+Q; owner quorum for final burns"; J21 step 6). It needs the V2 quorum on the execute op **and** a recorded V1 3-of-5 authorisation: a V1 op of `kind = authorisation` under the same `approval_id` and the same `calldata_sha256`, which collects three distinct V1 signers' fresh hardware-key assertions through `approveOp` (P1 and P9 applied as for any op, so the maker and excluded principals cannot count) and reaches `signed` without any bundle, attestation or chain call. The V2 op records `owner_authorisation_op_id`; without a `signed` V1 authorisation the V2 approve that would meet quorum is refused with `P3_FINAL_BURN_NEEDS_OWNER_QUORUM`. V1 never executes the value move.
- **P4 destination guard.** Mint, forced-transfer and recovery destinations must be wallets that `IdentityRegistryReader` reports as registered to a verified identity (A31 later adds the on-chain check behind the same port); mint destinations must also be lines of the referenced allocation file where one is referenced; phase-P3 payout destinations (V5) must be inside the approved file. `P4_UNREGISTERED_DESTINATION`, `P4_NOT_IN_FILE`.
- **P5 amount bands.** Per-vault, per-function bands as policy data (units for token ops, wei for V7, cents for phase-P3 payouts); a breach refuses (`P5_BAND`) rather than silently escalating.
- **P6 time window.** Business hours in the `Australia/Sydney` time zone (default 08:00-18:00 on business days), with business days and public holidays (national plus NSW) in the `custody_business_calendar` table as data. P6 applies only to each vault's `p6_scoped_selectors`: V1 all owner functions; V2 `mint`, `batchMint`, `burn`, `batchBurn`, `forcedTransfer`, `batchForcedTransfer`, `recoveryAddress`, `unfreezePartialTokens`, `setAddressFrozen(false)`, `unpause`, `setHalt(false)`. Exempt: the V2 protective selectors (`setAddressFrozen(true)`, `batchSetAddressFrozen(true)`, `freezePartialTokens`, `setHalt(true)`), all of V3, V4 and V7. An out-of-window scoped op needs a `window_override` recorded on the approval by a `6E` policy row. `P6_OUT_OF_WINDOW`.
- **P7 KYT.** Reserved for phase P3 (wallet screening score from the sanctions adapter); in phases P1 and P2 returns `not_applicable_in_phase`, logged as such and never counted as a pass.
- **P8 policy-change quorum.** Custody policy data changes only through an A14 effector this node registers with `registerEffector('custody.policy.change', {execute, revert: null, postcondition})`. Which fields each path governs:
  - **V1 path** (`custody.policy.change`, the A14 policy row with SECO as maker and a `6E` checker set, 24 h timelock owned by A14's `queued`): signer slots and key refs, allow-lists, `p6_scoped_selectors`, quorums, timelock values, P5 bands, P6 hours, rotation classes, V4 rate limit. `execute` requires a V1 `authorisation` op under the same approval id at 3 of 5 distinct V1 hardware-key approvals (P9 applied), then writes a new `policy_version`. Once A25 exists, fields that the gateways and multisig also hold on-chain (signer set, quorum, allow-list, attestation signer) additionally go through the multisig selector for that change, and the multisig delay is that change's clock (P10's one-clock rule).
  - **ENGO → CFO path** (`wallet.gas_policy.change`, `4E`, A29's row "Change gas-sponsorship policy"): the V7 `daily_cap` and paymaster limits. The same effector ledger mechanism applies; no V1 authorisation.
  - **Read-only mirror**: which vault each action code uses (`custody_vault`) is read from A14's `approval_policies` (row 52 changes it); this node never stores or writes it.
  The guard against bypass is structural, not a session flag: the API's database role has no `UPDATE`/`INSERT` grant on `custody_accounts` or `custody_signers`; only the effector's dedicated role has it, and a trigger additionally requires, in the same transaction, an unconsumed `custody_policy_changes` row whose `approval_id` is in execution and whose payload hash equals the new row's canonical hash, which it then consumes. `P8_POLICY_CHANGE_UNAPPROVED`.
- **P9 initiator is not a signer.** The maker recorded on the request, everyone in A14's `excluded_signers[]` (checkers, delegates both ways, the humans behind any agent or token that touched the request) and every `AGNT` or `AGT-U` principal acting for any of them are excluded from the signer set for that op; an `AGNT`, `AGT-U`, token or `SVCA` principal can never be a signer of V1-V3 at all. Segregation of duties counts an agent as its human. A signing, approving, broadcasting, veto or suspend request whose credential is an API token or an MCP session (not a fresh hardware-key WebAuthn assertion or, for broadcast, a signed-in staff session) is refused before scope evaluation with `P9_TOKEN_CREDENTIAL`. The refusal is recorded through A12's `evaluateG22` path (one `gate_evaluation` row with gate G22 and reason codes `G22`, `P9_TOKEN_CREDENTIAL`, written by A12's middleware) and emits A12's outbox event `agent.action.refused` with reason codes `G22` and `P9_TOKEN_CREDENTIAL`, the token prefix and `on_behalf_of_id`. Turning that event into an anomaly is A101's job, not this node's. `P9_INITIATOR_IS_SIGNER`, `P9_AGENT_PRINCIPAL`, `P9_TOKEN_CREDENTIAL`.
- **P10 timelock, one clock owner per vault.** A15 starts no timelock of its own and holds no veto.
  - **V2 (and V3 if a row ever sets one): A14's `queued` is the only window and veto.** A14 creates the `custody_ops` row only after the window elapses. P10 re-derives `executable_at = time of the request's audit-anchored action.queued event + the policy version's timelock_hours` through `ApprovalReader`, and refuses `approveOp` and `broadcast` while `now < executable_at` (`P10_NOT_EXECUTABLE_YET`). For a function with a timelock, a request with no `action.queued` event and no approved waiver is refused (`P10_TIMELOCK_SKIPPED`). A waiver is the policy's named waiver approval (CCO + CEO with a court order for forced transfer, `court_order_waiver` in A14's policy data) referenced on the request. A veto during the window is A14's, and afterwards `ApprovalReader` reports the request cancelled, so any op under that id is refused `P1_CANCELLED`. `executable_at` on the op row is display only; editing it changes nothing because P10 never reads it.
  - **V1: the owner multisig's clock.** The op reaches `signed` at 3 of 5, is proposed to the multisig (the in-memory stub models A25's `RealXOwnerMultisig` until A25 exists), and enters `onchain_queued` with `executable_at` mirrored from the multisig's `Queued(id, executableAt)`; `broadcast` (the multisig `execute`) before it is refused `P10_NOT_EXECUTABLE_YET`. An owner veto on the multisig mirrors to `cancelled` and to A14 through its internal transition endpoint.
  - A103's drills advance the clock through A13's clock and the sandbox control, never by editing rows.
- Every evaluation writes a `custody_policy_evaluations` row (op id, rule, result, reason code, inputs hash, policy version, provider versions, evaluated at) so audits replay; a violation blocks and is never retried automatically.

**V7 paymaster behaviour.** Automatic sponsorship: A29's `paymaster/sponsor` asks this adapter to sign VerifyingPaymaster data with the V7 hot key under a standing `AUTO` approval (one per paymaster policy version, from A29's `wallet.gas_policy.change` request); P1 checks the standing approval is current and the hash of the effective paymaster policy matches it, and P5 checks that today's sponsored spend plus this op stays within `daily_cap` (in `Australia/Sydney` days). Top-ups of the paymaster deposit are `4E` requests (ENGO maker, CFO checker) per top-up, signed by the V7 key after approval and bounded by the P5 top-up band. Runway = current deposit ÷ trailing seven-day average daily sponsored spend, both read through `PaymasterBalance` (a sandbox fixture until A29 registers its provider); below `runway_days` exactly one Sev2 alert goes to ENGO through A13 per breach episode (re-armed only after runway recovers above the threshold).

**5. `CustodyOp` lifecycle (the custody half of SM-00)**

- States: `prepared` → `policy_checked` → `signing` → `signed` → (`onchain_queued`, V1 only) → `broadcast` → `confirmed` → `reconciled`; terminal `refused` (policy), `cancelled` (maker cancel, veto mirrored from A14 or the multisig, or parent expiry), `failed` (revert or registry reject). A V1 `authorisation` op stops at `signed` and is closed when the V2 op it authorises reaches a terminal state. The transition table lives in `packages/domain`'s custody slice (A03 owns the file; this node contributes the rows by the agreed extension point); anything not in the table is refused with `CST_ILLEGAL_TRANSITION`.
- `signing` collects distinct signer approvals. Each `approveOp` presents the signer's fresh hardware-key WebAuthn assertion over `calldata_sha256` (A11's fresh-assertion primitive), is re-checked against P9 and the signer's current vault membership, and is stored in `custody_signatures` with the decision. The approval that meets `quorum_m` (3 of 5 for V1, 2 of 3 for V2, 1 for V3, none for V4) performs the atomic step of §3 in the same request: bundle built, `(approvalId, nonce)` consumed, op `signed`. A signer cannot approve twice; an approval on an op that is already `signed` is refused (`CST_ALREADY_SIGNED`); a signer removed from the vault mid-flight has their approval discarded and the count recomputed; a vault in `suspended` or `rotating` accepts no approvals.
- `broadcast` hands the existing bundle to the `ChainSubmitter` port (the in-memory chain stub inside this node until A28 registers its verified path over A27) and moves `signed → broadcast`; it never re-signs. It is a console action by TOKO or any signer of the vault on a signed-in staff session; V4 and V7 `AUTO` ops broadcast automatically from the service account. `confirmed` and `reconciled` are driven by status callbacks from the chain adapter and the reconciliation module through `getStatus` and A14's internal transition endpoint. Only `reconciled` closes the parent `ApprovalRequest`; a `confirmed` op that recon has not closed stays open and visible, never reported as success.
- Cancellation after `signed` is impossible (the bundle exists); the op can only `fail` or proceed. Expiry or cancellation of the parent approval before `signed` cancels the op and marks the approval id refused for any later submit.
- Maker cancel: `cancelOp` is allowed only to the request's maker (or a token acting on the maker's behalf whose mandate includes the A03 matrix cell module M09, resource `custody_op`, action `cancel`, checked by A12's G22 evaluator) while the op is `prepared`, `policy_checked` or `signing`. It calls A14's public cancel on the parent `ApprovalRequest` first and cancels the op only if A14 accepts. A14's SM-00 table currently allows cancellation only from `draft` (and veto from `queued`), so until A03 adds `queued_for_custody -> cancelled : maker withdraws before signing`, the route refuses with `CST_PARENT_NOT_CANCELLABLE` and the op is left unchanged.
- V4 (`AUTO`) ops: `submitOp` from the identity service with an approved KYC case reference; the policy engine checks the case state through `KycCaseReader` and the rate limit, and the `SVCA` principal signs without a quorum; every V4 op is still one audit event and a targeted reconciliation trigger, and a V4 op for a case not in `approved` is refused (`P1_NOT_APPROVED`).

**6. API module (`services/api/src/modules/custody`)**

- Routes under `/custody`: `GET /vaults`; `GET /vaults/:code` (signer slots by role, `quorum_m`, `quorum_n`, allow-list, policy version, rotation due, V7 daily cap used and runway); `GET /ops?state=&vault=&trust=` (the "waiting for signatures" queue); `GET /ops/:id` (approval id, operation, detail line, calldata hash, policy evaluations, `signatures_have`, `signatures_required` (= `quorum_m`), `signers_total` (= `quorum_n`), `next_action` (`approve` while `signatures_have < signatures_required`, `broadcast` when `signed`, else none), `state`, `executable_at` and its source, tx hash, register-sync and recon state); `POST /ops/:id/approve` (signer, fresh hardware-key assertion; the approval that meets quorum returns `signed` and the `bundle_id`); `POST /ops/:id/broadcast` (op `signed`; staff session); `POST /ops/:id/veto` (V1 ops in `onchain_queued` only, owner with hardware-key assertion, forwarded to the multisig; for any other op it returns `409 CST_VETO_AT_APPROVALS` pointing to A14's veto on the request); `POST /ops/:id/cancel` (maker, §5); `POST /vaults/:code/rotate` (creates the request through A14 for the P8 effector); `POST /vaults/:code/suspend` (`SGL+R`, protective); `GET /policy-evaluations?op=`. All routes are RBAC-checked from A03's permission matrix (TOKO, SECO, CCO, CFO, CEO, MLRO, on-call ENGO by vault slot; TP-RE read, and veto only through A14; TP-OBS and TP-AUD read-only; SUPER never a signer, SoD rule 3) and published to `packages/sdk` for A72 and the MCP server (A104).
- Agent parity (founder requirement D04, gate G22): every read route is callable with a staff API token within its module scopes; `approve`, `broadcast`, `veto` and `suspend` refuse token and MCP credentials outright with `P9_TOKEN_CREDENTIAL`, naming G22 and P9 in the message, with the `gate_evaluation` row and `agent.action.refused` event of P9; `cancel` as maker is allowed to a token acting on behalf of the maker within the M09 `custody_op` `cancel` cell and is audited "agent <token prefix> on behalf of <person>". A12's G22 evaluator runs on every token call here like on any other route.
- Audit: every transition, evaluation, approval, veto and refusal writes exactly one hash-chained event through the audit module's interface (`custody.op.prepared`, `custody.op.policy_checked`, `custody.op.refused`, `custody.op.approved` per signer, `custody.op.signed`, `custody.op.onchain_queued`, `custody.op.broadcast`, `custody.op.confirmed`, `custody.op.reconciled`, `custody.op.cancelled`, `custody.op.failed`, `custody.vault.rotated`, `custody.vault.suspended`, `custody.policy.changed`, `custody.paymaster.runway_alert`) with `actor_id`, `on_behalf_of_id`, `approval_id` and `op_id`; the `signed` event's actor is "Custody quorum" with the n-of-m count, the shape the design's audit row shows.
- Empty and error states: no vaults seeded → `503 CST_NOT_INITIALISED` with the first-run instruction; an op for a `suspended` or `reserved` vault → `409 CST_VAULT_UNAVAILABLE`; a missing provider → `503 CST_PROVIDER_MISSING` naming the port; policy refusal → `422` with the rule code and a plain-English reason and never the private inputs; a signer without a hardware-key assertion → `403 CST_HARDWARE_KEY_REQUIRED`; an empty queue → `[]` with `count = 0` so ADM-14 renders "No operations waiting"; `GET /ops/:id` on a terminal op returns 200 with its terminal state, never 404.
