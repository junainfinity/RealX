# A99 - Developer surface: API versioning, reference docs, per-user sandbox and SDK/MCP packaging

**The D04 surface items no other node owned, built so a person can point their own agent at RealX safely: a versioning policy (`/v1` in the path, additive-only changes inside a version, deprecation and sunset headers, a published sunset calendar, the SDK and MCP packages pinned to the API version), reference docs rendered from the OpenAPI document at `/docs` in the design language (every operation with its scope, the gates that may refuse it, whether an agent may do it, idempotency and pagination notes and examples per user type, plus an agent quickstart per user type and the MCP connection guide), a per-user sandbox (an `rx_sb_` token acts on an isolated dataset generated for that person, through the same handlers, gates and maker-checker, never touching a live row, reset on demand) and version-stamped npm tarballs of `packages/sdk` and `packages/mcp` published to a local registry in compose.**

**2. Versioning, deprecation and the sunset calendar**

- The API major version is in the path (`/v1`; `/sbx/v1` for the sandbox). Inside a major version only additive changes are allowed: new operations, new optional request fields, new response fields, new error codes under an existing status, and new values in enums marked `x-realx-extensible-enum: true` (the SDK types those as `string & {}` unions, so clients must handle unknown values). Any other enum is closed, and adding a value to it is breaking.
- Breaking-change checker: `npm run api:compat`, a TypeScript rule set in `developer/versioning/compat/`. It compares the emitted `openapi.json` with the baselines in `docs/api/baselines/`. There are two kinds. **Pre-release baselines** (`v1.0.0-pre.N.json`) are written by `npm run api:baseline --node <id>` at each node's integration step from A99 onward. No customer holds them, so a breaking change against a pre-release baseline is a warning, not a failure: it must be written into `CHANGELOG.md` under "Pre-release breaking changes" with the node id and the rule that fired, and `verify` fails only if that entry is missing. **Released baselines** (`v1.0.0.json` onward) are frozen by `npm run api:release-baseline` at A89 (HG-LAUNCH, follow-up (p)) and never before. Against a released baseline the checker fails `verify` on any of these: a removed operation or path; a removed or renamed field; a type change or narrowed format; an optional request field made required, or a new required request field; a closed enum gaining a value or any enum losing one; a changed default or maximum page size; a removed response status or a changed success status; a changed error code string; a changed `x-realx-scope` to a narrower or different cell; a removed `x-realx-gates` entry; a changed `x-realx-mutation` or `x-realx-money`; or a changed idempotency requirement. Adding a gate to `x-realx-gates` is allowed but is listed in the changelog as "may now refuse" (a new rule can refuse more, never less). Narrowing an operation's delegation (`agent` to `agent-draft`, `agent` or `agent-draft` to `person` or `counsel`, or a counsel flag added by an HG-LEGAL answer) is also allowed inside `/v1` without a new major version, because the law or a counsel answer must win over client stability. It is listed as "may now refuse" with the reason, and it triggers the notice job below for every token that called the operation in the last 30 days. Widening a delegation is additive. Once a released baseline exists, a checker exception needs a new major version, and there is no override flag. The checker's own tests run on the fixture corpus (a fixed base spec plus one fixture per rule), never on the live baselines.
- Deprecation rows live in `developer/versioning/deprecations.data.ts` and are registered into A09's hook at boot: `{ operation_id, deprecated_at, sunset_at, replacement_operation_id?, notice_url }`. A load-time check refuses a row whose `sunset_at` is less than 180 days after `deprecated_at`. When the deprecated operation's delegation is `agent` or `agent-draft`, the row must name a `replacement_operation_id` that exists, is not itself deprecated, has a required scope in the same A12 family, and has the same or a wider delegation in A03's `delegable.ts`; otherwise the row is refused at load with `DEPRECATION_REPLACEMENT_INVALID`. A `person` or `counsel` operation may be deprecated without a replacement. From `deprecated_at` the operation answers with `Deprecation: @<unix seconds>`, `Sunset: <HTTP-date>` and `Link: <https://…/docs/changelog#op>; rel="deprecation"`. After `sunset_at` (read from the injected clock) it answers `410 operation_sunset` with `details.replacement_operation_id`. A future `/v2` runs beside `/v1` for at least 12 months. The founder confirms that figure at Specify.
- Pinning: `@realx/sdk` and `@realx/mcp` carry the same major and minor as the API (`1.4.x` for API `1.4`). Both embed `openapi_sha256` and send `X-RealX-Sdk-Version` or `X-RealX-Mcp-Version`, which A12 records in `api_token_activity` so ADM-35 can show which agents run outdated clients. `GET /v1/developer/versions` (public) returns `{ api_version, supported_majors, openapi_sha256, catalogue_sha256, sdk_version, mcp_version, tarball_sha256: {sdk, mcp}, deprecations[] }`.
- Changelog: `npm run docs:changelog` writes `docs/api/CHANGELOG.md` from the diff between consecutive baselines, grouped as added, may now refuse (new gates and narrowed delegations), deprecated, sunset and, before HG-LAUNCH, pre-release breaking changes. It is served at `/docs/changelog` and at `GET /v1/developer/changelog` (paginated).
- Deprecation notices: the worker job `developer.deprecation_notices` (in this node's worker folder, scheduled through a row in A46's catalogue on the injected clock) finds live tokens that called a deprecated operation, or an operation whose delegation was narrowed, in the last 30 days (from `api_token_activity`). It sends one notice to each owner through A43 at announcement and at 90, 30 and 7 days before sunset (for a narrowing, once at the change). Notices go to the person, never to the agent, following A101's NoticePolicy channel rules. It also emits `developer.deprecation.announced` on the outbox, so A46 webhook subscribers receive it.

**3. The per-user sandbox**

- One partition per owner principal (`sandbox_of = principal_id`). It is created on the first sandbox token of that principal, and it holds no copy of any live row and no real personal data, including the owner's own. The owner appears inside it as a fictional persona of their own user type ("Sandbox Investor", "Sandbox · Harbour & Co Property"), bound to the owner's principal id so RLS and G22 work unchanged.
- Environment routing: sandbox calls go to `/sbx/v1/...`. These are the same handlers, operation ids, schemas, gates, A14 maker-checker policies and G22 evaluator as `/v1`. A12's middleware refuses a sandbox token on `/v1` and a live token on `/sbx/v1` with `TOKEN_WRONG_ENVIRONMENT`, before any handler runs. On `/sbx/v1`, `withTx` sets `app.sandbox_of`, so A04's RLS is the second wall. Every response carries `X-RealX-Environment: live | sandbox`. The owner's own passkey session may also call `/sbx/v1/developer/sandbox/*`, which is how A60's "Reset my sandbox" works.
- Sandbox token issue rule (the input A12's issue path applies). **Spec point (a):** a fresh passkey assertion is required, as for every token. D04 lists "creating API tokens" as non-delegable and names no sandbox exception. A50 drew the sandbox create without a passkey step, so A50 is corrected through follow-up (o) unless the founder decides otherwise. **Spec point (b):** no second-person approval for sandbox tokens of sponsor members and staff, because the token cannot reach a live row or money. Staff still need the hardware-attested assertion. The founder or compliance confirms this at Specify. Scopes can never exceed the owner's live cells (A12's `validateTokenScopes`, unchanged), and the non-delegable and counsel-pending cells are refused exactly as on live. Limits are optional, so developers can test cap refusals. Expiry defaults to 30 days and cannot exceed 90. The issue event is written to the live audit chain, because issuing a token is a live act by the person.
- Generation: the profile is chosen from the owner's type and roles (`investor` with individual, joint or entity variants; `sponsor-member` for SP-OWN, SP-OPS, SP-FIN, SP-IR, SP-VAL and SP-PM; `partner` for TP-RE, TP-AUD, TP-OBS and TP-LIC; `staff` by role). Profiles live in `developer/sandbox/profiles/` and are passed to A06's `generate` with `asOf` = the live clock at generation, and loaded with `{ sandboxOf }`. Each profile contains the fictional counterparts that maker-checker and the journeys need: a sandbox SP-OWN, CFO, CCO, SECO, TRSY, CAPM, FINA, TOKO, REGO, ENGO, LEGL, PART, TAXO and a TP-RE, each with an A11 simulated passkey (sandbox only), so every approval in the partition is made by a principal who is not the maker. When the owner holds one of those roles, the counterpart for that role is a second fictional principal, never the owner. An investor partition (scenario `default`) has A$100,000.00 of fictional cleared funds in the partition's client-money ledger, two holdings, one pending distribution and one live offer `SBX-WLG01` (A$250.00 per unit, 10,000 units, soft cap 4,000 units = A$1,000,000.00, hard cap 10,000 units = A$2,500,000.00, 6,000 units of fictional funded orders). A sponsor partition has a tenant with three trusts, a register, a draft listing and a distribution to prepare. A partner partition has the vehicles or engagement that type reads. A staff partition (scenario `j20-daily-run`) has queues shaped like the J20 daily run: one planted chain alert, threshold monitors, a matched 02:00 reconciliation, integrations and jobs, overnight audit events, licence conditions, a disclosure update to prepare, sponsor performance, withholding exceptions, complaint deadlines and launch flags. Named scenarios are fixed data in `developer/sandbox/profiles/scenarios/` and are chosen with `POST reset { scenario }`:
  - `j04-wlg01-sandbox` (investor): offer `SBX-WLG01` with the terms above, but 9,900 units of fictional funded orders; the persona is INV-W with a wholesale certificate valid for 12 months after `asOf` (G04) and A$0.00 cleared funds, so the order is short and a PayID `receive_payment` of A$25,125.00 funds it (J04 step 5, G14). A 100-unit order therefore reaches the hard cap exactly, the offer closes at the hard cap (J04 step 7) with no scale-back, and the soft-cap refund path (J05) is never taken.
  - `j20-daily-run` (staff): as above.

  The same seed and scenario give the same `content_sha256`. The J04 reference run loads the same scenario with the same seed in live mode (no `sandboxOf`) into a disposable database and runs A49's J04 step runner over it; the sandbox doc-test must match that run (see Requirements covered). Generation is refused while a generation or reset is running (`409 SANDBOX_NOT_READY`) and is limited to 3 per owner per hour (`429 SANDBOX_LIMIT_REACHED`), a limit A83 asserts.
- Adapters and chain, partitioned (follow-ups (f), (n)): adapter calls made under a sandbox context reach an A08 sandbox instance keyed by `sandbox_of` (A15, A17, A18 and A22 each key their state by it), so the partition's bank statements, registry extracts, custody signing queue and identity scenarios are separate from the live partition's. Chain calls go to a second Hardhat node, `chain-sb` (chain id 31338), defined in `infra/sandbox-env/`. A27's deploy script runs there per partition, only for the vehicles the profile uses, and the addresses are recorded in the partition manifest. The live partition's chain, bank sandbox, reconciliation (A20, follow-up (i)), alerts (A13, follow-up (j)), notifications (A43, follow-up (k): for a sandbox they show only in the sandbox inbox, marked "[Sandbox]", never by email or SMS), anomalies and person notices (A101, follow-up (m)), webhooks (A46, follow-up (g)) and metrics never see a sandbox event. Worker jobs marked `partitioned: true`, including the 02:00 three-way reconciliation with zero tolerance, run per active partition on that partition's clock through A46's scheduler (follow-up (h)). A break in a sandbox halts resale only in that sandbox (A48, follow-up (l)).
- Sandbox controls (the panels, per partition, under `/sbx/v1/developer/sandbox/`): `GET` state (profile, generation, generator version, seed, clock, row count, balances, chain manifest, counterpart mode); `POST reset { scenario? }` (purges through A04's function, writes `developer.sandbox.reset` with the partition's final audit head hash and row count to the live chain, then regenerates as generation n+1 with the named scenario or `default`); `POST clock/advance { seconds }` (forward only, at most 400 days per call, moves only this partition's offset and `chain-sb` time for its contracts, never `system_clock`); `POST events/{event}` for the four outside-world events an agent may simulate (`receive_payment { amount, reference }`, `return_payment`, `drift_register`, `valuation_due`); `PUT counterpart-mode` (`manual | approve_all | reject_all | approve_after { minutes }`); and `POST counterpart/release { kind: approval | custody_sign | registry_ack, ref }`. `GET activity` returns the partition's audit rows with cursor pagination.
- Counterparts and the checker side (G13). The counterparts act only through the ordinary routes, as their own principals, run by the worker job `developer.sandbox.counterparts`. They are the only principals that ever approve, ratify, sign in the partition's custody quorum or acknowledge on its registry. The modes are: `approve_all` and `reject_all` (each pending item the owner's side creates is decided at once, as the counterpart); `approve_after { minutes }` (decided after that many minutes on the partition clock); and `manual` (nothing is decided until the owner, in their own passkey session, calls `counterpart/release` for one specific pending approval, custody operation or registry acknowledgement; the worker then makes that one decision as the counterpart principal, and A14 and A10 record the counterpart as the decider and the owner only as the requester of the release, never as the decider). `custody_sign` and `registry_ack` are never events an agent can fire: custody signatures and registry acknowledgements happen only through the counterpart engine under the current mode, or through a person-only release. A token calling `POST events/custody_sign` or `POST events/registry_ack`, `counterpart/release` or `PUT counterpart-mode` is refused `AGNT_NOT_ALLOWED` (reason code `G22_SCOPE_NON_DELEGABLE`) on the `requiresHuman` route before the handler runs (A12 §5 order of agent refusals), and no signature, acknowledgement or decision is recorded. So an agent can never choose when its own human's mint, payout or register entry is checked, even in a sandbox.
- Oversight and purge: `GET /v1/developer/sandboxes` (ENGO, SECO) lists partitions with owner, type, generation, rows, last used and state, for ADM-35's sandbox filter. `POST /v1/developer/sandboxes/{principal_id}/purge` is the abuse stop, and it also revokes that owner's sandbox tokens through A12. It is person-only: one SECO in a hardware-key passkey session, with a reason code, under A14 approval code `developer.sandbox.purge` (`SGL+R`, follow-up (a)). A different SECO or the CCO ratifies it inside A14's ratification window, and an unratified purge raises A14's alert. A SECO's agent, any token, and the acting SECO as ratifier are all refused. Partitions idle for 30 days are purged by the nightly job `developer.sandbox.idle_purge` (a system act, not a person's), and the next sandbox call regenerates the partition.
- Isolation checks beyond RLS: the idempotency scope includes `sandbox_of`, so a key used in the sandbox can never replay a live response. Cursors embed the environment, and a sandbox cursor on `/v1` returns `400 invalid_cursor`. Outbox events carry `sandbox_of`. A foreign key from a sandbox row to a live row is refused by a partition-consistency check that the loader and a nightly scan both run, because Postgres checks foreign keys without applying RLS. `liveDigest()` is sha256 over the canonical dump of every live row (`sandbox_of IS NULL`, or no `sandbox_of` column) in every table, leaving out only the frozen constant `LIVE_DIGEST_EXCLUSIONS` in `sandbox/digest.ts`. Both are exported from `index.ts` for A82, A83, A100 and the hidden tests, which import the constant and fail if it differs from this list:
  - table `sandbox_partition` (every row);
  - table `rate_limit_window`, rows whose `bucket_key` starts with `sbx:`;
  - table `api_token`, columns `last_used_at` and `last_used_ip` only, and only on rows with `environment = 'sandbox'`;
  - table `api_token_activity`, rows whose token has `environment = 'sandbox'`;
  - live audit rows and outbox rows whose event type is `developer.sandbox.*`, or is `token.issued` or `token.revoked` with `environment = 'sandbox'`.

  Any other exclusion, or any live-side change a sandbox call makes outside this list, fails. A probe takes its "before" digest after issuing its sandbox tokens.

## Node-specific challenges (node QA)

- **Sandbox bleed through shared keys (security, money).** The same `Idempotency-Key` is used for a live order and a sandbox order by two agents of one person. A sandbox cursor is replayed on `/v1`. A sandbox order is posted with a live offer id. Expected: no replay across environments (`422` or a fresh execution in the right partition), `400 invalid_cursor`, `404` for the live offer, and the live digest unchanged.
- **Sandbox money reaching live rails (money).** A sandbox withdrawal of A$40,000 is requested, the partition's counterparts approve it, and the payout runs. Then `drift_register` is fired in the sandbox. Expected: the payout appears only in the partition's bank-sandbox namespace; the live bank statement, live client-money reconciliation, live alerts (ADM-01), live approvals inbox and live webhooks are unchanged; the drift halts resale only in the sandbox.
- **Clock and chain crossing (compliance).** A sandbox clock is advanced 400 days, so a lock-in expires and a wholesale certificate lapses there. Expected: the live `system_clock`, live lock-ins (G08), certificate states (G04), SLA clocks and the live Hardhat chain time are unchanged, and a second partition's clock is unchanged too.
- **Agent as its own checker in the sandbox (agent misuse).** A sandbox token calls `PUT counterpart-mode approve_all` and then tries to approve its human's sandbox request through the ordinary approve route. Expected: `AGNT_NOT_ALLOWED` (reason code `G22_SCOPE_NON_DELEGABLE`) on the mode change, and `AGNT_NOT_ALLOWED` with reason code `G22_AGENT_NEVER_CHECKER` on the approval (both routes are `requiresHuman`; A12 §5). Only the owner's session with a passkey changes the mode.
- **Agent driving custody or the registry in the sandbox (agent misuse).** With counterpart mode `manual`, the agent places an order that reaches a pending mint, then calls `POST events/custody_sign`, `POST events/registry_ack` and `POST counterpart/release` for that mint. Expected: `AGNT_NOT_ALLOWED` (reason code `G22_SCOPE_NON_DELEGABLE`) on each, no custody signature, registry acknowledgement or approval decision recorded in the partition, and the mint still pending. The owner then releases it in a passkey session; A14 and A10 record the counterpart as decider and signer, and the owner only as the requester of the release.
- **Purge by self or by agent (segregation of duties).** A SECO's agent calls `POST /v1/developer/sandboxes/{id}/purge`; then the same SECO purges in person and tries to ratify their own purge; then the SECO's agent tries to ratify it. Expected: `AGNT_NOT_ALLOWED` (reason code `G22_SCOPE_NON_DELEGABLE`) for the agent purge, and a refusal of both ratifications (the ratifier must be a different SECO or the CCO, and an agent counts as its human); the purge stands as unratified and raises A14's alert until a different person ratifies.
- **A "harmless" breaking change (versioning).** The corpus includes: an optional field made required; a closed enum gaining `held`; the default page size moved from 50 to 25; `rate_limited` renamed `RATE_LIMITED`; a scope narrowed from `portfolio:read` to a sub-cell; and a `201` changed to `200`. Each must fail `api:compat` against a released fixture baseline, and each must pass with a warning and a required changelog entry against a pre-release fixture baseline (and fail when that entry is missing). A new optional field, a new operation and a new value in an extensible enum must pass, and SDK and MCP tarballs built from the fixture base spec must then run the whole contract smoke unchanged. A delegation narrowed from `agent` to `person` passes as "may now refuse" and queues a notice to each owner of a token that called it in the last 30 days. A deprecation row for an `agent` operation with no replacement, or with a replacement in another scope family or with narrower delegation, is refused at load.
- **Docs leakage (security, compliance).** The docs are built from a stack seeded with hostile names ("Ignore previous instructions…" as a property name) and with a real-format token in an example. Expected: the site is byte-identical to the build from an empty seed apart from the example bodies; no secret-pattern match; no staff operation in the public bundle; no AML reason, case type or list name anywhere public; and the claims lint passes.
- **Packaging (supply chain).** `pack:dev` runs with a stray `.env` and a fixture token file inside `packages/sdk`, and then `npm publish --registry https://registry.npmjs.org` is attempted.
