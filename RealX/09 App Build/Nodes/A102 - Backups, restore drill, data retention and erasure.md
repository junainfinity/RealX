# A102 - Backups, restore drill, data retention and erasure

**The node that owns what nothing else owned: encrypted nightly backups of the whole local stack (a physical Postgres base backup plus a continuous WAL archive, a logical dump, the kms keystore, the storage volume and the run-state volume), a restore script and a restore drill into a fresh stack that proves the audit-chain head hash (A10), the latest RegisterVersion hash per vehicle (A18), the ledger totals (A16) and the deployment manifests (A27) match the evidence taken before the backup, with recovery-point and recovery-time measured; one retention policy table (seven years for audit events, documents, register versions, approvals, distributions and tax and AML records, legal holds override, a sweep that refuses and logs every delete inside the window); and the privacy side: an erasure request that pseudonymises a closed investor, revokes their tokens, mandates and session keys and seals the wallet-to-person link while the chain and the hash chain stay intact, plus regulator and auditor exports that carry no personal data beyond what the request names.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-16 agent-hours (build, challenge and verify loops; each fix loop re-runs a full drill). If the orchestrator prefers smaller nodes, the natural split is A102a (sections 2 and 3: backups, restore, drill) and A102b (sections 4 to 6: retention, erasure, exports), both feeding A88; that split is a graph change, not made here. The drill runs at scale (A06's load profile) are wall-clock time on the local machine, not agent-hours; their duration is measured and recorded.

A98, A99 and A101 are AM3 and A85 is AM8; none depends on A102, so no cycle. These four edges must also be added to `final-graph.json` (a graph change, not made in this note).
**Unlocks:** [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A102\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. This is an oracle node (`oracle: yes`, set on 24 Sep 2026 by the plan review; `final-graph.json` must carry the same flag): it moves no money, supply or holdings, but authority moves here (erasure approvals, seal unsealing and PII-bearing exports under `4E` and `6E`), and it deletes, pseudonymises and restores the records that prove money, supply and holdings. The hidden set covers at least: the restore-evidence comparator (an independent re-computation of the four evidence hashes and totals), the tampered-backup set (flipped byte, swapped manifest, replayed older set, missing volume, key created after the backup), the retention oracle (a reference `isDeletable(record_class, anchor_date, holds, clock)` checked against the sweep on random triples to the day), the erasure probes (search by every identifier after erasure, chain verification, ledger and register equality, tipping-off diff), the restore-isolation counters (chain transactions, bank-sandbox writes and webhook deliveries from a destination project, all expected zero), the keep-class property (no sweep ever targets a `keep` class, an `INSERT_ONLY_TABLES` member or a table read by A16 totals or A18 register evidence) and the agent-misuse matrix. The tests are published into `app/` only after the gate passes ([[App Gauntlet]] §2).

This note is not legal advice. Every retention period, anchor date, statutory floor, backup retention period, recovery target and the handling of a privacy request below is a row of data marked "set with counsel" (or, for recovery targets, "set by the founder"); answers change rows, not code. Australia's Privacy Act has no general "right to be forgotten": what the product calls an erasure request is handled as a request to destroy or de-identify personal information that RealX no longer needs (APP 11.2), subject to the records other laws make RealX, the trustee or the RE keep. That framing is itself a counsel question.

## Build brief

This node owns four paths: the backup tooling and its compose profile (`infra/backup/`), the API module `retention` (`services/api/src/modules/retention/`: policies, holds read-through, the sweep planner, erasure, exports, backup and drill records), the worker jobs (`services/worker/src/jobs/retention/`) and the operator documentation (`docs/backup/`). It draws no screen. Every rule below is enforced in the API, the worker or the database, never only in a screen, and every read contract is in the OpenAPI document from the first commit so `packages/sdk` and the MCP tool catalogue (A12, A104) see it. The only source of time is A09's injectable clock; the only way to encrypt, sign or store is A08's `kms` and `storage` adapters.

**1. What this node reuses and what it adds (no duplication of A04, A10, A35, A44, A48)**

- Tables come from A04: `retention_policy`, `legal_hold`, `erasure_request` exist already. A04 said "a hard `DELETE` is refused by trigger for every role except the retention role A102 adds later", so the fifth database role `realx_retention` is requested from A04 as a numbered core migration in its follow-up loop (A04.n) before this build starts, per A04's own rule. The A04.n request lists the exact grants and nothing else: no `BYPASSRLS`; `DELETE` only on the tables of classes whose `action_after` is `purge` in the seed table of section 4 (never on a `keep` class, never on an `INSERT_ONLY_TABLES` member, whose insert-only triggers are not changed); `UPDATE` only on the columns listed in A04's `PII_PATHS` and the `_bidx` columns; `INSERT`, `SELECT` and `DELETE` on `erasure_seal`; `SELECT` on the tables the sweep planner and the erasure walk read; audit and outbox writes only through A10's `record` and `recordRefusal` functions (declared `SECURITY DEFINER` by A10, or an explicit `EXECUTE` grant named in A04.n, whichever A04 and A10 already use); never granted to `realx_app` or `realx_worker`; used only by the `retention.sweep` executor and step 2 of `privacy.erasure.execute` through a separate connection pool. The node's own tables (`backup_set`, `backup_file`, `restore_drill`, `erasure_seal`) are registered through A04's per-module schema registry, as A46 does; no core migration is written inside this node.
- Holds and retention checks are called, never re-implemented: A10's `audit.isHeld(object_ref)`, `verifyChain()`, `record`, `recordRefusal` and the `audit_export` contract; A35's `isRetained(version)` and `DOC_RETENTION_ACTIVE`; A48's `retentionHold({vehicleId | investorId}) -> {held, until, families[]}`; A44's `retention_until` on complaints and its `close-checks` list (units held, AUD balance, open orders, distributions in flight, open complaint, open KYC or AML matter, legal hold, estate flag). One composite read, `retention.check(object_ref) -> {retained, until, reasons[]}`, is exported from `index.ts` and is the only function the sweep and the erasure path consult; `reasons` is any of `in_window`, `legal_hold`, `trust_retention`, `document_retained`, `complaint_retention`, `aml_record`. For trust retention, `retention.check` and the erasure path call only A48's `retentionHold()` (whose value is the audit-anchored one) and never read `trust_retention` columns directly. `RETENTION_ACTIVE` carries A10's `audit_hold_active` in its `cause` field when the refusal comes from a hold, so both codes describe the same refusal.
- Revocation is delegated to each owner's existing public interface, called on the normal worker pool (never on the retention pool, and never inside the retention transaction). A12 already revokes every token, mandate, signing key and confirmation on `investor.offboarded` (A12's revocation table), and A29's `revokeSessionKey` runs through A12's revocation hook; erasure never happens before `investor.offboarded`, so the erasure effector asserts that the subject has zero active tokens and mandates and otherwise stops with `ERASURE_PRECONDITION_FAILED` naming `tokens_active`. For a `subject_type = principal` erasure (a staff, sponsor or partner user, section 5), A12 has no revoke-by-principal export today; an exported `revokeAllFor(principalId, reason)` is requested from A12 as follow-up loop A12.n, and until it passes the staff erasure path stops at `approved` with the named blocker `a12_revoke_unavailable`. On-chain: A29's `revokeAllSessionKeys(account)` is called and its UserOp must be confirmed on the local chain before the request can reach `completed`. Also delegated: A11's passkey, session and email-identifier revocation (except the privacy-only sign-in of section 5), A46's webhook-subscription removal, A43's channel and marketing-consent removal, and A99's sandbox-partition purge (rows with `sandbox_of` = the principal carry no value and are deleted by the retention role, a `purge` class).
- Evidence for the drill comes from the owners' public interfaces: A10 `verifyChain()` (head `seq` and `event_sha256`), A18 latest `RegisterVersion` per vehicle (`register_version_id`, `file_sha256`, `row_count`, `total_units`) and the stored CSV bytes, A16's nightly invariant totals (per tenant, currency and account type, plus the "client-money assets minus liabilities = 0" check), A27's `deployments/<chainId>.json` bytes and the code hashes it records, A20's reconciliation run. Nothing reads another module's tables directly.

**2. Backups (`infra/backup/`, compose profile `backup`)**

- Postgres (A01's Postgres 17 container, configured by A23) gains, through a compose override in `infra/backup/compose.backup.yml` layered on A23's file (A23's file is not edited; the override is registered under A23's profile convention): `wal_level = replica`, `archive_mode = on`, `archive_timeout = 60s`, and an `archive_command` that writes each WAL segment encrypted (below) to the named volume `realx_wal`, with the segment's sha256 appended to an archive index. A `backup-runner` service (the same Postgres image plus Node 24 and the backup scripts) runs on the `backup` profile; it is the only service that holds the Docker socket (section 3).
- The nightly set (job `backup.nightly`, 01:30 Australia/Sydney, after A18's 00:00 register snapshot and before A20's 02:00 reconciliation, registered through A09's `registerJob` so ADM-32 lists it through A46) takes, in order: the pre-backup evidence (section 3's four items, plus row counts per table and the erasure-ledger high-water mark); a physical `pg_basebackup` (tar, with the start and stop LSN) for point-in-time recovery with the WAL archive; a logical `pg_dump -Fc` of the same database (for portability and for the table-level checks of the drill); a copy of `realx_kms` (A08's keystore), the storage volume (A08's objects), `realx_state` (run state: deploy addresses, boot report) and any sandbox-adapter volume A23 declares. The volume list is computed from A23's compose file: every named volume is either in the set or on `infra/backup/exclusions.json` with a reason (`realx_chain`: "recreated on every boot by design; the chain is the external record and is reconciled, not restored"); a named volume in neither list fails `backup.nightly` and `npm run verify` with `BACKUP_VOLUME_UNCOVERED`.
- Encryption: every file is encrypted with AES-256-GCM under a fresh data key per set; the data key is wrapped by the kms key `kms://sandbox/platform/backup/v1`, and the keystore copy is wrapped a second time by a **backup escrow key** that lives outside the stack (file named by `BACKUP_ESCROW_KEY_FILE`, outside `app/`, gitignored, generated on first run like A08's dev master key), because a keystore encrypted only by a key inside that keystore cannot be restored. A `manifest.json` per set (`set_id` `BKP-<yyyymmdd>-<6 base32>`, `kind` `nightly | on_demand | pre_change`, start and stop LSN, file list with plaintext and ciphertext sha256 and byte size, key refs, the evidence block, `previous_set_id` and its manifest sha256 so sets form a chain) is signed with the kms P-256 key `backup-attest` and the signature is verified before any restore reads a byte.
- The keystore changes rarely but a key created after the nightly set would leave data unreadable after a restore. So `backup.keystore_on_change` subscribes to A08's key-created and key-rotated events and takes a keystore-only set within one job cycle; the drill's key-coverage check (section 3) proves it.
- Backup retention (data, founder and counsel to confirm): nightly sets 35 days, the first set of each month 12 months, WAL for the span of the oldest kept base backup. `backup.expire` (daily) deletes expired sets from `realx_backup` only after a newer verified set exists and writes `backup.set.expired`; a set is never expired while it is the last one a drill passed on.
- Records: `backup_set` (id, kind, state `running | completed | verified | failed | expired`, LSNs, sizes, manifest sha256, evidence block, `verified_by_drill_id`) and `backup_file`; events `backup.set.started`, `backup.set.completed`, `backup.set.failed` (Sev2 through A13, owner ENGO, ADM-32), `backup.set.verified`, `backup.set.expired`, each through A10 with actor `system:backup`.

**3. Restore and the restore drill**

- `npm run backup:restore -- --set <BKP-id> [--pitr <ISO time>] --project <name>` builds a **fresh** compose project (its own volumes, ports offset, never the running stack's volumes; restoring over the running stack is refused with `RESTORE_TARGET_NOT_FRESH`): verify the manifest signature and the set chain, unwrap the keystore with the escrow key, restore `realx_kms`, storage and `realx_state`, restore the base backup and replay WAL to the requested time (or to the end of the archive), then replay the **erasure ledger** (section 5) and run the checks. Order is enforced by the runner, not by convention: the destination's database container starts alone; the `api` and `worker` containers of the destination are not started (so they bind no port and run no job) until the erasure-ledger replay and check 9 have passed; only then is the `api` started, behind the read-only proxy below, and the `worker` starts only on release.
- **`RESTORE_MODE` isolates the destination from every shared external system, enforced by infrastructure this node owns** (so no other node's code has to change): the runner starts the destination on its own Docker network with no default egress; the only routes out are two proxies in `infra/backup/`: a read-only JSON-RPC proxy to the running Hardhat node that forwards only read methods (`eth_call`, `eth_get*`, `eth_chainId`, `eth_blockNumber`, `net_version`) and refuses `eth_sendRawTransaction`, `eth_sendTransaction`, `eth_sendUserOperation` and every other write or signing method, and a GET-only HTTP proxy to the source stack's bank sandbox statement endpoint. Webhook egress has no route at all. The destination's `worker` container is not started at any time before release, so the scheduler, outbox dispatch, A46 webhook delivery, A17 bank-rail writes, the A27, A28 and A29 chain-writing adapters, A48's HaltModule mirror and A20's break-to-halt path cannot run; the checks run as one-shot containers from the api image executing `infra/backup/scripts/` against the restored database. The destination API is reachable only through a runner-owned reverse proxy that refuses every non-GET request with `RESTORE_HOLD_ACTIVE`. The runner also sets `RESTORE_MODE=1` in the destination's environment so any component that already honours a safe-mode flag stays passive, but isolation never depends on it. `restore_hold` is this stack-level state, not an A48 `Halt`: it needs no approval id, it is never mirrored on-chain, and it is released only by a person at the keyboard (`npm run backup:release -- --project <name>`, which restarts the destination on the normal network after all checks passed and writes `restore.released`). A boot self-test (`isolation.ts`) probes each refused method and route from inside the destination network and fails the restore with `RESTORE_ISOLATION_FAILED` if any gets through.
- **Privilege boundary.** Only the `backup-runner` service on the `backup` profile mounts the Docker socket; the `api` and `worker` services never do, and a verify check (`npm run verify`, `BACKUP_SOCKET_EXPOSED`) parses every compose file and override and fails if any service other than `backup-runner` mounts `docker.sock` or a Docker context. `POST /v1/ops/restore-drills` and the monthly `backup.drill` job only insert a `restore_drill` row in state `requested` with one input, a `set_id`; the runner polls for such rows and runs a fixed drill command. The destination project name (`realx-drl-<drill id>`) and its port offset are generated by the runner, never taken from a caller, and the runner refuses any name equal to the running project's. `restore.ts` has two entry points: the interactive human restore (`backup:restore`, which refuses a non-interactive terminal with `RESTORE_HUMAN_REQUIRED`) and a drill mode that accepts only a set id and runs only when the runner-local secret file `infra/backup/.runner-secret` (created on first run, readable only inside the runner container, gitignored) is present; the drill mode never restores over an existing project.
- Checks, each a pass or a named failure written to `restore_drill.checks`: (1) A10 `verifyChain()` on the restored database passes and the head `seq` and `event_sha256` equal the manifest's evidence (for a PITR restore: equal the last head the WAL replay reached, that head appears in the source chain, and, in a drill (which always writes after the set), its `seq` is strictly greater than the manifest's evidence `seq` and every drill marker transaction (below) is present, so a base-backup-only restore fails this check); (2) for every vehicle, the latest `RegisterVersion` id and `file_sha256` equal the evidence, and re-hashing the CSV read back from restored storage gives the same `file_sha256`; (3) A16's totals per tenant, currency and account type equal the evidence to the cent and the zero invariant holds; (4) A27's `deployments/<chainId>.json` bytes hash to the evidence and the code at each recorded address on the chain still matches the manifest's code hash; (5) row counts per table equal the evidence; (6) key coverage: every key ref referenced by any wrapped key, `_enc` column envelope or storage object in the restored data exists in the restored keystore, and a sample decrypt per key succeeds; (7) every storage object's sha256 re-computes; (8) an A20 three-way reconciliation **dry run** (no break records, no halts, no alerts, no effects) in the restored stack, reading the running Hardhat chain through the read-only adapter and the source stack's live bank sandbox read-only (its statement endpoint only), shows zero breaks (A20's spec has no dry-run entry point today; one is requested from A20 as follow-up loop A20.n, and until it exists check 8 runs A20's comparison functions in a one-shot check container inside the isolated network, discards any break row it writes to the destination database, and the isolation counters prove nothing left the destination); (9) the erasure ledger replay left no erased subject findable (section 5's search probe) and every replayed seal matches its ledger hash (section 5).
- Drill (`npm run backup:drill`, also job `backup.drill` monthly, which raises this node's own A13 alert `backup.drill_due` (Sev4, SECO and ENGO, ADM-01) when the last passed drill is older than 35 days; A48's `runbook.drill_due` is computed only from A48's R1-R9 rows and is not used here): start a source project from A06's seed and simulator, drive a burst of traffic (orders, a distribution, a withdrawal, an erasure, a key rotation), take a set, then write **marker transactions** (a dedicated `restore_drill_marker` row committed after the set's stop LSN, then one per `archive_timeout` interval) and keep driving traffic for at least two `archive_timeout` intervals after the last marker, record the last committed transaction time, stop the source's database container (simulated loss), restore into a destination project with PITR to the end of the archive, run the checks, and record: **RPO** = last committed transaction time at the source minus the last transaction present after restore; **RTO** = restore command start to checks passed. Binding structural bound (not a founder target, never waived): on the design-seed drills RPO is at most `archive_timeout` plus 60 seconds, every marker committed at least two `archive_timeout` intervals before the loss is present after restore, and the restored head `seq` is greater than the manifest's evidence `seq`; a drill that misses any of these fails, which is what proves point-in-time recovery works. Founder targets (data, founder to confirm): RPO at most 5 minutes; RTO at most 30 minutes for the design seed and at most 2 hours for A06's load profile (100 trusts x 10,000 holders) on the build machine. Only the load-profile RTO may be recorded as a measured gap for the founder instead of failing. The source and destination share the running Hardhat chain container (the chain is not restored; see the exclusion above) and the source's bank sandbox; the destination reaches both read-only under `RESTORE_MODE`, and the drill counts, at the Hardhat node (transactions from any destination-held address or signer), at the bank sandbox (write requests from the destination) and at a webhook sink bound for the drill, every effect the destination produces; each count must be zero.
- Records: `restore_drill` (`DRL-<yyyymmdd>-<6 base32>`, set id, mode `full | pitr`, target time, `rpo_seconds`, `rto_seconds`, `checks[]` with expected and actual values, `isolation` (chain, bank and webhook effect counts), state `requested | running | passed | failed`, `evidence_path`); a passed drill marks its set `verified`. `docs/backup/` holds the operator runbook (take a set, restore, PITR, release the `restore_hold`, what to do on each named failure), written in the A85 runbook format with role placeholders only.

**4. Retention policy and the sweep (N01)**

- One policy table: A04's `retention_policy`, one row per record class with `record_class`, `tables[]`, `anchor` (`event_date`, `closed_at`, `relationship_end`, `wound_down_at`), `min_years`, `floor_years` (the statutory floor a policy change can never go below), `action_after` (`purge`, `pseudonymise`, `keep`), `set_with_counsel`, `source_node`. This node seeds the rows no other node seeded and checks the others exist: seven years for `audit_event`, `audit_anchor`, `audit_export` (A10), documents, acknowledgements, envelopes and templates (A35), `register_entry`, `register_version`, `register_instruction`, `register_extract` (A18), `approval_request` and decisions, `custody_op`, `distribution_run` and lines, tax components, AMMA statements, withholding and CRS/FATCA records (A41), ledger journals and bank statements (A16, A17), orders and allocations, halts and `trust_retention` (A48), complaints (A44, from `closed_at`), KYC cases, screening hits, AML cases, restrictions and filings (A30, A42, anchored at `relationship_end`: seven years after the account closes, whichever is later), `api_token_activity` and `gate_evaluation`. Shorter classes: sessions 90 days, idempotency keys and processed events 30 days, sandbox partitions 30 days after the owner's last sandbox token is revoked, telemetry per A85 (not a record). `audit_event` is `keep`: the sweep never deletes an audit row in this build (pruning a hash chain needs a checkpoint design and a counsel answer first); it reports how many rows are past the window.
- **`action_after` per class (seeded data, part of the frozen spec; a change is a policy version under `4E`, and moving a class from `keep` to `purge` also needs an A04 grant change):**

  | `action_after` | Record classes | What the sweep does after the window |
  |---|---|---|
  | `keep` (until counsel supplies a checkpoint or archival design) | `audit_event`, `audit_anchor`, `audit_export`; `ledger_journal`, `ledger_entry`, `ledger_snapshot`, `bank_transaction` (A16, A17); `register_entry`, `register_lot`, `register_version`, `register_instruction`, `register_extract` (A18); `approval_request`, `approval_decision`; `custody_op`; `distribution_run`, `distribution_line`, `tax_component`, `amma_statement`, withholding and CRS/FATCA records (A40, A41); orders and allocations; halts and `trust_retention` (A48); complaints and `complaint_event` (A44); KYC cases, screening hits and every A42 AML table; `gate_evaluation`, `api_token_activity`; every member of A04's `INSERT_ONLY_TABLES` | Counts rows past the window per class and reports them on the dry run and in the event `retention.past_window` (counts only). Deletes nothing. |
  | `purge` via owner | document versions and their stored objects (A35), when not an `INSERT_ONLY_TABLES` member; acknowledgements and envelopes stay `keep` | Only through A35's `isRetained(version)` and then A08's `storage.deleteObject` for each stored object, each object deletion audited (`retention.object_deleted` with object ref and sha256); the row goes only after its object is gone. |
  | `purge` | `session`, `idempotency_key`, `processed_event`, sandbox partitions (`sandbox_of`), expired `erasure_seal` rows (section 5), expired backup sets (section 2) | Deletes in batches on the retention pool. |

  The sweep's class list is computed from this table only; a class not in it is `keep` by default. `realx_retention` holds `DELETE` only on the `purge` tables. Two properties are hidden tests: the sweep never targets an `INSERT_ONLY_TABLES` member or any table read by A16's totals or A18's register evidence; and after a sweep at clock + 10 years over A06's simulator data, A16's totals per tenant, currency and account type and every A18 `RegisterVersion` `file_sha256` are unchanged.
- A policy change (`POST /v1/retention/policies/{class}/versions`) is an A14 request `retention.policy.change` under `4E` (LEGL maker, CCO checker); a version with `min_years` below `floor_years` is refused before the request is created with `RETENTION_BELOW_FLOOR`, and no approval can override the floor (the floor itself changes only by a data migration after counsel). Policy versions are insert-only; the sweep always reads the version in force at run time.
- `retention.sweep` (daily 03:30 Australia/Sydney, idempotent, on the `realx_retention` pool): for each class with `action_after = purge`, select candidate rows whose anchor is older than `min_years`; for each, call `retention.check`; delete only rows with `retained = false`, in batches, writing one `retention.purged` event per batch (class, count, id range hash, policy version). Every candidate refused (held or in window) is logged as `retention.delete_refused` with the reason, once per row per hold (not per run), through `audit.recordRefusal`. `POST /v1/retention/sweeps/dry-run` returns the same plan (eligible, held, in window, per class) without deleting.
- Defence in depth: a `BEFORE DELETE` trigger on every retained table (installed through the A04.n migration) calls `retention_guard()`, which refuses a delete from any role inside the window or under a `legal_hold` row with SQLSTATE `RX001` and a structured message; because a refused statement rolls back its own transaction, the refusal of a raw SQL delete is recorded by `retention.refusal_harvest` (every minute), which reads Postgres's `jsonlog` output (enabled by this node's compose override) for `RX001` lines, and for `42501` (permission denied) and A04's insert-only refusal lines on a `DELETE` against a retained table (the refusal a role without the grant, or a `keep` table, produces), and writes `retention.delete_refused` with the database role, table, row ids and statement fingerprint. A refused delete therefore always leaves an audit event: directly when it came through the sweep, within one job cycle when it came through SQL.
- J21 (wind-down, step 7): the sweep treats every record family that A48's `retentionHold({vehicleId})` returns in `families[]` as retained until the returned `until`; it never reads `trust_retention` columns, so a hand edit of `trust_retention.retention_until` in the database changes nothing here (a challenge case); a wound-down vehicle's records cannot be purged early by any path, and when the date passes they are purged only if no hold names them.

**5. Erasure (privacy request) and the sealed link**

- `POST /v1/me/privacy/erasure-requests` (`requiresHuman: true`, fresh passkey assertion with purpose `privacy_erasure` over the request hash from A11's primitive; an AGNT principal gets `AGNT_NOT_ALLOWED` before scope evaluation) creates an `erasure_request` (`ERQ-<yyyymmdd>-<6 base32>`) for the signed-in investor, opens the A13 clock `privacy_request_30d` (owner LEGL; the period is `set_with_counsel`) and writes `privacy.erasure.requested`. If the account is still open, the response lists the close-account blockers from A44's `close-checks` (the same list ACC-01 shows) and the request waits in `awaiting_closure`; the investor closes the account first through the existing close path.
- **Who can be erased (subject scope, data in the frozen spec):**

  | Account type | What is erased | Precondition | Fixture and test |
  |---|---|---|---|

- **Reaching the route after offboarding.** A30 makes `offboarded` terminal and A12 revokes every token on it, so no agent can reach these routes after closure. The person reaches them in one of two ways: (1) a passkey sign-in that A11 limits, for a principal whose investor is `offboarded`, to `/v1/me/privacy/*` and the read of their own statements (A11 has no rule for offboarded principals today; the limited session is requested from A11 as follow-up loop A11.n); or (2) an assisted request: SUPP records the request as maker after an identity check against the person's KYC record (A30's re-verification path), and LEGL is the checker; the request carries `channel = assisted`. Until A11.n passes, only path (2) is tested for closed accounts, and path (1) is tested only for a request raised before closure.
- Local transition table (A03 engine format, not one of the 14 product-map machines): `received -> awaiting_closure | assessing`, `awaiting_closure -> assessing` (on `investor.offboarded`), `assessing -> approved` (A14 request `privacy.erasure.approve`, `4E`, LEGL maker, CCO checker), `assessing -> deferred` (a hold, a trust retention hold on the investor, an open AML matter, an open complaint), `deferred -> assessing` (the blocker cleared; re-checked by `privacy.deferral_watch` daily), `approved -> executing -> completed`, `received | awaiting_closure | assessing -> withdrawn` (the person, `requiresHuman`), `assessing -> refused` (LEGL with reason code, CCO checker; for example the requester is not the subject). Any other pair is `409 ERASURE_ILLEGAL_TRANSITION`. A trust retention hold from A48's `retentionHold()` moves the request to `deferred` (never `refused`) and writes one `retention.delete_refused` audit event per held family with reason `trust_retention`; A48's challenge ("the erasure refused and logged") must be read as "deferred, with `retention.delete_refused` logged", and A48's spec is to record the same wording at its next loop (a change in A48, not made here).
- Tipping-off (N08, G14): the investor-facing status is one of `received`, `in_progress`, `completed`, `withdrawn`, `could_not_complete`, and `deferred` for any reason is shown as `in_progress` with the same expected date as any request in assessment. The completion notice lists the record classes kept by law and until when from a **fixed** list that is identical for every investor (it always includes "anti-money laundering records, kept seven years after your account closed"), so the notice never differs because an AML case exists. The internal reason for a deferral is readable only by LEGL, CCO and MLRO, and when it is an AML matter only by the MLRO and CCO (A42's need-to-know ACL); SUPP and IRCM see `in_progress`.
- End of the response period: when `privacy_request_30d` expires for any request not yet `completed`, `withdrawn` or `refused`, whatever the internal reason (an AML matter, a legal hold, an open complaint, a trust retention hold, or plain slowness), the investor-facing status becomes `could_not_complete` with one fixed generic notice ("We are required by law to keep some of your records for now. We will write to you when that changes." — the text is a counsel row) and the same fixed kept-records list; the internal state stays as it is and the A13 breach alert goes to LEGL only (never to SUPP or IRCM, and the alert payload carries no reason). If a deferred request later completes, the status becomes `completed` with the ordinary completion notice. Parity is therefore defined in two windows: inside the period, an AML-deferred request is indistinguishable from an ordinary request in assessment; after the period, it is indistinguishable from a request deferred for a non-AML reason (a legal hold or an open complaint). Latency parity is measured, not asserted: every investor-facing handler of this module pads its work to a constant budget, and over at least 200 samples per case the p95 difference is at most 20 ms.
- Execution (`privacy.erasure.execute`, the effector of the approved request) runs as ordered, idempotent steps keyed by the erasure id; a crash between any two steps resumes at the first step not recorded as done in `erasure_request.steps_done[]`, and the request reaches `completed` only when every step is done. Preconditions (account offboarded or subject scope met, no hold, no open AML matter, no open complaint, `retentionHold()` not held) are checked before step 0 and re-checked inside step 2.
  - **Step 0, write-ahead ledger line.** Assign the pseudonym `ERX-<8 base32>` (shown wherever a name was: "Erased investor · ERX-7Q2M4KD1") and the seal id; compute `subset_mac`, an HMAC-SHA256 under the kms key `kms://sandbox/platform/erasure-seal-mac/v1` over the canonical serialisation of the statutory subset (step 2b), so the ledger holds no personal data and the value cannot be guessed from a dictionary; append one line (erasure id, subject type and id, pseudonym, seal id, `subset_mac`, approved time) to the **erasure ledger**, an append-only file on the `realx_backup` volume outside the database, fsynced before step 1. Appending is idempotent by erasure id.
  - **Step 1, revocation through each owner's public interface** on the normal worker pool (section 1): assert A12 shows zero active tokens and mandates for the subject (or call A12.n's `revokeAllFor` for a principal subject); call A29's `revokeAllSessionKeys` and wait for the UserOp's confirmation on the local chain; A11's passkey, session and identifier revocation (the limited privacy session of the request ends here); A46's webhook-subscription removal; A43's channel and marketing-consent removal; A99's sandbox-partition purge. Each call is idempotent and its result is recorded in `steps_done`.
  - **Step 2, one database transaction on the `realx_retention` pool.** Re-check the preconditions and recompute `subset_mac` (a mismatch with the ledger line aborts with `ERASURE_PRECONDITION_FAILED` naming `subject_changed`). (a) Insert the `erasure_seal` row; (b) the statutory subset of personal data (identity and KYC fields, residency, the person's tax identifiers, bank account details used for payments, the on-chain claim-data preimages from A31, contact details at the time of closure) is encrypted under the kms key `kms://sandbox/platform/erasure-seal/v1` with the seal id as associated data; KYC documents and certificates stay in storage because they are AML records, and their object references move under the seal; (c) overwrite every personal field of the subject listed in A04's `PII_PATHS` (per the subject-scope table above) with the pseudonym or null, and clear every blind index (`email_bidx`, `phone_bidx`, `tfn_bidx` and any other `_bidx` in `PII_PATHS`); (d) redact free text only in the tables of the **redaction list** below; (e) write `privacy.erasure.executed` through A10's `record` (ids and hashes only).
  - **Step 3, free text owned by other nodes.** For insert-only free-text tables that are not statutory records, the original body is moved under the seal and replaced only through the owner's function: A44's `ticket_message` body through a redaction function requested from A44 as follow-up loop A44.n (`redactMessageBody(messageId, sealId)`, the only update A44's insert-only rule would allow); until A44.n passes, ticket bodies are left unchanged, listed in the request's `pending_redactions[]` and the request stays `executing`.
  - **Step 4, completion.** Emit `privacy.erasure.completed` through A10 with ids and hashes only (so the chain never changes and verifies afterwards), and to the sponsor tenants that held the investor's `tenant_consent` so the trustee can decide on its own record (counsel question).
  - Kept unchanged by every step: every record that holds ids only (orders, allocations, journals, distribution lines, tax components, approvals and their reason fields, custody ops, acknowledgements, complaint and `complaint_event` rows, gate evaluations, audit events); every A42 AML table (alerts, cases, `aml_case_note`, RFIs, restrictions, filings), which are AML/CTF records kept seven years (G14) and are never scanned or redacted, and are byte-identical before and after erasure (a hidden test); and the trustee's register (A18's entries, versions and stored CSVs), which is the trustee's or RE's legal record under s169, not RealX's.
  - **Redaction list (data in the frozen spec):** included: A44 `ticket_message` bodies (through A44.n only) and this module's own free-text fields. Excluded, never touched: every A42 table, A44 `complaint` and `complaint_event`, A14 approval and decision reason fields, A10 audit rows, A48 halt and wind-down reasons. A table not on the list is excluded by default; adding one is a spec change.
- **Replay after a restore.** For each ledger line whose erasure id the restored database does not show as `completed`, the restore runs steps 2 and 3 of the effector again, idempotently, before the API or worker start (section 3). If the ledger's seal id is missing from the restored database (the set predates the erasure), the seal is rebuilt from the restored rows with the same seal id and pseudonym, and its `subset_mac` is checked against the ledger line; a match lets check 9 pass; a mismatch fails check 9 with `seal_subset_mismatch`, the destination stays in `RESTORE_MODE`, the person is still pseudonymised (in replay a `subset_mac` mismatch does not abort step 2; the walk runs regardless), and a human decides from the runbook. If the seal exists, it is not rebuilt. Step 1 is not replayed against shared external systems under `RESTORE_MODE`; its outcome in the destination is asserted from the restored rows (no active token, mandate, passkey or session for the subject), and on-chain session-key state is read from the shared chain.
- The wallet-to-person link is **sealed**, not destroyed: `smart_account`, `onchain_identity` and every holding still point at the principal id, which now leads only to the pseudonym; the link back to a person exists only inside the seal. `POST /v1/privacy/seals/{id}/unseal-requests` is an A14 request `privacy.seal.unseal` under `6E` (LEGL maker, CCO and MLRO checkers) that must carry a reason code (`COURT_ORDER`, `REGULATOR_NOTICE`, `AML_INVESTIGATION`, `LAW_ENFORCEMENT`) and the notice's document hash; the effector returns a 15-minute unseal grant for the named fields to a human session only (`requiresHuman` on the read), writes `privacy.seal.unsealed`, and never restores the record. ## Node-specific challenges (node QA)

- **The restore brings the erased back (privacy, security).** Take a set; erase an investor (closed account, approved by a second person); then restore the set into a fresh project with no PITR (the erasure is not in the restored database). Before the destination's `api` or `worker` container starts (the node QA checks that neither bound a port or ran a job before check 9 passed), the erasure-ledger replay must pseudonymise the person again and rebuild the seal with the ledger's seal id and pseudonym; a search by name, email, phone, DOB, licence number, TFN and bank account across every search endpoint (A30 directory, A44 Investor 360 search, A66 global search, support tickets) and every blind-index table returns nothing; the restored stack stays behind `restore_hold` until the check passes. After release, the seal is unsealed through a `6E` request and its content's `subset_mac` equals the ledger line's (the statutory subset survived). Separately, change the person's address in the source between the set and the erasure: the replay must still pseudonymise, and check 9 must fail with `seal_subset_mismatch` and keep the hold. A restore that opens with the person findable, or that loses the statutory subset silently, fails the node.
- **The restored stack that reaches out (isolation, money-adjacent).** During a full drill whose source has a scheduled distribution due, pending outbox rows, an open custody op, queued A46 webhook deliveries and a planted A20 break, count at the Hardhat node (transactions and UserOps from any address or signer the destination holds), at the bank sandbox (write requests from the destination network) and at a webhook sink: every count must be zero, no halt appears on the chain's HaltModule, and the `isolation.ts` self-test must have passed. Then inspect every compose file and override: only `backup-runner` mounts the Docker socket; exec into `api` and `worker` and confirm there is no Docker socket, context or CLI access.
- **Crash inside an erasure (privacy, audit).** Kill the worker after step 0, after step 1 and after step 2 of three separate erasures, and once in the middle of step 2's transaction. Each resumes to `completed` with one ledger line, one seal, one `privacy.erasure.completed` and no half-pseudonymised subject; A29's session-key revocation is confirmed on-chain before `completed`; A42's AML rows (alerts, cases, `aml_case_note`, RFIs, restrictions, filings), complaint and `complaint_event` rows and approval reason fields are byte-identical before and after.
- **Who is erased (privacy).** For each subject-scope fixture (closed foreign individual, joint account with one requesting holder while open and after closure, company with a departing director, closed SMSF, departed staff user, an assisted request after offboarding), exactly the rows in the subject-scope table change: the other joint holder, the entity's own data and the other director are untouched, and a request for an open joint account waits with `joint_account_open`.
- **The keystore that cannot open itself (security, money-adjacent).** Rotate a tenant data key at 02:00, after the nightly set, with `backup.keystore_on_change` disabled, write a new investor, then lose the source and restore. The drill's key-coverage check must fail with `RESTORE_CHECK_FAILED: key_coverage` naming the missing key ref, not pass with unreadable rows; with the hook enabled, the keystore-only set must exist within one job cycle and the drill must pass. Separately, remove `BACKUP_ESCROW_KEY_FILE`: `backup:restore` must stop with `BACKUP_ESCROW_KEY_MISSING` before touching any volume.
- **A tampered or replayed set (security).** Flip one byte in the base-backup ciphertext, re-sign a manifest with a key other than `backup-attest`, rename last week's set as today's, and delete one WAL segment in the middle of the PITR span. Each must be refused before any data is written (`BACKUP_MANIFEST_INVALID`, `BACKUP_CHAIN_BROKEN`, or a PITR stop that reports the exact last LSN reached and fails the "head appears in the source chain" check), never silently restored to a different point.
- **Evidence that lies (money, audit).** In the destination project, after restore and before the checks, change one ledger entry's amount by 1 cent through the migrator role, and separately replace a stored register CSV's bytes under the same object id. The ledger-totals check and the register re-hash check must each fail by name with expected and actual values; A10's verifier must fail on a mutated audit row. A drill that reports `passed` over any of these fails the node.
- **Deletes inside the window (compliance).** With the injectable clock at 6 years 364 days after a document version's `effective_to`, run the sweep, call the sweep executor directly with a hand-picked id list (it must still go through `retention.check`), edit `trust_retention.retention_until` to yesterday for a wound-down vehicle (the sweep must ignore the column and follow `retentionHold()`), set a `keep` class to `purge` in a scratch policy row without the A04 grant (the delete must be refused by privilege and harvested), and run `DELETE` as `realx_app`, `realx_worker`, `realx_readonly` and `realx_retention` in psql; place a court-order hold on a 7-year-and-1-day-old approval and repeat. Every attempt is refused, the sweep and direct-call refusals are audited at once and the raw SQL ones within one harvest cycle, each with role, table and reason; at 7 years and 1 day with no hold only the sweep deletes, in batches, with `retention.purged`. A one-row gap between the reference `isDeletable` and the sweep over 10,000 random triples fails.
- **Tipping-off through a privacy request (G14).** Two closed investors request erasure at the same instant; one has an open AML case and an unfiled SMR. Inside the response period, every investor-facing response, notification, status code and expected date must be byte-equal after id substitution, and the p95 latency difference at most 20 ms over at least 200 samples per case; the completion notice for the other must list "anti-money laundering records" exactly as the first will; SUPP sees `in_progress` for both; the deferral reason is readable by the MLRO and CCO only. Then run the clock to 90 days with a third investor deferred by an open complaint and a fourth by a legal hold: at the end of the period the AML-deferred, complaint-deferred and hold-deferred requests all show `could_not_complete` with the same generic notice, the same kept-records list and the same latency bound, and the breach alert reaches LEGL only with no reason in its payload. Any difference fails the node.
- **Agent misuse (D04, G13).** An investor's agent calls `POST /v1/me/privacy/erasure-requests` and `/withdraw`; LEGL's agent drafts `privacy.erasure.approve` and then tries to approve it, and tries to approve one drafted by another LEGL; an ENGO agent calls `POST /v1/ops/restore-drills` with an extra `project` field equal to the running project (and separately with a valid `set_id` only) and tries to run `backup:restore` or `backup:release` through any route; a TP-AUD token asks for an export naming investors with `fields_requested = [name, address]` and then downloads a PII-bearing export created by a human. - **The chain and the money after erasure (audit, money).** Erase an investor who held units in two vehicles and received three distributions before closing. - **Design fidelity of the data contract.** Every event of this node renders as an `adAudit` row (Time, Actor, Action, Object, Approval, Result) with a tone in {green, amber, red} and no unknown status string; the ADM-32 jobs table shows the three jobs with last run and state; the public privacy policy's kept-records wording equals the fixed list.
