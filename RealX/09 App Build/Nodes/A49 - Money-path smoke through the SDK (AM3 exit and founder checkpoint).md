# A49 - Money-path smoke through the SDK (AM3 exit and founder checkpoint)

**One `money` compose profile over A23's stack and one Vitest suite that drives the whole P1 money path through `packages/sdk` with no UI: a seeded investor is onboarded to approved with claims issued, pays in through the sandbox bank, places one order under a passkey session and signed orders under an agent mandate, the offer closes at its hard cap, allocation is locked with one scaled-back line and one excluded line, escrow is released, the trustee's register entry lands first, a registry drift planted between the register entry and the mint pauses the mint until a clean re-run, the mint runs on the local chain under a 6E+Q approval and a 2-of-3 custody quorum, a targeted reconciliation comes back clean, a soft-cap failure refunds every cent, distribution runs go from draft to closed with withholding lines and a rounding leg, withdrawals below and above the threshold settle, and a post-mint drift halts KST01 alone and clears only on a clean re-run; journeys J04, J05, J06 and J15 at service level, with a one-page "magic inputs" guide so the founder can watch money and units move on the sandbox panels and a plain watch page. Its pass, together with every other AM3 node passed, is the AM3 exit and the founder's first checkpoint; the founder's feedback becomes fix items on the nodes that own each behaviour, never patches here.**

## Build brief

This node writes no product behaviour and no product screen. It owns a compose overlay, a test suite, an evidence writer, a developer watch page and a guide. Every call it makes goes through `packages/sdk` (A09) against the running `api` container; nothing in `e2e/money-smoke/` imports from `services/*`, `packages/db` or any adapter, and a lint in the suite fails if it does. Human actions (passkey sign-in, staff hardware-key approvals, custody signer approvals) are performed through A11's local simulated authenticator (`/__test/*`, mounted only in `RUN_MODE=local|test`) and A15's console-action signing path, so the suite exercises the same routes a person would, with the same gates.

**Compose profile (`<workspace>\app\infra\money-preview\`)**
- `compose.money.yml` is an overlay on A23's `infra/stack/compose.yml` (`include:`, never a copy) that adds two services: `money-watch` (below) and, under the `runner` profile, `money-smoke` (a `node:24` container that runs the Vitest suite against `api` and writes evidence to the `realx_state` volume). It changes no A23 service, port, image or environment value; every `ADAPTER_*` stays `sandbox`, `RUN_MODE` stays `local`, `CHAIN_ID` stays 31337, and A23's static no-live test is extended to scan this folder too.
- Commands under A01's script-registration convention: `money:up` (= `stack:up` then `money-watch` healthy), `money:smoke [--seed <string>] [--keep]` (runs the suite from the host against the stack; `--keep` leaves the resulting state for the founder to look at instead of resetting), `money:walkthrough` (the same suite with `--pause`: it stops before each checkpoint, prints what to look at on which panel and which magic input was just used, and waits for Enter), `money:down`, `money:evidence` (rebuilds `app/evidence/A49.json` from the last run's state), and `verify:money` (= `stack:reset`, `money:up`, `money:smoke` three times with three different `--seed` strings, `money:down`; needs Docker Desktop and is what the gauntlet runs). `npm run verify` stays Docker-free and runs only this node's static checks (lint of imports, schema of the checkpoint table and of `expected-events.ts`, guide link check).
- `money-watch` (`infra/money-preview/watch/`): a small Node service serving one plain HTML page that polls four read models through `packages/sdk` and renders them as plain tables with a 5-second refresh: (1) the reconciliation grid per vehicle from A20's latest run (Trust, Register units, Token supply, Client money, Last run, Status, open breaks, halt flag), which is the `adRecon` grid as data; (2) A16's client-money summary per account and the bank sandbox's virtual-account totals side by side with the delta; (3) the offering and order states for the vehicles the smoke touches (SM-04 and SM-05 state per row); (4) the run states and line totals of any distribution run in flight (SM-08). It carries the fixed banner "RealX developer sandbox, not a product screen", uses no font, colour token or component from `packages/ui`, masks every PII field exactly as the API returns it (it has no unmask permission), and exists only in `RUN_MODE=local|test`. It is a developer tool for the founder's checkpoint; the product's transparency page (PUB-08) and the console's ADM-17 are built by their own nodes from the same read models.
- **The watch page's token.** `money:up` creates it through A12's normal route, never a back door: a **read-only** staff token (scopes limited to the four read models' read cells; no write family) owned by the seeded staff principal whose own A11 role holds those read cells (the builder records which role; evidence names it). Under A12 a read-only staff token activates on its requester's own hardware-attested assertion (through the simulated authenticator), so no second approver is needed; a write scope on it would move it to `pending_owner_approval` and the start-up fails with `MONEY_WATCH_TOKEN_NOT_READ_ONLY` rather than widening. The secret is shown once to `money:up`, which writes it to a Docker secret file mounted read-only at `/run/secrets/money_watch_token` on a `tmpfs` in `money-watch` only; it is never an environment variable, never in `realx_state`, never logged, never in evidence (evidence records only its prefix and token id). `money:down` revokes it. The C9 scan covers its full secret and its prefix pattern.

## Human gates touched

- **Founder checkpoint (a review, not a licence or money gate).** After A49's gate passes and every AM3 node's `status.json` entry is `passed`, the founder runs `npm run money:walkthrough` with the guide, or watches the builder run it, and notes what looks wrong or missing. Every note becomes a `founderFeedback[]` item in `app/evidence/A49.json` with an owning node, and the orchestrator opens a fix loop on that node (for example A37.1, A39.1, A40.1); this node is re-run afterwards as the check that the fix holds. AM3 is recorded closed when A49's gate has passed, every AM3 node's `status.json` entry is `passed`, and the checkpoint has been held, even if the feedback list is empty.
- **HG-CAPITAL / HG-VENDOR / HG-KEYS / HG-PROD / HG-AUDIT:** not crossed. Every cent is sandbox money, every key is a no-value key in a Docker volume or test memory, every signature is A15's console-action path, and the chain is the local Hardhat network; the overlay is tested to refuse any live selector, mainnet chain id or production run mode exactly as A23 does. The evidence records these gates as open.
- **HG-LEGAL:** no new counsel question is raised here; the questions the owning nodes carry (whether an order or withdrawal under a standing mandate, and standing disclosure consent, can stand in for a personal declaration; the wholesale-track escrow settlement mechanics; whether refunds may go to the wallet rather than the bank; the float-interest policy; the withholding treatment for each profile) are inherited and listed in the guide's "what this does not decide" paragraph so the founder does not read the smoke as a legal conclusion.
