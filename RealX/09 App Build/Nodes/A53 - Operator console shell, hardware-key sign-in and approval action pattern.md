# A53 - Operator console shell, hardware-key sign-in and approval action pattern

**`apps/console` on its own origin: the dark AdminSidebar with the seven extended groups and live badges, the staff user card, the PROD / SANDBOX badge and the network pill, global search, the audited "view as tenant" switcher, hardware-key sign-in (ADM-36), the shared "approve with hardware key" modal that shows the server's payload hash and custody binding and signs a server-derived challenge, the maker-checker action pattern every module screen reuses (draft, precheck, submit, diff, simulation, evidence), the break-glass button for CCO, SECO and the on-call ENGO, server-paged table and filter primitives with loading, empty and error states, and the "agent on behalf of" marker as one shared cell, so that the console nodes that follow add screens, never plumbing.**

No money, supply or holdings move here, and every rule it renders is decided by A11 and A14. The node QA writes hidden tests and Challenge fixtures to `<workspace>\gauntlet\hidden\A53\` before the build starts ([[App Gauntlet]] §2): Playwright specs against the running stack with the sandbox authenticator, its own crops of the `AdminSidebar` and `adApprovals` regions of the prototype and of the ADM-36, `KeyConfirmModal` and seven-group sidebar frames of extension B, a forged-assertion fixture, a tampered-cursor fixture, the production-bundle grep list and a scripted "maker approves own request" persona set. This node draws the shell and the shared patterns only. It contains no business rule: eligibility, segregation of duties, policy resolution, hashing and the WebAuthn verification all happen in the API (A11, A14). The console's job is to show what the API decided and never to let a person believe an action is done before the API says so. This note is not legal advice.

## Build brief

**0. Requested from upstream (entry condition for Specify)**

The shell reads routes and fields that no dependency defines yet. Each item below is an additive follow-up loop in the owning module (routes and schemas there, never code in this node), each with `x-realx-scope` so it is in the OpenAPI document, `packages/sdk` and A104's MCP catalogue from the moment it passes. A53's Specify step does not start until all of them have passed; the node waits rather than mocking an API in production code (fixtures exist only in tests). If one cannot land, the UI that needs it is removed from this node and recorded in `evidence/A53.json`, never faked.

- **One signing contract for staff decisions (A11 and A14, loops A11.2 and A14.1).** Today A11 §8 says `decide`, `ratify`, `veto` and `bulk-decide` take the raw assertion in "inline mode" (challenge equals `payload_sha256`; bulk challenge is `sha256` of the sorted hash list), while A14's "Decision binding" and "Bulk approve" say A14 calls A11's nonce-mode `fresh-assertion/options` over `decision_digest = sha256(approval_id || payload_sha256 || verdict)` (bulk: over `verdict` and the sorted `(approval_id, payload_sha256)` pairs). The builder cannot satisfy both. The contract this node is written against, and which both upstream specs must carry before Specify:
  - `POST /v1/auth/fresh-assertion/options` takes a subject, never a hash: `{purpose: approval_decide | approval_ratify | approval_veto, approval_id, verdict}`, `{purpose: approval_bulk_decide, approval_ids[], verdict}`, `{purpose: breakglass_activate, break_glass_id}`, or, for A12's token issuance and A11's role grants, the subject body those routes name. The server looks up the canonical hash itself (A14's `decision_digest`, or the bulk digest, or the break-glass request hash) and returns the challenge `sha256(server_nonce || digest || purpose)`. Any client-supplied `payload_sha256` field is refused `400 VALIDATION_FAILED` by the schema.
  - `POST /v1/auth/fresh-assertion/verify` verifies the WebAuthn response, keeps the raw assertion on the `fresh_assertion` row (A14's decision row copies it, as its check constraint requires) and returns `fresh_assertion_id`.
  - `decide`, `ratify`, `veto` and `bulk-decide` take `{verdict, fresh_assertion_id, acknowledged_warnings[], reason_code?, note?}`; A14 verifies it through A11's `requireFreshAssertion`, recomputing the digest from the request's current state, and refuses a missing or consumed id with `FRESH_ASSERTION_REQUIRED` or `APR_ASSERTION_INVALID`, a stale one with `FRESH_ASSERTION_STALE`, and a digest that no longer matches (payload edited, other id, other verdict) with `FRESH_ASSERTION_MISMATCH` or `APR_CHALLENGE_MISMATCH`.
  If the plan instead pins A11's inline mode, §4 changes to post the raw assertion and the hash-tamper challenge's accepted codes change with it; the orchestrator decides, and this note is re-frozen.
- **A11 (loop A11.2, before AM4; separate from the IAM admin API node A106, which was A67's working id A11.1):**
  - `POST /v1/iam/view-as-tenant/{grant_id}/extend` (refused `VIEW_AS_NOT_ALLOWED` on a second extension) and `POST /v1/iam/view-as-tenant/{grant_id}/end`.
  - `GET /v1/iam/me` gains `view_as {grant_id, tenant_id, tenant_name, reason, expires_at, extended}`, `break_glass {id, runbook, state, expires_at, activations[], review_due}` (null when none) and `on_call_engo` (boolean, true only inside the `on_call` window).
  - `GET /v1/iam/break-glass/{id}` and `GET /v1/iam/break-glass?state=pending` (requester, runbook, reason, requested duration, which holders have activated), moved forward from A67's IAM admin API draft (now node A106) so the pending state and the holders' activation list work at AM4; A67's A11.1 then keeps only the log, review and view-as grant routes.
  - The staff relying-party id as configuration: `CONSOLE_RP_ID` in `packages/config` (the console host, `console.localhost` locally), replacing the label `console`, which is not a registrable suffix of any origin.
  - A session bound to its surface: each session row records `surface` (`web` or `console`) from the origin it was created on, and a session cookie presented on the other surface is treated as absent (`401 SESSION_EXPIRED`).
- **A14 (loop A14.1):** `GET /v1/approvals/summary` returning `{checker_pending, maker_open, awaiting_ratification}` for the caller (the inbox badge; list routes return no totals); and on `GET /v1/approvals/{id}` a `custody` block `{vault: V1..V7 | null, signing_condition, op_state}` read from the policy row's `custody_vault` and `custody_ops`, and `file_sha256` where the payload binds a file (distribution runs, allocation files, refund batches), so the modal can show what signs, on what condition, and which file the decision binds.
- **A09 (added to its pending A09.1 loop):** `/v1/meta` gains `adapters[] {name, environment: sandbox | live}` (staff-readable, no hosts or secrets), so the environment badge does not need the staff-only `/internal/health/adapters` route. `/v1/meta` already returns run mode and chain id.
- **A33 (loop A33.1):** `GET /v1/admin/tenants` (cursor, filters `state`, `q`; fields `id`, `name`, `short_name`, `state`) for the view-as dialog. A69 reuses it.

**1. The app and its origin (`apps/console`, Next.js 15 App Router, React 19)**

- Root files: `package.json`, `tsconfig.json`, `next.config.ts`, `middleware.ts`, `eslint.config.js`, `Dockerfile` (multi-stage, Node 24, non-root), `.env.example` generated from A08's config schema, `compose.console.yml` included by `infra/` (A53 never edits `infra/`), `README.md`. The console runs on its own origin (`CONSOLE_ORIGIN`, default `http://console.localhost:3001` in compose; the web app stays on `http://localhost:3000`) so cookies, passkeys and bundles are never shared with `apps/web` (architecture brief §1.1). A startup check refuses to boot if `CONSOLE_ORIGIN` equals `WEB_ORIGIN`, or if `CONSOLE_RP_ID` is not the host of `CONSOLE_ORIGIN` or a registrable suffix of it.
- **Same-origin API proxy.** `next.config.ts` rewrites `/api/*` to the API service (`API_INTERNAL_URL`, the compose service name), preserving `X-Forwarded-Host` and `X-Forwarded-Proto`. The browser only ever talks to the console origin, so A11's `__Host-` cookies are host-only on the console origin with `SameSite=Strict`, A11's CSRF check sees the console origin in `Origin`, and `connect-src` is `'self'`. The SDK (`RealXClient` with cookie auth) is constructed with base URL `/api`. The API resolves the surface from the forwarded host and binds each session to it (§0), so a web session cookie never authenticates on the console and the reverse. WebAuthn ceremonies run with `rpId = CONSOLE_RP_ID` read from `packages/config`.
- `app/layout.tsx` loads `@realx/ui/tokens.css`, the vendored Newsreader, Geist and Geist Mono from `packages/ui/fonts/` (no Google Fonts request), sets `<html lang="en-AU">`, a nonce-based strict Content-Security-Policy with no inline scripts (`script-src 'self' 'nonce-…'`, `connect-src 'self'`, `frame-ancestors 'none'`), `Referrer-Policy: no-referrer`, and the providers (query client, toast region). It does **not** mount the shell: a server root layout cannot tell which route group is rendering. Instead, **every feature route group's own `layout.tsx` renders `ConsoleShell` from `src/shell/index.ts`** (a documented contract for A66-A77, A92, A93 and A96, checked by a test that walks `app/` and fails for any group other than `(auth)` whose `layout.tsx` does not render `ConsoleShell`). The `(auth)` group's layout renders the bare sign-in frame. All data reads go through `packages/sdk`; no `fetch` outside the SDK (lint rule in the app's `eslint.config.js`).
- Route conventions for the console nodes that follow: every page under a feature route group exports `screen` (a `ScreenCode` from A02's `packages/domain/screens.ts`) and `designKey` (the prototype key or the `design-ext:ADM-xx` anchor from A51's `screens.json`); the shell reads them for the page header's mono code eyebrow (the prototype's `ADM-30` line), the document title and the e2e fidelity step. Route groups reserved for later nodes and not created here, as the graph's owned paths assign them: `(overview)` A66, `(access)` A67, `(investors)` A68, `(platform)` A69, `(assets)` A70, `(offerings)` A71, `(token)` A72, `(register)` A73, `(money)` A74, `(risk)` A75, `(reporting)` A76, `(agent-access)` A77, `(market)` A92, `(governance)` A93, `(travel-rule)` A96. A53 owns only the root files, `app/layout.tsx`, `app/(auth)/` and `src/shell/`.
- `middleware.ts` sends any request without a console session cookie to `/sign-in?return=<path>`; the return path must be a same-origin relative path (an absolute URL, a `//` prefix or a backslash variant is dropped). The middleware checks presence only; the API is the authority and every SDK call still carries the cookie.
- No role or persona switcher exists in any build or `RUN_MODE` (D20). Every staff member, seeded or invited, enters through ADM-36 with their own hardware-attested passkey, and sees the sidebar that `GET /v1/iam/me` grants. Automated runs sign in the same way: Playwright opens ADM-36 and answers the ceremony with a virtual authenticator attached to that persona's browser context, loaded with the persona's sandbox passkey (allow-listed AAGUID) from A06's gitignored `credentials.json`, with one browser context per staff person, never shared. The seeded staff personas (Jordan Blake CCO, Priya N. TRSY, Tom H. CAPM, Grace L. REGO, Sam R. RISK, plus the KYCA, MLRO, CFO, CEO, TOKO, SECO, SUPER, LEGL and on-call ENGO personas A06 seeds for maker-checker tests) are test identities, not a menu. A test asserts that no console bundle contains `DevRoleSwitcher`, a role-switcher component or a persona name. The prototype's own "view as" bar is never built.

**2. ADM-36 sign-in and 2FA (`app/(auth)/sign-in`, `app/(auth)/signed-out`, `app/(auth)/locked`)**

- The frame is extension B's `SignInCard`: the onboarding card (14 px radius, 36 px padding, centred, `max-width 480px`) on cream with the `Logo` and `ADMIN` tag, the "RealX operator console" eyebrow and a DropBox prompt "Sign in with your security key"; no sidebar. Step one asks for the staff email (an identifier hint only); step two runs A11's discoverable-credential ceremony (`POST /v1/auth/passkeys/login/options`, then `navigator.credentials.get` with `rpId = CONSOLE_RP_ID` and `userVerification: required`, then `POST /v1/auth/passkeys/login/verify`). The "2FA" the product map names is met by the hardware key itself (possession) plus its user verification (PIN or biometric) and A11's AAGUID allow-list; there is no password, SMS or TOTP field anywhere, and a test greps the app for `type="password"` and `otp`.
- First sign-in after an invitation (A67 grants the role) registers the hardware-attested passkey on the same card (`POST /v1/auth/passkeys/register/options` with attestation `direct`, then `/v1/auth/passkeys/register/verify`); a software authenticator is refused by the API and the card shows extension B's `attestation-required` state ("A hardware-backed key is required for staff") for `ATTESTATION_REQUIRED` and `AAGUID_NOT_ALLOWED`.
- Every A11 error code has a sentence and a next step on the card, using extension B's drawn states where they exist: `SESSION_EXPIRED` (return path kept), `DEVICE_MISMATCH` (sign in again on this device), `ACCOUNT_DORMANT` (the `/locked` page with the dormant copy "Locked after 30 days without sign-in · ask SECO"), `RATE_LIMITED` (shows `Retry-After`), `PASSKEY_WRONG_PURPOSE`, and `FORBIDDEN` for a non-staff principal (an investor or sponsor passkey presented to the console origin cannot verify because the relying-party id differs; if a principal without any staff role ever verifies, the card shows "No console access" and deletes the session). Failures never say whether the account exists.
- Session behaviour rendered by the shell: A11's staff idle timeout of 15 min triggers a two-minute warning banner at 13 min with "Stay signed in" (one SDK ping) and a hard redirect to sign-in on `401 SESSION_EXPIRED`; the 8 h absolute limit is shown in the user card's tooltip; "Sign out" calls `DELETE /v1/auth/sessions/{current id}` and lands on `/signed-out`. The user card menu lists the person's sessions from `GET /v1/auth/sessions` with "Sign out other devices" (`DELETE /v1/auth/sessions`).

**4. The "approve with hardware key" modal (`src/shell/hardware-key/`)**

- `HardwareKeyConfirm` is the React build of extension B's `KeyConfirmModal` and the one component through which any staff decision reaches A14: approve, reject, veto, act and ratify (`SGL+R`), bulk-decide, break-glass activation, and the fresh assertions that A12's staff-token issuance and A11's role grants need (purpose is a prop). The design's plain Approve / Reject buttons on `adApprovals` are slots on A05's `ApprovalDetail`; this node fills them with buttons that open the modal, so no console screen can call a decision without it (a lint rule forbids importing the SDK's `approvals.decide`, `approvals.bulkDecide`, `approvals.ratify`, `approvals.veto` and `auth.freshAssertion` operations outside `src/shell/hardware-key/`).
- The modal renders A51's frame (white card, 14 px radius, 1 px `#E3DED4`, 28 px padding over the `rgba(23,25,28,.25)` scrim; Newsreader 28 "Confirm with your security key") with a `KeyValueList` of action, object (exactly one `object_ref` per id), approval id (mono), policy code pill (4E, 4E+Q, 6E, 6E+Q, SGL+R, AUTO), the `payload_sha256` from the server's `GET /v1/approvals/{id}` (Geist Mono through the one truncation rule `truncateAddress`, copy affordance, full hash on hover), impact line, TTL ("expires in 71 h") and timelock; the checker's name and role; and a **custody binding** group read from the detail's `custody` block and `file_sha256` (§0): the vault that signs (V1 owner 3-of-5, V2 token agent 2-of-3, V3 pauser, and so on, or "No custody signature" when null), its signing condition in one line ("V2 signs 2-of-3 after this approval, bound to approval {id}"), the custody op state (`none`, `queued_for_custody`, `signed`, …), and, where the payload binds a file, the file hash in Geist Mono with "Approval is bound to this file" (product map ADM-30 "Custody binding", J06 step 4 "bound to the file hash"). For the `+Q` codes the line "Approval ID is bound to the signing request" stays. Below: the diff against the last approved payload of the same object; the precheck results as `GateRow`s; every `warn` code as an `AcknowledgeCard` that must be ticked (sent as `acknowledged_warnings[]`); the evidence as `DocumentRow`s; and the SoD note the API returns. If A51's frame lacks a row for the custody group, the builder composes it from A05's `KeyValueList` and records a DF finding for A51.
- **States: six plus ratify (seven), plus the bulk variant.** All are implemented and each is reachable in the kitchen-sink route: `waiting` ("Touch your security key"), `verified` ("Decision recorded · sent to signing"), `failed` ("Key not recognised · try again or use your backup key"), `attestation-required`, `not-eligible` (the API says the caller is in the maker identity set or has decided: Approve and Reject absent, only Close, with the API's sentence), `agent` (the API's detail reports `APR_CHECKER_MUST_BE_HUMAN` for the caller: the button is absent and the grey banner reads "Agents prepare. A person approves."), the seventh, `ratify`, for `SGL+R` ("This acts at once. {Role} must ratify within 2 h" with the mono countdown, then the amber "Awaiting ratification · h:mm:ss" pill on the originating row), and the bulk variant on ADM-30 (the sorted id list with each id's hash and policy code). The client adds no eligibility rule of its own; it renders the detail endpoint's answer.
- **Signing (the §0 contract).** The modal calls `POST /v1/auth/fresh-assertion/options` with the subject only (`{purpose, approval_id, verdict}`; for bulk `{purpose: approval_bulk_decide, approval_ids[], verdict}`; for break-glass `{purpose: breakglass_activate, break_glass_id}`; for A12 and A11 purposes the subject body the calling feature passes as an opaque prop). The server derives the challenge from its own canonical hash. The modal runs `navigator.credentials.get` against the staff hardware key with the returned challenge and `rpId = CONSOLE_RP_ID`, posts the response to `POST /v1/auth/fresh-assertion/verify`, and then calls `POST /v1/approvals/{id}/decide` (or `/ratify`, `/veto`) with `{verdict, fresh_assertion_id, acknowledged_warnings[]}` and, for reject or veto, the mandatory reason code from the domain's reason-code list plus a free-text note in the console `TextArea` (§8, min-height 140 px). The client never computes, edits or sends a hash; it only displays the server's. **5. The maker-checker action pattern (`src/shell/privileged-action/`)**

- `PrivilegedActionFlow` plus the hook `usePrivilegedAction(action_code)` give every module screen the same five-step pattern over A14's API: **Draft** (the feature node supplies the form fields and the object reference; the flow calls `POST /v1/approvals` and shows the resolved policy code, checker role sets, TTL preview and the non-binding precheck preview; edits re-post and the hash changes visibly), **Precheck** (the binding results after `POST /v1/approvals/{id}/submit` as `GateRow`s with the rule-pack version and `GateEvaluation` ids; a hard `fail` shows the reason codes and a "Draft again" button, because A14 has moved the request to `rejected`), **Submit** (the `APR-<yyyymmdd>-<base32>` id, the required checkers with their status, "Submitted by you" or the `AgentMarker`), **Diff and simulation** (the payload diff against the last approved payload and the simulation the checkers will see, plus the same custody binding group as the modal (vault, signing condition, file hash), read from the same detail endpoint so maker and checker see one thing), **Evidence** (attach document ids from A35's library, listed through `GET /v1/documents` with `scope` and `type` filters; the flow never uploads files itself). Where a screen shows several people in sequence, the flow renders extension B's `ApprovalsChain` from the detail's decisions.
- A status card then follows SM-00 from the API: `draft`, `submitted`, `prechecked`, `approved`, `queued` (timelock countdown and the veto slot for eligible checkers), `queued_for_custody`, `signed`, `broadcast`, `confirmed` (worded "confirmed · register sync and reconciliation pending", never as done), `reconciled`, `closed`, `rejected`, `expired`, `cancelled`, `failed`, each with its tone from A05's `toneFor`. Cancel is offered only where A14's table allows it and veto only in `queued`, and both only when the detail endpoint lists them as allowed for the caller.
- Idempotency is automatic: the SDK sets an `Idempotency-Key` per mutation and the flow reuses the same key on a retry of the same draft, so a double-click or a flaky network cannot create two requests; a `409 IDEMPOTENCY_IN_PROGRESS` shows "Still submitting" and polls after `Retry-After`; a `422 IDEMPOTENCY_KEY_REUSED` (same key, different body) shows "This draft changed while it was being sent · review and send again" and mints a new key only after the person confirms.
- The flow is the only way a console screen creates or submits an `ApprovalRequest`: the same lint rule as §4 forbids `approvals.create` and `approvals.submit` outside `src/shell/privileged-action/`.

## Node-specific challenges (node QA)

- **The hash the client shows is not the hash it signs (security, G13).** The node QA intercepts the detail response and changes `payload_sha256` in the modal's props, and separately injects a `payload_sha256` field into the `fresh-assertion/options` body, then approves: the injected field must be refused `400 VALIDATION_FAILED`, and the decision must bind to the request's own server-side digest whatever the modal displayed (the recorded `decision_digest` equals the one A14 computes). It then edits the amount in a draft after the checker opened the modal and approves with the assertion already obtained: the decision must be refused with `FRESH_ASSERTION_MISMATCH` or `APR_CHALLENGE_MISMATCH`, a forged or already-consumed assertion id with `FRESH_ASSERTION_REQUIRED` or `APR_ASSERTION_INVALID`, and the modal must render the code and reload the new hash and diff. Any 2xx that binds a hash other than the request's current one fails the node.
- **The maker approves through the front door (compliance, G13 and agent misuse).** Priya N., whose agent `treasury-drafter` drafted APR-2291, signs in on a second device and opens the request by URL; then Jordan Blake is granted CFO mid-flight and approves a request drafted before the grant; then a CCO under an active break-glass session approves a request she herself drafted. Each must show the `not-eligible` state with the API's SoD note and no Approve button, and a forced call through the modal must render `APR_MAKER_IS_CHECKER` or `APR_ROLE_NOT_HELD`.
