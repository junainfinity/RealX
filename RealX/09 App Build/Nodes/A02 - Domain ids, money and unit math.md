# A02 - Domain ids, money and unit math

**Pure TypeScript domain package: branded ids, integer-cent money with en-AU formatting, whole units, basis points, the rounding rules, fee, budget, distribution-split, holder-cap, price-band, valuation and withholding arithmetic, and the canonical screen table generated from the charter as code.**

**Build status:** not started. **Milestone:** AM0 (Foundations). **Lane:** Domain core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 6-10 agent-hours (build, challenge and verify loops).

**Depends on:** [[A01 - Repo scaffold, toolchain and verify command]]
**Unlocks:** [[A03 - State machines, gate codes, approval codes and permission matrix as data]], [[A04 - Database schema, migrations and row-level security]], [[A08 - Sandbox adapter framework, config and phase flags]], [[A16 - Client-money ledger (double entry)]], [[A18 - Unit register (legal record) and registry sandbox adapter]]

A02 reads A00's charter files (`docs\charter\screens.json`, `ids.json`) as frozen inputs. It reaches A00 only through A01 in the graph (A00 → A01 → A02); an explicit A00 → A02 edge is a graph change for the plan owner, not something this node adds.

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A02\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The oracle scope is the money, unit, fee, budget, distribution-split, scale-back, cap, band, valuation and withholding functions, checked with fixed vectors and fast-check property tests, plus the id grammar and the `screens.ts` regeneration check.

This node is not legal or tax advice. Every rate, cap and threshold below is a parameter with a default; the rule packs (A03 and later) own the live values, and the arithmetic conventions that need a legal or tax answer are recorded as HG-LEGAL questions rather than decided silently (see "Human gates touched").

## Build brief

Everything in `src/**` is pure: no I/O, no database, no clock, no randomness of its own, no runtime dependencies. `packages/domain` (`@realx/domain`) compiles to ESM with `sideEffects: false`, is imported by every other workspace, and is the only place money arithmetic is allowed to live. The generator scripts in `packages/domain/scripts/` are build-time tools, not package code, and may read files; they are excluded from the purity rules and never imported by `src/`.

**Money lint inside the package.** A01's `no-float-money` rule exempts `packages/domain`, and A01's `eslint .` uses only the root flat config, so a nested config would never run. This node therefore ships its own rules and registers its own verify step through A01's script registration:
- `packages/domain/eslint-rules/no-domain-float.js` (type-aware) applies to all of `packages/domain/src/**` except test files: it forbids `parseFloat`, `.toFixed(`, `Number(...)`, `Math.round`, `Math.floor`, `Math.ceil`, float literals and any `number`-typed value flowing into or out of a `Cents`, `Units` or `Bp` value. Outside `src/money/` it also forbids the `*`, `/`, `%`, `+` and `-` operators on values typed `Cents`, `Units` or `Bp` (callers use the named functions). Because it covers `src/**` and not a list of folders, it also covers the folders A03, A12, A20 and later nodes add (`state-machines`, `permissions`, `codes`, `agent-authority`, `recon`).
- `packages/domain/eslint-rules/no-magic-rate-literals.js` applies to `src/money/**` except `src/money/constants.ts`, `src/money/defaults.ts` and tests: any numeric or bigint literal whose value is not 0 or 1 fails, whatever its spelling (`10000`, `10_000n`, `4_700`, `0x2710`, `1e4`). The literal check is on the parsed value, not the text.
- `packages/domain/eslint.config.js` loads both rules (it extends the root config for everything else).
- `packages/domain/package.json` declares, in its `realx` block, the verify step `{ "step": "domain-money-lint", "group": "lint", "run": "eslint -c packages/domain/eslint.config.js packages/domain", "scope": "packages/domain" }` so `npm run verify` at the repo root runs it. A02 does not edit A01's files; `npm run scripts:sync` picks the step up.

**Ids (`src/ids/`)**

- Branded string types, one per kind, each with `parse`, `is`, `format` and `make`. The prefix registry is one data table (`src/ids/registry.ts`); each row gives the prefix, the form and the generated body length, and adding a kind is a one-line change. A test asserts prefixes are unique and that no prefix is a prefix of another.
- Kinds and forms at launch:

| Kind | Prefix | Form | Body grammar accepted by `parse` | What `make` produces |
|---|---|---|---|---|
| Approval request | `APR-` | dated | `\d{8}-[C]{6}` (date `yyyymmdd`), or legacy `\d{3,7}` | `APR-YYYYMMDD-XXXXXX` |
| Custody and token operation | `OP-` | dated | `\d{8}-[C]{6}`, or legacy `\d{3,7}` | `OP-YYYYMMDD-XXXXXX` |
| KYC case (A30) | `KYC-` | dated | `\d{8}-[C]{6}` | `KYC-YYYYMMDD-XXXXXX` |
| Order | `RX-ORD-` | plain | `[C]{3,20}` | `RX-ORD-` + 10 chars |
| Investor account | `INV-` | plain | `[C]{3,20}` | `INV-` + 10 chars |
| AML case | `AML-` | plain | `[C]{3,20}` | `AML-` + 10 chars |
| API token record (D04) | `TOK-` | plain | `[C]{3,20}` | `TOK-` + 10 chars |
| Agent mandate (D04) | `MND-` | plain | `[C]{3,20}` | `MND-` + 10 chars |
| Principal (A11) | `PRN-` | kinded | `[HPAS]-[C]{10}` (kind letter as A11 defines it) | `PRN-<k>-` + 10 chars |

  `[C]` is Crockford base32 `[0-9A-HJKMNP-TV-Z]` (uppercase, no I, L, O, U). Plain bodies may be all digits, so the prototype's mock ids `RX-ORD-55120`, `RX-ORD-51877`, `INV-00912` and `AML-118` parse as plain ids. The dated kinds also accept an explicit **legacy** form, digits only, so `APR-2291`, `APR-2285`, `OP-7726` and `OP-7728` parse and the seed (A06) keeps the design's ids; `parse` reports the form (`dated`, `plain`, `kinded` or `legacy`) and `make` never produces a legacy id. Whether a new write may carry a legacy id is the caller's rule (A09), not this package's.
- Dated ids: the date segment must be a real calendar date (month 1-12, day valid for that month, leap years by the Gregorian rule); the date is the maker's **Australia/Sydney** calendar date, supplied by the caller as `{y, m, d}`. The package never derives a date from a clock.
- Generation: `make` takes an injected entropy source and the caller's date (never `Math.random` or `Date.now` inside the package). A test proves 1,000,000 ids generated from a seeded source (spread across every kind, with dated kinds over several dates) are distinct and all round-trip: `parse(format(id)) = id` and `format(parse(s)) = s`.
- Ids compare by exact string. `parse` refuses with a typed reason code: `empty` (nothing after the prefix), `bad_prefix` (no registered prefix, including lowercase prefixes), `bad_form` (wrong segment shape for the kind, including whitespace anywhere and a missing date segment), `bad_alphabet` (a character outside the kind's alphabet), `bad_length` (body length outside the bounds), `bad_date` (a date segment that is not a real calendar date), `looks_like_secret` (any string beginning `rx_`). `parseAny(string)` returns the id, its kind and its form, used by the audit log and search.
- Fixed vectors (in the package suite and the oracle): valid `APR-20260923-7K2M9Q` (dated), `APR-2291` (legacy), `OP-7726` (legacy), `RX-ORD-55120`, `INV-00912`, `AML-118` (plain), `TOK-4F8J2K9M3P`, `MND-8Q2W7E4R1T`, `PRN-H-3M8K2Q7T9V`; one refusal per code: `INV-` → `empty`; `XYZ-123` and `apr-2291` → `bad_prefix`; `APR-20260923` and `INV- 00912` → `bad_form`; `INV-00912O` → `bad_alphabet`; `INV-01` (a screen code) and a 21-character body → `bad_length`; `APR-20260231-7K2M9Q` → `bad_date`; `rx_live_4F8J2K` → `looks_like_secret`.
- Agent audit form (D04). The charter's `agent-access.json` freezes the audit line as "agent <token prefix id> on behalf of <person id>". In this package the token half is the `TOK-` record id (the stable, non-secret identity of the token) and the person half is the acting human's `PRN-` principal id, so the line reads `agent TOK-4F8J2K9M3P on behalf of PRN-H-3M8K2Q7T9V` for every user type: investor, sponsor user, licensed-partner user and staff. An `INV-` id is an investor account, not a person, and is never the "on behalf of" value. A12's `prefix` column (the non-secret leading characters of the `rx_` secret, shown in token lists so a person can recognise a token) is a display string owned by A12, not an id type here, and `parse` refuses it. Secret strings beginning `rx_` belong to A12 and the charter and are never generated or accepted here. A00 and A12 must state the same reading of "token prefix id" (see "Open items for other nodes").

**Money (`src/money/`)**

- `src/money/constants.ts` holds the only scale constants: `BP_SCALE = 10_000n` (basis points in one whole), `CENTS_PER_DOLLAR = 100n`, `PCT_SCALE_BP = 100n` (basis points in one percent). `mulBp`, `unitsShareBp`, `holderCapCheck`, `priceBand` and every other function use these names, never the numbers.
- `src/money/defaults.ts` holds default parameter values for tests and seeds only (the design's §7 constants and the withholding rates below). No function body reads `defaults.ts`; every rate, cap and fee is an argument.
- `Cents` is a branded `bigint` (AUD only at launch; the type carries the currency tag so a second currency in P3 is a type change, not a rewrite). Constructors: `centsFromInt(bigint)`, `centsFromDecimalString("2395.92")`, `parseAud("A$2,395.92")` (also accepts `2395.92`, `2,395`, `-A$1,000.00`, `A$25,000`; `A$25k` is rejected); rejects more than two decimals, `NaN`, `number` inputs and anything outside `bigint` with a reason code. No function accepts a JavaScript `number` for money; the types make it a compile error and a runtime check makes it a `DomainError` for untyped callers.
- Arithmetic: `add`, `sub`, `neg`, `sum`, `compare`, `min`, `max`, `isZero`, `isNegative`, `mulBp(cents, bp, rounding)`, `divInt(cents, n, rounding)`, `split(cents, weights[], rounding)`. Rounding is an explicit parameter from `'down' | 'up' | 'half_up'`; there is no default argument, so every caller writes its rule down. For negative values, `down` and `up` mean toward and away from zero, and `half_up` rounds half away from zero. `mulBp` and `divInt` work in `bigint` only (numerator scaled by `BP_SCALE`, then integer division and a remainder test); there is no intermediate `number`.
- Units: `Units` is a branded `bigint`, whole, never negative; `parseUnits("6,400")`; `unitsShareBp(qty, totalUnits)` gives the share of the trust in basis points rounded half-up (480 of 10,000 → 480 bp → `4.80%`; 10 of 10,000 → 10 bp → `0.10%`). `Bp` (basis points) is a branded integer; `pctToBp("5%") = 500`, `pctToBp("0.5%") = 50`, `bpToPctString(480) = "4.80%"`. Units are never fractional: a constructor given `6400.5` or `"6,400.5"` returns `fractional_units`.
- Formatting (`format.ts`, all through `Intl.NumberFormat('en-AU')` with the currency symbol replaced by the prototype's `A$` prefix):
  - `formatAud(cents, {decimals})`, where `decimals` is required and is `2` or `0`. `decimals: 2` → `A$2,395.92` (en-AU grouping, negative as `-A$1,000.00`, zero as `A$0.00`). `decimals: 0` rounds half-up to the whole dollar in `bigint` before formatting (`A$1,525,760`). Only these figures may drop cents: offer-level headline figures (amount raised, soft cap, hard cap, amount to soft cap) and property value or valuation headlines, which the prototype prints with `$(x,0)`. Balances, orders, fees, totals, refunds, distributions, withholding, statements, client money and anything a person pays or receives always use two decimals; `README.md` carries this list.
  - `formatAudCompact(cents)` → `A$1.53m` for amounts of A$1,000,000 and above (two decimals, half-up, suffix `m`) and the full two-decimal figure below that (`A$412,880.00`, `A$96,214.30`). Only KPI headline figures pass through it (the design shows the client-money total in full as `A$18,420,316.44` and the sponsor's raise as `A$1.53m`).
  - `formatPerUnit(cents, units)` → `A$0.2592` (four decimals, half-up, display only, never used in arithmetic); `formatUnits(10000n)` → `10,000`; `formatUnitsOf(6400n, 10000n)` → `6,400 of 10,000 tokens`; `formatBp(bp, {decimals})` → `4.80%`, `0.50%`, `5%` (the caller chooses two decimals or the shortest form).
  - A snapshot test pins the exact strings the prototype shows, including the whole-dollar strings `A$1,525,760` (152,576,000 cents), `A$1,788,000` (178,800,000), `A$2,384,000` (238,400,000) and `A$262,240` (26,224,000). Every node that displays money uses these formatters; A05's `packages/ui/src/format/` helpers, if they exist, must wrap them and add no arithmetic of their own (A05 does not depend on A02 in the graph today; see "Open items for other nodes").
- Fee math (`fees.ts`): `orderLines({qty, unitPriceCents, feeBp})` returns `{subtotal, fee, total, shareBp}` with `subtotal = qty × price` exactly, `fee = mulBp(subtotal, feeBp, 'half_up')`, `total = add(subtotal, fee)` exactly (never `subtotal × 1.005`). `feeBp` is passed in by the caller from the listing's fee schedule; `defaults.ts` holds `TRANSACTION_FEE_BP = 50` (0.5%) for tests and seeds only. Design vectors: 10 × A$238.40 = A$2,384.00, fee A$11.92, total A$2,395.92 (the prototype's "awaiting investment" figure); 100 × A$250.00 = A$25,000.00, fee A$125.00, total A$25,125.00 (journey J04; the product map's order field reads "$25,000.00 = 100 tokens · fee $125.00 · total $25,125.00"). Resale (P2) sell side: `sellProceeds({qty, priceCents, feeBp})` = gross − fee: 100 × A$99.80 = A$9,980.00, fee A$49.90, proceeds A$9,930.10. Buy side at an average price: 150 × A$100.17 = A$15,025.50, fee A$75.13 (75.1275 rounded half-up), total A$15,100.63. The requirements catalogue (D11 key rules) prints this sample as A$15,100.13, which is an arithmetic slip in the source; the oracle uses A$15,100.63 and the discrepancy is recorded in `README.md` and in the evidence for the catalogue owner. Fees are never expressed or deducted in units ("RealX never charges fees in tokens"): no fee function takes or returns `Units`.
- Budget to units (`budget.ts`): `unitsForBudget({amountCents, unitPriceCents, feeBp, feeMode})` returns `{units, subtotal, fee, total, leftoverCents}`, where `feeMode` is required:
  - `'on_top'`: the amount is the subtotal the person wants to invest and the fee is added (the product map's J04 buy field). `units = floor(amount / price)`; `leftoverCents = amount − subtotal`. Vector: A$25,000.00 at A$250.00, 50 bp → 100 units, subtotal A$25,000.00, fee A$125.00, total A$25,125.00, leftover A$0.00. Property: `subtotal ≤ amount` and `(units + 1) × price > amount`.
  - `'inclusive'`: the amount is the whole budget including the fee (a fixed monthly debit such as Auto Invest's "Sets $500 a month", or an agent told "spend at most $X"). `units` is the largest whole number with `orderLines(units).total ≤ amount`, found from `floor(amount × BP_SCALE / (price × (BP_SCALE + feeBp)))` and corrected by at most one unit either way using `orderLines`; `leftoverCents = amount − total`. Vectors: A$25,000.00 at A$250.00, 50 bp → 99 units, total A$24,873.75, leftover A$126.25; A$500.00 at A$106.40, 50 bp → 4 units, total A$427.73, leftover A$72.27. Property: `total ≤ amount` and `orderLines(units + 1).total > amount`.
  - Zero units is a valid result (`units = 0`, leftover = amount), never an error; a zero or negative price is `bad_price`.
- Distribution split (`distribution.ts`): `splitByUnits({totalCents, holders: [{id, units}]})` returns one line per holder with `grossCents = floor(totalCents × units / totalUnitsInSnapshot)` computed in `bigint` (no per-unit decimal rate is ever used in the arithmetic; the per-token figure is display only), plus `roundingCents = totalCents − Σ lines`. Invariants: every line rounds down; `0 ≤ roundingCents < holders.length` cents; `Σ lines + roundingCents = totalCents` exactly; a holder with zero units gets a zero line; the order of holders never changes any line; duplicate holder ids are refused. Design vector: A$2,592.00 over 10,000 units, holder with 480 units → A$124.41 (124.416 rounded down), 120 units → A$31.10, 60 units → A$15.55, 40 units → A$10.36; per-token display A$0.2592. The remainder is returned as a separate named amount for the ledger's rounding account (A16); it is never dropped and never re-spread.
- Withholding (`withholding.ts`, G16 arithmetic): `selectRateBp(profile, componentKind, rates)` returns `{rateBp, reason}`; `withholdingForLine({components: [{kind, grossCents}], profile, rates, rounding})` returns one `{kind, grossCents, rateBp, reason, withheldCents}` per component plus the line totals; `netForLine` gives `net = gross − withholding` exactly. The profile is `{residency: 'resident' | 'foreign' | 'unknown', tfnOnFile, abnOnFile, tfnExemptionOnFile, mitEligible, eoiCountry, cleanBuildingMit}` (`eoiCountry` means the investor's country of residence is an information-exchange country for the MIT withholding rules; it is not a tax-treaty flag). Component kinds are exactly `other_income` (for an MIT this is the fund-payment portion), `interest`, `unfranked_dividend`, `franked_dividend` and `non_assessable`; splitting a distribution into components is the tax engine's job (A41), not this package's. Rows are checked in order and the first match wins:

| # | Profile | Component | Reason code | Rate parameter (default in `defaults.ts`) |
|---|---|---|---|---|
| 1 | residency `unknown` | any | refusal `residency_unknown` (no rate is guessed) | none |
| 2 | resident, no TFN, no ABN, no TFN exemption | any | `no_tfn` | `NO_TFN_BP` (4700) |
| 3 | resident with a TFN, ABN or TFN exemption on file | any | `none` | 0 |
| 4 | foreign | `franked_dividend` or `non_assessable` | `foreign_exempt_component` | 0 |
| 5 | foreign | `interest` | `foreign_interest` | `NR_INTEREST_BP` (1000) |
| 6 | foreign | `unfranked_dividend` | `foreign_unfranked_dividend` | `NR_UNFRANKED_DIVIDEND_BP` (3000; a treaty rate is a per-profile override the caller passes in `rates`, never looked up here) |
| 7 | foreign, MIT, EOI country, clean-building MIT | `other_income` | `foreign_mit_clean_building` | `MIT_CLEAN_BUILDING_EOI_BP` (1000) |
| 8 | foreign, MIT, EOI country | `other_income` | `foreign_mit_eoi` | `MIT_FOREIGN_EOI_BP` (1500) |
| 9 | foreign, MIT, not an EOI country | `other_income` | `foreign_mit_non_eoi` | `MIT_FOREIGN_NON_EOI_BP` (3000) |
| 10 | foreign, not an MIT | `other_income` | `foreign_non_mit` | `FOREIGN_NON_MIT_BP` (3000, a placeholder until the tax adviser answers; the trustee's own assessment for a non-MIT trust is A41's, this is only the amount held back) |

  TFN withholding never applies to a foreign resident: a foreign investor with no TFN goes to rows 4-10, never row 2. Default rounding for withholding is `down` to the cent per component and is a parameter. Vectors (one `other_income` component of A$124.41): resident without TFN → A$58.47 withheld (58.4727), net A$65.94; foreign, MIT, EOI → A$18.66 / A$105.75; foreign, MIT, non-EOI → A$37.32 / A$87.09; foreign, clean-building MIT, EOI → A$12.44 / A$111.97; resident with TFN → A$0.00 / A$124.41 (the design's "Tax withheld A$0.00 (TFN on file)"); residency unknown → `residency_unknown`. The rates, the component list and the table itself are HG-LEGAL questions for the tax adviser (question 5 below); the table is data in `withholding.ts`, so an answer changes a row, not the function.
- Holder cap (`holder-cap.ts`, G07): `holderCapCheck({existingUnits, orderUnits, totalUnits, capBp})` returns `{ok, holdingAfterBp, holdingAfter: {numeratorUnits, denominatorUnits}, capBp, maxAllowedUnits, shortfallUnits}`.
  - Rule: `(existing + order) × BP_SCALE ≤ capBp × totalUnits` passes (at cap passes; one unit over fails), computed in integers with no division. `maxAllowedUnits = floor(capBp × totalUnits / BP_SCALE) − existing`, floored at zero, so the refusal message can name the maximum ("You can buy up to 20 more tokens").
  - `holdingAfterBp` rounds **up** to the next basis point, so a refused order never displays at or under the cap; the exact rational is returned alongside for callers that need it.
  - Denominator (`totalUnits`): the units on issue **after** the transaction. For a primary offer the order-time check uses the offer's hard-cap units plus any units already on issue (the most the trust can have after the offer); allocation re-checks against the units actually issued at close (see `scaleBack`). For a resale transfer (P2) it is the units on issue, which a transfer does not change.
  - `existingUnits` is whatever the caller aggregates (the holder plus associates, per the catalogue's "incl. associates"); the function does not know what an associate is.
  - Design vectors at cap 500 bp and 10,000 units: existing 0, order 120 → ok, 1.20%; existing 480 (Kwan Family SMSF, 4.80%) + 20 → ok, at cap; existing 480 + 21 → fails, max 20; existing 0, order 500 → ok; order 501 → fails. Rounding vectors: 20,000 units, order 1,001 → fails, `holdingAfterBp` 501 (`5.01%`), max 1,000; 30,000 units, order 1,501 → fails, 501 bp (500.33 rounded up), max 1,500. Close-below-hard-cap vector: see `scaleBack`.
  - The prototype's buy-stepper copy implies "≥ 500 tokens fails"; this spec fixes "at cap passes", matching the ERC-3643 max-balance module (which rejects only `balance > max`) and the design's own register KPI "Largest holding 4.8% (Cap 5%)"; A00's charter records that reading.
  - `maxBalanceUnits(capBp, totalUnits) = floor(capBp × totalUnits / BP_SCALE)` is the value exported to the ERC-3643 `MaxBalanceModule` (A24). Vectors: 500 bp of 10,000 → 500; 500 bp of 7,789 → 389. The module counts balances per on-chain identity (all wallets linked to one ONCHAINID), in token base units; RealX tokens have `decimals() = 0` (A24), so one unit is one base unit. Associates are aggregated off-chain only, by the caller of `holderCapCheck`.
  - Also `holderCountCheck({holdersAfter, capCount})` for the member-count monitor (the 20-member trigger is a parameter in the rule pack, never a literal here).
- Price band (`price-band.ts`, G09): `priceBand({valuationCents, lowerBp, upperBp})` returns `{lo, hi}` with `lo = mulBp(valuation, BP_SCALE − lowerBp, 'up')` and `hi = mulBp(valuation, BP_SCALE + upperBp, 'down')`, so rounding never widens the band. `inBand(priceCents, band)` is `lo ≤ price ≤ hi` (endpoints allowed). Defaults `lowerBp = upperBp = 1500` (85-115% of valuation) come from the listing. Vectors: A$102.40 → A$87.04 to A$117.76; A$246.10 → lo A$209.19 (209.185 rounded up), hi A$283.01 (283.015 rounded down); an ask of A$117.77 on the first band is rejected with the allowed range in the reason.
  - `bandMarker({priceCents, band, trackBandStartBp, trackBandEndBp})` returns `{bandPositionBp, trackPositionBp}` as integers from 0 to 10,000 (hundredths of a percent). `bandPositionBp = (price − lo) × BP_SCALE / (hi − lo)`, rounded half-up and clamped to 0..10,000. The design's PriceBand track draws the allowed band from 15% to 85% of its width with out-of-band zones either side (`linear-gradient(... 0 15%, ... 15% 85%, ... 85%)`), so the defaults are `trackBandStartBp = 1500`, `trackBandEndBp = 8500` and `trackPositionBp = trackBandStartBp + (price − lo) × (trackBandEndBp − trackBandStartBp) / (hi − lo)`, rounded half-up and clamped to 0..10,000 (a price outside the band lands in an out-of-band zone). Vectors on the A$87.04-A$117.76 band: A$102.40 → band 5,000, track 5,000; A$87.04 → band 0, track 1,500; A$117.76 → band 10,000, track 8,500; A$80.00 → band 0, track 0 (clamped). The prototype's static 52% marker is a picture, not a computed value; A05 and the P2 sell screen draw `trackPositionBp`.
- Token valuation (`valuation.ts`, G20 arithmetic only): `navPerUnit({propertyValueCents, cashCents, debtCents, liabilitiesCents, units})` = `(value + cash − debt − liabilities) / units`, returned both as an exact rational `{numeratorCents, denominatorUnits}` and as `Cents` rounded half-up. Vector from the product map, field by field: `propertyValueCents` 118,000,000 (A$1,180,000), `cashCents` 3,840,000 (A$38,400), `debtCents` 0, `liabilitiesCents` 620,000 (A$6,200), `units` 10,000 → numerator 121,220,000 cents → 12,122 cents (A$121.22). Negative net assets return a zero NAV with a `negative_nav` flag rather than a negative price; zero units returns `no_units`.
  - `discountBp(priceCents, valuationCents)` returns signed basis points of the exact rational `(valuation − price) / valuation`, rounded half away from zero (A$238.40 vs A$246.10 → +313 bp, price below valuation).
  - `formatDiscount(priceCents, valuationCents, {deadBandBp})` works from the same exact rational, never from the rounded `discountBp`, and reproduces the prototype's rule (the `disc` expression in the script block of `RealX App.dc.html`, where `d = (val − price) / val × 100`): if the exact discount is greater than the dead band → `<d>% below valuation`; if it is less than minus the dead band → `<|d|>% above valuation`; otherwise `At valuation`. The dead band is strict (exactly 5 bp is `At valuation`) and is a parameter (default 5 bp, the prototype's `0.05`). The percentage prints with one decimal, rounded half-up on the exact rational. The prototype's float `toFixed(1)` can differ from exact half-up only when the exact value ends in ...5 at the second decimal; none of the eight mock properties does, and this spec uses exact half-up.
  - Vectors, all eight mock properties: A$238.40 / A$246.10 → `3.1% below valuation`; A$418.50 / A$412.00 → `1.6% above valuation`; A$115.20 / A$118.60 → `2.9% below valuation`; A$364.00 / A$364.00 → `At valuation`; A$164.90 / A$168.80 → `2.3% below valuation`; A$189.00 / A$192.40 → `1.8% below valuation`; A$288.80 / A$296.00 → `2.4% below valuation`; A$106.40 / A$109.90 → `3.2% below valuation`. Boundary vectors on a A$1,000.00 valuation: A$999.50 (exactly 0.05%) → `At valuation`; A$999.49 (0.051%) → `0.1% below valuation`; A$1,000.50 (exactly −0.05%) → `At valuation`; A$1,000.51 → `0.1% above valuation`; A$968.50 (exactly 3.15%) → `3.2% below valuation`; A$968.51 (3.149%) → `3.1% below valuation`.
  - `movementBp(old, new)` serves the "+18.4%" change line and the ±10% comparable-sales trigger (the threshold itself is a parameter).
- Offer progress arithmetic (`offer.ts`): `raisedPct`, `softCapReached`, `hardCapRoom`, `scaleBack` and `refundAll`.
  - `scaleBack({orders: [{id, holderKey, requestedUnits, existingUnits, paidCents}], hardCapUnits, unitsOnIssueBefore, unitPriceCents, feeBp, capBp})`. Each order's `paidCents` must equal `orderLines({qty: requestedUnits, unitPriceCents, feeBp}).total` (subtotal plus the escrowed fee), otherwise the order is refused with `paid_mismatch`.
  - Step 1, pro-rata: if Σ requested ≤ hard cap every order is allocated in full; otherwise allocation is pro-rata in whole units by the largest-remainder method so Σ allocated = hard cap exactly, ties broken by order id.
  - Step 2, holder cap (G07, the ADM-12 "Allocate" check): with `finalUnits = unitsOnIssueBefore + Σ allocated`, any holder (`holderKey`, with `existingUnits`) whose existing plus allocated units fail `holderCapCheck` against `finalUnits` is cut to `maxAllowedUnits`, taken from that holder's highest order id first. Cutting lowers `finalUnits`, so the pass repeats until no holder fails; allocations only fall, so it ends. Units cut here are refunded, never re-spread. `softCapReached` is judged on the units left after this step.
  - Step 3, refunds: `refund = paidCents − orderLines({qty: allocated, unitPriceCents, feeBp}).total` for each order, never negative (the fee on units not allocated goes back with them). Invariant: Σ allocated totals + Σ refunds = Σ paid, to the cent.
  - `refundAll(orders)` (journey J05, soft cap missed): every order is allocated 0 and refunded its full `paidCents`, fee included.
  - Vectors: fee remainder — 7 units at A$238.40, 50 bp, paid A$1,677.14 (subtotal A$1,668.80 + fee A$8.34), allocated 5 → allocated total A$1,197.96 (A$1,192.00 + A$5.96), refund A$479.18. J05 — 100 × A$250.00, paid A$25,125.00, soft cap missed → allocated 0, refund A$25,125.00. Close below hard cap — hard cap 10,000, cap 500 bp, nothing on issue before, 20 orders of 370 units from 20 different holders plus one holder ordering 500: each order passes at order time against 10,000; the offer closes at 7,900 units; the cap pass cuts the 500-unit holder to 395, then 389 (4.99% of 7,789 final units, and 390 would be 5.006%), refunds 111 units with their fee, and the soft cap (7,500) is still met.
  - Design vectors: Kent Street 6,400 of 10,000 tokens, soft cap 75% ("64% of 75%"), raised 152,576,000 cents shown as `A$1.53m` on the dashboard and `A$1,525,760 raised` on the offer card, soft cap `A$1,788,000 (75%)`, hard cap `A$2,384,000`, to soft cap `A$262,240` (1,100 tokens); Ann Street 2,800 of 10,000 in escrow (28%).
