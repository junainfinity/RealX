# A12 - API tokens, scopes, agent principals and mandates for every user type (G22)

**Founder decision D04 as a core authentication capability that every later API route inherits: an API token for every principal of every user type, scopes that are cells of the role x module x action matrix so a token can never exceed its owner, mandates that bind an agent to a named human with caps and expiry, and the G22 "Agent authority" evaluator that runs on every token call and refuses, by name, anything outside the mandate.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Compliance core. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 14-20 agent-hours for this node (build, challenge and verify loops), plus 4-6 agent-hours for its follow-up loop A12.1 (§8), which runs after A14 passes.

**Depends on:** [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A10 - Append-only hash-chained audit log]], [[A03 - State machines, gate codes, approval codes and permission matrix as data]]
**Unlocks:** [[A14 - Approvals engine and maker-checker (SM-00)]], [[A19 - Rules engine- gates G01-G22, rule packs, threshold monitors, simulator]], [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests]], [[A33 - Sponsor tenancy, entities, licences of sponsors and admission pipeline]], [[A46 - Job scheduler, integrations health and webhooks]], [[A60 - Investor and sponsor API tokens and agents screens (ACC-05, SPN-16)]], [[A77 - Console- agent and API access (ADM-35)]], [[A82 - End-to-end- an agent drives the account through the API and MCP]], [[A98 - Partner principals- trustee-RE, valuer, property manager, auditor, regulator observer and licensee users]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]], [[A100 - Agent-parity suite- every UI action has an API and MCP equivalent under the same gates]], [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]], [[A104 - MCP server generated from the OpenAPI document]]

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A12\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The hidden set covers at least the eleven invariants in the Gauntlet loop section below.

What this node is for in one sentence: anything a person can do on their screens, their agent can do through the API under exactly the same rules, and nothing more. This node is the server side of that promise. It draws no screen: ACC-05, SPN-16 and ADM-35 are A60 and A77; the MCP server, docs, per-user sandbox, parity suite and anomaly guard are A104, A99, A100 and A101, and all of them consume the interfaces frozen here. ## Build brief

**1. What this node reuses and what it adds (no duplication of A03, A04, A08, A09, A10, A11)**

- Principals come from A11: the AGNT principal type (`PRN-A-…`) with `on_behalf_of_principal_id`, the `requiresHuman` route flag that refuses agents on person-only routes with `AGNT_NOT_ALLOWED`, the fresh-assertion primitive `requireFreshAssertion({maxAgeMinutes, purpose})`, `GET /iam/me` as the scope ceiling, `eligibleCheckers` for segregation of duties, the `Account` lifecycle (`active | dormant | locked | closed`) and the events listed in §2 "Automatic revocation and holds".
- Scope data comes from A03: `scopes.ts` (`scopesFor(owner)`, `familiesFor(owner)` for the scope-group pickers), `delegable.ts` (`true`, `false` or `"counsel"`; `"counsel"` behaves as non-delegable until counsel answers) and `validateTokenScopes(requested, owner)`. This node invents no scope names, no non-delegable list and no scope reason codes: it returns A03's codes verbatim, in A03's order (`SCOPE_UNKNOWN`, `SCOPE_AGENT_NEVER_CHECKER`, `SCOPE_NON_DELEGABLE`, `SCOPE_PENDING_COUNSEL`, `SCOPE_EXCEEDS_OWNER`, `SCOPE_PHASE_OFF`), each naming the cell. A03's `reason-codes.ts` is the single source of these spellings. The runtime refusals of the same conditions at call time are the same names with the `G22_` prefix (`G22_SCOPE_NON_DELEGABLE`, `G22_SCOPE_PENDING_COUNSEL`, `G22_AGENT_NEVER_CHECKER`), and A01's verify fails on any other spelling.
- **Which non-delegable list is authoritative.** A03's `delegable.ts` is the single source for which actions an agent may take (it mirrors A00's `agent-access.json` block (a)). A11's `packages/domain/non-delegable.ts` is a derived route list that sets `requiresHuman` on routes. This node ships a consistency test that fails `npm run verify` when the two disagree: every route whose `x-realx-scope` cell is `false` or `"counsel"` in `delegable.ts` carries `requiresHuman: true`, and every `requiresHuman` route's cell is non-delegable. A disagreement is an upstream spec defect (reopen A03 or A11), never a local patch.
- Tables come from A04 exactly as A04 names them; §7 lists the mapping, the tables this node registers itself, and the columns requested from A04 as its follow-up loop A04.1.
- Plumbing comes from A09: `x-realx-scope`, `x-realx-money`, `x-realx-delegable` and `x-realx-requires-human` on every route (a route without a scope fails registration, so nothing is reachable by omission), the error envelope with `gate` and `reason_codes`, `registerErrors()` for this node's codes, idempotency on every write (a token write without `Idempotency-Key` is refused by A09's core, not re-implemented here), the rate-limit slot with an injectable limit policy, `on_behalf_of_id` and `token_id` on every log line and outbox event, and the pino redaction list, which gains the token pattern `rx_[a-z]+_[A-Z2-7]{12}_[A-Z2-7]{32}`. A09's hook slots are used as named, never reordered: token authentication fills the `principal` slot; the tiered kill-switch check takes over the `kill-switch` slot (replacing A09's interim `agents.traffic` check, see §5); the mandate's rate limits are the policy injected into the `rate-limit` slot; the G22 evaluation runs after A09's `validation` slot (it needs the validated amount, units, vehicle and property) as the first step of the `handler` slot.
- Audit comes from A10: `audit.record(tx, event)` with `actor_type = AGNT`, `token_id` and `on_behalf_of_id` (the database refuses an agent event without a human behind it); `GET /me/activity` already returns the rows a person's agents wrote, and ACC-05 reads it.
- Flags come from A08 read-only: `isEnabled('agents.traffic')`. This node never writes `feature_flag`. Turning `agents.traffic` off is A48's effector through A21's `setFlag` (A08 §D04). Until A48 lands, the platform switch in this node writes a row in its own `agent_switch` table through an interim effector (§5).

**2. Token types, secret format, issue paths (self-service by the person, never by staff on the person's behalf)**

- One `api_token` row belongs to exactly one owner principal (HUMAN investor or sponsor user, PARTNER from A98, or STAFF) and names exactly one `agent_principal` (AGNT) as the actor, `on_behalf_of_id` = the owner. Prefixes are the fixed strings A04's `CHECK` allows: `rx_inv_` investor, `rx_spn_` sponsor user (including the valuer TP-VAL and property manager TP-PM who work in the sponsor console as tenant members; A98 calls these memberships "SP-VAL" and "SP-PM", which are aliases of the product-map role ids TP-VAL and TP-PM), `rx_ptr_` platform partner (TP-RE, TP-AUD, TP-OBS, TP-LIC), `rx_stf_` RealX staff, `rx_sb_` sandbox (any owner; `environment = sandbox`, which A04's `CHECK` ties to the `rx_sb_` prefix; A99 owns the partition).
- Secret format `rx_<type>_<lookup>_<secret>`: lookup = 12 base32 characters, indexed and stored in clear; secret = 32 base32 characters from a CSPRNG, stored only as an Argon2id hash with a per-row salt (`secret_hash`) and compared in constant time. The full secret is returned exactly once, in the create and rotate responses, and exists nowhere else: not in any column, log line, audit event, outbox event, evidence file, error message, cursor or URL.
- **Verification order (fixed, so every forgery gets one predictable answer):** (1) parse the bearer against the pattern; malformed gives `401 TOKEN_INVALID`; (2) look up the row by `lookup`; no row gives `TOKEN_INVALID`; (3) compare the presented prefix with the stored `prefix`; a mismatch gives `TOKEN_INVALID` (an edited prefix is a forged token, not a wrong environment); (4) verify the secret against `secret_hash`, or against `prev_secret_hash` while the rotation grace window is open; failure gives `TOKEN_INVALID`; (5) only now read the state: `pending_*` gives `401 TOKEN_PENDING`, `revoked` gives `TOKEN_REVOKED`, `expired` or past `expires_at` gives `TOKEN_EXPIRED`, `held` gives `423 AGENT_HELD` (§5); (6) compare the token's `environment` with the route's environment; a mismatch gives `403 TOKEN_WRONG_ENVIRONMENT`. State is never revealed to a caller who has not proved the secret.
- **Verification memo (optimisation, never the guarantee).** Argon2id is slow, so a process may memoise a successful verification. The memo key is the tuple (`lookup`, SHA-256 of the presented secret, stored `secret_hash` or `prev_secret_hash` it matched, `row_version` of the token). A presented secret that differs from the one that succeeded never matches the key, so a cached success can never admit a different secret. The memo is dropped on rotation, when the grace window closes, and on revoke or hold (through Postgres NOTIFY), and it holds only the fact "this secret matches this hash"; state, mandate and roles are still read from the database on every request.
- **Rotation** issues a new secret under the same `TOK-` id and mandate, with a grace window of at most 10 minutes during which both secrets verify (configurable down to zero; `prev_secret_hash` and `prev_secret_valid_until` hold the old one). Rotation is non-delegable in A03 ("creating, widening or rotating an API token"), so the route carries `requiresHuman: true` and needs a fresh passkey assertion (purpose `token_rotate`, no older than 5 minutes) over the canonical hash of `{token_id, row_version}`. Rotation needs no second person because rights do not change. It bumps `row_version`.
- **Creation and widening.** Every create and every widening carries a fresh passkey assertion (A11 primitive, purpose `token_issue` or `mandate_widen`, no older than 5 minutes) over the canonical hash of the request (name, agent, scopes, limits, expiry, IP list, signing key if any, standing disclosure consent if any; canonicalised as in §4). No assertion, a stale one, a reused one, or one over a different payload hash is refused with A11's `FRESH_ASSERTION_REQUIRED`, `FRESH_ASSERTION_STALE` or `FRESH_ASSERTION_MISMATCH`, and the token or mandate is unchanged. An assertion from an AGNT principal is impossible (agents have no passkeys), so an agent can never create, widen or rotate a token: those routes carry `requiresHuman: true`.
- **G01 precondition at issue.** The product map lists G01 on "Create token" (ACC-05, SPN-16). A live token is issued only when the owner's identity is verified: for an investor, the `IdentityStatusPort` answers `isWhitelisted`; for a sponsor user or partner, the person's own verification; for staff, A11 enrolment counts. A failure gives `403 TOKEN_IDENTITY_NOT_VERIFIED` with `gate: G01` in the envelope. Until A30 and A19 land (AM3), the port is backed by a fixture that the tests drive to both answers; A30 registers the real implementation and re-runs this node's G01 oracle cases. Sandbox tokens follow A99's rule.
- Individual investors (INV-W, INV-S, INV-R, INV-F): the assertion alone creates an `active` token.
- Joint investors (INV-J): the account's signing rule is read through the `SignatoryPort` (below). "Either to sign" needs one signatory's assertion. "Both to sign" creates the token in `pending_cosign`; the second signatory's assertion over the same payload hash within 24 hours activates it, otherwise it expires unissued (`TOKEN_COSIGN_EXPIRED`). The token is owned by the signatory who created it.
- Entity investors (INV-E: SMSF, company, trust): only a principal the `SignatoryPort` reports as a verified signatory of the entity may create; anyone else gets `TOKEN_SIGNATORY_REQUIRED`. Guardian-for-a-minor (INV-M, P3) is refused with `PHASE_NOT_ENABLED` from A08's phase flags.
- **`SignatoryPort`** (exported interface, `signingRule(accountId) -> either | both`, `signatories(accountId) -> principal ids`, `isVerifiedSignatory(principalId, entityId) -> boolean`). The joint signing rule and the entity signatory flag belong to A30 (AM3), which is neither a dependency nor built at this node's gate, so this node ships a fixture implementation used only in tests. A30 registers the real implementation and must re-run this node's joint and entity oracle cases as part of its own gate.
- **Second-person approval for sponsor and staff tokens (`IssueApprovalPort`).** Sponsor users (SP-OWN, SP-OPS, SP-FIN, SP-IR, TP-VAL, TP-PM) and staff whose token carries any write family wait in `pending_owner_approval` until a second person approves with their own fresh assertion; read-only tokens activate on the requester's assertion alone (Specify point (a) records this). The approval step is behind `IssueApprovalPort` (`open(request) -> pendingRef`, `onDecision(pendingRef, decision)`): this node ships an interim implementation, a local two-step that stores `approver_principal_id` and `approver_assertion_id` on the token; A14 registers its `4E` implementation (`agent.token.create_sponsor`, `agent.token.create_staff`) and re-runs this node's issue tests against the wired path. Who approves:
  - Sponsor: an SP-OWN of the same tenant who is not the requester; an SP-OWN requesting for themselves needs a second SP-OWN if the tenant has one, otherwise a RealX PART or SECO. The product map's SPN-16 "Create token" row names no second approver; the two-person rule for write scopes is a proposed deviation drawn from the nearest product-map row (ADM-32 "Create API key with write scope", which is about sponsor integration keys) and from CQ-04 (a sponsor agent never counts as one of the sponsor's two people), recorded as Specify point (a). Sponsor tokens are tenant-scoped: RLS from A04 applies to every call exactly as to the member's own session.
  - Staff: creation requires a hardware-attested assertion (A11's AAGUID check; a software passkey is refused with `ATTESTATION_REQUIRED`). The product map's ADM-35 row is "Create my token with write scopes · Passkey plus the line manager's approval · maker: staff member, checker: line manager". A11 records no line-manager relationship, so the proposed default is a SECO who is not the requester, with the line-manager option recorded as Specify point (a). SUPER may not hold a token with any money, custody or signer cell (A11 SoD rule 3 applied to the token exactly as to the person); the request is refused at issue with `SOD_HARD_CONFLICT`.
- Partners (A98): the PARTNER principal creates with a fresh assertion; the token can carry only the partner's own cells and is limited to the partner's `partnerScope` (assigned vehicles or engagement); TP-AUD and TP-OBS tokens are read-only and inherit the partner's time box as `expires_at`. Until A98 lands, a fixture PARTNER principal from A11's principal model is used for tests.
- **Token lifecycle** (A04's `state` values; a small local transition table in the A03 engine format, not one of the 14 product-map machines): `pending_cosign -> active | expired`, `pending_owner_approval -> active | revoked (declined) | expired`, `active -> held | revoked | expired`, `active -> active` on rotation, `held -> active` (cause `hold_cleared`, carrying the clearing assertion id or staff decision id), `held -> revoked`, `held -> expired`. A transition not in the table is refused with `TOKEN_ILLEGAL_TRANSITION`. Each transition writes one audit event of its own (see §5 for how these sit beside the per-request event).
- **Revocation rights (who may revoke whose token).** Revoke is delegable (A03) and never needs a fresh assertion:

  | Actor | May revoke | Notes |
  |---|---|---|
  | The owner, signed in | Any of their own tokens, one or all (`revoke-all`) | Product map ACC-05 "Revoke one token, or all at once" |
  | The token itself (its own bearer) | Itself, and may narrow its own mandate | A03: "revoke stays delegable so an agent can kill itself"; needs no scope |
  | Another token of the same owner | Sibling tokens of that owner, one or all | Only with the delegable revoke cell in its scopes (parity with the owner) |
  | SP-OWN, signed in | Any token of a member of the same tenant, including TP-VAL and TP-PM members | SPN-16 "Revoke a team member's token · Owner; immediate" |
  | SECO or SUPP, signed in | Any token platform-wide | ADM-35 "Revoke any token · Immediate; the owner is notified" |

  Anyone else gets `403 TOKEN_REVOKE_NOT_ALLOWED`. When the revoker is not the owner, `agent.token.revoked` carries `revoked_by` and `revoked_by_role` and the owner is notified (A43 notice through A101's notice policy). The matrix is data in `packages/domain/src/agent-authority/revoke-rights.ts` with one test per row and one refusal test per non-row.
- **Automatic revocation and holds (fail closed, no human step).** Each trigger is handled in the same transaction that consumes the event. The per-request live check in §5 (owner account state, owner roles, tenant and partner scope read on every call) is the real guarantee; the events make the state visible and tidy. Until each publisher lands, the tests drive the same handler with a fixture event of the exact name below.

  | Trigger | Event and publisher | Effect |

  | Login recovery completed | `auth.recovery.completed` (A11) | Revoke every token of the principal |
  | Investor closes the account or is offboarded | `investor.offboarded` (A30, AM3; ACC-01's close runs through A30) | Revoke all |
  | Investor frozen or under AML review | `investor.suspended` / `investor.reinstated` (A30, AM3; driven by A42's `aml.account.restrict` and ADM-09) | Hold every token of the account's members with hold class `account_under_review`; reinstatement releases only holds of that class. The agent sees the same neutral `AGENT_HELD` reason as any account under review (no tipping-off) |
  | Joint member leaves | no named event yet: fixture `joint.member.removed`, requested from A30 | Revoke that member's tokens |
  | Joint signing rule changes to "both" | `joint.signing_rule.changed` (A30) | Hold tokens created under "either" with class `cosign_required` until the second signatory's assertion |
  | Sponsor tenant suspended | `tenancy.tenant.suspended` (A33, AM3) | Revoke every token of the tenant's members (product map SPN-16 "Sponsor suspended: all its tokens stop at once") |
  | Sponsor member removed or suspended | `tenancy.user.removed`, `tenancy.user.suspended` (A33) | Revoke that member's tokens |

**3. Scopes: never wider than the owner, never a non-delegable act, never above policy**

- A scope is a cell id of the A03 matrix in the string form A03 defines (`scopeId === actionId`). Scope groups for the pickers (read, invest and trade, money movement, documents, governance, sponsor listing, sponsor distribution, sponsor reporting, staff module scopes M01-M27) come from A03's `familiesFor(owner)` and expand to cells; the module ships only the mapping from family to the plain-English labels the screens show.
- At issue and at widening `validateTokenScopes(requested, owner)` runs on the owner's live cells from `GET /iam/me` and its refusals are returned verbatim, one per refused cell, never silently dropped: `SCOPE_EXCEEDS_OWNER`, `SCOPE_AGENT_NEVER_CHECKER` (every approve, ratify, veto and execute-or-sign cell, which A03 checks first from the action kind; the refusal carries `kind` so the screen can say "agents never approve"), `SCOPE_NON_DELEGABLE` (the other non-delegable cells), `SCOPE_PENDING_COUNSEL` (with the message that the declaration must be made by the person until counsel confirms otherwise), `SCOPE_PHASE_OFF` (the cell's phase is not enabled) and `SCOPE_UNKNOWN` (not a cell of the frozen matrix).
- **Policy ceilings.** Two policy objects cap what any token can hold, and both are ceilings only:
  - *Platform agent policy* (ADM-35 "Platform agent policy: allowed scopes per user type, maximum limits and expiry, rate limits"): per owner type (investor, sponsor user, partner, staff) the allowed families, maximum per-action, daily and monthly caps, maximum expiry and rate-limit ceilings. Version 1 is seeded from `packages/config`; this node reads the current version on every issue and every call. The change path ("Change platform agent policy · Policy v+1 · SECO → CCO", `4E`) needs A14 and is in A12.1.
  - *Sponsor agent policy* (SPN-16 "Set sponsor agent policy · Owner only; can't loosen a platform minimum"): per tenant the allowed families, maximum expiry and a required IP allow-list. `PUT /v1/agent-access/tenant-policy` by an SP-OWN with a fresh assertion (`requiresHuman: true`); a value looser than the platform policy is refused with `POLICY_ABOVE_PLATFORM`.
  - Issue refuses anything above a ceiling with `POLICY_CEILING` naming the field. Tightening takes effect on the next call of every existing token: a scope the policy no longer allows is refused `G22_POLICY_CEILING`, and a cap is enforced at the lower of mandate and policy.
- A token's effective rights are recomputed on every request as token scopes ∩ owner's live cells ∩ platform policy ∩ tenant policy (sponsor tokens) ∩ `partnerScope` (partner tokens), never from a snapshot: when the owner loses a role, its cells stop working on the next request (`G22_OWNER_NO_LONGER_HOLDS_ROLE`); when the owner gains a role, the token gains nothing until the human widens it with a fresh assertion.

**4. Mandates, limits, counters, standing disclosure consent and token-bound confirmation**

- An `agent_mandate` binds a token and its AGNT principal to `on_behalf_of_id`, a scope set (a subset of the token's scopes), and limits: `per_action_cap_cents`, `daily_cap_cents`, `monthly_cap_cents` (ACC-05 "per-order and monthly limits"; the design mock's "$1,000 an order · $5,000 a month"), `per_action_units`, `daily_units`, `monthly_units`, `allowed_vehicle_ids`, `allowed_property_ids`, `allowed_actions` (a subset of the scope set), `time_windows` (weekday and hour ranges in Australia/Sydney), `expires_at` (default 90 days, maximum 365 or the platform policy's maximum if lower, never past the owner's classification certificate, licence or partner engagement expiry where one applies), `rate_limit_reads_per_min` and `rate_limit_writes_per_min` (within the platform policy's ceilings per owner type: 60 reads and 10 writes for investors and partners, 120 and 30 for sponsor users, 300 and 60 for staff in version 1; overridable downwards only), an optional `session_key_policy` and an optional `standing_disclosure_consent`. The IP allow-list lives on the token (A04's `api_token.ip_allowlist`), and removing an entry is a widening. Every cap is integer cents or integer units from A02's money math.
- Creation and every widening (adding a scope, raising a cap, adding a vehicle or property, extending expiry, widening a window, removing an IP restriction, raising a rate limit, registering a signing key, adding or widening the standing disclosure consent) needs a fresh assertion over the new canonical mandate hash; narrowing and revoking need only a signed-in session of the owner, or the token's own bearer (§2 revocation rights). A mandate is never edited in place: a change inserts a new version (`version`, `supersedes_id`) and moves the previous one to `superseded`, where it stays readable with its assertion id for audit.
- **Canonical hash.** Every payload that an assertion or a signature covers (token request, mandate version, confirmation) is canonicalised with RFC 8785 JSON Canonicalization Scheme (JCS) and hashed with SHA-256 in `packages/domain/src/agent-authority/mandate-hash.ts`. Money is integer cents and units are integers before canonicalisation; timestamps are RFC 3339 UTC strings with milliseconds.
- **Counters.** Usage lives in `agent_counter` (one row per mandate per Australia/Sydney day, `UNIQUE (mandate_id, sydney_day)`, registered by this node as A04 assigns). Every reservation first takes `pg_advisory_xact_lock` on the mandate id, then upserts today's row, then reads the month total as the sum of that Sydney month's rows under the same lock, so two concurrent calls that together exceed a daily or monthly cap cannot both pass, including across the midnight boundary. The reservation is written in the business transaction, so it is released automatically when the action fails after the gate. The day and month boundaries are Australia/Sydney, taken from A09's injectable clock, never UTC.
- **Standing disclosure consent (D04 "disclosures acknowledged under the holder's standing consent"; counsel parameter CQ-02).** A mandate may carry `standing_disclosure_consent`: a reference to the holder's `standing_consent` row (the store is A04's table, owned in behaviour by A35) plus the document types, document ids and versions it covers, snapshotted into the mandate and included in the mandate hash. It can be created or widened only under a fresh assertion over that hash, and only when the CQ-02 parameter (A00's `agent-access.json` key; default: allowed only where the person recorded a standing consent that names the document types, and never for the person's first purchase in a trust) allows it; otherwise the request is refused `CONSENT_NOT_PERMITTED` naming CQ-02. It is exposed in `introspect` and in the G22 input so A19's G12 evaluator and A35's `getAcknowledgementFacts` can both read it. A document version published after the consent was recorded is not covered unless A35's `new_version_policy` says so: the agent's acknowledgement fails in G12 and the order waits for the person. This node decides only whether the mandate carries the consent; whether a given acknowledgement passes is A19 and A35's.
- **Token-bound confirmation.** The actions the design confirms with a passkey (order confirm on INV-02, withdrawal request on POR-05) may be pre-authorised inside a mandate through a signing key: an Ed25519 public key in `mandate_signing_key`, registered under the human's fresh assertion over the mandate hash (which covers the key and the caps). For a "both to sign" joint account both signatories must assert, as for token creation; for an entity, a verified signatory.
  - Header: `RealX-Mandate-Signature: v=1; kid=<signing key id>; sig=<base64url Ed25519 signature>`. A104 and the SDK use this name unchanged; it is in the OpenAPI document as a security scheme extension.
  - Signed object (JCS, exactly these fields): `{ v: 1, token_id, mandate_id, mandate_version, operation_id, method, route_template, path_params, body_sha256 (SHA-256 of the JCS of the validated request body), idempotency_key, amount_cents, units, vehicle_id, property_id, issued_at, expires_at }`. `expires_at - issued_at` is at most 5 minutes and `issued_at` may not be more than 30 seconds in the future (A09 clock).
  - The API rebuilds the object from the request it received and verifies the signature against it. Refusals, all `403` with `gate: G22`: `CONFIRMATION_SIGNATURE_INVALID` (bad signature or any field differs from the request, so a signature for one route, amount, vehicle or body cannot be used on another), `CONFIRMATION_SIGNATURE_EXPIRED`, `CONFIRMATION_SIGNATURE_STALE_MANDATE` (signed under a mandate version that is no longer current, or a revoked key). A replay with the same idempotency key is answered by A09's idempotency store with the original result; with a new idempotency key the signature no longer matches.
  - A valid signature within the caps satisfies only the "confirm with passkey" step: every money-moving action still passes the ordinary gates G01-G21, the ledger rules and maker-checker. Above the per-action cap on a confirmable action, or for any confirmable action when no key is registered or no valid signature is presented, the call returns `428 CONFIRMATION_REQUIRED` with a `confirmation_id` and creates nothing (the cap table in §5 is the rule; a daily or monthly cap is a hard `403 G22_LIMIT_EXCEEDED` that no confirmation lifts); the server stores the canonical payload in `agent_confirmation`. The human confirms through `POST /v1/agent-access/confirmations/{id}/confirm` (`requiresHuman: true`) with a fresh assertion (purpose `agent_confirmation`) over the stored payload hash; the confirmer must be the token's owner, and for a "both to sign" joint account the other signatory must also confirm within the confirmation's life. The agent polls `GET .../confirmations/{id}` or receives `agent.confirmation.resolved`; unconfirmed confirmations expire after 24 hours. A signing key can be revoked alone without revoking the token.
- **On-chain delegation (for A29).** A mandate that includes a wallet cell carries a `session_key_policy` (allowed contracts and functions, per-transaction and daily unit ceilings, expiry equal to or earlier than the mandate's) derived from the mandate's caps and hashed into the mandate hash. A29 registers the delegated session key on the passkey smart wallet under the same fresh assertion. Revocation reaches A29 through the synchronous revocation hook in §6, inside the revoking transaction, and also as the event `agent.mandate.revoked`. The owner key is never delegated; this node stores nothing on-chain.

**5. The G22 evaluator and the middleware**

- `evaluateG22(input)` in `packages/domain/src/agent-authority/g22.ts` is a pure, deterministic function over plain objects: the token, the current mandate version, the owner's live cell set and account state, the policy ceilings, the requested cell, the action's amount, units, vehicle and property, the day's and month's usage so far, the request context (ip, time, environment, kill-switch tiers, hold), and the checker context (whether the cell is an approve, ratify, veto or sign action; the request's maker identity set from A14 once it exists, or the fixture approval request's maker until then). It returns `{ pass, reason_codes[], missing_scope?, cap?, remaining? }` and never touches a database. Checks in order: token `active` and unexpired; owner account `active` (a dormant, locked or closed owner gives `AGENT_HELD` with reason `owner_inactive`); environment matches the route; no kill-switch tier on; IP allowed; inside a time window; mandate live; cell in scope and in `allowed_actions`; cell delegable; cell within the policy ceilings; owner still holds a role that grants the cell; vehicle or property allowed; per-action, daily and monthly caps hold; the cell is not a checker or custody-signer action (`G22_AGENT_NEVER_CHECKER`, regardless of scope); the request being acted on was not made by the same human or by any agent of that human (segregation of duties counts the agent as its human). Every failing check adds its code; the envelope carries all of them.
- **Cap refusals (normative; every spec that states a cap outcome follows this table).** A confirmable cell is one that A03's data flags `confirmable`: at least order placement (INV-02 order confirm), the resale-board buy and the withdrawal request (POR-05). Every other capped cell (for example a staff agent's mint or funding request, a sponsor agent's distribution preparation) is not confirmable.

  | Cap that fails | Confirmable cell | Any other cell |
  |---|---|---|
  | Per-action (cents or units) | `428 CONFIRMATION_REQUIRED` naming `cap: per_action`, with a `confirmation_id`; nothing is created; the person may confirm with a passkey (§4) | `403 G22_LIMIT_EXCEEDED`, `cap: per_action`, with the remaining amount |
  | Daily | `403 G22_LIMIT_EXCEEDED`, `cap: daily`, with the remaining cents or units; hard, no confirmation lifts it | the same |
  | Monthly | `403 G22_LIMIT_EXCEEDED`, `cap: monthly`, with the remaining amount; hard | the same |
  | No cap fails, but no signing key is registered or the call carries no valid `RealX-Mandate-Signature` | `428 CONFIRMATION_REQUIRED` | not applicable |

  A hard refusal wins: when a daily or monthly cap fails together with the per-action cap, the answer is `403 G22_LIMIT_EXCEEDED` naming the daily or monthly cap, never `428`, and `428` is returned only when every other G22 check passes. A confirmed action counts toward the day's and the month's totals, and the daily and monthly checks run again under the counter lock when it executes; if they fail then, it is refused `403 G22_LIMIT_EXCEEDED`. A `428` writes the same three rows as a refusal (reason code `CONFIRMATION_REQUIRED`, with the cap). A `428` that carries `documents_required` (a disclosure not covered by the standing consent) is the G12 path of A19 and A35, not a cap.
- **Order of agent refusals and the code that wins (normative).** (1) The §2 verification order (`401 TOKEN_*`, `423 AGENT_HELD`, `403 TOKEN_WRONG_ENVIRONMENT`); (2) the kill-switch tiers (`423 AGENTS_PAUSED`); (3) the rate limits (`429 RATE_LIMITED`); (4) **the route flag**: a route A11 marks `requiresHuman` (its A03 cell is `delegable: false` or `"counsel"`, or it is an approve, ratify, veto or sign action) refuses every agent principal with `403 AGNT_NOT_ALLOWED`. The envelope carries `gate: G22` and exactly one G22 cause in `reason_codes`, naming the cell: `G22_SCOPE_NON_DELEGABLE` (`false`), `G22_SCOPE_PENDING_COUNSEL` (`"counsel"`, with the CQ id) or `G22_AGENT_NEVER_CHECKER` (a checker, approver or signer cell). This refusal is a G22 decision and writes the same three rows as every other token request: one `gate_evaluation` for G22 with result `fail`, those reason codes, `token_id` and `on_behalf_of_id`; one `api_token_activity` row with error code `AGNT_NOT_ALLOWED`; and one `agent.access` audit event. So it appears in the person's activity like any other agent action. (5) The G22 evaluator above, on the route's cell and on every secondary cell the handler submits to G22: a delegable route whose request carries a choice that is itself a non-delegable, counsel-pending or checker cell, or a module's own fail-closed guard behind the route flag (for example A93's ballot guard). Only at step (5) are `G22_SCOPE_NON_DELEGABLE`, `G22_SCOPE_PENDING_COUNSEL` and `G22_AGENT_NEVER_CHECKER` the envelope `code`. A spec in which an agent calls a person-only route therefore expects `403 AGNT_NOT_ALLOWED` and may also assert the reason code; it never expects `G22_SCOPE_NON_DELEGABLE` or `G22_SCOPE_PENDING_COUNSEL` as the code of a `requiresHuman` route. A spec that names `G22_AGENT_NEVER_CHECKER` as the refusal of an agent on an approve, ratify, veto or sign route means this reason code (A82's wording). Issue-time refusals (A03's `SCOPE_NON_DELEGABLE` and `SCOPE_PENDING_COUNSEL` at token creation or widening) are unchanged. This node registers the verify step `check-agent-refusal-codes` through A01's script registration: it reads `packages/sdk/openapi.json` and fails when a test or published oracle file expects `G22_SCOPE_NON_DELEGABLE` or `G22_SCOPE_PENDING_COUNSEL` as the code of an operation marked `x-realx-requires-human`, or expects `AGNT_NOT_ALLOWED` from an operation that is not.
- **Middleware `agentAuth`** runs on every request that presents a bearer token, before A11's session logic (a request carrying both a session cookie and a bearer token is refused with `TOKEN_AMBIGUOUS_PRINCIPAL`). In A09's slots: `principal` (verification order of §2, set the RLS context to the owner's tenant and principal), `kill-switch` (the tiered check below), `rate-limit` (the mandate's limits as the injected policy, counted in `agent_rate_bucket` so both API processes share buckets), then, after `validation`, the G22 step: enforce the route's `x-realx-scope`, read token, mandate, owner roles, account state, policies, kill-switch tiers and counters inside the request transaction (never from a cache across requests), run `evaluateG22`, run the registered `afterEvaluate` hooks (§6), reserve counters, continue or refuse. The middleware runs identically for the MCP server (A104) because A104 calls the same routes with the same bearer token.
- **What each token-authenticated request writes, and when.** Exactly one `gate_evaluation` row for G22 (gate G22, inputs hash, result, reason codes, missing scope, `token_id`, `on_behalf_of_id`), exactly one `api_token_activity` row (operation id, outcome, error code, client label, ip, `gate_evaluation_id`) and exactly one audit event of type `agent.access` with `actor_type = AGNT`, `actor_id` = the agent principal, `token_id` and `on_behalf_of_id` = the human. Other audit events in the same request (the business handler's own events, token transitions) are allowed and expected; each carries `on_behalf_of_id` and `token_id` when an agent caused it. A19's G22 adapter does not store a second verdict: when it runs inside a request that already has a G22 evaluation for the same cell and inputs hash, it returns that verdict and its `gate_evaluation_id` (exposed as `ctx.agent.g22EvaluationId`). Timing:
  - Refused before the handler: the three rows are committed in their own short transaction, then the refusal is returned.
  - Passed: the gate evaluation id is generated before the handler; the three rows and the counter reservation are written in the business transaction and commit with it.
  - Passed, then the handler fails or rolls back: the business transaction (including the counter reservation) rolls back, and a separate short transaction writes the same `gate_evaluation_id` with `result = pass`, the activity row with outcome `failed_after_gate` and the handler's error code, and the `agent.access` audit event. A test forces a handler failure and asserts the three rows exist and the counter is unchanged.
- Refusals are specific, machine-readable and stable in the OpenAPI document, registered through A09's `registerErrors`: `401 TOKEN_INVALID | TOKEN_REVOKED | TOKEN_EXPIRED | TOKEN_PENDING`, `403 TOKEN_WRONG_ENVIRONMENT`, `403 TOKEN_AMBIGUOUS_PRINCIPAL`, `403 G22_SCOPE_MISSING` (names the cell), `403 G22_SCOPE_NON_DELEGABLE`, `403 G22_SCOPE_PENDING_COUNSEL`, `403 G22_POLICY_CEILING`, `403 G22_LIMIT_EXCEEDED` (names the cap, `per_action | daily | monthly`, and the remaining cents or units; `per_action` only on a cell that is not confirmable, per the cap table), `403 G22_OUTSIDE_TIME_WINDOW`, `403 G22_IP_NOT_ALLOWED`, `403 G22_VEHICLE_NOT_ALLOWED`, `403 G22_AGENT_NEVER_CHECKER`, `403 G22_OWNER_NO_LONGER_HOLDS_ROLE`, `403 MANDATE_REVOKED | MANDATE_EXPIRED`, `403 CONFIRMATION_SIGNATURE_INVALID | CONFIRMATION_SIGNATURE_EXPIRED | CONFIRMATION_SIGNATURE_STALE_MANDATE`, `423 AGENTS_PAUSED` (names the tier), `423 AGENT_HELD` (carries `hold_id`, `hold_class`, and `anomaly_id` when A101 placed it), `428 CONFIRMATION_REQUIRED`, `429 RATE_LIMITED` with `Retry-After` (A09's header). Issue-time codes: A03's `SCOPE_*`, `POLICY_CEILING`, `POLICY_ABOVE_PLATFORM`, `TOKEN_IDENTITY_NOT_VERIFIED`, `TOKEN_SIGNATORY_REQUIRED`, `TOKEN_COSIGN_EXPIRED`, `TOKEN_REVOKE_NOT_ALLOWED`, `TOKEN_ILLEGAL_TRANSITION`, `CONSENT_NOT_PERMITTED`. Every refusal writes its three rows too, so the person's activity list shows refusals as well as successes.
- Revocation fails closed within one request: after a revoke commits, the next call with that token on any API process is refused with `TOKEN_REVOKED`, because state is read from the database on every request. The same holds for mandate revocation, signing-key revocation, holds, and every kill-switch tier. Revoking a token also revokes its mandate and signing key, runs the revocation hooks (§6) in the same transaction and emits `agent.token.revoked`.
- **Kill-switch tiers, stated once.** This node owns the `KillSwitchProvider` interface (`state(scope: platform | tenant | owner_type | user, id) -> on | off`), the check in A09's `kill-switch` slot (which replaces A09's interim `agents.traffic` check and its lowercase `agents_paused` code; from then on every agent refusal for a switch is `423 AGENTS_PAUSED` with `tier` and writes the three rows above), and the `agent_switch` table (registered here per A04). The middleware asks every registered provider and refuses when any tier is off.
  - Platform tier: this node ships the interim provider, which reads A08's `isEnabled('agents.traffic')` and the platform row of `agent_switch`, and the interim `PlatformSwitchEffector` behind `POST /v1/agent-access/switches/platform` (CCO or SECO, reason, fresh hardware-key assertion, audited), which writes that `agent_switch` row and never `feature_flag`. A48 registers its effector (an A14 `SGL+R` request `agents.traffic.kill_switch`, then A21's `setFlag`) and its platform-tier provider; the route stays and ADM-35 keeps calling it.
  - Tenant, owner-type ("suspend agent access for one user type", ADM-35) and user tiers: A101's providers, writing `agent_switch` rows as their only writer for those scopes.
  - Per-token: a hold (`setTokenHold`, §6) or a revoke, not a switch.

## Node-specific challenges (node QA)

- **Owner gains rights, token does not.** An investor's agent holds `read` scopes only; the investor's classification is then upgraded to wholesale and the agent calls the fixture money route on the order cell. It must be refused with `G22_SCOPE_MISSING` naming the order cell, not admitted because the owner now could; the widening route must then refuse the same scope without a fresh assertion.
- **Owner loses rights, token loses them at once.** A staff member holding CFO creates a token, is moved to SUPP, and their agent calls the fixture decide route on the distribution-run approve cell with the still-active token: refused with `G22_OWNER_NO_LONGER_HOLDS_ROLE` and, independently, `G22_AGENT_NEVER_CHECKER`; both reason codes present in the envelope, one gate_evaluation row.
- **Cap race (money).** Two calls from one mandate reach the fixture money route within 10 ms on two processes, each for A$4,000 against a daily cap of A$5,000 with A$0 spent: exactly one passes and the other is refused `G22_LIMIT_EXCEEDED` with `cap: daily` and `remaining` equal to the amount actually left. Then with the downstream gate set to refuse `G07_HOLDER_CAP`, a passing call's reservation is released in the same transaction. Then the same race across 23:59:59.990 and 00:00:00.010 Sydney time on the last day of a month against a A$5,000 monthly cap already at A$4,000.
- **Signed payload replay (money).** The agent registers a signing key and signs a payload for the fixture money route; then (i) replays it with a different `Idempotency-Key`, (ii) sends it to the fixture withdrawal route, (iii) changes the amount by one cent, (iv) sends it after the owner narrows the mandate (new version). Expected: `CONFIRMATION_SIGNATURE_INVALID` for (i) to (iii), `CONFIRMATION_SIGNATURE_STALE_MANDATE` for (iv), and no second fixture action. Then a signed payload for A$1 above `per_action_cap_cents` returns `428 CONFIRMATION_REQUIRED`, and confirming it with the agent's own bearer token is refused because confirmation needs a passkey; on a "both to sign" joint account, one signatory's confirmation leaves it pending.
- **Revoke against an in-flight action (money, security).** A revoke and a mandated call on the fixture money route race on two API processes: whichever transaction commits second sees the other; a token revoked before the action's transaction commits cannot produce an action; the registered fixture revocation hook (standing in for A37's open-order cancel) runs inside the revoke transaction; and a revoked token's memoised verification on the other process must not admit one more call.
- **Wrong secret after a cached success (security).** A token verifies once on process 1; the same lookup with a different 32-character secret is sent to process 1 and process 2: `TOKEN_INVALID` on both, and a rotated token's old secret stops at the end of the grace window on both.
- **Agent as sponsor checker (compliance).** A fixture sponsor listing request is made by SP-OWN A. A's own agent tries to approve it on the fixture decide route, and separately the agent of a second owner B tries: the first is refused (maker's own agent), the second is refused too (an agent never approves, CQ-04); only B in person, with a fresh assertion, can approve.
- **Stale assertion on a widening (security).** The widening request carries a valid fresh assertion over the previous mandate hash, not the new one: refused `FRESH_ASSERTION_MISMATCH`; the mandate is unchanged and its previous version is still readable. Then the same request with an assertion from the owner's second passkey registered five minutes earlier must succeed, proving the check is on the payload hash, not on the credential.
- **Environment and prefix forgery (security).** A genuine `rx_sb_` token is presented to a live route: `TOKEN_WRONG_ENVIRONMENT`. A live token with its prefix edited to `rx_sb_` is presented to a sandbox route: `TOKEN_INVALID` (prefix mismatch at step 3). Both are refused before any business handler runs, both leave a gate_evaluation, and neither touches a live row.
- **AML hold without tipping off (compliance).** A fixture `investor.suspended` event arrives for an investor with two tokens: both are held in the event's transaction, the next call gets `423 AGENT_HELD` with the same neutral reason an ordinary account under review gets, and nothing in the envelope, activity row or introspection says AML.
- **Design fidelity of the data contract.** The status and environment strings returned by every endpoint are exactly the vocabulary above, so the A60 and A77 tone-pill mapping has no unknown value; every refusal carries `gate` and `reason_codes` so the design's explanatory banner renders it without client-side parsing; any new status string or bare 4xx fails the contract test.
