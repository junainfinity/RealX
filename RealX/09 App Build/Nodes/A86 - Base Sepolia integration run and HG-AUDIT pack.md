# A86 - Base Sepolia integration run and HG-AUDIT pack

**The first time the RealX contracts leave the laptop: the full on-chain suite (shared identity layer, one trust token through the T-REX factory under the V1 owner quorum, both AgentGateways, the owner multisig, the wallet factory with its recovery and session-key modules, and the paymaster) deployed to Base Sepolia at the same CREATE2 addresses as the local chain, using throwaway keys funded from a faucet. The run uses a real ERC-4337 bundler, carries out claim issuance, a mint bound to one approval ID, a smart-wallet recovery that waits out its real 48-hour timelock, the token-level recovery fallback and a forced transfer through the sandbox custody signers, and reconciles every step against the local register and bank sandbox with zero tolerance. Every leg uses the approval code and maker that A28's frozen catalogue names. The 84532 manifest is committed. Alongside the run, the node produces the audit pack for HG-AUDIT: every piece of custom Solidity with its tests, invariants, privileged functions, threat model and known limits, ready for two independent audit firms. No value moves. Redbelly testnet stays a script option until credentials exist (HG-ACCOUNTS), and mainnet stays behind HG-PROD after HG-AUDIT.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Chain. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-16 agent-hours (build, challenge and verify loops). **Elapsed time:** about 5 wall-clock days for the three sessions (the multisig and recovery timelocks on a public chain cannot be skipped, §3), plus the human lead time for HG-ACCOUNTS (bundler account and faucet funding) before session 1. The generated graph carries 10-16 h and reads the elapsed time from this line; the orchestration parks this node between sessions (below), so A88's start allows for it.

**Depends on:** [[A81 - End-to-end journeys- recovery, AML and planted breaks]], [[A27 - Chain adapter, deployment manifests and indexer]]
**Graph change (made 24 Sep 2026 through `Data\graph-revisions.json`):** this spec uses A23 (compose stack and its refusal tests), A36, A37 and A38 (offering, orders, allocation and `allocation.mint`), A48 (halts), A98 (the trustee's acks), A54 and A55 (PUB-04, PUB-08) and A76 (ADM-32), none of which is an ancestor in `final-graph.json`. Adding [[A79 - End-to-end journeys- investor money path]] and [[A80 - End-to-end journeys- sponsor and operations]] to A86's deps carries all of them. The graph also needs the elapsed-time field above (or A86 taken off A88's blocking path) and the 10-16 h estimate.
**Unlocks:** [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised]]

**Oracle rule:** this is not an oracle node (`oracle: no`). It adds no business logic, and nothing it moves has value: every mint, recovery and transfer runs through services that A28, A29, A31, A15 and A20 already proved as oracle nodes. The node QA still writes hidden challenge material from this note to `<workspace>\gauntlet\hidden\A86\` before the build starts. That material covers the escape attempts (mainnet chain id, RPC reporting the wrong chain id, mainnet host under a `base.org` name, Hardhat mnemonic on 84532), the gateway-bypass and replayed-ID calls from a stranger account, the wrong-maker and wrong-route requests, the early execution of a recovery, session-key abuse sent straight to the bundler, the clock-advance call, the audit-pack completeness probe (a planted `.sol` file and a planted `onlyOwner` function) and the secret scan patterns. The builder never reads that folder; the material is published into `app/` after the gate passes ([[App Gauntlet]] §2).

This note is not legal advice. Choosing the mainnet chain (Base or Redbelly), the audit firms and the go-live date are founder decisions behind HG-AUDIT and HG-PROD. Nothing in this node brings them closer except the evidence it hands to the humans who make those decisions.

## Build brief

**1. Preconditions, upstream exceptions and the testnet profile**

- The testnet run is an opt-in profile, never the default. It is on only when all of these hold: `CHAIN_ID=84532`; `CHAIN_RPC_URL` whose host is exactly `sepolia.base.org` or one of the Base Sepolia provider hosts named one by one in A07's `contracts/TOOLCHAIN.md` (no wildcard: `mainnet.base.org` and every other `*.base.org` host are refused); `TESTNET_OPT_IN=A86`; and deployer and broadcaster keys that are not derived from the Hardhat mnemonic. The variable names are A07's and A08's (`RUN_MODE`, `CHAIN_ID`, `CHAIN_RPC_URL`); the `.env.testnet` names are `TESTNET_DEPLOYER_KEY`, `TESTNET_BROADCASTER_KEY`, `TESTNET_STRANGER_KEY` and `BUNDLER_RPC_URL`, listed without values in `.env.testnet.example`. The standard compose stack (A23) never sets the opt-in, so A23's live refusal tests keep passing unchanged. The profile is `contracts/deploy/testnet/compose.testnet.yml`. It is a separate compose project (`realx-testnet`) with its own Postgres volume, so testnet rows never mix with the local development database. It runs the api, the worker and the sandbox panels against Base Sepolia. The `hardhat` service is used only for the local control run (§2).
- Upstream loops are requested before this node's build starts, following the same rule A12 used for A04.1. None is patched here, and each is in the Specify freeze list and the pass criteria.
  - **A07.1.** As written, A07's `hardhat.config.ts` guard refuses every non-loopback RPC under `RUN_MODE=local|test` with `CHAIN_RPC_NOT_LOCAL` and accepts any `*.base.org` host for 84532. The change admits exactly the four-condition case above, with the host pinned to `sepolia.base.org` plus the named provider hosts, and nothing else. The guard tests gain one positive case and five negative cases (opt-in missing, wrong host, `mainnet.base.org` with `CHAIN_ID=84532`, chain id 8453, Hardhat mnemonic key).
  - **A08.1.** A08's config admits `ADAPTER_BUNDLER=rpc4337` only under the same four conditions, and A08's no-production test is extended to assert exactly that exception. No vendor SDK is added. The `rpc4337` client (§4) speaks the standard ERC-4337 JSON-RPC methods over `fetch`, so A08's block list (`@pimlico/*`, `@alchemy/*`, `permissionless` with a live key) is untouched.
  - **A09.1.** The testnet profile runs under `RUN_MODE=local|test`, where A09 serves `POST /__test/clock/advance` with a `DbClock` offset. An advanced platform clock would open A28's off-chain 48 h forced-transfer and recovery timelocks early. The change makes the endpoint refuse whenever `CHAIN_ID != 31337` (proposed error `CLOCK_ADVANCE_CHAIN_NOT_LOCAL`, no offset written and no `clock.advanced` outbox event).
  - **A27.1.** A27 refuses `POST /sandbox-deploy` on 84532 with `SANDBOX_DEPLOY_LOCAL_ONLY`. The change adds a `designed → sandbox_deployed` transition **by reference** for a non-local row: it names a 31337 control row of the same vehicle, the same commit and the same test-report hash, and it is refused if any of the three differs. Without this loop the run would stop in session 1, after faucet funding.
  - **A28.1.** A28's precheck allows `unpause` only from SM-06 `paused`, while A24 §3 makes the go-live `issuing → active` a `HaltModule.activate` plus `unpause` under one approval (the token is still paused on-chain after the first mint). The change adds the go-live request to A28 (`activate` + `unpause`, the `unpause` row's `6E+Q`, CCO → SECO + CFO, allowed only from `issuing`). A24 also asks A28 to replace `recoveryAddress` in its `recovery` row with the A24 §3a sequence; this run uses the sequence (§3), so that row change must be merged too.
  - **A01.1.** A01's secrets scanner learns the `.env.testnet` file name and the `TESTNET_*_KEY` value pattern.
- Human steps come before session 1 (HG-ACCOUNTS; see Human gates touched). A human creates a free-tier bundler account with Pimlico or Alchemy for Base Sepolia and puts its endpoint in the gitignored `contracts/deploy/testnet/.env.testnet`. A human funds the throwaway addresses that `npm run testnet:keys` prints. Faucets ask for a sign-in or a CAPTCHA, and agents must not complete either. Until both steps are done, `testnet:preflight` stops with `TESTNET_HUMAN_STEP_PENDING`, naming the missing item. The orchestration then records the node as `parked` with the resume condition `humanApprovals["A86:HG-ACCOUNTS"]` (the user says in chat that both steps are done), never as failed or escalated, and the loop counter is kept ([[Build Orchestration]] §5).
- `npm run testnet:keys` generates three throwaway secp256k1 keys with a CSPRNG into `.env.testnet`: `deployer` (deploys the shared layer and funds the paymaster deposit), `broadcaster` (pays gas for the custody bundles that A27's `sendSignedBundle` submits) and `stranger` (used only by the node QA's challenges). The custody signer keys (V1 3-of-5, V2 2-of-3, V3 1-of-N, V4, V7, the EIP-712 attestation key, the RealX guardian) are A15's kms keystore keys, created fresh in the testnet database; they hold no value and do not change. **Every address that sends its own transaction on 84532 is funded, not only the three new keys**: the V4 identity agent (`registerIdentity`, `addClaim` and `deleteIdentity` check `msg.sender`), each V1 owner whose confirmation A25's multisig takes as a transaction rather than a signature, and the RealX guardian (`proposeOwner` and `executeRecovery` check `msg.sender`). If A25, A26 or A31 offer a relayer path for any of these, the Specify step names it and that sender drops off the list. `testnet:keys` prints every sender by role name and address with its per-session gas estimate. It prints no key. A nested `contracts/deploy/testnet/.gitignore` (inside the owned path) lists `.env.testnet` and `runs/*` except the final `report.json`; the root `.gitignore` is not edited. `npm run testnet:retire-keys` runs after the run. It sends leftover test ETH from each funded key back to one fixed address the founder names (or leaves it if no address is given), overwrites the file and writes a disposal record to the run report.
- `npm run testnet:preflight` runs before anything is signed, at the start of every session, and refuses on the first failure, with named errors. `TESTNET_CHAIN_ID_MISMATCH`: the RPC's `eth_chainId` is not 84532. `TESTNET_RPC_HOST_NOT_ALLOWED`: the host is not `sepolia.base.org` or a named provider host. `TESTNET_ENTRYPOINT_MISSING`: there is no EntryPoint v0.7 code at the canonical address. `TESTNET_CREATE2_PROXY_MISSING`: the deterministic deployment proxy that A07 uses is absent. `TESTNET_BUNDLER_UNSUPPORTED`: the bundler's `eth_supportedEntryPoints` does not list v0.7. `TESTNET_BALANCE_LOW`: for any sender on the list, that sender's gas estimate for the session multiplied by 1.5 is above its balance; the error names the role, the address and the shortfall. `TESTNET_PROPOSAL_EXPIRED` and `TESTNET_SESSION_TOO_LATE` (§3's upper bounds). `TESTNET_CLOCK_OFFSET_NONZERO`: A04's `system_clock` offset is not 0. `TESTNET_KEY_IS_HARDHAT`. `TESTNET_OPT_IN_MISSING`. Every signature uses EIP-155 with chain id 84532, so nothing signed here can be replayed on another chain.

**2. Local control run and deterministic addresses**

- `npm run testnet:control` deploys exactly the same scripts, commit and keystore to a fresh local Hardhat chain (31337) just before session 1. The scripts are A24's `deploy-shared.ts` and per-vehicle suite deploy, A25's `10-owner-multisig.ts` and `20-gateways.ts`, and A26's `deploy-wallet.ts`. The run records every address and code hash, and it runs the vehicle's sandbox deploy on 31337 so its token row reaches `sandbox_deployed` with a test report; that row is the one the 84532 row references under A27.1. On 84532 every shared-layer address (identity registry storage, trusted issuers, claim topics, claim issuer, identity factory, the five compliance modules, document anchor, suite inspector, T-REX factory, owner multisig, AgentGateway V2 and V3, smart-account factory, recovery module, session-key module, paymaster) must equal its 31337 address. The per-trust token, identity registry and compliance addresses must equal the counterfactual addresses computed from the vehicle id before deployment. An address that differs is a failure unless the difference is caused by a named chain-specific constructor argument listed in `docs/testnet/ADDRESSES.md`. None is expected.
- Every step checks before it acts. If code already exists at a CREATE2 address with the expected code hash, the step is skipped and recorded as `verified-existing`. If code exists with a different hash, the run stops with `TESTNET_ADDRESS_SQUATTED`. A re-run of `testnet:deploy` after success sends zero transactions.
- The 84532 manifest is written only through A27's `writeManifest()` into `packages/contracts/deployments/84532.json`. A26's own script writes `contracts/deploy/wallet/out/84532.wallet.json` (A26's path). Both are committed. `npm run manifest:check` with the testnet profile must be green against Base Sepolia from a fresh clone. The manifest carries addresses, deploy blocks, code hashes, ABI hashes, the deployer address and the commit. It carries no key, no bundler key and no RPC credential.

**3. The testnet offering and the three sessions (`npm run testnet:run -- --session 1|2|3`)**

On a public chain time cannot be moved, so the run follows real time. The platform clock (A09's injectable clock) stays at wall time for the whole run: under A09.1 the advance endpoint refuses on 84532, A27's `clock.advanced` subscription is a no-op on 84532, and the run measures it (A04's `system_clock` offset is 0 at the start and end of every session, and there are zero `clock.advanced` outbox events in the run window). Each session is resumable. **Between sessions the node is `parked`, not running:** at the end of session 1 and of session 2 the Build step writes the earliest start of the next session (from `state.json`, on chain time) and returns it as the node's `notBefore`; the orchestration records `state=parked` with that timestamp, and a later milestone run resumes the node only after it (the user passes the current time in `args.now`, because the Workflow script cannot read a clock). No agent call waits 48 hours. State lives in `contracts/deploy/testnet/runs/<runId>/state.json`, and every step records its route, its principal (HUMAN or AGNT and `on_behalf_of_id`), its approval ID and action code, its maker and checkers, its `CustodyOp` id, its UserOp or transaction hash, its block number and its gas. A step that was interrupted resumes from what the chain and the database show, never from memory. All actions go through the public API with the SDK, as the UI or an agent would. Staff approvals and custody signatures use A11's simulated hardware authenticator under each signer's own login. There are no direct database writes and no direct contract calls, except the deploy scripts in session 1, the node QA's stranger-account challenges and `eth_call` simulations that broadcast nothing.

- **The testnet offering fixture** (`contracts/deploy/testnet/fixtures/offering-84532.json`, owned here). It is created through the public routes of A34 and A36 as the seeded sponsor and the operator would (property record, offer terms, listing review, open), never by a seed write, on a new test vehicle `TSB01` with no legal effect. Terms: A$250.00 a unit; hard cap 200 units (A$50,000.00); soft cap 100 units (A$25,000.00); on-chain supply limit 200; fee 50 bps paid in AUD; `allocation_rule = first_come`; `allow_oversubscription = true`; `holder_cap_bps = 10000` for this three-holder test trust, with the on-chain `MaxBalance` set to match; no lock-in. Orders, in arrival order: INV-W 100 units (A$25,000.00 plus A$125.00 fee = A$25,125.00); INV-J 40 units (A$10,000.00 plus A$50.00 = A$10,050.00); INV-E 80 units (A$20,000.00 plus A$100.00 = A$20,100.00). At the hard cap, A37's first-come scale-back cuts INV-E's line to 60 units and refunds the 20 units' cents as A37's rule computes (expected A$5,025.00). Allocations: 100, 40 and 60 units, total 200.
- **Session windows (lower and upper bounds, on chain time).** Session 1 starts at T0. Session 2 starts no earlier than the later of T0 + the factory delay and INV-W's recovery `executableAt`, and no later than 24 h before the earliest expiry of any open proposal or attestation it will execute (A26: `expiresAt = executableAt + 7 days`; A25's V1 proposals and attestations carry their own expiry, read from the chain). Session 3 starts no earlier than the later of the two 48 h timelocks started in session 2, and no later than 24 h before the earliest expiry of the approvals and attestations it consumes. A session run early stops with `TESTNET_SESSION_TOO_EARLY` (with the earliest start); a session run too late stops with `TESTNET_SESSION_TOO_LATE`, and a proposal already past expiry stops with `TESTNET_PROPOSAL_EXPIRED`. `RUNBOOK.md` documents the re-propose path: the expired proposal is recorded as expired in the report, a **new** approval is requested with a new approval ID through the same catalogue row, and a new proposal is queued; an approval ID is never reused.

- **Session 1 (T0).**
  - Preflight, control run, then the shared layer, gateways, multisig, wallet stack and paymaster deposit, deployed by `deployer` through the deterministic proxy. Ownership of the gateways and the T-REX factory is handed to the V1 multisig, and the run verifies on-chain that `deployer` holds no role afterwards.
  - The `TSB01` token row is created as `designed` on 84532 and moves to `sandbox_deployed` by reference to the 31337 control row (A27.1), carrying its test report hash. It moves to `deploy_requested` with that test report and `audit_slot = placeholder`. Then A28's `deploy` operation runs: TOKO's agent token drafts it as maker (within TOKO's role), CCO and SECO approve in person under `6E+Q`, and the V1 3-of-5 proposal for `deployTREXSuite` (token, identity registry, compliance, modules, agents in one call) is queued with the factory-selector delay that A25's frozen config sets (72 h expected).
  - Three synthetic investors (INV-W individual, INV-J joint, INV-E company, all with approved sandbox KYC cases from A30 and no real personal data) get passkey smart wallets. Each wallet is counterfactual first and deployed on its first UserOp through the real bundler, sponsored by the paymaster.
  - Claim issuance runs through A31's V4 path: `registerIdentity` plus the `KYC_VERIFIED`, `SANCTIONS_CLEAR`, `WHOLESALE_AU` and `RESIDENCY_FIRB` claims for each wallet.
  - The offering fixture is created and opened, and the three orders are placed and funded by PayID receipts into the sandbox trust account (J04 steps 1-9 on the local sandboxes).
  - A smart-wallet recovery for INV-W is requested (A29, SM-13; the request revokes any session keys on INV-W's wallet). After KYCA re-verification and an approved `RecoveryRequest`, the RealX guardian's `proposeOwner` is queued on-chain. A second recovery, on INV-E's wallet, is proposed and then vetoed by the old passkey.
- **Session 2.**
  - The V1 proposal executes. The indexer (A27, 3 confirmations) records `deployed`, and `verifyConfigured` records `configured`, with every direct-read check named in the report (including `paused() == true`).
  - INV-W's recovery executes, at least 48 h after its proposal by chain time. The new passkey then signs a UserOp and the old one is refused. The run checks A26's rule that execution revoked every session key on the account (zero live keys, one `SessionKeyRevoked` per key).
  - J04 steps 10-13 run on the local services against the testnet-backed chain adapter, through A38's pipeline. The offering closes at the hard cap with INV-E's scaled-back line, escrow is released, and A38 raises the single `allocation.mint` approval: `6E+Q`, maker CAPM (or CAPM's agent token acting as maker within CAPM's role, if A38 allows it), checkers CFO and CCO in person. The trustee's register entries are written first through A18's registry sandbox under that approval ID (the TP-RE acknowledgement through A98). A28 then runs `batch_mint` per the locked allocation file under the same approval ID: two of the three V2 custody signers sign, neither of them the maker, and the call goes through AgentGateway V2. The token is still paused on-chain, so SM-06 moves `configured → issuing` on the first confirmed mint (A24: `mint` does not require unpaused). A20's targeted reconciliation must show supply = register = allocations = 200, with the bank leg clean.
  - Go-live (A28.1): CCO (or CCO's agent token as maker) requests `activate` plus `unpause` under the `unpause` row (`6E+Q`, SECO and CFO in person), signed by the V2 quorum under one approval ID. SM-06 moves `issuing → active`.
  - A planted registry drift of one unit on `TSB01` (A18's drift switch) must open a Sev1 break. Because the token is `active`, A48's recon-break halt is **on-chain**: `halt_set` (`HaltModule.halt` via V3, cause `RECON_BREAK`, under A20's break event id as A48 names it). When the drift is removed, a clean re-run must close the break; A48 then requests `halt_clear` (V2 `lift`) through A28 with its own approval ID, and the halt is `cleared` only when the lift is confirmed. This happens before any forced-transfer or recovery execution.

INV-E grants a mandate under A12 to an investor agent, and A29 registers two delegated session keys with the mandate's session-key policy: target = the `TSB01` token (manifest address), selector `approve(address,uint256)` only, per-action cap 5 units, daily cap 5 units. Key K1 expires at the mandate's end; key K2 expires 6 h after session 2's latest end, so its expiry falls between sessions 2 and 3. The allowed case is a K1 UserOp `approve(INV-W, 1 unit)` sent through A29's session-key path and the real bundler, sponsored by the paymaster; it moves no units, so the register and reconciliation are untouched. The refused cases are in the challenges; the revoke case revokes K1's mandate in A12 during session 2, and the expiry case uses K2 at the start of session 3.

The chain of people is A28's catalogue row: SUPP takes the intake, KYCA is maker with the re-verification record and the notice to INV-J's old contact channel, CCO gives `compliance_approval`, then CFO **and** the trustee give `checker_approval`. When that freeze is `confirmed`, SM-13 moves `checker_approval → old_wallet_frozen`, the notice is sent, and only then does the 48 h `timelock` start (A28 refuses otherwise with `TOP_OLD_WALLET_NOT_FROZEN`).
  - A forced transfer of 10 units from INV-E to INV-W under a sandbox court-order fixture: LEGL (or LEGL's agent token as maker) raises it, CCO gives `compliance_approval`, CFO and the trustee give `checker_approval`, the source wallet's freeze follows the same `checker_approval → old_wallet_frozen → timelock` order, and the 48 h timelock starts. The action code is `6E+Q`.
- **Session 3.**
  - Preflight, then K2's expiry case (challenges).
  - INV-J's token-level recovery executes, using the A24 §3a sequence (the vendored `recoveryAddress` is never called; it would revert on the shared storage, re-freeze the new wallet and delete the identity on every token): (1) the old wallet is already frozen from session 2; (2) A31 (V4) runs `registerIdentity(new, identity, country)` once, before anything is sent to the new wallet; (3) A29 and A31 add the new wallet as a management key on INV-J's ONCHAINID (`addKey(new, 1, 1)`) and remove the lost wallet's key, each with its own recorded transaction at an earlier block than step 4; (4) after the timelock, the V2 custody quorum executes `forcedTransfer(lost, new, balance)` and `setAddressFrozen(new, true)` under the recovery's single approval ID; (5) A31 runs `deleteIdentity(lost)` once the lost balance is 0. As A24 states, the new wallet ends frozen, so A28's `unfreeze` (MLRO → CCO, `4E+Q`, V2) then unfreezes it. The register is updated with A18's ack, and the targeted reconciliation is clean.
  - V3 `pause`: the pauser is CCO (or SECO or the on-call pauser) as `SGL+R`; the V3 signer is a different person from the pauser; a second person ratifies within 2 h (A13's `ratification.sgl_r` clock). SM-06 moves `active → paused`. - **Burn is not run on 84532.** `burn` and `burn_final` stay proven on 31337 by A28 and A80 (J08); the audit pack lists `burn` with its tests like every other privileged function.

**4. The real bundler client and the P-256 path**

- `contracts/deploy/testnet/bundler-rpc/` implements A29's `bundler` interface (`supportedEntryPoints`, `estimateUserOperationGas`, `sendUserOperation`, `getUserOperationByHash`, `getUserOperationReceipt`, `health`) over plain ERC-4337 JSON-RPC. It is registered as `rpc4337` in A08's registry only under the A08.1 exception. Before the run, A29's bundler conformance suite must pass against the live endpoint, and the result goes into the evidence. UserOp construction, the paymaster policy and receipts stay A29's. This client changes nothing but the transport.
- Base Sepolia has the RIP-7212 P-256 precompile. The run records which verification path A26's selection logic took on 84532 (precompile) and on 31337 (Solidity fallback). It also records the validation gas per UserOp on each chain, so the audit pack can state which path each environment uses.

**5. The HG-AUDIT pack (`<workspace>\app\docs\audit-pack\`)**

- `npm run audit-pack:build` builds the pack from source, test output and evidence. It never uses hand-typed figures. `npm run audit-pack:check` runs inside `npm run verify` and fails when the pack is stale or incomplete.
- `INVENTORY.md` and `inventory.json` cover one entry per custom contract. The set must equal every `.sol` file under `contracts/src/`. The expected set is: AgentGateway (the V2 and V3 instances), RealXOwnerMultisig, HolderCountModule, LockInModule, HaltModule, RuleHash, RealXClaimIssuer, DocumentAnchor, SuiteInspector, the smart account and its P-256 wrapper, SmartAccountFactory, RecoveryModule, SessionKeyModule, RealXPaymaster and its sponsorship policy, and any RealX equivalent of a vendored module that A24 had to write. Each entry records:
  - path, SLOC (comments and blank lines excluded) and sha256;
  - parents and imports, marked vendored T-REX, OpenZeppelin or custom;
  - storage layout and whether the contract can be upgraded;
  - every external and public state-changing function, with its access control. For privileged functions it also gives the vault (V1-V7), the approval code (`4E`, `4E+Q`, `6E`, `6E+Q`, `SGL+R`, `AUTO`) read from A28's catalogue, and the timelock. This list is generated from the ABI and a source scan, so a new `onlyOwner` function cannot be missed;
