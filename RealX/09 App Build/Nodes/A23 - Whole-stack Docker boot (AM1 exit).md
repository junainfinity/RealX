# A23 - Whole-stack Docker boot (AM1 exit)

**One compose profile under `infra/stack` that boots Postgres, the API, the worker, the Hardhat chain, the sandbox panels (bank, identity, registry, custody signer and every other registered sandbox), the MCP server and an OpenTelemetry collector stub with a single command on Windows 11 Docker Desktop, then migrates, seeds the design dataset, deploys the T-REX reference suite to the local chain, generates the no-value sandbox keys on first run and prints a health report; it is the AM1 exit check that the risk core built in AM1 runs as one system, and it surfaces toolchain drift (Node 24 in containers, Hardhat 2 vs 3, T-REX compile on Linux, Playwright in Docker) about forty nodes before the investor preview.**

**Build status:** not started. **Milestone:** AM1 (Money, register, approvals and agent-access core). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 5-8 agent-hours (build, challenge and verify loops).

**Depends on:** [[A06 - Seed data and scenario simulator]], [[A07 - Local chain and contracts toolchain (Hardhat, T-REX vendored)]], [[A10 - Append-only hash-chained audit log]], [[A15 - Custody sandbox adapter and policy engine P1-P10]], [[A17 - Bank rail sandbox adapter (NPP-PayID-PayTo) and receipt matching]], [[A18 - Unit register (legal record) and registry sandbox adapter]], [[A22 - Identity-DVS and sanctions sandbox adapters]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]], [[A20 - Three-way reconciliation engine with zero tolerance]], [[A13 - Alerts and SLA-clocks service]], [[A21 - Licences, feature flags and licence perimeter (G21)]], [[A104 - MCP server generated from the OpenAPI document]]
**Unlocks:** [[A49 - Money-path smoke through the SDK (AM3 exit and founder checkpoint)]], [[A61 - Docker Desktop preview of the investor app (AM5 exit)]]

**Oracle rule:** this node has no hidden oracle (`oracle: no`); no money, supply or holdings move here, and every business behaviour it exercises is owned and oracle-tested by a dependency (A10, A12, A15, A17, A18). The node QA still writes its Challenge material to `<workspace>\gauntlet\hidden\A23\` before the build starts, from this note alone: the override probes (live adapter selector, mainnet RPC, mainnet chain id, `RUN_MODE=production`, and mainnet RPC with the testnet chain id and opt-in), the crash-loop and behind-migration plants, the three-boot determinism diff script, the key-material scan patterns, the token and MCP smoke expectations and the expected outcome of each. The builder never reads that folder; the material is published into `app/` only after the gate passes ([[App Gauntlet]] §2).

## Build brief

This node writes no product behaviour. It composes what AM0 and AM1 built into one stack that a person (or the orchestrator) starts with one command, and it proves the milestone exit condition stated in the [[App Build Plan]]: the whole stack boots green three times in a row, restarts green on kept volumes, the audit chain verifies, a token-authenticated call works and a revoked one fails, the MCP catalogue matches the OpenAPI document under A104's exclusion rules, and nothing live or mainnet can be selected. Every bullet below is testable from a fresh clone with Docker Desktop running.

**Compose profile (`<workspace>\app\infra\stack\`)**
- `infra/stack/compose.yml` is the compose project `realx` (the same project name as A01's base file, so only one Postgres ever runs). It uses `include:` for the fragments other nodes own and never copies or redefines them: `infra/base/compose.yml` (A01, `postgres`), `infra/chain/compose.chain.yml` (A07, `chain`), `services/api/compose.api.yml` and `services/worker/compose.worker.yml` (A09, `api`, `worker`) and `packages/mcp/compose.mcp.yml` (A104, `mcp`, command `realx-mcp http`, `REALX_API_URL=http://api:4000`). A23 never declares a service that an included fragment declares (Compose refuses a duplicate service). Stack-specific settings for included services (the `depends_on` conditions, `restart: "no"`, the 127.0.0.1 port bindings, the per-service `DATABASE_URL`, the volume mounts and the MCP listen address) go in the A23-owned merge file `infra/stack/compose.stack.yml`, passed as the second `-f` file after `compose.yml`, following A09's several-`-f` pattern. Every `stack:*` script passes both files; Specify confirms on the pinned Docker Compose version that a second `-f` file merges onto services loaded through `include:`, and if it does not, the builder escalates rather than copying a fragment.
- Services this node owns (declared in `compose.yml`): `migrate` (one-shot, runs A04's `db:migrate` and exits 0 only at head), `kms-init` (one-shot, below), `seed` (one-shot, below), `deploy` (one-shot, runs A07's upstream T-REX deployment fixture plus the EntryPoint v0.7 check against `chain` and writes the addresses to the run-state volume), `sandbox-panel` (below), `otel-collector` (below), `smoke` (one-shot, profile `smoke`, runs the token and MCP smoke inside the compose network) and, under the `tools` profile only, `playwright` (below). Profiles: `core` (postgres, migrate, kms-init, seed, chain, deploy, api, worker), `sandbox` (sandbox-panel, mcp), `otel` (otel-collector), `smoke` (smoke), `tools` (playwright). The default command starts `core`, `sandbox` and `otel`.
- `seed` runs A06's `npm run seed` followed by `npm run seed:verify` only on a fresh database (no seed-owned rows after `migrate`). On success it writes the seed marker `seed-marker.json` to the `realx_state` volume: A06's manifest fields (`seed`, `asOf`, `schemaVersion`, `scenario`, `contentHash`), the seed's audit row count N, and the hash of audit event #N (the seed head hash). On a database that already holds seed-owned rows it does not re-run `seed:verify` (after any smoke or downstream use the database legitimately holds events later than `AS_OF`, and the audit table is append-only, so a reseed can never restore the seed state). Instead it checks the marker: the manifest fields equal A06's current manifest, the migration head equals the marker's `schemaVersion`, the database holds at least N audit events, and audit event #N hashes to the marker's seed head hash. If all hold it prints `SEED_PRESENT` and exits 0 without writing; otherwise it exits 1 with `SEED_STALE`, naming the field that differs and telling the person to run `stack:reset`. If A06 exposes its manifest only after a write, the need for a read-only manifest export is raised as an A06.x follow-up loop, never worked around by reseeding.
- Start order is enforced with `depends_on` conditions, not sleeps: `postgres` healthy → `migrate` completed → `kms-init` completed → `seed` completed → `chain` healthy → `deploy` completed → `api` healthy (`/readyz`) → `worker` healthy (`/readyz` on its own port) → `mcp` healthy → `sandbox-panel` healthy. The one-shot services have `restart: "no"`; the long-running ones have `restart: "no"` in this profile on purpose, so a crash is visible as a stopped container rather than hidden by a restart loop (A61 and the launch profile may choose otherwise).
- Every image is pinned by digest in `infra/stack/images.lock.json` (postgres 17, `node:24` slim for api, worker, chain, mcp, panel and the one-shot services, the OpenTelemetry collector, the Playwright image with a Chromium matching A01's pinned Playwright version) and the file names the date each digest was recorded. A verify check fails if a compose file references an image tag that is not in the lock file.

**Configuration (`infra/stack/.env.example`)**
- `infra/stack/.env.example` (committed, local-only values) is copied to `infra/stack/.env` (gitignored) on first run. Nothing in this folder is a secret; A08's `packages/config` validates the environment inside each container and A01's secrets scanner covers the folder. It holds:
  - Run and phase: `RUN_MODE=local`, `PHASE=P1`, `CLOCK_AS_OF=2026-09-23T10:30:00+10:00` (A08's core variable for the injected clock's start, set to A06's `AS_OF`; A06's `packages/db/seed/as-of.ts` stays the single source and a static test asserts the two are equal), `TESTNET_OPT_IN` absent.
  - Chain: `CHAIN_ID=31337`, `CHAIN_RPC_URL=http://chain:8545`.
  - Adapters: every `ADAPTER_<NAME>=sandbox` for every name in A08's manifests (custody, bank, registry, identity, sanctions, kms, storage, chain and any other registered), `ADAPTER_HEALTH_TIMEOUT_MS` and `ADAPTER_HEALTH_DEGRADED_MS` at A08's defaults.
  - Database: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` (A01's base Postgres, local-only values), and `DATABASE_URL`, set per service in `compose.stack.yml` to the A04 role that service uses (migrate and seed: the migration owner; api: `realx_app`; worker: `realx_worker`; the report's read-only queries: `realx_readonly`).
  - Sandbox storage and keys: `STORAGE_SANDBOX_ROOT=/var/lib/realx/sandbox`, `STORAGE_MAX_OBJECT_BYTES` at A08's default, `KMS_SANDBOX_MASTER_KEY_FILE=/var/lib/realx/kms/dev-master.key` (inside the `realx_kms` volume, never under `app/`), `KMS_SANDBOX_CREATE_MASTER=false` (overridden to `true` for `kms-init` only).
  - MCP: `REALX_API_URL=http://api:4000`, `MCP_ALLOWED_ORIGINS` empty (A104's default), and the MCP listen address `0.0.0.0` inside the container (see ports).
  - Telemetry: `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`.
  - Host ports: `PGPORT` 5432, `API_PORT` 4000, `WORKER_HEALTH_PORT` 4001, `CHAIN_PORT` 8545, `MCP_PORT` 4010, `PANEL_PORT` 4020, `OTEL_HEALTH_PORT` 13133.
  - A static test diffs `.env.example` against the variable list generated from A08's merged config schema (all sections) and fails on any required variable that is missing.
- Ports: every published port is written `127.0.0.1:${PORT}:<container port>`, never a bare port, so the sandbox panel, the `/sandbox/*` money triggers, the `/__test/*` routes, the chain RPC and MCP HTTP are never reachable from the LAN. Inside its container every process listens on `0.0.0.0` (a process bound to `127.0.0.1` inside a container is unreachable through a published port); for `mcp` this is set in `compose.stack.yml`, and if A104's server has no listen-address setting that is an A104.x follow-up loop. A check on the resolved `docker compose config` fails on any published port whose host IP is not `127.0.0.1`.
- Named volumes only, never bind mounts into `app/` for data:

| Volume | Mounted in | Path in container | Holds |
|---|---|---|---|
| `realx_pg` | postgres | `PGDATA` | the database |
| `realx_kms` | kms-init (read-write); seed, api, worker (read-only) | `/var/lib/realx/kms` | A08's kms sandbox master key file only |
| `realx_sandbox` | seed, api, worker (read-write) | `/var/lib/realx/sandbox` (`STORAGE_SANDBOX_ROOT`) | A08's kms keystore (`partitions/<p>/kms/`), storage objects and per-adapter sandbox files |
| `realx_seed_local` | seed (read-write), smoke (read-only) | `packages/db/seed/.local` | A06's gitignored `credentials.json` (sandbox persona passkeys and token plaintexts, no value) |
| `realx_chain` | chain | Hardhat's working folder | nothing persistent; the chain is recreated every boot by design |
| `realx_state` | deploy, seed, smoke (read-write) | `/var/lib/realx/state` | deploy addresses, seed marker, boot report, collector file export |

- The master key is created by `kms-init` only: a one-shot that loads A08's kms sandbox with `KMS_SANDBOX_CREATE_MASTER=true`, creates `dev-master.key` in `realx_kms` if it is absent, prints `master: created` or `master: present` (never the key) and exits 0. Every other service runs with `KMS_SANDBOX_CREATE_MASTER=false`, so a missing master key fails fast with A08's `MASTER_KEY_MISSING`. A08's kms section names a docker secret `realx_kms_master` for compose; a Compose file secret is a host bind mount, which this node forbids for data, so the key lives in the `realx_kms` volume instead and A08 aligns its wording at its next Specify. A15's signer keys are created on first use through `kms.createKey` into `realx_sandbox`; they are random, never derived from a fixed seed.
- Docker Desktop on Windows with the WSL2 backend is the target; the README states that NTFS bind mounts for Postgres are unsupported and the check refuses to start if `PGDATA` is a bind mount.

**Commands**
- Registered under A01's script-registration convention (`npm run scripts:sync`, never a hand edit of the root `package.json`): `stack:up` (copy `.env` if missing, `docker compose up --wait` for the default profiles, then `stack:check`), `stack:check` (the health report below; exits non-zero on the first red line), `stack:smoke` (runs the `smoke` one-shot, the chain control smoke and, with `--tools`, the Playwright smoke), `stack:down` (stop, keep volumes), `stack:reset` (`down -v`, so keys and data regenerate), `stack:logs`, `stack:soak <n>` (n cycles of reset, up, check, smoke, down with a diff between cycles, then one final up, check, down, up, check on the kept volumes of the last cycle), `verify:stack` (= `stack:reset`, `stack:up`, `stack:smoke`, `stack:down`, `stack:up` on the kept volumes, `stack:check`, `stack:down`, plus the live refusal tests; it needs Docker Desktop and is what the gauntlet runs; `npm run verify` stays Docker-free and only runs this node's static checks).
- All scripts are TypeScript run with `tsx` (no bash-only steps), work identically in PowerShell and Git Bash, and every file in `infra/stack/` is LF under A01's `.gitattributes`.

**Health report (`stack:check`)**
- Prints one line per service (name, container state, restart count from `docker inspect`, health, latency, version) and then the stack-level checks: `api` `/readyz` (Postgres reachable, migrations at A04's journal head, clock mode `DbClock`, outbox relay lag under 60 s, adapter registry loaded with no live adapter), `worker` `/readyz` (pg-boss started, scheduler tick alive), `api` `/v1/meta` (run mode `local`, phase `P1`, flag snapshot with every P2 and P3 flag off and `agents.traffic` on, chain id 31337), `chain` `eth_chainId` = `0x7a69` and account 0 = `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`, EntryPoint code present at `0x0000000071727De22E5E9d8BAf0edAc6f37da032`, the T-REX deploy addresses from the run-state volume with `totalSupply` = 1 on the fixture token (A07's smoke result), `otel-collector` health on 13133, and the token-free MCP and sandbox-panel checks below.
- MCP, token-free part (the token-bearing part is in the smoke, because creating a token needs a person's passkey step-up):
  - Using `loadCatalogue()` from `@realx/mcp/catalogue`, the operation ids in `catalogue.json` plus those in `excluded.json` equal the operation ids in `packages/sdk/openapi.json`, with no id appearing twice.
  - `catalogue.meta.json` `generated_from_openapi_sha256` equals `GET /v1/meta` `openapi_sha256` (the `openapi_sha256` field is A09's follow-up loop A09.1 requested by A104; until it lands this row is red, not skipped), and `mcp` `/readyz` is 200.
  - A request to `mcp` `/mcp` with no `Authorization` header gets HTTP 401 with `WWW-Authenticate: Bearer` and `MCP_TOKEN_MISSING`.
  - An empty `catalogue.json` is red.
- Sandbox panel: the panel serves one page per entry of A08's `sandboxControls()` for the default partition; that set includes at least `bank`, `identity`, `sanctions`, `registry`, `custody` and `kms` (storage and any other registered sandbox appear too), and every entry's `AdapterHealth` reports `implementation = sandbox`.
- Restart count must be 0 for every service and every one-shot service must have exited 0; a container that is "healthy" but has restarted is reported red (a crash loop is a failure, not a recovery).
- Audit chain: runs A10's `npm run audit:verify` against the compose Postgres. It must report `verified`, with an event count greater than or equal to the seed marker's N, and audit event #N must hash to the marker's seed head hash. On a fresh volume (the boot that wrote the marker) the count must equal exactly N plus the boot-time events listed in `infra/stack/boot-events.json` (event type and expected count per type, for example any event A15 or A12 writes at first start; the list is empty unless a dependency's spec names such an event, and any unlisted event before the smoke is red). The head hash is written into the report; any `AUDIT_CHAIN_BROKEN` is red.
- Sandbox keys: on a fresh `realx_kms` and `realx_sandbox` the report shows `keys: generated` with the public keys and key refs of A15's V1-V3 signer slots, V4, V7 and the attestation key, and the count equals the signer slots the seed's vault rows declare plus V4, V7 and the attestation key; on a boot with both volumes kept it shows `keys: reused` with identical public keys and key refs. Keys differ after every `stack:reset` because they are random. Private key material never appears in the report, in `docker compose logs`, in `evidence/` or anywhere under `app/`; the check greps its own output for A01's key patterns before printing.
- Reconciliation at boot (the AM1 goal names three-way reconciliation): after seed and deploy, the check triggers one on-demand reconciliation cycle through A20's run interface (the operation named from `openapi.json` at Specify) for every seeded trust and account, and requires a clean result: register = chain = bank for each, zero open breaks, and no resale halt raised by the run. A break fails the check by name (`RECON_BREAK_AT_BOOT`) with the trust and the three figures. A12.1 (approval-backed token routes) must also have passed before this gate, so the booted stack serves the full token surface that ADM-35 and the AM3 nodes use; it is a graph dependency of this node.
- No money is created by booting: the sum of A17 `state()` balances on the three client-money accounts (`client-money-wallets`, `offer-escrow`, `distributions`) equals A16's ledger client-money total and A06's manifest client-money figure to the cent; `realx-operating` (flagged `not_client_money`) equals its seeded balance; and no bank sandbox line exists dated after the seed. The boot never triggers a sandbox scenario. A06's `seed:verify` passes inside the `seed` service on every fresh boot.
- The report is written as JSON to the `realx_state` volume and copied to `infra/stack/.run/report.json` (gitignored); the last green report of the gate run is copied into `evidence/A23.json`.

**Smoke (`stack:smoke`)**
- The token and MCP smoke runs as the `smoke` one-shot container on the compose network, so it can read A06's persona credentials from `realx_seed_local` without a bind mount. It signs in as the seeded investor Alex Morgan with A11's software WebAuthn authenticator running in the smoke process, loaded with Alex's sandbox passkey from A06's `credentials.json`, against A11's normal login and step-up endpoints (no test-only sign-in route). The authenticator presents the relying-party origin configured in `packages/config`.
- Token REST pair: with a fresh assertion over the request hash, create token T1 (`rx_inv_`, named `stack-smoke-rest`) with the single read scope that A12's scope groups name for the activity list. From a fresh `packages/sdk` client with no cookie jar and only the bearer header, call `GET /v1/me/activity` and require `200` with at least one seeded row. Revoke T1 through `POST /v1/agent-access/tokens/{id}/revoke` (on Alex's session client), repeat the same bearer call from the cookie-free client and require `401` with code `TOKEN_REVOKED`, and not `TOKEN_INVALID`, which would mean the bearer was never accepted. Codes are compared against A09's error registry (A12's registered codes, upper case per A09), never typed as literal strings. One more probe: a request carrying both Alex's session cookie and a bearer token is refused with `TOKEN_AMBIGUOUS_PRINCIPAL`.
- Token rows: filtered by T1's `token_id` (the seed already holds agent events on Alex's behalf from `alex-portfolio-bot`), the two bearer calls left exactly two G22 `gate_evaluation` rows, exactly two `api_token_activity` rows and exactly two audit events with `actor_type = AGNT`, `token_id` = T1 and `on_behalf_of_id` = Alex Morgan. The rows are read by SQL as `realx_readonly` and cross-checked through A12's `GET /v1/agent-access/activity?token=<T1>` and A10's `GET /v1/me/activity` on Alex's session. The ambiguous-principal probe is counted separately. The audit chain still verifies afterwards.
- MCP with a token: create token T2 (`rx_inv_`, named `stack-smoke-mcp`) with the same single read scope. (a) `tools/list` through the running `mcp` HTTP service with T2 returns only the tools whose scope T2 covers, a non-empty subset of `catalogue.json`. (b) `tools/list` through `realx-mcp stdio`, started with `docker compose run --rm` on the `mcp` image with `REALX_MCP_LIST=all`, the token in `REALX_TOKEN` (never in argv) and `REALX_API_URL=http://api:4000`, returns exactly the tool names in `catalogue.json`, byte-identical entries. (c) No name returned by (a) or (b) appears in `excluded.json`; in particular no `agent_never_checker` (checker cell), `requires_human`, `non_delegable_scope`, `pending_counsel`, `service_only`, `test_only` or `stub` operation is a tool, so no `/sandbox/*`, `/__test/*` or stub route is listed. Revoke T2 at the end.
- The smoke revokes every token it created, so a finished boot holds no active smoke token.
- Chain control smoke: through A07's `control.ts` against the compose chain, turn automine off, send one transfer, confirm it is pending, `evm_mine`, confirm the receipt, turn automine on; proves test-controlled mining works through the stack, not only in A07's own test.
- Playwright-in-Docker smoke (`tools` profile): the `playwright` container runs `infra/stack/playwright/stack-smoke.ts`, which reuses A01's `scripts/playwright-smoke.ts` only by import or invocation (A01's file is not edited) and opens `http://api:4000/healthz` and `http://sandbox-panel:4020/`, then exits 0; this is the early warning for the e2e nodes (A49, A61, A8x) that Chromium runs inside Docker on this machine.

**Live-selector and mainnet refusal**
- The single expected chain allow-list, which A08's `CHAIN_ALLOW_LIST` and A07's `contracts/TOOLCHAIN.md` must both equal: `CHAIN_ID` in {31337, 84532}; for 31337 the RPC host is exactly one of `localhost`, `127.0.0.1`, `::1`, `chain`; for 84532 the host is exactly `sepolia.base.org` (plus any other exact host both lists name for Base Sepolia), accepted only with `TESTNET_OPT_IN=A86`; hosts are matched exactly, never by wildcard or suffix; `mainnet.base.org` is refused under every chain id, with or without the opt-in.
- Static test in `npm run verify` (`infra/stack/test/no-live.test.ts`): every `ADAPTER_*` value in `.env.example` and in every compose fragment is `sandbox`; `RUN_MODE` is `local`; `CHAIN_ID` is 31337 and `CHAIN_RPC_URL` is `http://chain:8545`; `CLOCK_AS_OF` equals A06's `AS_OF`; no compose file or override file under `infra/` names a chain id from {1, 8453, 151}, an RPC host that is not `chain` or loopback, or any vendor from A08's block list; A08's `CHAIN_ALLOW_LIST` and A07's `TOOLCHAIN.md` lists both equal the expected allow-list above; and both refuse `https://mainnet.base.org` with `CHAIN_ID=84532` and `TESTNET_OPT_IN=A86`.
- Live test in `verify:stack`: an override file sets, one at a time, `ADAPTER_BANK=monoova`, `CHAIN_RPC_URL=https://mainnet.base.org`, `CHAIN_ID=8453`, `RUN_MODE=production`, and the combination `CHAIN_ID=84532` + `CHAIN_RPC_URL=https://mainnet.base.org` + `TESTNET_OPT_IN=A86`. The test parses the resolved `docker compose config`, not the source files, so an override cannot sneak a value in. Expected outcome per override:
  - `ADAPTER_BANK=monoova` and `RUN_MODE=production`: every container that loads A08's `packages/config` (at least migrate, kms-init, seed, api and worker) exits 1 in under 1 s, naming the variable and the offending value. Because `migrate` refuses first, the test also runs `docker compose run --rm` for `api` and `worker` with the same override to confirm each refuses on its own. A08 defines no stable code for these two refusals, so the test asserts the variable name, the value and exit code 1; a stable code is requested from A08 as an A08.x follow-up loop, and the assertion tightens when it lands. For `RUN_MODE=production` the `chain` container also exits non-zero with A07's `RUN_MODE_NOT_ALLOWED`, and a direct probe runs the `deploy` container with the override and requires A07's guard (loaded by `hardhat.config.ts`) to refuse it; if Hardhat accepts it, escalate to A07.
  - `CHAIN_RPC_URL=https://mainnet.base.org`, `CHAIN_ID=8453` and the 84532 combination: every A08-loading container exits 1 with `CHAIN_RPC_NOT_LOCAL` or `CHAIN_ID_NOT_ALLOWED` as A08 defines them, and `chain` and `deploy` exit non-zero with A07's guard codes of the same names.
  - In every case: `api` `/readyz` never returns 200, no service that depends on the refusing one starts, and the report is red naming the refusing container and the variable. `postgres` (which ignores these variables) may be healthy, and so may `chain` for the adapter override.

## Node-specific challenges (node QA)

- *Live escape through the resolved config.* A compose override or an `environment:` line sets `ADAPTER_BANK=monoova` or `CHAIN_RPC_URL=https://mainnet.base.org`; the static test reads only the source files and passes, the api starts against the override. The live test must parse `docker compose config` output and the refusing containers must exit as stated per override; a real bank rail or a funded RPC reached from a build machine is a money incident.
- *Allow-list drift.* A07 accepts `*.base.org` while A08 matches exact hosts, so `mainnet.base.org` with `CHAIN_ID=84532` and the opt-in passes the Hardhat guard; the static test must compare both lists with the expected list and plant exactly that input.
- *Green by accident.* The worker crash-loops under `restart: always`, migrations are one behind head, or the seed check was skipped on a dirty volume, yet every container reports "healthy" and the report is green; the report must read restart counts, the migration journal head and the seed marker against the audit chain, not container health alone.
- *Restart breaks the stack.* After a smoke, `stack:up` on kept volumes runs `seed:verify`, meets events after `AS_OF` and fails, or tries to reseed over append-only audit rows; the seed service must use the marker and the audit check must accept the count above N while pinning event #N.
- *Revoked token passes, or fails for the wrong reason.* The second activity call returns `401 TOKEN_INVALID` because the bearer header was never accepted (the first call succeeded on the session cookie), so the smoke "passes" without ever exercising G22; or a memoised token status lets the revoked token through once on the worker-side process. The smoke must use a cookie-free client, assert `200` with seeded rows and then exactly `TOKEN_REVOKED`, with two G22 GateEvaluations, two `api_token_activity` rows and two audit events carrying `on_behalf_of` for T1.
- *Key material leaks or churns.* The kms master key is written into `app/infra/stack/` through a bind mount, appears in `docker compose logs` at first run, is created by more than one process, or is regenerated on every boot so the custody signer public keys stored in Postgres no longer match the keystore; or keys are derived from a fixed seed so they never change across resets. The kept-volume restart and the cross-reset comparison must catch both.
- *Money appears at boot.* A sandbox bank "receive payment" scenario or a registry instruction fires during seeding or deploy, so the client-money account balances, A16's ledger and A06's manifest differ before any journey has run; the no-money check must hold to the cent.
- *Non-deterministic boot.* Deploy addresses, seed row counts or the seed audit head hash differ between boots because the chain was not reset, seeding raced the API, or boot or smoke events were counted in the seed hash; three boots must diff to zero on every listed item.
- *MCP over-exposure.* The served catalogue lists `/sandbox/*`, `/__test/*`, stub, checker or person-only operations as tools, the catalogue is stale against the running API, or the MCP server answers a request with no token; tools plus exclusions must equal the operations, no listed name may appear in `excluded.json`, and a tokenless request must get `MCP_TOKEN_MISSING`.
- *LAN exposure.* A port is published as `4020:4020`, so the sandbox money triggers are reachable from another machine; the resolved-config check and the LAN probe must catch it.
- *Windows breakage.* CRLF in an entrypoint, Postgres data on an NTFS bind mount, `host.docker.internal` assumed inside a Linux container, or a hard-coded port that collides with the founder's other tools; the boot must fail early with `PORT_IN_USE` naming the variable, and the soak must pass on Docker Desktop with WSL2.
- *Design confusion.* The sandbox panel borrows the prototype's palette or components and a later screenshot comparison treats it as a product screen; the banner and the `packages/ui` import ban are checked, and the report's adapter rows must be A08's `AdapterHealth` shape so ADM-32 (A76) needs no translation.

## Pass criteria

- Each of the three soak cycles' reports shows a clean reconciliation run at boot (zero breaks, register = chain = bank for every seeded trust and account), and a planted one-unit register drift on a scratch volume fails the check with `RECON_BREAK_AT_BOOT`.
- On a fresh clone on Windows 11 Docker Desktop, `npm run stack:soak 3` completes three consecutive cycles of `stack:reset`, `stack:up`, `stack:check`, `stack:smoke`, `stack:down` with every service healthy, every one-shot exited 0, restart count 0 for every container, and each cycle reaching all-healthy within 6 minutes once images are present (the first cold-cache pull is timed and recorded but not limited).
- Restart on kept volumes: after the last cycle's smoke and `stack:down`, `stack:up` on the kept volumes is green, prints `keys: reused` with public keys identical to that cycle's and `SEED_PRESENT`, and `audit:verify` reports `verified` with event #N equal to the seed head hash.
- The three reports are identical on: the T-REX deploy addresses and the EntryPoint address, the seed row count per table, the seed marker and seed audit head hash, the MCP tool-name list hash and `catalogue_sha256`. On each fresh boot `audit:verify` reports `verified` with a count of exactly N plus the events in `boot-events.json`. Public keys differ across the three resets.
- MCP: tools plus exclusions equal the operation ids of `packages/sdk/openapi.json` with no duplicate; `generated_from_openapi_sha256` equals `/v1/meta` `openapi_sha256`; `tools/list` with `REALX_MCP_LIST=all` equals the names in `catalogue.json`; `tools/list` under the single-scope smoke token returns only that scope's tools; no listed name is in `excluded.json`; a tokenless request gets `401 MCP_TOKEN_MISSING`.
- Token smoke: `GET /v1/me/activity` under T1 from a cookie-free client returns `200` with at least one seeded row; after revocation the same call returns `401 TOKEN_REVOKED` (A09's registered code); for T1 exactly two G22 `gate_evaluation` rows, two `api_token_activity` rows and two audit events with `on_behalf_of_id` = the seeded investor exist; cookie plus bearer is refused with `TOKEN_AMBIGUOUS_PRINCIPAL`; the audit chain verifies afterwards; no active smoke token remains.
