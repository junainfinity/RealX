# A67 - Console: users, roles, access reviews and break-glass (ADM-37)

**ADM-37 in the operator console, built from design extension B: the staff user list with hardware-key status, last sign-in and dormancy; role grants as a `4E` request (SUPER maker, SECO checker, no self-grant, hard SoD conflicts refused with the rule cited, soft conflicts only under a time-boxed exception); immediate role revoke; a protective single-person suspend (`SGL+R`) that contains a compromised privileged account at once; the dormancy unlock and hardware-key re-enrolment desks; the quarterly access review with keep, reduce or remove per assignment and API tokens listed beside roles; the break-glass log (2-of-3 sealed credentials, at most 4 h, review within 5 business days); and the audit of every "view as tenant" grant. Every action on the page is an API operation that a staff member's agent can call under the same rules, except the acts that must be a person's.**

**Build status:** not started. **Milestone:** AM7 (Operator console). **Lane:** Operator console. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops) for the page alone: five tabs, five privileged flows plus revoke and suspend, a campaign workflow, an action manifest with its parity test, and state screenshots at two widths. The backend it needs is estimated separately in [[A106 - IAM admin API for ADM-37]] (12-16 h).

**Depends on:** [[A53 - Operator console shell, hardware-key sign-in and approval action pattern]], [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A51 - Design extension B- operator console screens not in the prototype]], [[A106 - IAM admin API for ADM-37]] (the backend of this page, AM3, an oracle node that passes its own gauntlet first), [[A06 - Seed data and scenario simulator]] with its seed loop A06.1 (§ Gauntlet, Specify). A66 (approvals inbox, ADM-31 audit screen) and A104 (MCP server) are deliberately **not** needed: this page approves through its own row `HardwareKeyConfirm`, checks ADM-31 deep links by their query only, and drives agents through the SDK; the inbox, the rendered audit page and the MCP catalogue are proved by A78 and A100.
**Unlocks:** [[A77 - Console- agent and API access (ADM-35)]], [[A78 - Operator journey J20 end to end in Docker (AM7 exit)]]

**Oracle rule:** this node has no hidden oracle (`oracle: no`); it holds no authority logic. The authority rules behind ADM-37 (quorum floor, reviewer self-exclusion, remove-to-revoke with token cells, unlock, re-enrol and suspend policies, the break-glass reviewer set) live in the IAM admin API node A106, which is an oracle node (`oracle: yes`, the node QA writes its hidden tests first). For this page the node QA still writes **hidden challenge fixtures (non-oracle)** to `<workspace>\gauntlet\hidden\A67\` before the build starts, as every `oracle: no` node in this plan does ([[App Gauntlet]] §2 must define this step for `oracle: no` nodes): Playwright specs against the running stack with the sandbox authenticator, a self-grant and SoD persona set, a break-glass drill script under the injectable clock, an access-review campaign fixture, its own crops of the extension-B ADM-37 frames, and an agent-parity table for every action on the page. The builder never reads that folder; the tests are published into `app/` only after the gate passes.

This node draws screens. It holds no business rule: who may grant, what conflicts, when an account goes dormant, how break-glass activates and who may review it are all decided in the API (A11 for identity, roles, SoD and break-glass; A106 for the ADM-37 administration routes; A14 for the maker-checker requests; A12 for tokens). The page shows what the API decided, always cites the rule the API names, and never lets a person believe access has changed before the API says so. Agent principals, their tokens and mandates are managed on ADM-35 ([[A77 - Console- agent and API access (ADM-35)]]); this page lists staff tokens only as rows in the access review and links there. This note is not legal advice.

RLS: `break_glass_session` rows and their review are visible only to CCO, SECO, CEO, the requester, the activators and TP-AUD (need to know); everything else in M25 follows A04's `app.platform_access` rules.
- Requested routes and effects (A106), using A11's `modules/auth` conventions:
  - `GET /iam/staff` and `GET /iam/staff/{id}` (cursor-paged, filters `principal_kind` in {`staff`, `partner` (once A98 exists), `service`, `agent`} for the pack's page 25.1 "users by type", with `service` and `agent` rows read-only here and linking to ADM-35 for agents; `role`, `state` in {`invited`, `active`, `dormant`, `locked`, `closed`}, a `suspended` flag for locked accounts carrying a suspension, `hardware_key` in {`enrolled`, `not_enrolled`, `single_key`}, `sod` in {`clear`, `exception`, `violation`}, `dormant_within_days`): the person (name, email masked by A04's `mask()`), roles with `granted_at`, `expires_at`, `granted_by`, `approval_id`, hardware keys (AAGUID label, registered, last used; never a credential id in full), last successful sign-in, days to dormancy, active SoD exceptions, the number of live API tokens they own (from A12's introspection, count only), and `allowed_actions[]` for the caller, so no button is decided in the client.
  - `POST /iam/roles/revoke` `{assignment_id, reason_code, note?, dry_run?}`: SUPER or SECO, immediate and protective, no checker (product-map M25 row "Revoke role: SUPER / SECO, no maker-checker"); in one transaction it ends the assignment, revokes every session of the person (A11 §3), fires A11's `iam.role.revoked` so A12 revokes the token cells that role granted, and re-resolves A14's `required_checkers[]` on open requests. Revoking a person's last role moves the account to `locked`. The dry-run (`dry_run: true`, no change) lists sessions, token cells, open requests where the person is a required checker, **and the person's custody signer slots (A15 `custody_signers`) and on-chain role memberships (token agent, pauser, owner-multisig signer through A25 and A24)**. The pack's action catalogue row "Revoke role -> remove signer/agent (M08/M09)" is honoured in two steps: the principal is excluded from signing and from any on-chain agent call **at once** (A15's `approveOp` refuses a principal whose role no longer covers the slot), and a signer-set change request is opened through A15's policy-change path and A25's multisig selector under their own policy (`6E+Q`), whose `APR-` id the revoke returns; the row shows "signer removal pending APR-…" until it completes.
    - **Quorum floor (defined).** After the revoke, both must hold, counting only principals in state `active` or `dormant` and never the subject: (i) at least 2 **distinct principals** each holding at least one of CCO, SECO or CEO (the sealed-credential holders; one person holding two of the roles counts once); (ii) for every live A14 policy row, the number of distinct eligible checkers for each checker role set is at least that row's `minCheckerSets` from A03's `approval-policies.ts`. Otherwise the revoke is refused with `IAM_QUORUM_FLOOR`, whose body names the rule broken (`breakglass_holders` with the remaining count, or the policy row id and role). A planned change goes through a grant first. Suspend (below) is the only path that may cross the floor.
  - `POST /iam/staff/{id}/suspend` `{reason_code, note}`: **protective single-person act, `SGL+R`** (the pack's page 25.1 row action "suspend"; A03's "Suspend account" row pattern). Actor: SECO or CCO, never the subject, never an agent (`requiresHuman`, fresh hardware-key assertion, purpose `staff_suspend`). In one transaction: account to `locked` with the suspension fields set (A11's account enum is unchanged; the page shows it as "suspended"); every session, API token (through A12's automatic-revocation path, event `iam.account.suspended`), active break-glass elevation and "view as tenant" grant of the person ended; the person excluded from custody signing at once and a signer-set change request opened as for revoke; the person removed as eligible checker from open requests. With reason `SUSPECTED_COMPROMISE` it **bypasses the quorum floor**, raises a Sev1 alert through A13 to CCO, SECO and CEO, and returns a break-glass hint (shown by the page as a Banner linking to the shell's break-glass request) when fewer than two uninvolved sealed-credential holders remain. Ratification: one of CCO, SECO or CEO other than the actor and the subject, within A03's `approval.ratifyWithinMinutes` window; if nobody qualifies, the named independent reviewer (below). An unratified suspend stays in force and escalates Sev1; a rejected ratification does not reinstate the account, which returns only through re-enrolment.
  - `POST /iam/staff/{id}/unlock` as an A14 request `iam.account.unlock` (A11's dormancy unlock policy: SECO maker, CCO or a second SECO checker, `4E`; the unlocked person and their agents are excluded from both sides). The effector moves `dormant -> active`, sets the dormancy clock from the unlock time, and writes `iam.account.unlocked`; the person must still sign in with their hardware key within 72 h or the account returns to `dormant`. A suspended (locked with a suspension) account cannot be unlocked; it needs re-enrolment.
  - `POST /iam/staff/{id}/re-enrol` as an A14 request `iam.staff.reenrol` (proposed: maker SECO, or CCO when the subject is a SECO; checker **CCO, a second SECO or CEO, never the subject** and never the maker; `4E`; reason code `KEY_LOST`, `KEY_DAMAGED`, `LEAVER_RETURN`, `SUSPECTED_COMPROMISE`): the effector revokes every login passkey and session of the person, revokes their API tokens through A12's automatic-revocation path (event `iam.staff.reenrolled`, treated like `auth.recovery.completed`), and issues a single-use enrolment invitation (24 h) that ADM-36 (A53) completes with a hardware-attested key. The person under re-enrolment and their agents cannot be maker or checker, so a compromised CCO is re-enrolled with a SECO maker and a second SECO or the CEO as checker.
  - **Role expiry and JIT elevation.** A time-boxed grant (`expires_at` set) **is** the pack's "just-in-time elevation (`iam.jit.granted`, 4E time-boxed)": it runs the same `iam.role.grant` path and A11 writes `iam.role.granted` with `expires_at`. Auto-expiry is A11's job `auth.role.expire` (every 5 min, event `iam.role.expired`); this page only shows expiry dates and the expired event.
  - `POST /iam/staff/invite` `{email, full_name, roles[], expires_at?}`: an invitation is a role grant (A11: "Staff are invited by a role grant"), so it creates the `invited` principal and one `iam.role.grant` request per role in one A14 request group; nothing is active until SECO approves and the person enrols a hardware key.
  - **SoD violation list and precedence.** Every SoD refusal (grant precheck, submit, invite, exception request) returns `violations[]`, one entry per broken rule with `code`, `rule_no`, `message` and `source_ref` from A03's `sod.ts`, and a top-level `code` chosen by fixed precedence: `SOD_SELF_GRANT` (rule 9) first, then `SOD_HARD_CONFLICT`, then `SOD_EXCEPTION_REQUIRED`. The page lists every entry, top code first. If A11's existing precheck returns a single code, A106 wraps it; A11's own contract change, if needed, is raised at Specify.
  - SoD exceptions: `GET /iam/sod-exceptions` and a create path as an A14 request `iam.sod_exception.grant` (maker: SUPER, or a SECO who is not the subject; checkers CCO and SECO as A11 states, which is `6E` in the frozen vocabulary, so a SECO maker needs a second SECO in the SECO checker set; the subject and their agents on neither side; confirmed at Specify against A03's policy rows), `expires_at` at most 90 days, a mandatory compensating-control text of at most 500 characters. Hard conflicts can never take an exception (`SOD_HARD_CONFLICT` is final).
  - Access reviews (the `access_review` table): `GET /iam/access-reviews`, `GET /iam/access-reviews/{id}` (items with cursor), `POST /iam/access-reviews/{id}/items/{item_id}/decide` `{decision: keep | reduce | remove, reason_code, reduce_to?}`, `POST /iam/access-reviews/{id}/sign-off` (fresh hardware-key assertion over the campaign's canonical result hash, purpose `access_review_signoff`), and the quarterly job `iam.access_review.open` registered with A46's scheduler (00:05 Sydney on the first business day of January, April, July and October; idempotent per quarter) that snapshots A11's review set into a campaign.
    - **Who decides and signs off (proposed A03 matrix cells, M25).** A campaign's `reviewer_role` is SECO: the job assigns it to the role, not a person, and any active SECO may decide items (`access_review.decide`, cell `A` for SECO). Items about a SECO holder (their roles, tokens and exceptions) are routed to CCO (`access_review.decide`, cell `A` for CCO, limited to routed items), and to CEO if the CCO is also a subject or no CCO is active. Nobody decides an item about themselves or their own tokens (`ACCESS_REVIEW_OWN_ITEM`). Sign-off (`access_review.signoff`, cell `A` for SECO only) is by any active SECO once every item is decided, including routed items; if the only SECO is also the only reviewer, sign-off is still theirs because their own items were decided by CCO or CEO. These cells are proposed as an A03 `matrix.ts` diff at Specify.
  - `GET /iam/break-glass` and `GET /iam/break-glass/{id}` (requester, runbook R1-R9, reason, the two activators, `activated_at`, `expires_at`, `closed_at` and why, count and deep link of the audit events carrying that `break_glass_id`, board-notice state and time, post-session notice state, review state, due date and eligible reviewers) and `POST /iam/break-glass/{id}/review` `{outcome: no_findings | findings_raised, findings, actions[]}` with a fresh hardware-key assertion (purpose `breakglass_review`).
    - **Reviewer set (proposed).** Any active holder of CCO, SECO or CEO who was neither the requester nor an activator of that session. Only if that set is empty (for example, all three took part) does the review fall to the named independent reviewer (a board delegate or TP-AUD, recorded as a governance question under HG-LEGAL). A wrong reviewer is refused with `BREAK_GLASS_REVIEWER_INVOLVED`.
    - **Board notice (produced here, not only read).** On A11's `iam.breakglass.board_notice` event (written at `iam.breakglass.activated`), A106 sends the notice through A43 to the board chair (recipient from settings) and records `board_notice_state = sent` and the time, or `failed` with a Sev2 alert through A13; on `iam.breakglass.closed` it sends a post-session notice to TP-AUD (the pack's X-AUD) with the actions count and records it. The notice wording is an HG-LEGAL item.
  - `GET /iam/view-as-tenant/grants` (cursor; filters staff, tenant, from, to, `active`): staff person, tenant, reason, started, extended, ended and why, request count under the grant, and a deep link to ADM-31 filtered by `acting_tenant_id` and `session_id`.
- If A106 cannot land before this node's Build step, the node waits; it does not mock the API in production code (fixtures exist only in tests). Every endpoint above carries `x-realx-scope` in M25, so it is in the OpenAPI document and `packages/sdk` from the moment A106 passes, and in A104's MCP catalogue once A104 generates it (checked by A100, not here).

- `ConsolePage` with `screen = "ADM-37"` and `designKey = "design-ext:ADM-37"`, eyebrow `ADM-37`, h1 "Users, roles and access reviews", subtitle "Who can do what in the console, and proof that someone checked." A `KpiGrid` of five tiles from one summary call (`GET /iam/staff/summary`, part of A106): staff users, hardware-key coverage (target 100 %; amber below 100, red if any active staff member has no enrolled key), dormant privileged accounts, access review completion for the current quarter (a `RaiseBar` with due date), break-glass sessions open or awaiting review. Counts come from the summary endpoint, never from a list page.
- Tabs, each a route so the URL is shareable and survives reload: `users` (default), `roles` (role catalogue and SoD), `reviews`, `break-glass`, `view-as`. The sidebar item "Users, roles and access" sits in extension B's Platform group; it and every tab are rendered only for principals whose `GET /iam/me` has `V` on M25 (SECO, SUPER, CCO, CEO by A03's matrix; TP-AUD read-only once A98 exists). Registers the badge source `access.attention` (dormant accounts awaiting unlock, grants awaiting SECO, reviews due within 5 business days, break-glass reviews due) and the search provider for `PRN-H-` staff ids and staff names (names only for principals with `V` on M25, never placed in the URL). A53's id-jump families do not yet include `PRN-`; until A53 adds it, `PRN-H-` ids resolve through this node's free-text provider.

**3. Users tab (the DataTable of extension B: Person / Roles / Hardware key / Last sign-in / Dormant / SoD)**

- `ConsoleTable` over `GET /iam/staff` with `FilterChip` groups for role, state, hardware key and SoD. Cells: person (name, `IdCell` with the `PRN-H-` id), roles as grey pills with an expiry suffix when `expires_at` is set, hardware key (`enrolled · 2 keys` green, `single key` amber, `not enrolled` red for active staff and grey for `invited`), last sign-in (`WhenCell`), dormant (`dormant` red pill; `in N days` amber when N ≤ 7; blank otherwise), SoD (`clear`, `exception to <date>` amber, `violation` red with the rule number). The last column is always a `StatusPill` as the design's DataTable rule says.
- Row detail (split view in the design's ApprovalList/Detail pattern): `KeyValueList` of the person, roles with who granted them and the `APR-` id, hardware keys, sessions (count and last device label from A11), API tokens count with a link to ADM-35 filtered to that owner, SoD exceptions, and the last 20 `iam.*` audit events for the person from A10 with `AgentMarker` on agent-made rows. Actions rendered only from `allowed_actions[]`: **Grant role**, **Revoke role**, **Suspend account**, **Unlock** (dormant only), **Re-enrol hardware key**, **Request SoD exception**.
- **Grant role** runs `PrivilegedActionFlow` with action code `iam.role.grant`: the form (grantee, role from A03's role list, optional `expires_at`, required for roles A03 flags as time-boxed, reason), then the API's precheck. A hard conflict comes back before submission and shows extension B's blocked state: a red `Banner` with the API's plain-English message and rule, for example "SUPER + TRSY is a hard conflict · SoD rule 3", with Submit absent. The text is the API's `sod_rule.message` and `source_ref`, never a string in this app; the frame's example "CFO + TOKO is a hard conflict" is rendered only if A03's data holds that pair, and otherwise is recorded as a DF finding for A51. `SOD_SELF_GRANT` (grantee or named checker is the maker) shows "You cannot grant a role to yourself or choose your own checker · SoD rule 9". A soft conflict shows `SOD_EXCEPTION_REQUIRED` with a "Request SoD exception" link that pre-fills the exception flow. When the API returns more than one entry in `violations[]`, the Banner lists every rule, top code first (for example a SUPER granting herself TRSY sees rule 9 and rule 3). The pending assignment then shows as an amber `pending_approval` row with the `APR-` id until SECO decides through the row's own `HardwareKeyConfirm` (the same request also appears in A66's inbox, which this node does not depend on); the modal's `not-eligible` state renders for the maker.
- **Revoke role**: a danger button, a confirm dialog naming the role, the person and the consequences the API lists in a dry-run response (sessions revoked, token cells removed, open requests where the person was a required checker, custody signer slots and on-chain roles to be removed), a mandatory reason code, then `POST /iam/roles/revoke`. After success a signer or on-chain role shows "signer removal pending APR-…" until A15/A25 complete it. `IAM_QUORUM_FLOOR` renders with the rule broken named (sealed-credential holders left, or the policy row and role). Success toasts only after the 2xx and reloads the row.
- **Suspend account** (protective, `SGL+R`): a danger button for SECO or CCO, never on the caller's own row; a dialog with the dry-run consequences, a reason code (`SUSPECTED_COMPROMISE`, `LEAVER`, `POLICY_BREACH`, `OTHER`) and a note, then `HardwareKeyConfirm` with purpose `staff_suspend`. The row turns red "suspended · ratification due {time}" with the ratifier set the API returns; a ratifier sees a **Ratify** slot through `PrivilegedActionFlow`. When the API returns the break-glass hint, a red Banner says so and links to the shell's break-glass request. An agent never sees the button.
- **Unlock** and **Re-enrol** run `PrivilegedActionFlow` with `iam.account.unlock` and `iam.staff.reenrol`. The row shows the pending request id; the dormant or suspended person's own session (they cannot sign in) and their agents never see an approve slot.
- Empty state: "No staff match these filters" (dashed box). A platform with no staff other than the caller shows "You are the only staff user. Grants need a second person as checker." with Grant role disabled by the API's `allowed_actions[]`.

**4. Roles tab (role catalogue, SoD rules and exceptions)**

- Read-only role catalogue from A03 through A11 (`GET /iam/roles`): role code, title, staff count, and the module × action grid (V/C/E/A/O/X) as a compact matrix for the selected role, plus the roles each role conflicts with and whether hard or soft. Editing a role's permissions is not on this page: the matrix is data changed through A03 and `policy.change`; the tab says so and links to ADM-30's policy view.
- SoD rules table (the ten from A11 plus the carried rows, with `source_ref`), current violations (should be zero; any row is red with the two principals and a link to their detail) and active exceptions with expiry countdown. An exception within 7 days of expiry is amber; an expired exception whose soft conflict still exists shows the red "violation" state and links to Revoke.

**5. Access reviews tab (quarterly recertification)**

- Campaign list (quarter, opened, due, reviewer, items, decided, removed, reduced, state `open | overdue | signed_off`) and the campaign detail: extension B's access-review card, one `CheckList` per person with a row per item (each role assignment, each staff API token from A12 shown as prefix, name, scope families and expiry, each active SoD exception, and each platform partner grant once A98 exists), three choices per row (keep, reduce, remove) and a mandatory reason code for reduce and remove, and a `RaiseBar` of items decided out of total with the due date in mono.
- Decisions are applied by the API, not by the page: `remove` on a role calls the revoke path inside the decide endpoint; `reduce` on a role becomes a revoke of the named role plus, if needed, a new `iam.role.grant` request; `reduce` or `remove` on a staff token calls A12's narrow or revoke route (A12 lets the approver role narrow and revoke staff tokens with a session only). The row shows the effect the API reports ("role removed", "token narrowed to read", "grant request APR-… opened").
- Reviewer rules shown from the API's answer, never computed here (the role set is in §1: SECO decides and signs off, CCO, or CEO as fallback, decides items about a SECO): a reviewer cannot decide items about themselves or their own tokens (those items show "reviewed by the CCO" or "reviewed by the CEO", as the API routed them); sign-off is refused while any item is undecided (`ACCESS_REVIEW_INCOMPLETE` names the count) and needs a hardware-key assertion over the campaign's result hash through `HardwareKeyConfirm` with purpose `access_review_signoff`. A campaign past its due date shows the red `overdue` pill; the A13 alert it raised (Sev3 to SECO, the research pack's "access recertification campaign" row) is linked. Whether unreviewed items should be suspended automatically after the due date is settled at Specify (proposed: no automatic removal; Sev3 at due, Sev2 to CCO at due plus 5 business days).
- Empty states: "No review open. The next one opens on {date}." and, inside a campaign, "Every item decided. Sign off with your security key."

**6. Break-glass tab (the log and the review; activation stays in the shell)**
