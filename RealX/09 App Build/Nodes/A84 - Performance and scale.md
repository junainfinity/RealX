# A84 - Performance and scale

**The proof that RealX still works when it is big: a simulator-generated platform of 100 trusts x 10,000 holders (1,000,000 register rows held by 50,000 investors, the same holders on the local chain, 5,000,000 audit events, a heavy investor with 50,000 transactions), on which the 00:00 register snapshot and the 02:00 three-way reconciliation finish inside their windows, the largest trust's distribution calculates, executes and closes with paid equal to approved, every long list pages on the server, the investor screens stay within budget at phone width, the API holds its p95 targets on two API processes under a mixed load and a token-driven agent burst, agent webhooks keep up, and the chain indexer catches up in bounded time; every miss becomes a fix item on the node that owns the slow code, never a patch here.**

**Build status:** not started. **Milestone:** AM8 (Journeys, hardening and launch). **Lane:** Quality. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 6-10 agent-hours (build, challenge and verify loops). This excludes wall time, which is modelled separately below.
**Wall time (excluded from agent-hours, run in the background):** one `perf:all` runs every scenario family once, with its own seed: six measured nights at real clock speed (about 1.5 hours each, and about 3 hours for the snapshot-overrun night), the month-end of up to 2 hours, the largest trust's distribution with three worker kills, a cold indexer run of up to 45 minutes plus the outage catch-up, S1-S5, the paging suite, the phone suite and the restore. That is about 15-18 hours per `perf:all`. The pass criteria need three `perf:all` runs (these three runs give the three samples per budget), plus a first-time chain generation of up to 2 hours, the audit-log load of up to 2 hours and the node QA's cold re-runs of about 4 hours. Total: about 50-60 wall-clock hours of measured runs. Each re-measure after a fix in another node re-runs only the affected family (typically 1-4 hours). The graph data must carry this as the node's wall time so the schedule models it (requested from the plan's graph data, not edited here).

**Depends on:** [[A79 - End-to-end journeys- investor money path]], [[A80 - End-to-end journeys- sponsor and operations]]
**Unlocks:** [[A88 - P1 full regression- 18 P1 journeys, three clean runs, every gate exercised]]

**Oracle rule:** this is not an oracle node (`oracle: no`): it moves no money of its own and owns no product rule, but it drives money, supply and agent authority at volume, so the node QA still writes hidden tests from this frozen spec to `<workspace>\gauntlet\hidden\A84\` before the build starts (its own copy of the budgets, the invariant probes that must hold under load, the planted slow paths described in the challenges below, an independent replay of A101's rule set for the S3 hold set, and an independent recomputation of the largest trust's payment file); the builder never reads that folder, and the tests are published into `app/` only after the gate passes ([[App Gauntlet]] §2).

What this node is for in one sentence: N12 ("performance of a long product") and N13 ("idempotent, replayable jobs") measured on the finished P1 stack at the scale the requirements name, with the D04 agent path held to the same budgets as the screens. It writes no product code and draws no screen. It owns a load harness, data generators that compose A06's simulator, budgets, measurement scripts and an evidence writer. Every number below that is not quoted from another node is a proposed budget, settled at Specify and recorded in `budgets.json`; tightening a budget is a spec edit, loosening one needs the user.

**Specify blockers (requested from other nodes, not edited here).** A84 cannot freeze until these exist in the named nodes' specs:
- **A01 (A01.x):** add `e2e/perf` (or `e2e/*`) to the npm workspace globs, so that `e2e/perf` is its own workspace `@realx/e2e-perf` (section 9). The graph data must record `app\e2e\perf\package.json` as owned by A84.
- **A08 (A08.x):** a `SANDBOX_LATENCY_PROFILE` config (section 8).
- **A12 (A12.x):** numeric limits on failed token verifications per lookup and per source IP, and the rows written for a wrong secret on a real lookup (section 7, S5).

## Build brief

**1. What this node reuses, and the rule that it patches nothing**

- The stack is A23's whole-stack Docker compose as extended through AM5-AM7 (A61's investor preview, A65's sponsor stack, A78's operator stack), started with production builds: `npm run build:release` for the three web apps (A52), the API and worker images of A09, Postgres 17, the Hardhat chain of A07, and every sandbox adapter of A08. No dev server, no hot reload and no source maps are measured.
- Data comes from A06's `packages/sim` through its public functions (`generate`, `load`, `emitFixtures`) and its `load` profile (100 trusts x 10,000 holders, 1,000,000 register rows). The extra volume this node needs (section 2) is generated by thin composers in `e2e/perf/data/` that call the same generators with larger counts. It is never written by hand-rolled SQL that skips A04's constraints, triggers or RLS. If a generator cannot produce a shape, that is a spec defect raised against A06 as a follow-up loop (A06.x), not a workaround here.
- Every request goes through `packages/sdk` (A09), `packages/mcp` (A104) or a Playwright browser. The only other entry points are A09's local clock endpoint (`POST /__test/clock/advance`, `RUN_MODE=local|test` only, forward only), A11's simulated authenticator for passkey steps, and A46's fixture webhook sink (`WEBHOOK_FIXTURE_SINK_URL`, local and test only).
- The jobs measured are other nodes' jobs, run unchanged: `register.snapshot` (A18), `recon.nightly`, `recon.targeted` and `preflight` (A20), `distributions.calculate`, `distributions.execute`, `distributions.retry` and the closure run (A40), `indexer.tail` (A27), the outbox relay (A09), A101's anomaly evaluator, A43's notification delivery and A46's `webhooks.dispatch` and `webhooks.retry`.
- **Findings become fix items on the owning node, never patches here.** When a budget is missed, this node writes a finding with the metric, the budget, the three measured values, the query plan or flame graph, a one-line reproduction command, and the owning node. The owning node is resolved from the hot code's path through A01's owned-paths map (`check-owned-paths.ts`), or from the route's module for API routes. The owning node runs a fix loop and this node re-measures. A84 may not edit any file outside `app\e2e\perf\` (plus the lockfile and generated root files that A01's owned-path check tolerates, section 9). Proposing an index, a batch size or a query rewrite inside the finding is encouraged; applying it is not.

**2. The perf environment and the data set (`profile: perf`)**

- `e2e/perf/compose.perf.yml` includes A23's compose file and adds:
  - a separate database name `realx_perf` (the baseline seed database is never touched), with `pg_stat_statements` and `auto_explain` enabled through the perf compose command line (settings per pass in section 5);
  - **two API replicas (`api-1`, `api-2`) and two worker replicas**, each API replica on its own base URL with no load balancer in between. The driver alternates base URLs request by request and writes the instance into its request log, so every multi-process invariant is observed per instance;
  - driver containers on compose networks whose subnets are the RFC 5737 documentation ranges that A101's `GeoIpResolver` fixture maps to seeded countries. This gives the S3 and S5 drivers distinct, known source IPs and countries without touching the API's trusted-proxy setting and without trusting `X-Forwarded-For`;
  - the Hardhat chain with a raised block gas limit for the load deploy;
  - fixed CPU and memory limits per container.
- The limits, the replica counts, the host CPU model, core count, RAM, disk type, Docker Desktop version and WSL2 settings are written into every evidence file, so results from two runs can be compared.
- The scripts refuse to start unless `RUN_MODE=local`, every API base URL resolves to `localhost` or a compose service name, and every A08 adapter reports `environment: sandbox` (N15). A non-local URL fails with `PERF_TARGET_NOT_LOCAL` before any request is sent.
- `npm run perf:data -- --seed realx-load` builds the data set deterministically (same seed gives the same content hash). On top of A06's `load` profile it contains:
  - **Population:** 50,000 investors across the seven investor sub-types (individual, joint, SMSF/company/trust, wholesale, sophisticated, retail, foreign), each holding in about 20 vehicles. Foreign investors hold only commercial vehicles (G06). Load Morgan holds in all 100. This gives 50,000 verified identities, 50,000 ONCHAINID identities, 50,000 passkey smart wallets and about 1,000,000 mint `Transfer` events. These counts are part of the data-set content hash.
  - **Trusts and holders:** 100 issued vehicles across the three seed sponsors plus 20 generated sponsor tenants. Each vehicle has 10,000 holders with one unit each (supply 10,000, so no holder passes the 5 % cap and G07 stays valid), a certified `RegisterVersion`, and residential and commercial types with valid G06 residency rules.
  - **The S2 vehicles `PERF-S2A` and `PERF-S2B`:** two identical extra issued vehicles, used only by S2 (one per S2 run). Each has 20 near-cap investors whose holdings, counting associates as G07 requires, put each at 4.9 % of the vehicle by G07's own measure. They are built with A06's `holder-cap-attempt` generator at larger counts. Each also has 1,000 ordinary holders and a follow-on offering, described in S2.
  - **On-chain mirror:** every vehicle deployed as an ERC-3643 suite on the Docker chain, with identities registered and units minted to the registered smart wallets. This uses T-REX batch registration and batch mint through A28's token operations under approved `APR`s created by the seed's approval fixtures, so the chain, the register and the bank agree at the start. See spec point (a) for the fallback.
  - **Money:** client-money ledger balances and bank statement lines for every vehicle (A16, A17 sandbox), escrow for 5 open offers, and one month of rent-roll attestations (A34), so every vehicle can run a distribution.
  - **Heavy investor "Load Morgan":** 100 holdings, 50,000 transactions over five years (deposits, orders, allocations, distributions, withdrawals), 60 statements and 5 years of AMMA documents.
  - **Blotters:** one open offering with 10,000 orders across SM-05 states, and 200,000 historic orders platform-wide.
  - **Offerings list:** 1,000 public offerings (100 live or closed from the vehicles, 900 historic closed).
  - **Audit log:** 5,000,000 audit events written through A10's normal append path (`audit.record` inside `auditedTx`), so A10's chain verifier passes on the perf database. The load is budgeted at up to 2 hours of wall time, measured and recorded; it runs once per data set and is cached in the paired snapshot. The log includes at least 150,000 agent events for one probe person (whose agents act on their behalf) inside the date range the deep-page challenge uses, which spans the 4 Oct 2026 daylight-saving change.
  - **Agent tokens:** 2,000 tokens covering every principal type of A12's fixtures: the seven investor sub-types, six sponsor and tenant-partner roles, four platform partner types and the staff roles. Each has a mandate and 30 days of agent activity history from A06's `agent-activity.jsonl` generator, so A101's baselines exist. The history is shaped for S3 as that section states.
  - **Webhook subscriptions:** 200 agent webhook subscriptions (A46) across investors, sponsors and staff, each bound to one of the tokens above, for eligible event types within that token's scopes (`distribution.*`, `order.*`, `payment.*` for investors; `register.*`, `offer.*` for sponsors; `recon.*`, `approval.*`, `alert.*` for staff), all pointed at A46's fixture sink.
- `npm run perf:data:verify` runs A06's invariant set on the perf database (no holder above 5 %, no foreign holder of residential units, every APR maker not a checker, audit chain verifies) plus: register total equals chain supply equals the ledger for every vehicle at the start (a clean A20 run). A perf run on dirty data is refused with `PERF_DATA_INVALID`.
- **Paired snapshot and restore.** After `perf:data` and `perf:data:verify`, the harness stops the stack and snapshots the `realx_perf` database volume (including A04's `system_clock` row) and the chain volume together, with one manifest holding both hashes. `npm run perf:restore` restores both before every `perf:all` and refuses with `PERF_SNAPSHOT_MISMATCH` if the two hashes do not belong to the same manifest. A09's clock and Hardhat time only move forward, so the data set's clock starts on 1 Aug 2026 (Australia/Sydney). After restore, the harness checks that the platform's "now" and the chain's latest block time are both before 3 Oct 2026 23:00 Sydney, and refuses with `PERF_CLOCK_PAST_TARGET` otherwise (regenerate the snapshot). Each `perf:all` then advances forward through its ordinary nights, 4 Oct 2026 and 4 Apr 2027 in that order.
- **Clock rule for measured windows.** The harness advances the clock only when no measured job is running. From 23:59:00 until every snapshot run of the night has completed, and from 01:59:00 until the reconciliation cycle has completed, the clock runs at real speed and is never advanced. On the snapshot-overrun night (the node QA's challenge), the clock runs at real speed from 23:59:00 to 03:00 without any advance.
- **Spec point (a), settled at Specify:** generating 1,000,000 on-chain holdings on the Hardhat chain may take too long on the build machine. Proposed: generate all 100 vehicles on-chain once, time the generation, and cache the chain state in the paired snapshot. If generation exceeds 2 hours, the fallback is 20 vehicles fully on-chain plus 80 served by A20's stub chain source. The reduced coverage is then recorded in `A84.qa.md`, and the reconciliation budget below applies only to the 20 on-chain vehicles plus a linear projection. The user decides whether the fallback is acceptable.

**3. Nightly windows: snapshot at 00:00, reconciliation at 02:00**

- The clock is moved through A09's clock endpoint to 23:59:00 Australia/Sydney and then runs at real speed (section 2's clock rule). The run observes `register.snapshot` for all 100 vehicles, followed by `recon.nightly` at 02:00 (A20: batches of 10 plus the platform R18 run) against the real sources: A27's indexer snapshot source, A18's sandbox registrar extract fetched at 02:10 (A20's timing), and A17's bank statement.
- Windows (proposed; spec point (b)): the snapshot cycle for 100 x 10,000 completes in at most 45 minutes, so the 02:00 run always has tonight's `RegisterVersion`. The reconciliation cycle completes in at most 30 minutes with the real sources (A20 measured under 10 minutes against its in-memory stub), and in any case before 03:00, leaving three hours of headroom before the design's "all figures reconciled at 06:00 AEST" (adCmd subline). Both are measured as wall time from job start to the last run's `completed` row, and both are checked against the platform clock in the job rows.
- Six measured nights per `perf:all`: (1) quiet clean night, with a replayed cycle (the job started twice) that must change no row (N13); (2) clean night under a background load of 50 requests per second (overnight agent traffic plus the month-end distribution batches of section 4); (3) planted-drift night; (4) 4 Oct 2026; (5) 4 Apr 2027; (6) the snapshot-overrun night.
- Correctness at scale is part of the window: clean cycles end with zero breaks. The planted cycle, after A06's three drifts (a register 9,998 against a supply of 10,000, an unknown holder, one cent of client money), ends with exactly those three breaks, their alerts and the resale halt, in the same window.
- `preflight({vehicleId})` for a 10,000-holder vehicle is sampled 50 times against the indexer source: p95 at most 5 s (A20's hard budget). An `incomplete` answer counts as a miss, not a pass.
- Daylight saving: on the night of 4 Oct 2026 (AEST to AEDT: 02:00 does not exist) and the night of 4 Apr 2027 (AEDT to AEST: 02:00 happens twice), each job runs exactly once, uses tonight's version, and finishes inside its window.
- Snapshot overrun: the snapshot is slowed until it runs past 02:00 by the storage-adapter delay of A08's `SANDBOX_LATENCY_PROFILE` (section 8). Job timings must show the delayed vehicles' snapshots completing after 02:00 clock time, or the run is invalid, not a pass. `recon.nightly` must then either wait for tonight's version or record the vehicles as `snapshot_missing`. It must never reconcile silently against yesterday's version. How A20 behaves is observed and asserted, and a silent stale reconciliation is a Critical finding against A20.

**4. Distribution calculation and execution for the largest trust, and a month-end**

- The largest trust is a vehicle with 10,000 holders of one unit each: the worst case for line count under the 10,000-unit supply rule. It runs one full SM-08 cycle through A40's API, with the approval chain written exactly as A40 defines it and driven by the seed personas through A11's simulated authenticator and A14:
  1. SP-FIN creates the run from a `confirmed` income period (`POST /v1/sponsor/distributions/runs`).
  2. SP-FIN locks it (`…/lock`: income period `confirmed -> locked`, snapshot locked, no A14 request, audited), and the job moves `draft -> calculating -> calculated`.
  3. SP-FIN proposes (`…/propose`): A14 request `distribution.propose`, SP-FIN maker, SP-OWN checker, `4E`. On approval SVCA moves `calculated -> in_review`.
  4. FINA submits (`POST /v1/distributions/runs/{id}/submit`): A14 request `distribution.run.approve`, CFO checker.
  5. The sponsor funds `net_cents` through A17's sandbox rail. TRSY requests funding (`…/fund`, `distribution.run.fund`, TRSY maker, CFO checker, `4E`), and `distributions.funding_check` moves `funding -> funded`.
  6. `funded -> executing` fires as A14's `AUTO` row `distribution.run.execute`, then `executed -> reconciling -> closed` (A20's R8 and R13 targeted run).
  The harness asserts each step's A14 row (request type, maker, checker, approval code) and the SM-08 transition in the audit log.
- Budgets (proposed): `lockAndCalculate` at most 60 s; `buildPaymentFile` plus the sha256 at most 10 s, and a regeneration byte-identical to the approved file. `distributions.execute` posts 10,000 `distribution.pay` journals at A40's default `distributions.execute_batch_size` of 200 in at most 10 minutes, and every `distribution.line.paid` outbox event reaches A47's read model and A43's notification queue within 2 minutes of its journal. `executed -> reconciling -> closed` takes at most 5 minutes.
- Correctness at scale: `Σ line net + Σ withholding + Σ carry_out + remainder = net + Σ carry_in` holds exactly. `paid_cents = payable_cents` holds. The node QA's independent recomputation of the payment file hash from the locked register version equals the approved hash. No line is posted twice.
- Crash injection at scale: the worker containers are killed three times during `distributions.execute` (at roughly 10 %, 50 % and 90 % of lines). After each restart the run resumes from the first unposted line, and the final ledger has exactly 10,000 `distribution.pay` rows for the run.
- Month-end: all 100 vehicles distribute for the same period. The harness sets no concurrency of its own: it uses the worker's registered concurrency for `distributions.execute`, the default batch size and the two worker replicas, and records all three in the evidence. All 100 runs reach `closed` within 2 hours of the first `execute`, with 1,000,000 lines paid. The 02:00 reconciliation that night (night 2) still finishes inside its window. API p95 for investors reading `GET /v1/me/distributions` during execution stays within the section 5 budget.
- Other M11 and M12 actions at scale (proposed budgets):
  - a signed register extract for a 10,000-holder vehicle (A18, through A73's `…/register/{vehicleId}/extracts`): generation and signing at most 30 s, and a regeneration byte-identical;
  - the monthly certification of 100 vehicles (A18's `certifyVersion`, `4E` by each vehicle's trustee checker set, driven through A11's simulated authenticator): system time at most 15 minutes in total, excluding the personas' scripted pauses;
  - `POST /v1/distributions/exit-waterfall/preview` (A40's `computeExitWaterfall`) for a 10,000-holder vehicle: p95 at most 10 s over 20 samples, with the floor-and-remainder rule exact.

**5. Server-side paging on every long list (N12)**

- Each list is measured with the SDK's `paginate` over the perf data. Budgets: first page p95 at most 300 ms; the deep page, defined as `min(500, last page)` and reached by walking the cursor, p95 at most 1.2 x the first page; and `limit=200` p95 at most 500 ms. Each p95 is taken over at least 50 samples. Where another node already states a tighter budget, that budget is carried into `budgets.json` with its source: `GET /v1/recon/vehicles` at most 200 ms (source A20). Every list must use A09's keyset `listRoute`: an offset parameter or a response over 200 items is a finding. Lists that grow during the run (the G22 and activity lists) are measured again after S3.
  - **Investments:** `GET /v1/public/offerings` (1,000 offerings, status filter) and the investor's holdings list under `GET /v1/me/portfolio`.
  - **Transactions:** `GET /v1/me/transactions?type=&vehicle=&from=&to=` for Load Morgan (50,000 rows), plus `GET /v1/me/distributions`, `GET /v1/me/statements` and `GET /v1/me/ledger`.
  - **Audit log:** `GET /v1/audit/events` with actor, action, object, on-behalf-of and date filters over 5,000,000 events, and `GET /v1/me/activity` for the probe person whose agents wrote at least 150,000 events.
  - **Blotters:** `GET /v1/admin/orders` (200,000 orders, filters on state, vehicle and date), `GET /v1/offerings/{id}/orders` (10,000 orders), the register entries `GET /register/{vehicleId}/entries` and cap table `GET /register/{vehicleId}/cap-table` (10,000 holders), `GET /v1/distributions/runs/{id}` lines (10,000, also what ADM-19 of A74 reads), `GET /v1/distributions/runs?state=&vehicle=&period=` (A74), and `GET /v1/recon/vehicles` (100 vehicles plus history).
  - **Sponsor tables (A64):** SPN-08's `GET /v1/sponsor/vehicles/{vehicleId}/register-view?as_of=&cursor=` (10,000 holders) and the sponsor distributions table `GET /v1/sponsor/distributions/runs?vehicle=`.
  - **Agent access (A12, A60, A77):** the ACC-05 and SPN-16 activity list `GET /v1/agent-access/activity?token=` (A12's route, read by A60), and ADM-35's oversight lists `GET /v1/agent-access/oversight/tokens` and `GET /v1/agent-access/oversight/evaluations` (A77), which grow by millions of G22 rows during S3.
- Every operation named in `budgets.json` is checked against the OpenAPI document before any measurement. A missing one aborts with `PERF_OPERATION_UNKNOWN`, naming it.
- **Query-plan guard (a separate pass, never during timed scenarios).** The plan pass sets `auto_explain.log_min_duration = 0`, `log_analyze = on`, `log_buffers = on` and `log_format = json`, and runs every list query above at the first page and at the deep page. At least one captured plan per listed query at each of the two depths is required; a missing plan is a finding against the harness. A sequential scan on a table with more than 100,000 rows, a sort spilling to disk, or buffer reads that grow with page depth (deep-page buffers above 2 x first-page buffers) is a finding, and the proposed index is named in it. During timed scenarios, `log_analyze` is off and `log_min_duration` is 100 ms. The settings of each pass are recorded in the evidence.
- Walk integrity under writes: while a full cursor walk of Load Morgan's transactions runs, new transactions are inserted for that investor at 10 per second. The walk must return every row that existed at its start exactly once, in order, with no duplicate and no gap. The same holds for the audit log walk while events are appended.
- Tables filter on the server: the Playwright run captures network traffic on ADM-31 (A66), the order blotter (A71), the register and reconciliation screen (A73), the investor directory (A68), ADM-19 run lines (A74), SPN-08 register and the sponsor distributions table (A64), the ACC-05 and SPN-16 activity lists (A60) and the ADM-35 oversight token and evaluation lists (A77), the last three after S3. Every filter or sort change must send its parameters to the API and receive at most one page. Any client-side filtering over a response larger than one page, or any table that loads more than one page before the user asks, is a finding against the screen's node.

**6. Investor screens at phone width, within budget**

- Screens measured at 375 x 812 on Playwright's pinned Chromium, as Load Morgan and as the design's Alex Morgan:

  - Buy flow: INV-01 to INV-03.
  - Portfolio: POR-01, holding detail POR-02, distributions POR-03, transactions POR-04, statements POR-07.
  - Account: the AUD and token wallet screens (A59), and ACC-05 API tokens and agents (A60), with the investor holding 20 tokens and 10,000 activity rows.
- Mobile profile: CPU throttled 4x through the DevTools protocol; network at 1.6 Mbps down, 750 kbps up and 150 ms round trip; cold cache and warm cache runs. Metrics come from the `web-vitals` npm package injected by the harness plus DevTools performance traces.
- Budgets per route (proposed; spec point (c)):
  - Largest contentful paint at most 2.5 s cold and 1.5 s warm.
  - Cumulative layout shift at most 0.1.
  - Interaction to next paint at most 200 ms on the main interactions: quantity stepper, filter change, Load more, tab switch, and the scope picker on ACC-05.
  - Initial JavaScript at most 170 kB compressed per route.
  - Font bytes at most 150 kB (Newsreader, Geist and Geist Mono subsets, `font-display: swap`).
  - At most 1,500 DOM nodes at first render.
  - `document.documentElement.scrollWidth === 375` (N11 and A52's rule) on every state.
- Long lists on a phone: on POR-04, 20 presses of Load more keep the page responsive (interaction to next paint at most 200 ms on the 20th press). The DOM holds at most the rows on screen plus one page if the list is virtualised, or at most 20 pages if it is not. The JS heap stays at most 60 MB. The investor app never requests all 50,000 rows.
- Fidelity guard: the budgets are measured on the pages exactly as the screen nodes left them (A87's fidelity and accessibility pass runs beside this node in AM8, and both feed A88). A fix that meets a budget by dropping a design element (a font, a tile, a pill) is refused at the owning node's gauntlet, and this node re-runs A05's token-level fidelity comparison on the changed page before closing the finding.

**7. API load, including a token-driven burst (D04)**

- Load driver: a TypeScript driver in `e2e/perf/load/` built on `undici` and the SDK, with HDR histograms from the `hdr-histogram-js` npm package, open-model arrivals (constant arrival rate, not closed loops that hide queueing) and coordinated-omission correction. It needs no binary outside the npm registry. It alternates the two API base URLs request by request. Every request carries a run id header, and the request log records the instance, status, latency and principal type; every error body is kept for the report.
- Each `perf:all` runs every scenario once, with its own seed. The three `perf:all` runs give the three samples per budget.
- **Two-process checks, for every scenario:** each API instance serves 40-60 % of the requests. Before S3, the harness confirms that A99's `PgRateLimitStore` is the registered store: after the first window, `rate_limit_window` rows exist for the S3 tokens. If they do not, the rate-limit exactness check fails, whatever the counts show.
- Scenarios:
  - **S1 steady business day, 10 minutes at 200 requests per second:**
    - Traffic mix: 70 % investor reads, 10 % investor writes (orders, deposits through the sandbox rail, withdrawal requests under threshold), 10 % sponsor console reads and writes, and 10 % staff console reads, half of it by humans with sessions and half by agents with tokens.
    - Budgets: reads p95 at most 250 ms and p99 at most 600 ms; writes p95 at most 500 ms and p99 at most 1,200 ms; zero 5xx.
  - **S2 offer-close spike, on the follow-on offerings of `PERF-S2A` and `PERF-S2B`:**
    - Traffic: 2,000 orders in 60 s, together worth 150 % of the hard cap. 400 of them come from the 20 near-cap investors (4.9 % each by G07's measure), who each send 20 orders through their agents, taking each of them to about 6 % if all were accepted. The other 1,600 come from other investors, half through their agents. 50 pairs are duplicates reusing the same `Idempotency-Key`. The driver funds a subset of accepted orders through A17's sandbox rail.
    - S2 runs twice with the same traffic, once per vehicle, with A37's `allow_oversubscription` set on the offering:
      - `PERF-S2A`, `allow_oversubscription = false`: accepted order units stay at or below the hard cap at placement, and refusals past it name G11.
      - `PERF-S2B`, `allow_oversubscription = true`: A37 may accept orders past the hard cap for scale-back, so the check is on allocation. Allocated units in the locked Allocation file stay at or below the hard cap, and every scaled-back order is refunded to the cent.
    - In both runs: no holder ends above 5 % by G07's measure, and every G07 refusal names G07. - **Stale snapshot reconciled as tonight's (money, M11).** On the overrun night, the node QA sets the storage-adapter delay of A08's `SANDBOX_LATENCY_PROFILE` so that `register.snapshot` for 7 of the 100 vehicles finishes at about 02:14 clock time; the job timings must show those 7 snapshots completing after 02:00, or the challenge is invalid and re-run. - **Offer-close stampede (money, G07 and G11).** In both S2 runs (`PERF-S2A` and `PERF-S2B`), 2,000 orders arrive in 60 s for 150 % of the hard cap. The 20 near-cap investors (4.9 % each by G07's measure, associates counted) each send 20 agent orders, and 50 pairs are duplicates reusing the same `Idempotency-Key`. - **Month-end double pay (money, M12).** During the 100-vehicle month-end, the node QA kills the worker containers every 90 s and restarts them, and at the same time replays 1,000 `distribution.line.paid` outbox events by resetting the relay's dedupe cursor. - **Agent burst that hides a real anomaly (security, D04 and G22).** Inside S3's 2,000-token burst, 10 tokens are planted against A101's actual rules: 4 trip `new_country` (calls from a documentation range the fixture maps to a country the token has never used), 3 trip `near_cap_repeat` (three orders or withdrawals within 24 hours, each at least 90 % of the per-action cap), and 3 trip `off_hours` (at least 10 calls at Tuesday 14:00, an hour-of-week bucket in which their 28-day history has zero calls; tokens older than 14 days, no mandate time windows). The platform `agents.traffic` switch is turned off for 30 s and back on. Expected: the held set equals the replayed `AG-2026.1` fired set with `action = hold`, which is exactly the 10 planted tokens, each held within 60 s. The demoted human's token is refused `G22_OWNER_NO_LONGER_HOLDS_ROLE` on its next call on the other instance. Every call during the switch-off gets `423 AGENTS_PAUSED`. The G22 row counts reconcile with the driver's log to the request. A single missing `gate_evaluation`, a late revocation, an unheld deviant or a hold outside the replayed set fails the node.
- **Argon2 amplification (security).** S5 is run at 2x and then 4x its rate, from several source IPs, with the third class of bad tokens carrying the lookup id of a real active token. Humans' p95 must stay within 1.5 x of baseline at 2x. At 4x, degradation must be graceful: 429 for the flooding sources, never a 5xx or a process crash. Unknown lookups must stay under 10 ms server-side (no hash). An API process whose CPU saturates on Argon2 because failed verifications are not limited before hashing, as A12.x requires, is a Critical finding against A12.

Each must stay within the paging budget with an index-only or index scan plan. The cursor must survive the DST boundary without skipping the repeated hour. A tampered cursor must return `400 invalid_cursor`, not a slow full scan.
