# A95 - P3: Auto Invest and PayTo mandates

**The investor's monthly plan, built so that it can never do anything the investor could not do by hand: a PayTo agreement adapter behind a swap point (agreements, amendments, suspensions, payments, payer-side events) whose money reaches the wallet only through A17's receipt matching; a plan the person signs with a passkey (amount, day of month, their own rules, maximum per property, reinvest on or off) that the RealX Auto Invest service account executes each month by placing ordinary orders through A37's pipeline with every gate checked again per purchase (G01, G04, G05, G06, G07, G11, G12, G21); a run that collects only what it can invest, pays anything it cannot invest into the AUD wallet as cash ("cap reached: paid as cash instead"), and turns a first purchase in a new trust into a proposal the person must acknowledge themselves; optional distribution reinvestment into the next run; the INV-04 screen with the AcknowledgeCard and the P3 banner; and full agent parity for every delegable action. The whole node ships behind a licence-bound P3 flag that stays off until the advice and arranging review (HG-LEGAL).**

## Build brief

This node is the module `autoinvest` in the Fastify monolith (`services/api/src/modules/autoinvest/`, worker jobs registered through A09's job registry and scheduled by A46), the PayTo port `packages/adapters/payto` with its sandbox, and the investor screen INV-04 (`apps/web/app/(investor)/auto-invest/` and `apps/web/src/features/autoinvest/`). Every rule is enforced in the API, never only in the screen; every route is in the OpenAPI document from the first commit so `packages/sdk`, the MCP catalogue (A104) and the parity suite (A100) see it. The only time source is A09's injectable clock (the `Date.now()` grep in `npm run verify` applies), and every schedule is in Australia/Sydney.

**1. Scope, placement and the phase switch**

- Two flags, both kind `licence-bound`, phase `P3`, default off, owned in data by A08 and toggled only through A21's `flag.toggle` (`4E`, SUPER maker, CCO checker) against a `valid` licence binding: `autoinvest.enabled` (plans, runs, INV-04 live mode) and A17's existing `payments.payto` (agreements and payments). The licence activity the binding must cover is a counsel answer; until it exists, A21 refuses the toggle with `G21_NO_BINDING` and a test proves it. With either flag off every write route of this module returns A17's `501 not_in_phase` shape with code `PHASE_NOT_ENABLED`, reads return `{ enabled: false, preview: true }`, no job runs, and INV-04 renders the preview described in §11. A third flag, `autoinvest.runs` (kind `kill-switch`, default on once `autoinvest.enabled` is on), stops every run platform-wide without touching plans; loop A48.1 rewires its toggle as `SGL+R` like every other kill switch.
- In `RUN_MODE=local|test` the env override may turn both flags on so the node can be built and tested end to end on the sandbox; the "no production selector" test from A08 covers them. Nothing in this node can be on in any other environment before HG-LEGAL evidence is recorded against the binding.
- What this node never does: pick properties for the person, rank listings by RealX revenue or sponsor fees, lend, use the investor's wallet key or a session key (allotment mints to the registered smart account through A38 exactly as for a hand-placed order), hold money outside A16's `investor_cash` and `offer_escrow` accounts, or create an order any other way than A37's placement endpoint.

**3. PayTo port (`packages/adapters/payto`, the Q12 swap point for the PayTo half of the bank rail)**

- **One PayTo implementation, one swap point.** This port supersedes A17's P1 stub verbs `createPayToMandate`, `getPayToMandate` and `cancelPayToMandate` (A17's manifest already says "A95's packages/adapters/payto port becomes the PayTo swap point"). This node never calls those stub verbs; the agreement state in this port's sandbox is the only authoritative sandbox mandate state. Loop A17.3 marks A17's stub verbs and their `mandate.*` events deprecated and drops them from A17's conformance suite with no other contract change. The generated `SWAP-POINTS.md` has exactly one PayTo row, produced from this port's manifest; a test asserts one row.
- Interface (zod in and out, integer cents): `createAgreement({ investorId, debtor: { bsb, account, accountName }, maxAmountCents, frequency: 'monthly', startsOn, description, idempotencyKey })` → `{ agreementRef, state: 'pending_authorisation', authoriseBy }`; `getAgreement`; `amendAgreement({ agreementRef, maxAmountCents })` (the payer re-authorises in their banking app; the old maximum stays in force until then); `suspendAgreement`, `resumeAgreement`, `cancelAgreement`; `initiatePayment({ agreementRef, amountCents, reference, idempotencyKey })` → `{ paymentRef }`; `getPayment`; `verifyWebhook(headers, body)` → typed events `agreement.authorised`, `agreement.declined`, `agreement.expired`, `agreement.suspended_by_payer`, `agreement.resumed_by_payer`, `agreement.cancelled_by_payer`, `payment.settled`, `payment.failed` (reasons `insufficient_funds`, `agreement_not_active`, `amount_exceeds_agreement`, `account_closed`, `rail_unavailable`); `health()`.
- The sandbox implementation composes A17's sandbox bank: a settled payment appears in A17's feed as `credit.received` with `rail = payto`, the provider agreement reference, the payment reference (`run_id`) and the payer name, and **money reaches the investor only through A17's `ingestTransaction` and name rule and A16's journal**. The port never posts a journal, never credits a wallet and never sees a PayID.
- **How A17 finds the investor for a PayTo credit (loop A17.2).** A17's matching engine step (1) resolves only a PayID or a virtual-account reference, so a PayTo credit would otherwise be held as `unknown_destination`. Loop A17.2: for `rail = payto`, step (1) looks up the provider agreement reference through a resolver this node registers with A17 (`registerPayToAgreementResolver(agreementRef) → virtualAccountRef | null`, answering from `payto_agreement.virtual_account_ref`); `null` means `held: unknown_destination` as today. Steps (2) to (6) stay unchanged: the restriction hold, the exact name rule, the one journal and `payment.credited`. The resolver is a pure read of this module's table and never posts, credits or decides anything else. Hidden test: a PayTo credit with an unknown agreement reference is held `unknown_destination` with only A17's one `deposit.unmatched` suspense journal, nothing credited to `investor_cash`, no `payment.credited`, and the run `funding_failed` at the cut-off. Scenarios through A08's `scenarioOf()` only: amount ending `.51` fails `insufficient_funds`; reference `SIM-PT-DECLINE` declines authorisation; `SIM-PT-AUTH-DELAY-<hours>`; `SIM-PT-PAYER-SUSPEND` and `SIM-PT-PAYER-CANCEL` fire the payer-side event on the next injected-clock tick; `SIM-PT-DUP` delivers `payment.settled` three times, once out of order; `SIM-PT-LATE` settles after the run's funding cut-off.
- The port ships A08's conformance suite (agreement lifecycle, amendment keeps the old maximum until authorised, payment idempotency, `amount_exceeds_agreement` refusal inside the port before any rail call, webhook signature, replay and stale timestamp) so a human can run it against a vendor's sandbox after HG-VENDOR; the adapter manifest names the swap (Monoova or Zepto-type PayTo provider, client only).
- A17 keeps its route `POST /v1/payments/payto-mandates` as the contract. This node registers the P3 implementation behind that route through the `registerPayToHandler(handler)` hook A17's module already exports (spec point (e)); it does not edit A17's folder. The handler creates an agreement only for the caller's own Auto Invest plan at signing (§4): a call with no plan version being signed returns `409 PAYTO_PLAN_REQUIRED`. G02 must be clear for the investor (the product map's gate on "Set up PayTo").
- **Which account is debited.** The debtor is always the investor's verified, name-matched nominated bank account from A17 and ONB-09 (the account withdrawals go to), read by `nominated_account_id` and shown masked on INV-04 ("From CBA ••4471"). No API, MCP or web route of this node accepts raw BSB or account details. To debit a different account the person first changes the nominated account through ONB-09's passkey change flow, which is non-delegable under D04; an agent can never change it. A nominated account that no longer passes A17's name rule refuses creation with `PAYTO_DEBTOR_NAME_MISMATCH` and nothing is sent to the rail. A change of nominated account while an agreement is active does not move the agreement: the plan pauses with `paused_reason = person` and INV-04 asks the person to set up the agreement again (a new passkey signature).
- **Plain top-ups are out of scope.** A PayTo agreement for automatic wallet top-ups with no plan (WalletCard's "Or set up PayTo for automatic monthly top-ups" and ONB-09's "Set up PayTo") is not built here. When `autoinvest.enabled` is on, those two actions link to INV-04; a standalone top-up agreement, if the founder wants one, needs its own node or loop (the ONB-09 action is A56's, the WalletCard link A59's).

**4. Plan lifecycle (a local machine registered as an extension in A03's `extensions.ts` with this node as source)**

- States: `draft`, `pending_confirmation`, `awaiting_payto`, `active`, `paused`, `suspended`, `cancelled` (terminal). Transitions: `draft → pending_confirmation` (an agent submits a draft for starting, §10; the plan records `pending_version_id` and A12's `confirmation_id`); `pending_confirmation → draft` (A12's confirmation is rejected or expires; the pending version goes `rejected` or `expired`); `draft|pending_confirmation → awaiting_payto` (person signs the version with a passkey, or confirms the agent's request with the required assertions; the agreement is created in the same request); `awaiting_payto → active` (`agreement.authorised`); `awaiting_payto → cancelled` (`agreement.declined` or `expired`, default authorise window 5 days, a data row); `active → paused` (person or their agent; payer suspension; three consecutive funding failures, `autoinvest.max_consecutive_funding_failures` default 3; a change of nominated account, §3); `paused → active` (person or agent resume, only if the agreement is `active`); `active|paused → suspended` (staff or restriction, §9); `suspended → paused` (staff reinstate, refused while a restriction is set, §9; the person then resumes); any non-terminal → `cancelled` (person or agent; payer cancellation at their bank; account `offboarded` from A30). Every other pair is refused with `AIP_ILLEGAL_TRANSITION`. Cancelling cancels the agreement through the port, voids open proposals and marks any pending version `rejected`; it never touches placed orders.
- **Plan-version lifecycle (amending a live plan).** Amendments never change the plan machine's state. A version is inserted as `pending_confirmation` or `effective`:
  - A narrowing change (§4 `isNarrowing` below returns `true`), by the person or their agent, is inserted `effective` at once (or from the next period inside the run window); the previous effective version goes `superseded`.
  - A widening change by the person in a web session needs a fresh passkey assertion in the same request (`POST /v1/autoinvest/plan/sign` over the new version's `signed_hash`; two assertions for a joint account with `signing_rule = both`); with it, the version is inserted `effective`.
  - A widening change under a token inserts a `pending_confirmation` version, sets `pending_version_id` and `confirmation_id`, and returns `428 CONFIRMATION_REQUIRED`. The plan keeps its `active` or `paused` state and every run keeps using the effective version. The pending version becomes `effective` only on A12's `approved` resolution of that confirmation carrying the required assertions (the person's; both holders' for `signing_rule = both`, each over the same `signed_hash`; one holder's approval alone leaves it pending); A12's `rejected` resolution makes it `rejected`; expiry makes it `expired`. Either way `pending_version_id` and `confirmation_id` are cleared.
  - At most one pending version per plan. A second widening request, or any narrowing edit, while one is pending marks the pending one `superseded` and the agent must ask again.
  - A pending version confirmed inside the run window takes effect from the next period (`202` with `effective_from`).
  - Illegal version pairs (`effective → pending_confirmation`, anything out of `superseded`, `rejected` or `expired`) are refused with `AIP_ILLEGAL_TRANSITION` and are in the refused-pair tests with the plan machine.
- **`isNarrowing(old, new)`: one pure function in `plans/narrowing.ts`**, the only place the classification is made. It returns `true` only when every field is provably no more permissive, and `false` for anything else:
  - `monthly_amount_cents`: new ≤ old.
  - `run_day`: equal. Any change of run day is widening.
  - `scope`: equal, or `any_open_offer → trusts_i_hold`.
  - `asset_classes`: new is non-empty and a subset of old.
  - `states[]` and `sponsor_include[]` (empty means "all"): if old is empty, new may be any non-empty list; if old is non-empty, new must be non-empty and a subset of old. So `['NSW'] → []` is widening.
  - `sponsor_exclude[]`: new is a superset of old. Removing an exclusion is widening.
  - `max_per_listing_cents` and `max_per_property_cents` (null means no cap): old null and new any value, or both non-null and new ≤ old. Raising or removing a cap is widening.
  - `reinvest_distributions`: equal or `true → false`.
  - `acknowledged_terms`: equal.
  - Any field not named here (including a field added later) makes the result `false`.
  Hidden tests: a fast-check property over random pairs of versions checking that whenever `isNarrowing` is true, the set of listings and amounts the new version allows is a subset of the old one's (evaluated by the allocation's rule filter over random offers); explicit vectors for `['NSW'] → []`, `[] → ['NSW']`, removing a sponsor exclusion, emptying `sponsor_include`, raising `max_per_property_cents`, setting a cap to null, and a `run_day` change. A `false` result under a token always returns `428`.
- Routes (all `/v1`, cursor pagination, `Idempotency-Key` on every write): `GET /v1/autoinvest/plan` (current plan, version, agreement state, next run date and the estimated collect amount), `POST /v1/autoinvest/plan` (create or replace draft), `POST /v1/autoinvest/plan/sign` (fresh assertion over `signed_hash`, `requiresHuman`), `PATCH /v1/autoinvest/plan` (new version; narrowing applies at once, widening needs a signature or, under a token, a confirmation, as above), `POST /v1/autoinvest/plan/pause`, `/resume`, `/skip-next` (skips the next period, recorded as a `skipped` run with reason `person`), `/cancel`, `GET /v1/autoinvest/runs` and `GET /v1/autoinvest/runs/{id}` (history with lines and gate rows), `GET /v1/autoinvest/proposals`, `POST /v1/autoinvest/proposals/{id}/decline`, `GET /v1/autoinvest/preview` (a dry run of the current or a draft version against today's open offers, returning the would-be lines and their gate rows without collecting or placing anything; the screen's "what would happen this month").
- Edits inside the run window (from collection start to run completion) are queued to the next period and answered `202` with `effective_from`; a cancel inside the window stops placement of any line not yet placed and pays the budget as cash.
- Joint accounts with `signing_rule = both` need both holders' assertions over the same `signed_hash` (`FRESH_ASSERTION_REQUIRED` names the missing holder); entity accounts need a verified signatory (`AUTOINVEST_SIGNATORY_REQUIRED`, read from A30's `is_verified_signatory`); a `minor_guardian` investor gets `PHASE_NOT_ENABLED` until A97.

**5. The monthly run (worker jobs, idempotent, one run per plan per period)**

- Run machine (same extension mechanism): `scheduled → dry_run → collecting → funded → executing → completed`, with `dry_run → skipped` (nothing investable, plan paused or suspended, restriction, `autoinvest.runs` off, flag off), `dry_run → funded` with no payment (only when `collect_cents = 0` and the unconsumed reinvest pool is positive: the run invests the pool alone), `collecting → funding_failed` (payment failed or not matched by the cut-off) and `executing → completed` always ending with a cash line when anything is left. Illegal pairs are refused with `AIR_ILLEGAL_TRANSITION`.
- **Placeable lines and proposal lines.** At the dry run each matching listing is classified before any arithmetic: a *placeable* line (a vehicle the person holds whose G12 standing-instruction path of §7 is open) or a *proposal* line (a first purchase, or a held vehicle whose §7 path is refused). **Proposal lines never count towards capacity, collection or budget**: no money is pulled for a purchase the person may decline. A proposal's suggested `amount_cents` is the share `aiv1` would give it if the proposal lines were included in a split of the monthly amount alone; it is a suggestion shown on the card, and the person pays from their wallet when they accept through INV-02.
- `autoinvest.dry_run` (07:00 on `run_day`): freezes the effective plan version, lists `live` offerings from A36 that match the rules (asset class, state, sponsors, `trusts_i_hold` through A47), classifies the lines, and runs `aiv1` over the placeable lines with an **estimate budget = `monthly_amount_cents` + the unconsumed reinvest pool** (no dependency on capacity, so the definition is not circular), calling A37's `POST /v1/offerings/{id}/orders/quote` as `SVCA-AUTOINVEST` on behalf of the investor for each allocated line. `capacity_cents` is the sum of units cost plus fees of the lines that would pass. Capacity 0 → `skipped` with `nothing_matched` and **nothing is collected** (spec point (d): collect only what can be invested).
- `autoinvest.collect`: `collect_cents = min(monthly_amount_cents, max(0, capacity_cents − reinvest_pool_cents), agreement.max_amount_cents)`, where `agreement.max_amount_cents` is the maximum the payer has currently authorised (an amendment waiting for the payer's re-authorisation does not count). `collect_cents = 0` with a positive pool goes `dry_run → funded` with no payment; otherwise `initiatePayment` with `idempotencyKey = run_id` and `reference = run_id`; one payment per run, ever. The run waits for A17's `payment.credited` event for the receipt whose reference is the `run_id` (resolved through loop A17.2, §3); funding cut-off 15:00 (`autoinvest.funding_cutoff`, a data row). A failure or a late credit moves the run to `funding_failed`, increments `consecutive_funding_failures` and notifies; a late credit that arrives after the cut-off stays in the wallet as cash and is never invested by a later run automatically.
- **The collected money is spent by the run, not by A37's funding sweep (loop A37.3).** A37 funds a person's `awaiting_funds` orders, oldest first, on each `payment.credited`. Without a change, a PayTo collection could fund a hand-placed order, an agent order or a retail order whose cooling-off just ended, and the run budget would shrink silently. Loop A37.3: A37's funding sweep does not fire on a `payment.credited` whose receipt is `rail = payto` with an Auto Invest run reference; instead `autoinvest.execute` runs on that event, and A37's sweep takes the same per-investor advisory lock the run holds. When the run completes, this module emits `autoinvest.run.executed` and A37 runs its normal sweep for that investor, so the run's leftover cash (the person's money) may then fund any waiting order. If the budget is still short at execution (a withdrawal or another sweep in between), `budget_cents = min(...)` below absorbs it and a run line `skip_gate = funds` explains it on INV-04 ("Part of this month's collection was used by another order before the plan ran"). Challenge: an `awaiting_funds` manual order exists at collection time.
- `autoinvest.execute` (on funding, under the per-investor advisory lock): `budget_cents = min(collected + reinvest_pool, available balance of investor_cash at that moment)` (A16 read; the run never spends cash the person already had, and never spends more than is there). Allocation (`algorithm_version = aiv1`, spec point (b)), over placeable lines only: eligible listings are split equally, `per_listing = floor(budget ÷ n)`, each capped by `max_per_listing_cents`, by the room left under `max_per_property_cents`, and by G07's `max_allowed_units`; `units = floor(per_listing ÷ (unit_price_cents × (10,000 + fee_bps) ÷ 10,000))` with A02's unit math; a listing whose units fall below `min_ticket_units` is dropped and its share redistributed once; ties and the redistribution order are by offer close date ascending, then offering id. A line skipped at placement (a gate refusal) is not redistributed: its share becomes cash. No other input (fees, sponsor, RealX revenue, popularity) enters the algorithm, and a test proves it by permuting those fields.
- Each placement is A37's `POST /v1/offerings/{id}/orders` with `channel = auto_invest`, `actor_principal_id = SVCA-AUTOINVEST`, `on_behalf_of_id = investor`, `Idempotency-Key = autoinvest:<run_id>:<offering_id>`, and `confirmation: { kind: 'standing_instruction', plan_version_id, signed_hash }` (spec point (a): loop A37.1; A37 verifies it by calling this module's exported `verifyPlanInstruction(order_canonical, plan_version_id, gate_results)` after its gate set, which checks the version was effective at run start, the order is inside its caps and rules, the listing passed the run's quote, and G05 passed without a flag (§6); the order row's `mandate_version_id` holds the plan version id). A wholesale order, or a retail order under `fund_at = confirm`, is funded at placement and the line is `placed`. An order that lands in `awaiting_funds` at placement (a race with a withdrawal) is cancelled at once through `POST /v1/orders/{id}/cancel` and the line is `skipped` with `funds`.
- **Retail orders in cooling-off.** Under A90's cooling-off with `fund_at = after_reflection` (the default), a retail run order goes to `reflection_period` with no money moved. Its line is `placed_pending_reflection` and its total (units cost plus fee) counts in `reflection_cents`, not in `placed_cents` or `fees_cents`. That cash is **not reserved**: it stays in `investor_cash`, withdrawable, and INV-04 shows the line as "Awaiting cooling-off · ends {date}" with A90's revoke link. These orders are exempt from the "cancel `awaiting_funds` at once" rule. When the timer ends, A37 moves the order `reflection_period → awaiting_funds` and funds or expires it under A37's own rules; this module records a follow-up run line (`reflection_funded`, `reflection_expired` or `reflection_revoked`) pointing at the first and sends one notification. Under the §7 default (`orders.autoinvest_standing_consent = wholesale_only`) a retail line in a held trust is a proposal, so this path runs only once counsel widens that parameter; the property test covers it with the parameter on.
- Money invariant for every run: `placed_cents + reflection_cents + fees_cents + cash_left_cents = budget_cents`, every figure an integer, `cash_left_cents ≥ 0`; `collect_cents ≤ min(monthly_amount_cents, currently authorised agreement.max_amount_cents)`; the leftover is not moved at all: it is already in `investor_cash`, so "paid as cash" means "left in the wallet, withdrawable, with a run line saying why". Later allocation scale-backs and refunds (A37, A38) and the outcome of a reflection-period order return to or stay in `investor_cash` and are never reinvested automatically.
- Hidden edge vectors for the arithmetic: (i) plan raised to A$800 while the authorised agreement maximum is A$500: collect ≤ A$500; (ii) capacity ≤ reinvest pool: `collect_cents = 0`, no payment, `dry_run → funded`, the pool alone invested; (iii) the estimate budget = monthly amount + pool through `aiv1`; (iv) a run with two placeable and two proposal lines collects only for the two placeable lines.
- Jobs replayed over the same interval change nothing (unique run per period, idempotency keys on the payment and every order); a worker crash between two placements resumes from the run lines already written.

**6. Gates per purchase (all server-side, every run, every listing)**

- A37's placement set runs unchanged on every run order (G01, G04, G06, G07, G11, G12, G21, and G05 through A90's retail rule pack); this node adds no exception and no cached result: the quote at dry run is advisory, the placement re-evaluates.
- **G04 Wholesale status valid** (A32): a wholesale-track listing is skipped for an investor whose certificate is expired or absent (`skip_gate = G04`), with the run line saying so and a notification pointing to the certificate renewal; the $500k single-offer test cannot be met by a plan and is never assumed. Retail-track listings (P2 scheme sub-funds) stay eligible through G05.
- **G05 Target market fit** (A90): a retail listing is placed only when the person's target-market answers are current and in the TMD's target market; out-of-market or missing answers skip the listing (`skip_gate = G05`) and prompt ONB-07. Auto Invest never uses a "flag and proceed" path for out-of-market dealings (spec point (c), stricter than the manual path; counsel to confirm). **Enforcement point:** A90's `outside_market_action` may be `flag`, under which A37 runs A90's G05 unchanged and a manual order proceeds with a flag. For run orders the refusal sits inside placement: `verifyPlanInstruction`, which A37 calls after its gate set (loop A37.1 passes the gate results to it), refuses any `standing_instruction` order whose G05 result passed with a flag, with `AUTOINVEST_G05_OUTSIDE_MARKET`; A37 then rejects the order (`rejected` at placement) and the run records `skip_gate = G05`. The dry run applies the same rule so the line is not counted in capacity. Hidden test: a listing whose TMD has `outside_market_action = flag` and an out-of-market investor, both at dry run and when the TMD changes between dry run and placement: zero orders, `skip_gate = G05`. Retail orders enter A37's `reflection_period` where A90's cooling-off parameter applies (§5), and the run notification carries the revoke link.
- **G07 Holder cap** (A19): units are reduced to the quote's `max_allowed_units`; zero means `skip_gate = G07` and the share becomes cash ("cap reached: paid as cash instead", J18's failure path).
- G06 residency and FIRB, G11 offer caps, a halted vehicle (A48), and G21 are skip reasons like any other; a skip is a run line with the gate row, never an error and never a retry within the run.

**7. Disclosure and first purchases (G12 with A35's CQ-02 default)**

- **The G12 path for a run order in a held vehicle (loops A35.1 and A37.2).** A37 accepts G12 only through per-order acknowledgements or an agent mandate's standing consent, and `SVCA-AUTOINVEST` is neither a person nor a token under an A12 mandate. Two loops give the run its own path, with nothing weaker than the agent path:

Because a service account opens nothing, the open requirement is met by the holder's own human `document_open` rows for the same versions, recorded before the standing consent was created (the opens the person made when they gave the consent); an agent's opens never count. A35's CQ-02 regime parameter, `first_purchase_policy = person_required` and `new_version_policy` checks apply unchanged, in the same order as for an agent.
  - Loop A37.2: A37's G12 evaluation accepts that set for an order with `confirmation.kind = standing_instruction` only when a new named parameter `orders.autoinvest_standing_consent` (values `off`, `wholesale_only`, `all`; default `wholesale_only`; set with counsel) allows the offering's regime.
  - Under the default, a retail line in a held trust is **always a proposal** (reason `autoinvest_parameter`). A wholesale line in a held trust is placed when every check passes.
  - Refusal reasons, each turning the line into a proposal with `proposal_reason` set and never a retry: `autoinvest_parameter`, `counsel_parameter` (CQ-02), `consent_missing`, `consent_scope`, `consent_predates_version`, `holder_open_missing`, `first_purchase`. A first purchase in any vehicle (A35's `first_purchase_policy = person_required`) is **always** a proposal: `autoinvest_proposal` in `open`, nothing is collected for it (§5) and the suggested amount is shown as a suggestion, the person is notified, and INV-04 shows the proposal card whose "Review and buy" opens A57's INV-02 prefilled (units, offering) so the person opens and acknowledges the documents and confirms with a passkey there. INV-04's signing step offers the person the A35 standing-consent step (passkey, `ui` only) for the vehicles they hold, so the J18 held-trust lines can be placed; without it every line is a proposal.

**8. Distribution reinvestment (J18 step 3, POR-03)**

- On A40's line-paid event for an investor whose plan version has `reinvest_distributions = true` and whose plan is `active`, a `autoinvest_reinvest_credit` row records the net amount already credited to `investor_cash`; the next run's budget includes the unconsumed pool, capped by capacity; what the run cannot invest stays as cash and the credit is marked consumed by that run (reinvestment is one attempt, not a standing reserve). **9. Service account, restriction, kill switches and tipping-off**

- **A restriction always suspends, exactly like staff.** By rule, this module (not A42) applies the plan transition: on A30's or A42's restriction-set event, and as a backstop at every dry run through A19's G02 and G14 providers, a restricted or under-review investor's `active` or `paused` plan goes `suspended` with `paused_reason = restriction`, the same transition, copy and notification as a staff suspension. A42 needs no change; its optional suspension becomes this rule.
- **One agreement policy for both:** neither a restriction nor a staff suspension suspends the PayTo agreement at the bank (the payer can see a bank-side suspension in their banking app). While the plan is `suspended`, no payment is ever initiated, so the agreement stays `active` and idle in both cases.
- **No auto-revert while restricted.** A staff `SGL+R` suspension reverts automatically only if ratification lapses **and** no restriction is set; a restriction-backed suspension never auto-reverts while A42's flag is set, and staff reinstate is refused (staff-only code `AUTOINVEST_REINSTATE_RESTRICTED`) until it clears. After it clears the plan stays `suspended` until staff reinstate, exactly as after a staff suspension.
- **Investor-visible fields that must match** between a restriction-backed and a staff suspension (byte-equal after id substitution): `plan.state = suspended`; the projected `paused_reason = under_review` (both `staff` and `restriction` map to it; the raw value is staff-only); `status_label` "Under review"; `agreement.state = active`; `next_run_on = null`; one `skipped` run per period with public `skipped_reason = on_hold` and the copy "This month's run is on hold while we review your account"; the one suspension notification and its webhook payload (`autoinvest.plan.suspended`, reason `under_review`); the status codes and bodies of pause, resume, skip-next, edit and cancel (resume → `409 AUTOINVEST_PLAN_STATE` in both); and response timing. No AML reason, case id or hit appears on any investor or support surface.
- Staff (M05 ops, TRSY or CCO) can suspend a plan with `POST /v1/admin/autoinvest/plans/{id}/suspend`, an A14 protective `SGL+R` request (acts at once, ratified within 2 hours, AUTO revert on lapse as above); `POST /v1/admin/autoinvest/plans/{id}/reinstate` is `4E`. The platform switch `autoinvest.runs` stops every run at the dry-run step; A12's `agents.traffic` and A101's per-user agent switches do not stop runs (the actor is a service account, not an agent) and a test proves both directions.
- Each run posts A17 AML intake lines through A17 as every credit does; a PayTo credit whose payer name fails A17's name rule is held there and the run is `funding_failed` with the generic reason.

## Node-specific challenges (node QA)

- **The run takes more than it was given (money).** The person holds A$3,000 of their own cash; the plan is A$500; the dry run finds A$4,000 of capacity. The node QA checks that exactly A$500 is collected, the budget is A$500 (not A$3,500), and the A$3,000 is untouched after the run; then has the person raise the plan to A$800 with a passkey (the version becomes effective and the agreement amendment is sent) without the payer re-authorising the amended agreement and checks the next collection is still at most A$500 with `PAYTO_AMOUNT_EXCEEDS_AGREEMENT` never reaching the rail; then replays `autoinvest.collect` and delivers `SIM-PT-DUP` and checks one payment, one receipt, one journal. Any extra cent pulled or spent fails the node.
- **Gates checked once, not per purchase (compliance).** Between the 07:00 dry run and the 10:00 placement the node QA (i) expires the investor's wholesale certificate, (ii) marks the investor out-of-market in a retail listing's TMD, (iii) lowers the listing's holder cap from 5 % to 1 % through a rule-pack change, (iv) halts one vehicle. Every affected line must be skipped at placement with the right `skip_gate` and its share paid as cash; an order placed on the dry run's stale result fails the node.
- **A first purchase slips through (compliance, G12).** With `any_open_offer`, a new trust opens; the person has a standing consent covering "all vehicles" and the CQ-02 parameter is set to allow delegated acknowledgement. The run must still produce a proposal, not an order, for the first purchase; then after the person accepts through INV-02, the second month's line in the same trust may be placed only if the IM version is unchanged. The node QA then publishes IM v2 and checks the third month is a proposal again.
- **The agent widens the plan (agent misuse, D04).** On an **active** plan, an investor's agent token with `autoinvest:manage` raises the amount from A$500 to A$5,000, switches `trusts_i_hold` to `any_open_offer`, turns reinvestment on, empties the `states` filter (`['NSW'] → []`), removes a sponsor exclusion and changes `run_day`, and then tries to confirm its own `confirmation_id` with its bearer token and to accept an open proposal. Expected: every widening returns `428 CONFIRMATION_REQUIRED`; the plan stays `active` with its effective version unchanged and the next run still uses A$500; at most one `pending_confirmation` version exists; the self-confirmation is refused (passkey only); the proposal is refused with `ACK_FIRST_PURCHASE_PERSON`; the same agent may pause and lower the amount at once (a narrowing, which supersedes the pending version). On a joint account with `signing_rule = both`, one holder's passkey leaves the version pending; A12's rejection or expiry leaves it `rejected` or `expired`, and a plan not yet started goes back to `draft`. Any widening that takes effect before the required passkey confirmations fails the node.
- **Tipping-off through the plan (compliance, security).** Two personas have active plans; A42 restricts one and a TRSY user suspends the other's plan under `SGL+R` (ratified). The node QA diffs INV-04, `GET /v1/autoinvest/plan`, `/runs`, the notification outbox, the webhook payloads, the sandbox bank's payer-side agreement view and the response timing for the two over the next run, field by field against the §9 list (`plan.state`, projected `paused_reason`, `agreement.state`, `next_run_on`, run `skipped_reason`, copy, codes): any difference fails the node. Neither agreement is suspended at the bank and neither receives a payment initiation. The node QA then lets the staff ratification lapse on a plan whose investor is also restricted and checks it does not revert while A42's flag is set.
- **Money arrives late, twice, or in someone else's name (money).** `SIM-PT-LATE` settles after the 15:00 cut-off; `SIM-MISMATCH` on the PayTo credit; `.51` insufficient funds three months running. Expected: `funding_failed` with the late money left as cash and not invested by the next run; the mismatched credit held by A17 with only A17's one `deposit.unmatched` suspense journal and nothing credited to `investor_cash`, and the run failed with the generic reason; a credit whose agreement reference is unknown held `unknown_destination` the same way; the plan `paused` after the third failure with exactly one notification each time.
- **The collection funds someone else's order (money).** At collection time the person has an `awaiting_funds` manual order, an agent order, and a retail order whose cooling-off ends during the run window. Expected: none of them is funded from the run's credit before `autoinvest.execute` finishes; the run's budget equals collected plus pool; after `autoinvest.run.executed` A37's sweep may fund them from the leftover cash only. The node QA then forces a withdrawal between funding and execution and checks the `funds` line and its INV-04 copy.
- **Retail cooling-off inside a run (money, G05).** With `orders.autoinvest_standing_consent = all`, a retail held-trust line is placed into `reflection_period`: its amount is in `reflection_cents`, the cash stays withdrawable, and at the timer's end the follow-up line is `reflection_funded` (or `reflection_expired` after the node QA withdraws the cash first, or `reflection_revoked` after a revoke) with one notification; the run identity holds throughout. With `outside_market_action = flag` and an out-of-market answer, no order is placed and the line is `skipped` G05.
- **The algorithm is not neutral (conflict, advice perimeter).** The node QA permutes sponsor fees, RealX platform-fee rates, sponsor ids and listing popularity across a seeded set of open offers and checks the run lines are byte-identical; then checks that the ordering depends only on close date and offering id, and that `algorithm_version` is on every run.
- **Design fidelity and the preview promise.** With the flag off in the Docker preview, INV-04 must match the design extension within tolerance, show the P3 banner, and make zero write calls while the node QA clicks every control; with the flag on, the AcknowledgeCard must reproduce the prototype's card (border and fill colours, 20 px box, ✓) and the primary button must be inert until ticked.
