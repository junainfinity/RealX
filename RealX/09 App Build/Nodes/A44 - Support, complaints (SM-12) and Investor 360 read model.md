# A44 - Support, complaints (SM-12) and Investor 360 read model

**The service behind ACC-04, ADM-27 and ADM-09: support tickets, the complaints register with its acknowledgement and final-response clocks as parameters (defaults 1 business day and 30 calendar days, both marked "set with counsel"; A13 seeds both rows), the mandatory ticket-to-complaint conversion, the RG 271 delay notice, redress proposed by the complaints handler and approved by the CCO (plus the CFO above A$5,000) and paid by treasury, AFCA escalation with AFCA's details shown to the complainant, reopen and retention; and the Investor 360 read model that composes one investor's profile, limits, wallets, holdings, orders, payouts, tax, documents, cases, messages, votes, tokens and mandates and audit trail, masked by default (unmask is A30's grant, checked here), where support sees only "account under review" and can change no money and no record.**

**Build status:** not started. **Milestone:** AM3 (Business services). **Lane:** Services. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops; two modules, about 45 routes, SM-12 with extensions, a ticket machine, two jobs, the redress, AFCA-redress and estate effectors, delay notices, the masking walk, close blockers, real contributors and three screen contract tests). The graph still carries 4-8 and must be raised to match (open item below).

**Depends on:** [[A30 - Investor onboarding, KYC cases and KYB (SM-01)]], [[A42 - AML screening, monitoring, cases and SMR clocks (SM-11)]]
**Upstream interfaces used through those dependencies (all ancestors in the graph, all called only through their public `index.ts`):** A03 (SM-12 table, matrix, `delegable.ts`), A04 (core `ticket` and `complaint` tables, `registerModuleSchema`, `mask()`, `PII_PATHS`, `retention_policy`), A09 (routes, outbox, job registry, injectable clock), A10 (audit, legal hold), A11 (sessions, matrix refusals), A12 (`agentAuth`, G22, introspection), A13 (clocks and alerts), A14 (approvals), A16 (ledger reads), A18 (register reads), A19 (gate registry, parameters, holder-cap readings), A28 (freeze state), A30 (investor record, unmask grants, internal transitions), A42 (AML ACL).
**Unlocks:** [[A59 - AUD wallet, token wallet and account screens]], [[A68 - Console- identity review, wholesale certificates, investor directory and Investor 360]], [[A75 - Console- AML cases, complaints register, marketing compliance, disclosure library]], [[A102 - Backups, restore drill, data retention and erasure]]

**Oracle rule:** this is not an oracle node (`oracle: no`): no money, supply or holdings move here (redress is paid by treasury under its own rules, never by this module). Personal data and a regulated clock do move here, so the node QA still writes hidden tests from this frozen spec to `<workspace>\gauntlet\hidden\A44\` before the build starts: an SM-12 transition oracle, the clock vectors, the tipping-off and masking probes, the support write-set probe and the design-seed fixtures. The builder never reads that folder; the tests are published into `app/` only after the gate passes ([[App Gauntlet]] §2).

This note is not legal advice. The acknowledgement and final-response periods, the AFCA wording and time-limit wording, the acceptance and reopen windows, the quiet period and the retention period are rows of data with defaults and a `set_with_counsel` marker (RG 271 territory, QA item 8 of the product map); counsel's answers change rows, not code.

## Build brief

**1. Scope and placement**

- Two API modules in the A09 pattern, each with a public `index.ts` (the only import other modules may use), zod schemas that feed the OpenAPI document from the first commit, and worker jobs `support.clock-watch` and `support.retention-sweep` on A09's injectable clock. Read contracts (ticket list and detail, complaint register, complaint detail, Investor 360 header and tabs) are in the OpenAPI document before any state logic exists so `packages/sdk` carries them and A104's generator can derive MCP tools from them.
- Schema. `ticket` and `complaint` are A04 core tables that this node shapes (A04 §2 lists A44 as their shaper). Any column this spec names that those core tables lack (for example `ticket.dissatisfied_at`, `complaint.redress_state`, `complaint.delay_notified_at`, `complaint.afca_channel`) goes to A04 as follow-up loop **A04.44**, a loop id unique to this node (A35 already claims A04.2); the graph must carry A04.44 before this build starts (open item below). The tables this node wholly owns are registered from its own path through A04's `registerModuleSchema({ node: "A44", tables, rlsClass, insertOnly, ... })` in `support/schema.ts`: `ticket_message` (insert-only), `complaint_event` (insert-only), `complaint_category`, `root_cause_code` and `afca_contact`. This node creates no `unmask_grant` table: grants are A30's (section 8).
- `support/` owns tickets, complaints, SM-12, the delay notice, the G18 evaluator registration, AFCA data and DDO root-cause data (module M23). `investor360/` owns the ADM-09 read model, the tab-contributor registry and this node's contributors, the masking walk, the unmask-grant check on tab reads, the estate request and the close blockers this node reports (module M06). Nothing in either module writes to the ledger, the register, the token tables, orders, distributions or `investor` state directly; the one change to an investor's state (the estate suspension) is made by A30's internal transition endpoint, called by this node's effector.
- **Write-set rule (support).** Under a SUPP session or a SUPP agent token, the tables written are: (1) the domain allow-list `ticket`, `ticket_message`, `complaint` (conversion and acknowledgement only) and `complaint_event`; (2) the named infrastructure tables every write touches: `audit_event`, `outbox_event`, `idempotency_key`, A13's clock and alert rows (`sla_clock`, `alert`), and `gate_evaluation`; (3) nothing else. A deny-list is asserted at zero writes: every ledger, register, token, holding, order, distribution, investor, `approval_decision`, `unmask_grant` and `legal_hold` table. A test proves all three (section 8).
- Time comes only from A09's injectable clock; `Date.now()` and argument-less `new Date()` are forbidden in the owned paths (A09's grep in `npm run verify`). Calendar-day clocks run through A13's `openClock` with `kind = calendar_days` in `Australia/Sydney`; this module never computes a deadline itself.

**2. Tickets (M23, SUPP)**

- `ticket` row: `id` (`TKT-<yyyymmdd>-<6 base32>`), `party_type` (`investor | sponsor_user`), `principal_id`, `tenant_id` (the sponsor tenant for sponsor tickets, the platform tenant for investors), `channel` (`chat | form | email | api`), `category` (from `complaint_category`, shared list), `subject`, `state`, `assignee_id` (SUPP), `dissatisfied_at`, `converted_complaint_id`, `opened_at`, `last_activity_at`, `resolved_at`, `closed_at`. `ticket_message` rows are insert-only (`author_principal_id`, `on_behalf_of_id`, `body`, `created_at`, `internal` flag for staff notes the customer never sees, `attachments` as A08 object references, `dissatisfied` flag, and, when staff classify it later, `dissatisfied_classified_by`, `dissatisfied_classified_at` and `dissatisfied_classification_reason`, stored as a separate insert-only classification row keyed to the message so the message itself never changes).
- Ticket lifecycle (a local machine `TICKET`, not one of SM-00..SM-13, documented in the module): `open -> waiting_on_customer | waiting_on_realx -> resolved -> closed`, `resolved -> open` on a customer reply within 14 days (parameter), `open | waiting_* -> converted` when a complaint is opened from it. `closed` and `converted` are terminal. Every transition not in the table returns `409 TICKET_TRANSITION_NOT_ALLOWED` with the current state.
- Dissatisfaction is a fact recorded on a message, not an inference: the customer ticks "I am not happy with how this was handled" on ACC-04 (or passes `dissatisfied: true` through the API), or a SUPP classifies an existing message as dissatisfied with a reason. **`ticket.dissatisfied_at` is always the `created_at` of the earliest message flagged dissatisfied, whether the investor flagged it when writing or SUPP classified it later**; the classifier, classification time and reason are stored separately and shown on the timeline, and a later classification of an earlier message moves `dissatisfied_at` back to that message's `created_at` (never forward). Once set, conversion is mandatory: the ticket cannot be `resolved` or `closed` while `dissatisfied_at` is set and `converted_complaint_id` is null (`409 TICKET_CONVERSION_REQUIRED`), the ADM-27 ticket queue shows it with the "convert" action first, and the A13 queue source reports it under policy `complaint_conversion` (1 business day, Sev3 to CMPH on breach). A plain keyword list (`complaint`, `not happy`, `unacceptable`, `AFCA`, `ombudsman`, `compensation` and their variants, a data file) only suggests classification in the staff view; no model is used in P1, so there is no prompt-injection surface here (risk register item for any later AI triage).
- Sponsor-user tickets never become complaints (the complaints register is for investors as clients of the licensee); a dissatisfied sponsor ticket becomes a partner escalation for PART through the outbox event `ticket.sponsor_escalation` (proposed; the user decides at Specify).
- Help search is a read over A35's published help articles and platform documents (including the complaints policy) when that module is available through the graph; until then `GET /v1/support/help?q=` returns `{items: [], next: null, fallback: "chat"}` so ACC-04 renders its empty state and the chat button. A35 is not an ancestor of this node, so the help source is a registration point (`registerHelpSource(fn)` exported from `support/index.ts`) that A35 or an integration node fills; this node's tests use an in-module fake.

**3. Complaints and the SM-12 machine (M23, G18)**

- `complaint` row: `id` (`C-<4+ digits>` from a sequence so the fixture pack reproduces `C-1042`, `C-1037`, `C-1011`), `investor_id`, `ticket_id` (nullable: a complaint may be lodged directly on ACC-04), `category`, `description`, `desired_outcome`, `sponsor_id` and `vehicle_id` when the complaint concerns a listed trust, `received_at`, `ack_due_at`, `acknowledged_at`, `final_response_due_at`, `delay_notified_at`, `response_issued_at`, `response_text`, `redress_cents`, `redress_source` (`idr | afca`), `redress_approval_id` (A14), `redress_state` (`none | pending_approval | approved | held | settled`), `redress_journal_id` (A16, set by treasury's callback), `afca_reference`, `afca_escalated_at`, `afca_channel`, `afca_outcome`, `root_cause_code`, `handler_id` (CMPH), `state` (SM-12 enum from A03), `reopened_count`, `resolved_at`, `closed_at`, `retention_until`, `legal_hold_id` (A10). `complaint_event` is insert-only and records every transition and notice with actor, `on_behalf_of_id`, reason and the approval id when one applies; it is the timeline ACC-04 and ADM-27 render.
- Conversion (`POST /v1/tickets/{id}/convert`, SUPP, no checker, mandatory) creates the complaint in `received` with `received_at = ticket.dissatisfied_at` (the created time of the earliest dissatisfied message, never the moment staff classified or converted it), copies the thread as the first `complaint_event`, records the conversion delay on the timeline, moves the ticket to `converted` and opens the acknowledgement and final-response clocks from `received_at` (a clock whose deadline is already past opens breached). A direct lodgement (`POST /v1/complaints`, investor, ACC-04 "Lodge a complaint") sets `received_at` to the request time.
- SM-12 transitions come from A03's table (9 states, 11 transitions between named states) and are applied only through the A03 engine: `received -> acknowledged : within SLA` (CMPH or SUPP acknowledges; the acknowledgement text is sent through the outbox event `complaint.acknowledged` and stops the acknowledgement clock, met or breached); `acknowledged -> investigating` (CMPH takes ownership, `handler_id` set); `investigating -> redress_proposed` (CMPH proposes an amount); `redress_proposed -> response_issued : CMPH then CCO` (the A14 request below is approved and the response is issued together); `investigating -> response_issued : no redress` (an A14 `4E` request `complaint.final_response.issue`, CMPH maker, CCO checker); `response_issued -> resolved : accepted` (the investor accepts on ACC-04 or by reply, or the acceptance window elapses without objection, parameter default 30 days; whether silence may count as acceptance is a counsel question, below); `response_issued -> escalated_external : AFCA`; `escalated_external -> resolved : outcome implemented`; `resolved -> reopened : new information` (CMPH with reason, or the investor from ACC-04 within the reopen window, parameter default 30 days); `reopened -> investigating`; `resolved -> closed : retention starts` (the retention sweep, after the quiet period). Every transition not in the table (or in the accepted extensions) returns `409 SM12_TRANSITION_NOT_ALLOWED` naming the current state; every applied transition writes one `complaint_event`, one A10 audit event `sm.complaint.<trigger>` and, where a clock changes, one A13 clock call.
- **Window invariant.** The quiet period is a parameter with default 30 days and a validated invariant `quiet_period >= reopen_window` (and `>= acceptance_window` is not required because the quiet period starts at `resolved`). A policy change that breaks the invariant is refused by the parameter write with `422 COMPLAINT_WINDOW_INVARIANT`, so an investor can always use the full reopen window before the complaint closes.
- Spec gaps to settle at Specify, before the node QA writes the hidden tests, proposed as entries in A03's `extensions.ts` with this node as source and no new state: (a) `redress_proposed -> investigating : redress rejected` when the CCO (or CFO) rejects the A14 request, otherwise a rejected redress leaves the complaint stuck; (b) `investigating -> escalated_external : complainant goes to AFCA` and `acknowledged -> escalated_external`, because AFCA accepts a complaint RealX has not answered in time whether or not a response was issued; (c) `escalated_external -> closed : AFCA closed without a finding` for a complaint AFCA discontinues; (d) `resolved -> escalated_external : complainant goes to AFCA after resolution` and (e) `closed -> escalated_external : AFCA accepts a closed complaint`, because AFCA generally accepts a complaint up to two years after the IDR response, well after the quiet period; (e) keeps `retention_until` and the legal hold untouched and reopens only the AFCA fields for writing. The user decides; declined items are recorded in `A44.qa.md`, and if (d) or (e) is declined, `POST /v1/complaints/{id}/afca` on a resolved or closed complaint is instead accepted as a permitted record-only write (like a legal hold) that sets the AFCA fields and a timeline entry without a state change, so an AFCA matter is never unrecordable.

**4. Clocks, G18, delay notices and AFCA**

- `sla_policy` rows `complaint_ack` (1 business day, `kind = business_days`) and `complaint_final_response` (30 calendar days, `kind = calendar_days`), both `set_with_counsel = true`. **A13 seeds these two rows and is their only seed** (A13's seed list; this node reads them and never writes a second default, so the two nodes' oracles cannot disagree). One business day is the safe side: RG 271 expects acknowledgement within 24 hours or one business day. This node seeds only its own rows: `complaint_conversion` (1 business day), `complaint_acceptance_window` and `complaint_reopen_window` (30 calendar days each, proposed), `complaint_quiet_period` (30 calendar days, invariant above) and `complaint_delay_notice_warning` (warn at 80 percent of the final-response clock when neither a final response nor a delay notice exists). Counsel may confirm or change the periods (RG 271 speaks of one business day for acknowledgement and 30 calendar days for the final response for most complaints, with shorter periods for some products); that is a data change in A13's rows and a re-run of the clock tests, not a code change. The product map's "acknowledgement due by day 5 of 7" is read only as an internal warning threshold, never as the deadline: warn CMPH at 60 percent of the acknowledgement clock (Sev4, dedup per complaint), breach at the deadline (`queue.sla_breach`, Sev3, owner CMPH, queue `complaints`), and a final-response breach raises `queue.sla_breach` at Sev2 to CCO because a late final response is what makes AFCA available to the complainant. The reading is confirmed at Specify.
- **IDR delay notification (RG 271).** `POST /v1/complaints/{id}/delay-notice` (CMPH, no checker; a CMPH's agent may draft it, and a draft returns `428 CONFIRMATION_REQUIRED` in A12's shape until the handler confirms with a fresh passkey assertion) takes `{ reasons }` and is accepted only before `final_response_due_at` (after the deadline it is `409 DELAY_NOTICE_TOO_LATE`, and the breach stands). It records `delay_notified_at`, writes a `complaint_event`, emits `complaint.delay_notified` for A43 to send, and does not move the deadline or the state. G18 reports `delay_notified` until the response is issued or the deadline passes.
- **AFCA details in every notice.** Every final-response and delay-notice payload carries the `afca_contact` block (name, website, phone, email, postal address) and the `time_limit_wording` row (the time limit for taking the complaint to AFCA, `set_with_counsel`). The server composes both from the rows; a final response or delay notice issued while either row is missing, expired or incomplete is refused with `422 AFCA_DETAILS_REQUIRED` naming the missing field.
- `evaluateG18(complaint, now, policies)` is a pure function in `packages/domain/src/support/g18.ts` (this node's own folder in the domain package, listed in owned paths) registered with A19's gate registry as the evaluator for G18, returning `{ status: on_time | ack_due_soon | ack_overdue | delay_notified | response_due_soon | response_overdue | with_afca | closed, afca_prominent: boolean, days_remaining }`. It is recorded as a `gate_evaluation` row (gate G18) on every SM-12 transition and notice and once a day per open complaint by `support.clock-watch`, so ADM-27's register columns and the ADM-01 "complaints" operations queue are reads of the latest evaluation. G18 refuses nothing; it is a monitoring gate, and the daily platform summary (`GET /v1/complaints/summary`) reports open, overdue acknowledgements, overdue responses, delay notices and with-AFCA counts for J20 step 11.
- `afca_contact` is one platform row (`name`, `url` www.afca.org.au, `phone` 1800 931 678, `email`, `postal`, `wording`, `time_limit_wording`, `effective_from`, `set_with_counsel`), returned by `GET /v1/support/afca` and embedded in every complaint read. `afca_prominent` is true when the acknowledgement is overdue and not yet given, when the final response is overdue, when a final response has been issued (the complainant may take it to AFCA), when the complaint is `escalated_external`, and whenever the investor has been waiting longer than the final-response period in any state; once true for a complaint it stays true. ACC-04 renders the small line always and the prominent card when the flag is true. The wording never claims an outcome or a time AFCA will take.
- `POST /v1/complaints/{id}/afca` (CMPH, no checker) records `afca_reference`, `afca_escalated_at` and the channel, moves to `escalated_external` (from `response_issued`, or from the states the accepted extensions allow), cancels RealX's own response clock (`cancelClock`, reason `afca`), freezes `description`, `desired_outcome` and `response_text` against edits, and emits `complaint.afca_recorded` so A43 tells the investor what happens next. `POST /v1/complaints/{id}/afca-outcome` records the outcome; when it carries redress, the AFCA-redress path in section 5 runs and `escalated_external -> resolved : outcome implemented` applies only after treasury's settlement callback.

**5. Redress: proposed here, approved through A14, paid by treasury, never by this module**

- `POST /v1/complaints/{id}/redress` (CMPH maker) is accepted only in `investigating` and only when `root_cause_code` is set (`422 ROOT_CAUSE_REQUIRED`). It creates an A14 `ApprovalRequest` `complaint.redress.propose` with `object_ref` the complaint, `amount_cents` in A02 integer cents, the beneficiary investor and the response text; A14's policy table selects `4E` (CCO checker) up to A$5,000 and `6E` (CCO and CFO checkers) above A$5,000.00 (`amount_cents >= 500001`), and A14's segregation of duties applies (the handler cannot check; a CMPH's agent may draft the request as maker, counts as its human for segregation, and can never approve; an agent's draft returns `428 CONFIRMATION_REQUIRED` in A12's shape until the handler confirms with a fresh passkey assertion or a mandate signing key covers M23 drafts). The threshold is a policy row, not a constant.
- **AFCA-outcome redress.** `POST /v1/complaints/{id}/afca-outcome` with an amount creates an A14 request `complaint.afca_redress.implement` (this node registers the action and its policy rows with A14: `4E` CCO checker up to the same threshold row, `6E` CCO and CFO above it), allowed only while the complaint is `escalated_external`, with `redress_source = afca` and the AFCA reference in the payload. The same segregation and agent rules apply.
- On approval of either request the effector stores `redress_approval_id`, sets `redress_state = approved` and emits `complaint.redress.approved` (amount, investor, approval id, complaint id, source). For IDR redress it also moves `redress_proposed -> response_issued` and emits `complaint.response_issued`; for AFCA redress the complaint stays `escalated_external` until settlement. Treasury (A39) is meant to consume `complaint.redress.approved`, pay under G02 and G14 as a client-money credit to the investor's AUD wallet or a payout to the verified bank account under its own rules (name match, AML restriction hold, thresholds) and call `POST /v1/internal/complaints/{id}/redress-settled` (service principal only) with the A16 journal id; that consumer is not yet in A39's spec (open item below). In this node's tests a fixture treasury settles. On settlement the effector sets `redress_journal_id` and `redress_state = settled`, and for AFCA redress applies `escalated_external -> resolved : outcome implemented`. If treasury holds the payment (for example an AML restriction from A42), `redress_state = held` and the investor-facing timeline says "payment under review", never why.
- A redress amount of zero is refused (`422 REDRESS_AMOUNT_REQUIRED`; use the no-redress path); an IDR proposal outside `investigating` or an AFCA-redress request outside `escalated_external` is `409 SM12_TRANSITION_NOT_ALLOWED`; a second open redress request on the same complaint is `409 REDRESS_PENDING` naming the approval id; a rejected IDR request applies extension (a) or, if declined, leaves the complaint in `redress_proposed` with the rejection reason on the timeline.

**6. Reopen, retention, DDO root cause and the licensee's view**

- Reopen (`POST /v1/complaints/{id}/reopen`, CMPH with a reason, or the investor from ACC-04 inside the reopen window) moves `resolved -> reopened`, increments `reopened_count`, records the reason on the timeline and opens a fresh final-response clock from the reopen time (counsel question: whether the original deadline survives a reopen; the default is a fresh clock because the default is the safer reading for the investor). `reopened -> investigating` is immediate when a handler takes it. An investor reopen after the window is `409 REOPEN_WINDOW_ELAPSED` and the response points to AFCA.
- `support.retention-sweep` (daily 03:00 Sydney, idempotent) moves `resolved -> closed` after the quiet period, sets `retention_until = closed_at + 7 years` from A04's `retention_policy` row for `complaint`, and thereafter refuses every write with `409 COMPLAINT_CLOSED` except a legal hold (A10), AFCA recording (extension (e) or the record-only write in section 3) and A102's erasure path, which pseudonymises the investor reference but keeps the complaint row, its dates, category, root cause and redress amount because they are regulatory records (N02 retention, counsel to confirm).
- DDO root-cause data: every complaint carries a `root_cause_code` (a data list: `distribution_calculation`, `withdrawal_delay`, `disclosure_unclear`, `fees`, `vote_process`, `service`, `privacy`, `platform_error`, `sponsor_conduct`, `other`) set by the handler before a redress proposal or a final response can be made (`422 ROOT_CAUSE_REQUIRED`), plus `vehicle_id` and `offering_id` when known. `GET /v1/complaints/ddo-summary?vehicle=&from=&to=` groups counts and redress by root cause and category; in P1 it feeds ADM-27's root-cause panel and PUB-05's "incidents and complaints" count (aggregate only, never a complaint's content), and in P2 A32's target-market review reads it (the endpoint exists in P1; the P2 consumer is phase-flagged in A08).
- TP-LIC (the licensee) has read-only access to the register and complaint detail with personal data masked, through the same routes under the PARTNER principal type of A98. A98 is not an ancestor, so this node proves the rule with a fixture partner principal; the re-test under A98's real principal belongs in A98's pass criteria (open item below). Sponsors see only counts on their own vehicles.

**7. Investor 360 read model (M06, ADM-09)**

- `GET /v1/investor360/{id}` returns the header and the tab index for one investor: `display_name` masked by A04's `mask()` codec (the ADM-09 string "Alex N."), `investor_code` (`INV-004821`), `type`, `slice` (the viewer's slice, below), header chips `identity` (valid to date, from A30), `classification` (wholesale to date, from the classification contributor when registered, else `not_available`), `residency`, `risk_rating` and `pep` (only in the slices listed below), `restriction` (`none | under_review | estate | suspended` as the viewer may see it), and `tabs[]` each with `key`, `available`, `owner_node`, `phase`, `count` where cheap. Tabs, in ADM-09's order: `profile`, `limits`, `wallets`, `holdings`, `orders`, `payouts`, `tax`, `documents`, `cases`, `messages`, `votes` (P2), `agents` (tokens and mandates, the D04 addition), `audit`.
- Composition is by registry: `Investor360Contributor { key, slices[], phase, list(investorId, viewer, cursor, unmaskGrant?) }` and `registerInvestor360Contributor(c)` are exported from `investor360/index.ts`, plus `unservedTabs(phase)` which lists P-phase tabs with no real contributor. **This node ships real contributors built from its ancestors' public read functions** (the exact function names are those ancestors' exports; a read this node needs that an ancestor does not export is an upstream data defect to escalate, not a query this node writes against another module's tables):
  - `profile` from A30's masked record plus this node's complaints and tickets summary;
  - `limits` from A19's `getEffectiveParams` and its G07 holder-cap readings per trust;
  - `wallets` from A16 (the AUD wallet balance and client-money account state) and A28 (freeze state); the smart-account section (address, passkey, guardians, chain risk) is added by A29's contributor;
  - `holdings` from A18's register lots and register-match status, with A28's freeze state per holding;
  - `payouts` from A16's journal lines of distribution and redress credits; the run detail is added by A40's contributor;
  - `cases` (KYC cases from A30 for every staff slice; AML cases from A42 only when the viewer is MLRO or CCO, through A42's own ACL, so support never receives even a count; the estate record for the legal slice);
  - `messages` (tickets and complaint timelines), `agents` (A12's introspection of the investor's tokens and mandates, secrets never present) and `audit` (A10's `GET /v1/audit/events?object=` filtered to the investor as object or on-behalf-of).
- Contributors owned by nodes that are not ancestors of this node: `orders` (A37), `tax` (A41), `documents` (A35), the `classification` chip (A32), the smart-account section of `wallets` (A29), the distribution-run detail of `payouts` (A40), statement links (A47) and `votes` (the P2 governance node A93). Each of those must register its contributor and pass this node's contributor contract test; that pass criterion belongs in each owning spec or in an integration node before A68 (open item below). Until registered, a tab returns `200 { available: false, owner_node, phase }` and the screen shows its "not yet available" state rather than an empty table. A contract test in this node pins the interface so those nodes implement it unchanged, and `unservedTabs("P1")` is what A68 and A88 assert to be empty (P2 `votes` excepted).
- Slices by role, decided server-side from A03's matrix (cells `M06.investor360.view_support`, `M06.investor360.view_onboarding`, `M06.investor360.view_compliance`, `M06.investor360.view_ir`, `M06.investor360.view_legal`, `M06.investor360.view_complaints`):
  - `support` (SUPP): profile, messages, cases limited to KYC state names and complaints, agents, holdings and payouts read-only; `restriction` collapses everything to `under_review`; no risk, PEP, hit, score, screening or AML content, and no document images;
  - `onboarding` (KYCA): plus documents, risk, PEP, KYC case detail;

**8. Masking, unmask grants and the support restriction**

- Every field in `PII_PATHS` (A04) is masked in every Investor 360 response by A04's `mask()` codec, whose formats are fixed by A04's snapshot tests against the prototype strings; this node restates none of them. Masking happens in the response serialiser from the schema, never by hand in a handler, and a test walks every tab's response against `PII_PATHS` using A04's snapshot as the expected shape.
- **Unmask is A30's.** `POST /v1/investors/{id}/unmask`, its reason codes, its permitted roles (SUPP and IRCM never unmask), its 15-minute grant bound to the session, its `AGNT_NOT_ALLOWED` refusal for tokens and its audit code `investor.pii.unmasked` are all defined and implemented by A30 in `investors/`. This node registers no unmask route, no reason-code list and no grant table. Investor 360 tab reads carrying `X-Unmask-Grant` call A30's exported `validateUnmaskGrant(grantId, session, investorId, fields)` (A30 must export it from `investors/index.ts`; open item below) and return clear values only for the granted fields while the grant is live; an expired, foreign-session, other-investor or wider-than-granted use is `403 UNMASK_GRANT_INVALID` (A30's code), and each clear read writes one `investor.pii.unmasked` event naming the grant and the fields only, through A30's recorder so both modules emit one code. - Support restriction, in three layers that the node QA probes independently: (1) A04 row-level security makes `aml_case` and `aml_alert` invisible to a SUPP session; (2) the `support` slice omits the fields and tabs above even when a row is visible (a KYC case shows `state: reviewing`, never a hit or a score); (3) the SUPP role has no cell on the ledger, register, token, orders, distributions, tax or approvals modules, and this node's routes under SUPP write only within the write-set rule of section 1. ## Node-specific challenges (node QA)

- **The clock that starts late (compliance).** An investor writes "this is unacceptable, I want my money back" on a ticket on Friday 2 October 2026 at 17:30 AEST without ticking the box; a SUPP classifies that 2 October message as dissatisfied on Wednesday 7 October at 09:00 AEDT and converts the ticket at 09:05. `dissatisfied_at` and `received_at` must be 2 October 17:30 AEST (07:30 UTC), the classifier and 7 October classification time must be stored separately, `ack_due_at` must be 17:00 on Tuesday 6 October AEDT (06:00 UTC) under A13's business-day rule: the message arrived after close of business on Friday, Monday 5 October is Labour Day in NSW, and DST began on 4 October. The complaint is therefore already `ack_overdue` when it is converted on 7 October, and the register must show the classification and conversion delay on the timeline. A second vector: the same message classified on 9 October (after the acknowledgement deadline) opens the complaint with its acknowledgement clock already breached, raises `queue.sla_breach` to CMPH once and keeps `received_at` on 2 October. A node that stamps `received_at` at classification or conversion, adds 86,400 seconds instead of one business day, counts Labour Day as a business day, or lets the ticket be resolved instead of converted fails.
- **Redress just over the line (money).** A CMPH proposes A$5,000.00 and then, on a second complaint, A$5,000.01: the first request must resolve to `4E` (CCO only), the second to `6E` (CCO and CFO), the CMPH must be refused as checker on both, the CMPH's agent token must be able to draft both as maker and be refused on approve with `G22_AGENT_NEVER_CHECKER`, and no ledger row may exist in this module's tables or be written by this module's code: the only money movement is the fixture treasury's journal, referenced back by id. A second `redress` call while the first is pending must return `409 REDRESS_PENDING`; a proposal without a root cause must return `422 ROOT_CAUSE_REQUIRED`. Repeat the threshold on an AFCA outcome in `escalated_external`: the request must be `complaint.afca_redress.implement` under the same policy, refused in any other state, and the complaint must stay `escalated_external` until the settlement callback.
- **Support asks about a frozen investor (compliance, tipping-off).** An investor has an open AML case with a wallet freeze from A42's fixture. A SUPP session and a SUPP agent token call the Investor 360 header, every tab, the ticket list and the complaint list, then try `?state=` filters that would only match AML rows and request a non-existent AML case id: every response must be indistinguishable from the same calls for an investor with no case except `restriction: under_review`, with identical status codes, no count, tab or error text that differs, and a median latency difference under 20 ms over 200 paired calls. The investor's own `GET /v1/complaints/me` for a complaint whose redress is held must say "payment under review" and nothing else. A single leaked field fails the node.
- **The support role tries to change a record (security).** Under a SUPP session, replay every route of this module and of the modules it imports with the touched-table trigger on: the tables written must be only the domain allow-list (`ticket`, `ticket_message`, `complaint` on convert and acknowledge only, `complaint_event`) and the named infrastructure tables of section 1, and every deny-list table (ledger, register, token, holding, order, distribution, investor, `approval_decision`, `unmask_grant`, `legal_hold`) must show zero writes. Then attempt, as SUPP, `POST /v1/complaints/{id}/redress`, `final-response`, `afca`, `POST /v1/investors/{id}/estate`, A30's unmask route and a direct `POST /v1/internal/complaints/{id}/redress-settled`: each must be refused by A11's matrix check (`403 forbidden`, reason `NO_CELL`) before any handler runs, with A11's refusal audit event, and no row changed. The same attempts under a SUPP agent token are refused by A12 with a `gate.refused` G22 audit event.
- **Grant misuse on tab reads (security).** A KYCA obtains an A30 grant for `contact` fields on investor A with a case reference, then presents it on investor A's `holdings` tab (clear contact fields only), on investor B, on a `bank` field, after 16 minutes, and from a second session that copied the header: the last four are `403 UNMASK_GRANT_INVALID`, the only `investor.pii.unmasked` events are A30's grant event plus the legitimate reads, and the events carry field names only (a grep of the audit table for the investor's real name, TFN or account number finds nothing).
