# A07 - Local chain and contracts toolchain (Hardhat, T-REX vendored)

**A pinned Hardhat project with the T-REX (ERC-3643) reference implementation vendored as a checksummed git submodule, EntryPoint v0.7 deployed from its canonical init code at its canonical address, and a deterministic Hardhat chain running as a Docker service with test-controlled mining, so that every later chain node builds and tests on a known-good toolchain on Node 24.21.0. No RealX Solidity is written here.**

**Build status:** not started. **Milestone:** AM0 (Foundations). **Lane:** Chain. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 6-10 agent-hours (build, challenge and verify loops).

**Depends on:** [[A01 - Repo scaffold, toolchain and verify command]]
**Unlocks:** [[A23 - Whole-stack Docker boot (AM1 exit)]], [[A24 - ERC-3643 suite and RealX compliance modules]], [[A26 - Passkey smart wallet, paymaster and guardian recovery contracts]]

**Oracle rule:** this node has no hidden oracle (`oracle: no`); no money, supply or holdings move here, and the vendored T-REX test suite (written upstream, not by the builder) is the reference behaviour. The node QA still writes its Challenge material to `<workspace>\gauntlet\hidden\A07\` before the build starts, from this note alone: the independent checksum script (commit SHA, git tree SHA, per-file SHA-256 list), its own derivation of the expected upstream test and skip counts, its own derivation of the EntryPoint v0.7 runtime code hash, the fault plants (tampered vendored byte, mainnet chain id, non-loopback RPC, `RUN_MODE=production`, default mnemonic on a public network, a stray `.sol` outside `contracts/vendor/`, `contracts/src/` and `contracts/test/`, a T-REX interface copied into `packages/`, a legitimate import of a vendored contract from `contracts/src/`, a `hardhat_setCode` aimed at the EntryPoint address), the two-boot comparison and the expected output of each. The builder never reads that folder; the material is published into `app/` only after the gate passes ([[App Gauntlet]] §2). Money, supply and holdings first move in [[A24 - ERC-3643 suite and RealX compliance modules]] and [[A26 - Passkey smart wallet, paymaster and guardian recovery contracts]], which are oracle nodes.

## Build brief

This node is toolchain only. It proves that the open-standard token layer assumed under Q12 option 1 (a proposed, reversible engineering decision) compiles, tests and runs on the build machine (Windows 11, Node 24.21.0, Docker 29.8.0, Git 2.55) before any RealX contract exists. Everything below is testable from a fresh clone made with `git clone --recurse-submodules`.

**Hardhat project (`<workspace>\app\contracts\`)**
- npm workspace `@realx/contracts-hardhat` on the Hardhat 2.26 line with `@nomicfoundation/hardhat-toolbox` (ethers v6, chai, hardhat-network-helpers, typechain) and a TypeScript config. Every version in `contracts/package.json` is an exact pin (no `^` or `~`, A01's `.npmrc` `save-exact` rule) chosen after a real install on Node 24.21.0; the resolved versions land in A01's root `package-lock.json`.
- Compiler list in `hardhat.config.ts`: solc 0.8.17 with T-REX's own optimizer settings (the entry every T-REX, ONCHAINID and later A24 source uses, so T-REX bytecode matches upstream), and solc 0.8.23 (the entry for sources that import `@account-abstraction/contracts` 0.7, whose core files need `^0.8.23`; this is the slot A26 uses, already declared here so A26 does not touch the compiler list). Each entry records the solc long version (with commit hash) and the SHA-256 of the compiler binary in `contracts/TOOLCHAIN.md`. The source-path mechanism (how the compile reaches `contracts/vendor/T-REX/contracts` and later `contracts/src/` without copying any file) is chosen by the builder, written in `TOOLCHAIN.md`, and must leave upstream's source paths intact.
- **Library coexistence (a deliverable of this node).** T-REX v4.1.x and `@onchain-id/solidity` are built on OpenZeppelin 4.x (`@openzeppelin/contracts` and `@openzeppelin/contracts-upgradeable`), while `@account-abstraction/contracts` 0.7 imports OpenZeppelin ^5, and Hardhat 2 resolves one version per package name. Rules: (1) `@openzeppelin/contracts`, `@openzeppelin/contracts-upgradeable` and `@onchain-id/solidity` are pinned in `contracts/package.json` to exactly the versions resolved in the pinned T-REX tag's own `package-lock.json`, and a verify check fails if they differ. (2) OpenZeppelin 5 reaches account-abstraction sources by one mechanism, chosen in this order and recorded in `TOOLCHAIN.md` with the probe result: (a) if the Hardhat 3 trial below adopts Hardhat 3, its per-package npm resolution and remappings; otherwise (b) OpenZeppelin 5 installed under the npm alias `@openzeppelin/contracts-v5` plus a remapping applied only to files under `@account-abstraction/contracts/`, supplied through Hardhat 2's remappings subtask in `contracts/toolchain/remappings.ts`; and only if (b) cannot scope the remapping, (c) a separate A07-owned Hardhat sub-project at `contracts/aa/` (solc 0.8.23, OpenZeppelin 5, its own exact-pinned lockfile installed by `setup:chain` and audited by A07's registered verify step). (3) A probe test (`contracts/test/toolchain/aa-probe.test.ts`) writes a throwaway 0.8.23 contract that imports the account-abstraction 0.7 interfaces and `BaseAccount` into a gitignored scratch folder, compiles it through the chosen mechanism, and then proves that the metadata-stripped deployed bytecode of every T-REX contract is unchanged by the presence of the 0.8.23 entry and the OpenZeppelin 5 copy. EntryPoint itself is never compiled by RealX (see below).
- Compiling twice from clean produces byte-identical artifacts for every T-REX contract.
- Networks: `hardhat` (in-process, chainId 31337) and `localhost` (the Docker chain, `http://127.0.0.1:8545` from the host, `http://chain:8545` inside compose). A `baseSepolia` entry (chainId 84532) exists for later testnet runs only; it is usable only on an explicit `--network baseSepolia` run with `CHAIN_ID=84532` and a `CHAIN_RPC_URL` host on the testnet list, and it never uses the Hardhat default mnemonic (its deployer key is supplied at run time by the node that first deploys to Base Sepolia). A `redbellyTestnet` entry (chainId 153) is a commented placeholder. There is no mainnet entry of any kind. A unit test asserts that the exported config contains no network with chainId 1, 8453 or 151, and that no network other than `hardhat` and `localhost` can use the Hardhat default mnemonic.
- **Config guard** (`contracts/toolchain/guard.ts`, imported by `hardhat.config.ts` and run by the chain container's entrypoint before `hardhat node` starts; Hardhat loads its config outside the app's config loader, and A07 does not depend on [[A08 - Sandbox adapter framework, config and phase flags]]). It reads the same variables as A08's `packages/config`: `RUN_MODE`, `CHAIN_ID` and `CHAIN_RPC_URL` (it never reads a network-specific variable such as `BASE_SEPOLIA_RPC_URL`). It evaluates every rule and reports every failure at once, then exits non-zero:
  - `RUN_MODE` other than unset, `local` or `test` fails with `RUN_MODE_NOT_ALLOWED` (no production mode exists in this build; adding one is a change under HG-PROD).
  - `CHAIN_ID` outside `{31337, 84532}` fails with `CHAIN_ID_NOT_ALLOWED`; inside the chain container only 31337 is allowed.
  - `CHAIN_RPC_URL` host: for chain id 31337 (or unset) only loopback (`localhost`, `127.0.0.1`, `::1`) and the compose service name `chain`; for 84532 only the testnet host list (A08's `*.base.org` hosts), and only when the selected network is `baseSepolia`. Anything else fails with `CHAIN_RPC_NOT_LOCAL`.
  - The Hardhat default mnemonic or any `accounts.json` key on a network other than `hardhat` or `localhost` fails with `DEFAULT_KEY_NOT_LOCAL`.
  - The chain-id set and both host lists are written in `contracts/TOOLCHAIN.md` as a copy of A08's lists, so A23 can assert the two agree.
- npm scripts in `contracts/package.json`: `compile`, `test` (RealX contract tests; at this node only A07's toolchain tests under `contracts/test/toolchain/`), `test:trex` (the vendored suite, see below), `setup:chain` (submodule init, checksum check, working copy and its install), `chain:up`, `chain:down`, `chain:smoke`. `chain:control` lives in `packages/chain-control`. Root aliases (`npm run chain:up` and so on) are added under A01's script-registration convention. A01's `npm run verify` iterates over workspaces, so A07's typecheck, compile, guard tests, AA probe, manifest check, OpenZeppelin pin check, `.sol` placement check and licence-boundary check run inside `verify` without Docker; the Docker chain smoke, the `chain-control` tests against Docker and the full T-REX suite run under `npm run verify:chain`, which needs Docker Desktop and takes minutes, and which A23's boot criterion calls.
- Secrets scanner allow-list: the Hardhat default mnemonic and the deterministic account keys trip A01's scanner by design. A07 appends the expected entries to `scripts\secrets-allowlist.json` (file, SHA-256 of the exact string, reason "Hardhat public test mnemonic, no value"), as A01 anticipated; this is a named, append-only exception to A07's owned paths (see Owned paths), and no other allow-list entry is added by this node.
- Hardhat 3 trial: the builder runs a scripted trial in a scratch folder outside the repo (a copy of `contracts/` plus the submodule on Hardhat 3) and records the outcome in `contracts/TOOLCHAIN.md`: Hardhat 3 is adopted only if the T-REX suite compiles and passes with zero source changes; otherwise the 2.26 line stays and the note says what broke. Either way the decision, the versions and the date are written down so A24 and A26 do not repeat the trial.
- **Solidity placement rule (final form, written now so later nodes never edit it):** a `.sol` file may exist only under `contracts/vendor/`, `contracts/src/` (A24, A25, A26), `contracts/test/` (test mocks) and, only if coexistence mechanism (c) is chosen, `contracts/aa/`; `node_modules`, generated output and gitignored scratch folders are excluded. At this node `contracts/src/` does not exist and A07 writes no committed `.sol` file.
- **Local deployment output folder:** `contracts/deployments-local/<chainId>/` (gitignored in `contracts/.gitignore`) is where A24, A25 and A26 deploy scripts write their per-suite JSON fragments (addresses, salts, config hash, artifact bytecode hashes, block number); A27 reads it and is the only writer of the committed manifests. The fragment schema is in `TOOLCHAIN.md`.

**T-REX vendored (`<workspace>\app\contracts\vendor\`)**
- `contracts/vendor/T-REX` is a git submodule of the upstream ERC-3643 reference implementation pinned to a v4.1.x release tag (the latest 4.1 patch tag at build time; the builder records the exact tag). Not a branch, not a fork, never patched in place, and nothing is ever installed or built inside it. The root `.gitmodules` entry (owned by A07) sets `ignore = dirty` for it.
- `contracts/vendor/MANIFEST.json` records: repository URL, tag, commit SHA, the git tree SHA of that commit, a sorted list of every file in the tree with its SHA-256 (the binding checksum is the commit SHA plus the tree SHA plus this list), the SHA-256 of the GitHub release tarball (informational only, because GitHub-generated tarballs are not guaranteed byte-stable), the SHA-256 of `LICENSE`, the solc long versions and optimizer settings, the OpenZeppelin and `@onchain-id/solidity` versions from upstream's lockfile, the number of skipped tests declared in the source at that commit, and the Node version used. A verify check recomputes all three parts from the checked-out submodule and fails if any differs. With an uninitialised submodule the check fails at once with `VENDOR_NOT_INITIALISED` and names `git submodule update --init` and `npm run setup:chain`; it never skips.
- **Upstream suite in a working copy.** `setup:chain` exports the pinned commit into the gitignored folder `contracts/.vendor-work/T-REX/` (never inside the submodule), verifies every file against the manifest list, applies the dependency patch from `contracts/vendor/OVERRIDES.md` to that copy's `package.json` if one is needed, and runs `npm ci` there (with the patched lockfile, if any, whose SHA-256 is recorded in `OVERRIDES.md`). `test:trex` re-verifies the working copy's sources against the manifest before each run and then runs upstream's own test command, unmodified, on the in-process `hardhat` network with upstream's own config, with no `--grep`, no `.only` and no filter. The `npm audit` result of the working copy is reported in evidence, no post-install script of unknown origin runs (any package with a post-install script is named in A01's `scripts\toolchain.json`). If no dependency override makes the suite install and pass on Node 24.21.0, the node escalates (see the loop below).
- **Same bytecode as upstream.** For every contract under the tag's `contracts/` folder, the metadata-stripped `deployedBytecode` from the RealX compile equals the metadata-stripped `deployedBytecode` from upstream's compile in the working copy.
- Licence handling: `contracts/vendor/LICENSE-NOTES.md` states that T-REX, its `@onchain-id/solidity` dependency and `@account-abstraction/contracts` are GPL-3.0, that the vendored code lives only in this workspace with its licence files intact, that no T-REX Solidity, TypeScript, test or ABI text is copied into `packages/*`, `services/*` or `apps/*` (compiled ABIs and addresses are the only things exported, through A27's `packages/contracts` exporter), and that the question "may RealX deploy and operate T-REX under GPL-3.0, and does the AgentGateway, the smart wallet or a compliance module that inherits from GPL-3.0 code become a derivative work" is recorded as counsel question HG-LEGAL. It holds an inheritance list (empty at this node; A24, A25 and A26 append the RealX files that import or inherit vendored or account-abstraction code). The clean-room fallback is named in the same file: keep the EIP-3643 interfaces (`IERC3643`, `IIdentityRegistry`, `IIdentityRegistryStorage`, `ITrustedIssuersRegistry`, `IClaimTopicsRegistry`, `IModularCompliance`, `IIdentity`) and re-implement them in `contracts/src/` in A24 without reference to T-REX code.
- **Licence-boundary check (final form).** It is a content fingerprint, not a name grep: every vendored `.sol`, `.ts` and `.js` file is reduced to normalised line hashes, and any file outside `contracts/vendor/` (excluding `node_modules`, generated output, ABI JSON and the working copy) that contains a run of eight or more consecutive normalised lines matching a vendored file fails. In addition, any file outside `contracts/vendor/` carrying an `SPDX-License-Identifier: GPL-3.0` header must appear in the inheritance list in `LICENSE-NOTES.md`. Importing or inheriting a vendored contract by path, calling it from a script, and naming a contract (`Token`, `IdentityRegistry` and so on) in typed helpers or ABI exports all pass.

**Account abstraction packages and EntryPoint v0.7**
- `@account-abstraction/contracts` pinned to an exact 0.7 release. EntryPoint v0.7 is **never recompiled**: its canonical init code bytes are stored at `contracts/toolchain/canonical/entrypoint-v0.7.initcode.hex`, taken from the pinned package's shipped artifacts if they carry the canonical bytecode, otherwise from the eth-infinitism v0.7.0 release's deployment data, with the SHA-256 of the file and the canonical salt recorded in `TOOLCHAIN.md`. Before any transaction, the placement helper checks that the CREATE2 formula over the deterministic deployment proxy `0x4e59b44847b379578588920cA78FbF26c0B4956C`, the canonical salt and the keccak of those bytes gives exactly `0x0000000071727De22E5E9d8BAf0edAc6f37da032` (only the exact canonical init code can do this), and refuses with `ENTRYPOINT_INITCODE_MISMATCH` otherwise.
- Placement helper (`contracts/toolchain/entrypoint-v07.ts`, used by the chain container and by in-process test fixtures): places the deterministic deployment proxy with `hardhat_setCode` (its runtime code hash checked against `TOOLCHAIN.md`), then deploys EntryPoint by a CREATE2 call through the proxy sent from an impersonated, separately funded address (so the 20 deterministic accounts keep nonce 0 and exactly 10,000 test ETH), then checks that keccak of `eth_getCode` at the canonical address equals the published EntryPoint v0.7 runtime code hash recorded in `TOOLCHAIN.md`. `hardhat_setCode` is never aimed at the EntryPoint address anywhere in the repository; a verify check greps for it. Local, testnet and any later mainnet therefore share one EntryPoint address and one code hash. `EntryPoint.getNonce(account, 0)` returns 0 for a fresh account.
- The P-256 verifier library that A26 will use (daimo `p256-verifier`, MIT) is pinned as a dependency and recorded in `TOOLCHAIN.md` but not deployed here.

**Hardhat chain as a Docker service (`<workspace>\app\infra\chain\`)**
- `infra/chain/Dockerfile` is based on `node:24.21.0-slim` pinned by `@sha256` digest (so the container's `node -v` equals the host's). The image installs the `contracts` workspace from the root lockfile and runs `infra/chain/entrypoint.ts` (through A01's pinned `tsx`), which, in order: runs the config guard and exits non-zero with its named errors before anything starts; starts `hardhat node --hostname 0.0.0.0 --port 8545` with chainId 31337, the Hardhat default mnemonic, 20 accounts each funded with 10,000 test ETH, automine on by default and no interval mining; places the proxy and deploys EntryPoint through the placement helper; and only then writes its ready marker. Because chain state is in memory, every start and every restart repeats the placement.
- `infra/chain/compose.chain.yml` is a compose fragment that A23's stack compose includes (it extends A01's `infra\base\compose.yml` structure rather than copying it); it names the service `chain`, publishes the port from `CHAIN_PORT` (default 8545), and has a healthcheck (`infra/chain/healthcheck.ts`) that requires `eth_chainId` = `0x7a69` **and** non-empty code at the EntryPoint address, so the service is never healthy before EntryPoint exists. A bare `docker compose -f infra/chain/compose.chain.yml up` and A23's include behave identically. `chain:up` and `chain:down` are thin wrappers over the same compose file.
- Deterministic accounts: `infra/chain/accounts.json` lists the 20 addresses (account 0 is `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`) and reserves roles for later nodes as a convention only: 0 deployer (ENGO, the Engineering and chain operations staff role), 1-5 V1 owner signers, 6-8 V2 token-agent signers, 9 V3 pauser, 10 V4 identity agent, 11 V7 paymaster funder, 12 API attestation key, 13-19 test investors. These keys are public and carry no value; the file says so and the config guard above stops them reaching any non-local network.
- Test-controlled mining: `<workspace>\app\packages\chain-control\` is an A07-owned npm workspace (`@realx/chain-control`, picked up by A01's `packages/*` glob, so verify typechecks and unit-tests it) holding a small CLI (`npm run chain:control`) and importable helper over the JSON-RPC methods `evm_setAutomine`, `evm_mine`, `evm_setIntervalMining`, `evm_increaseTime`, `evm_setNextBlockTimestamp`, `evm_snapshot` and `evm_revert`, so e2e and sim runs can freeze time, batch transactions into one block, jump 48 hours for timelocks and session-key expiries, and reset between scenarios. Every method is covered by a test against the Docker chain (run under `verify:chain`). A27 imports it as `@realx/chain-control`.
- Chain smoke: `contracts/scripts/toolchain/smoke.ts` is a Hardhat script in the contracts workspace (`npm run chain:smoke`, `--network localhost`) that connects to the running service and checks chainId, account 0 balance and the EntryPoint code hash, then deploys the T-REX suite through upstream's own deployment fixture imported from the vendored path (implementation authority, factory, one token with identity registry and compliance), registers one identity, mints one unit to it, and reads `balanceOf` = 1 and `totalSupply` = 1. This is the Docker proof that the chosen toolchain issues an ERC-3643 unit locally; it writes nothing to any register or ledger.
- `infra/chain/` keeps only the Dockerfile, the entrypoint and healthcheck scripts, the compose fragment and `accounts.json`.
- Windows: Dockerfile, entrypoint and compose files are LF (A01's `.gitattributes`), no bash-only scripts, and the chain is reachable from the host on `127.0.0.1:8545` with Docker Desktop; port collisions are resolved by `CHAIN_PORT`.
- Error and empty states of the tooling: Docker not running gives a one-line message naming Docker Desktop, not a stack trace; `chain:smoke` against a stopped chain fails within 10 seconds with `CHAIN_UNREACHABLE` and the URL it tried; `chain-control` against a non-Hardhat RPC refuses with `NOT_A_HARDHAT_NODE` before sending any `evm_*` call; a missing submodule makes `compile` and verify fail with `VENDOR_NOT_INITIALISED` naming `npm run setup:chain`; a wrong EntryPoint init code file fails with `ENTRYPOINT_INITCODE_MISMATCH` and the container never turns healthy.

**`<workspace>\app\packages\contracts\` (root files only)**
- `package.json` (`@realx/contracts`), `tsconfig.json`, `README.md` and `chains.json`. `chains.json` is the address book seed: the local chain entry (chainId 31337, RPC URL, EntryPoint address, deterministic deployer address) and a Base Sepolia entry with the EntryPoint address only. `README.md` states that `packages/contracts/src/` (ABIs, chain policy, `addresses.ts`, viem types) and `packages/contracts/deployments/<chainId>.json` belong to [[A27 - Chain adapter, deployment manifests and indexer]], which is the only exporter (`contracts:export`) and the only manifest writer; that A24, A25 and A26 write only to `contracts/deployments-local/<chainId>/`; and the rule that only compiled ABIs and addresses cross from `contracts/` into this package (A01's boundary rule: `contracts` is imported by nothing except `packages/contracts`).

**Evidence** (`<workspace>\app\evidence\A07.json`): T-REX tag, commit SHA, tree SHA, per-file list hash, informational tarball hash; solc long versions and binary SHA-256s; the OpenZeppelin and ONCHAINID pins against upstream's lockfile; the coexistence mechanism chosen and the probe result; the T-REX bytecode comparison against upstream; the local pass, fail and skip counts for three runs; the Hardhat versions and the Hardhat 3 verdict; the EntryPoint init code SHA-256, computed CREATE2 address and runtime code hash; the Docker image digest; the two-boot and restart comparisons; the output of every guard test, including the in-container ones; the builder and verifier model versions.

## Gauntlet loop for this node

**Specify.** This note is the frozen spec. The node QA confirms the T-REX tag line, the Hardhat line, the EntryPoint address, the coexistence order, the chain-id and host allow-lists and the run-mode rule are stated before the build starts, and writes its Challenge material to `<workspace>\gauntlet\hidden\A07\`.

**Build (Grok 4.7 xhigh, split by the planner).** Three parallel sub-agents on disjoint folders, then one integration pass:
1. *Contracts workspace*: Hardhat 2.26 project, T-REX submodule at the pinned tag with `.gitmodules`, `MANIFEST.json`, `LICENSE-NOTES.md`, `OVERRIDES.md` if needed, the working copy and the vendored suite green on Node 24, the OpenZeppelin pins, the upstream bytecode comparison; in parallel, the Hardhat 3 trial in a scratch folder and `TOOLCHAIN.md`.
2. *Account abstraction*: pin `@account-abstraction/contracts` 0.7, the coexistence mechanism and AA probe, the canonical init code file and placement helper, `chains.json` and the `packages/contracts` root files.
3. *Docker chain*: Dockerfile, entrypoint with the guard and EntryPoint placement, healthcheck, compose fragment, `accounts.json`, `packages/chain-control` with its tests, `contracts/scripts/toolchain/smoke.ts`.

## Node-specific challenges (node QA)

- *Supply chain.* The submodule points at a branch or a fork instead of the release tag, or a `^` range lets Hardhat, solc, OpenZeppelin or `@account-abstraction/contracts` drift, so the bytecode A24 audits later is not the bytecode that was tested; the node QA swaps one vendored byte and expects `verify` to fail on the manifest.
- *Two OpenZeppelins.* OpenZeppelin 5 leaks into the T-REX compile (or OpenZeppelin 4 into the account-abstraction sources), so T-REX bytecode silently changes or the AA probe fails; the upstream bytecode comparison and the probe must both hold.
- *Faked EntryPoint.* The builder recompiles EntryPoint and gets a different address, or uses `hardhat_setCode` to put code at the canonical address; the code hash, the CREATE2 recomputation and the `setCode` grep must catch both.
- *Licence contamination.* A T-REX interface or test helper is copied into `packages/domain` or `services/api` to save time, pulling GPL-3.0 code into RealX's own packages before counsel has answered HG-LEGAL; the content fingerprint must catch it without flagging legitimate imports.
- *Non-deterministic chain.* Two boots of the Docker service give different addresses, the EntryPoint is missing after a restart, the healthcheck goes green before EntryPoint exists, or a test depends on wall-clock mining and passes only sometimes; the node QA boots twice, restarts once and runs the suite three times.
- *Testnet or mainnet escape.* A Base mainnet chain id, a real RPC URL, `RUN_MODE=production` or the public Hardhat mnemonic reaches a non-local network through the config, or the guard lives only in A08's `packages/config` while `hardhat.config.ts` or the chain container reads `process.env` unguarded; the guards must refuse with a named error in every place, since a leaked Hardhat mnemonic against a funded key is a real-money incident later.
- *Silent partial test run.* The vendored suite "passes" because tests were skipped beyond those declared in the source, filtered with `--grep` or `.only`, or the builder wrote down its own expected count; the evidence must match the node QA's independent count.
- *Dirty tree.* Installing or compiling inside the submodule leaves untracked files and turns A01's clean `git status` red.
- *Windows breakage.* CRLF in the Dockerfile or entrypoint, `hardhat node` bound to `127.0.0.1` inside the container, or a path with a space, so the healthcheck never goes green on Docker Desktop.
- *Hardhat 3 adopted on a hunch.* The builder adopts Hardhat 3 with a small T-REX patch "to make it compile", breaking the rule that the reference suite must pass unchanged.

## Pass criteria

- On a fresh `git clone --recurse-submodules`, `npm ci`, `npm run setup:chain` then `npm run verify` is green on Node 24.21.0 without Docker running, and `git status` is clean afterwards; without the submodule, verify fails with `VENDOR_NOT_INITIALISED`.
- `npm run verify:chain` runs the vendored T-REX suite in-process on `hardhat` from the working copy with 0 failures, a pass count equal to the node QA's independently derived count and a skip count equal to the skips declared in the source at the pinned commit, with no `.only` and no `--grep`, in three consecutive runs.
- Commit SHA, tree SHA and the per-file SHA-256 list recomputed by the node QA equal `MANIFEST.json`; one tampered vendored byte fails `verify`.
- For every T-REX contract, the metadata-stripped `deployedBytecode` from the RealX compile equals upstream's compile; two clean RealX compiles produce byte-identical T-REX artifacts; the solc long versions and optimizer settings in `hardhat.config.ts` equal those in `MANIFEST.json` and `TOOLCHAIN.md`; the OpenZeppelin and `@onchain-id/solidity` pins equal the pinned tag's lockfile.
- The AA probe (0.8.23, importing account-abstraction 0.7 interfaces and `BaseAccount`) compiles through the recorded coexistence mechanism, and the T-REX bytecode is unchanged by it.
- EntryPoint: the CREATE2 address computed from the stored init code, the proxy and the canonical salt equals `0x0000000071727De22E5E9d8BAf0edAc6f37da032`; keccak of `eth_getCode` at that address on the Docker chain equals the published EntryPoint v0.7 runtime code hash, re-derived independently by the node QA; no `hardhat_setCode` targets that address anywhere; EntryPoint is never compiled by RealX.
- `docker compose -f infra/chain/compose.chain.yml up` (the bare fragment, as A23 includes it) reaches healthy within 60 seconds on Docker Desktop, and the healthcheck is not green until EntryPoint code exists; `eth_chainId` returns `0x7a69`; `eth_accounts` from each of two boots equals the addresses in `accounts.json`, with account 0 `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266`; the EntryPoint code hash is identical across both boots; after `docker compose restart chain` the service is healthy again with EntryPoint present; the container's `node -v` is `v24.21.0`.
