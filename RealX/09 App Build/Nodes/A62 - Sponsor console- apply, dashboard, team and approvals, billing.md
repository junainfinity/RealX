# A62 - Sponsor console: apply, dashboard, team and approvals, billing

**The four sponsor-console screens that bracket a sponsor's life on RealX, rendered only from A33's, A43's, A36's and A14's contracts: SPN-01 the five-step application (company, licence, people, track record, terms with AcknowledgeCards for the three commitments) and its status page (under review, more information needed, fee agreement to accept, declined with the reapply date, console ready); SPN-02 the dashboard (tenant header, four KPI tiles, the "Needs you" TaskRows from the comms module with overdue turning red and the listing flagged publicly, the Listings table by status, messages from RealX, the onboarding checklist and the listing-pause banner); SPN-14 team and approvals (members with role, passkey and "can approve", invitations, the valuer and property-manager firms and members of A98 with their limited roles and the engage and end-engagement actions, internal approval rules that can never drop below the platform minimums, pending team approvals decided with a passkey, the read-only RealX guardrails and a link to SPN-16 tokens); SPN-15 billing (plan lines, usage, invoices with the 30-day pause rule, pay-by-transfer instructions). Every screen is tenant-scoped by the API and RLS, every action has an API and MCP equivalent under the same rules (D04), and nothing is computed, permitted or refused in the browser.**

**Build status:** not started. **Milestone:** AM6 (Sponsor console). **Lane:** Sponsor console. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 8-12 agent-hours (build, challenge and verify loops).

**Depends on:** [[A52 - Web app shells, routing and passkey sign-in (public, investor, sponsor)]], [[A33 - Sponsor tenancy, entities, licences of sponsors and admission pipeline]], [[A50 - Design extension A- investor and sponsor screens not in the prototype]], [[A43 - Communications, notifications, tasks and marketing claims (G17)]], [[A98 - Partner principals- trustee-RE, valuer, property manager, auditor, regulator observer and licensee users]], [[A36 - Offerings- offer terms, listing review, raise monitor (SM-04)]], [[A40 - Distributions engine (SM-08)]], [[A47 - Portfolio, holdings and transactions read models with statements]], [[A104 - MCP server generated from the OpenAPI document]] (the last four added by the 24 Sep review because this note reads their contracts; the graph data must add them to A62's `deps`, none of them descends from A62)
**Unlocks:** [[A65 - Sponsor journeys J11, J12, J13, J14, J19 end to end in Docker (AM6 exit)]], [[A80 - End-to-end journeys- sponsor and operations]]

**Oracle rule:** not an oracle node (`oracle: no`): this node moves no money, supply or holdings; it renders reads and forwards a person's decisions to APIs that enforce them. It does decide what a sponsor sees about its own admission, its team's authority and its listing pauses, so the node QA still writes hidden challenge tests to `<workspace>\gauntlet\hidden\A62\` before the build starts, from this note alone: component and Playwright tests that pin every tile, row, pill and banner to A33's, A43's, A36's and A14's response fields; the application, tenant, membership, invoice and task states listed below; the self-approval, agent-approval and below-minimum probes driven through the screens; the cross-tenant and cross-role URL probes; the tipping-off DOM scan for a declined applicant; the parity capture; and the design-fidelity comparison against the prototype's `spDash` and TaskRow regions and A50's SPN-01, SPN-14 and SPN-15 drawings. The builder never reads that folder ([[App Gauntlet]] §2).

This note is not legal advice. What a sponsor must declare personally, what the sponsor terms and fee agreement must say, whether a declared licence or a named licensed trustee is sufficient, and every threshold on these screens (10 percent retained stake, 6-month reapply period, 30-day billing pause, the fee basis) are counsel or founder questions that A33 carries as data rows marked "proposed". This node renders the strings and numbers the API returns; an answer changes a row in A33 or A03, never this node's code.

## Build brief

This node is UI-only: the `(admin)` route group inside the sponsor tenant frame of `apps/web` and the `features/sponsor-admin` package of components, hooks and formatters. It calls the API only through `packages/sdk` (A09, regenerated from A33's, A43's, A36's, A14's and A12's OpenAPI) and never through a hand-written fetch. It owns no API route, table, job or permission. Every rule on these screens (who may invite whom, which rule change needs RealX, whether a listing is paused, whether an application may be resubmitted, who may approve) is decided by the API; the screen shows the answer and the stable error code's sentence. Because the same routes serve a person's agent through A12's tokens and A104's MCP server, this node adds nothing an agent could not also do within its mandate, refuses nothing the API would allow, and publishes the mapping that proves it (`parity.json`, section 7).

- Entry: public links from the footer and PUB-05 ("Become a sponsor") go to `/s/apply`; an anonymous visitor is sent through A52's sign-up landing (verify email, first passkey) and returns here as a HUMAN principal holding only A33's own-application self-scope. - Wizard, the listing-wizard pattern (HorizontalStepper of five labels Company / Licence / People / Track record / Terms, Newsreader 26 step title, field grid, Back and Continue): **Company** (legal name, ABN or ACN, registered address, website); **Licence** (OptionCards "Own AFSL number", "Trustee licence", "Will hire a professional RE", then number, holder entity and expiry fields that map to A33's `licence` row kinds `sponsor_afsl`, `trustee_licence`, `authorised_rep`; the card never says the licence is sufficient, it records a declaration in state `declared`); **People** (CheckList of directors, beneficial owners at 25 percent or more and key persons with name, role, ownership and email rows and an "Add person" row; each row carries the fit-and-proper declaration toggle; the caption "RealX checks every director and beneficial owner" from the product map's banner); **Track record** (years operating, trusts managed, assets managed, past trusts with planned versus actual yield, a TextArea description; every figure is labelled "Declared by you" because A33 stores it as `sponsor_declared` and never as audited); **Terms** (three AcknowledgeCards: "We keep at least {retained_stake_min} of every trust we list", "We report rates, insurance and compliance monthly", "We accept the RealX sponsor terms v{version}" with the document link and sha256 caption, then **Submit application** primary). The retained-stake figure and the terms version come from the application read, never from copy.
- **Save** (outline) is `PATCH /v1/sponsor-applications/{id}` with the current section; **Continue** saves and moves to the next step only when the API returns no field errors; field errors render inline from A09's error shape (field path and code), and a section is never marked complete by the client. Masked values (ABN, address) come back masked and the field shows the mask with an "Edit" affordance that clears it; the unmasked value is never re-rendered.
- The three commitments are accepted one card at a time through `withFreshAssertion` (A52's helper over A11 §8) calling A33's `POST /v1/sponsor-applications/{id}/commitments/{code}/accept`, creating A33's `standing_consent` rows with purpose `sponsor_terms`; **Submit application** is `POST /v1/sponsor-applications/{id}/submit` and is enabled only when the read says `submittable: true`. A submit refused with `SCOPE_PENDING_COUNSEL`, `AGNT_NOT_ALLOWED` or a validation code renders the code's sentence; the button is never the control.
- Status page after submit (HorizontalStepper Applied / Checks / Background / Fee agreement / Approved / Console ready, mapped one to one from A33's `applied`, `kyb`, `background`, `fee_agreement`, `approved`, `tenant_created`; A50's banners): **Under review** amber "RealX replies within {reply_sla} business days"; **More information needed** (`info_requested`) amber banner listing the questions from the application read, each with an answer field and an upload drop box through A35's document upload, sent through A33's `POST /v1/sponsor-applications/{id}/info-requests/{rid}/answer` (`{text, document_ids[]}`), after which the stepper returns to the stage the API reports; **Fee agreement** (`fee_agreement`) a card with the fee schedule lines exactly as A33 returns them, the agreement document link and an AcknowledgeCard accepted through `withFreshAssertion` (purpose `fee_agreement`) calling `POST /v1/sponsor-applications/{id}/fee-agreement/accept`, then "Waiting for RealX approval"; **Declined** grey "Declined · you can reapply from {reapply_after}" from the application read, with a support link. Reasons, Specify point (h): the product map says a declined sponsor is given a reason, and A33 publishes `reason_class: withheld` on its non-staff event only for `kyb_failed` and `sanctions`, yet A33's `GET /v1/sponsor-applications/me` today returns no reason class for any decline. Tipping-off justifies hiding only the KYB and screening outcomes. Proposed follow-up to A33: the applicant read returns `decline_reason {class, text}` only when A33 marks the class disclosable (for example licence, background or track record), and returns nothing for `kyb_failed`, `sanctions` or any screening outcome. The page renders the class sentence exactly as returned under the banner, and for `kyb_failed`, `sanctions` and any screening outcome it shows only "We could not complete your application" (the status component still has no prop through which a KYB or screening reason could arrive, section 8). Whether any decline reason may be given at all is recorded under HG-LEGAL and as a founder question; if the answer is "no reason for any decline", A33 returns none and the page shows the neutral sentence for every decline, with no code change here. **Console ready** (`tenant_created`) "Your console is ready" with the invitation state ("Check your email to finish setting up" until the owner's invitation is accepted, then a link to `/s/{slug}`); **Withdrawn** grey with "Start a new application".
- People status after submission: each person row shows `invited`, `verifying` or `verified` from the `people[].kyb_state` of A33's application read (masked names as the API sends them). That three-value mapping is A33's, computed server-side from A30's case states; the read must never expose a raw A30 state, and the page has no mapping of its own (Specify point (f) pins the mapping and its A30 source in the manifest). A person with an open screening hit, or still in sanctions and PEP screening, reads `verifying` exactly like any other (G02 shown, not judged), and no count, colour or timing on this page differs for them (tipping-off guard, section 8).
- Reapply: a new application attempted before `reapply_after` returns `APPLICATION_REAPPLY_TOO_SOON` naming the date; the page renders the Declined banner, not a blank wizard. **Withdraw application** (outline-soft, before `approved`) is A33's `POST /v1/sponsor-applications/{id}/withdraw` with a confirmation dialog.
- Applicant agents (D04), Specify point (g): A33 marks the applicant's create, save-section, answer-information and withdraw routes as agent `maker` or `confirm`, but no upstream node lets an applicant make a token. The applicant is a HUMAN holding A33's proposed `SP-APP` role with `own-records` cells and no tenant; A12 has no `SP-APP` issue path, ACC-05 (A60) is the investor app and SPN-16 (A60) needs a tenant. Proposed reopen loops, raised before the node QA writes the hidden tests: A12 adds an `SP-APP` issue path whose scope catalogue offers only the applicant's own-application cells (the `"counsel"` cells refused with `SCOPE_PENDING_COUNSEL`, the `human` cells never offered), and A60 (or A52) supplies the creation surface, for example an "API tokens" card on the `/s/apply` status page mounted from A60's `TokenListPage`, which this node would place without owning it.
