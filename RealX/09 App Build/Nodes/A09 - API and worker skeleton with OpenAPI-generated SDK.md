# A09 - API and worker skeleton with OpenAPI-generated SDK

**The two long-running processes every later service node plugs into: a Fastify 5 API whose zod route schemas generate the OpenAPI document and the typed SDK, and a pg-boss worker that relays the transactional outbox, sharing one injectable clock, one log-line format (request, approval and on-behalf-of ids), one error envelope and one module boundary that the lint enforces.**

**Build status:** not started. **Milestone:** AM0 (Foundations). **Lane:** Platform. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops).

**Depends on:** [[A03 - State machines, gate codes, approval codes and permission matrix as data]], [[A04 - Database schema, migrations and row-level security]], [[A08 - Sandbox adapter framework, config and phase flags]]
**Unlocks:** [[A10 - Append-only hash-chained audit log]], [[A11 - Authentication, sessions, RBAC and segregation of duties]], [[A13 - Alerts and SLA-clocks service]], [[A16 - Client-money ledger (double entry)]], [[A18 - Unit register (legal record) and registry sandbox adapter]], [[A19 - Rules engine- gates G01-G22, rule packs, threshold monitors, simulator]], [[A27 - Chain adapter, deployment manifests and indexer]], [[A46 - Job scheduler, integrations health and webhooks]], [[A52 - Web app shells, routing and passkey sign-in (public, investor, sponsor)]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]], [[A104 - MCP server generated from the OpenAPI document]]

**Oracle rule:** this is an oracle node (`oracle: yes`) for a limited scope. No money, supply or holdings move in this node, but its idempotency store and outbox dedupe are the only barrier against a double-applied money write (N13) in every money node that follows (A16, A17, A37, A39, A40). So the node QA writes two **oracle suites** from this frozen spec, before any code exists, into `<workspace>\gauntlet\hidden\A09\` and records their `hiddenCasesHash` in the evidence manifest: **idempotency** (cross-principal, concurrent, lease expiry, crash between business commit and response, error after commit, token rotation) and **outbox** (atomicity, crash-injected duplicate delivery, interleaved commits on one aggregate, worker context under RLS). The node QA also writes three **hidden Challenge suites** in the same folder: **redaction** (fixture PII through every failure path and the idempotency store), **clock** (advance, agreement across processes, absence with test controls off) and **registration rules** (boundary lint, clock lint, `/v1` prefix, mandatory and derived operation metadata, error-code form, cursor pagination). The builder never reads that folder, and the tests are published into `app/` only after the gate passes ([[App Gauntlet]] §2).

## Build brief

Why this node exists: the architecture brief (§1.2, §2, §8.1) fixes one Fastify API as a modular monolith plus one worker, OpenAPI generated from zod, idempotency keys on every write, rate limits per principal, request and approval ids on every log line, and a transactional outbox; the requirements catalogue's N13 (jobs idempotent and replayable, webhook retries never double-apply) and N06 (SLA clocks in hours and days) need a clock that tests can move. Everything here is plumbing that later nodes must not re-invent.

**The rule for every later service node:** its first commit publishes its read contracts (list, detail and read-model zod schemas) into the OpenAPI document through the stub-route helper below, so that `packages/sdk` types and the MCP tool catalogue ([[A104 - MCP server generated from the OpenAPI document]]) exist before that node's engine passes its gate. The gauntlet refuses to pass a node while any stub route remains in its owned module. The one named exemption is `system.get.stub_widget` in this node's reference module, which exists only to test the `501` path.

### 0. Test controls (one switch, no new run mode)

A08 allows only `RUN_MODE=local | test`, and every other value exits with code 1. This node therefore does not invent a third mode. Both processes are built by factories, `buildApi({ testControls })` and `buildWorker({ testControls })`, whose `testControls` option **defaults to `false`**. The process entry points (`src/main.ts`) pass `true`, because in this build `RUN_MODE` is always `local` or `test`. `openapi:emit` and every "production-shaped" check build with `testControls: false`.

With test controls **on**: the `/__test/*` routes and the `/sandbox/<adapter>/*` mounts exist; `/metrics` is served; the clock is `DbClock`; the in-process fixture-principal helper and the failpoint registry (below) are registered; `details.stack` is added to `500 INTERNAL` bodies when `RUN_MODE=local`. With test controls **off**: none of those exist. The clock is `SystemClock`, the offset row is ignored, `/__test/*` and `/sandbox/*` are ordinary unknown routes (`404 NOT_FOUND`), they are absent from the OpenAPI document, and a stack is never serialised.

If a later node needs to switch test controls off in a running container, the switch is an env variable that A08 would declare (for example `TEST_CONTROLS=on|off`) in an A08.1 loop. This node does not need it: every "off" check here runs in-process through the factory.

### 1. API process (`services/api`)

- **Framework and route definition.** Fastify 5 with the zod type provider (`fastify-type-provider-zod`, version line pinned in A01). Every route is declared with `defineRoute({ method, url, schema: { params, querystring, body, response }, meta, handler })` from `src/core/routes.ts`; a route without a zod response schema for its success status fails registration. `registerModule({ name, prefix, routes, contracts, jobs, schema })` in `src/core/modules.ts` mounts the module under `/v1/<prefix>`, tags its operations with the module name, registers the module's own tables (if any) through A04's module-schema registry, and adds its jobs to the worker registry. Module code lives in `src/modules/<name>/` (owned by later nodes); `src/core/` is importable by every module; a module imports another module only through that module's `index.ts`.
- **Boundary lint, with an extension point.** The ESLint flat config in each service root (`eslint.config.js`) carries `no-restricted-imports` patterns plus a small custom rule for relative deep paths: `npm run verify` fails on any `../<other-module>/<anything but index>` import and on any import of `src/core/internal/*` from a module. The rule is case-insensitive on path segments so a Windows checkout cannot evade it. **Later nodes never edit `eslint.config.js`.** Instead, the config reads an optional `lint.json` in every module folder (`services/api/src/modules/<name>/lint.json`) and every worker job folder (`services/worker/src/jobs/<name>/lint.json`), shaped `{ restrictedImports: [{ name | pattern, allowedIn: [paths relative to the service root], message }] }`, and turns each entry into a restriction that applies everywhere except `allowedIn`. For example A10 ships `modules/audit/lint.json` so the `audit_event` table object may be imported only inside `modules/audit` and `jobs/audit`. A malformed `lint.json` fails `verify`.
- **Operation metadata is mandatory.** `meta` carries `operationId` (`<module>.<verb>.<noun>`), `requiredScope` (the scope id the caller needs, one of A03's scope enum, `scopes.ts`; the literal `public` for unauthenticated routes), `gates` (G-codes the handler evaluates, may be empty), `screens` (product-map screen codes that expose the action, may be empty), `mutation` (boolean), `money` (boolean: the call can move money, supply or holdings) and an optional `requiresHuman` (boolean; set by A11 on the routes for its non-delegable acts). These are emitted into the OpenAPI document as `x-realx-scope`, `x-realx-gates`, `x-realx-screens`, `x-realx-mutation` and `x-realx-money`. Registration throws on a missing field or an unknown scope id.
- **Derived agent metadata (D04).** At registration `defineRoute` also looks up the scope's cell in A03's data and emits four derived fields, so that no consumer has to re-derive them: `x-realx-delegable` (A03's `delegable`: `true`, `false` or `"counsel"`), `x-realx-requires-human` (`true` when `delegable` is not `true` or `meta.requiresHuman` is set; this is the extension A104 asked for), `x-realx-sensitive` (A03's `sensitive` flag: an agent call notifies its person and may need A12's `428 CONFIRMATION_REQUIRED` step-up) and `x-realx-duty` (`maker`, `checker`, `signer` or `none`, from A03's action record: an approve action of a maker-checker row is `checker`, a custody-signing action is `signer`, a draft or submit is `maker`). The literal `public` scope gets `delegable: true`, `sensitive: false`, `duty: none`. Registration fails when the scope's cell is missing from A03 or the duty cannot be derived. A contract test asserts that no operation with `x-realx-duty` of `checker` or `signer` has `x-realx-delegable: true`. This is what A12's token authentication, the docs (A99), the agent-parity suite (A100) and the MCP generator (A104) read: founder requirement D04 says every UI action must have an API equivalent under the same rules, and the metadata is how that is proven.
- **Stub routes for contract-first publishing.** `stubRoute(def)` registers a route with full schemas that answers `501 NOT_IMPLEMENTED` and is marked `x-realx-status: stub` in OpenAPI. `npm run openapi:stubs` lists stubs by module for the gauntlet.
- **Versioning.** All business routes sit under `/v1`. The only non-versioned paths are `/healthz`, `/readyz`, `/metrics` (Prometheus text, test controls on only), `/internal/health/adapters` (A08's `adapterHealth()`, staff scope), `/sandbox/<adapter>/*` (A08's `SandboxControl` hooks and the storage sandbox's upload URL, test controls on only) and `/__test/*` (test controls on only). A `Deprecation` / `Sunset` / `Link` header hook reads a deprecation table (`src/core/deprecations.ts`, empty at this node; the policy and its rows come from [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]]). Every response carries `X-RealX-Api-Version` (the package version), `X-Request-Id` and `X-Trace-Id`.
- **Request context.** An `AsyncLocalStorage` context `ctx` is created in the first hook and carries `request_id` (ULID; a well-formed inbound `X-Request-Id` is honoured, anything else replaced), `causation_id` (null for an HTTP request; the triggering event's `request_id` for a job or event handler), `trace_id`, `span_id`, `principal`, `approval_id` (null until an approvals handler sets it), `clock`, `log`. The principal shape is defined here using A03's principal types and carries **every field A04's row-level security reads**, all nullable except `kind`:

  `{ kind: 'anonymous' | 'HUMAN' | 'PARTNER' | 'AGNT' | 'SVCA', id, role, tenant_id, session_id, token_id, on_behalf_of_id, investor_id, vehicle_scope, platform_access, view_as_tenant, sandbox_of, scopes: string[] }`

  A09 always sets `anonymous` (every RLS field null, so A04's policies fail closed). The principal is filled only in the `principal` slot: [[A11 - Authentication, sessions, RBAC and segregation of duties]] from sessions, [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]] from API tokens, A98 for partner users and A99 for sandbox sessions. **For an `AGNT` principal**, `id` is the agent principal and `token_id` the token, while `tenant_id`, `investor_id`, `vehicle_scope`, `role`, `platform_access`, `view_as_tenant` and `sandbox_of` are those of the `on_behalf_of_id` person, so an agent sees exactly the rows its person sees in the UI. Hook order is fixed as named slots (`request-id`, `otel`, `principal`, `kill-switch`, `rate-limit`, `idempotency`, `validation`, `handler`, `response-headers`); later nodes register into a slot, never reorder.
- **Fixture principals (tests only, never from the network).** The checks below need fixture principals (an `AGNT` with `on_behalf_of_id` and `token_id`, a tenant-B session, a `HUMAN`). They are set only through the in-process helper `injectAs(app, principal, request)` in `src/core/testing/`, which wraps `fastify.inject()` and hands the fixture to the `principal` slot through a private symbol on the injected request object. The helper module is not imported by `main.ts`, and its slot hook is registered only when test controls are on. **No HTTP header, query value or cookie ever sets or alters a principal in A09.** A grep in `verify` fails on any read of a principal-like header (`x-test-principal`, `x-principal`, `x-on-behalf-of`, `x-token-id`, case-insensitive) anywhere in `src/` outside the A11 and A12 module folders.
- **Kill-switch slot.** The `kill-switch` slot ships empty here except for one check: it calls A08's `isEnabled('agents.traffic', ctx)` **on every request** and refuses any request whose principal kind is `AGNT` with `423 AGENTS_PAUSED` when the flag is off. It never reads a config snapshot taken at startup. Any cache A09 keeps is at most 1 s old and is dropped at once when the Postgres channel `realx_flags` notifies (A21's database-backed override source sends that NOTIFY on commit; until A21 lands, the 1 s limit alone applies). A12 and A101 add the per-token, per-user and per-tenant tiers behind the same slot.
- **Database access.** `withTx(ctx, fn)` in `src/core/db.ts` is a thin router over A04's transaction wrappers and **never issues `SET` or `SET LOCAL` itself** (A04: `withTenant` and `withPlatform` are the only sanctioned way to set context). It calls A04's `withPlatform(ctx, fn)` when the principal is `SVCA` running platform-wide work or has `platform_access` true (staff sessions and their agents), and A04's `withTenant(ctx, fn)` for every other principal. A04 maps the principal fields to its session variables (`app.tenant_id`, `app.principal_id`, `app.principal_kind`, `app.principal_role`, `app.platform_access`, `app.view_as_tenant`, `app.investor_id`, `app.vehicle_scope`, `app.sandbox_of`). `withTx` also exposes `outbox.enqueue(tx, event)` so a domain event is written in the same transaction as the state change. No handler may obtain a connection any other way (lint rule on the `@realx/db` client import path: only `src/core/db.ts` may import it).
- **Error envelope and the code table.** One shape for every non-2xx: `{ error: { code, message, request_id, details?, gate?, reason_codes? } }`. **Every code, core or module, is UPPER_SNAKE_CASE** (`^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*$`); `registerErrors()` rejects any other form, a duplicate code, and a status outside 400-599. (Upper case is chosen because the module codes already specified downstream, such as A10's `AUDIT_*`, A11's `AGNT_NOT_ALLOWED`, A12's `TOKEN_*`, `G22_*`, `AGENTS_PAUSED`, `RATE_LIMITED` and `CONFIRMATION_REQUIRED`, and A99's `SANDBOX_*`, are upper case.) The core table, which the contract suite covers row by row:

  | Code | HTTP | SDK retries automatically |
  |---|---|---|
  | `VALIDATION_FAILED` | 400 | no |
  | `INVALID_CURSOR` | 400 | no |
  | `UNAUTHENTICATED` | 401 | no |
  | `FORBIDDEN` | 403 | no |
  | `GATE_FAILED` | 403 | no |
  | `NOT_FOUND` | 404 | no |
  | `CONFLICT` | 409 | no |
  | `IDEMPOTENCY_IN_PROGRESS` | 409 (with `Retry-After`) | no |
  | `IDEMPOTENCY_KEY_REUSED` | 422 | no |
  | `AGENTS_PAUSED` | 423 | no |
  | `RATE_LIMITED` | 429 (with `Retry-After`) | yes |
  | `INTERNAL` | 500 | no |
  | `NOT_IMPLEMENTED` | 501 | no |
  | `SERVICE_UNAVAILABLE` | 503 | no |

  Modules register their own codes with a status through `registerErrors()` (A10's `AUDIT_*`, A12's `AGENT_NEVER_CHECKER`, `CONFIRMATION_REQUIRED` with status 428, and so on); an unregistered code thrown from a handler becomes `500 INTERNAL` and a warning in the log. zod failures map to `400 VALIDATION_FAILED` with field paths only; the offending values are never echoed. `GATE_FAILED` carries `gate` (for example `G07`) and `reason_codes` so the apps can show the design's inline explanatory note (design component 46) and an MCP tool can return a structured refusal. `500 INTERNAL` returns only code, message and request_id; the stack goes to the log. The stack is added under `details.stack` only when test controls are on and `RUN_MODE=local`; otherwise it is never serialised.
- **Idempotency (oracle scope).** Every `mutation: true` route requires an `Idempotency-Key` header (ULID or UUID; a missing key is `400 VALIDATION_FAILED`). The rules:
  - **Scope.** The key is scoped to `(principal_kind, principal_id, token_id, operationId)`. `token_id` is the `TOK-` id, which A12 keeps unchanged when a token is rotated, so a retry sent with the rotated secret replays the stored result instead of executing again; a different token of the same person (another `TOK-` id) never sees it. For a `HUMAN` or `PARTNER`, `token_id` is null and `session_id` is deliberately not part of the scope, so a retry after a session refresh replays rather than executes a second time.
  - **Claim with a lease.** Before the handler runs, a short transaction inserts the claim row in A04's `idempotency_key` table: request body sha256, state `in_progress`, a random `claim_token` and `locked_until` = clock now + 60 s. On conflict: a `completed` row with the same body hash is replayed with `Idempotent-Replayed: true`; a `completed` row with a different body hash is `422 IDEMPOTENCY_KEY_REUSED`; an `in_progress` row whose lease has not expired is `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After` = seconds left on the lease; an `in_progress` row whose lease has expired is re-claimed (new `claim_token`, new lease), which is how a claim left behind by a crash is recovered.
  - **Completion is atomic with the business write.** For a `mutation: true` route the route runner opens the single business transaction through `withTx` and passes `tx` to the handler; the handler does not open another transaction (a runtime assertion fails the request in tests). Inside that transaction, after the handler returns, the runner serialises the response through the route's response schema, then writes the completion (`state = completed`, status, allow-listed headers, body, `completed_at`, `expires_at` = clock now + 24 h) with `UPDATE ... WHERE claim_token = <mine> AND state = 'in_progress'`. If that update touches zero rows (the claim was re-claimed after a lease expiry), the runner throws and the whole business transaction rolls back. So the business change and the stored response commit together or not at all, and at most one claimant's business transaction can commit.
  - **Release only on rollback.** A claim is released (row deleted where `claim_token` matches) only when the business transaction rolled back: the handler threw, a gate refused, or the commit failed. An error raised after the commit (for example in an `onSend` hook or while writing the socket) never releases the claim, and the already-serialised bytes stored in the row are what a retry receives.
  - **Storage of the response.** The stored response body is encrypted with A04's `enc` codec (bound to A08's `kms` adapter), stored headers are an allow-list (`Content-Type`, `Location`, `X-RealX-Api-Version`, never `Set-Cookie`), and neither the body nor the headers are ever logged or put on a span. Expired rows are swept by a worker job.
- **Rate limiting.** A hook in the `rate-limit` slot computes a bucket key from the principal (`human:<id>`, `partner:<id>`, `agent:<token_id>`, `service:<id>`, `anon:<ip>`), applies the limit policy (a function injected by later nodes; the default is a per-key sliding window from A08's config: 600/min HUMAN and PARTNER, 300/min anonymous, 1,200/min SVCA, 300/min AGNT until A12 replaces it with the mandate's own limits) and answers `429 RATE_LIMITED` with `Retry-After` and the IETF `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` headers. Agent tokens get their own bucket, never the human's and never the IP's, so a per-token throttle or kill in ADM-35 is possible without touching the person's session. The store is an interface (`RateLimitStore`) with an in-process implementation; A99 may replace it with a Postgres one for multi-instance runs.
- **Cursor pagination on every list endpoint.** `listRoute()` wraps a list handler: query `cursor` (opaque) and `limit` (default 50, max 200); response `{ items: T[], next_cursor: string | null }`. The cursor is base64url of `(sort key values, row id)` plus an HMAC under a local key from A08's `kms` adapter, so a tampered cursor is `400 INVALID_CURSOR`; the cursor is not an authorisation and every page is still read under RLS. Offset pagination does not exist; a GET route whose success schema is a bare array fails registration.
- **Logging and redaction.** pino, one JSON line per event, base bindings `service`, `version`, `run_mode`, `pid`; per request `request_id`, `causation_id`, `trace_id`, `principal_kind`, `principal_id`, `on_behalf_of_id`, `token_id`, `tenant_id`, `approval_id`, `operation_id`, `status`, `duration_ms`. Redaction has two layers:
  - **Path redaction, schema-driven.** `@realx/db` exports `PII_PATHS` (every `_enc` column plus the fixed list: `authorization` and `cookie` headers, `tfn`, `abn`, `bsb`, `account_number`, `date_of_birth`, `document_number`, `payid`, `address*`, `email` outside the principal binding); the pino `redact` list is generated from it at startup and a startup check fails if the generated list is shorter than the fixed list.
  - **Value scrubbing, pattern-driven.** `registerRedactionPattern(name, regex)` in `src/core/redaction.ts` adds a pattern that is applied as a value scrubber to every log message string, every logged URL and query string, every error message and every span attribute, because pino's path redaction cannot see a secret inside free text. This node ships the API-token pattern `rx_[a-z]+_[A-Za-z0-9]+` by default; later nodes register theirs (A46's `whsec_[A-Z2-7]{32}`, and so on). Patterns are registered at module load, never at request time.
  Request and response bodies are never logged at info level; at debug level only with test controls on and `RUN_MODE=local`, through both layers.
- **OpenTelemetry.** `@opentelemetry/sdk-node` with HTTP, Fastify and pg instrumentation; OTLP export to the compose `otel-collector` when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, otherwise a no-op exporter. Every request, job run and outbox relay batch is a span; `trace_id` is in every log line; `approval_id`, `on_behalf_of_id`, `token_id` and `causation_id` are span attributes when present; span attributes pass through both redaction layers.
- **Health and meta.** `/healthz` (process up); `/readyz` (Postgres reachable as `realx_app`, migrations at head per A04's journal, clock mode, A08 adapter registry loaded with no live adapter while `RUN_MODE=local`). `/readyz` returns 503 with a `reasons[]` array of codes when any of those checks fails; reasons never carry connection strings or host names. The API's `/readyz` does **not** depend on outbox lag, so a worker backlog never takes reads or withdrawal status out of service. `/v1/meta` returns version, run mode, `PHASE` and flag snapshot from A08, `now` from the clock, chain id from config, and `degraded[]` (codes, for example `outbox_lag` when the oldest unpublished outbox row is older than 60 s); A13 raises its alert from the same measure.
- **The clock.** `src/core/clock.ts` implements A08's `Clock { now(): Date }` interface and is the only place in the API and worker allowed to call `Date.now()` or `new Date()` without arguments; a lint rule (`no-restricted-syntax` with an allow-list of the clock files) fails `verify` otherwise. With test controls on, both processes use `DbClock`: real time plus an offset stored in A04's single-row `system_clock` table, read per request and cached for one second, so the API, the worker and A08's sandbox adapters share the same "now". With test controls off, `SystemClock` is used and the offset row is ignored. `POST /__test/clock/advance { seconds }` (positive integers only, at most 400 days per call; test controls on only; absent from the OpenAPI document and a 404 otherwise) adds to the offset in one statement, enqueues a `clock.advanced` outbox event and returns the new `now`. [[A27 - Chain adapter, deployment manifests and indexer]] subscribes to that event to call `evm_increaseTime` and `evm_mine` on Hardhat; A08's sandbox delays and [[A13 - Alerts and SLA-clocks service]] read the same clock, so timelocks, lock-ins, approval TTLs and SLA clocks that are hours or days long run in minutes in the gauntlet.
- **Failpoints (tests only).** `failpoint(name)` in `src/core/testing/failpoints.ts` is a no-op unless test controls are on and a test armed it. Named failpoints: `idempotency.after_business_commit` (kill the process or throw after the business transaction committed and before the response is sent), `outbox.after_publish_before_mark` (kill the worker after publishing to pg-boss and before `published_at` is set). The node QA's crash injections use these and a real process kill.

### 2. Worker process (`services/worker`)

- **Job registry.** pg-boss 10 line against the same Postgres as `realx_worker`. Per A04, the `pgboss` schema is created and migrated by pg-boss itself at worker start under the `realx_worker` role (which A04 grants that schema); A04's migrations do not create it. `src/core/jobs.ts` exposes `registerJob({ name, schema, handler, retryLimit, retryBackoff, cron?, singleton? })`; every job is created with pg-boss's `deadLetter: 'jobs.dead-letter'` option (the queue A46's collector works). Payloads are zod-validated before the handler; a handler receives `(payload, ctx)` where `ctx` has the same shape as the API context (`request_id` = job id, `causation_id`, principal = the named `SVCA` service account for that job from A04's `service_account` table, clock, log, `withTx`). Every job run is logged with `job_name`, `job_id`, `attempt`, `duration_ms` and outcome, and recorded in A04's `job_run` table.
- **Scheduler tick.** pg-boss cron runs on wall time, which the injected clock can outrun. Cron definitions are therefore not handed to pg-boss: a `scheduler.tick` job runs every real second, computes each cron's next due instants against the injected clock (business-day and AEST/AEDT rules are A13's and A46's; this node handles plain cron), and sends the job when clock-now passes a due instant, idempotent per `(job, due instant)` through the unique key in A04's `job_schedule_fire` table. Before sending, the tick asks an injectable `SchedulePolicy { shouldFire(jobName, dueAt): 'fire' | 'skip' }` (default always `fire`; A46 installs its own) and records a skipped fire with its reason in `job_schedule_fire`. **Catch-up rule:** after a clock advance, every due instant is fired in due-instant order, at most 1,000 fires per tick; the rest are fired on the next ticks, still in order. Coalescing missed fires is a `SchedulePolicy` decision, not a tick decision. Advancing the clock by 30 days fires every schedule that fell inside those 30 days, in order, within seconds.
- **Transactional outbox relay.** The API and the worker write domain events to A04's `outbox_event` table inside the business transaction: `{ id ULID, type, occurred_at (clock), aggregate_type, aggregate_id, tenant_id, sandbox_of, actor_id, actor_kind, on_behalf_of_id, token_id, approval_id, request_id, causation_id, schema_version, payload }`. The relay job polls `outbox_event where published_at is null order by id` in batches of 100 with `FOR UPDATE SKIP LOCKED`, publishes each row to pg-boss as `event.<type>`, then sets `published_at`. Delivery is at-least-once.
- **Delivery is unordered, and consumers must not assume otherwise.** Ids are assigned before commit, so a later-committed transaction can carry an earlier id, and concurrent relays can reorder batches. No consumer may rely on the arrival order of two events for the same aggregate: a consumer that mirrors state (register and chain mirroring in A27 and A28, webhooks in A46) reads the aggregate's current version or state from its own row inside its handler transaction and ignores an event older than what it has applied. The `system` reference handler demonstrates this pattern.
- **Event handlers.** `registerEventHandler({ type, schema, handler })` makes every consumer idempotent on `event.id` through A04's `processed_event` dedupe table inside the handler's transaction. [[A46 - Job scheduler, integrations health and webhooks]] builds webhook fan-out on these events; [[A10 - Append-only hash-chained audit log]] consumes them for audit rows; every event carries `on_behalf_of_id` and `token_id` so agent activity is attributable end to end (D04).
- **Worker context under row-level security.** The worker has no `BYPASSRLS` role (A04). Two contexts exist:
  - **Platform runtime work** (the outbox relay, the scheduler tick, the idempotency sweep) runs through A04's `withPlatform` as its named service account (`svc-outbox-relay`, `svc-scheduler-tick`, `svc-idempotency-sweep`, each a `service_account` row), under an A04 policy that gives those accounts access to the runtime tables only (`outbox_event`, `idempotency_key`, `processed_event`, `job_schedule_fire`, `job_run`, `system_clock`) and to nothing else.
  - **Event handlers** run with a context built from the event: `tenant_id`, `sandbox_of`, `on_behalf_of_id`, `token_id`, `approval_id`, and `causation_id` = the event's `request_id`, with the handler's `SVCA` as principal, and use A04's `withTenant`. Any outbox event a handler enqueues copies those fields, so attribution and tenant scope survive a chain of events.
- **Shared runtime pieces.** Same pino configuration, both redaction layers, OpenTelemetry hooks and clock as the API. `services/worker/src/core/` importing the API's `src/core/` is not allowed; the shared code is the small `@realx/config` and `@realx/db` exports plus copies that a `verify` script asserts are byte-identical, until A99 decides whether to extract a `packages/runtime`.
- **Health and shutdown.** Worker health on its own port: `/healthz`, `/readyz` (Postgres as `realx_worker`, pg-boss started, scheduler tick alive within 5 s, outbox lag under 60 s: over 60 s the worker's `/readyz` is 503 with `outbox_lag`). Graceful shutdown drains in-flight jobs for up to 30 s, then exits non-zero if any remain so the orchestrator sees it.

### 3. OpenAPI and SDK (`packages/sdk`)

- `npm run openapi:emit` builds the API in-process with `buildApi({ testControls: false })` and a **lazy database connection** (route registration never connects), registers every module, and writes `packages/sdk/openapi.json` (OpenAPI 3.1, `info.version` = package version, tags = modules, every operation carrying the five `x-realx-*` fields and the four derived D04 fields, `components.schemas` named from each zod schema's `.meta({ id })`, the scope enum derived from A03's `scopes.ts`). It needs no Docker and no Postgres. `npm run openapi:check` re-emits and diffs; a difference fails `verify`, so the committed document always equals the routes.
- `npm run sdk:build` generates `packages/sdk/src/generated/types.ts` (openapi-typescript) and wraps them in `RealXClient` (openapi-fetch): base URL, bearer token or cookie auth, `paginate(op, params)` async iterator over `next_cursor`, typed `RealXApiError` with `code`, `gate`, `reason_codes`, `request_id`, `retry_after`. **Retry rules:** the client generates one `Idempotency-Key` (ULID) per logical mutation call, unless the caller supplies one, and reuses that same key on every automatic retry of that call. Automatic retries cover `429 RATE_LIMITED` (honouring `Retry-After`) and network errors (connection reset, timeout) only, at most 3 retries per call. `423 AGENTS_PAUSED` (a kill switch: the agent must stop), `409 IDEMPOTENCY_IN_PROGRESS`, every other 4xx and every 5xx are returned at once as `RealXApiError`. No hand-written endpoint code in the SDK; anything not in `openapi.json` does not exist in the client. The SDK is consumed by both Next.js apps ([[A52 - Web app shells, routing and passkey sign-in (public, investor, sponsor)]]) and is the base of the published TypeScript SDK and the MCP tool catalogue ([[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]], [[A104 - MCP server generated from the OpenAPI document]]).

### 5. Error and empty states

- Missing or invalid env: the process exits code 1 through A08's `loadConfig()` before opening a port.
- Postgres unreachable at start: the API serves `/healthz` 200 and `/readyz` 503 (`postgres_unreachable`) and retries the connection with backoff; it never serves a `/v1` route without a database (`503 SERVICE_UNAVAILABLE`).
- Migrations behind head: `/readyz` 503 (`migrations_pending`); business routes answer `503 SERVICE_UNAVAILABLE` until `db:migrate` runs.
- Empty list: `{ items: [], next_cursor: null }`, never a 404.
- Unknown route: `404 NOT_FOUND` in the envelope, no HTML.
- Clock endpoint with test controls off: `404 NOT_FOUND`, indistinguishable from any unknown route.
- Outbox backlog: relay lag over 60 s flips the worker's `/readyz` to 503 (`outbox_lag`), adds `outbox_lag` to the API's `/v1/meta.degraded[]`, and is what A13's alert reads. The API's `/readyz` is unaffected.
- A claim left `in_progress` by a crash: retries get `409 IDEMPOTENCY_IN_PROGRESS` with `Retry-After` until the 60 s lease ends, then the next retry re-claims and executes once.

## Node-specific challenges (node QA)

- **Cross-principal idempotency replay (money, oracle).** Agent token T1 submits a mutation with `Idempotency-Key: K`; a different principal (another token of the same person, the same person's own session, or another person) submits `K` with any body. The second caller must never receive T1's stored response, and neither call may execute twice. T1 is then rotated (same `TOK-` id) and the retry with the new secret must replay, not execute. Then 1,000 concurrent identical requests under one principal: the target table must show exactly one execution. Then a handler that throws after claiming the key (business transaction rolled back): the retry with the same key must execute once, not be answered `409` forever.
- **Crash and error after commit (money, oracle).** (a) Kill the API process at `idempotency.after_business_commit`, restart, retry with the same key: exactly one `system_echo` row, the retry answered with the committed result and `Idempotent-Replayed: true`. (b) Throw from an `onSend` hook after the commit, retry: the same outcome, and the claim was not released. (c) Kill the API after the claim and before the business commit, retry at once (`409` with `Retry-After`), then after the 60 s lease (advance the clock): the retry executes exactly once. (d) Two claimants race on an expired lease: at most one business transaction commits.
- **PII in the failure path and at rest (compliance).** A body containing a fixture TFN, BSB, account number and date of birth fails zod validation. The 400 `details` must contain field paths only; the log line, the OTel span attributes and the debug-level body log (local mode) must not contain any fixture string; the redact list must have been generated from `PII_PATHS`, not typed by hand (the node QA adds a fake `_enc` column to a scratch schema and checks it appears in the list). A successful echo whose response contains a fixture address leaves no plain-text fixture string in `idempotency_key`. A fixture `rx_inv_...` token string placed in a URL query, an error message and a span attribute is scrubbed in every sink.
- **Clock drift or clock escape (compliance).** With test controls on, advance the clock 30 days: `/v1/meta.now`, the worker's `/readyz` `now` and a sandbox adapter's `now` must agree within one second, a job scheduled 29 days out must fire within five seconds, the fires come in due order and never more than 1,000 per tick, and a 48-hour timelock fixture must read as expired. With `buildApi({ testControls: false })`, the same endpoint must be a 404 and absent from OpenAPI. A negative, zero, non-integer or over-limit advance must be refused. A module file calling `new Date()` must fail `verify`.
- **Outbox atomicity, ordering and duplicate delivery (money, oracle).** A handler that enqueues an outbox event and then throws must leave no outbox row. Killing the worker at `outbox.after_publish_before_mark` must produce a second delivery that the dedupe table absorbs: the handler's side effect happens once per `event.id` across ten crash injections. Two interleaved transactions on one aggregate, where the later-committed one carries the earlier id: both events are delivered exactly once and the reference handler ends in the later state. An outbox row for tenant A must not be visible to an event handler running with tenant B's context, while the relay (platform runtime account) sees both.
- **Worker and agent context under RLS (security).** A04's generated two-tenant RLS test is run through `withTx` for: a `HUMAN` of tenant A; an `AGNT` on behalf of that human (exactly the same rows visible, nothing of tenant B); the `svc-outbox-relay` account (runtime tables only; zero rows of `system_echo`); and an event handler for a tenant-A event (tenant A rows only). `withTx` issuing any `SET` itself fails a grep in `verify`.
- **Fixture principal by the front door (security, D04).** Over real HTTP against the running API (test controls on, and again with a factory build with them off), send `X-Test-Principal`, `X-Principal`, `X-On-Behalf-Of` and `X-Token-Id` with every plausible value: the principal stays `anonymous` in the log line and the response. A planted header read in a scratch module outside A11 and A12 fails `verify`.
- **Cursor and version escape (security).** A cursor whose HMAC is valid but whose row id belongs to another tenant must return no rows from that tenant on `GET /v1/system/echoes` under A04's RLS. A cursor with one flipped byte must be `400 INVALID_CURSOR`. A route registered outside `/v1` without being on the fixed exception list, without `requiredScope`, with a scope id not in A03's enum, with a scope whose cell has no derivable duty, or with a lower-case error code must fail at registration, not appear in OpenAPI, and therefore not appear in the SDK.
- **Agent kill switch by-pass (security, D04).** With `agents.traffic` off, a request carrying a fixture `AGNT` principal must be refused with `423 AGENTS_PAUSED` before the rate-limit and idempotency slots run (no idempotency row claimed, no bucket consumed), while a `HUMAN` principal on the same route succeeds. With the process running and the flag on, a fake database override source flips it off: the next `AGNT` request after the `realx_flags` notification (and in any case within 1 s) answers 423. A later node registering a hook that reorders slots must fail registration.
- **SDK retry safety (money).** The SDK's first attempt times out after the server has committed: the automatic retry carries the same key and is answered with `Idempotent-Replayed: true`, with one execution. A `423 AGENTS_PAUSED` answer is returned to the caller at once with no retry. A `429` is retried at most 3 times with the same key.
- **Stack trace and internals leak (security).** Force an unexpected exception in a handler with `testControls: false`: the body must be the envelope with `code: INTERNAL` and a `request_id` only; the same request with test controls on and `RUN_MODE=local` may include the stack under `details.stack`. `/readyz` reasons must be codes only, never connection strings or host names.
