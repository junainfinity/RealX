# A60 - Investor and sponsor API tokens and agents screens (ACC-05, SPN-16)

**The two self-service screens of founder decision D04, drawn from design extension A and fed only by A12's agent-access contract: ACC-05 "API tokens and agents" for every investor sub-type (a token list with tone pills, a five-step create flow with a ScopePicker that can only offer the viewer's own delegable rights, mandate limits and expiry restated in plain English before a fresh passkey assertion over exactly that payload, a copy-once secret with the MCP connection snippet, per-token activity with G22 outcomes and "on behalf of", last used, rotate, narrow, widen with a passkey, revoke at once, the "Waiting for you" confirmations an agent raised above its cap, a sandbox token beside the live ones, notice settings, anomaly holds and "Pause all my agents"), and SPN-16, the same page for each sponsor team member under `/s/[tenant]` (valuers and property managers included) with the tenant dimension: scopes capped at the member's role, a pending state until a sponsor owner who is not the requester approves with their own passkey, a team view and tenant-wide activity for the owner, rights narrowed or tokens revoked on a role change exactly as the API reports them, and a tenant-wide pause. The browser decides nothing: every scope ceiling, limit, refusal and approval right is the API's answer rendered without translation.**

**Build status:** not started. **Milestone:** AM5 (Investor app and preview). **Lane:** Investor app. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 10-14 agent-hours (build, challenge and verify loops; two surfaces, five parallel sub-agents, the full state matrix and 50 create plus 50 rotate secret scans).

**Depends on:** [[A52 - Web app shells, routing and passkey sign-in (public, investor, sponsor)]], [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]], [[A50 - Design extension A- investor and sponsor screens not in the prototype]], [[A33 - Sponsor tenancy, entities, licences of sponsors and admission pipeline]], [[A99 - Developer surface- API versioning, reference docs, per-user sandbox and SDK-MCP packaging]], [[A101 - Agent guard- anomaly detection, sensitive-action notices and tiered kill switches]], [[A98 - Partner principals- trustee-RE, valuer, property manager, auditor, regulator observer and licensee users]] (SP-VAL and SP-PM tenant members, their principal kind and fixtures), [[A23 - Whole-stack Docker boot (AM1 exit)]] (the stack every Playwright flow runs against), [[A37 - Orders, escrow, allocation and refunds (SM-05)]] (the orders an agent places in "Revoke under fire" and the revocation hook), [[A40 - Distributions engine (SM-08)]] (the prepare route the J19 slice drives). All four are in earlier milestones (AM1 and AM3); the graph's dependency list for A60 must carry them too.
**Unlocks:** [[A65 - Sponsor journeys J11, J12, J13, J14, J19 end to end in Docker (AM6 exit)]], [[A82 - End-to-end- an agent drives the account through the API and MCP]], [[A105 - Partner portal- trustee-RE, auditor, regulator observer and licensee views]]

**Oracle rule:** not an oracle node (`oracle: no`): the screens move no money, supply or holdings themselves; the authority they grant is enforced by A12 (an oracle node) and A101. Because what this node shows is what a person signs, the node QA still writes hidden challenge tests to `<workspace>\gauntlet\hidden\A60\` from this note alone before the build starts: component tests that pin the ScopePicker to the API's per-viewer family listing, a property test that the MandateSummary sentence and the hash the passkey signs describe the same payload, the copy-once secret scans (DOM, storage, caches, network, logs, RSC payload), the SPN-16 maker-checker matrix, Playwright flows against the Docker stack for create, widen, narrow, rotate, revoke, confirm, pause and resume, and the design-fidelity comparison against A50's ACC-05 and SPN-16 drawings. The builder never reads that folder; it is published into `app/` only after the gate passes ([[App Gauntlet]] §2).

This note is not legal advice. Which declarations must be made by the person rather than their agent is a counsel question held by A12 and A03's `delegable.ts`; this node renders the answer ("Needs counsel" until then) and never encodes it.

## Build brief

This node is UI-only: two page folders in `apps/web` and one feature package, `src/features/agent-access/`, that both pages and A105's partner pages import. It calls the API only through `packages/sdk` (regenerated from A12's, A99's, A101's, A46's and A33's OpenAPI entries) and owns no route, table, job or event. The browser never decides whether a person may hold a scope, whether a change widens a mandate, whether a sponsor member may approve, or whether an agent may act: it asks, renders the answer and, when the API says a passkey is needed, runs A52's `withFreshAssertion` and retries once. Every action on these screens is also listed in the agent parity manifest (below), with the non-delegable ones marked as such, so A100 can prove that what an agent can do here equals what A03's `delegable.ts` allows and no more.

**1. Routing, shells and screen codes**

- Pages: `app/(investor)/account/agents/page.tsx` (ACC-05 list at `/account/agents`), `app/(investor)/account/agents/new/page.tsx` (create flow), `app/(investor)/account/agents/[tokenId]/page.tsx` (token detail: mandate, versions, activity, rotate, revoke), `app/(investor)/account/agents/activity/page.tsx` (all agents' activity), and the same four under `app/(sponsor)/s/[tenant]/agents/` for SPN-16, plus `app/(sponsor)/s/[tenant]/agents/team/page.tsx` (owner-only team view and pending approvals). Each page calls `defineScreen({ map: 'ACC-05' | 'SPN-16', design: 'ext:ACC-05' | 'ext:SPN-16', title: 'API tokens and agents' })`. `[tokenId]` is the `TOK-` id only; no name, email, prefix or secret is ever a path or query parameter (A52's parameter allow-list test covers it).
- Route reconciliation (Specify point (a), settled by A52's frozen table): A52 routes ACC-05 to `/account/agents` and SPN-16 to `/s/[tenant]/agents` (A52 route table and its account-menu and sidebar rule), and its `mapRoute` rule already registers the product map's `/sponsor/agents` as a permanent redirect. This node serves exactly those two paths from its owned folders and asks for no redirect or route change. The folder `app/(investor)/account/agents/` sits inside A59's `/account/` tree; A59's owned-path line already excludes the ACC-05 sub-folder "if spec point (a) places ACC-05 under `/account/`, which then belongs to A60", so the sub-folder is this node's. Both Owned paths sections record the carve-out, and the generator reads `owned_paths` from them, so `Data/app-graph.json` carries it (settled 24 Sep 2026; A52's table was aligned the same day). This node does not hand-write a path (`href('ACC-05')` everywhere), and `screens.generated.json` must show one path per code.
- Entry points owned elsewhere: A52's investor account menu and sponsor sidebar entry "API tokens and agents"; A59's ACC-01 settings row ("API tokens and agents · 2 active · 1 sandbox"); A58's POR-04 "by your agent {name}" marker, which links to `/account/agents/[tokenId]#activity`; A59's ACC-03 agent notice rows, which link to the token's activity row. A58 and A59 are in the same milestone and are not dependencies of this node, so the entry links are not tested here: this node provides the stable `#activity` anchor and the `href('ACC-05', { tokenId })` target, and the journey check that ACC-01 and POR-04 reach them belongs to A79's J17 run (requested there, not edited here). The counts on those rows come from the same A12 list call this page reads, so the settings row and this page never disagree.
- Who sees the sponsor page: any principal the API reports as a member of the tenant, rendered from the API's answer and never from a client-side principal-kind check. That is a `sponsor_user` (SP-OWN, SP-OPS, SP-FIN, SP-IR) or an A98 tenant partner linked to the tenant by a membership (a PARTNER principal of kind TP-VAL or TP-PM with the limited role SP-VAL or SP-PM, whose tokens carry the `rx_spn_` prefix per A12 and A98). The team view and tenant-wide activity are fetched only for callers the API authorises (SP-OWN in the seed); for anyone else the API answers 403 and the page renders "Only the sponsor owner can see the whole team's tokens", never a client-filtered copy of data it received. An investor who is also a sponsor member sees two separate pages with separate token lists (two principals, A11); nothing is merged.

**2. ACC-05 page (investor): list, statuses and summary**

- Header from A52's `PageHeader` (eyebrow `ACC-05`, h1 "API tokens and agents", sub "Your AI agents act through the API with exactly the rights you give them, never more than you have."). KpiGrid from the list response's counts (Active tokens, Sandbox tokens, Agent actions this month, Refused this month); the browser does not count rows.
- Token DataTable (Name / Agent / Prefix / Scopes / Limits / Expires / Last used / Status): prefix and lookup only (`rx_inv_K7Q2M4X9B3ND`) in Geist Mono, never any part of the secret; Scopes as plain-English family labels from A12's `families.ts` labels ("Read · Invest · Documents"); Limits as the API's formatted twins ("A$1,000 an order · A$5,000 a month"); Last used as "Today 09:14" plus the client label the activity row carries (API or MCP) when A12 records it; Status as the StatusPill with A12's vocabulary mapped by one table in the feature package: `active` green, `pending` amber (with `pending_reason` `cosign | approval`), `suspended` amber (with a sentence per A12 `hold_class` and A101 hold source, for example "Held by an anomaly check", "Held by RealX support", "Waiting for your co-holder's passkey" for `cosign_required`, "Locked while your account was dormant" for `owner_dormant`, "Paused while we review your account" for `account_under_review`), `revoked` red (with a sentence per A12 `revoke_reason` value, for example "Revoked by you", "Revoked by your sponsor owner", "Revoked by RealX support", "Account recovered", "Removed from the team", "Tenant suspended", "Account closed"), `expired` grey, and the `sandbox` environment brick. The sentence tables are keyed only by the values A12 and A101 publish in their OpenAPI entries; an unknown status, `hold_class` or `revoke_reason` string renders the pill without a sentence and fails the contract test; it is never guessed. A kill-switch pause is not a token status (it is A12's `423 AGENTS_PAUSED` with its tier) and renders as the banner in §6, not on the row.
- Row actions: "Activity" (to the token's activity), "Change limits", "Rotate", "Revoke" (danger). Revoked and expired tokens stay listed (greyed, below the live ones) with their activity readable; they cannot be reactivated, only replaced by a new token.
- Banner under the header (A05 Banner, blue tone as in the product-map mock): "Your agent can never change your bank account, recover your wallet, create tokens or make declarations for you." The sentence is fixed copy; the list of never-delegable acts shown in the ScopePicker comes from the API.
- Empty state (no tokens): A52's `EmptyState` "No agents yet · Create a token to let your own AI agent read your portfolio or invest within limits you set" with "Create token" and "Open the API docs ↗" (A99's `/docs` agent quickstart for investors). A person whose type cannot hold tokens (INV-M guardian, P3) gets the API's `PHASE_NOT_ENABLED` rendered as a PreviewBanner and no create button. A person whose account is under review: the page renders only the status and reason class the API returns and never infers review status itself. Today A12's trigger table holds every token with the neutral class `account_under_review` on A30's `investor.suspended` (driven by ADM-09 freezes and by A42's `aml.account.restrict`), which renders "Paused while we review your account"; A101's AML boundary says an AML restriction should trigger nothing, because a pause is itself a signal. That conflict is raised at Specify as point (i) for the founder and MLRO (HG-LEGAL), not settled here. Whichever way it is settled, the tipping-off rule on this page is the same: the component has no prop for a case id, list name, alert or reason text, no AML, sanction, PEP or case wording may render, and an AML-restricted account's responses and DOM must be identical (after id substitution) to either an ordinary account's (if A12 drops the hold) or a non-AML ADM-09 freeze's (if it keeps it).
- Page-wide states: loading skeleton rows (no placeholder figures); `ErrorState` from A52 for any non-2xx with the error-sentence table plus this node's screen sentences (§8); the paused banner (§6) when any kill-switch tier is on.

**3. Create flow (`/account/agents/new`): five steps, one payload, one passkey**

- A HorizontalStepper as A50 draws it: Name and agent / Scopes / Limits / Confirm with passkey / Copy once. The flow holds one draft payload object in component state (never in the URL, local storage or the server); each step edits that object; Back never loses entries; leaving the flow discards the draft after a confirmation card if anything was entered.
- **Name and agent.** Token name (1-60 characters, shown to the person and in notices) and an agent label; both are plain text, trimmed, with control and bidi-override characters refused by the API and escaped on render everywhere they appear (list, activity, notices, the team view). A "Live" / "Sandbox" choice sits here; choosing Sandbox jumps to the sandbox path in §5.
- **Scopes: the ScopePicker.** Rendered from A12's per-viewer family listing (`available_families`, each family with its cells and each cell's state for this viewer: `selectable`, `not_yours`, `never_delegable`, `needs_counsel`). Families for investors: Read; Invest and trade; Money movement; Documents; Governance (P2 rows carry the phase pill); Account settings. A selectable row has a checkbox; the other three states render greyed and unclickable with the reason pill ("Not yours" grey, "Never delegable" grey, "Needs counsel" amber) and a one-line explanation. Approve, ratify, veto and execute-or-sign cells never appear as rows at all: the feature drops any such cell defensively and reports a contract failure in test and local modes. If A12's frozen listing does not carry the greyed states (only the selectable cells), the full per-viewer listing is requested from A12 as a follow-up loop at Specify; the browser never builds its own list of scopes or its own non-delegable list. The picker re-reads the listing when the step opens, so a classification upgrade or a role change since page load is reflected.
- **Limits.** Fields feeding the mandate exactly as A12 §4 names them: per-order cap and daily and monthly caps (AUD text fields in Geist Mono parsed to integer cents with A02's money parser from `packages/domain`; no float, no `parseFloat`, lint-enforced), property and trust allow-list as FilterChips from the person's eligible vehicles read, allowed actions (a subset of the chosen scopes, pre-checked), time windows (weekday and hour chips in Australia/Sydney), expiry (default 90 days, maximum 365, and never later than the `max_expires_at` the API returns for this person, shown as "capped at your wholesale certificate expiry, 30 Jun 2028" when that is the cause), optional IP allow-list (TextArea, one CIDR per line, validated by the API; the screen only pre-checks syntax), rate limit (read-only ceiling per principal type from the API, adjustable downwards only). Two optional sections: "Pre-authorise confirmations up to these caps" (an AcknowledgeCard; when ticked the person pastes the Ed25519 public key their agent generated, the screen validates its encoding and length, and never generates or sees a private key: a private key created in a browser would sit in the browser), and "Allow on-chain actions" (shown only when the listing has a wallet cell that is delegable in the current phase; it shows the session-key policy A12 derives from the caps: contracts, functions, amounts, expiry; in P1 with no delegable wallet cell it renders a PreviewBanner "On-chain actions for agents arrive with resale and votes (2027)").
- **MandateSummary.** A cream card restating the draft in plain English, produced by a pure function `mandateSummary(payload)` in the feature package from the same payload object that will be sent: "My research agent may buy up to A$1,000 an order and A$5,000 a month, in any open wholesale offer, on weekdays 9 am-6 pm Sydney time, until 22 Dec 2026. It can read your portfolio and download your documents. It can't withdraw money, change your bank account or create other tokens." Every field of the payload appears in the sentence and nothing else does; "can't" clauses list the families the person left unticked plus the never-delegable acts from the listing. The card is repeated on the confirm step and on the token detail page for the current mandate version.
- **Confirm with passkey.** The DropBox-style panel "Confirm with Face ID, Touch ID or Windows Hello · this proves it's you, not an agent". The screen posts `POST /v1/agent-access/tokens` with an idempotency key bound to the canonical payload: a new key whenever the payload's canonical hash changes (the person went back and edited a scope, cap, window or expiry), the same key for every retry of an identical payload. The key is derived in component state from a random draft seed plus the payload hash, never stored outside component state. The API answers `FRESH_ASSERTION_REQUIRED` with the canonical payload hash; before starting the ceremony the feature recomputes the hash of the displayed payload with the hashing function exported by A12's frozen `packages/domain/src/agent-authority/mandate-hash.ts` (imported, never re-implemented) and refuses to start if the two differ ("What you'd sign doesn't match what's on screen. Nothing was created." and a contract-failure report). Then `withFreshAssertion` runs the ceremony and retries once. Specify point (g) confirms with A09 and A52 that a 4xx refusal (including `FRESH_ASSERTION_REQUIRED` and every `SCOPE_*` refusal) releases the idempotency claim rather than being stored and replayed; if A09 stores 4xx replies, the retry after the ceremony uses a key derived from the payload hash plus the assertion id instead, and the node records which rule applies. A double click, a reload mid-ceremony or a network retry produces at most one token; a refusal followed by an edit and a resubmit produces exactly one token and never `idempotency_key_reused`. Refusals return the person to the step that caused them with the cell or field named: `SCOPE_EXCEEDS_OWNER`, `SCOPE_AGENT_NEVER_CHECKER` (an approve or sign cell, which reads "Agents never approve"), `SCOPE_NON_DELEGABLE`, `SCOPE_PENDING_COUNSEL`, `SCOPE_PHASE_OFF` and `SCOPE_UNKNOWN` go to Scopes; `POLICY_CEILING`, cap, expiry, window and IP errors to Limits; `FRESH_ASSERTION_STALE` and `FRESH_ASSERTION_MISMATCH` restart the confirm step with nothing created; `TOKEN_IDENTITY_NOT_VERIFIED` (G01, identity not verified) ends the flow with "Verify your identity before you create a token. Nothing was created." and a link to the person's identity-verification step through `href` (ONB for investors, the member's own verification for sponsor members); `TOKEN_SIGNATORY_REQUIRED` (entity investor, not a verified signatory) and `PHASE_NOT_ENABLED` end the flow with the sentence. The create button is never hidden on a guess that the person is unverified: the refusal comes from the API.
- **Copy once.** The WalletCard mono ValueChip with the full secret, a Copy button (clipboard write only on click), a red Banner "Shown once. RealX stores only a hash. If you lose it, rotate the token.", and the connection details: the REST base URL, the MCP connection snippet for stdio and HTTP transports rendered from A99's connection-guide template with the secret filled in on this step only, the SDK install line from A99's local registry, and links to the docs quickstart and to webhooks (§7). "Done" returns to the list with the new row. After "Done", back navigation, reload or a later visit shows the snippet with `rx_inv_K7Q2M4X9B3ND_••••` and no way to reveal the rest.
- Secret handling rules (this node's part of A12's "no secret anywhere" invariant): the create and rotate calls are made from a client component through the browser SDK client, never through a server action, route handler or server component, so the secret never enters Next.js server memory, the RSC payload or server logs; the response is excluded from the query cache (the mutation result is read once and dropped); the secret lives only in the Copy-once step's component state and is cleared on unmount, on "Done", on `visibilitychange` after five minutes hidden, and on sign-out; it is never written to `localStorage`, `sessionStorage`, IndexedDB, Cache Storage, the URL, history state, analytics, console output or an error report (A52's error reporter scrubs A12's token pattern as a second line); the ValueChip sets `autocomplete="off"`, is excluded from the accessibility name after leaving the step, and the page sends `Cache-Control: no-store`.
- Joint and entity paths, rendered from the API's answer: an INV-J account with "both to sign" gets a `pending` row "Waiting for {other holder} to confirm · expires in 23 h" and the other holder sees an "Activate with passkey" card on their ACC-05 with the MandateSummary of the pending payload (the same hash check before their ceremony); an expired co-sign shows `TOKEN_COSIGN_EXPIRED` as "Not confirmed in time. Nothing was issued." An entity signatory's token names the entity in the header ("For {entity name}", from the API).

**4. Token detail (`/account/agents/[tokenId]`): change, rotate, revoke, versions, activity**

- The current MandateSummary, the mandate version list (version, created, created by, "widened with passkey" or "narrowed", assertion time) read from A12's `mandates/{id}/versions`, remaining today and this month from `introspect` (the API's formatted figures), signing-key presence with "Remove key" (session only, immediate), and the session-key policy when on-chain actions are allowed.
- "Change limits" reuses the Scopes and Limits steps on a copy of the current payload. The browser shows its own guess ("This widens your agent's rights and needs your passkey" or "This only narrows them and applies at once"), but the API decides: the screen submits, and if the API answers `FRESH_ASSERTION_REQUIRED` it runs the hash check and the ceremony even when the guess said "narrow"; it never reports success before the API's 2xx, and a mixed change (lower cap, later expiry) is treated as a widening by the API and shown as one.
- "Rotate" (signed-in session, no passkey, per A12): a confirmation card naming the grace window returned by the API ("Your old token keeps working for 10 more minutes"), then the Copy-once step with the new secret under the same `TOK-` id; the same secret handling rules apply.
- "Revoke" (danger, signed-in session): a confirmation card "Revoking stops the agent on its next call". The card lists what will happen to the agent's open work (open orders placed by this token, open confirmations, webhook subscriptions created under it, the wallet session key) only from an API answer read before the click: A12 has no such read today, so a `GET /v1/agent-access/tokens/{id}/revoke-preview` is requested from A12 as a follow-up at Specify (point (h)). Until it exists the card shows the fixed sentence "Open confirmations are cancelled and webhooks created by this agent stop. Orders it placed follow the rule in the API docs." with a link to A99's docs, and no list; the browser never assembles the list from other reads. After the API's 2xx the row turns red. The row is never shown as revoked optimistically; if the call fails the card says so and the token is still shown as active. What happens to an agent's open orders on revoke is decided server-side through A37's revocation hook on `agent.token.revoked` (Specify point (d): the product map says "open agent orders cancelled"; proposed reading, to be confirmed with A37's frozen spec: orders not yet funded are cancelled, funded orders in escrow stay the person's orders). The browser never loops over cancel calls itself.
- "Revoke all" on the list page calls A12's `revoke-all` (one API call, signed-in session, a confirmation card) and renders its per-token result; it never reports "all revoked" unless the API's response says every live token was revoked. It is never emulated by a pause or by a loop of per-token revokes; if the operation is absent from the frozen OpenAPI entry the button does not render and the gap is escalated to A12.
- Activity (anchor `#activity`, and `/account/agents/activity` for all tokens): A12's `activity?token=` cursor list through the SDK's list helper, as a DataTable (Time / Action / Object / Amount / Result), newest first, "Load more", filters by token, result (allowed, refused) and date kept in the query string (ids and codes only). Each row carries the API's `actor_display` string rendered verbatim in Geist Mono, in A10's exact form `agent <TOK id> (<agent_name>) on behalf of <person label>` (for example `agent TOK-TD00000001 (treasury-drafter) on behalf of Priya N. (TRSY)`), on ACC-05 and SPN-16 alike; the screen never builds its own wording (if A12's `activity` read does not carry A10's `actor_display`, that field is requested from A12 at Specify), the G22 result as a pill (green "checked", red "refused"), and for refusals the reason in words with the named cell or cap and remaining figure ("Refused · daily cap · A$1,200 remaining", "Refused · scope missing · Withdraw money", "Refused · outside your time window", "Refused · paused by you"); other gate refusals the call hit downstream are shown by `gateLabel` ("Refused · G07 holder cap"). Object cells link to the object's own screen (order, statement, distribution) through `href`; an object the person can no longer see renders as its id without a link.

**5. Sandbox tokens (A99)**

- A bordered "Sandbox" card on both pages with the brick pill, the person's `rx_sb_` tokens, "Create sandbox token" (outlineSoft), the note "Sandbox tokens can't touch real data or money" and "Open the API docs ↗" and "Reset my sandbox" (A99's reset, with a confirmation). A sandbox token's create path is the same flow with the Limits step reduced to what A99 accepts; whether it needs a passkey is A99's decision returned by the API (Specify point (b): A50 draws it without a passkey step, A12 and A99's spec point (a) require an assertion on every create; the screen supports both by following the API's `FRESH_ASSERTION_REQUIRED`, never by skipping the step on its own). "Reset my sandbox" calls A99's `POST /sbx/v1/developer/sandbox/reset` from the person's own session after a confirmation card and renders `409 SANDBOX_NOT_READY` and `429 SANDBOX_LIMIT_REACHED` with their sentences. Sandbox tokens and their activity are never mixed into the live table, KPIs or activity list; the environment pill is always visible on the row and on the Copy-once step, and the connection snippet points at the sandbox base URL A99 returns.

**6. Confirmations, notices, anomaly holds and kill switches (A12 and A101)**

- "Waiting for you" section at the top of the page when the API lists open confirmations (`428 CONFIRMATION_REQUIRED` raised by an agent above its caps or without a signing key): one card per confirmation with the action, property, amount and expiry rendered from the confirmation's server-side canonical payload (never from text the agent supplied), the token that asked, and "Confirm with passkey" (A12 `confirmations/{id}/confirm` through `withFreshAssertion`, with the same hash check) or "Decline". An expired confirmation shows "Expired · the agent will need to ask again". Agent-supplied strings anywhere on the card (token name, order note) are inert text, never a link or markup, and are visually subordinate to the server's description, so a name such as "RealX Security · confirm now" cannot pose as RealX.
- Notice settings: a CheckList "Tell me when an agent…" from A101's NoticePolicy read for the person (places an order, moves money, is refused by a gate, is used from a new IP, reaches its daily cap, is held by an anomaly check, reads documents), with the rows A101 locks rendered with the grey "Required" pill and no toggle (money movement and orders always on); thresholds (for example "orders above A$500") are A101's fields with its bounds. Changes are saved through A101's `PUT /v1/agent-guard/notice-policy`: a change that only tightens (a row switched on, a threshold lowered) saves with the signed-in session; a change that loosens anything gets `FRESH_ASSERTION_REQUIRED` (purpose `notice_policy_loosen`) and runs `withFreshAssertion` over the new policy hash, with the same hash check as the create flow. The screen may label a change "loosens · needs your passkey" as a guess, but the API decides, as in §4. Notices go to the person's channels, which this page lists but does not edit (ACC-03 and ACC-01 own them).
- Anomaly holds: a token `suspended` by A101 shows an amber card "Held because it placed many orders in a short time · Today 09:14" (the rule's plain-English name from A101) with "Review activity" and "Clear hold with passkey". Clearing offers the choice A101 requires, "Resume this agent" or "Revoke this agent" (`resolution: resume | revoke`), then runs `withFreshAssertion` (purpose `anomaly_clear`) over A101's canonical hash of the hold, its anomalies, the chosen resolution and the acknowledgement text version. A hold that RealX staff placed shows "Held by RealX support" with the person-facing sentence of A101's reason code and no Clear button; a crafted clear is refused `GUARD_HOLD_PLACED_BY_STAFF` and rendered as a refusal. A hold cleared by RealX staff shows who cleared it as "RealX support" with the reason A101 exposes to the person.
- Kill switches: "Pause all my agents" (danger button with a confirmation card) calls A101's per-user tier; the paused state is an amber Banner across both pages "All your agents are paused · Resume", and "Resume" always needs a passkey. Specify point (c): A101's summary says the person pauses "with a passkey"; proposed, since pausing only removes rights, that pausing needs the signed-in session and a confirmation (like revoke in A12) and resuming needs a passkey; A101's frozen rule wins and the screen follows the API's answer either way. A change applied without an assertion when the API required one fails the node.
- **Revoke under fire (money, security).** An agent script places a Kent Street order through the SDK every 200 ms while the person clicks Revoke: the row must not turn red before the API's 2xx; after it, the script's next call must be refused `TOKEN_REVOKED`, the consequences card must list exactly what A12's `revoke-preview` returned (or, until that read exists, no list at all, never a client-assembled one), and "Revoke all" must make one `revoke-all` call and never say "all revoked" unless its response says so; the same run with "Pause all my agents" must stop every live token at once and show the per-user banner, and Resume without a passkey must be impossible.
- **Confirmation phishing (money, agent misuse).** An agent named "RealX Security · confirm now" asks for a A$1,500 order against a A$1,000 cap with an order note containing markup and a link: the "Waiting for you" card must describe the action, property and amount from the server's canonical payload, render the name and note as inert, subordinate text, and require the passkey; confirming with the agent's own bearer token through the SDK must be refused; a confirmation left for 24 hours must show as expired and refuse a late confirm.
- **Tipping-off and tenant isolation (compliance).** For the seeded AML-restricted investor, the node QA diffs the API responses and the rendered DOM of ACC-05 (list, detail, activity, notices) against the same pages for the non-AML ADM-09 freeze persona and against an ordinary account: after id substitution they must match whichever the API's settled rule produces (Specify point (i)), the page must render only the status and hold class the API returned, and the DOM, accessibility tree and SDK responses must contain no "AML", "sanction", "PEP", case id, alert id or reason text; a rendering that differs from the non-AML case, or any sign that the client inferred review status itself, fails; Mia Chen opens `/s/other-tenant/agents` and a token id of Alex Morgan's in her activity filter: A52's 404 and the API's 404, never an empty list that confirms existence.
- **Design drift (design fidelity).** Screenshots of ACC-05 (list, create steps 2-5, detail, paused, empty) and SPN-16 (my tokens, team tab, pending row as requester and as owner) at 1280px and 375px are compared with A50's drawings by the token-level harness: a status pill outside the TONE map, a secret not in Geist Mono, a Revoke styled as primary, an Approve shown on the requester's view, a colour one step off a token, or page-level horizontal scroll at 375px fails; seed names and times do not.
