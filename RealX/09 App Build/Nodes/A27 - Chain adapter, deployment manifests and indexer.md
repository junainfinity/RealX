# A27 - Chain adapter, deployment manifests and indexer

**The one road between the RealX API and the chain, in both directions: a viem transport behind the `chain` adapter (Hardhat now; Base Sepolia and, behind a human gate, mainnet by URL and chain id only), typed ABIs and a deployment manifest per chain in `packages/contracts`, the Token registry rows that carry SM-06 from `designed` to `configured`, and the worker indexer that turns logs into `Holding` read models at block N, binds every gateway and multisig execution to its `CustodyOp` on `(approvalId, nonce)` plus emitter, transaction hash, target and keccak of the calldata, cross-checks itself against direct `balanceOf` / `totalSupply` / `isFrozen` / `isAgent` reads, serves A20's frozen `ChainSnapshotSource` contract, and raises the stuck-transaction (30 min) and indexer-lag (5 min) alerts. Nothing in this node signs a privileged transaction; it observes, verifies and reports, and it decides when a supply-moving `CustodyOp` is `confirmed` (the observation half of G13).**

**Build status:** not started. **Milestone:** AM2 (Token and wallet core). **Lane:** Chain. **Planner:** Opus 5.5 (high). **Builder:** Grok 4.7 (xhigh). **Node QA:** Opus 5.5 (high, every loop). **Graph QA:** Fable 5.1 (high, at milestone close).
**Estimate:** 12-16 agent-hours (build, challenge and verify loops).

**Depends on:** [[A24 - ERC-3643 suite and RealX compliance modules]], [[A25 - AgentGateway and owner multisig- approval IDs bound on-chain]], [[A26 - Passkey smart wallet, paymaster and guardian recovery contracts]], [[A09 - API and worker skeleton with OpenAPI-generated SDK]], [[A13 - Alerts and SLA-clocks service]], [[A06 - Seed data and scenario simulator]] (token records, `chain-state.json`, the seeded approvals), [[A12 - API tokens, scopes, agent principals and mandates for every user type (G22)]] (G22 middleware, token-per-role tests, `on_behalf_of`; brings [[A11 - Authentication, sessions, RBAC and segregation of duties]] and the service principal), [[A14 - Approvals engine and maker-checker (SM-00)]] (the approved `deploy_approval_id` and the config-switch approval), [[A15 - Custody sandbox adapter and policy engine P1-P10]] (`CustodyOp` states, status callback, bundles, sandbox custody), [[A18 - Unit register (legal record) and registry sandbox adapter]] (the seeded 9,998 register), [[A20 - Three-way reconciliation engine with zero tolerance]] (`registerChainSnapshotSource`, targeted and pre-flight runs, its oracle), [[A104 - MCP server generated from the OpenAPI document]] (the MCP catalogue criterion). All added dependencies are AM0 or AM1, so there is no cycle and AM2 ordering holds; the graph data must carry these edges too.
**Unlocks:** [[A28 - Token operations service (mint, burn, freeze, pause, forced transfer, recovery)]], [[A29 - Wallet service- smart-account factory, bundler sandbox, guardians and recovery requests]], [[A31 - On-chain identity and claims service (V4 identity agent)]], [[A46 - Job scheduler, integrations health and webhooks]], [[A47 - Portfolio, holdings and transactions read models with statements]], [[A86 - Base Sepolia integration run and HG-AUDIT pack]], [[A96 - P3- AUD stablecoin rail, V5-V6 vaults and travel rule (G15)]]

**Oracle rule:** oracle node (`oracle: yes`). Money, supply and holdings are not moved here, but this node decides when a supply-moving `CustodyOp` is `confirmed`, so the node QA writes hidden oracle tests from this note to `<workspace>\gauntlet\hidden\A27\` before the build starts ([[App Gauntlet]] §2). The oracle scope is fixed: (1) the binding match: a `CustodyOp` reaches `confirmed` only on a full match of `(approvalId, nonce)`, emitter, transaction hash, target and recomputed keccak of the op's own calldata, after the configured confirmations, exactly once; (2) unbound flagging: every supply-changing or restrictive event without a matched execution in the same transaction is flagged `unbound` and raises a Sev1 at once; (3) the fail-closed snapshot: a read model that disagrees with a direct archive read at the same block never reaches recon; (4) the reorg rewind: a fork deletes exactly the orphaned rows, rebuilds from the fork block, never leaves a ghost balance and never silently leaves a confirmed op standing on an orphaned block. The rest of the hidden material (the gateway-bypass mint, the forged `Executed`, the corrupted `Holding` row, the wrong code hash, the stuck and lag clocks, the seed against the design regions) is challenge material written at the same time. The builder never reads that folder; the material is published into `app/` after the gate passes. The money-moving dependents (A28, A29, A31) re-run it as regression.

This note is not legal advice. The chain id and RPC allow-lists, the confirmation depth and every threshold below are data with a default; nothing here decides which mainnet RealX uses (a founder decision behind HG-PROD).

## Build brief

**1. The `chain` adapter (`<workspace>\app\packages\adapters\chain\`)**

- `manifest.ts` calls A08's `defineAdapter` with `name: 'chain'`, the zod interface contract, `implementations: { sandbox }` only, and `swap: { humanGate: 'HG-PROD', candidates: ['Alchemy', 'QuickNode', 'Redbelly RPC'], whatChanges: 'RPC URL and chain id only; the Hardhat control verbs are absent on any chain other than 31337' }`. A08's `SWAP-POINTS.md` cross-check picks the row up unchanged. There is one implementation because the sandbox is simply viem over an allowed RPC: `CHAIN_ID=31337` with the Docker Hardhat chain from A07 in every gauntlet run, `CHAIN_ID=84532` with a `*.base.org` host only when A86 runs; A08's config refuses anything else and this node never re-reads `process.env`.
- `interface.ts` (all verbs typed with the ABIs of §2, every call carrying the request or job id into the pino log): `chainId()`, `head()` (number, hash, timestamp), `getBlock(n)`, `getLogs({ addresses, fromBlock, toBlock, events })` in windows of at most 2,000 blocks, `readAt(contract, fn, args, blockNumber)` for archive reads (`balanceOf`, `totalSupply`, `isFrozen`, `getFrozenTokens`, `paused`, `isAgent`, `identityRegistry`, `compliance`, `owner`, `getModules`, `HaltModule.isHalted`, `LockInModule.unlockAt(compliance, identity)`, `SuiteInspector.rulesHash` and `holdingState`, `DocumentAnchor.latest`, ONCHAINID `getClaim`, the gateway's signer, quorum and attestation-signer getters), `getTransaction(hash)`, `getReceipt(hash)`, `estimateGas`, `sendGatewayCall(bundle)` and `getCodeHash(address, blockNumber)`.
- **One broadcast verb, `sendGatewayCall(bundle)`**, the name A28 uses (A86's reference to `sendSignedBundle` is renamed; see the cross-node list in the gauntlet section). It is idempotent on `op_id`: a second call with an `op_id` that already has a `chain_tx` row in `submitted`, `pending`, `mined` or `confirmed` returns that row and sends nothing. It accepts three bundle kinds and verifies each before any RPC call, refusing with `CHAIN_UNBOUND_BUNDLE` otherwise:
  - `custody` (A15): the `op_id` exists in A15 in state `signed` (V2, V3) or `onchain_queued` past `executableAt` (V1 execute); the raw transaction's `to` is the manifest gateway (V2 or V3) or owner multisig for the op's vault and its chain id is the configured one; the inner call's `target` equals the op's target and `keccak256(inner calldata)` equals `keccak256` of the op's stored calldata, which this node recomputes; the attestation (V2, V3) recovers over A25's EIP-712 domain to the attestation signer and the signer signatures recover to at least `quorum` distinct current signers, both taken from the indexed gateway configuration at the cursor (`SignerAdded`, `SignerRemoved`, `QuorumSet`, `AttestationSignerSet`), so no RPC is needed to refuse; the op has never been broadcast (no `chain_tx` for it).
  - `userop` (A29's sandbox bundler, `RUN_MODE=local|test` only): the `handleOps` transaction targets the manifest EntryPoint and its `userOpHash` is recorded by A29 in state `sent`.
  - `deployer` (§3's sandbox deploy only): chain id 31337, `RUN_MODE=local|test`, from A07's account 0, carrying the sandbox deploy request id.
  A hand-built raw transaction, or a well-formed custody bundle whose `op_id` is unknown, not `signed`, already broadcast, or whose calldata, target, attestation or signatures do not verify, is refused with `CHAIN_UNBOUND_BUNDLE` and nothing is sent. The adapter holds no key of any kind.
- **Re-broadcast is owned by this node alone.** When a `chain_tx` of kind `custody` or `userop` has been `submitted` or `pending` for 10 minutes (policy data, below the 30-minute alert), the watch job re-sends the identical signed raw bytes (same hash, so the chain can include it at most once and A25's replay guard is a second barrier), at most three times, counted in `chain_tx.rebroadcast_count` on the same row. No caller re-broadcasts; A28 and A29 never call `sendGatewayCall` twice for one op.
- `control` capability, present only when `chainId() === 31337`: `increaseTime(seconds)`, `setNextBlockTimestamp(ts)`, `mine(n)`, `setAutomine(bool)`, `snapshot()`, `revert(id)`, `impersonate(address)` (test harness only), implemented over A07's `infra/chain/control.ts` helper. On any other chain id the capability is absent and a call returns `NOT_A_HARDHAT_NODE` without sending anything. The worker subscribes to A09's `clock.advanced` outbox event and calls `increaseTime(seconds)` then `mine(1)` so that timelocks, lock-ins and session-key expiries on the local chain move with the platform clock; the subscription is a no-op on any other chain id.
- **Chain time and platform time are aligned.** The local platform clock starts at A06's `AS_OF`, and Hardhat cannot move time backwards, so the Docker chain must start at A06's chain genesis date (Hardhat `initialDate` from `CHAIN_GENESIS_DATE`, which A06's `chain-state.json` sets before its earliest seeded chain event; this is an A07 configuration item, listed below). At API and worker start, after the local replay of §6, and after every `clock.advanced`, the adapter asserts `|latest block timestamp - clock.now()| <= blockTimeSeconds + 5 s`; on failure status reports `chain: unhealthy` with `CHAIN_CLOCK_SKEW`, the indexer stops evaluating lock-ins, `sendGatewayCall` refuses, and the Sev2 `chain.clock_skew` alert is raised. When chain time is behind the platform clock on 31337 the adapter first closes the gap with `setNextBlockTimestamp` and `mine(1)`; when it is ahead it cannot, and the chain must be reset.
- **Network or RPC switch (ADM-32 "Switch RPC or network config", ENGO -> SECO, G13, config v+1).** The action lives on A46's integrations surface; this node exposes `validateChainConfig(candidate)` and `applyChainConfig(version, approvalId)` through its `index.ts`. `validateChainConfig` refuses a chain id outside the allow-list or a host outside the policy table with `CHAIN_NOT_ALLOWED` before any approval request is created, and probes the RPC for the chain id it reports. `applyChainConfig` runs only for an A14 approval in state `approved` whose payload hash equals the candidate's hash: it drains in-flight reads, re-initialises the transport, re-runs `manifest:check` for the new chain id, and resumes the indexer from `indexer_cursor[chain_id]` (the cursor is keyed by chain id, so switching back resumes where that chain stopped). `CHAIN_ID_MISMATCH` latches the adapter until the next approved config is applied or the process restarts.
- Errors are named and typed: `CHAIN_UNREACHABLE` (with the host, never the full URL with credentials) after 10 s, `CHAIN_ID_MISMATCH`, `CHAIN_NOT_ALLOWED`, `CHAIN_CLOCK_SKEW`, `CHAIN_BLOCK_NOT_AVAILABLE` for an archive read the node cannot serve, `CHAIN_LOG_WINDOW_TOO_WIDE`, `CHAIN_UNBOUND_BUNDLE`, `CHAIN_MANIFEST_DRIFT`. Idempotent reads retry three times with backoff.
- `conformance/*.conf.ts` runs through A08's `runConformance` harness against the sandbox: every verb, the window limit, the chain-id mismatch refusal, the unbound-bundle refusals (raw transaction and well-formed forged bundle), idempotency on `op_id`, `readAt` at three historic blocks after a mint, snapshot and revert, the skew check, and determinism (two runs from `reset` give identical logs). It is the suite a human runs against a vendor RPC after HG-PROD before that URL may be configured.

**2. Typed ABIs, chain policy and deployment manifests (`packages\contracts\src\` and `packages\contracts\deployments\`)**

- `src/abis/` is generated from `contracts/artifacts` (A07's rule: only compiled ABIs and addresses cross from `contracts/` into this package; no T-REX source, tests or comments are copied) by `npm run contracts:export`, which A24, A25 and A26 already invoke from their deploy scripts. Each ABI file carries the artifact's bytecode keccak and the solc settings hash; `src/index.ts` exports viem `Abi` constants and typed `getContract` helpers for Token, IdentityRegistry, IdentityRegistryStorage, TrustedIssuersRegistry, ClaimTopicsRegistry, RealXClaimIssuer, Identity, ModularCompliance and the **six** compliance modules A24 binds, DocumentAnchor, SuiteInspector, TREXFactory, AgentGateway, RealXOwnerMultisig, SmartAccountFactory, the smart account, RecoveryModule, SessionKeyModule, RealXPaymaster and EntryPoint v0.7. A verify check fails if an exported ABI's bytecode hash differs from the current artifact (stale export).
- `src/events.ts` is generated from those ABIs: the decode table the indexer uses is exactly the set of events the exported ABIs declare, per contract kind. No event name is hand-written; an event this note names that no exported ABI declares is a spec defect, not something to invent.
- `src/format.ts` exports `shortHash(hash)` returning the design's `0xa1…9f` form (the `0x` prefix and first two hex digits, an ellipsis, the last two hex digits) so no screen truncates by hand. A09's SDK re-exports it (an A09 addition); until then apps import it from `@realx/contracts`.
- `src/chain-policy.ts`: per allowed chain id, `confirmations` (31337: 1; 84532: 3), `blockTimeSeconds` (31337: 0 with automine; 84532: 2), `logWindow` (2,000), `explorerBase` (null for 31337; the Base Sepolia explorer for 84532), `controlAllowed` (31337 only), `rebroadcastAfterSeconds` (600). It reads A07's `chains.json` for RPC and EntryPoint entries and refuses at import time if a chain id appears in one file and not the other.
- `deployments/<chainId>.json` is the manifest, one file per chain, written only by `src/manifest.ts`'s `writeManifest()` which A24, A25, A26 (and A86 for 84532) call from their deploy scripts: `chainId`, `networkName`, `generatedAt`, `gitCommit`, `deployer`, `entryPoint`, `shared` (identityRegistryStorage, trustedIssuersRegistry, claimTopicsRegistry per rule pack, claimIssuer, identityFactory, trexFactory, suiteInspector, documentAnchor, the six modules, smartAccountFactory, recoveryModule, sessionKeyModule, paymaster, ownerMultisig, agentGatewayV2, agentGatewayV3, identityAgentV4 (A15's V4 address), each with `address`, `deployBlock`, `codeHash`, `abiHash`), `tokens[]` (one entry per vehicle deployed through the owner multisig: `vehicleId`, `token`, `identityRegistry`, `compliance`, `modules{}`, `deployBlock`, `codeHash`, `salt`, `deployApprovalId`), `sandbox[]` (the sandbox copies of §3, never treated as a vehicle's token) and `schemaVersion`. Writes are merge-by-key, never overwrite-all, and refuse to change an existing address (a redeploy is a new entry with a new salt). Manifests for 31337 and 84532 are committed; there is no code path that writes a manifest for any other chain id, and `manifest:check` fails on a file whose chain id is not in the allow-list.
- `npm run manifest:check` (part of `verify:chain`, called by A23's boot criterion and by the API at start in `local|test`): for every address in the manifest, `getCodeHash` on the configured chain equals the recorded `codeHash`; the EntryPoint is at its canonical address; for every token the agent set (§4 enumeration) is exactly `{agentGatewayV2, agentGatewayV3}` and `ownerMultisig` is its owner (R1 role check, read directly); every `abiHash` equals the exported ABI. A mismatch makes the API start in `chain: unhealthy` state (reads work, the indexer stops, `sendGatewayCall` refuses with `CHAIN_MANIFEST_DRIFT`) and raises the alert in §6.

**3. Token registry rows and SM-06 (`services\api\src\modules\chain\`)**

- Module `chain` follows A09's pattern: a public `index.ts` (boundary lint), zod schemas feeding the OpenAPI document from the first commit, Drizzle schema and migration in the module folder registered with A04's per-module registry, RLS on `tenant_id` (a sponsor sees only its own vehicles' rows). Tables: `token` (the registry row per vehicle: `chain_id`, `vehicle_id`, `name` "RealX <Trust> Units", `symbol`, `decimals` 0, `supply_rule` default 10,000, `token_address`, `identity_registry`, `compliance`, `modules_json`, `document_anchor`, `agent_gateway`, `owner_vault_id` V1, `rule_pack_id`, `params_sha256` expected, `rules_hash` expected (A24's keccak), `state` (SM-06), `deploy_approval_id`, `test_report_sha256`, `audit_slot` (`placeholder` until HG-AUDIT), `deploy_block`, `salt`), `chain_tx`, `chain_event`, `multisig_proposal`, `holding`, `token_chain_state`, `gateway_state`, `indexer_cursor` (keyed by `chain_id`) (§4).
- **SM-06 ownership, one owner per transition.** This node owns `designed -> sandbox_deployed -> deploy_requested -> deployed -> configured` and drives every one of them itself (HTTP for the first three, the indexer and `verifyConfigured` for the last two). A28 owns every transition from `configured -> issuing` onward and drives them through this module's internal `transition(tokenId, to, cause)` interface, which checks A03's table and writes the audit event; `transition()` refuses any of the five transitions owned here with 409 `transition_not_owned`. A28's spec currently also lists `deploy_requested -> deployed -> configured`; that line must be removed there (cross-node list). Anything not in the A03 table returns 409 `transition_not_allowed` with the current state.
  - `designed`: `POST /v1/chain/tokens` from a vehicle in a state that allows it (A03 table; `spv_formed` or later), permission `chain:design`, computing A24's production salt `keccak256(chainId, "realx.vehicle.", vehicleCode)` and the counterfactual addresses of token, IR and compliance from the manifest `trexFactory`, so the row has addresses before anything is deployed.
  - `sandbox_deployed`: `POST /v1/chain/tokens/{id}/sandbox-deploy`, `RUN_MODE=local|test` and chain id 31337 only, `chain:sandbox_deploy`. It deploys a **sandbox copy** with the distinct salt `keccak256(chainId, "realx.vehicle.sandbox.", vehicleCode, attempt)` through A24's `deploy-vehicle.ts` (the salt-namespace parameter is an A24 addition) and a `deployer` bundle, runs A24's vector suite for the vehicle's parameters against the copy, records `test_report_sha256` on the row and the copy in the manifest's `sandbox[]`. The production salt is never used, so the quorum deploy at the counterfactual addresses stays possible. Any other chain id returns 403 `SANDBOX_DEPLOY_LOCAL_ONLY` before any RPC call; a row not in `designed` returns 409.
  - `deploy_requested`: `POST /v1/chain/tokens/{id}/request-deploy`, `chain:request_deploy` (TOKO as maker), with the test report hash and the audit slot; refused with 422 `TEST_REPORT_REQUIRED` without the report. The call creates, through A14's interface, the `6E+Q` approval request (TOKO -> CCO + SECO, executed by the V1 owner 3-of-5) for the action `M09.token.deploy`, whose payload is the vehicle's suite-deploy call on the manifest `trexFactory`; the effector that turns the approved request into a V1 `CustodyOp` is registered by A28. The row stores `deploy_approval_id`.
  - `deployed`: recorded by the indexer only, on every chain including 31337, when all of these hold: (a) `deploy_approval_id` is in A14 state `approved` or later; (b) a multisig `Executed(id, approvalId)` from the manifest `ownerMultisig` with `approvalId = deploy_approval_id`, joined to its stored `Proposed(id, approvalId, target, selector, dataHash, makerId)` whose `target` is the manifest `trexFactory`, whose `dataHash` equals `keccak256` of the V1 op's stored calldata, and whose execution transaction hash equals the op's broadcast hash; (c) the token, IR and compliance exist at the row's counterfactual addresses with code hashes equal to the exported artifacts. There is no receipt-only path. An attempt to reach `deployed` any other way returns 409 `DEPLOY_NOT_BOUND`.
  - `configured`: recorded by `verifyConfigured(tokenId)`, a direct read at the head block: `identityRegistry()` and `compliance()` equal the row, all six modules are bound in A24's order and `SuiteInspector.rulesHash` equals the row's `rules_hash`, the token's agent set (§4 enumeration, each member confirmed by `isAgent` at the block) is exactly `{agentGatewayV2, agentGatewayV3}`, the IR's agent set is exactly `{identityAgentV4}`, `owner()` is the multisig for the token, IR and compliance, `paused()` is true (T-REX deploys paused; A28's first `unpause` and first mint move it to `issuing`). A row cannot reach `configured` with any check false; the failing check is returned by name.
- Read endpoints (all in the OpenAPI document under M09 and M26, cursor-paginated, `{items: [], next: null}` when empty):
  - `GET /v1/chain/tokens` (the ADM-40 token registry list, fields aligned to A51's columns: trust, symbol, contract address, supply, cap (`supply_rule`), register units and Δ (read from A20's last completed run through its `index.ts`), compliance modules (country, max balance, lock-up, identity, holder count, halt), paused, SM-06 state, plus holders, last indexed block, explorer link when the chain has one, and a `sandbox` flag for every row on 31337); `GET /v1/chain/tokens/{id}` with `token_chain_state` and the manifest entry.
  - `GET /v1/chain/holdings?token=&wallet=&state=` (SM-07 rows; staff and partners with `chain:read`, sponsors for their own tenant, and investors and their D04 tokens for their own wallets only, the `own-records` constraint).
  - `GET /v1/chain/txs/{hash}`, `GET /v1/chain/txs?custody_op=`, `GET /v1/chain/events?token=&type=&from_block=`.
  - `GET /v1/chain/manifest/{chainId}` (addresses and code hashes only; the source of PUB-08's "View on explorer" rows).
  - `GET /v1/chain/proof/{vehicleId}`, the **public projection** for PUB-08 and the `prop` ProofBand, readable by every principal including VIS and investor tokens: chain id, token, IR and compliance addresses, code hashes, explorer links, `total_supply` at the block of A20's last clean run for the vehicle, that run's completion time and result. No holder, wallet or balance other than the total appears in it.
  - `GET /v1/chain/snapshot?token=&block=` (§5; staff and partners with `chain:read` see addresses, sponsors see holders masked to wallet ids for their own tenant, investors are refused).
  - Under M26: `GET /v1/chain/status` (chain id, RPC host name only, head, cursor, lag seconds, confirmations, manifest check result, clock skew, control capability, config version).
  - `POST /v1/chain/reindex {token?, from_block, reason}`, `chain:reindex`, a mandatory reason, audited; it stops nothing else.
- Permissions (action cells in A03's matrix; any cell A03 lacks is an A03 addition): `chain:read` (ENGO, TOKO, SECO, CCO, REGO, CFO, TP-AUD, TP-OBS, TP-RE; SP-OWN, SP-FIN, SP-IR for their own tenant), `chain:proof_read` (every principal including VIS), `chain:own_holdings` (every investor role, `own-records`), `chain:design` (TOKO, ENGO), `chain:request_deploy` (TOKO, the maker of the `6E+Q` request), `chain:sandbox_deploy` (ENGO), `chain:reindex` (ENGO), `chain:config_propose` (ENGO; the checker SECO acts in A14, not here), `integrations:read` for status. Every call made with a token passes A12's `agentAuth` middleware, which runs `evaluateG22` with the route's cell and, for every per-vehicle write (`design`, `sandbox-deploy`, `request-deploy`, `reindex` with a token), the vehicle id, so the token's allowed vehicles, time windows, expiry, IP list and kill-switch tiers apply exactly as for any other route. A token may do exactly what its person may, as maker; none of these actions is a checker, approver or signer act. Every write is audited through A10 as the token on behalf of the person.

**4. The indexer (`services\worker\src\jobs\indexer\`)**

- `indexer.tail` runs every 2 seconds on 31337 (and every block time elsewhere), reading from `indexer_cursor[chain_id].last_block + 1` to `head - (confirmations - 1)` in windows of `logWindow`, for every address in the manifest plus every `token` row's addresses and every deployed smart account. Each log becomes one `chain_event` row keyed by `(chain_id, tx_hash, log_index)` with an insert-or-ignore, so re-running any window changes nothing (N13 idempotency). Decoding uses only `src/events.ts` (§2): the T-REX token, IR, IR storage, trusted-issuers, claim-topics and compliance events, ONCHAINID claim events, the RealX module events (including `UnlockSet` and `OverrideConsumed`) and `DocumentAnchor` events (A24); the gateway `Executed(bytes32 indexed approvalId, uint256 nonce, address indexed target, bytes4 selector, bytes32 dataHash, address executor)`, `SignerAdded`, `SignerRemoved`, `QuorumSet`, `AllowListSet`, `AttestationSignerSet`, and the multisig `Proposed`, `Approved`, `Queued`, `Vetoed`, `Cancelled`, `Executed(id, approvalId)` (A25); the account, `RecoveryProposed`, `RecoveryVetoed`, `RecoveryExecuted`, `SessionKeyRegistered`, `SessionKeyUsed`, `SessionKeyRevoked` and paymaster events (A26). A topic from a manifest address that the table cannot decode is stored raw with `decoded = false`, counted in status, and raises `chain.indexer_inconsistent`; in the standard suite the count must be zero.
- **State that has no event is read, not inferred.** A24's mint sets `unlockAt` without an event and the halt flag has no event in A24's list, so for every transaction that touches a token's compliance (mint, transfer, forced transfer, recovery, `UnlockSet`, a gateway `Executed` whose selector is `setHalt`, `halt` or `lift`) the job reads `LockInModule.unlockAt(compliance, identity)` for each touched identity and `HaltModule.isHalted` with `readAt` at that block and stores the values with the event.
- **Agent sets are enumerated from events.** ERC-3643 `AgentRole` can only answer `isAgent`, so the agent set of each token and each IR is the replay of `AgentAdded` / `AgentRemoved` since its `deployBlock`, and every member is confirmed with `isAgent` at block N; an address that `isAgent` confirms but no event added, or the reverse, marks the snapshot inconsistent.
- Reorg handling: before applying a window the job compares the stored hash of `last_block` with `getBlock(last_block).hash`; on mismatch it rewinds one block at a time until hashes agree, deletes `chain_event`, `multisig_proposal` and read-model rows above the fork, rebuilds every affected read model from the fork block, writes one `chain.reorg` audit event with the depth, and continues. For every orphaned transaction:
  - a `chain_tx` not yet `confirmed` goes back to `pending` (it may be re-included);
  - a `chain_tx` already `confirmed`, whose `CustodyOp` A15 has moved to `confirmed`, is set to `reorged`. Neither A03 nor A15 defines a way back from `confirmed`, so this node never moves the op backwards: it raises the Sev1 `chain.reorg_past_confirmation` (ENGO + CCO, ADM-14, dedup per op), writes the outbox event `chain.executed.reorged`, and asks A20 for a targeted run on the new canonical head (§5), whose R2 and R7 rules see the missing supply and hold the op out of `reconciled` with break ids. If the same transaction is re-mined and matches again, the `chain_tx` returns to `confirmed` on the new block and the alert resolves by system; nothing is confirmed twice.
  On Hardhat this path is exercised by `snapshot` / `revert`; on 84532 the confirmation depth makes it rare but the code is the same.
- `Holding` read model (SM-07, the mirror, never the legal record): one row per wallet x token with `identity_address`, `balance`, `frozen_amount`, `address_frozen`, `unlock_at` (taken **per identity** from `unlockAt[compliance][identity]`, since A24 locks per ONCHAINID; two wallets of one identity show the same value), `block_number`, `block_hash`, `as_of`, `state`. State is a pure function in `holding-state.ts` of the facts at block N and the platform clock, with this precedence when conditions overlap: `deregistered` (after `IdentityRemoved`) > `recovered_out` (the lost wallet after `RecoverySuccess` or a token-fallback forced transfer out) > `frozen` (`AddressFrozen(true)`) > `partially_frozen` (`frozen_amount > 0`) > `locked` (`unlock_at` after the platform clock) > `active` (balance > 0) > `eligible_empty` (registered, balance 0). So a locked holding with a partial freeze is `partially_frozen`, a frozen wallet inside its lock-in is `frozen`, and `IdentityRemoved` with a balance still present is `deregistered` and also raises `chain.indexer_inconsistent` (A31 must burn or move the balance first). `locked` returns to `active` when the clock passes `unlock_at` (evaluated on read and by the tail job, not by an event). For the six states A24's `SuiteInspector.holdingState` covers, the function must agree with `holdingState(token, wallet)` at block N; `recovered_out` and `deregistered` are event-derived here only.
- Unknown holders: a `Transfer` to an address whose identity was not registered in the token's IR by the manifest `identityAgentV4` (and, once A29 is present, has no `wallet` row) raises `chain.unknown_holder` Sev1 (REGO + CCO) through A13 with the token and address as subject, dedup per pair.
- `token_chain_state` per token at the cursor block: `total_supply`, `paused`, `halted`, `owner`, `agents[]`, `identity_registry`, `compliance`, `modules[]`, `rules_hash`, `holder_count`, `document_anchors[]`. `gateway_state` per gateway: signers, quorum, attestation signer, from events and confirmed by getters.
- `chain_tx` rows: `hash`, `chain_id`, `custody_op_id` (nullable; set when `sendGatewayCall` accepts a custody bundle), `approval_id`, `nonce`, `kind` (`custody`, `userop`, `deployer`, `foreign`), `submitted_at`, `seen_at`, `block_number`, `block_hash`, `status` (`submitted`, `pending`, `mined`, `confirmed`, `failed`, `dropped`, `reorged`), `rebroadcast_count`, `gas_used`, `revert_reason`. A tx is `confirmed` only when `cursor >= block_number + confirmations - 1`.
- **Binding executions to `CustodyOp`s (the observation half of G13).** One hash rule everywhere: on-chain comparisons use `keccak256(calldata)`; A15's `calldata_sha256` is a storage-integrity digest of the op's bytes and is never compared with an on-chain hash. A gateway `Executed` matches an op only when all of these hold: (a) the emitter is the manifest `agentGatewayV2` or `agentGatewayV3` and equals the op's vault gateway; (b) the pair `(approvalId, nonce)` equals the op's approval id and attestation nonce (one approval can cover several mint nonces, so the id alone never identifies an op) and the op is in `broadcast`; (c) the transaction hash equals the op's `chain_tx.hash`; (d) `target` equals the op's target and `dataHash` equals `keccak256` of the op's stored calldata, recomputed here, and equals `keccak256` of the inner calldata decoded from the transaction input; the emitter's `dataHash` is never trusted on its own. A multisig `Executed(id, approvalId)` has no target or data, so it is joined to its stored `Proposed(id, approvalId, target, selector, dataHash, makerId)` and matched on the same four parts; the multisig `Queued` for a V1 op drives A15's `signed -> onchain_queued` through the same callback. A `RecoveryExecuted(account, proposalId, ...)` is matched in the same transaction to the gateway `Executed` whose target is the RecoveryModule (and so to the `CustodyOp`), and to A29's `RecoveryRequest` (SM-13) by account and `proposalId` through the outbox event `chain.recovery.executed`; `RecoveryProposed` and `RecoveryVetoed` are published as `chain.recovery.proposed` and `chain.recovery.vetoed` for A29.
- On a full match after `confirmations` the job calls A15's status callback to move the op `broadcast -> confirmed` with block, hash and gas; A15 then emits `custody.op.confirmed`, which stays the single confirmation event that A20, A28 and A38 consume. On a mined transaction with status 0 the job calls the callback `broadcast -> failed` with the revert reason. The job never moves an op to `reconciled`.
- Any partial match (right id and nonce, wrong hash or data; right hash, unknown id; an `Executed` from an address not in the manifest; a `Proposed` join that fails) writes the event with `match_state = unmatched`, leaves the op untouched, and triggers a targeted run whose R7 and R1 rules raise the Sev1 `recon.break`.
- **Unbound changes.** A supply-changing or restrictive event (`Transfer` from or to the zero address, `AddressFrozen`, `TokensFrozen`, `Paused`, `RecoverySuccess`, `AgentAdded`, `AgentRemoved`, `OwnershipTransferred`, `ModuleAdded`, `ModuleRemoved`, `UnlockSet`, a halt or lift) in a transaction with no matched gateway or multisig execution is stored with `binding = unbound`. This node raises the Sev1 `chain.unbound_change` itself through A13 at once (SECO + CCO, ADM-14, dedup per transaction), writes the audit event and the outbox event `chain.unbound_change`, and asks A20 for a targeted run; A20's R1 (roles) and R7 (mints without an approval id, from `mints[]` in §5) raise their own breaks. Ordinary holder-to-holder `Transfer`s (P2 resale, session-key transfers) are `binding = n/a`.
- **Outbox events** (A09's outbox, one per occurrence, never per re-run), payload `{custodyOpId?, approvalId, nonce, vehicleId, txHash, blockNumber, blockHash, confirmations}`: `chain.executed.confirmed`, `chain.executed.unmatched`, `chain.executed.reorged`, `chain.tx.failed`, `chain.unbound_change`, `chain.recovery.proposed`, `chain.recovery.vetoed`, `chain.recovery.executed`. A28 consumes `chain.executed.unmatched` and `chain.executed.reorged` to cross-link the op detail; A29 consumes the recovery events; A46 lists them for webhooks.
- Stuck transactions and lag (A13's catalogue type `chain.stuck_or_lagging`, Sev3, ENGO, ADM-32): `indexer.watch` every minute, on the injectable clock, raises sub-code `stuck_tx_30m` for any `chain_tx` in `submitted` or `pending` for 30 minutes after its first submission, re-broadcasts included (dedup per hash; resolved by system when it is mined, failed or dropped) and `indexer_lag_5m` when the oldest unindexed block is older than 5 minutes (dedup per chain; resolved by system when the cursor catches up). The job never creates a second open alert for the same subject; a flapping condition increments `occurrences` only.
- **Alert types this node adds** through A13's registry from its own folder (`services/api/src/modules/chain/alerts.ts`, no change to A13's paths): `chain.manifest_drift` (Sev2, ENGO, ADM-32), `chain.indexer_inconsistent` (Sev2, ENGO, ADM-32), `chain.clock_skew` (Sev2, ENGO, ADM-32), `chain.unbound_change` (Sev1, SECO + CCO, ADM-14), `chain.reorg_past_confirmation` (Sev1, ENGO + CCO, ADM-14), each with a template and a params schema without PII. The catalogue types `chain.stuck_or_lagging` and `chain.unknown_holder` are used as A13 defines them.
- Bootstrap and empty states: with no manifest for the configured chain the indexer idles and status reports `manifest: missing`; with a manifest and no tokens it indexes the shared layer only; a fresh database re-indexes from the earliest `deployBlock` in the manifest and reaches the head before it reports `lag = 0`; `reindex` deletes and rebuilds only the rows for the requested token from `from_block`, under a per-token lock, while other tokens keep tailing.

**5. The chain snapshot source for reconciliation**

- `IndexerChainSnapshotSource` implements A20's frozen `ChainSnapshotSource` exactly and is registered through `registerChainSnapshotSource(source)` at worker and API start, replacing A20's in-memory stub (the stub remains for A20's own tests). `getSnapshot({tokenAddress, atBlock?})` (default: the last confirmed cursor block) returns A20's shape with A20's snake_case names: `{block_number, chain_id, token_address, total_supply, paused, roles {owner, agents[], identity_registry, compliance, agent_gateway}, holders[] {address, balance, frozen_amount, frozen}, ir_members[] {address, onchain_id, country}, claims[] {onchain_id, topic, issuer, valid_until, revoked}, compliance_params_sha256, document_anchors[] {doc_type, sha256}}` plus `mints[] {tx_hash, log_index, to, amount, block_number, approval_id | null}` for R7 ("every mint the snapshot source reports carries one approval id"). `agent_gateway` is the manifest `agentGatewayV2` when it is in the agent set; `claims[]` come from ONCHAINID claim events and the claim issuer's revocation events for every IR member's identity, confirmed with `getClaim` at the block; `document_anchors[]` from `DocumentAnchor` events, confirmed with `latest(token, docType)`; `compliance_params_sha256` carries the value A20 defines for it (see the cross-node list: A20 must say whether it is A24's keccak `rulesHash` or the SHA-256 `params_sha256`). A field A20 does not yet read (`mints[]`) is logged as an A20 spec defect before the freeze; nothing is renamed on this side.
- The snapshot is built from the read models at that block and then cross-checked by direct `readAt` calls at the same block for `totalSupply`, `paused`, `owner`, the agent set (event enumeration plus `isAgent`), the IR and compliance addresses, `rulesHash`, and `balanceOf`, `isFrozen` and `getFrozenTokens` for every holder in the read model plus every address in `ir_members`. Any difference marks the snapshot `inconsistent`: the call throws `CHAIN_SNAPSHOT_INCONSISTENT` naming the field and address, recon refuses to run on it (fail closed; A20 records the run as failed), a `reindex` of that token is queued automatically, and the Sev2 `chain.indexer_inconsistent` alert is raised. A20's pre-flight budget (5 s for 10,000 holders) applies to this source; over budget returns `incomplete`, which A20 treats as a refusal.
- The snapshot is reproducible: two calls for the same block return byte-identical JSON (canonical key order), which is what lets A20's `ReconRun` be replayed from its three keys. The block hash of each snapshot is kept in this node's `snapshot_meta(token, block_number, block_hash)` so a run on an orphaned block can be recognised.
- Targeted runs requested by this node (after an unbound change, an unmatched execution, or a reorg past confirmation) go through A20's `index.ts` (`preflight({vehicleId, purpose})` with purpose `chain_unbound`, `chain_unmatched` or `chain_reorg`) until A20 consumes the `chain.*` outbox events directly. After a reorg the run is on the new canonical head and must supersede any earlier clean run on an orphaned block (an A20 addition in the cross-node list).
- `GET /v1/chain/snapshot?token=&block=` exposes the same object to staff and partners, masked for sponsors as in §3; the public figure (ADM-17's "Token supply" column for staff, the `prop` ProofBand and PUB-08's "On-chain" column for everyone) is `total_supply` at A20's last clean run through `GET /v1/chain/proof/{vehicleId}`, so every surface reads one function.

## Node-specific challenges (node QA)

- **Reorg past confirmation.** Take an `evm_snapshot`, mint 100 units to a registered wallet through the gateway, let the indexer confirm it and A15 mark the op `confirmed` (with `confirmations = 1` on 31337), let A20 run a clean targeted run on that block, then `evm_revert` and mine an empty block. The tail job must detect the hash mismatch at the cursor, rewind only to the fork, delete the event and the `Holding` delta, write one `chain.reorg` audit event, set the `chain_tx` to `reorged`, raise `chain.reorg_past_confirmation` once, publish `chain.executed.reorged`, and request a run on the new head; the next snapshot must show the pre-mint supply, A20's new run must open the R2/R7 break and supersede the clean run on the orphaned block, and the op must never reach `reconciled`. Re-including the same transaction must return the `chain_tx` to `confirmed` and resolve the alert by system, with no second confirmation. An indexer that keeps the ghost balance, rewinds to genesis on a one-block fork, or silently leaves a confirmed op on an orphaned block fails.
- **Mint around the gateway.** With automine off, `impersonate` the owner multisig and call `addAgent(account 0)` on a token, then from account 0 mint 5 units, and mine both in one block, with no gateway or multisig `Executed`. The indexer must store the `AgentAdded` and `Transfer` events as `binding = unbound`, raise `chain.unbound_change` Sev1 once per transaction, the next snapshot must show the extra agent in `roles.agents` and the mint in `mints[]` with `approval_id = null`, and A20's targeted run must open Sev1 breaks for the vehicle (R1 role drift and R7 supply); no `CustodyOp` may move, and `GET /v1/chain/tokens/{id}` must show the extra agent. A node that only reconciles totals, and so reports "supply 10,005 = register 10,005" when A18's register was also edited by the node QA, has not checked roles or binding and fails.
- **Forged `Executed`, a forged bundle and a replayed id.** (a) Deploy a throwaway contract that emits an event with the same signature and the `approvalId`, `nonce`, `target` and `dataHash` of an open `CustodyOp`, from a transaction whose hash is not the op's: stored `unmatched`, op stays `broadcast`. (b) Pass `sendGatewayCall` a well-formed custody bundle with a real `op_id` whose op is not `signed`, then one whose calldata differs from the op's by one byte, then one with a signature from a non-signer: each refused with `CHAIN_UNBOUND_BUNDLE` before any RPC call (the RPC mock records zero calls). (c) Send a real gateway call re-using a consumed non-mint approval id (A25 reverts it): a `chain_tx` in `failed` with the revert reason, the op moved to `failed` through the callback, no `Executed` row. (d) Mint twice under one approval with nonces 1 and 2: two ops confirmed, each exactly once. An indexer that matches on `approvalId` alone, or trusts the emitter's `dataHash` instead of recomputing keccak from the op's own calldata, fails.
- **Corrupted mirror, honest chain.** As the database owner, change one `Holding.balance` from 1,200 to 1,250 and one `token_chain_state.total_supply` by 50. `getSnapshot` must throw `CHAIN_SNAPSHOT_INCONSISTENT` naming the wallet and the field, A20 must record a failed run and not a clean one, a `reindex` of that token must be queued and, after it, the snapshot must be consistent again with the original figures. A node that serves the read model without the direct cross-check, or that reconciles the corrupted figure against the register and opens a false break against the trustee, fails.
- **Clocks that only work in wall time.** With automine off, broadcast one custody bundle, then advance the platform clock by 29 minutes (no alert, and re-broadcasts of the identical bytes recorded at 10 and 20 minutes), then by 2 more minutes (`stuck_tx_30m` once, Sev3, ENGO); mine, and the alert must resolve by system with exactly one confirmation. Stop the tail job, mine 10 blocks, advance the clock 6 minutes: `indexer_lag_5m` once; restart and catch up: resolved. Flip the lag condition 300 times: one alert, `occurrences` 300. Boot the chain with its default wall-clock genesis far from `AS_OF`: status `chain: unhealthy` with `CHAIN_CLOCK_SKEW`, one `chain.clock_skew` alert, `sendGatewayCall` refused. A watcher that uses `Date.now()`, or one that measures lag in blocks on a chain that only mines on demand, fails at least one of these.
- **Manifest and chain disagree.** Edit `deployments/31337.json` so `agentGatewayV2.codeHash` is wrong, then start the API: `manifest:check` must fail, status must show `chain: unhealthy` with the drifting entry named, `sendGatewayCall` must refuse with `CHAIN_MANIFEST_DRIFT`, the indexer must stop, and `chain.manifest_drift` must be raised once. Then redeploy a token at the same salt with different bytecode and confirm `writeManifest` refuses to overwrite the address. A node that boots green on a wrong manifest fails.
- **Deploy without the quorum.** Put a row in `deploy_requested` whose APR is still `pending` in A14, and one whose APR is approved but whose deployment is sent directly from the deployer account at the counterfactual salt: neither may reach `deployed` (409 `DEPLOY_NOT_BOUND` on any forcing attempt, and the indexer leaves the row in `deploy_requested`, flagging the deployer-sent contracts `unbound`); only the multisig execution joined to its `Proposed` with the approved id moves the row. A sandbox deploy must leave the production counterfactual addresses without code.
- **Escapes.** `POST /sandbox-deploy` with `CHAIN_ID=84532` configured must return 403 `SANDBOX_DEPLOY_LOCAL_ONLY` before any RPC call; `increaseTime` on 84532 must return `NOT_A_HARDHAT_NODE`; a hand-built signed transaction passed to `sendGatewayCall` must be refused with `CHAIN_UNBOUND_BUNDLE`; a `chain_id` of 8453 in any manifest file must fail `manifest:check`; a config switch to chain id 8453 must be refused with `CHAIN_NOT_ALLOWED` before an approval request exists, and a switch to an allowed chain must not apply before SECO's approval, then apply, re-run `manifest:check` and resume from that chain's own cursor; the RPC URL with credentials must never appear in a log, an error or the status endpoint. Any one of these succeeding fails the node.
- **Who can see what.** As VIS and as an investor's D04 token, `GET /v1/chain/proof/{vehicleId}` returns addresses, code hashes, supply and the last clean run time and no holder; `GET /v1/chain/snapshot` is refused; `GET /v1/chain/holdings` returns only the caller's own wallets. A TOKO token limited to KST01 can design and request a deploy for KST01 and is refused for HAW01 with A12's G22 reason code.
- **Design fidelity of the read models.** With the standard seed after the local replay, `GET /v1/chain/tokens` must return eight rows (MRN01, BAY01, HAW01, GYM01 `active`; KST01, ANN01, UNL01 `configured` and paused; MPA01 `designed` with no code at its addresses), supplies 10,000 / 10,000 / 10,000 / 10,000 / 0 / 0 / 0 for the seven deployed trusts as the `adRecon` grid shows, MRN01 unpaused after its seeded pause and unpause, and the three `adToken` "Recent" rows joined by approval id (APR-2270, APR-2268, APR-2261) to real confirmed `chain_tx` rows whose `shortHash` has the `0x`+2 hex+`…`+2 hex form; the Gympie Road snapshot must show 10,000 against A18's 9,998 so the break is the register's, not the chain's; no trust shows an unbound change or an unknown holder. A seed that fixes the design's "7 of 8" by dropping the eighth trust, shows applications in escrow as token supply, or inserts chain rows that a reindex does not reproduce, fails.
