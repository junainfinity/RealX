# A37 - Orders, escrow, allocation and refunds (SM-05)

**The primary-order machine of the marketplace. Every subscription in an open offer runs the SM-05 lifecycle: a quote, then eligibility (A19's order gate set for the offering's regime, plus G22 when an agent places it), then the offering's escrow account. A deterministic allocation workbench (first-come or pro-rata, scaled to the hard cap, holder-capped and never silently accepted) then produces one locked, hashed Allocation file that the finalise-and-mint pipeline must mint against. The node also covers refunds under 4E within five business days, expiry of unfunded orders, cancellation while the listing permits, cancellation of an agent's open orders when its token is revoked, and escrow Δ 0 before any allocation. An order is "settled" only when the trustee's register entry and the reconciled token delivery both exist. This node publishes one frozen `index.ts` contract that A38, A39, A71 and A60 use; it owns the only allocation-lock request, the only refund-batch table and the only order timeline.**

**Oracle rule:** The node QA writes hidden oracle tests from this spec to `<workspace>\gauntlet\hidden\A37\` before the build starts ([[App Gauntlet]] §2). The builder never reads that folder. The cases are published into the repo only after the gate passes. The oracle covers the money and authority arithmetic of this node:
- For any set of funded orders and any offering parameters, the sum of allocated units in the locked file equals the file's total and never exceeds the hard cap.
- Every line's allocated cents plus its fee plus its refund equals what that order funded, to the cent.
- On a failed raise the sum of refunds equals the sum of money held in escrow for the offering, and no order ends anywhere but `refunded`.
- The fee on every quote and order is `mulBp(subtotal, fee_bps, half_up)`. Vectors: 10 × A$238.40 = A$2,384.00, fee A$11.92, total A$2,395.92; 100 × A$250.00 = A$25,000.00, fee A$125.00, total A$25,125.00.
- G07 counts the investor's existing register holdings, associates and the investor's other orders in the same file.
- An agent order above its per-action cap with a valid mandate signature returns `428 CONFIRMATION_REQUIRED` and creates no order row, reservation or journal until the person confirms with a passkey. An agent order that breaks a hard limit (daily or monthly cap exhausted, scope, vehicle, time window, IP, hold or kill switch) is refused with A12's `403 G22_*` or `423` code, again with zero rows. The daily and monthly caps are checked again when a confirmed order is replayed, and a replay that fails them is `cancelled` with no reservation or journal.
- G11 at placement: an order is accepted only while `requested_units ≤ acceptance_ceiling_units − Σ units of open orders` (vectors at the ceiling and at the ceiling plus one unit, for both allocation rules).
- No transition outside the SM-05 table can be reached by any sequence of API calls, events and job runs.

Money in this node is sandbox money and units are sandbox units. The ledger is A16's, the bank facts come from A17's sandbox, the register is A18's sandbox registrar and the local chain is Hardhat. Nothing here touches a real trust account, a real registry or mainnet; those sit behind HG-CAPITAL, HG-VENDOR and HG-PROD. This plan is not legal advice.

## Build brief

This node is API-only: module `orders` in the Fastify monolith plus its worker jobs. It has no screens of its own. INV-01 to INV-03 are built by A57, SPN-07's applications table by A36's screen node (A63), and ADM-08/ADM-12 by A71, all on the read contracts below. The module:
- posts business facts into A16's ledger (`order.fund`, `order.refund`, the two catalogue rows whose caller is A37);
- reacts to A17's payment events;
- asks A19 for every gate verdict;
- asks A18 whether a register entry exists;
- hands A38 the locked Allocation file.

It never mints. It never releases escrow: `escrow.release` is A16's catalogue row whose caller is A39. A39 drafts that approval, registers its effector and posts its journal, and this node only supplies A39 the release basis through `getEscrowReleaseBasis` (loop A39.1 aligns A39's own note, which still says otherwise). It never changes the offering's own state: SM-04 is A36's, and A38 drives close, finalise and revert. Every rule below lives in the service layer and is refused there, never only in a screen or a caller.

**SM-05 lifecycle (registered with A03's state-machine runner; every transition below is in the table and nothing else is)**

- States exactly as the product map: `submitted`, `cancelled`, `eligibility_check`, `rejected`, `reflection_period`, `awaiting_funds`, `revoked`, `funded`, `expired`, `allocated`, `refund_pending`, `settled`, `refunded`.
- Every transition runs through A03's runner **with its guards on**. This node never bypasses a guard. Where A03's frozen guard does not allow a transition this note needs, the change is listed in loop A03.1 below and the transition stays refused until A03's owner lands it.
- `[*] → submitted` on `POST /v1/offerings/{id}/orders`. `submitted → eligibility_check` in the same transaction for a person or a signed agent order. `submitted` is committed on its own only on the agent confirmation replay (below).
- `eligibility_check → rejected` (A03 guard `eligibility_failed`) when any gate in the placement set fails. The order row stays as a record with the gate and reason codes; nothing is reserved.
- `eligibility_check → reflection_period` (guard `retail_regime_p2`) for **every** retail order in P2 or later, as A03 requires, so a retail P2 order can never skip it. `reflection_ends_at = placed_at + cooling_off_days` on A13's calendar. With `cooling_off_days = 0` (the default) `reflection_ends_at` is the placement instant, and the order passes straight on to `reflection_period → awaiting_funds` in the same transaction (two history rows, two events). `eligibility_check → awaiting_funds` (guard `not_retail_regime_p2`) otherwise. **Wholesale orders never enter `reflection_period`**: the guard refuses it for `s708_wholesale` whatever the parameters, and the oracle checks it.
- `reflection_period → revoked` (guard `reflection_open`) on the investor's revoke. `reflection_period → awaiting_funds` (guard `reflection_ended`) only when the timer ends. An early close does **not** cut a cooling-off period short.
  - With `fund_at = after_reflection` (default) no money moves during reflection. An order whose reflection ends after `funding_deadline_at` enters `awaiting_funds` and goes to `expired` in the same transaction, before the funding step can run. It is never funded after close.
  - With `fund_at = confirm` (a counsel-dependent variant kept behind the parameter) the `order.fund` journal posts at confirm while the order is in `reflection_period`. When the timer ends the paid order goes `reflection_period → awaiting_funds → funded` in one transaction with no second journal (`funded_journal_id` is already set). A paid order is never expired. `revoked → refund_pending` (guard `already_paid`) returns it in full.
  - `requestAllocationLock` and the lock effector refuse with `ORD_REFLECTION_OPEN` (naming the count and the latest `reflection_ends_at`) while any order of the offering is still in `reflection_period`. Allocation waits for every cooling-off period to end.
  - Both paths are tested. P1 never enters reflection.
- `awaiting_funds → funded` (guard `payment_matched`) when the investor's `investor_cash` available balance covers `total_cents` and the offering is still `accepting_orders`. Reserve (`purpose = order`) and `consume` through the `order.fund` journal in one transaction, so the reservation never outlives the transaction and A16's sweep never sees it. This happens at placement when the wallet covers the order (the design's "Paid from funds available"), otherwise on each `payment.credited` for that investor (oldest awaiting order first) and on the worker's `orders.funding_sweep`.
- `awaiting_funds → expired` (guard `funds_not_received`) at `funding_deadline_at`, the earlier of the offering's `closes_at` and `placed_at + orders.funding_window_hours` (default 72). The job `orders.expiry_sweep` does this every 5 minutes, and `expireUnfunded` does it at close. The investor is told what was missing.
- `awaiting_funds → cancelled` on the investor's cancel before funding, or on the revocation of the agent token or mandate that placed it (loop A03.1 adds this transition; A03 drew only `submitted → cancelled`, because `submitted` lasts one transaction here). `submitted → cancelled` stays in the table for a replayed placement whose token or mandate was revoked, which the person cancelled, or which failed A12's execution-time cap, hold or kill-switch check (below), before its eligibility step ran.
- `funded → allocated` (guards `allocation_locked` and `units_allocated`) when the Allocation file locks with `allocated_units > 0` for the order.
- `funded → refund_pending` when:
  - the file gives the order zero units (excluded or nothing left): A03 guard `offer_failed_or_zero_allocation`;
  - the offering fails (`soft_cap_missed`, `revert`): the same guard;
  - a funded order is cancelled while `cancellable_until_close` is true and the offering is still accepting orders: loop A03.1;
  - a material change is not re-confirmed by `reconfirm_due_at` (5 business days, from A36's `offering.material_change` event): loop A03.1;
  - a returned deposit (`deposit_returned`): loop A03.1.
- `allocated → settled` (guards `register_entry_exists` and `token_delivery_exists`) only through `settle()` (below).
- `allocated → refund_pending` only through `excludeAllocationLine` (the holder became ineligible between allocation and mint), which supersedes the file and refunds the order in full. A03's guard for this edge is `partial_allocation` (`0 < allocated < ordered`), which never holds for a full exclusion; loop A03.1 replaces it with `line_excluded` (the order's line in the new current version has 0 units). This also answers A03's escalation (iv).
- `refund_pending → refunded` when the `order.refund` journal for the order's line has posted under the batch's own `orders.refund.batch` approval (the `4E` row FINA → CFO, or its `AUTO` row). The journal and the transition commit together while the approval is still executing, so A03's `linked_approval_closed` guard (row 12) cannot hold at that moment; loop A03.1 replaces it with `refund_journal_posted` (a posted `order.refund` journal for the line under an approved `orders.refund.batch` request of either row).
- Partial allocations (scaled back or holder-capped) keep `state = allocated` for the units path. They run the money path on `refund_state: none → pending → refunded` with a refund line for the difference, so a scaled-back investor still reaches `settled` for the units they got. This is the reading of SM-05's "partial allocation" arrow that keeps settlement reachable (A03's escalation iv). It is recorded in the evidence manifest as the one interpretation this node makes of the diagram.
- Every transition writes one `order_state_history` row, one hash-chained audit event through A10 (with `on_behalf_of_id` whenever an agent or a service account acted) and exactly one outbox event (A09):

  | Transition | Outbox event |
  |---|---|
  | `[*] → submitted` | `orders.submitted` |
  | `submitted → eligibility_check` | `orders.placed` (the one placement event consumers use; carries `channel` and `token_id`) |
  | `submitted → cancelled`, `awaiting_funds → cancelled` | `orders.cancelled` |
  | `eligibility_check → rejected` | `orders.rejected` |
  | `eligibility_check → reflection_period` | `orders.reflection_period` |
  | `eligibility_check → awaiting_funds`, `reflection_period → awaiting_funds` | `orders.awaiting_funds` |
  | `reflection_period → revoked` | `orders.revoked` |
  | `awaiting_funds → funded` | `orders.funded` |
  | `awaiting_funds → expired` | `orders.expired` |
  | `funded → allocated` | `orders.allocated` |
  | `funded → refund_pending`, `allocated → refund_pending`, `revoked → refund_pending` | `orders.refund_pending` |
  | `allocated → settled` | `orders.settled` |
  | `refund_pending → refunded` | `orders.refunded` |

  A transition not in the table, or one whose guard fails, is refused with `ORD_INVALID_TRANSITION` naming the current state (and the failed guard).

**Gate sets (A19 decides the set; this node never picks gates itself)**

- Quote, placement and allocation each call A19's `evaluateAction` (or `simulate` with `dry_run = true` for the quote) with the offering's regime and phase: `kind = order` for the quote and the placement, `kind = order_allocation` at allocation. The gate lists, their order and the valid `not_applicable` results are exactly A19's table 3, rows `order` and `order_allocation` (with G22 in front when the principal is an agent). This note does not copy the lists; its contracts and tests import A19's generated `gate-sets.ts`, so they can never drift from A19's oracle.
- Every row A19 returns is carried in the quote's `gates` array, `not_applicable` rows included and marked. Which rows a screen draws is A57's decision; the design shows five of them (below).
- G05 is `not_applicable` for a wholesale order and G04 for a retail order, as table 3 lists. If A19's evaluators return anything else for the other regime's gate, that is a loop on A19, not a local filter here.
- G11's verdict is A19's evaluator over A36's `offer_state` fact; the rule this node relies on is stated under Placement.

**Placement: quote, then order (the buy stepper's two calls)**

- `POST /v1/offerings/{id}/orders/quote` (A03 action `INV.order.quote`; investors and their agents) with `{ requested_units }` returns `{ quote_id, expires_at, lines: { units, unit_price_cents, subtotal_cents, fee_bps, fee_cents, total_cents, share_bps }, formatted (en-AU), wallet: { available_cents, shortfall_cents }, gates: [ { gate, result, title, detail, fix_it, max_allowed_units? } ], documents_required, statement_hash, raise: { raised_units, soft_cap_units, hard_cap_units, acceptance_ceiling_units, remaining_acceptable_units, closes_at, may_be_scaled_back }, min_ticket_units, max_ticket_units }`.
  - The gate rows are A19's dry run for table 3's `order` row. The G07 row carries the post-order share and the cap in the design's exact words ("After this order you’d hold 0.10% (cap 5%)"). The G11 row says "Within hard cap · funds held until soft cap", or gives the scale-back warning when the order would sit above the hard cap but within the acceptance ceiling.
  - `documents_required` and `statement_hash` come from A35's `getDisclosureSet(offering)`; whether each document has been opened comes from A35's `GET /v1/offerings/{id}/disclosure-set` (`all_opened`), never from the client.
  - A quote is refused only for an offering that is not accepting orders (`ORD_OFFERING_NOT_LIVE`). Every other failure is returned as a failed gate row, so the screen can disable the button and say how to fix it.
  - Units below `min_ticket_units` or above `max_ticket_units` return G11 failed with the bounds. Units above `remaining_acceptable_units` return G11 failed naming the remainder. Units above `max_allowed_units` return G07 failed naming the maximum (the design's "cap breach → maximum suggested").
- `POST /v1/offerings/{id}/orders` (A03 action `INV.order.place`; `Idempotency-Key` required) with `{ quote_id?, requested_units, document_version_ids: [ … ], statement_hash, confirmation: { kind: 'passkey_assertion', assertion_id } | { kind: 'mandate_signature', signature } }`. The zod schema is strict: any `opened_at`, `acknowledged_at` or `sha256` field is refused with `422 ACK_FIELD_NOT_ACCEPTED` (A35's code) before any row is written, so a client can never assert that it opened a document. In one transaction:
  1. Re-price from the offering. A quote binds nothing but the pack version and the 15-minute window; a stale quote is `ORD_QUOTE_EXPIRED`.
  2. Verify the confirmation. For a person: A11's `requireFreshAssertion({ purpose: 'order.confirm', maxAgeMinutes: 5 })` over the canonical order hash. For an agent: A12's mandate signing key over the same hash including the idempotency key.
  3. Write the order (`[*] → submitted → eligibility_check`).
  4. Call A35's `recordAcknowledgements(tx, { holderId, offeringId, orderRef, documentVersionIds, statementHash, actor })` with `actor` taken from A11's resolved principal (the person, or `{ kind: token, tokenId, onBehalfOfId }`). A35 derives every `opened_at` from its own server-side `document_open` rows. For a token actor it runs A35's delegated path (the CQ-02 parameter for the regime, an active `standing_consent` row naming every required type and the vehicle, version dating, the **first-purchase exclusion** through this node's `prior_allotment` fact, and the token's own opens).
  5. Run table 3's `order` set through A19. G12 reads A35's `getAcknowledgementFacts(orderRef)`; G22 has already run in A12's middleware for a token.
  6. Reserve and fund if the wallet covers the total.
- G12 for a person: if `recordAcknowledgements` fails (a missing, unopened or superseded version, or a stale statement hash), A19's G12 fails with A35's reason codes (for example `DISCLOSURE_VERSION_STALE`) and the order is `rejected`, never `awaiting_funds`.
- G12 for an agent: if `recordAcknowledgements` returns `428 ACK_PERSON_REQUIRED` with a `sub_reason` (`counsel_parameter`, `consent_missing`, `consent_scope`, `consent_predates_version`, `first_purchase`, `agent_not_opened`), the whole transaction rolls back, A12 opens a confirmation for the person, and the agent gets `428` with that code, the `sub_reason`, `documents_required` and the `confirmation_id`. No order row, reservation or journal exists. An agent's order is held for the person, never `rejected`, for disclosure.
- G11 at placement (A19's evaluator over A36's `offer_state`): the offering is `accepting_orders`; `min_ticket_units ≤ units ≤ max_ticket_units`; and `units ≤ acceptance_ceiling_units − Σ units of open orders` (A36's `remaining_acceptable_units`, which counts funded and pending orders). For `first_come` the ceiling is the hard cap. For `pro_rata` the ceiling is `hard_cap_units + floor(hard_cap_units × oversubscription_cap_bps / 10,000)`, and an order that lands above the hard cap but within the ceiling is accepted with the flag `may_be_scaled_back`, and the response says so. One unit past the ceiling is G11 failed. A19's G11 text still tests against the hard cap alone; loop A19.1 aligns it with A36's ceiling.
- The response is the full order with its timeline: `201` when created, `200` with the original order when the idempotency key is replayed, `409 ORD_DUPLICATE_KEY_CONFLICT` when the same key carries a different payload.
- Two open orders from one investor on one offering are allowed (a top-up). G07 at placement counts the earlier order's units through the `open_order_units` fact, including an earlier order still in `awaiting_funds`, and allocation treats them as one holder.
- When Σ funded units for the offering first reaches `hard_cap_units`, this node emits `offer.hard_cap_reached` `{ offering_id, funded_units, funded_subtotal_cents, hard_cap_units, at }` once per offering (idempotent on the offering id). A38's F0 close trigger consumes it under that exact name.

**Agent placement (D04, G22) and the confirm step — one rule, used everywhere in this note**

- A12's `agentAuth` plugin runs before this handler. It checks the token holds `INV.order.place`, the mandate's `allowed_vehicle_ids`, `daily_cap_cents`, `monthly_cap_cents`, unit caps, time window, IP list, holds and kill-switch tiers, and returns `G22_AGENT_NEVER_CHECKER` for anything that is an approval. A **hard-limit** failure ends the request in the middleware with A12's code (`403 G22_LIMIT_EXCEEDED` with `cap: daily | monthly` and the remaining amount, `403 G22_SCOPE_MISSING`, `403 G22_VEHICLE_…`, `403 G22_OUTSIDE_TIME_WINDOW`, `403 G22_IP_NOT_ALLOWED`, `423 AGENT_HELD`, `423 AGENTS_PAUSED`). The result is one `gate_evaluation` row and no order row, no quote use, no reservation and no journal. That is the oracle's "never reserves funds". When G22 passes, the A12 daily counter is reserved in the same transaction and released if a later gate (G07, G11, G12) rejects the order.
- **Per-action cap.** The action amount is `total_cents` (subtotal plus fee), as A12 measures it. An order above `per_action_cap_cents` (or above the per-action unit cap) with a valid mandate signature is not refused. It returns `428 CONFIRMATION_REQUIRED` with a `confirmation_id` and creates no order row, reservation or journal, exactly as A12 and product-map J22 ("above the amount limit it waits for the person's passkey") say. The same `428` is returned for any order when no signing key is registered.
- A valid signature within the caps satisfies the "confirm with passkey" step and nothing else. It is verified against the mandate version: the canonical order payload, including the idempotency key, signed with the registered Ed25519 key (A12 §4).
- **Replay after the person confirms.** When the person confirms with a passkey (A60 renders it; A12 emits `agent.confirmation.resolved`), this node's consumer writes the order in `submitted` from A12's stored canonical payload, with `confirmation_kind = passkey_assertion` and the confirmation id as `confirmation_ref`, and enqueues `orders.placement_replay`. The job, in one transaction:
  1. re-checks that the token and mandate are still live, else `submitted → cancelled` (`agent_token_revoked` or `agent_mandate_revoked`);
  2. re-checks holds and every kill-switch tier, else `submitted → cancelled` (`agent_paused`), and the person is told to place the order themselves if they still want it;
  3. applies A12's execution-time rule: the confirmed order counts toward the day's and the month's totals, and the daily and monthly caps are checked again under A12's counter lock. If either is now exhausted (for example another order used the day's cap between the `428` and the passkey), the order goes `submitted → cancelled` with `cancel_reason = agent_limit_exceeded` and A12's `G22_LIMIT_EXCEEDED` detail, with no reservation or journal;
  4. otherwise runs `submitted → eligibility_check → …` under the original idempotency key, with the person as the acknowledging actor (the person opens and acknowledges the documents in A60's confirmation step through A35, and `recordAcknowledgements` binds those rows to the order).
  An unresolved confirmation expires in A12 after 24 hours and leaves no order here.
- **Disclosure under standing consent.** There is one rule and it is A35's. An agent's acknowledgement is accepted only through A35's delegated path inside `recordAcknowledgements`: the CQ-02 parameter (A00's key; default wholesale allowed under consent, retail person required), an active passkey-created `standing_consent` row, versions published before the consent (unless its `new_version_policy` is `auto`), **never the person's first purchase in that trust**, and the token's own opens. This node keeps no consent switch, no version list and no acknowledgement table. A superseded IM therefore gives the agent `428 ACK_PERSON_REQUIRED` (`consent_predates_version`) with no row, while a person's own order carrying the superseded version is `rejected` as above.
- **Agent re-confirmation** after a material change: a mandate signature clears `reconfirm_due_at` only when `recordAcknowledgements` passes for the token on the new versions. Otherwise the call returns `428 ACK_PERSON_REQUIRED` and the person must confirm with a passkey.
- Every agent-placed order carries the flag `agent_placed`, `token_id` and `on_behalf_of_id`, and the audit line "agent `<token prefix>` on behalf of `<person>`". It appears in the person's activity (A12's `/me/activity`) and in the ADM-12 blotter with the agent marker A71 draws. Sensitive-action notices for an agent order above the person's notice threshold are A101's, fed by the `orders.placed` event's `channel` and `token_id`.

**Token and mandate revocation (J22 step 4, "Token stops at once; open agent orders cancelled")**

- This node registers A12's `registerRevocationHook({ onTokenRevoked, onMandateRevoked })`. The hook runs inside A12's revoking transaction, so a revoke and its order effects commit together or not at all. This node also consumes `agent.token.revoked` and `agent.mandate.revoked` as an idempotent backstop that finds nothing left to do after the hook.
- Effect on orders placed under that token (or mandate):
  - `submitted` (a queued replay) and `awaiting_funds` become `cancelled` with `cancel_reason = agent_token_revoked` (or `agent_mandate_revoked`). Nothing was reserved, so nothing moves.
  - `reflection_period` becomes `revoked`. In the `fund_at = confirm` variant it then goes to `refund_pending` with reason `revoked_in_reflection`.
  - `funded` and later states stay as the person's orders. The person's money is in escrow under their own confirmation, and the listing's cancel rule still applies. The person is notified through A43 ("Your agent's token was revoked. These orders stay yours: …").
- Holds and kill switches (every tier, A12 and A101) stop the agent's next call with `423` and do **not** cancel open orders. They are reversible pauses. The one exception is a queued `submitted` replay whose job runs while the pause is on: it has not been placed yet, so it is cancelled with `agent_paused` (above) rather than placed by a paused agent. Cancelling every agent order on a platform-wide switch would be a mass money action that the product map does not ask for. The person or staff can still cancel under the normal rules.
- `GET /v1/me/orders?token_id=&open=true` (A03 action `INV.order.read`, self only) returns the open orders placed by that token, each with `on_revoke: 'cancel' | 'revoke' | 'stays_yours'`. A60's revoke card reads it before the click, so the browser never loops over cancel calls.

**Funding, expiry, reversal and cancellation**

- The `order.fund` journal (A16 catalogue) has two legs: `investor_cash` → `offer_escrow` for the full `total_cents` (subtotal plus fee). The escrow leg carries `line_ref` = the order id and `beneficiary_id` = the investor. The fee stays inside the order's escrow sub-balance until A39's `escrow.release` moves it to `fee_payable_realx`. `external_ref` = the order id, so a second attempt is a replay, never a double debit. On success:
  - the order is `funded`;
  - `funded_at` is the transaction time (A09's clock);
  - `funded_journal_id` and `escrow_held_cents = total_cents` are stored;
  - the `order` confirmation record is issued;
  - `orders.funded` is emitted.
  A frozen `investor_cash` account (A16 `LDG_ACCOUNT_FROZEN`) leaves the order `awaiting_funds`, and the investor sees only "under review" (no tipping-off).
- `payment.reversal_pending` from A17 (a returned credit whose money already sits in escrow): the order moves `funded → refund_pending` with reason `deposit_returned`. Its escrow money is unwound by an `order.refund` journal under a `4E` batch, and A17 is told to complete the reversal. The investor is never left holding escrow against a returned deposit.
- Cancellation `POST /v1/orders/{id}/cancel` (A03 action `INV.order.cancel`; the person or their agent, since money only flows back to the person):
  - allowed from `submitted` (a queued replay), `awaiting_funds` and `reflection_period` (as `revoked`) at any time;
  - allowed from `funded` only while the offering is accepting orders and `cancellable_until_close` is true, which makes a `refund_pending` with reason `investor_cancelled`;
  - refused with `ORD_NOT_CANCELLABLE` (naming the state or the listing rule) from `allocated`, `settled`, `refund_pending`, `refunded`, `expired` and `rejected`, and from `funded` after close or when the listing forbids it.
- Material change (A36's `offering.material_change` with a 5-business-day window): every open order gets `reconfirm_due_at`. `POST /v1/orders/{id}/reconfirm` (A03 action `INV.order.reconfirm`) with a fresh confirmation (a person's passkey, or a mandate signature under the standing-consent rule above) clears it and records new acknowledgements. At the deadline the job `orders.expiry_sweep` moves unconfirmed funded orders to `refund_pending` (`material_change_not_reconfirmed`) and unconfirmed unfunded ones to `expired`.

**Escrow position and the Δ 0 rule**

- `GET /v1/offerings/{id}/escrow` returns different fields by principal:
  - Sponsor users of the offering's tenant and their agents (A03 action `SPN.offerEscrow.read`) get only the per-offering figures: `{ escrow_orders_cents, escrow_orders_count, funded_units, offer_escrow_ledger_cents, delta_cents, platform_escrow_clear: boolean, last_clean_recon_at, ok }`.
  - Staff with `M16.escrow.read` or `M05.escrow.read` also get `escrow_account_level: { bank_mirror_cents, sum_of_offer_escrow_accounts_cents, delta_cents }`.
  - The account-level figures describe the shared escrow trust account, which holds every sponsor's client money, so they are never returned to a sponsor principal. `platform_escrow_clear` is a boolean with no figures.
- Per offering the rule is: Σ `escrow_held_cents` over every order with money in escrow equals the `offer_escrow` account balance from A16, tolerance zero. Orders with money in escrow are `funded`, `allocated` before release, `refund_pending` and partial `refund_state = pending` before their refund posts, and, in the `fund_at = confirm` variant, `reflection_period` and `revoked` orders whose `order.fund` has posted. The fee is part of `escrow_held_cents` because A16 keeps it in the sub-balance until release.
- At account level, the bank mirror for the escrow trust account (A17's ••2202 as posted by A17 into A16) must equal Σ of every offering's `offer_escrow` balance.
- `last_clean_recon_at` is the run id and time A20's `assertClear(vehicle_id, 'allocation')` last returned for the offering's vehicle (A20 is an ancestor, so this is wired from the first build, never faked as clean).
- `requestAllocationLock`, and again the lock effector at execution, refuse with `ORD_ESCROW_DELTA_NONZERO` (carrying both deltas; a sponsor caller sees only the per-offering delta) unless both deltas are zero. Both then call A20's `assertClear(vehicle_id, 'allocation')` directly; if it throws `ReconNotClear` (for example an open cash break on the escrow account, even with both deltas at zero), they refuse with `ORD_RECON_NOT_CLEAR` carrying A20's break ids, write no allocation row and raise no approval request. This is the product map's "client money must show Δ 0 before allocation" and "bank Δ must be 0 before any allocation approval", enforced in the service, not on ADM-08.

**Allocation workbench (deterministic, pure, replayable)**

- `previewAllocation` (`GET /v1/admin/offerings/{id}/allocation/preview`, A03 action `M05.allocation.preview`, CAPM and FINA; sponsor users may read a masked preview under `SPN.offerAllocation.read`) runs the algorithm over the funded orders and returns the draft file without writing it.
- `requestAllocationLock` (no public route of its own; reached through A38's `POST /v1/settlement/offerings/{id}/finalise`, CAPM maker) runs the algorithm again inside a transaction that locks the offering's orders. It writes the `allocation` and `allocation_line` rows as `draft` and raises A14's `ApprovalRequest` with action code `orders.allocation.lock`, policy `4E` (CAPM → CFO, the product map's screen-level ADM-12 "Allocate" row, which D07 lacks and loop A03.2 seeds), `object_ref` = `allocation:<id>` and `payload_sha256` = `file_sha256`. It is the only place on the platform that drafts this request.
  - Preconditions: offering `closed` (A36's SM-04, soft cap reached), else `ORD_OFFERING_NOT_CLOSED`; no locked file already, else `ORD_ALLOCATION_LOCKED`; no pending lock request with different inputs, else `ORD_ALLOCATION_LOCK_PENDING`; no order of the offering in `reflection_period`, else `ORD_REFLECTION_OPEN`; escrow Δ 0 and A20 clear (above); no offering-level `hold` in the allocation evaluation (step 1), else `ORD_ALLOCATION_HELD`.
- On the approval's `approved` event, this node's effector `lockAllocation` re-checks Δ 0, A20's `assertClear(vehicle_id, 'allocation')`, no open reflection period and that `payload_sha256` equals the draft's `file_sha256` (`ORD_FILE_HASH_MISMATCH` otherwise). Then:
  - the file becomes `locked`;
  - every line's order moves `funded → allocated` or `funded → refund_pending`;
  - the lock-time refunds are drafted as one `refund_batch` with reason `scale_back` (each line's `reason_code` says scaled back, capped, excluded or zero units; an empty set drafts nothing);
  - `orders.allocation.locked` is emitted for A38.
- Inputs are only: the funded orders sorted by `funded_at` then `id`, the offering parameters, the register version A18 reports as current (existing holdings per investor and associates), freeze status from `InvestorFreezeSource`, and the verdicts of A19's `order_allocation` set. The algorithm is a pure function in `packages/domain/src/orders/allocate.ts` (owned by this node) over plain objects. The hidden oracle can drive it with synthetic inputs, and `inputs_hash` plus `algorithm_version` make any file reproducible.
- **Step 1, eligibility at allocation.** A19 evaluates table 3's `order_allocation` set (G01 G02 G04 G05 G07 G10 G11 G14 G21, as A19 lists it) for every funded order, as a new evaluation set referencing the placement set.
  - An investor-level `fail` or `hold` (for example a G02 sanctions hit, a G14 AML hold, an expired G01 identity, a lapsed G04 certificate) or a frozen investor excludes that order (`allocated_units = 0`, `exclusion_gate`, flag `excluded_at_allocation`), and it is refunded in full. One investor's hold never delays everyone else's allocation. Only the gate code is stored; no AML reason reaches the investor or the sponsor (A42's tipping-off rule).
  - An offering-level `hold` or `fail` that would hit every order the same way (a G10 halt on the vehicle, a G21 licence-perimeter failure, a G11 offer-state failure) does **not** exclude and refund everyone. It refuses the lock with `ORD_ALLOCATION_HELD` naming the gate, writes nothing, and the lock can be requested again once A19 passes. A permanent failure of the offering is A38's revert path, not an allocation.
- **Step 2, holder cap.** Each investor's allowance is `max_allowed_units` from G07 (existing register units plus associates counted, and all of the investor's orders in this file counted together).
- **Step 3, the rule.**
  - `first_come` fills orders in `funded_at` order in full until fewer units remain than the next order asks. That marginal order gets the remainder (flag `scaled_back_first_come`) and every later order gets zero.
  - `pro_rata` gives every order `floor(requested × hard_cap_units ÷ Σ requested)` when Σ requested exceeds the hard cap. It distributes the leftover whole units one each by largest fractional remainder, then earliest `funded_at`, then id (flag `scaled_back_pro_rata`). It fills every order in full when there is no over-subscription.
- **Step 4, capping.** Any line above its investor's allowance is cut to the allowance (flag `capped_at_holder_cap`). The freed units return to the pool, and steps 3-4 repeat over the uncapped lines until no line changes (bounded by the number of orders). An order capped to zero is a full refund. Units are integers throughout; nothing is ever rounded to a fraction of a unit.
- Money per line: `allocated_cents = allocated_units × unit_price_cents`; `fee_cents = mulBp(allocated_cents, fee_bps, half_up)`; `refund_cents = total_cents_funded − allocated_cents − fee_cents`. This is never negative, because the fee is monotone in the amount. The refund comes out of the order's own `offer_escrow` sub-balance, fee share included, as A16's `order.refund` row defines. Nothing is taken from `fee_payable_realx`, which receives fees only at A39's release. The one case this rule does not cover is an exclusion after escrow release (A38's point 3 and after issue): the line's fee has already moved to `fee_payable_realx`, and A16's `order.refund` row cannot reach it. This node does not invent a journal for it; loop A16.1 asks A16 for a catalogue row that returns a released line's fee share to that order's `offer_escrow` sub-balance under the exclusion approval, after which `executeRefundBatch` refunds the whole restored sub-balance as usual.
- File invariants, checked before the row is written and again by the oracle:
  - Σ `allocated_units` ≤ `hard_cap_units`;
  - Σ `allocated_units` ≤ Σ `requested_units`;
  - per line, `allocated_units ≤ requested_units` and ≤ the investor's allowance;
  - Σ (`allocated_cents + fee_cents + refund_cents`) = Σ funded totals, to the cent;
  - every investor's units across the file plus existing holdings ≤ the holder cap.
  A file that fails any invariant is refused with `ORD_ALLOCATION_INVARIANT` and nothing is written. "Capped, never silently accepted" means every capped or scaled line carries its flag and its refund, and the investor's order status says "Allocated 200 of 300 tokens · A$23,959.20 refunded".
- `excludeAllocationLine(allocation_id, order_id, gate, ctx, { evaluation_id, approval_id? })` (the approval rule is in the interface table):
  - writes version `n+1` as `draft` with that line at zero and a full refund, and marks version `n` `superseded` at once, so nothing can mint against it;
  - moves the order `allocated → refund_pending` (`excluded_at_mint`) and drafts an `excluded_at_mint` refund batch;
  - raises a new `orders.allocation.lock` request for version `n+1` through `requestAllocationLock` (the new hash needs a new decision) and emits `orders.allocation.superseded` with the new `file_sha256`.
  A38 must re-run its `allocation.mint` approval against the new locked hash. Freed units are not redistributed automatically. This is a product question recorded for A36; the file's `unallocated_units` shows them.
- `GET …/allocation/file` returns the locked file, its `file_sha256`, `inputs_hash`, `algorithm_version` and the approval id. `GET …/allocation/versions` lists every version. A38's mint references `allocation_id` and `file_sha256`, and A20's R7 (Σ minted per offering = the locked file) reads the same rows.

**Refunds (4E, five business days, one table, one clock)**

- `computeRefundBatch(offering_id, reason, ctx, { order_ids? })` builds the lines from each order's `escrow_held_cents`:
  - for `soft_cap_missed` and `revert`, every order with money in escrow is refunded its whole remaining sub-balance (for an unrefunded order, its full `total_cents`, subtotal and fee);
  - for `scale_back` and `excluded_at_mint`, the file's `refund_cents` per line (the whole sub-balance for an excluded line);
  - for `investor_cancelled`, `material_change_not_reconfirmed`, `deposit_returned` and `revoked_in_reflection`, the single order's remaining sub-balance.
  An order already refunded, or already in another open batch, is never added twice (`UNIQUE (order_id)` over lines in non-terminal batches). `file_sha256` is over the canonical lines.
- Approval. Every batch, whatever its reason, gets its **own** A14 request: action code `orders.refund.batch`, `object_ref = refund_batch:<id>`, `payload_sha256 = file_sha256`, drafted only by `submitRefundBatch`. That is the object A16's `order.refund` row binds to, so every refund journal passes A16's approval binding.
  - By default every reason resolves to the `4E` row (FINA → CFO, the product map's row 12 "Issue refund").
  - Reasons `soft_cap_missed` and `revert` may instead resolve to the `AUTO` row. On the revert path A38 prepares the batch (R1), drafts `offer.revert_and_refund` (`4E+Q`, CAPM → CFO) with this batch's `file_sha256` in its payload, and after a human CFO approves it and A36 fails the offering, calls `submitRefundBatch(batch_id, ctx, { revert_approval_id })`. A14 approves the `orders.refund.batch` request under its `AUTO` row only when `auto_condition = file_sha256_equals_approved` holds exactly: the referenced `offer.revert_and_refund` request is `approved` and its payload's batch hash equals this batch's `file_sha256`. The journals then post with the `AUTO` request's id, never with the revert approval's id. A batch whose hash differs (one more order funded after the revert was drafted) does not match, falls through to the `4E` row as A14 rules, and waits for a human CFO; it never executes under `AUTO`.
  - Loop A03.2 seeds both rows of `orders.refund.batch` (the `4E` row mapped to row 12 and the `AUTO` row tied to row 10). This node is the only drafter of the code.
- `executeRefundBatch` posts one `order.refund` journal per line (`offer_escrow` → `investor_cash`, fee share included, `external_ref` = `<batch id>:<order id>`, `approval_id` = the batch's own `orders.refund.batch` request id, under either row). In the same transaction as each journal, it reduces `escrow_held_cents` and moves the order to `refunded` (or `refund_state = refunded` for partial lines). A batch is `executed` only when every line has a journal. A line whose journal fails leaves the batch `executing` with the failing line named, never half-marked. Payout from `investor_cash` to the investor's bank, when asked for, is A39's.
- The one clock: A13's `orders.refund_sla`, opened per `refund_line` when its order enters `refund_pending` or `refund_state = pending`. `sla_due_at` is five business days later on A13's business-day calendar (Australia/Sydney). It raises Sev2 to FINA and CFO at `sla_due_at` and Sev1 at ten business days, and it stops when the line posts. A38 opens no refund clock of its own; its run-stall clocks stay A38's. The investor's timeline shows "Refunded A$2,395.92 · 3 Oct 2026" from the journal's `posted_at`.

**Settlement and confirmations**

- `settle(order_id, { allocation_id, file_sha256, register_entry_id, register_version_id, custody_op_id, recon_run_id })` (internal, called by A38 after its targeted reconciliation is clean) checks four things:
  1. `allocation_id` and `file_sha256` are the order's current **locked** version. A superseded or draft version gives `ORD_FILE_HASH_MISMATCH`.
  2. Through A18's "register first" query, an acknowledged entry exists for this investor on this vehicle, whose lot references the allocation line and carries at least `allocated_units`.
  3. Through `TokenDeliveryProvider`, the custody op is confirmed for exactly `allocated_units` to the order's `wallet_address`.
  4. Through `ReconStatusProvider`, `recon_run_id` is a clean run for the vehicle that covers this custody op.
  A missing register entry, delivery or clean run gives `ORD_SETTLE_REQUIRES_BOTH` naming which is missing. A units mismatch gives `ORD_SETTLE_UNITS_MISMATCH`. On success: `allocated → settled`, `settled_at`, the stored refs, the `allotment` confirmation record and `orders.settled`.
- G13 for the mint and the delivery is enforced where they happen: A38's `allocation.mint` (`6E+Q`) request bound in custody by A25/A28. `settle` records facts and does not decide an approval, so it is not part of this node's G13 criterion. Its guard is the locked-file hash check in step 1.
- Confirmation records are canonical JSON with sha256 and are immutable. The `order` kind is issued at `funded`, the `allotment` kind at `settled`. `GET /v1/me/orders/{id}/confirmations` lists them, and A47's statements route renders the PDF.

## Node-specific challenges (node QA)

- **Pro-rata that loses or invents a unit (money).** Hard cap 10,000 units, and twelve funded orders totalling 12,000 units with requested sizes chosen so that every `floor` leaves a fractional remainder. Σ allocated must be exactly 10,000. The leftover units must go one each by largest remainder, then earliest `funded_at`. No line may exceed its request. Σ (allocated + fee + refund) must equal Σ funded to the cent, with the fee on each line recomputed as `mulBp` on the allocated amount, not scaled from the original fee.
- **Holder cap through the back door (compliance, G07).** One investor places 300 units, then a second order of 300, on the same 10,000-unit offering at a 5 % cap. An associate of theirs already holds 100 units on the register.

  - The allocation must cap the pair to 400 combined, with the `capped_at_holder_cap` flag on the later order and a refund line for the excess.
  - A file that gives the pair more than 400 must be refused with `ORD_ALLOCATION_INVARIANT`.
- **Agent above the per-action cap (security, G22, money).** An investor's agent holds `INV.order.place`, a per-action cap of A$5,000, a daily cap of A$20,000 and a signing key. The investor's wallet holds A$12,000.
